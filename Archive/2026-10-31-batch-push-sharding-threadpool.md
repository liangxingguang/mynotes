# 第70篇：批量消息推送优化——百万级推送如何避免内存爆炸（分片 + 线程池 + 异步）

> 摘要：Java 架构实战笔记·消息与任务处理系列第 70 篇。从一次双十一 100 万条短信推送 OOM 事故出发，拆解百万级批量推送的三对核心矛盾（内存/性能/可靠性），给出一套可落地的 Java 方案：游标分片（每批 1000 条，避免深分页）+ 专用线程池（有界队列、按 IO 密集估算 10-50 线程）+ Redis 进度追踪 + 单条失败重试（3 次后入死信表）+ 任务 ID 去重与断点续跑。附踩坑清单（OOM、线程池耗尽、服务商限流、任务重复执行等 7 项）与按规模选型表。

## 核心要点

- **事故根因**：一次性把 100 万用户全量加载进 JVM（约数 GB）+ 串行逐条发送（50ms/条 → 13 小时+）+ 无进度追踪 + 无失败重试 + 无并发控制。
- **三对矛盾**：① 全量加载 vs 流式处理；② 串行 vs 并行（并行不能无限制，线程过多反而因上下文切换与资源竞争变慢）；③ 一次失败 vs 失败重试。
- **分片方式对比**：ID 范围（`BETWEEN`）/ 分页（`LIMIT offset,size`，深分页慢）/ **游标（`WHERE id > lastId LIMIT size`，本文采用，性能恒定）**/ 哈希（`MOD(id,N)`，适合并行互不干扰）。
- **线程池**：不能用 `commonPool()`（线程少，偏 CPU 型）、`newFixedThreadPool`（无界队列会 OOM）、`newCachedThreadPool`（线程数无上限）。必须自定义 `ThreadPoolExecutor` + 有界队列。
- **线程数估算**：IO 密集型 = CPU 核心数 × (1 + 等待时间/计算时间)；实际受短信服务商 QPS 限制，一般取 10-50。
- **异步与进度**：提交后台线程池立即返回 taskId；进度存 Redis（已处理/总数/成功/失败），每批处理完统一更新一次以减少 Redis 写。
- **可靠性设计**：单条失败记入失败列表稍后重试 → 重试超 3 次写死信表由定时任务兜底 → 整批失败记录状态支持断点续跑（记住 lastId）。
- **进阶优化**：分批提交避免大事务；Guava `RateLimiter.create(100)` 限流保护服务商；任务持久化到库防服务重启丢失；任务 ID 去重 + 分布式锁防重复点击。
- **规模选型**：100 万以内用游标分片+专用线程池+进度追踪；1000 万以上加消息队列异步解耦；实时性高则分片+多线程+限流。推荐参数：分片 1000-5000、池核心数 10-20、队列 1000、重试 3 次指数退避、进度每批更新。
- **七条踩坑**：OOM→游标分片；线程池耗尽→有界队列+合理拒绝策略；服务商限流→限流器+指数退避；进度不更新→每批写 Redis；任务重复执行→taskId 去重+分布式锁；分片查询占满连接池→控制分片大小及时释放；异步任务重启丢失→任务落库。

## 正文

**一、真实的生产事故**：电商平台双十一前给 100 万用户推送预售短信，点击"发送"后 10 分钟服务 OOM 崩溃。错误写法即一次性加载全部用户到内存。

**二、问题根源**：百万级推送的三个核心矛盾（见上方要点）。

**三、核心技术原理**：分片处理、线程池隔离、异步任务与进度追踪、失败重试与死信处理。

**四、整体架构与关键设计点**：用户点击批量推送 → 生成 taskId → 游标分片拉取（每批 1000）→ 专用线程池执行 → 每批统一更新 Redis 进度 → 单条失败重试、超限入死信表。

**五、完整实现**：`heyou-batch-message-push/` 项目结构，含 Maven 依赖、线程池配置、用户实体与 Mapper、进度服务、批量推送服务（核心）、推送结果对象、Controller、`application.yml` 配置、`user` 建表语句。

**六、进阶优化**：分批提交避免大事务；Guava RateLimiter 限流；`resumePush(taskId, lastId)` 断点续跑；`push_dead_letter` 死信表。

**七、踩坑指南**：见上方要点（7 项）。

**八、生产环境推荐**：按规模与实时性选型 + 参数推荐表。

**九、总结**：核心三句话——① 百万级推送的核心矛盾是内存和性能，必须游标分片+多线程；② 专用线程池+有界队列+合理拒绝策略是稳定性保障；③ 进度追踪+失败重试+死信队列是可靠性三大支柱。
