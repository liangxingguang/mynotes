# 拆解京东海博 AI-Native 落地保障：海博团队 AI 知识库能力建设

> 京东本地生活即时零售 SaaS"海博"（覆盖 780+ 商家、10 万+门店）的 AI 知识库实践。核心判断：AI 用不好的瓶颈不在模型、也不在运行时检索，而在知识生产——历史业务知识沉在人脑和零散文档里。解法是把"知识编译"前移到维护期，采纳 Google OKF 规范，用 Skill 从代码自动生成结构化互链 Markdown 知识树，织入研发流水线双向闭环；AB 实验显示带知识库需求分析快约 44%，并能发现只读代码触达不到的隐藏阻塞点。

## 核心要点

1. **问题定义**：大模型像"天才实习生"，每次会话都要重建业务认知，三大痛点——读不懂系统（百万行代码里乱猜）、影响面靠老人脑记、测试预期散落 PRD/聊天记录。
2. **选型结论**：向量 RAG / GraphRAG / Agentic Search 都只解决"运行时检索"，真正卡点是知识源头；借鉴 Karpathy LLM Wiki 与 Google Cloud **OKF 规范**（一概念一 md、YAML 元数据、index.md 渐进披露、log.md 变更可溯、字段缺失宽容降级），入库时即编译成互链 Markdown 树，运行时只做"导航+摘录"，精确定位到 `文件:行号`。
3. **三层知识架构**：底层"项目知识×领域知识矩阵"（横向每仓一个 catalog，纵向按业务时序缝合多仓链路，领域层只引用不复制）；中层角色化视图（测试/产品/运营）；上层 Skill 能力（跨仓依赖分析、需求拆解、测试拆解、impact 影响面分级、okf-knowledge-read）。
4. **历史代码初始化**：后端四个 Skill 建库（GitNexus 索引→flows 一接口一篇→chains 按共享表/MQ/task_type 聚合成业务链→跨项目 JSF/JMQ 依赖）；前端抽取页面操作/真实入参/权限/微主子应用通信；域层不读代码、零成本换视角派生。40 万行 WMS 仓生成约 1051 篇（584 HTTP+167 RPC+140 MQ+96 JOB 等），微前端生成约 530 篇。抽取铁律：只写代码可查证事实，查不到留白，绝不编造。
5. **Harness 知识引擎**：消费侧把需求定档→评审→规约→TRD→编码全链路的每步变成"读知识库定方向+按需索引代码补细节"，沟通产物作非正式过程资产；沉淀侧需求完成后 master 代码+过程产物经 `/distill-catalog` 蒸馏成业务知识、开发经验、人维经验三类，**人工确认后才合并**，形成"用中喂养"双向闭环；生命周期四步防腐：建档绑负责人→蒸馏反哺→冲突人工拍板→置信度过期治理（续期/降级/归档）。
6. **效果验证（AB 同提示词同代码仓）**：跨仓配置门禁类需求，A 组（知识库）需求分析 542 秒、读 8 篇知识+核对 3 个源码文件；B 组（仅代码）967 秒、翻 16 个文件，**快约 44%**；A 组还额外发现跨仓消费端缺重试、上线白名单门禁静默失败两个隐藏阻塞点，且来源可溯源、更省 token。
7. **测试实践**：用例即资产挂在领域知识的 `test-knowledge/cases/`（功能/接口/自动化三类），正向 PRD 生成用例、反向历史用例归档去重；自动化=用例原子+chains 编排+变量贯穿；code diff 经反向索引+链路扩散反查回归范围，输出必跑/应跑/建议跑三级。4 个业务组落地，采纳率 90%~100%、覆盖率最高 100%，测试从写用例转向审校补全。
8. **总结与方向**：一套 Context Engineering 理念（供给端质量决定 AI 上限）+三层架构+GitNexus 图谱与依赖分析两台引擎+Skill 建补用与四步治理闭环；下一步平台化、提升 contracts/chains 自动蒸馏置信度、从"人找知识"走向"知识找人"。

## 正文

### 一、背景

大模型接入研发后暴露三个反复痛点：AI 在百万行、几十个子仓里乱搜，给出"能跑但与架构不兼容"的实现；改字段/接口的影响面只有少数老人能判断；业务规则、历史约定、踩坑记录散落在 PRD、聊天记录和个人记忆里。目标是把知识固化为可搜索、可回溯、可传承、可被 AI 消费的组织资产，帮"天才实习生"快速建立业务认知。

### 二、技术选型：重点建设知识源头

对比向量 RAG（切块语义召回、接入成本低）、GraphRAG（实体关系检索）、Agentic Search（模型自主决定检索轮次）后，团队判断三者重心都在运行时检索，而实践卡点在知识生产：知识要结构化、绑定关联、精确定位、全生命周期维护。方案是把"知识编译"从运行时前移到维护期，与 Karpathy 的 LLM Wiki（模型平时把知识整理成持续维护的 Markdown）和 Google Cloud OKF（面向 AI Agent 的知识包装规范）思路一致。

OKF 三个关键点：一个概念一个 Markdown 文件（指标、表、接口、流程、领域模型原子化，标题/表格/代码块作语义锚点）；YAML 头部元数据（type 唯一必填，AI 不通读即可识别用途归属）；系统级保留文件 index.md（全局目录、渐进式披露、避免一次撑爆 token）与 log.md（变更可追溯）。并支持宽容消费：字段不全、死链不报错，自动降级为普通文档，存量资料可渐进改造。

### 三、整体架构：自底向上生长的三层结构

- **底层 项目知识×领域知识矩阵**：横向每个应用一个 `{app}-knowledge-catalog`，其中 `views/` 反向索引记录每张表、Redis-key、MQ-topic 的读写/生产消费方，是影响面分析的关键；纵向 `domain-knowledge/` 按业务时序把多仓接口用 MQ/JSF/调度缝成链路，一级域挂大链路、二级域挂细链路。横向看清"单系统怎么跑"，纵向看清"一次改动横扫哪几个系统"；领域层只引用不复制，项目知识变了只更新链接层。
- **中层 角色化知识**：同一份地基派生测试（规则/用例/历史坑）、产品（需求索引/功能说明/业务决策）、运营（规则/配置/SOP）视图。
- **上层 Skill 能力**：generate-cross-project-deps（跨仓依赖梳理）、project-analysis-tool（需求分析与规约生成）、qa-test-breakdown（测试场景拆解）、impact（d1/d2/d3 影响面分级）、okf-knowledge-read（全员知识读取，先摘要后下钻）。

### 四、知识初始化：分端分角色造知识

后端关注入口、链路、落点、影响四件事，用 build-knowledge-catalog（GitNexus 索引+扫全部对外接口，生成 flows/services/domain）、build-flow-chains（共享表/MQ topic/task_type 三类边聚合 chains）、generate-cross-project-deps 三个 Skill 建库；前端用 build-frontend-knowledge-catalog 产出 pages/，难点是回到每个调用点反推接口真实入参、列全按钮背后的校验与显示条件、理清微前端主子应用拆分通信；域层用 build-domain-overview 与 build-domain-flows 读 catalog 换视角派生业务流程与测试点，不重复读代码。

产出规模示例：40 万行的 yzt-erp-wms 仓沉淀约 1051 篇——flows 1001 篇（HTTP 584、RPC 167、MQ 消费 140、JOB 96、OpenAPI 14）、chains 41 篇、ADR 3 篇、领域模型 1 篇（约 59KB）、参考 4 篇；微前端 middleground-react-web 约 530 篇（接口 139、UI 组件 249、页面 101、架构流程 22）；聚合配送域知识库 93 篇（核心交易链路 25、基础服务配置 51、流程总览 17）。抽取规则：只写能从代码查证的事实，读不懂的业务语义标出交人工补全并抽样核对。

### 五、Harness 知识引擎

知识库的价值在织入研发流水线、全程既消费又沉淀。

- **消费侧**：编码前的业务定档→需求粗评→持续沟通→评审→研发规约→TRD→正式编码全链路，每步通过 Skill"读知识库定方向+按需索引代码补细节"；慧记、joyspace、对话、流程图等沟通产物作为非正式知识沉淀到 harness 工程临时项目目录。okf-knowledge-read 以意图为输入，经识别意图（业务概念/服务契约/数据流/架构决策）等 6 步 Pipeline 逐层收敛，产出按类型分组的精准上下文。
- **沉淀侧**：需求完成后有两个事实来源——master 代码（最终事实）与 harness 过程产物（规约、TRD、沟通记录），经 /distill-catalog 一起蒸馏成三类知识：业务/项目知识（规则、决策、影响面、术语、口径、边界）、项目开发经验（坑、根因、避坑清单、可复用脚本模板）、人维度经验（选型背景、评审反馈、协作约定）。蒸馏结果不直接落库，**人工确认、冲突由负责人拍板后才合并 master 知识分支**，保证每次更新可信可回溯；知识在"被用"的同时"被喂养"。
- **生命周期防腐**：①建档（扫代码/配置/文档生成基线，每条知识绑负责人+京 ME 通道）②蒸馏反哺（代码自动+过程产物主动）③冲突确认（人工合并）④过期治理（按知识置信度定期续期、部分失效降级、完全失效归档）。

**AB 效果验证**：两个子 Agent 用逐字一致的提示词、同一需求、同一代码仓、同一方法论并行做方案设计，唯一区别是 A 用知识库、B 只用代码。跨仓消费链路+配置门禁较多的需求上：A 组需求分析 542 秒（先建业务全貌再定向核对 3 个源码文件，8 篇结构化知识交叉验证，每条结论标注业务链/行号可溯源），B 组 967 秒（翻 16 个源码文件自行拼装语义，约 1.8 倍耗时）——**快约 44%**。更关键的是"更全"：A 组沿链路追到两个本仓代码难以触达的隐藏阻塞点——跨仓消费端缺自动重试、上线配置白名单门禁会静默失败。多需求重复验证，提速且不牺牲准确性，还更省 token。

### 六、测试实践：用例即资产，精准测试反查

针对用例散在各平台、与业务对不上、历史用例难复用三痛，在 `test-knowledge/` 下每个业务域挂角色知识与独立 cases/ 层（功能/接口/自动化框架三类）。用例挂靠具体业务域/子流程，覆盖度翻一层索引即可查；正向 /prd-diff-testcase 从 PRD+知识库生成用例（已有沉淀则取用、没有则回写），反向 /harvest-cases 把历史用例去重归档回库；自动化采用"用例原子+chains 编排+变量贯穿"，原子可复用、链路可组合。

精准测试：用例挂业务锚点与代码锚点（接口、文件/方法、表），code diff 一进来沿知识库反查受影响用例——只跑相关用例而非全量回归；靠 views 反向索引+chains 链路扩散覆盖"改 A 表影响 B 接口"的隐蔽影响面；输出必跑/应跑/建议跑三级优先级。已在海博田、订单履约、商品、base 四个业务组落地，代表记录如美食 mall 计费结算采纳率 95%/覆盖率 100%、银河 SOHO 自动门店回抛 100%/95%、蜜雪商品价格优化 100%/91%；测试同学从"从零写用例"转向"审校与补全"。结论：AI 用例天花板取决于知识能否覆盖全链路且持续保鲜。

### 七、总结与展望

最终沉淀：一套 Context Engineering 理念（供给端质量决定 AI 上限）、一个 AI Native 三层知识架构、GitNexus 图谱+依赖分析两台引擎、Skill 建/补/用+生命周期四步治理一个闭环、AB 实验一组对照。下一步三方向：平台化（团队工具升级为平台服务，进行中）、自动化（提升 contracts/chains 层自动蒸馏置信度，减少人工成本）、知识找人（在合适时机把相关知识主动推给需要的人）。
