# 不审代码，靠什么兜底

> 承接"代码审查退场"的讨论，文章回应两个尖锐反问：热路径里的隐蔽坑不审代码怎么防、线上出事人背锅没底气怎么办。结论：code review 只是手段，缺陷必然逃逸，质量底座应转向架构隔离与线上闭环——收缩输入边界、隔离爆炸半径、影子流量对比、持续巡检、秒级回滚，像工厂质检与神经网络保命机制那样兜底。

## 核心要点

- **逻辑全对也会出事**：热路径上每次请求重复编译正则/反序列化配置，单测全绿、逻辑无瑕，真实流量规模下 CPU 打满——这类"低负载无破绽、高负载拖垮服务"的坑，靠人眼 review 同样只是碰运气，并非流程可靠
- **AGENTS.md 软约束不可靠**：提示词里的软规矩时灵时不灵，几百行文档会被模型选择性失忆；性能基准往往事后才补，新仓库无法预知要埋哪几百道护栏
- **责权分离的底气问题**：机器干活人背锅，"读过每行源码"的旧绑定已失效；对标民航机长与芯片架构师，底气来自边界隔离、冗余、仪表盘与安全机制，而非逐行通读
- **部分代码本就无法审**：神经网络组件（推荐、风控、审核）占比将从九一滑向六四，逐行审权重不现实；它们靠影子流量评测、分片测试、运行时阈值、监控熔断活着
- **终极目标**：把未知缺陷的爆炸半径压到可控，把发现与修复闭环缩到最短；默认缺陷逃逸，靠架构隔离与线上闭环兜底
- **四件事落地**：①语言特性收缩到严格子集、依赖锁白名单、静态检查做成硬规则（先扎紧笼子）；②账单+指标每日巡检智能体（作者用 AWS CUR2 揪出缓存失效、读放大、无效写入等跨模块隐患）；③向工厂借三招——统计抽检校准流水线、安灯拉绳停线、蟑螂法则全库扫同类问题沉淀为 Linter/回归测试；④影子流量+小比例灰度+限流熔断秒级回滚，让合并变成可撤回的实验
- **分层演进**：新项目/AI 原生团队可直接重造流水线；债台高筑的老团队须先补齐护栏再逐步撤人工审查，不可一刀切
- **人的新角色**：底气来自亲手设计并验证的风险控制机制，而非"我看过所有代码"的幻觉——从手工作坊跨入系统工程
