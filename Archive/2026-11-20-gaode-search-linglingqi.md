> **摘要**：搜索凌凌漆（007）基于 Hermes Agent 基座建设，解决海量 VOC 工单排查提效与经验沉淀。选 Hermes 因其"开箱即用+记忆/技能反哺"机制契合业务，虽存单用户设计、单实例文件读写、SQLite 写入上限三处不匹配，策略是跟随社区演进、仅在框架问题影响业务时才干预。核心是按需取证（接上百数据源，每条证据可回溯请求参数/配置/日志）与自进化飞轮：候选生成→隔离（Git 分支）→审核→发布回滚，审核前不生效。强调错误经验混入知识库比没有经验更糟，人工审核不能沦为橡皮图章。已累计处理上万条用户提问。

## 核心要点

- **背景与定位**：搜索 VOC 需值班同学查清后答复，每个 Case 串起数据/召回/排序/Merger/实验/展示等节点，熟手 1-2 小时、新手 1-2 天，经验留在个人脑中。007 接 Case 后自查数据、走链路、给结论，覆盖主搜/车机/详情页/销售/广告等多业务线，截至 2026 年 10 月累计处理上万条提问。
- **Hermes Agent 基座**：Nous Research 开源，通过记忆（MEMORY.md/USER.md 跨会话检索）与技能（任务后写 Skill 文件、后续同类任务加载）反哺；选型时对比低代码平台（异步缺失/上下文裁剪靠 Prompt/多轮记忆无法跨会话）与 LangChain/LangGraph（抽象层级低需自行组装），选 Hermes 求开箱即用。
- **三处不匹配与策略**：Hermes 面向单用户需额外数据隔离、大量本地文件读写假设单实例（多机部署中间文件跨机丢失）、SQLite 大流量写入有上限；策略是跟随社区版本演进、优先吸收上游能力，仅框架问题明确影响业务时才在框架层干预（如升级 v0.12.0 启用 steer 模式解决连续第二条消息打断上次处理）。
- **按需取证**：归因效果取决于能否获得与当前请求对应、可核验、足够完整的证据；证据不足再强模型也靠猜，证据非越多越好（无关数据引噪声、超预算被截断、越权数据合规风险）。原则是能拿一手数据不用加工过的、用数据说话不靠猜；已接入上百数据源覆盖引擎/日志/在线离线存储/配置/实验/代码/业务接口/协作平台。
- **取证四步案例**：POI 搜不出来，四步收敛——queryPoiDetail 确认数据态正常、simulateAppHomeSearch 用真实参数复现拿召回列表、slim_trace 确认目标 POI 不在召回、spEngineDebug 确认召回/重排/final 各阶段均无位次；结论定位到召回链路，但不等于查明根因，建议"转引擎团队按此证据继续排查"而非"已定位根因"。
- **自进化四段链路**：候选生成（任务后异步提取经验，写 Git 分支）→隔离（运行版只从主分支拉取，未合并候选对线上不可见）→审核（定期 Review 差分，判断可泛化性/证据充分性/是否带偏决策）→发布回滚（合并即生效、可追溯、异常整体回滚上一 tag）；同主题候选先聚类去重。
- **一正一反案例**：正——POI ID 格式陷阱（用户把 B0 写成 BO），经验沉淀成结构化 Skill，审核合并后为同类问题提供先校验 ID 格式的线索（是否适用仍结合本次输入确认）；反——模拟 APP 搜索工具失败时 Agent 改用浏览器访问 amap.com 拿 PC 端结果判断，但 App 与 PC 搜索逻辑完全不同、PC 结果不能作依据，该经验在人工审核被取消。
- **经验治理原则**：错误经验混入知识库污染之后所有类似决策，比没有经验更糟；人工审核不能沦为橡皮图章，自动化替掉重复劳动但替不掉关键业务判断。工单评论与流转记录先作线索，须结合最终处理结果与证据核验后才进经验候选。
- **知识库路径**：007 不走自上而下收集文档切片向量化，而是自下而上以每日自进化经验为补充；经验有两态（候选池→审核发布），已发布经验复用时仍须按当前版本与数据重新核验，不替代权威业务规则；特点是新鲜、有场景（未被调用不入集）、有覆盖。
- **从排查到处置与系统机会**：单点问题从"查到"到授权范围内直接发起处置（风控解封/标签权重调整工单，但提交只证明动作发起不证明问题解决）；共性问题定期聚类归因提炼产品优化点，按四阶段跟踪（已形成建议→已创建需求→已开发→已上线并验证），仅第四段计入有效产出。
- **底座复用**：除 Case 排查外，自发用于新人熟悉业务（带真实代码位置/配置出处/数据通道的解释）、产品逻辑追溯（从产品逻辑追到引入提交与受控参数）、销售提效（辅助排查广告投不出去因素）；三场景提问方式与输出形态不同，复用同一套数据接入与业务 Skill。
