# JVM 内存排查实战：用 GC 日志、JFR 和堆转储串起证据链

> 以 Doris FE（HotSpot JDK 17、G1）排查实践为素材，总结"GC 日志 + JFR + 堆转储"三件套的 JVM 内存排查方法论：先分清"内存高"的三种病灶（分配过速、长期持有、堆外增长）与五个易混的量，再用三份证据分别回答时间、来源、结构三个问题，交叉印证形成可复核的因果链。核心结论：GC 日志判断"病"的性质，JFR 找到病灶入口，堆转储确认病灶结构；采集前想清代价、下结论前写明验收条件。

## 核心要点

- **先定性再动手**：内存告警背后是三种病——分配过速（GC 频繁、冲高回落震荡）、长期持有（狭义泄漏，GC 收不走被持有的对象）、堆外增长（堆内分析无解，须走 NMT/smaps/分配器统计）。第一步是分清涨的是哪个"量"（分配速率/used/committed/retained/RSS），先判断增长属地再选工具。
- **三件套各答一个问题**：GC 日志答"回收后还剩多少、回收能力是否退化"（看回收后低位而非峰值）；JFR 答"字节从哪条代码路径来"（线程组→业务入口→分配栈→对象类型逐层收敛）；堆转储答"对象被谁持有"（直方图→支配树→GC Roots 路径）。
- **先对齐再分析**：确认资料归属（以启动记录/文件头为准，文件名不算证据）；用 JFR `gcId` 与 GC 日志 `GC(n)` 对齐时间线；堆转储标注语境，跨快照用稳定标识，不拿对象地址匹配。
- **GC 日志看低位**：低位持续抬高才说明有东西收不走；暂停要算两笔账（频率、总占比与单次分布分开），"回收周期数≠停顿次数"；尾延迟单独看最大暂停。
- **JFR 两个案例**：85 个 `Object[]` 采样折合约 47.6 GiB 引用区，与 GC 日志 Humongous 区域回落 50.2 GiB 量级互证；深复制改流式后路径分配从 502.35 GiB 降至 16.50 GiB，但整机分配速率反升——路径级收益、任务存留、全局 GC 表现要分开验收。
- **堆转储找持有者**：649 万条会话 ID 被静态集合持有，根因是内部上下文关闭时漏掉注销；堆转储确认持有者、GC 日志给趋势、源码确认生命周期缺口，三者拼出因果链。
- **采集按影响分级**：优先用既有监控/日志/持续 JFR；jcmd 影响从低（VM.flags、/proc）到高（GC.heap_dump，伴随 Full GC）分级选工具，把采集命令与耗时记入时间线。
- **验证闭环**：修复前写明预期，验收同时覆盖目标路径与服务指标（分配优化与性能回退可同时成立），按固定字段记录，让结论可复核、可被推翻。
