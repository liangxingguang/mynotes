# 【新文导读】详解IM消息已读未读功能的高并发技术实现

> 52im.net 的公众号导读文：已读未读不是"小红点"UI 功能，而是横跨长连接、消息顺序、状态一致性、在线路由与高并发存储的系统工程。导读完整拆解生产级单聊已读未读架构：按会话维护已读游标、解耦长连接与状态计算、游标推进替代逐条更新、Lua 保证原子幂等、未读数缓存非事实源、精准投递与容灾收敛。

## 核心要点

1. **生产级目标**：正确性优先（已读位置单调递增不回退）、顺序性可控、写路径异步化+热点状态缓存化、网关无状态可水平扩展、故障下可收敛（最终一致但保证最终正确）。
2. **已读语义选型**：单聊优先采用"会话级已读游标"——每个会话对每个参与人只维护一个 `last_read_message_seq`，序号 ≤ 游标即视为已读，客户端只上报读到哪条而非逐条 ACK；状态量从消息数降到会话数，天然支持 ACK 合并、更新幂等，适配 MQ 重试。
3. **角色解耦**：WebSocket 网关只做快速收包/轻量校验/异步投递/快速回写，消息写库、未读计算、回执推送拆为独立角色；网关承担过多业务会同时失去连接承载力、扩容弹性与故障隔离。
4. **数据模型**：`im_conversation`（msg_seq 会话内单调递增、client_msg_id 发送幂等、uk_conv_seq 保证序号唯一）+ `im_conversation_read_cursor` 已读游标表；分工原则——Redis 负责快、MySQL 负责准、Kafka 负责解耦与削峰，Redis 只做高频读写缓存、不当最终事实源。
5. **关键原理**："游标推进"比"逐条更新"更稳；已读推进用 Lua 保证原子性与幂等；推送不做全网关广播，尽量精准投递；未读数缓存必须有修正机制。
6. **落地视角**：以电商客服单聊为真实场景，覆盖高并发优化（瓶颈通常不在直觉处）、故障时状态回收、容器化云原生部署，以及从 1 万连接到百万在线的架构演进路径；全文详版见 52im.net 社区帖（thread-4929）。

导读前半部分已展开的核心论述：

- **难点升级**：生产环境面临分布式连接（发送方与接收方在不同网关）、消息异步流转（写库/推送/ACK/未读更新不在同一事务）、客户端乱序上报、系统须抗重复（Kafka 重投、客户端重发、网关重连）与可恢复（节点宕机、Redis 抖动、消费回溯不能打乱状态）。
- **网关职责边界**：网关第一职责是快速收包、轻量校验、异步投递、快速回写；复杂事务、多表查询、长时间阻塞、高冲突状态更新均不应落在网关。
- **Redis 状态模型**：只承担在线路由等高频读写缓存状态，最终事实源在 MySQL。
