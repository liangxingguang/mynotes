# AI Coding 交付四环节（意图/上下文/评审/评估）

## Definition（定义）

把一次 AI Coding 交付拆成**意图、上下文、评审、评估**四个相互衔接的环节：意图环节把需求写成可验收的规格，上下文环节给 Agent 可靠且有效的信息，评审环节让每个结论能追溯到具体变更，评估环节通过持续比较判断改进是否有效。前三个环节帮助完成当前任务，评估把多次任务中的问题带回系统改进。

## Why It Matters（为什么重要）

代码生成提速之后，需求里没写清的约束、跨仓依赖和验证环境的缺口，会直接影响整个任务能否交付。四环节把"让 Agent 写代码"扩展为"让一次交付可验收、可追溯、可改进"，把工程投入放在规格、上下文、验证和评估上，而不是生成速度本身。

## Core Characteristics（核心特征）

1. **每个环节有明确的关键问题与交付产物**：意图问"目标、范围和验收条件是否明确"，交付可执行规格、异常分支和待确认事项；上下文问"代码、知识和日志是否相关且有效"，交付带来源和适用范围的上下文；评审问"当前变更是否达到下一阶段要求"，交付变更说明、验证结果和未验证项；评估问"改进是否持续提升任务质量与效率"，交付可比较的任务结果、失败原因和改进项。
2. **意图环节把隐含要求显式化**：兼容、降级和异常分支尽量转成可检查的条件；规格有效性以能否减少反复澄清、提前暴露冲突、支撑验收为检验标准。
3. **上下文环节强调信息可核验**：知识库存稳定的架构、规则与接口约定，任务记忆存具体经验、纠正与偏好；两类信息都要标明来源、适用范围和更新时间，系统变化后重新核验。
4. **评审环节连接需求、实现与验证**：评审者应能从变更说明追溯到代码差异、工具调用、测试和真机结果；差异摘要、规则检查、验证结果整理可交 Agent，业务语义、架构取舍、重要风险和线上发布由人判断。
5. **评估环节分离"修好这次"与"减少下次出错"**：比较改进时固定代码快照、模型版本和执行条件，整理经验的任务与检验效果的任务分开，经验被后续任务实际调用才算复用。

## Structure（结构）

| 环节 | 关键问题 | 交付产物 |
| --- | --- | --- |
| 意图 | 目标、范围和验收条件是否明确 | 可执行规格、异常分支和待确认事项 |
| 上下文 | 代码、知识和日志是否相关且有效 | 带有来源和适用范围的上下文 |
| 评审 | 当前变更是否达到下一阶段要求 | 变更说明、验证结果和未验证项 |
| 评估 | 改进是否持续提升任务质量与效率 | 可比较的任务结果、失败原因和改进项 |

## How It Works（运作方式）

1. **意图**：在需求基础上产出可执行规格——业务目标、任务范围、关键约束、验收方式；影响目标和范围的问题由负责人先判断，兼容、降级、异常分支转成可检查条件。需求洞察 Agent 可参与问题排查与需求文档辅助，需求价值判断与需求评审仍待完善。
2. **上下文**：Agent 回到代码中核对设计判断，改造已有功能先检索现有实现再定复用与修改路径；检索围绕当前任务选择相关代码、知识和日志并保留关键来源，全部塞入上下文会增加无关信息、让错误更难追踪。检索覆盖不足时，Agent 应说明缺什么信息、如何验证，必要时转交人工。
3. **评审**：把原先承诺、实际改动、已验证结果与未满足条件连起来；多 Agent 或多模型交叉评审补充视角，结论仍落到可检查的代码和运行结果上。失败与修复记录（首次为什么失败、改了什么、复检覆盖了什么）同样随最终结果交给评审者。
4. **评估**：会话分析、工单反馈与回访帮助定位问题环节；评估把反馈与实际解决结果对应，纳入失败、返工和人工接续的任务，不以会话结束或用户满意代替问题解决。

## Relationships（关系）

### Related Concepts（相关概念）

- [[ai-native-sdlc|AI 原生 SDLC]]：制品提交链驱动的交付闭环，与四环节互补——前者讲流程与控制模型，四环节讲工程组织与评估口径。
- [[ai-coding-evidence-boundary|证据边界驱动的 AI Coding]]：同为 AI Coding 落地的方法论，四环节的"评审/评估"与之证据边界互证。

### Dependencies（依赖项）

- 交付质量依赖真实的验证环境（冒烟测试、真机验证、云真机）与可追溯的变更记录。

### Distinctions（区分）

- 与 [[ai-native-sdlc|AI 原生 SDLC]] 不同：四环节不是阶段式流程规定，而是围绕"一次交付该有哪些产物与核对点"的组织框架，强调评估环节把经验回流系统。

## Evolution（演进）

- 2026-11-20：高德搜广推团队在 Agent Teams 系列总纲篇提出，附四仓协同、双仓改造（ATDD 落地）、96 模块真机验证（9 PASS/47 FAIL/40 BLOCKED）三次实际交付作为各环节的印证。

## Open Questions（开放问题）

- 四环节在非跨仓、单人任务中的适用程度：原文以团队跨仓交付为背景，单仓库小任务可只取意图与评审。
- 评估环节的量化基线如何建立：原文指出回答团队整体提效多少，还需在相近任务类型与难度下持续比较。
