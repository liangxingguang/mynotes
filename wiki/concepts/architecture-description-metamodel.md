# ISO 42010 架构概念元模型

## Definition（定义）

ISO/IEC/IEEE 42010 的架构概念关系图（元模型）把架构要素分为左右两侧：左侧「人与诉求」——关注对象、环境、干系人、干系人立场、关注点；右侧「视图与设计」——视点、视图、架构描述、架构。四条逻辑线顺序绝对不能颠倒。其核心教训：架构的起点从来不是结构，而是一群立场迥异的人、一堆互相冲突的诉求，以及把所有分歧收敛成一套全局一致方案的全过程。

## Why It Matters（为什么重要）

- 日常工作里「架构」几乎被简化成三件事：画框图/分层图/部署图、敲定技术栈与中间件、填标准化文档；但工程落地时图纸严丝合缝一到联调就矛盾、分层清晰迭代一次要动多层、各团队都说自己被满足但整合时没一方觉得合理（信源）。
- 问题根源不是画图能力不足，而是把「系统结构」当成了「系统架构」——只会拆解结构产出的只是图纸，能平衡多方冲突才称得上真正的架构（信源论断）。

## Core Characteristics（核心特征）

1. **左侧五要素**：关注对象（要开发的目标：整车/域控制器/软件系统）、环境（外部约束：法规/外部对接系统/工况/寿命，硬约束来源）、干系人（功能开发/功能安全/测试/成本控制/项目管理/终端用户/合规审核）、干系人立场（冲突来自立场而非个人——换人不换岗位，矛盾依然存在）、关注点（立场催生的诉求，标准原文标注「这件事对该干系人至关重要」）。
2. **右侧四要素**：视点（一套固定的观察规则——从哪个维度切入、含哪些元素、表达哪些信息，是画图必须遵守的规范而非图纸本身）、视图（严格按视点规范绘制的模型：逻辑视图/物理部署视图/时序交互视图）、架构描述（所有视图、模型、设计文档的集合）、架构（视图与文档想要表达的系统内在本质）。
3. **四条核心逻辑线（顺序绝对不能颠倒）**：①视点框定关注点（明确这类视图解决哪类问题）②视点约束视图（绘图必须遵循规则）③视图用来回应关注点（视图存在的唯一价值——无法回应任何一方核心诉求的图是没有工程价值的废图）④多张视图整合为架构描述，最终表达系统架构。
4. **架构描述 ≠ 架构，就像地图 ≠ 真实疆域**：架构是系统与生俱来的内在属性、看不见摸不着；架构描述（图纸+文档）只是呈现载体。绝大多数架构争吵本质是混淆二者——反复争论图纸画得好不好，却很少讨论架构方案本身是否合理。
5. **三个极易漏掉的节点**：环境（只考虑内部功能设计、上线才发现不满足法规，方案被迫推倒重来）、立场（把矛盾归咎于个人、以为换掉对接人就能解决）、方面（只用一张视图覆盖全部系统、把局部侧面当成整体全貌）。**两条常被忽略的连线**：干系人关注架构本身（架构评审必须全员到场——不是来听汇报，而是确认自己的诉求有没有被处理）、视图只对应单一维度（不存在一张总图覆盖全部设计，多视图建模是大型系统的必然选择）。
6. **小系统不用架构，大系统必须架构**：单人开发日志脚本目标单一、约束极少，只解决「功能能不能实现」；团队扩充到三人，接口谁定义/异常谁兜底/日志格式如何统一立刻浮现，属缺少统一约定。「普通开发解决功能实现问题，架构师解决系统共存问题。」
7. **车载域控五大团队诉求天生对立**：功能团队（插件化动态下发、缩短迭代周期）vs 安全团队（出厂前完成认证、运行阶段禁止变更）是典型死结；性能团队（控制环路 10 ms 周期稳定、拒绝多层转发）vs 成本团队（共用芯片、单颗 SOC 省几十元、批量省千万级）。**冲突永远无法彻底消除**；做好架构管控的局面是分层解耦切断强耦合点、清晰边界划分权责、优先级决策明确取舍规则——矛盾不消失但变得可控、可解释、可追溯。
8. **架构师核心价值四件事（全程与画图/编码无关）**：①完整识别所有干系人（漏掉法务出境合规要求→整套架构推倒重来）②精准定位核心冲突点（找「A 的诉求恰好是 B 的红线」，两个极端：漏掉真冲突或把所有分歧当矛盾不敢取舍）③采用多视图拆分设计（功能团队逻辑视图、硬件团队物理部署视图、测试团队时序视图）④全局权衡形成收敛决策（把取舍理由完整记录下来）。
9. **ADR（架构决策记录）**：每条写清四项——当前面临的问题、备选技术方案、最终选型、做出选择的核心原因；对应 ISO 42010 的架构原理（rationale）。没有记录则三年后没人说清当初为什么放弃另一种方案，同样的争论反复上演。
10. **四道校验题**：①所有干系人是否全部覆盖 ②每张视图对应哪一方的核心关注点（答不上来就是自娱自乐）③多视图之间能否互相对齐（逻辑层组件在物理部署里找不到载体=设计没收敛到位）④关键冲突的取舍理由是否书面留存（没有文字记录等于没有真正做出决策）。

## Structure（结构）

元模型左右双结构（信源归纳）：

左侧（人与诉求）：关注对象 → 环境 → 干系人 → 干系人立场 → 关注点。
右侧（视图与设计）：视点 → 视图 → 架构描述 → 架构。
连接逻辑：关注点 ← 视点框定/约束 → 视图回应关注点 → 多视图整合为架构描述 → 表达架构。

## How It Works（运作方式）

架构师的工作不是消灭矛盾，而是把取舍形成书面决策（ADR），做到有据可依、全程可复核；架构从不追求单点技术最优，只追求全局利益平衡（信源）。收尾：架构的皮囊是分层结构，灵魂是权衡与归一；读懂 42010 这张元模型图才算真正入门架构思维（信源）。
