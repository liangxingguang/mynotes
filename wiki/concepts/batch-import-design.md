# B端批量导入设计（Batch Import Design for B-side Systems）

## Definition（定义）

B 端系统中"用户通过 Excel 等文件批量写入业务数据"的功能模块的工程设计方法。其本质不是"上传+入库"，而是**数据治理**：批量导入的终点不是"导进去"，而是"能处理、能追踪、能重来"。三大支柱：①后端业务校验（三层校验模型）②异步任务+分片处理（性能与进度）③错误报告+部分成功策略（异常可定位可重试）。

## Why It Matters（为什么重要）

批量导入"看似很小、实则很难"：只看到"上传"没看到"数据治理"，上线后会被业务、用户支持、研发三方同时质问。B 端业务一个 Excel 几千行、几万行很常见，同步导入会触发网关超时、数据库长事务、体验崩塌、内存溢出四类故障；而校验缺失会让脏数据直接落库（CRM 撞单、EHR 工号重复、ERP 停用物料生成单据），事后很难冲销。

## Core Characteristics（核心特征）

1. **前端校验 ≠ 业务校验**：前端/模板只处理格式（手机号 11 位、日期合法、必填），处理不了业务规则（客户是否已存在、物料编码是否启用、供应商账户与信用代码是否匹配）；业务校验（后端三层模型）才是真正的防线。
2. **三层校验模型**：字段格式层（必填/长度/类型/枚举/正则/日期范围/数值区间）→业务实体层（独特性/存在性/状态/版本四类校验）→跨单据规则层（金额一致性/状态流转合法/明细汇总等于头表总额/上下级关系不成环）；每一层失败给出不同错误码和错误信息。
3. **校验规则配置化**：规则编码、描述、类型、执行顺序、错误提示、是否阻断做成可复用组件——业务方新增规则不用改前后端，直接配置生效；这是从"一次功能"到"平台能力"的分水岭。
4. **异步任务 + 分片处理 + 进度可感知**：上传落盘→创建任务→异步 Worker 流式解析（1000-2000 行/片）→每片独立事务写入→进度更新→完成通知；避免同步接口的网关超时、长事务、内存溢出。
5. **任务状态机含"部分成功"终态**：待处理→处理中→部分成功→全部成功→全部失败→已取消；"部分成功"是 B 端导入常态，要让用户清楚知道哪些成功、哪些失败。
6. **错误报告 7 要素 + 三档错误级别**：行号、业务主键、错误字段、错误级别、错误码、中文原因、建议处理方式；致命（整单失败不写入）/行级（该行跳过）/警告（可写入需留意）；错误码表统一维护（E1001/E2003/E3002/E4001）。
7. **部分成功策略**：不追求"全有或全无"；明确告知成功/失败行数并提供失败重试入口；重试只重试失败行、过滤已成功行（幂等键=任务 ID+行号）。

## Structure（结构）

三层校验模型：

| 层 | 校验内容 | 示例 |
|---|---|---|
| 字段格式层 | 必填、长度、类型、枚举、正则、日期范围、数值区间 | 手机号格式、email 格式 |
| 业务实体层 | 独特性（工号/客户编码/合同号）、存在性（部门/物料/用户）、状态（启用/停用/冻结）、版本（当前生效版本） | 手机号/email 是否已被占用、部门 ID 是否存在 |
| 跨单据规则层 | 单据间金额一致性、流程状态流转合法、明细汇总=头表总额、上下级关系不成环 | 同一用户不能既是审批人又是申请人 |

异步导入六步流水线：上传落盘（对象存储，返回文件标识）→创建任务（待处理，写任务表）→异步 Worker 解析（流式，1000-2000 行/片）→分片写入（每片独立事务）→进度更新（百分比/成功行数/失败行数）→完成通知（错误报告文件，站内信/email）。

任务状态机 6 态：待处理 → 处理中 → 部分成功 → 全部成功 → 全部失败 → 已取消。

错误级别三档：

| 级别 | 触发条件 | 行为 |
|---|---|---|
| 致命 | 文件格式错误、表头缺失、必填全空 | 整单失败，不写入数据 |
| 行级 | 某行字段不合法或业务规则不通过 | 该行跳过，其他行正常写入 |
| 警告 | 可写入但需业务留意（如保质期<30 天） | 正常写入，提示留意 |

技术要点：文件上限明确（20MB/50 万行）；批量插入单批 500-1000 条；幂等（任务 ID+行号）；并发控制（同一组织同一导入类型只允许一个"处理中"任务）。

## How It Works（运作方式）

以业务中台统一导入中心为成熟形态：各业务线（订单、商品、客户、库存）接入统一导入服务，前端只需上传文件并订阅任务进度，后端统一调度、统一校验、统一错误报告——避免每个业务线各自实现一套导入。财务中台凭证案例：导入 1000 条凭证（30 条借贷不平、20 条科目停用）→返回成功 950 失败 50 并生成失败行 Excel→会计修正后只上传失败行文件→系统自动匹配原任务完成补充导入，体验从"崩溃"变成"可控"。

## Relationships（关系）

### Related Concepts（相关概念）

- [[idempotency-design|幂等设计]]：导入幂等键 = 任务 ID+行号；部分成功策略的"重试仅重失败行"依赖幂等过滤已成功行——重试与幂等共生。
- [[durable-execution|持久执行]]：异步导入的任务表+状态机+分片独立事务是"状态推进与副作用记录原子提交"在导入领域的落地；每片独立事务避免长事务。
- [[async-task-system-design|异步任务系统设计（信源）]]：同源互证——其任务表/状态机/进度更新/幂等键 (task_id, row_number) 与本概念完全对应，本信源补上 B 端特有的"部分成功"终态。

### Distinctions（区分）

- 与 [[mysql-bulk-import|MySQL 大批量导入优化]] 的不同：后者是数据库层吞吐优化（rewriteBatchedStatements/LOAD DATA/先灌后建索引/分片并行，面向十亿行级离线灌入）；本概念是产品层数据治理（校验/异步任务/错误报告/部分成功，面向 B 端日常业务导入）。两层问题常被混为一谈——"导得快"（DB 层）与"导得对、导得明白"（产品层）是不同问题。
- 与 [[batch-message-push|批量消息推送]] 的不同：推送是出站渠道扇出（百万级下发），导入是入站数据治理（外部文件进入内部系统），方向与风险面相反。

## Open Questions（开放问题）

- 百万行以上导入在"产品层异步框架"与"数据库层批量写优化"之间的职责切分？现有信源只在产品层给到 20MB/50 万行上限，未展开更大体量的协同方案。
- 错误码表的跨系统统一（不同业务线导入共用一套错误码 vs 各自维护）如何治理？信源只说"统一维护"，未给归属规则。
