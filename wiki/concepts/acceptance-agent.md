# 验收 Agent（AI 生成代码的验收）

## Definition（定义）

验收 Agent 是 AI 原生研发链路中位于代码生成之后的 Agent：不靠静态 Review 判断代码，而是真实调用接口，并结合接口返回、业务状态、日志、DB 等实际证据，逐层验证 AI 生成的代码是否真正实现了需求，输出分层验收结论。在 OPT 平台的实践中，后端验收 Agent 的执行内核是 **api-acceptance Skill**（把相对固定的验收步骤沉淀为可复用 Skill），验收不通过则打回代码实现修复后重验。

## Why It Matters（为什么重要）

AI 代码生成速度远大于人工需求验收速度：接口返回 200 只说明当前参数下完成一次调用，需求逻辑是否正确、边界条件是否覆盖、老数据是否兼容、异步任务是否生效、日志与 DB 状态是否符合预期，仍需逐层验证。仅靠静态 Review 难以确认 AI 生成的代码是否满足需求，验收由此成为需求交付的新瓶颈。验收 Agent 把「判断代码能否采纳」从人工重复劳动转为带证据链的自动化初验 + 人最终判断。

## Core Characteristics（核心特征）

1. **五阶段主流程**：变更接口分析（从 git diff 反推验收范围）→ 编译发布与接口验证（确认「能否验」）→ Gherkin 测试（设计并执行「怎么验」）→ TAPD 预测试（补充用例来源）→ 验收结果输出（用证据链回答「怎么判」）。
2. **硬阻塞与软失败二分**：硬阻塞保证 Agent 不越过必要的人机确认与环境前提；软失败让 Agent 在发布失败、spec 缺失、日志不可用等受限情况下继续完成能做的部分（变更分析、场景生成、静态 Review、风险标注），并诚实标注 WARN/SKIP/无法判定。核心原则：能验证的尽量验证，不能验证的诚实标注，不把受限项伪装成通过。
3. **Gherkin 人工确认硬阻塞点**：Gherkin 场景确认报告必须人工确认后才进入真实执行——Gherkin 承载的是需求预期，预期错了报告反而更有迷惑性；确认时重点看前置条件、接口选择、关键参数和 Then 预期。
4. **L1-L4 多层证据链**：避免「接口返回 code=0 就写通过」的表面成功陷阱；场景结果分层表达，最终结论分四档，报告以 HTML 呈现供人阅读与决策。
5. **人机协同的最终判断**：Leader Agent 调度、各环节 Agent 执行；人负责确认需求预期、方案与最终交付结论。AI 帮助人基于更充分的证据做决策，不替人承担交付责任。

## Structure（结构）

五阶段主流程（据 OPT 平台 api-acceptance Skill）：

| 阶段 | 回答的问题 | 关键动作 | 产出 |
|---|---|---|---|
| 1 变更接口分析 | 验哪里 | 基于 git diff、需求描述、分支信息、接口定义识别变更文件/函数、调用链、入口接口；标注三类兼容性风险 | 测试接口列表、变更接口分析报告 |
| 2 编译发布与接口验证 | 能否验 | 确认服务可编译发布、环境可达、接口可用最小参数调通、契约一致；环境优先级：Agent 专用隔离环境 > 个人开发环境 > 公共测试环境 | 接口连通性与契约一致性验证 |
| 3 Gherkin 测试 | 怎么验 | 用 Given-When-Then 拆场景（覆盖正常/异常/边界）；场景确认报告人工确认后执行；参数构造真实数据优先、LLM 推理兜底；依赖业务测试知识库 | 可执行接口场景与执行结果 |
| 4 TAPD 预测试 | 补充用例 | 读取 TAPD 关联用例，分类筛选适合后端独立验证的用例 | 补充需求路径与边界场景 |
| 5 验收结果输出 | 怎么判 | L1-L4 多层证据链；避免 code=0 表面成功；结论分四档 | HTML 验收报告 |

## How It Works（运作方式）

- **变更接口分析**：需求影响不总停留在改动文件本身——字段类型变化、枚举范围收紧、错误码语义调整都可能波及已有调用方与边界场景，故从代码变更反推验收范围；该阶段决定验收方向而非执行速度。
- **接口验证先行**：接口连通性验证通过不代表需求逻辑已验证，但标志着验收从「准备阶段」进入「业务验证阶段」。
- **Gherkin 校正流程**：若只让 Agent 按接口定义自行执行，容易漏掉业务预期或按错误预期跑出看似完整的报告，故引入 Gherkin 与人工确认做校正；每个 Scenario 映射为接口调用序列，构造业务与鉴权参数后执行。
- **证据链判断**：常见「表面成功」四情形——字段含义不符需求、写接口成功但 DB 状态未变、主接口成功但下游失败、异步消息未消费或日志链路显示副作用未发生；多层证据（接口返回、业务状态、链路日志、静态 Review 兜底）联合给出结论。
- **打回与复验**：验收不通过将问题打回代码实现，修复后重新验收；问题发现前置到开发阶段。

## Relationships（关系）

### Related Concepts（相关概念）

- [[ai-native-sdlc|AI 原生 SDLC]]：验收 Agent 是 AI 原生 SDLC 中「测试/验证」环节的工程实例——瓶颈从构建转移到验证，验收 Agent 用真实执行与证据链补上验证侧的自动化。
- [[artifact-verification-delivery|产物核验与独立交付]]：两者同向——都反对以单一信号（模型概括 / 接口返回 code=0）判定通过，主张多源事实核验与诚实标注未知。
- [[ai-coding-evidence-boundary|证据边界驱动的 AI Coding]]：证据分层互补——美团实践的「静态推理/构建+单测/集成测试/运行时日志」四层与本文 L1-L4 多层证据链同构，均以多层证据替代单点信号。

### Dependencies（依赖项）

- 可执行的验证环境与发布通道（编译发布、接口可达）——阶段 2 的前提。
- 业务测试知识库（鉴权说明、测试账号、数据构造方法、业务字段知识）——阶段 3 参数构造与减少 WARN/SKIP 的前提。
- 需求用例来源（TAPD 关联用例）——阶段 4 的补充输入。

### Distinctions（区分）

- 与静态 Review 的区分：静态 Review 只看代码，无法确认需求逻辑、边界条件、老数据兼容、异步任务与 DB 状态；验收 Agent 以真实执行的多层证据为准。
- 与 [[artifact-verification-delivery|产物核验与独立交付]] 的区分：产物核验是单次 Agent 任务内的「核对与移交」控制回路（核验输入三组成、交付入口独立）；本概念是需求交付链路中位于编码之后的验收环节，面向接口级真实执行与证据链判断。
