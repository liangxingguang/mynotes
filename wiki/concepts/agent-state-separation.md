# Agent 状态分离（执行状态/操作状态/产物核验）

## Definition（定义）

Agent 执行系统的状态模型设计判断：单一「成功/失败」字段无法同时表达「工作停在哪里、动作是否发生、产物满足了哪些条件」三类独立事实，因此把执行状态（执行状态）、操作状态（操作事实）与产物核验（产物核验）分别记录、各归模块所有，恢复决策按状态组合作出而非按单一状态字段。源自 Codex 桌面客户端 Harness 架构实践（微信公众号「Codex 桌面客户端开发」系列第六篇）。

## Why It Matters（为什么重要）

「模型回复顺利结束但产物内容不合格」与「工具完成写入但执行记录未收尾」是两种相互独立的失败，需要不同的修复动作。压成单一状态后，恢复只能从头重跑或让模型凭聊天历史猜测进度；统一写成「完成」则可能交付不合格成果。状态分离后，恢复可以处理局部缺口（补交付、限定返修、查询回执、保留等待）而不必丢弃全部进度。

## Core Characteristics（核心特征）

1. **三态各有归属**：执行状态由任务控制模块记录（有效要求与进度）、操作状态由操作记录模块记录（实际动作与回执）、产物核验由产物记录模块记录（文件及检查结果）；状态变化必须经各模块提交接口——工具执行器只能提交「本次写入」的事实，核验器只能提交检查缺口，都不能自行宣布任务完成。
2. **状态组合驱动恢复动作**：不穷举所有组合，恢复入口做决定时读取相关记录——执行中断且文件已核对→保留文件、检查剩余步骤；执行结束且产物未通过检查→限定范围返修或返回缺口；外部请求已发出结果不明→查询回执、暂不重复写入；部分成果完成仍在等用户→展示已有成果、保留等待状态。
3. **流结束 ≠ 任务终态**：`[DONE]` 或 token 用量只说明流与计量情况；后台消费者须读取实际阶段、停止原因与错误事件，避免连接正常结束后直接把工作写成 completed。终态解析从 HTTP 路由层抽出，供后台与其他入口统一消费。
4. **停止不是回滚**：停止后运行时可阻止继续派发，但已在外部执行的请求仍可能返回；晚到结果需检查所属尝试与当前状态，已发生的操作事实应保留。
5. **多身份是状态分离的前提**：会话、任务、执行尝试、外部操作、产物（含内容哈希与文件版本）生命周期各不相同。没有执行尝试身份，晚到回包会覆盖已派发的新尝试的进度（A 超时派发 B 后，A 的回包须按派发身份被拒并留拒绝记录）；没有产物版本身份，「路径相同」会被误认为「内容相同」。
6. **要求版本冲突单独处理**：用户执行中更正任务范围后，旧计划不能凭「最后写入」覆盖新要求；提交计划时检查相关要求或计划是否已变化，遇冲突让执行重新读取当前依据。

## Structure（结构）

三控制模块 + 一条执行路径（逻辑边界，当前实现可共处同一引擎进程）：

- 执行路径：请求 → 引擎 → 模型 → 执行器 → 检查 → 交付。
- 任务控制：有效要求与进度；本地状态用同一 SQLite 事务保存状态+事件+版本快照（一个已提交版本必有对应状态与事件）。
- 操作记录：动作何时开始、是否发出、取得什么回执；恢复时结合文件读回或远端查询确认。
- 产物记录：文件版本（内容哈希、检查时间、所属运行）与检查结果。

本地状态可被数据库事务覆盖；外部操作（文件写入、远端请求）不能——「数据库事务覆盖不了外部工具」，恢复不能盲目重发或直接回滚。

## How It Works（运作方式）

恢复决策顺序（四步）：先读持久记录，区分界面断连与引擎中断 → 原执行仍在推进则重新订阅 → 工作已结束则读回结果 → 确认需要继续才进入新执行尝试。接续时恢复原工作目录、有效要求、已完成事实与操作记录；方法内容或输入版本已变化时应重新建立依据，不能把旧试跑结论直接带入；恢复消息属系统提供的运行资料，不能冒充用户的新要求。

结果不明的外部写入：支持按业务单号查询时先查最终状态；支持幂等键时按接口约定复用；都没有时保留未知状态、取得确认后再处理。更换模型不会增加业务授权，也不会消除不确定的外部结果。

## Relationships（关系）

### Related Concepts（相关概念）

- [[task-run-step-event-model|Task/Run/Step/Event 领域模型]]：两者互为呼应——该页 Task/Run/Step/Event 四元分离（Run 即执行尝试、Event 即 append-only 事实）与「晚到结果不得覆盖当前状态」正是本页多身份与提交检查的设计动机；本页提供工程动机（为什么一个会话 ID 不够），该页提供形式化模型（状态机、守卫、OCC）。
- [[durable-execution|持久执行（Durable Execution）]]：中断恢复与回执确认与本页恢复决策顺序同族（fencing、PAUSED_INDOUBT 冻结对账、Outbox）；本页「没有远端支持时保留未知状态，比作出无法兑现的自动恢复承诺更符合实际接口能力」与 Go+PG 信源同调。
- [[agent-loop|Agent Loop]]：状态分离是 Loop 之外的状态管理层——Loop 回答「循环怎么跑」，本页回答「执行、动作、产物三类事实如何记录、谁有权修改」。

### Dependencies（依赖项）

- 多身份体系（会话/任务/尝试/操作/产物）与版本号（要求版本、文件内容哈希）——提交检查与拒绝留痕的前提。
- 持久化操作记录与回执查询能力——恢复决策的前提。

### Distinctions（区分）

- 与事件溯源的区分：本页不要求从事件流重建全部状态，主张各模块分别维护状态、恢复入口读取决定；形式化路线见 [[task-run-step-event-model|Task/Run/Step/Event 领域模型]]。
- 与单一状态字段的区分：「RUNNING/COMPLETED」式进度状态机可与三态分离并存——前者管执行进度，后者管事实与质量；本页反对的是用前者替代后者。

## Evolution（演进）

- 2026-10-31 — 自立。单一信源（Codex 桌面客户端 Harness 架构第六篇，作者自组织工程实验 E1–E4）。「三态分离」判断目前单信源，但内部证据较强（E1 以原稿字节与修改时间验证保留、E2 实测「产物合格却未交付」「运行结束但内容不合格」两类失败）；置信度 medium，待后续信源印证。

## Open Questions（开放问题）

- 三态分离与既有状态机设计（如 Task/Run/Step/Event 六态）应统一还是并存？当前证据不足以裁决。
- 分布式多实例部署下「操作记录+回执确认」如何与 fencing token 配合？信源为单机 SQLite+隔离引擎，未覆盖。
