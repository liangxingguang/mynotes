# 积分系统设计（不变量/批次账务/并发扣减/冲正与对账）

## Definition（定义）

积分（点数/里程类账户）系统的架构设计方法论：以「余额可被历史记录完整解释」为数据模型判据，用五条不变量（幂等、不透支、历史不可覆盖、修正留新记录、余额可解释）约束整个系统，通过批次账务（分批过期 + 批次消耗明细）支撑消费与冲正，用本地事务 + 事务发件箱守住账户内部一致性，在超时、退款与任务失败后通过幂等、冲正与对账重新收敛。

## Why It Matters（为什么重要）

积分系统表面上只是余额加减，真正落地时要同时处理并发扣减、分批过期、请求重试、退款冲正和账务核对。一张账户表加一个余额字段「可能就能支撑系统运行」，但遇到分批过期和退款时数据模型很可能要推倒重来——难点不在加减，而在回答「第一次成功没有、重试会不会重复扣、80 来自哪些批次、退款怎么退、失败后怎样证明余额仍正确」。

## Core Characteristics（核心特征）

1. **先定不变量再谈技术**：同一业务操作只生效一次；可用积分不能扣成负数；余额变化有不可覆盖的历史；退款与修正必须留新记录；余额能由交易、流水、批次共同解释。排行榜可晚几秒，余额、幂等结果、账务历史不能。
2. **「高并发」要变成可验证数字**：教学假设 1000 万用户、查询 2 万 QPS、变更 3,000 TPS；还要看**单账户最大并发写入**——它直接决定行锁/乐观锁/条件更新选型，也决定热点账户是否单独限流。
3. **批次账务**：积分按批次管理（来源/到期日/剩余量），消费按「较早到期优先」消耗批次并记批次消耗明细；退款按明细找回原批次做冲正。这是分批过期与退款能落地的前提。
4. **6 类数据模型**：账户快照、积分交易（幂等键唯一）、账户流水（只追加）、积分批次、批次消耗明细、发件箱事件（与核心变更同事务提交）。一笔消费 80 产生：交易 T001、流水 L001（110→30）、批次消耗 A001/A002、快照、发件箱事件。
5. **写入链路 7 步**（一次消费的本地事务）：建交易（已存在返回原结果）→ 锁账户或版本号 → 原子扣减且 ≥0 → 按较早到期优先消耗批次 → 写批次消耗明细 + 追加流水 → 更新快照 + 写发件箱 → 提交。**绝不能先读余额、应用里判断后无条件覆盖**。
6. **冻结不是标配**：一次调用能完成的兑换直接扣减；只有订单之后还可能确认或取消时才用「冻结 → 确认扣减／取消解冻」状态机。
7. **冲正不删账**：退款是新增冲正交易 + 反向流水，绝不删原流水；过期按批次处理 + 稳定任务标识 + 调度租约防重复清零。
8. **对账三类关系**：余额与流水批次汇总一致、业务与积分系统总量与逐笔状态对应、发件箱与下游读模型有无长期未完成记录。**自动发现问题 ≠ 自动改账**——直接改余额会断审计链。
9. **扩展顺序克制**：查询多→缓存 + 异步读模型（读模型不能用于决定能否扣分）；核心数据多→先归档再决定分片；真到上限才按账户标识稳定路由，**不要只按时间把同一账户打散**（否则幂等键无法靠单库唯一约束全局去重）。热点账户加实例无效，靠限单账户并发、按序执行、缩短事务、拆子账户。

## Structure（结构）

一次消费 80 的记账实例（数据模型的对应关系）：

| 记录 | 内容 | 作用 |
| --- | --- | --- |
| 积分交易 T001 | 消费 80，处理成功 | 记整体业务操作与处理状态 |
| 账户流水 L001 | 可用 -80，余额 110→30 | 解释总余额变化 |
| 批次消耗 A001 | 取 B001 的 50 | 说明积分来自哪个批次 |
| 批次消耗 A002 | 取 B002 的 30 | 同上 |
| 账户快照 | 可用 30 | 快速查询，与账务变更同事务更新 |
| 发件箱 E001 | points.consumed | 通知下游 |

## How It Works（运作方式）

写入链路四步：①幂等键确认是否处理过（键 = 业务方 + 业务单号 + 操作类型）；②一个本地事务完成记账（7 步）；③提交数据库后再处理缓存（先提交后删缓存 + 失效事件重试 + 必要时送 MQ）；④跨系统通过事件收敛（订单系统同事务保存订单状态与发件箱事件，后台任务或 CDC 发送，积分系统按业务单号 + 操作类型幂等入账）。

异常恢复：超时重试靠同一幂等键返回首次状态；退款按批次消耗明细找回原批次做冲正；过期任务按批次处理 + 稳定任务标识 + 调度租约。

## Relationships（关系）

### Related Concepts（相关概念）

- [[idempotency-design|幂等设计]]：本概念是幂等设计在账户系统的实例——幂等键三要素（业务方 + 业务单号 + 操作类型）、最终幂等由核心持久化并用 DB 唯一约束守住、扣减绝不先读余额后无条件覆盖。
- [[local-message-table|本地消息表]]：本概念的发件箱与「同事务提交」同构；「MQ 不是发件箱必选项」「事务发件箱不保证只处理一次，消费者仍要幂等」直接印证本地消息表核心特征。
- [[hot-cold-data-separation|冷热分离]]：「核心数据多了先归档再决定是否分片」「历史流水可分区或转入低成本归档存储」印证冷热分离的定位。
- [[cursor-sharding|游标分片]]：按账户标识稳定路由 + 分片内按时间分区，与游标分片/路由键设计互为印证。

### Distinctions（区分）

- 与**复式记账**：积分子账不等于企业财务总账；单一平台规则简单时「账户快照 + 不可变流水 + 积分批次」已够用，涉及多发行方/商户结算/账户间价值转移才上复式记账——选型标准是余额能否被历史记录完整解释。
- 与**读模型**：缓存与异步读模型分担查询压力，但**读模型不是账务事实，不能用于决定能否扣分**；扣减判断始终回到账户核心与权威库。

## Open Questions（开放问题）

- 批次到期后的冲正规则（立即失效/沿用原有效期/获得新有效期）属产品规则，信源只给出「必须提前约定并记录结果」的要求。

- 热点账户拆子账户后汇总读的一致性窗口：信源未覆盖。
