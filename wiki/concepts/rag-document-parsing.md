# RAG 文档解析

## Definition（定义）

RAG 建库流程的第一环：把文档（PDF/Word 等）中的文本**连同结构**一起提取出来的处理环节。解析的产出文本一路传给分块、嵌入、召回，直至进入模型上下文。与"纯文字提取"的区别在于目标口径：解析要还原标题层级、表格行列关系、页码与位置，缺哪样都会在某个下游环节暴露。

## Why It Matters（为什么重要）

解析是文档进入 RAG 系统的第一环，这段文本错了，后面每一环都在错误的基础上工作，**而且没有任何环节会报错**。制度类文档的报销标准、审批权限几乎都在表格里，表格结构丢失最直接影响答案质量；解析错误在上游产生、在下游放大，表现为"某些问题永远答不对"的隐性故障。

## Core Characteristics（核心特征）

1. **目标 = 连同结构提取**：标题层级、表格行列关系、页码与位置，缺一不可。
2. **三类典型难点**：文本层缺失（扫描图像提取为空或乱码，必须走 OCR）；阅读顺序错乱（双栏按行读通，左右两栏串成一句，单看都对、连起来不通）；表格结构丢失（单元格被拆成独立行，表头与数据失去对应）。
3. **四类结构各有下游用途**：标题层级决定分块从哪切；表格结构决定答案能否被正确读出；页码决定引用能否指回原文；正文文本决定检索能否命中。
4. **错误放大且不报错**：一页被解析成空白的制度，索引里没有对应片段，召回拿不到内容，模型仍会凭先验给出行业常见值——格式完整、语气确定，用户很难分辨是编造还是规定；一条从中间断开的条款，具体数字落在另一个片段，模型只能推断或省略。
5. **验收靠抽样对照而非通用准确率**：从语料抽 50 页覆盖不同来源与版面，逐页记录四项是否还原（标题层级、表格行列、段落顺序、页码），结论按文档来源分组统计而非给总分。
6. **解析方案三条路线可分层组合**（信源 2026-11-20）：规则解析（读文件内部排版对象，纯文本 PDF 毫秒级、可复现，但扫描件拿不到内容、双栏按行合并）、版面模型（渲染图像检测区域再识别，扫描件必走，代价是算力/准确性/工程）、商用 API（接入最低，但数据出域、限流成本、能力边界固定）；实际系统常分层（规则跑全量、异常走模型，或按来源/用途分流）。
7. **解析引擎工具（DeepDoc / MinerU）**（信源 2026-11-23）：DeepDoc 是 RAGFlow 的视觉+语义文档解析引擎，整合 OCR、版面分析、表格结构识别与多格式解析器，将"绘制指令/图像"还原为语义化、可检索的文档单元；**混合策略**——模型负责复杂判断、规则修边界（垃圾文本过滤、合并阈值等），**模块化 Parser** 同一套视觉输出驱动不同格式解析（PDF/Word/Excel/PPT），每个 chunk 保留截图并在前端高亮便于可视化校验；工程上用 onnx 推理、batch 处理、scale factor 缩放、XGBoost/规则融合做 box 合并决策。MinerU 则把所有格式统一转成 md/json，与 DeepDoc"逐类型处理"的取向不同。
8. **问答对作为可检索单元**（信源 2026-11-23）：除常规分段外，可对文档提取**问答对**（结构化 Q→A 键值对）作为可检索知识单元——普通文本块拆分后是连续的非结构化文本片段，问答对是明确的结构化键值对，存储与检索时可针对性地对"问题"和"答案"分别处理，适合把文档中明确的 Q→A 映射直接提取出来。
9. **三大视觉任务**（信源 2026-11-23）：解析依赖的视觉能力分三项——**OCR** 提取图片或扫描件中的文字内容；**DLR** 分析文档结构布局（标题、段落、图像等）；**TSR** 识别表格行列、合并单元格并结构化输出。

## Structure（结构）

解析在 RAG 管线中的位置（上游→下游）：

```text
文档（PDF/Word/扫描件）→ 解析（结构还原）→ 分块 → 嵌入 → 召回 → 模型上下文
```

解析产出的文本与结构信息分别供给下游：正文文本供给分块与检索命中，标题层级供给分块切点，表格结构供给答案读出，页码供给引用回指。

## How It Works（运作方式）

**抽样对照验收法**：抽 50 页，覆盖不同来源与版面，逐页记录四项是否还原；按文档来源分组统计（同一来源往往由同一套模板生成，问题也集中在一处）。成本约半天到一天；跳过它直接上线，问题会以"某些问题永远答不对"的形式出现，排查时间通常是抽检的十倍。

**够用三判**（判断解析方案是否不再构成瓶颈）：

1. 四类结构是否都保留；
2. 抽检 50 页的还原率是否达标；
3. 失败是否集中在可识别的文档类型上。

三条都过关，解析不再是瓶颈。

**解析方案选型**（信源 2026-11-20，系列第 5 篇）：

把文档变成结构化文本有三条路线，机制不同、适合语料不同：

- **规则解析**：读文件内部排版对象（字体字号粗细、文本块坐标、段落列表标记）。纯文本 PDF 毫秒级、不需 GPU、可复现、出问题能追到具体规则；但扫描件无文本对象拿不到任何内容、双栏排版坐标排序按行合并、文本框/嵌套表格/图片化文字的内部对象与阅读顺序不一致。
- **版面模型**：每页渲染成图像，先检测标题/正文/表格区域再逐区域识别，处理人眼所见版面、不受内部对象混乱影响，**扫描件必须走此路**。代价三块：算力（单页毫秒→百毫秒到秒级，纯 CPU 部署吞吐下降）、准确性（OCR 识别错，生僻字/印章遮挡/细线表格影响，跨页与合并单元格常见失败点）、工程（模型版本与环境维护，升级可能改输出格式需重建分块索引）。
- **商用 API**：接入成本最低；三约束——数据出域（制度合同财报保密）、限流与成本（按页按次计费、全量导入排队分批）、能力边界固定（格式与还原程度由服务商定义）。

**分层而非单选**：规则解析跑全量，产出异常（文本过少、顺序混乱、表格失败）的挑出来走模型，模型只处理少数难例；或按文档来源分流（识别出扫描件固定走 OCR）；或按用途分流（预览要粗略文本、检索要完整结构）。

**选型顺序**：先看有无扫描件（有就必须能处理图像）→ 再看能否出域（不能就排除商用 API）→ 再看来源数量（来源多、模板各异时先建分流逻辑）→ 最后算总成本（自建的维护、升级、人工复核常超过服务费）。

**换解析器的隐性绑定**：换解析器意味着同文档产出不同文本，文本变分块变、向量全部失效，必须全量重建索引；选型须在建库前定，或至少记录每份文档用的解析器与版本，换方案时能精确知道哪些需重建。

### Distinctions（区分）

- 与 OCR 的区分：OCR 是文本层缺失（扫描件）时的补救手段；解析的目标不止文字，而是连同结构还原。OCR 只是解析处理三类难点之一时用到的手段。
- 与普通文本提取的区分：普通提取只关心文字；解析把"标题层级、表格行列、页码位置"纳入验收口径。
