# B端需求调研SOP

## Definition（定义）

B 端产品经理在 ERP/CRM/OA/供应链等系统立项、流程梳理或版本范围确认前，围绕业务目标、岗位执行、系统边界做分层挖掘的可复用工作流。核心命题：**调研的目的不是记录用户说什么，而是搞懂用户为什么这么说**。由六个环节组成：调研前准备 → 干系人识别 → 现场观察 → 五层提问 → 需求整理与优先级 → 调研报告输出。

## Why It Matters（为什么重要）

- 口头访谈容易得到"理想答案"，用户说不清需求时，现场走一遍工位需求才会浮现；调研质量直接决定后续系统设计的输入质量。
- B 端需求跨部门、跨层级，不同层级对同一需求描述差异大，不分层采集会导致需求互相打架、无法形成判断。
- 同专辑的系统设计方法论（[[crm-system-design|CRM]]、[[contract-lifecycle-management|合同管理]]、[[approval-workflow-engine|审批流引擎]]、[[dashboard-metric-tree|数据看板]]、[[complex-system-breakdown|五件套拆解]]）都以调研为上游：调研清单与三维优先级是这些系统立项/版本范围确认的直接输入。

## Core Characteristics（核心特征）

1. **先定边界再进场**：进场前明确调研目标（立项论证/流程梳理/版本范围确认）与覆盖范围（调研地图），产出"调研清单"——从谁那里确认什么，而不是访谈问题列表。
2. **分层采集、交叉验证**：按决策层/管理层/执行层三类干系人分别采集再交叉验证（决策层要结果，执行层要过程）。
3. **观察优先于询问**：跟岗观察、记录断点、收集物证（Excel 模板/纸质单据/聊天截图），以"说和做的差距"识别真需求。
4. **从目标问到边界**：五层提问框架避免直接问"你想要什么功能"（业务方答不上或抄别家系统）。
5. **需求带业务价值与来源标注**：每条需求写清谁使用/多久用一次/应对什么问题/不处理会怎样，并标注来自哪个层级哪个岗位。
6. **三维优先级排序**：价值-频率-影响范围评分，优先高价值+高频率+广范围。

## Structure（结构）

| 环节 | 产出 | 关键动作 |
|---|---|---|
| 调研前准备 | 调研清单 | 调研目标 + 资料包（组织架构/岗位说明书/系统截图/业务制度/历史需求）+ 调研地图（部门/岗位/场景/系统/数据流向） |
| 干系人识别 | 分层访谈计划 | 决策层（业务目标/资源投入/风险偏好）、管理层（流程指标/考核/协同）、执行层（日常使用/重复环节/断点） |
| 现场观察 | 断点与物证 | 跟岗走完一笔业务全路径（发起→归档）；记录重复录入/手工汇总/等待审批位置；收集 Excel/纸质单据/截图 |
| 五层提问 | 结构化访谈记录 | 目标层→现状层→期望层→边界层→风险层 |
| 需求整理 | 需求清单 | 去重合并（角色+场景+期望一致）、补充业务价值四问、标注来源层级与岗位 |
| 优先级评估 | 三维评分表 | 业务价值（影响收入/风险/效率的关键程度）、使用频率（日/周/月）、影响范围（岗位/部门/全公司） |
| 报告输出 | 需求调研报告 | 业务现状（流程图）+ 痛点清单（按干系人分组）+ 需求清单（编号+描述+评分）+ 待确认问题 + 后续计划 |

## How It Works（运作方式）

1. 接到调研任务后先不急着约访谈，准备目标/资料包/调研地图三样，产出调研清单。
2. 按三类干系人分层排访谈，每层侧重不同（结果 vs 过程 vs 断点）。
3. 访谈与现场观察交替：跟岗 1-2 个典型场景走完整业务路径，用物证验证口述。
4. 访谈用五层框架推进，示例问法："如果这个需求只做一个版本，你希望优先处理哪一段？""这个环节如果取消，会影响谁？"
5. 汇总散落在会议纪要/微信/Excel 里的需求，去重、补价值、标来源，三维评分排优先级。
6. 输出调研报告，"待确认问题"交业务负责人二次确认，后续计划含原型范围与再访时间。

### Dependencies（依赖项）

- 依赖业务方配合跟岗观察与分层访谈（执行层可用性是调研质量前提，此为解读）

### Distinctions（区分）

- 与用户访谈（问"想要什么功能"）的区别：本 SOP 反对直接问功能，主张从业务目标问到系统边界；口头访谈得"理想答案"，现场观察得"真实断点"。
