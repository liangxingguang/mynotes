# 拉模式红点树系统（游戏 UI 提示徽标）

## Definition（定义）

一种用路径树管理游戏 UI 红点（提示徽标）的客户端架构：红点天然成树（入口数字=页签之和，页签数字=条目之和）。数据变化时叶子只标脏不做计算，每帧后序遍历整棵树、只对脏节点重算——叶子承载"该亮几个"的业务逻辑，中间节点只做子节点求和，父红点自动汇总。与主流"前缀树+父节点脏集合"方案（只合并了汇总）相比，本文把"计算"也合并了：叶子自订阅数据事件、自计算数值（拉模式），业务代码只需说"变了"。

## Why It Matters（为什么重要）

中大型游戏红点数量上百、层级深、数据来源杂（服务器推送/本地数据变化/时间到点），是玩家体验的高频感知点。传统做法要么界面自己算（逻辑散落、入口与内部不一致）、要么扁平 key 表（无层级汇总）、要么推模式（业务侧算值推给红点系统，计算逻辑散落在各功能模块）。本文的拉模式+脏标记+每帧合批，把一个红点的全部逻辑收进一个叶子类，业务代码零改动，事件风暴无害（标脏幂等近零成本）。适合红点数量多、层级深、数据来源杂的中大型项目。

## Core Characteristics（核心特征）

1. **路径树结构**：每个红点用路径标识（如 `Mail_System`），按分隔符逐级建树；只有叶子承载业务逻辑（"该亮几个"），中间节点只做子节点求和。同一份数据挂多个入口时，在两条路径下各挂一个叶子（不做成一节点多父），树永远是树，求和不重复计数。
2. **拉模式**：叶子自己订阅关心的数据变化事件，收到后只标脏不做计算；真正的计算写在 `GetCount()`（当前数据的纯函数，只读无副作用，任何时候调用返回同样结果）里，由框架在合适时机调用。业务代码零改动、事件风暴无害、一个红点全部逻辑收在一个类里。
3. **脏标记冒泡**：`SetDirty()` 只做两件事——自己标脏、沿父链把每个祖先标脏。成本 O(树深度)≈常数（红点树一般三四层），可在任何事件回调里放心调用；标脏幂等，标一次和标十次结果一样，合批效果正来自此。
4. **每帧合批**：每帧固定时机从根节点后序遍历（先处理子节点再处理自己），叶子脏则调 `GetCount()`、中间节点脏则求子节点当前值之和。不管来多少事件，每个节点每帧最多算一次——计算量只与"多少节点变脏"成正比，与"来了多少事件"无关。代价是最多延迟一帧（玩家感知不到）。
5. **先取走脏标记再计算**：脏标记必须在计算之前取走（`IsDirty=false`），不能在计算之后才清。否则遍历中某子节点再次标脏，标记冒泡到父节点，父节点按旧值求和后误清标记，下一帧子节点算出新值但父节点已不脏、不再求和，入口红点停在旧值。
6. **有意全树遍历**：每帧完整走一遍整棵树（含未脏节点）。遍历干净节点仅微秒级，脏标记省的是"计算"而非遍历；全树 Update 顺带让时间驱动红点（冷却到期/跨天重置）在叶子 `OnUpdate` 自查标脏，无需外部定时器。节点数量到数千级才值得改成只遍历脏子树。
7. **变化才通知 + UI 先拉后推**：节点重算后只有数值真的变了才发变更事件（带路径和新值）；UI `OnEnable` 时先拉一次当前值（隐藏期间错过的事件不用补），之后靠推（只响应同路径事件）。显示压制（如当前选中页签不显示红点）放在 UI 层、只改显示开关不碰数值，父节点汇总不受影响。
8. **建树与 Init 分离**：加载配置后 `BuildTree()`（只建结构、不订阅不计算）→ 登录数据就绪后 `InitData()`（整棵树 Init、全部标脏、叶子开始订阅）。避免登录数据未齐时基于不完整数据算出中间结果导致红点"亮了又灭"的闪烁。

## Structure（结构）

四个核心类：`RedPointNode`（基类：冒泡+数值变了才通知）→ `RedPointLeafNode`（叶子：脏则清脏再调 `GetCount()`）→ `RedPointEventLeaf`（事件叶子：订阅/解绑收进生命周期，子类只管声明"关心哪些事件"）。另含 `UIRedPoint`（MonoBehaviour 组件：下拉选路径、先拉后推、显示压制）。叶子全声明在一张 `RedPointTree.Leaves` 注册表里（新增红点唯一需改的公共文件）。路径用常量定义（`MailRedPoint.System = "Mail_System"`）。

## How It Works（运作方式）

- **建树**：`AddLeaf(fullPath, leafType)` 按路径逐级查找、缺哪一级补哪一级（`RedPointInternalNode`），叶子挂在最后一段；同时登记"路径→节点"字典供 O(1) 查询。重名/叶子下挂子节点两类结构冲突在建树期直接报错。
- **数据变化**：叶子的订阅回调触发 → `SetDirty()` 冒泡到根（只标记、不计算）。
- **每帧 Update**：管理器驱动根节点 → 中间节点后序遍历：先取走自身脏标记、递归子节点 `OnUpdate`、脏则对子节点当前值求和 → 叶子 `OnUpdate`：脏则清脏、调 `GetCount()`、`SetCount()`（数值变了才发事件）。
- **UI 刷新**：`OnEnable` 时 `Refresh()` 直接查 `GetCount(Path)` → 之后 `OnChanged` 事件回调中只认同路径 → `SetBadgeCanShow` 只改显示开关。

## Relationships（关系）

### Related Concepts（相关概念）

- [[notification-system-design|站内消息系统领域模型]]：同属"通知/提示"领域但层不同——本概念是客户端 UI 徽标计算（按钮/页签亮不亮、数字多少），该概念是服务端消息投递（公告/提醒/私信的库表与订阅拉取）；前者管"显示层提示"，后者管"消息传递"。

### Dependencies（依赖项）

- 无外部系统依赖（纯客户端架构，信源未涉及 MQ/服务端推送通道协议细节）。

### Distinctions（区分）

- 与主流方案 D（前缀树+父节点脏集合）的不同之处：方案 D 只合并了"汇总"（父节点每帧算一次），叶子仍是推模式（业务算好值推给红点系统）；本文把"计算"也合并了（叶子也每帧算一次），业务只需说"变了"。代价是同一份数据挂多个入口时每个叶子各算一次（方案 E 用运算单元组合解决）。
- 与方案 E（运算单元组合+标脏+每帧限量）的不同之处：方案 E 有单元组合层和每帧预算，同一份数据只算一次、能削峰；本文更轻（只需写一个叶子类），代价是共享数据各算一次。项目红点计算重、共享多时方案 E 更合适。
- 与 [[notification-system-design|站内消息系统]] 的不同之处：见 Related Concepts。

## Evolution（演进）

- 2026-10-28 原始方案：基于方案 D（前缀树+父脏集合）改进——叶子也标脏每帧统一算（拉模式）、订阅逻辑收进叶子生命周期、时间驱动红点靠全树 Update 自查。完整 C# 实现 + 免费抽卡示例。

## Open Questions（开放问题）

- 方案 E 的"运算单元组合+每帧限量"在红点计算极重（如每个列表项都是动态节点、千级）时的具体实现信源未展开。
- 多入口共享数据各算一次的性能损耗，在红点数上千时的量化数据信源未提供。
