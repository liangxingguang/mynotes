# MySQL SQL 执行管线（五阶段）

## Definition（定义）

MySQL 中一条 SQL 语句从客户端发出到结果返回，所经历的**多组件协同处理流程**。按信源描述，该管线贯穿**连接层 → 服务层（查询缓存、解析器、优化器、执行器）→ 存储引擎层**三层体系结构，可拆解为**准备、解析、优化、执行、结果返回**五个阶段。它是理解"SQL 为何快/为何慢"的机制基础，也是查询优化与性能排查的底层坐标系。

## Why It Matters（为什么重要）

- **优化查询的前提是懂执行过程**：不理解词法/语法/语义分析、优化器选计划、执行器调引擎，就无法定位"为何慢"，只能盲目加索引或改 SQL。
- **排查性能问题的定位框架**：性能瓶颈可能落在任一阶段——连接慢、缓存未命中、解析报错、优化器选错计划、引擎读盘慢、结果集过大，五阶段是逐段排查的清单。
- **索引与结构设计的理论依据**：优化器按成本与覆盖条件选索引，多条件查询应设计覆盖多条件的联合索引，这直接来自管线中"优化"阶段的成本模型。
- **引擎选择的决策基础**：InnoDB 与 MyISAM 在事务、锁、外键上的差异，决定了它们在管线"执行"阶段的适用场景。

## Core Characteristics（核心特征）

1. **三层体系结构**：连接层（建连接、收发 SQL 与结果）、服务层（缓存/解析/优化/执行）、存储引擎层（数据存储与检索）。三层分工明确，引擎层可插拔（InnoDB/MyISAM）。
2. **五阶段串行管线**：准备 → 解析 → 优化 → 执行 → 结果返回，前一阶段产物为后一阶段输入，任一阶段失败即中断并返回错误。
3. **解析分三步**：词法分析（拆符号）→ 语法分析（建语法树）→ 语义分析（查存在性/类型/约束），逐步从"字符流"收敛到"可执行结构"。
4. **优化器按成本选计划**：基于语法树与统计信息生成多个候选执行计划（如全表扫描 vs 走索引），评估成本后选最低者；多条件优先覆盖最多条件的索引。
5. **执行器调引擎接口**：执行器不直接读写数据，而是通过存储引擎提供的统一接口（读/写/更新/删除）操作，引擎实现各异但须遵循服务器规范。
6. **写操作保证 ACID**：涉及事务的写操作，执行器确保原子性、一致性、隔离性、持久性；锁与 MVCC 的并发控制细节见 [[mysql-locking]]。

## Structure（结构）

```
客户端
  │  ① 准备：连接层建连接 + 身份验证/权限检查；服务层查查询缓存（命中即返回）
  ▼
服务层
  │  ② 解析：词法分析 → 语法分析（建语法树）→ 语义分析（存在性/类型/约束）
  │  ③ 优化：查询优化器基于语法树+统计信息生成候选计划，按成本选最低
  │  ④ 执行：执行器按执行计划调存储引擎接口（读数 / 写操作保 ACID）
  ▼
存储引擎层（InnoDB / MyISAM）
  │  ⑤ 结果返回：执行器处理结果集（去重/排序/分页）→ 返回客户端；出错返回错误
  ▼
客户端
```

## How It Works（工作原理）

1. **准备阶段**：连接层与客户端建立连接，完成身份验证与权限检查。服务层首先检查**查询缓存**——若存在完全相同 SQL 的执行结果则直接返回。查询缓存仅对完全相同的 SQL 有效、占内存、数据变更需清除，故 MySQL 8.0 后已移除该机制。
2. **解析阶段**：
   - **词法分析**：将 SQL 拆为关键字、表名、列名、运算符等符号（如 `SELECT * FROM users WHERE id = 1` → SELECT、*、FROM、users、WHERE、id、=、1）。
   - **语法分析**：按语法规则构建语法树，表示 SQL 的语法结构。
   - **语义分析**：检查表名/列名是否存在、数据类型是否匹配、约束是否满足；引用不存在的表报 `Table 'xxx' does not exist`。
3. **优化阶段**：查询优化器根据语法树与数据库统计信息生成多个候选执行计划（如全表扫描 vs 走索引），评估各计划成本，选择成本最低者。多条件查询（如 `id = 1 AND name = 'John'`）优先选择能覆盖最多条件的联合索引。
4. **执行阶段**：执行器按选定执行计划调用存储引擎接口。查询从引擎读数，需排序/分组时在内存完成；写操作（插/改/删）确保事务 ACID。存储引擎提供统一读写接口，不同引擎实现不同但遵循服务器规范。
5. **结果返回阶段**：执行器处理结果集（去重、排序、分页）后返回客户端；执行出错则返回错误信息由客户端处理。

## Relationships（关系）

### Related Concepts（相关概念）

- [[mysql-locking]]：执行阶段"写操作保 ACID"涉及的锁与并发控制机制，是管线在并发维度的延伸。
- 索引与查询优化：优化阶段的"索引选择"与索引原理、覆盖索引、执行计划分析紧密相关（该概念页若存在则链接于此；当前 Wiki 暂无独立页，可后续编译）。

### Dependencies（依赖）

- 依赖 MySQL 三层体系结构（连接层/服务层/存储引擎层）作为管线载体。
- 依赖存储引擎（InnoDB/MyISAM）提供读写接口实现。

### Distinctions（区分）

- **执行管线 vs 锁体系**：管线描述单条 SQL 的纵向处理流程（准备→返回），锁体系描述并发场景下写与写的横向冲突控制，两者维度不同、互补。
- **执行管线 vs 引擎架构**：管线是"一条 SQL 怎么走"的动态流程，引擎架构是"数据怎么存"的静态结构，管线在引擎层调用后者的接口。

## Evolution（演进）

- **查询缓存的兴衰**：查询缓存曾是准备阶段的性能优化手段，但因仅对完全相同 SQL 命中、占内存、数据变更需清除等局限，MySQL 8.0 后被移除，管线"准备"阶段随之简化。这一演进说明：缓存类优化需权衡命中收益与维护成本。
- **引擎可插拔**：从 MyISAM 到 InnoDB 成为默认，存储引擎层在管线中保持接口统一，业务可在不改变管线的前提下切换引擎，体现了分层设计的扩展性。
