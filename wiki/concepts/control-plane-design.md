# 规则控制面与寻优计算面分离

## Definition（定义）

一种面向复杂业务约束的架构模式：将频繁变更的业务规则收敛为领域契约（控制面），将求解算法限定为在合法空间内搜索（计算面），两者通过接口隔离、互不侵入。核心目标是让业务规则变更不触碰核心算法代码，同时保证算法只在合法约束空间内寻优。

## Why It Matters（为什么重要）

当业务规则高频变更（如营销策略调整）而求解算法相对稳定时，若将规则硬编码到业务逻辑中，每次规则调整都要改代码、走发布流程，迭代节奏被研发锁死。反之，若将规则与算法分离，运营可自助调整规则配置，算法代码零改动。这一模式在优惠券组合、风控规则、定价策略等「规则多变 + 求解复杂」的场景中具有普遍适用性。

## Core Characteristics（核心特征）

1. **领域模型收敛规则**：将散落在产品文档、口头沟通中的规则固化成统一的领域契约（聚合根 + 值对象），供给规则引擎消费，避免逻辑碎片化和 if-else 无限堆积。
2. **规则引擎前置过滤**：在搜索前先做候选集裁剪（过期、门槛不满足、范围不匹配的直接剔除），减少进入递归的基数；搜索过程中实时校验约束（互斥、叠加、上限、优先级）。
3. **算法只在合法空间搜索**：寻优算法不感知具体业务规则，只消费规则引擎给出的「合法/不合法」判定，在约束空间内寻优。
4. **降级与一致性兜底**：算法输出不能绑定业务可用性——搜索节点上限、超时熔断、降级回退经过验证的保守方案，是工程红线而非可选优化。
5. **多目标拆分控制复杂度**：不追求单轮搜索解决所有目标，将次要目标（如赠品约束）后置做硬校验，避免搜索空间二次爆炸。

## Structure（结构）

三层架构（据优惠券最优组合案例）：

| 层 | 职责 | 关键组件 |
|---|---|---|
| 控制面（DDD 领域模型） | 收敛业务规则为领域契约 | 聚合根（模板/实例）、值对象（Condition/Benefit/Constraint）、限界上下文 |
| 规则引擎层 | 前置过滤 + 路径约束校验 | 候选集裁剪、互斥校验、叠加权限、门槛校验 |
| 计算面（算法层） | 合法空间内寻优 | 有界 DFS 回溯 + 多层剪枝 |

## How It Works（运作方式）

规则变更路径：运营调整门槛/互斥关系/叠加策略 → 只改配置 → 规则引擎本地缓存刷新 → 算法代码零改动。

算法执行路径：候选输入 → 规则引擎前置过滤 → 剪枝压缩搜索空间 → 在合法空间内 DFS 回溯寻优 → 产出最优组合 → 写入一致性快照。

降级路径：触发搜索上限或超时 → 放弃最优解 → 平滑切回保守方案 → 业务侧兼容金额变动 → 埋点记录降级触发。

## Relationships（关系）

### Related Concepts（相关概念）

- [[idempotency-design|幂等设计]]：控制面降级路径中的请求幂等流水号，防止重复调用带来重复计算与快照重复写入。
- [[retry-governance|重试治理]]：超时熔断与降级回退的系统设计，与本概念的稳定性兜底机制互补。

### Distinctions（区分）

- 与「规则硬编码」的不同：后者规则与算法耦合，变更需改代码发布；前者规则外置为领域契约，变更只改配置。
- 与「纯算法优化」的不同：后者聚焦算法本身（如剪枝公式、搜索策略），前者强调算法之外的规则收敛与降级体系——算法正确性只是基础门槛，工程落地难点在配套控制面。

## Evolution（演进）

- 2026-10-30：优惠券最优组合设计信源（首信源）提供电商营销场景的完整工程实例：DDD 两大聚合 + 六张表 + 三个限界上下文、四层剪枝体系、BitMask 互斥校验、稳定性红线与踩坑复盘。

## Open Questions（开放问题）

- 控制面与计算面的接口边界如何随业务复杂度扩展而演进：当前信源仅覆盖优惠券场景，其他领域（风控、定价）的适配路径尚无信源确立。
- 规则引擎的缓存刷新策略（领域事件驱动 vs 定时轮询）在不同规模下的性能取舍：当前信源采用事件驱动，未提供对比数据。
