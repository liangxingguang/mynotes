# 质量兜底策略（默认缺陷逃逸 + 架构隔离 + 线上闭环）

## Definition（定义）

质量兜底策略是 AI 时代软件质量保障的立场与方法：放弃「在合并前靠人眼审透代码、把未知隐患消灭在萌芽」的幻想，**默认缺陷必然逃逸**，把质量底座从「事前人工 code review」转向**架构隔离与线上闭环**——通过收缩输入边界、隔离爆炸半径、影子流量对比、持续巡检与秒级回滚，把任何未知缺陷的影响压在局部、把发现与修复的闭环缩到最短。（据 2026-11-26 信源整理，属作者方法论论断）

## Why It Matters（为什么重要）

- 代码规模与变更速率数量级上升后，「读过每一行源码」不再可能，人工逐行审查的安全感失效；而热路径性能暗雷等隐患连资深工程师也只能凭运气拦截，code review 作为兜底并不可靠（信源）。
- 系统里神经网络等黑箱组件占比上升（信源估计当前规则代码与神经组件约九一，几年后或滑向六四），这类组件天生无法逐行审查，只能靠线上机制保命（信源，作者估计口径）。
- 责权分离下机器干活、人背锅：人的「底气」须来自亲手设计并验证过的风险控制机制（边界隔离、冗余、仪表盘、安全机制），对标民航机长与芯片架构师，而非「我看过所有代码」的幻觉（信源论断）。

## Core Characteristics（核心特征）

1. **默认缺陷逃逸**：不追求事前全知，承认缺陷无论人写还是智能体写都躲不掉，把目标从「消灭隐患」转为「控制后果」。
2. **收缩输入边界（事前硬约束）**：语言特性收缩到严格子集、禁用易藏副作用的动态特性、第三方依赖锁供应链白名单，架构边界/类型约束/热路径禁忌做成静态检查硬规则——不靠 AGENTS.md 类提示词软约束（信源：软约束时灵时不灵，几百行文档会被模型选择性失忆）。
3. **隔离爆炸半径（事中）**：权限边界与资源配额锁死，即使组件「彻底发疯也炸不出隔间」；影子模式镜像流量逐笔比对输出差异、延迟分布与内存占用。
4. **持续巡检（事后）**：指标与账单的全天候后台巡检（信源实例：AWS CUR2 账单+运行指标喂巡检智能体，揪出缓存失效、读放大、无效写入等跨模块隐患），发现异常顺藤摸瓜挖热路径隐患并补确定性回归基准。
5. **秒级回滚闭环**：小比例灰度放量 + 限流/降级/熔断开关，指标越线自动无损切回上一版，把 PR 合并从赌全站生死变成可撤回的可控实验（信源：几十秒内切回）。
6. **工厂式质量控制迁移**：N-sigma 统计抽检校准流水线、安灯拉绳停线（事故时停掉相关智能体合码、锁现场）、蟑螂法则（单点 bug 触发全库同类扫描，沉淀为编译器规则/Linter/回归测试）。

## Structure（结构）

信源给出的四件事落地结构（2026-11-26 信源）：

| 层 | 手段 | 对应机制 |
|---|---|---|
| 事前 | 扎紧笼子 | 语言子集 + 依赖白名单 + 静态检查硬规则 |
| 事后 | 持续巡检 | 账单/指标巡检智能体，异常→定位→补回归测试 |
| 流程 | 工厂三招 | 统计抽检、拉绳停线、蟑螂法则沉淀 |
| 线上 | 保命机制铺到所有变更 | 影子流量 + 小比例灰度 + 限流熔断 + 秒级回滚 |

传统 CI 的「一次性准入考试」被重定义为贯穿事前约束、事中隔离、事后持续巡检的完整防线（信源论断）。

## How It Works（运作方式）

- **防线分层**：事前硬约束拦掉可静态判定的问题；事中隔离限制已逃逸缺陷的波及范围；事后巡检与回滚闭环承接漏网之鱼。三层任一失效不致命，整体按「默认逃逸」设计。
- **巡检回路**：定时取账单明细与运行指标 → 巡检智能体按预设目标找异常花销与性能波动 → 定位热路径隐患 → 补一条确定性回归基准测试（信源实战回路）。
- **变更即实验**：新版本先影子模式接镜像流量对比老版本 → 小比例灰度 → 指标越线自动熔断回滚 → PR 合并成为可撤回动作。
- **组织纪律**：事故时按影响范围停掉相关智能体合码（拉绳停线），复盘时全库扫同类写法沉淀为永久规则（蟑螂法则）。

- [[blue-green-deployment|蓝绿/灰绿部署]]：秒级回滚、小比例灰度是本策略的线上执行组件，灰度放量与熔断回滚机制见该页。

### Dependencies（依赖项）

- 运行时限流/降级/熔断与秒级回滚能力：没有线上回滚底座，「默认缺陷逃逸」无法兜住后果。
- 账单与指标可观测性：持续巡检依赖账单明细（如 AWS CUR2）与运行指标的完整采集。
- 静态检查/编译器硬规则工具链：事前硬约束依赖可机器判定的规则。

### Distinctions（区分）

- 与**人工 code review 为主**的质量体系不同：本策略不否认 review 的局部价值（老手直觉可能拦下个别坑），但认为其作为兜底靠运气、不可依赖，质量底座在架构与线上机制。
- 与**纯静态质量门禁**（lint/单测/覆盖率）不同：静态门禁管事前，本策略强调事中隔离与事后闭环，覆盖静态手段防不住的「真实流量规模才暴露」的缺陷。
- 与 **Agent 评测**不同：评测解决「怎么验证」，本策略回答「默认会漏、漏了之后怎么活」，后者是前者的兜底层。

## Evolution（演进）

- 2026-11-26：据微信公众号《不审代码，靠什么兜底》（《代码审查退场》续篇）整理。该文回应「热路径隐蔽坑怎么防」「人背锅没底气」两个反问，提出 code review 只是手段、缺陷必然逃逸，质量底座转向架构隔离与线上闭环，并给出四件事落地与分层演进路径（新团队重造流水线、老团队先补护栏再撤人工审查）。当前为单信源方法论论断，无第三方实证，confidence: medium。

## Open Questions（开放问题）

- 撤人工审查的触发条件与节奏未量化：信源只给「分层演进」原则，无护栏成熟度的可判定标准。
- 事前硬约束的覆盖度：语言子集/依赖白名单/静态规则能拦住哪类缺陷、漏哪类，信源未给数据。
- 巡检智能体的误报率与成本：信源只报成功案例，未给误报、漏报与巡检自身开销。
- 与「保留人工审查、逐步提高 AI 审查置信度」的渐进路线存在路线分歧，两种主张的实证对比尚无信源。
