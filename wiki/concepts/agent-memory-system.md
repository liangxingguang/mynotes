# Agent 记忆系统

## Definition（定义）

Agent 记忆系统是一套面向任务的信息管理机制，而非一个数据库：它负责把跨会话有价值的信息从对话中提取出来、分类保存，在下次任务需要时按任务动态检索回来，并持续更新、纠错、过期与优化。信源的立论基础：「模型会推理，不代表 Agent 会记忆；能存下历史记录，也不等于真正拥有一套记忆系统。」（粗体为信源强调）记忆系统至少包含三个层次：**存储**（让有价值的信息留下来）→ **检索**（让需要的信息及时找回来）→ **管理**（让记忆持续更新、纠错、过期和优化），最终目标是「在正确的时间，为当前任务提供正确、有效、可信，并且允许使用的信息」（信源原句）。

## Why It Matters（为什么重要）

- **上下文窗口做大不解决问题**：上下文服务于当前推理，模型能处理超长窗口也不意味着能判断哪些信息该长期保存、哪些已过期、哪些应在下次任务重新调用——放大窗口缓解"放不下"，不解决"信息管理"。
- **聊天记录解决保存，不解决管理**：历史可以原样存库，但下周问"继续完善方案"时，系统应找回"最终确定的方案 + 选择原因 + 未解决问题 + 汇报要求"，而不是重读全部聊天记录。
- **跨会话持续协作的根基**：没有记忆系统的 Agent 每次都是"新员工"；记忆是"养马"（Agent 越用越聪明）的核心机制。
- **记忆积累≠能力积累**：只有能在未来任务中被正确调用并持续改善实际结果的信息才构成有效记忆（信源论断）——记进去不代表产生价值。

## Core Characteristics（核心特征）

1. **五问框架**（信源提出的记忆系统验收标准）：什么值得记（一次性指令与稳定偏好不用同策略）｜什么时候去找（不是每次回答都需检索）｜找回来怎么用（多条记忆可能重复/过期/矛盾）｜新的信息怎么保存（新增/更新/丢弃）｜什么时候应该忘记（失效事实留在记忆里会干扰决策）。
2. **七模块双链路**：用户、Agent、记忆触发器、短期记忆、长期记忆、记忆管理器、知识库七个模块共同完成两条链路——信息流（提问→生成）与记忆流（提取→写入→维护）。
3. **检索全链路 10 步**：问题理解 → 触发判断 → 检索 Query 生成 → 三路并行召回 → 融合排序 → 增强上下文 → 生成，覆盖"从一次提问到结果产出"的完整调用链。
4. **业务事实是状态而非静态知识**：写入须有三态（新增/合并/更新），旧事实标记"已被替代"并保留版本；记忆有生命周期，须区分"有效性"与"重要性"（重要但过期≠保留；长期有效但不影响任务≠高排序）。
5. **反馈闭环决定质量**：五类指标（检索质量/任务效果/记忆准确性/运行成本/安全与权限）结合看，单纯提高召回率不保证任务效果；用户反馈须先判适用范围才能用于更新记忆。
6. **存储只是基础设施**：「存储只是记忆系统的基础设施，如何决定一条记忆的价值，才是记忆系统的核心逻辑之一」（信源原句），记忆管理器（检索、去重、排序、融合、更新、过期清理、重要性调整）承担真正的价值判断。

## Structure（结构）

七模块（信源拆解，各模块在双链路中分工明确）：

| 模块 | 职责 |
|---|---|
| 用户（User） | 记忆的主体与适用范围（个人/项目/组织） |
| Agent | 理解当前任务，并判断记忆是否必要参与 |
| 记忆触发器（Memory Trigger） | 记忆系统入口：判断当前任务是否需要历史、围绕什么检索（规则/分类器/模型判断均可，从简起步） |
| 短期记忆（Short-term Memory） | 当前会话关键内容、最近几轮交互、临时任务状态、未完成操作、中间结果；决定因素是生命周期与恢复语义，而非存储介质（信源点名可落 Redis/数据库） |
| 长期记忆（Long-term Memory） | 稳定偏好、已定关键决策、历史任务结果、可复用经验、对未来任务有帮助的重要事实 |
| 记忆管理器（Memory Manager） | 检索、去重、相关性排序、多来源融合、记忆更新、过期清理、重要性调整、策略优化 |
| 知识库（Knowledge Base） | 外部事实（企业制度、产品文档、业务数据），与长期记忆逻辑职责不同、实现可共用基础设施 |

信息流 vs 记忆流（两条链路一问一答）：

- **信息流**：用户提出问题，Agent 理解任务，系统检索相关信息，模型生成答案。
- **记忆流**：系统从对话和任务结果中提取有价值的信息，经过分类后写入记忆，再通过维护和优化，让这些信息在未来继续发挥作用。

检索调用 10 步（信源完整列举）：用户提出问题 → Agent 理解意图 → 记忆触发器判断是否检索 → 生成检索 Query（问题拆解）→ 三路并行召回 → 记忆融合与排序 → 增强上下文 → 模型生成结果。信源图例将三路召回拆为三步（STEP 05-07），与触发/生成等步骤合计 16 个处理步骤。

写回四步（记忆流的实现路径）：从对话中提取值得记住的信息 → 分类（四问）→ 写入（三态）→ 生命周期维护。

数据结构 11 字段建议（信源）：Memory ID / Content / Type / Source / Created At / Updated At / Valid Until / Confidence / Scope / Permissions / Status。

六阶段落地路线（信源工程建议，每阶段可独立产出价值）：任务状态管理 → 持久化记忆 → 记忆提取与分类 → 多路检索融合 → 安全与治理 → 评估体系。

## How It Works（运作方式）

### 检索链路：10 步的分工

1. **用户提出问题 / Agent 理解意图**：Agent 至少明确三件事——处理什么对象、希望完成什么任务、必须遵循的约束（如"上次确定的评估标准"），据此判断是否需要记忆参与（数学问题无需检索数月前的项目记录）。
2. **触发器判断**：对"继续上次的任务""按我之前的偏好"这类句式检索通常必要；问题只依赖当前输入则可跳过部分检索。触发器须平衡两个方向：既不能该查不查、也不该把不相关历史当成当前任务必要条件。
3. **生成检索 Query**：把原始问句拆解为具体查询条件（当前项目是什么 / 上次确认的标准 / 已形成的结论 / 任务进度 / 未决问题），让检索从"文本相似度匹配"转向"围绕任务目标找信息"——只拿原始问句做向量检索会找到大量谈"项目评估"的历史，却漏掉真正需要的那份决策结果。
4. **三路并行召回（信源最值得注意的设计之一）**：
   - 第一路：短期记忆——召回最近几轮对话、任务状态、临时信息，接上当前进度；
   - 第二路：长期记忆——召回历史决策、偏好、重要事实、可复用经验，补齐任务背景；
   - 第三路：外部知识——涉及当前业务数据/最新资料/企业制度时查数据库、知识库、网页或 API，给事实依据。
   
   三路解决不同问题，可并行执行，也可按任务类型动态选路（改代码主要靠短期记忆；按公司最新制度检查报销单则需业务规则 + 当前申请信息双路）。
5. **融合排序五维度**：相关性（与当前任务相关度）/ 时效性（现在是否有效）/ 可信度（用户明确确认 / 正式业务系统 / 模型推断）/ 重要性（含关键决策或约束）/ 冲突关系（能否按时间与权威来源确定当前有效状态）。信源示例：项目预算 100 万 → 两周前会议纪要 120 万 → 昨日正式审批 110 万，须解析出当前有效值为 110 万而非三值并列。语义相似只能回答"像不像"，不能独立判断"现在是否有效"；无法确定冲突时不应强行合并成看似确定的结论。
6. **增强上下文**：不是把历史记录拼接在问题后面，而是围绕当前任务组织——任务目标、相关历史事实、已确认决策、偏好与约束、任务状态、未决问题，以及关键事实的来源、时间与有效性。围绕任务整理的信息集合优于再塞十几轮完整对话。
7. **模型生成结果**：记忆只能提供信息、不保证答案正确；历史记忆错时，检索越准确错误被放大越深——故记忆系统须关注来源、可信度、有效期与冲突处理，而非只追求召回率。

### 写入链路：四步与三态

1. **提取**：偏好（"以后所有面向管理层的汇报先写结论再列数据和风险"）、业务事实、关键决策及原因、任务结果、项目状态变化、可复用经验。一次性指令（"这段再改短一点"）与稳定偏好（多次强调"技术文章要有工程细节"）须区分。
2. **模型推断须验证**：连续三次要求缩短文章可推断"偏好简洁"，但只是推断——成为长期偏好须明确确认机制或置信度渐进提升，否则一次偶然行为就贴上长期标签（信源）。
3. **分类四问**：只对当前有用还是未来反复使用｜遗忘它会不会影响后续任务｜有多稳定｜属于哪个范围（用户/项目/组织）。分类不必做成四个独立数据库，关键是逻辑上明确不同信息的用途、生命周期和更新规则。
4. **写入三态**：新增（有价值且此前不存在）/ 合并（高度相关且提供补充，关联或合并成更完整记录）/ 更新（改变有效状态，更新当前值并保留历史版本）。示例：上线时间 11 月改 12 月时，新记录标记当前有效、旧记录标记"已被替代"并保留变更记录——只追加会导致检索同时命中两个日期。企业业务事实随审批/订单/合同变化，只追加会让记忆越积越不可靠。
5. **生命周期**：过期、降优先级、去重合并、重新确认、用户删除处理、审计保留；分类型设策略——临时任务状态随任务结束清理、偏好在长期使用中验证修正、项目状态随推进更新、企业业务事实优先与权威系统保持一致。

### 反馈闭环：质量由使用结果定义

- **五类指标**：检索质量（找没找到、相关度、漏掉重要记忆）/ 任务效果（完成率、回答质量、连续性改善）/ 记忆准确性（错事实、误把推断当事实、过期未更新）/ 运行成本（延迟、Token、是否对简单任务做全量检索）/ 安全与权限（跨用户泄露、越权读取、来源与修改可追踪）。组合看待——为召回更多信息而塞入大量无关过期记忆，模型反而表现更差。
- **反馈先判适用范围**："你记错了"与修改答案都是高价值信号；但某次回答要简短≠以后都要简短，某项目方案临时改变≠组织标准变化——须判断反馈作用于当前任务/某项目/某类场景/长期偏好，否则局部变化被错误推广到所有场景。
- **越用越有用而非越用越复杂**（信源）：成熟系统未必记忆库最大、检索算法最复杂，而是越来越清楚什么值得保存、越找越准、重复犯错越少、失效记忆及时修正。

## Relationships（关系）

### Related Concepts（相关概念）

- [[agent-long-term-memory|Agent 长期记忆]]：互补路线——本概念给出检索/写入/管理与反馈的**全链路**视角，[[agent-long-term-memory]] 给出长期记忆的**存储接口与执行架构**视角（Hermes 四层、retain/recall 接口、before_agent_start/turn_end 扩展点）。两页合并读：一个管"记忆系统长什么样、怎么运转"，一个管"长期记忆具体怎么存、怎么接进 Agent Loop"。
- [[context-management|上下文管理]]：本概念是会话外（cross-session）层，[[context-management]] 只管一次推理内的窗口预算；「上下文窗口≠记忆」是本概念对[[context-management]]"忘事"问题（跨会话失忆）的正式回答——窗口内管理靠压缩/裁剪/隔离，窗口外靠本概念的检索写回。
- [[agent-evaluation|业务 Agent 全生命周期评测]]：本概念的五类指标（检索质量/任务效果/记忆准确性/运行成本/安全与权限）是[[agent-evaluation]]评测体系的子集/具体化；"反馈先判适用范围"是评测结论回流到记忆更新的纪律。
- [[rag-production-guardrails|企业级 RAG 生产护栏]]：知识库模块（外部事实检索）承接 RAG 能力，但 RAG 不解决记忆提取/偏好管理/状态更新/过期清理/用户纠正——"把 RAG 当完整记忆系统"是信源五坑之一。
- [[agent-as-memory|Agent as Memory]]：另一条路线——短期记忆职责交给主 Agent 的协调过程；本概念主张记忆系统是独立工程体系（七模块），两路线不互斥（作者在长期记忆文件化上与此互引）。
- [[agent-loop|Agent Loop]]：记忆读写挂在 Loop 的扩展点（会话前召回 / 轮次后写入）是标准接入方式；触发器判断即 Loop 内的门控。
- [[harness-engineering|Harness Engineering]]：记忆系统是 harness"上下文与记忆"观察面的工程落点（触发器、三路召回、写回均为 harness 层能力）。

### Distinctions（区分）

- **记忆系统 ≠ 上下文窗口**：前者跨会话、管信息生命周期；后者服务单次推理、管 token 预算。
- **记忆系统 ≠ 聊天记录库**：保存之外的筛选/组织/检索/更新四问决定可用性。
- **记忆系统 ≠ RAG**：RAG 提供检索相关性，记忆系统还提供更新、纠错、过期、冲突裁决与反馈闭环；知识库（外部事实）与长期记忆（用户/任务相关）职责分开，实现可共用——RAG 检索的是"事实"，记忆系统管理的是"状态与经验"。
- **长期记忆 ≠ 所有历史**：跨会话保留的是经提取的结构化事实与经验，原始对话可另走 Session Search（见 [[agent-long-term-memory]] 中 L2 层）。

## Open Questions（开放问题）

- 融合排序五维度的权重方案与量化口径：信源未给度量，只有定性原则与一个预算示例。
- 三路召回的选路规则：规则/分类器/模型判断的具体判别训练与评估方法信源仅给方向（从简、可观察、可评估触发策略）。
- 记忆冲突的自动裁决边界：信源主张"无法确定时不强行合并"，但什么算"可按时间和权威来源确定"未定义。
- 触发器的漏检/误触发代价权衡：信源提"两个方向平衡"，未给评估指标与数据。
- 六阶段路线中"评估体系"阶段的具体落地：信源只说"真实任务 + 测试集持续评估"，无方法细节。
