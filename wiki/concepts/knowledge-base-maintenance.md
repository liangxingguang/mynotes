# 知识库维护：检索之后的另一半

## Definition（定义）

知识库"后半段"能力的总称：知识进入库中之后，保持内容"活着"所必需的动作集合——在线编辑更新、结论刷新、过期资料下掉、缺陷修正、新增纳入。与"前半段"（文档解析、切片、向量化、检索问答）相对。核心命题：检索决定知识库"能不能找到"，维护决定知识库"值不值得信、能不能一直用"。

## Why It Matters（为什么重要）

- 知识库不是搭完就完了：文档要改、结论要更新、过期资料要下掉，这些日常动作若无入口，库会随时间失真，检索越准、错得越系统化。
- 主流开源方案重心全在前半段（解析/切片/向量化/建立链接），维护能力普遍只有"删掉重新上传"，形成产品化空白（WeKnora 案例）。
- 作者判断：检索那一半已不难（开源+AI 二开可落地），真正难、且没人替你解决好的是"知识怎么被持续维护起来"那一半。

## Core Characteristics（核心特征）

1. **维护动作清单**：编辑现有文档、更新结论、下掉过期资料、修正错误条目、新知识纳入既有结构（非简单追加）。
2. **编辑入口是硬门槛**：没有在线编辑=维护=删+重传再跑全链路；更新成本随库龄线性上升，维护动力随之衰减。
3. **维护质量门禁**（WeKnora 部门实践的三条边界）：①"没发现异常"≠"通过"，证据不足输出待确认清单给人拍板；②定量阈值用确定性规则算，AI 不当计算器；③未经人工确认的结论不进正式知识库。
4. **录入激励决定维护供给**：部门级维护靠人，问题分析专题库用固定字段模板降低记录成本 + 积分/排行榜激励录入（"榜一大哥"称号讨论中）。
5. **HUB 架构支撑跨应用维护**：统一资料/检索/权限层上，各子应用互供确认过的经验（原理图评审直接引用已确认的 MIC 电路问题），避免每应用自维护孤岛。
6. **理想形态=检索+编辑拼接**（作者观点）：知识库系统 + 在线文档双拼，才凑齐完整闭环。

## Structure（结构）

完整知识库系统 = 前半段（解析→切片→向量化→检索问答）+ 后半段（编辑维护→质量门禁→过期回收→录入激励→跨应用复用）。多数工具只做了前半段；后半段目前靠"维护流程约定 + 自动化巡检"补位（解读：如本仓库 raw append-only + wiki-ingest/wiki-lint 队列机制，见 [[llm-wiki]]）。

## How It Works（运作方式）

前半段解决"进得来、找得到"；后半段解决"活得久、信得过"：知识写入时经人工确认门禁进入正式库 → 日常维护提供编辑/更新/下掉入口 → 巡检机制发现过期与矛盾 → 激励与模板保证源头供给。任一环缺失，库的长期价值衰减（解读）。

### Distinctions（区分）

- 与数据备份/同步不同：维护是有语义的更新（改结论、下过期），不是文件搬运；"删了重传"之所以不算维护，是因为它不保留条目身份，无法表达"这条更新了/那条作废了"。
- 与知识录入（采集）不同：录入决定库的增量，维护决定库的存量质量；采集链路再顺，维护入口缺失，存量照样腐烂。
