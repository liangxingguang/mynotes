# LLM Agent 混合路由（规则路由 + 模型路由 + 级联降级）

## Definition（定义）

在 Agent 调用大模型之前插入的一层"难度判断"机制：把请求按简单/复杂分流到不同档位的模型，在成本与质量之间找平衡点。核心逻辑一句话——把简单任务交给小模型，复杂任务交给大模型。工程上真正落地的是**混合路由**三层结构；**级联降级**是与之并列、常被对比的另一种思路（先试小模型、不行再升级大模型），二者可叠加。

## Why It Matters（为什么重要）

Agent 起步阶段一律走最强模型是常见做法，但约 80% 请求是闲聊/FAQ/格式转换/简单总结类简单任务，小模型与大模型质量几乎无差距、价格差十倍，延迟从几十毫秒拖到秒级——一刀切大模型同时烧 API 账单与用户体验两份钱。路由层把这笔账系统化地省下来，且把"模型选择"从每次请求的拍脑袋变成可评估、可调优的工程闭环。

## Core Characteristics（核心特征）

1. **分层判断，没把握的往下传**：混合路由三层——高频简单场景规则兜底（零成本零延迟）→ 模糊地带路由模型打分 → 拿不准的一律大模型兜底。每层只处理自己有把握的请求。
2. **评分器优于分类器**：路由模型输出 0~1 难度分而非离散模型名，加模型只调阈值、不用重训，难度分比模型名稳定。
3. **冷启动保守**：无历史数据时全走大模型记录置信度，先只放行置信度极高（如 >0.95）请求给小模型，渐进降阈值；宁可多花钱，质量是底线。
4. **评估闭环驱动阈值**：记录每次路由决策，离线评估核心指标为"复杂请求错分给小模型的比例"，低于质量红线才灰度；阈值是活的，随评估数据持续调。
5. **级联降级有明确适用边界**：适合成本极其敏感、能容忍延迟的场景；对质量与延迟都有要求的场景，先路由再选模型优于先试再升级。

## Structure（结构）

混合路由三层（自外向内）：

1. **规则层**：if-else 拦截意图明确的高频简单 case（闲聊、FAQ 等）。
2. **模型层**：轻量路由模型对规则覆盖不到的长尾请求打难度分，按阈值映射模型档位。
3. **兜底层**：路由模型没把握的请求一律上大模型。

路由器训练的三件事：数据来源、分类器还是评分器、冷启动。训练数据三来源：全量大模型日志置信度、人工采样、主动探索（随机抽 5% 请求大小模型对比）。

## How It Works（运作方式）

- **规则路由**：零额外成本、零延迟、透明可审计；缺陷是规则膨胀（上线五条半年后五十条、互相打架）、识别不了"看着简单其实复杂"的请求（如"这个数对吗"可能是确认也可能是推理验证）。
- **模型路由**：轻量模型判断该走哪个模型，覆盖规则长尾；缺陷是需要训练数据、会误判，错分复杂任务质量当场崩掉。
- **级联降级**：请求先给小模型，置信度够高直接用，不够升级大模型重跑。成本测算（假设 70% 简单/30% 复杂，一刀切成本记 100）：级联总成本 50，理想路由 40，级联比理想多花 25%——多出来的是 30% 复杂请求被小模型"白试"一次的成本。三大坑：复杂请求走两遍延迟翻倍；置信度阈值太松放行复杂任务、太紧级联形同虚设；小模型"看着对、藏着微妙错误"的漏检下游才爆雷。
- **组合使用**：级联与混合路由可叠加（先路由判断该不该让小模型试，没把握的直接走大模型），但叠加带来更多状态与调试难度，起步阶段先跑通单条链路。

## Relationships（关系）

### Related Concepts（相关概念）

- [[thinking-mode]]：模型路由的两态最小规则（thinking 开关），面向推理能力分档，与本页的请求难度路由互补、不冲突。
- [[llm-inference-cost-governance]]：成本治理口径（CPS、路由期望成本、发布统计门禁），路由层是其"路由期望成本"的落地手段。

### Dependencies（依赖项）

- 需要请求分布分析与路由决策日志作为数据基础（无日志则冷启动与评估闭环无从谈起）。

### Distinctions（区分）

- 与**负载均衡路由**不同：本概念路由的是"模型能力档位"而非"服务实例"，判断依据是请求难度而非节点负载。
- 与**级联降级**的关系：混合路由先判断再选模型，级联先试再升级；二者可叠加但级联多花 25% 成本且延迟翻倍，适用场景更窄。
