# B端PRD写作框架（一图三表一份清单）

## Definition（定义）

让 B 端 PRD 达到"开发不骂人"的可执行颗粒度的写作框架（信源）：一图（主流程图，覆盖正向链路与核心逆向链路）、三表（状态流转表、字段规则表、异常边界表）、一份清单（上线前自检清单，覆盖非功能、权限、埋点、验收）。核心主张：开发骂 PRD 的本质不是文档不够长，而是信息没有对齐到可执行颗粒度；B 端面对的是组织、权限、状态、异常、审计、账号、规则的多维交叉（信源）。PRD 不是写给自己的，是写给研发、测试、未来接手的人看的（信源）。

## Why It Matters（为什么重要）

- 开发骂 PRD 的三个根因（信源）：背景和价值缺失（开发不知道为什么要做，只能按字面写代码）；范围边界不清（没写"不做什么"，小需求蔓延成大重构）；异常状态漏写（逆向流程、并发冲突、幂等要求没写清，开发上线后背锅）。
- （解读）框架的价值在于把"可执行颗粒度"拆成可核对的制品：图给流程、表给规则、清单给验收，每件制品都有固定字段，评审与开发自查都有抓手。
- 与 [[demand-review-sop|B端需求评审SOP]] 衔接（解读）：三表产出正是评审前三张表（业务目标范围边界/角色权限异常流程/验收标准回归范围）的素材来源，PRD 写好则评审冲突前置。

## Core Characteristics（核心特征）

1. **异常优先**：异常分支比正向流程更关键（车贷案例，信源）；逆向链路必须出现在主流程图中（信源）。
2. **表格化规则**：状态、字段、异常三类规则全部表格化，"开发可以看到规则边界，不会自己猜"（信源）。
3. **泳道图优于线框图**：主流程图必须含角色、系统、关键动作、分支条件，少用没有判断节点的线框图（信源）。
4. **范围显式化**：必须写"不做什么"，防止需求蔓延（信源）。
5. **清单收尾**：上线前自检清单覆盖非功能、权限、埋点、验收（信源；清单本体内容见 Open Questions）。

## Structure（结构）

```
B端PRD（开发不骂人）
├── 一图：主流程图
│   └── 角色 / 系统 / 关键动作 / 分支条件（正向+核心逆向）
├── 三表
│   ├── 状态流转表：当前状态 / 触发事件 / 前置条件 / 后置动作 / 下一状态 / 异常处理
│   ├── 字段规则表：字段名 / 类型 / 必填 / 枚举取值 / 校验规则 / 权限 / 示例
│   └── 异常边界表：异常场景 / 触发条件 / 系统行为 / 提示文案 / 处理人
└── 一份清单：上线前自检（非功能 / 权限 / 埋点 / 验收）
```

（结构骨架自信源；各表字段为信源原文列举。）

## How It Works（运作方式）

### 主流程图（含 EHR 案例）

必须包含角色、系统、关键动作、分支条件，建议用泳道图（信源）。案例：EHR 员工入转调离——员工发起转岗申请 → HRBP 审核 → 原部门负责人确认 → 新部门负责人确认 → 薪酬组调整薪资归属 → 系统生效；关键分支：新部门有试岗期要求则进入"试岗期观察"，而不是直接终态（信源）。

### 状态流转表（含 ERP 案例）

六字段格式：当前状态、触发事件、前置条件、后置动作、下一状态、异常处理（信源）。案例：ERP 采买入库单——当前状态"已审核"；触发事件"仓库发起部分入库"；前置条件"至少一个行项目库存可收"；后置动作"扣减计划入库数量、增加库存台账"；下一状态"部分入库"；异常处理"若收货数量超计划，进入差异处理流程，不允许静默通过"（信源）。

### 字段规则表（含 CRM 案例）

七字段格式：字段名、类型、必填、枚举/取值、校验规则、权限、示例（信源）。案例：CRM 客户公海规则——"客户状态"枚举：待领/已领/已返回/已成交/已流失，必填，枚举由规则引擎维护；只有"已领"才能进入销售跟进阶段；"已返回"不能直接改成"已成交"（信源）。

### 异常边界表（含车贷案例）

五字段格式：异常场景、触发条件、系统行为、提示文案、处理人（信源）。案例：车贷风控规则引擎——身份证号命中反欺诈灰名单；规则集执行到反欺诈节点；中断审批、生成风险单、通知用户支持口头沟通；提示文案"请补充资产证明"；处理人"风控专员"（信源）。

## Relationships（关系）

### Related Concepts（相关概念）

- [[complex-system-breakdown|五件套拆解]]：同构互补——五件套（业务对象/单据/状态机/权限/异常）回答"业务怎么拆"，本框架回答"PRD 怎么写"；状态流转表≈状态机表格化，异常边界表≈异常六要素表格化（解读）。
- [[demand-review-sop|B端需求评审SOP]]：本框架产出是评审前置三张表的素材；需求评审是 PRD 的下游环节（解读）。
- [[agent-prd-template|Agent 化 PRD 模板]]：本框架是"传统 PRD 部分（页面/字段/流程）"的底稿，Agent 化五模块（能力卡片/协作时序/护栏机制/评测集/指标）是其上的增量（信源+解读）。
- [[crm-system-design|CRM 系统设计框架]]、[[finance-reconciliation-design|财务对账与异常冲正系统设计]]、[[approval-workflow-engine|审批流引擎]]：分业务 PRD 重点速查表中的互证锚点（解读）。

### Dependencies（依赖项）

- 业务领域知识（ERP/EHR/车贷等模块的状态机与规则，信源案例）。
- 状态机与流程建模基本功（解读）。

### Distinctions（区分）

- 与 [[agent-prd-template|Agent 化 PRD 模板]]：本页管传统 B 端 PRD 的写法框架，Agent 化 PRD 在其上新增五模块，不是替代关系（信源+解读）。
- 与需求分析系列（工程实践视角的需求文档标准，如 [[2026-10-31-xuqiufenxi-09-hao-wendang-daodi|好的需求文档到底应该什么样]]）：该系列面向软件工程通用需求文档，本页面向 B 端产品 PRD 的表格化写作规范，颗粒度与受众不同（解读）。
- 与 [[enterprise-systems-map|B端企业系统全景地图]]：地图页给 10 系统四段式速查（定位/模块/指标/注意点），本页给 10 业务模块的 PRD 重点，角度不同且模块口径不同（见该页范围说明）（解读）。

## Evolution（演进）

- 2026-11-04：建页。首信源：B 端 PM 视角的"一图三表一份清单"框架与 10 业务模块 PRD 重点（专辑第 30 篇），单信源，置信度中。
- 2026-11-04：第二信源印证（专辑第 2 篇，工单系统 PRD）：流转表/字段表/验收标准三件套与"三表一份清单"同构——工单案例以状态机流转表（8 条流转规则）、18 字段表、五类可验证验收落地了框架主张"难点不是功能清单而是状态/权限/规则清晰"（详见 [[ticket-system-design]]）。
- 2026-11-04：第三信源印证（专辑第 23 篇，B 端埋点体系）：自检清单中"埋点"项展开为独立框架——埋点 PRD 六模块（文档信息/目标/事件清单/参数字典/上报策略/验收标准），详见 [[tracking-system-design]]。
- 2026-11-12：第四信源印证（需求分析系列总结篇，九段检查清单）：本框架"范围显式化"（必须写"不做什么"）与"清单收尾"（验收标准客观可测）两项主张获跨领域信源印证——该清单第六段验收标准明确"结果可客观检查，无'流畅''良好'等主观词"，第三段范围界定明确"必须做/可后做/明确不做"三栏，与本框架立论一致（见 [[requirements-doc-checklist]]）。
