# 工单系统设计（B端）

## Definition（定义）

工单系统：以统一入口承接分散任务（IT 报修、售后支持等），以"创建→分配→处理→关闭→统计"闭环实现"任务可追踪、流程可约束、结果可统计"的 B 端系统（信源）。其设计框架由五件套构成：三类角色权限矩阵、生命周期状态机与流转表、五大功能模块、字段设计原则、可验证的验收标准（信源）。核心主张（信源）：工单系统 PRD 的难点不是功能清单，而是状态、权限和规则是否清晰。

## Why It Matters（为什么重要）

- 无统一工单入口时，任务来源散落在 email/微信/口头沟通，处理无记录、无时效管理、无法统计效率（信源）。
- 状态流转是 PRD 核心，建议用状态机而非纯文字描述，避免开发理解偏差（信源）。
- 权限矩阵是开发容易遗漏的部分，写清"数据范围"与"执行动作"，测试才能按矩阵验权限（信源）。
- 验收标准必须可验证，避免"体验良好"类笼统描述，否则开发/测试/业务无法对齐（信源）。
- （解读）工单系统是 ITSM 的轻量入口形态：[[enterprise-systems-map]] 给 ITSM 四段式速查，本页给工单子系统的落地结构。

## Core Characteristics（核心特征）

1. **状态机为骨架**：五态（待受理/处理中/已处理/已关闭/已驳回）+ 流转表六要素（当前状态/触发动作/执行人/前置条件/下一状态），每条流转形成闭环、避免循环；管理员保留强制关闭能力（信源）。
2. **权限矩阵双维度**：数据范围（自己创建的/分配给自己的/全量）× 执行动作（信源）。
3. **多入口创建 + 统一编号**：门户/email/微信服务号/内部系统各入口字段差异与校验规则不同；编号=类型前缀+日期+顺序号（如 GD20250601-001）（信源）。
4. **自动路由分配 + 兜底**：按类型+组织架构+处理人负载路由；路由失败自动进默认处理组并提醒管理员（信源）。
5. **SLA 时效 + 分层超时提醒**：按优先级设响应/处理时限，超时经站内信+email 提醒处理人及其上级（信源）。
6. **字段去冗余**：关联对象只存 ID 和类型，展示层再查询（信源）。
7. **留痕与埋点**：流转动作全留痕（执行人/动作/前后状态/时间）；埋点 5 核心事件（见 [[tracking-system-design]]）（信源）。
8. **验收五类可验证**：功能/权限/数据/性能/兼容（信源）。

## Structure（结构）

五大功能模块（信源）：

| 模块 | 要点 |
|---|---|
| 工单创建 | 多入口字段差异与校验规则；email 抓主题为标题、正文为描述；服务号允许上传图片 |
| 工单分配 | 自动分配（类型+组织+负载路由）/人工转派/接单模式；路由失败兜底 |
| 工单处理 | 处理记录（文本/附件/图片）；申请关闭至少一条记录；SLA 提醒；模板回复 |
| 工单关闭 | 提交人确认或 X 天自动关闭；关闭前提醒策略；关闭后评价（响应速度/处理质量/服务态度） |
| 查询与统计 | 多条件查询；工单量/平均处理时长/SLA 达标率/满意度；报表权限仅管理员与负责人 |

字段设计：18 个关键字段，类型/必填/规则在 PRD 中写明（信源）。

## How It Works（运作方式）

- 生命周期：创建（待受理）→ 接单（处理中）→ 申请关闭（已处理）→ 确认关闭（已关闭）；异常分支：驳回（已驳回→修改后重新提交）、转派、重新打开（已处理→处理中）（信源）。
- 自动分配按"类型+组织架构+处理人负载"路由，接单模式适合处理人池（信源）。
- SLA 按优先级配置时限，超时提醒沿"处理人→上级"层级传导（信源）。

### Dependencies（依赖项）

- 组织架构与角色数据（分配路由依赖处理组/组织 ID，信源）。
- SLA 配置与通知渠道（站内信+email，信源）。

### Distinctions（区分）

- 与 [[approval-workflow-engine|审批流引擎]]：工单状态机以任务闭环为目标（接单/转派/评价），审批流以多角色签核为目标；工单可含审批子流程但重心在任务追踪（解读）。
- 与 [[enterprise-systems-map]] 的 ITSM 口径：ITSM 是 10 系统全景中的服务管理大类，工单系统是其入口级子系统，本页粒度更细（解读）。
