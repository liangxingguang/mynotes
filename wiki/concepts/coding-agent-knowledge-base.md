# Coding Agent 知识库（域—场景—知识建模方法）

## Definition（定义）

面向 Coding Agent 的知识库构建方法论：把业务知识当作可版本化的工程产物，按"业务域—业务场景—共享知识"三层建模组织，用层次索引 + Agentic Search 让 Agent 按需消费并回源核验，借 LLM 编纂与 Git 治理完成知识的持续演进。由淘宝直播互动团队的 LiveX Wiki 实践系统阐述（单一信源，转述自信源）。

## Why It Matters（为什么重要）

通用 Coding Agent 能快速实现函数签名与局部逻辑，但跨仓跨端、含业务黑话与复杂配置的需求，直接喂原始 PRD 产出不可用。向量 RAG 能扩大召回，却只返回"语义相似"的点状材料，整体视角、业务归属、影响范围与新鲜度仍需临时拼装。该方法论把知识供给从"材料检索"升级为"按业务结构理解"：以场景为知识单元，让 Agent 在每个阶段只取用此刻需要的层次，并把"读到知识"与"核实实现"分成两个完成条件。

## Core Characteristics（核心特征）

1. **四条设计约束**（第一性原理推导）：①按需供给而非全量堆给；②按业务结构组织而非条目堆积；③给可核验的路径而非只给可引用的结论；④有生命周期、随变更演进（知识像代码一样版本化）。
2. **三层建模**：业务域承载职责/边界/维护人/场景入口；业务场景（核心知识单元）保存页面或系统全景、核心接口链与查证路径；共享知识（平台接入/规范/共用概念）独立维护、通过已核实的直接依赖被场景引用，避免复制后各自过期。
3. **场景划分三准则**：可独立理解、可明确归责、可单独核验。场景过大扩大核验范围，过小退化为需临时拼装的碎片。
4. **消费五步与终止条件**：发现域 → 选择场景 → 按需求选链 → 展开必要依赖 → 回源核验。证据齐备即停，重复或未命中时报告缺口，来源不可达时不把"查不到"推断成"没有影响"；消费过程保持知识只读。
5. **知识版本与事实版本分开管**：业务地图（知识版本）帮助缩小调查范围，源码与运行平台（事实版本）决定本次实现依据。
6. **工程治理演进**：LLM 负责理解与核验，程序负责结构和范围，Git 负责版本与发布；自更新与自审查先形成候选，经结构检查、质量门禁与评审后受控发布。

## Structure（结构）

三层知识对象与工程约束（信源）：

| 知识对象 | 负责表达 | 对应的工程约束 |
|---|---|---|
| 业务域 | 一组能力的职责、边界、维护人和场景入口 | 场景有唯一归属，先确认域边界再进入场景 |
| 业务场景 | 页面或系统职责的全景、核心接口链及查证路径 | 一个场景一份权威地图，源码变化按场景汇总；内部沿 真实接口→服务编排→核心模块→底部依赖 建立查证路径 |
| 共享知识 | 平台接入、规范、共用概念和约束 | 独立维护，通过已核实的直接依赖引用 |

知识库规则由仓库级 AGENTS.md（入口、读取顺序、行为边界）与 MAINTENANCE.md（生产、维护、发布流程）承接，能力封装为统一 Skill 对 Agent 提供。

## How It Works（运作方式）

**生产（冷启四动作）**：①固定来源与版本（每仓绑定本轮提交）；②两轮搜索跨术语差异（业务行为/页面文案找候选 → 已确认标识反查）；③从入口向下追、从消费者反向查（枚举 API/消息/调度/扩展点，正反向调查判断场景完整性）；④LLM 核实后编纂，未闭合证据单独列出。人工定场景边界与责任，业务歧义交负责人确认，待确认项不作为实现依据。

**消费（渐进披露协议）**：确定性程序生成发现清单（域/场景名称、别名、摘要），Agent 判断相关性后逐层展开；回源核验逐项建立"导航断言—当前事实—核验结论"对应关系。

**迭代（三机制）**：知识自更新（代码 diff → 跨仓影响汇总 → 同一场景的一次候选修订）；知识自审查（定期回源查事实与覆盖，沿两个方向寻找遗漏，无代码提交的场景也要检查运行控制变化）；Git 治理（独立候选分支、工作区与变更评审，重试复用候选，确保合入内容即本轮完成核验的内容）。

## Relationships（关系）

### Related Concepts（相关概念）

- [[llm-wiki|LLM Wiki]]：模式基础——本方法以 LLM Wiki 编纂业务理解，并补上面向 Coding Agent 的场景化建模、消费协议与 Git 治理。
- [[okf-knowledge-format|OKF]]：表达层——借鉴 OKF 轻量文件思想，用 Markdown + YAML frontmatter 声明知识身份、来源与依赖，使人可审阅、程序可检查、Agent 按结构读取。
- [[knowledge-base-maintenance|知识库维护]]：本方法的迭代段（LLM 增量更新 + 全量审查 + Git 受控发布）是维护职责工程化治理的一个具体答案，但业务判断准确性仍由人兜底。

### Dependencies（依赖项）

- 依赖 [[llm-wiki]] 的编纂模式与 [[okf-knowledge-format]] 的表达约定；脱离二者，"场景知识"缺少编译与表达载体。

### Distinctions（区分）

- 与向量 RAG（未立专页，见 [[rag]]）：RAG 在查询时按语义相似召回点状片段；本方法在入库时按业务结构编译，检索退化为"层次导航 + 回源核验"。信源明示其局限针对当时的知识组织与消费方式，并非所有 RAG 方案的必然限制。
- 与 Ontology/知识图谱：Ontology 显式建模对象、属性、关系与动作，语义约束更强但建模与维护范围更大；本方法以场景为单元保留足够语义结构、控制建模范围，契合知识导航任务（信源取舍）。
- 与 [[agent-memory-system|Agent 记忆系统]]：本方法供给的是业务知识的工程化上下文，不是 Agent 经历的事实记忆。

## Evolution（演进）

- 2026-11-20 — 据淘宝直播互动团队 LiveX Wiki 信源立概念页。该实践给出"域—场景—知识"三层建模、消费五步协议、生命周期三段的完整工程方案与同批次量化评测（端到端生码较无知识库平均相对提升约 39.15%、较 RAG 约 30.1%，仓库定位准确率 60%→90%）。

## Open Questions（开放问题）

- 方法论的跨业务普适性：场景划分依赖业务判断，能否在跨端跨仓、持续变化且反复开发之外的业务类型上复现，尚无第二信源验证。
- Git 治理对业务事实准确性的边界：版本管理保证可追溯与可回退，不保证业务判断正确，人兜底的成本模型无量化数据。
- 消费成本：逐层读取与回源核验有调用成本，受控对照（关闭依赖展开、调整回源核验）分离质量与成本来源的后续结果未见披露。
