# 架构设计 | 积分系统：并发扣减、分批过期、幂等、冲正与对账

## Overview（概览）

从一笔积分消费推演整个积分系统架构——用户有 110 积分（B001 批次 50 于 9/30 到期 + B002 批次 60 于 12/31 到期）消费 80，客户端超时重试、几天后订单退款。难点不在加减，而在回答「第一次成功没有、重试会不会重复扣、80 来自哪些批次、退款怎么退、缓存/MQ/过期任务失败后怎样证明余额仍正确」。八步推演：定不变量 → 总体架构 → 6 类数据模型 → 写入链路 → 异常恢复 → 扩展 → 上线 → 演进。

## Key Facts（关键事实）

- 五条不变量：①同一业务操作只生效一次；②可用积分不能扣成负数；③余额变化有不可覆盖的历史；④退款与修正必须留新记录；⑤余额能由交易、流水、批次共同解释。排行榜可晚几秒，余额、幂等结果、账务历史不能。
- 教学假设：1000 万注册用户、查询峰值 2 万 QPS、变更峰值 3,000 TPS；还要看**单账户最大并发写入**（决定行锁/乐观锁/条件更新选型与热点账户限流）。
- 6 类数据：账户快照、积分交易（幂等键唯一）、账户流水（只追加）、积分批次（来源/到期日/剩余量）、批次消耗明细、发件箱事件（与核心变更同事务提交）。消费 80 的实例：交易 T001、流水 L001（110→30）、批次消耗 A001（取 B001 的 50）/A002（取 B002 的 30）、快照 30、发件箱 E001（points.consumed）。
- 幂等键 = 业务方 + 业务单号 + 操作类型；「消费/冻结/确认扣减/取消冻结」是不同操作。网关可拦重复流量，但**最终幂等必须由积分核心持久化并用数据库唯一约束守住**。
- 一次消费的本地事务 7 步：建交易（已存在返回原结果）→ 锁账户或版本号 → 原子扣减且 ≥0 → **按「较早到期优先」消耗批次** → 写批次消耗明细 + 追加流水 → 更新快照 + 写发件箱 → 提交。**绝不能先读余额、应用里判断后无条件覆盖**。
- 冻结不是固定步骤：一次调用能完成的兑换直接扣减；只有订单之后还可能确认或取消时才用「冻结 → 确认扣减／取消解冻」状态机。
- 缓存与事件：Cache-Aside 先提交 DB 再删缓存，删除失败由账务事务里的失效事件重试；需通知多系统或削峰时再送 MQ，**MQ 不是发件箱的必选项**。热点失效用请求合并或短期租约，回填前再校验版本；**扣减始终以数据库为准，不能按 Redis 余额记账**。事务发件箱不保证只处理一次，消费者仍要幂等。
- 异常恢复：超时重试靠同一幂等键返回首次状态；**退款是新增冲正交易 + 反向流水，绝不删原流水**，按批次消耗明细找回原批次；过期任务按批次处理 + 稳定任务标识 + 调度租约防重复清零。
- 对账三类关系：余额与流水批次汇总一致、业务与积分系统总量与逐笔状态对应、发件箱与下游读模型有无长期未完成记录。**自动发现问题 ≠ 自动改账**。
- 扩展顺序：查询多→缓存 + 异步读模型（读模型不能用于决定能否扣分）；核心数据多→**先归档再决定是否分片**；真到上限才按账户标识稳定路由，流水量大时在分片内按时间分区，**不要只按时间把同一账户打散**（否则幂等键无法靠单库唯一约束全局去重）。热点账户加实例无效，靠限单账户并发、按序执行、缩短事务、拆子账户。
- 演进四步：先把账记对（模块化单体 + 本地事务闭环）→ 再移开非核心工作 → 按瓶颈扩展（容量到才分片、团队多了才拆服务）→ 提高恢复等级（抵扣高价值权益后才加强清算/容灾/审计）。

## Important Claims（重要论断）

### 方法论主张：先画清业务边界、核心流程、数据关系，再给出当前真正要落地的架构

可能出现的下一步另用演进图说明并写清触发条件。「思考尽量完整，落地保持克制，演进路线提前留好」。

### 账务设计的选型标准：余额能否被历史记录完整解释

单一平台规则简单时「账户快照 + 不可变流水 + 积分批次」已够用；涉及多发行方、商户结算或账户间价值转移才上复式记账——**积分子账不等于企业财务总账**。

## Implications（影响／启示）

- 账务系统的「历史可解释性」是数据模型设计的第一判据：每条余额变化必须能追溯到交易、流水、批次三层记录。
- 批次消耗明细是冲正的前提：没有「80 来自哪些批次」的记录，退款就无从恢复。
- 分片路由键必须包含账户维度：只按时间路由会让幂等键失去全局唯一约束的落点。
- 冻结状态机不是标配：只有「订单之后还可能确认或取消」的业务才需要。
