# 不审代码，靠什么兜底

## Overview（概览）

微信公众号方法论文章，是《代码审查退场》讨论的续篇。文章回应两个尖锐反问：热路径里的隐蔽坑不审代码怎么防、线上出事人背锅没底气怎么办。结论：code review 只是手段、缺陷必然逃逸，质量底座应转向架构隔离与线上闭环——收缩输入边界、隔离爆炸半径、影子流量对比、持续巡检、秒级回滚，并借传统工厂的质量控制方法与神经网络的线上保命机制兜底。

## Key Facts（关键事实）

- 典型业务系统中纯规则代码与神经网络组件占比当前约**九比一**，作者预判几年内可能滑向**六比四**；剩下六成确定性代码绝大部分由编码智能体生成（作者估计口径，无第三方数据）。
- 神经网络组件（推荐排序、风控拦截、内容审核、客服路由、意图识别）已跑在支付风控、广告竞价、自动驾驶、医疗影像生产环境，靠影子流量对比评测、分片测试、运行时阈值、监控熔断存活。
- 作者实战：每天定时把 **AWS CUR2 账单明细与运行指标**喂给巡检智能体，揪出跨应用隐患——不必要的 **CloudFront 缓存失效**、**KVS 读放大**、**DynamoDB 无效写入**、**S3 冗余读写**。
- 热路径性能暗雷实例：网关入口中间件每次请求重复编译正则、重复反序列化静态路由策略，单测全绿，高峰时 CPU 打满、长尾延迟飙升。
- 工厂三招：N-sigma **统计抽检**校准流水线、丰田**安灯系统拉绳停线**、**蟑螂法则**全库扫同类问题并沉淀为编译器规则/Linter/回归测试。
- 线上闭环四件套：影子模式镜像流量逐笔比对（输出差异/延迟分布/内存占用）→ 小比例灰度放量 → 限流/降级/熔断开关 → 指标越线后几十秒内无损切回上一版。
- 引用文本：《孙子兵法·兵势》「求之于势，不责于人」；《庄子·养生主》「以神遇而不以目视，官知止而神欲行」。

## Important Claims（重要论断）

### Claim 1：code review 不是可靠兜底，缺陷必然逃逸

热路径性能暗雷连资深工程师都只能靠碰运气拦下，靠老专家「状态在线又熟悉链路」不叫工程保障；代码里的缺陷无论人写还是智能体写都躲不掉，「事前全知」的执念在复杂系统里不成立。（作者论断）

### Claim 2：底气来自风险控制机制，而非读过每行源码

对标民航机长与芯片架构师：他们不逐行审飞控源码、不肉眼核对晶体管连线，底气来自边界隔离、冗余备份、仪表盘与把后果锁死在局部的安全机制。代码规模与变更速率翻十倍后，「人眼通读」的安全感已失效。（作者论断）

### Claim 3：部分核心逻辑天生无法 code review

四成神经网络组件逐行审查是天方夜谭，质量底座必须放弃「事前全靠人眼审透」的幻想，默认缺陷逃逸，转向架构隔离与线上闭环。（作者论断）

### Claim 4：终极目标是压爆炸半径、缩修复闭环

「把任何未知缺陷的爆炸半径压到可控范围，同时把发现和修复的闭环缩到最短」；人类、智能体、黑箱神经网络惹出的祸模样相似（延迟飙升、错误率抬头、账单失控、数据写脏），须用同一套防线应对。（作者论断）

### Claim 5：演进须分层，不可一刀切

新项目/AI 原生团队可直接重造交付流水线；债台高筑、测试稀烂的老团队须先补齐自动回滚、监控闭环、隔离边界，再逐步撤人工审查，贸然撤审查无异于闭眼飙车。（作者论断）

## Implications（影响／启示）

- 对 Agent 化交付流水线的启示：质量管理从「合并前人工把关」转向「事前硬约束 + 事中隔离 + 事后持续巡检」的完整防线，传统 CI 的一次性准入考试思路需重做（解读）。
- 人的工程角色从「读过所有代码」转为「亲手设计并验证风险控制机制」，从手工作坊跨入系统工程（解读）。
- AGENTS.md 类提示词软约束不可靠，须以语言子集收缩、依赖白名单、静态检查硬规则等工具链手段扎紧笼子（解读）。

## Limitations（局限）

- 单信源、公众号作者方法论自述，无第三方实证；九一/六四占比、CUR2 巡检成效均为作者口径。
- 前篇《代码审查退场》未入库，本文对其立场的承接只能从本文转述中得知。
- 工厂三招与神经网络保命机制的迁移适用性未经独立验证；「撤人工审查」的具体阈值与节奏未量化。
