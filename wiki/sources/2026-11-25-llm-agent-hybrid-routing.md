# 大模型 Agent 混合路由详解：规则路由、模型路由、级联降级一篇讲透

## Overview（概览）

微信公众号技术文章。针对"Agent 一律走最强模型"的常见起步方式，算清成本与延迟两份账，对比规则路由、模型路由、混合路由三种判断思路，给出路由器训练的三件事（数据来源、评分器优于分类器、保守冷启动）、离线评估口径，并分析级联降级的成本测算与三大坑，最后落到五条工程建议与两个常见误区。

## Key Facts（关键事实）

- 典型请求分布：约 80% 为闲聊/FAQ/格式转换/简单总结等简单任务，强推理复杂任务约两成；简单任务小模型与大模型质量几乎无差距、价格差十倍，延迟从几十毫秒拖到秒级，一刀切大模型烧两份钱（API 账单 + 用户体验）。
- 规则路由：零成本零延迟、透明可审计，但规则会膨胀、互相打架，且识别不了"看着简单其实复杂"的请求。
- 模型路由：轻量模型做判断，覆盖规则管不到的长尾，但需要训练数据、会误判，错分复杂任务给小模型质量当场崩掉。
- 混合路由三层结构：高频简单场景规则兜底 → 模糊地带路由模型打分 → 拿不准的一律大模型兜底；精髓是"每层只处理自己有把握的，没把握的往下传"。
- 路由器训练数据三来源：全量大模型日志置信度、人工采样、主动探索（随机抽 5% 请求大小模型对比）。
- 评分器（输出 0~1 难度分）优于分类器：加模型只调阈值、不用重训。
- 冷启动铁律：初期全走大模型记录置信度攒数据，先只放行置信度极高（如 >0.95）请求给小模型，渐进降阈值；宁可多花钱，质量是底线。
- 离线评估核心指标：路由把复杂请求错分给小模型的比例，低于质量红线才灰度。
- 级联降级成本测算（假设 70% 简单/30% 复杂，一刀切成本记 100）：级联总成本 50（比一刀切省一半），理想路由 40，级联比理想多花 25%（复杂请求被小模型白试一次）；且延迟翻倍、阈值难拿捏、存在"看着对藏着错"的漏检风险。适合成本极其敏感、能容忍延迟的场景。
- 五条工程建议：先做请求分布分析；从"规则加兜底"起步；评分器优先、阈值留调整空间；冷启动保守；记录每次路由决策形成评估闭环。
- 两个常见误区：阈值当成一次性配置；只盯成本不看质量红线——路由要算总账。

## Important Claims（重要论断）

### Claim 1

路由的核心不是模型选择问题而是工程问题：把"每一分钱花在该花的地方"做成可持续运转的系统（规则拦截 + 模型打分 + 大模型兜底 + 评估闭环）。

### Claim 2

级联降级与混合路由不是二选一，可叠加使用，但叠加增加状态与调试难度，起步阶段应先跑通单条链路。

### Claim 3

冷启动阶段质量优先于成本：宁可多花钱，不让质量出问题；成本优化是锦上添花。

## Implications（影响／启示）

- 对 Agent 平台设计：模型调用前应设路由层，按请求分布做成本/延迟/质量三账合算，并建立路由决策日志作为评估闭环的数据基础。（解读）

## Limitations（局限）

- 单一信源（微信公众号技术自媒体），成本数字（80% 分布、价格差十倍、级联 25% 等）为作者举例测算，未经独立验证。
- 未覆盖路由在多 Agent 编排、工具调用链等更复杂场景下的形态。
