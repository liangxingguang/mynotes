# RAG 是什么：RAG 的整体技术架构

## Overview（概览）

微信公众号 RAG 系列的开篇综述（系列第 1 篇，教程式文章）。从 LLM 的六大缺陷（幻觉、知识滞后、隐私、上下文窗口有限、输入噪声、成本高）切入，讲 RAG 的破局思路：结合检索系统与生成模型，从外部知识库检索相关内容作为 Prompt 输入，增强知识密集型任务。随后给出 RAG 系统五组件与离线/在线技术架构，驳"RAG 已死"论（RAG/长上下文/微调/MCP 互补而非替代），辨析传统问答/FAQ/RAG 三种形态与双层知识库设计，梳理 Naive→Advanced→Modular 技术演进路线，并以"天地之间"框架（数据细节为地、系统架构为天，中间为索引构建与检索策略）收尾，列出落地七大误区。

## Key Facts（关键事实）

- RAG 即检索增强生成：结合检索系统和生成模型提高语言生成的准确性和相关性，通过从外部知识库检索相关信息作为提示（Prompt）输入给大模型，增强知识密集型任务能力。
- LLM 六大缺点：幻觉（无答案时提供虚假信息）、新鲜度（知识更新滞后）、数据安全与隐私、Context Window 有限、输入杂乱影响理解、输入越多推理成本高且速度慢。
- RAG 优势：生成时引入外部知识；内部知识容易修改甚至实时补充；相比微调具备可观测性、可解释性，可有效降低幻觉。
- 三大困境对照：知识实时性（大模型训练数据时间截断 vs RAG 实时检索最新文档）、事实准确性（幻觉 vs 先检索证据再严格基于内容生成）、领域适配成本（微调需大量标注与算力 vs RAG 仅需构建领域文档库，如法律/医疗场景）。
- RAG 特点：可扩展性（企业知识库以 TB/PB 计，远超长上下文窗口承载能力）、准确性（长上下文存在"上下文悬崖"）、延迟与效率、数据隐私（支持基于角色的访问控制）、部署资源受限（Qwen-14B 在 A100-40G 上仅能接收约 20k token）、实际案例（即使百万 token 窗口也仅相当于 1500 页文档）。
- RAG 系统五组件：Chunk（切块）、Embedding（向量化）、Vector Database（常见 Milvus、Weaviate、Pinecone）、Retrieval（检索）、Generation（生成）；切块+向量化+建库为离线部分，检索+生成为在线部分。RAG 是一个系统而非单一组件，LLM 只是其中一个组件。
- "RAG 已死"驳论：Meta AI 的 RAG 原文作者的初衷是结合参数化记忆（模型本身知识）+ 非参数化记忆（外部检索知识）扩展知识库，解决私有数据无法访问、参数知识过时、幻觉与归因问题。RAG vs 长上下文 vs 微调 vs MCP 不是"你死我活"，而是互补：RAG 获取外部知识、微调优化处理与应用、长上下文承载更多检索信息、MCP 简化工具/Agent 集成；类比硬盘与内存各司其职。结论：RAG 是 AI 知识利用的基础设施，真正有价值的是检索+长上下文+微调+MCP 的组合拳。
- FAQ vs RAG：FAQ 是"预设答案库"，关键词或语义匹配、直接返回已有答案、可脱离 LLM、简单轻量；RAG 是文档切块向量化后由 LLM 综合检索结果生成，能推理组合、更灵活。双层知识库：第一层 FAQ 知识库（人工标注、领域专家撰写审核、针对高频标准问题、目标"零偏差"），第二层向量知识库（操作手册/行业规范/领域文档等语料，处理长尾复杂查询）。
- 技术架构：离线 = 文本切块→分词向量化→文本索引/向量索引；在线 = 文本混合检索 + 向量检索→重排序→TopK 文本块与用户问题一起送入大模型生成。
- 技术演进：Naive RAG（2023 年，检索结果直接组装提示词）→ 高级 RAG（前优化：查询改写/路由；后优化：重排序/融合）→ 模块化 RAG（检索、重排序、OCR 等组件可插拔、松耦合、各组件独立评估配置）。
- "天地之间"框架：地 = 数据细节（业务数据独一无二、含隐私数据，RAG 落地必须先做数据分析、把数据细节做好）；天 = 系统架构（工程架构，保证系统整体最优而非局部最优，优化检索或优化大模型不一定对整体最优）；中间 = 索引构建（离线文档解析、知识入库构建向量 embedding、数据库选型）+ 检索策略（全文检索、向量检索、检索前多轮 query 改写、检索后整合排序排版）。
- 落地七大误区：①数据不分析不分库；②过度依赖通用混合检索（全文+向量），应按提问特征分析单路或混合；③切块粒度一刀切（默认 256/512，法律类文章用 512 更合适，应开放接口让用户按业务选）；④误将召回率等同于检索效果（更需关注精确率/准确率，看 TOP1/TOP3/TOP5/TOP10 与 NDCG）；⑤生成阶段过度依赖大模型（提示词须约束"严格基于内容、与用户问题相关"地回答）；⑥忽视用户查询意图（需查询改写把口语化提问标准化）；⑦缺前置意图分类与分发（不同知识库分开存放，先意图分发再改写检索更准）。
- 主流开源框架：文中点名 RAGFlow、QAnything，另有"RAG 开源框架对比"与"RAG 自研技术架构"两节，但正文均只有配图无文字，未收录实质内容。

## Important Claims（重要论断）

### RAG 是系统而非单一组件

RAG 由切块、向量化、向量库、检索、生成等多个组件组成，LLM 只是其中一个组件；离线与在线两部分分工明确，搭建与调试应从系统整体出发。

### "RAG 已死"是错误二分法

长上下文出现后"RAG 已死"的说法不成立：RAG/长上下文/微调/MCP 各改不同变量、互为补充，RAG 不是过时替代品，而是 AI 知识利用的基础设施，组合拳才有价值（支撑 [[rag]] 的四条路对比与 Distinctions）。

### 落地的关键在"天地之间"的取舍

RAG 思想简单（检索增强生成），难在普适推广：必须做好数据细节（地），同时以系统整体最优而非局部最优设计架构（天），索引构建与检索策略居中衔接；任何检索优化都可能引入杂质，须测试并适配业务。

### 评估不能只看召回率

召回率不等于检索效果：必须结合精确率/准确率与 TOP-K 排序质量（TOP1/3/5/10、NDCG）评估，仅"召回来了"不能说明回答质量。

### 查询意图是检索质量的隐藏前提

用户提问偏口语化时，直接检索易命中无关内容；查询改写与前置意图分类分发（不同知识库分开检索）是提升准确度的必要动作。

## Implications（影响／启示）

- RAG 系统设计应先回答"地"的问题：数据是否分析过、是否分库、切块粒度是否按文档类型调整，再谈检索与生成策略。
- 检索路线（单路 vs 混合）应按用户提问特征选择，而非默认混合检索；评估口径应从召回率转向精确率+排序质量。
- 提示词必须显式约束模型"严格基于检索内容、与用户问题相关"地回答，否则检索引入的杂质会被模型照单全收。
- 意图分发（前置分类+分库检索）是易被忽视但性价比高的环节，FAQ 层与向量层可分工覆盖高频与长尾。
