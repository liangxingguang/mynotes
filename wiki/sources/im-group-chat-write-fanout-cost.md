# IM千人群聊该不该用消息写扩散？详细算算成本账！

## Overview（概览）

拉丁解牛说技术在 SegmentFault 发表的 IM 群聊写扩散工程成本分析。以「千人群一条 7 字消息」为样本，把写扩散的服务端账单逐项拆开（副本扇出、路由、未读、推送），并给出扇出位置、副本指纹、MQ 批量化、双轨存储、失败处理的完整设计要点，最后对比钉钉/微信/企业微信三家的大群方案选型。

## Key Facts（关键事实）

- 千人群一条消息，写扩散下服务端约 3000~5000 次后端操作（999 副本扇出 + 路由查询 + 未读写入 + 三方推送）。
- 单条 MQ 写入 ~1~3ms，999 条串行 ≈ 1~3 秒；100 个活跃千人群 → broker 每秒约 10 万条扇出消息。
- MQ 批量化（50 人/批）把 MQ 写次数从 999 降到 ~20，吞吐提升一个数量级。
- 副本指纹格式：`uuid|G<short_id>`，下游历史库/离线/已读聚合靠它区分原消息与副本。
- 双轨存储：历史库只存 1 条原消息，离线盒子存 N 条副本；历史库消费者按 uuid 是否含 `|G` 决定入库或丢弃。
- 重试 3~5 次上限后进死信队列；发送方在原消息入库即 ACK，不感知扇出失败。
- 群规模分档：100 人舒服、1000 人需批量化、5000 人需专项优化、10000 人写扩散走不通。

## Important Claims（重要论断）

### toB 场景几乎必然走向写扩散

已读回执、消息撤回、离线补全是硬需求，没有每成员维度的投递记录这三个功能立不住；这些约束串起来「几乎一定走向写扩散」。

### 扇出应放在群服务展开

群成员、群属性、群配置全在群服务，扇出天然是它的责任边界（候选还有发送方客户端展开、接入层展开）。

### 写扩散不是终点，是某个规模下的最优解

「真正的工程能力，是知道什么时候该走，什么时候该停」；先定产品群规模上限，再定架构，顺序反过来会积累技术债。

### 大厂选型分化

- 钉钉：万人群扛不住写扩散，演进为读扩散 + 推拉结合 + 成员多级缓存（消息只存一份）。
- 微信：坚持写扩散，换读路径极致简单（撤回/漫游/未读只操作单成员消息流），代价是写放大。
- 企业微信：仍走写扩散，靠硬件堆料 + 批量/缓存/异步硬撑万人群 + 已读回执。

## Implications（影响／启示）

- 中小 toB IM 的扇出层有一条清晰演进路径：群服务展开 → MQ 批量化 → 双轨存储 → 分档限规模 → 临界点混合模式（千以下写扩散、千以上读扩散，群创建时静态标记分流）。
- 副本瘦身分档（<1KB 带 payload，超过带首 100 字符摘要 + 按需反查）兼顾预览体验与带宽峰值。
- 扇出层三个核心可观测指标：扇出 RT P99、副本投递失败率分桶、批内部分失败率。

## Limitations（局限）

- 单一作者的经验性分析文章，成本数字（3000~5000 次操作、1~3ms 等）为估算量级而非实测基准。
- 大厂方案部分转引第三方资料（DTIM 设计文、微信聊天室架构文、企业微信架构文），非一手官方文档。
- 未给出读扩散侧的同等成本账，对比不完全对称。
