# 阿里电商IM消息平台在群聊、直播场景下的技术实践

## Overview（概览）

淘宝消息业务团队（李历岷/骨来，首发"淘系技术"公众号，52im.net 收录）的一手实践分享：阿里新零售 IM 平台（日处理百亿级消息）在 2020 双 11 强互动场景（盖楼群、百万在线直播间）下，群聊侧从写扩散转向读写扩散混合、直播侧按"弱关系特殊的群"重建分发链路的架构实践。

## Key Facts（关键事实）

- 写扩散瓶颈量化：主互动 500 人群、平均群大小 320+，按 DB 承接 120w/s 写入速度，消息上行仅 3K/s，远低于峰值互动流量。
- 群内 99.99% 是"非个性化消息"（全员可见），这是读扩散把 1:N 写入压成 1:1 的前提。
- 读扩散同步模型：群会话消息队列自增 syncId 保序；客户端存同步位点（去中心化）；服务端 syncId − 客户端 syncId = 1 则无空洞，否则携位点回云端拉区间数据补洞，最终一致。
- 读写扩散混合模式落地后：覆盖几千万互动群用户，一条上行消息 500ms 内到达群内其他端侧。
- 直播间是"弱关系特殊的群"：单群 ≤500 人，而直播间 40万~200万设备同时在线；分布为大直播间（>30W 在线）若干个、中几百个、小几万个。
- 直播分发链路：互动消息 → 网关接入 → 应用系统 Buffer（秒级、topic/直播间维度）→ 编码/合并/批量 → 直播间维度设备分段切片扩散 → 长连推送 → 端侧解码。小直播间不走 buffer，大直播间按 N 秒或条数异步 flush 削峰。
- 可靠消息（红包/优惠/宝贝卡片）：持久化存储 + 推送失败重试 3 次 + 下一条消息捎带 + 端侧去重，保证最终一致且 3 秒内达端。
- 订阅关系：大小直播间分片路由；离线数据分析预判大直播间账号，主播开播即预分片，脉冲绑定分散到 N 台订阅集群。
- 热点直播间：一致性 Hash 热点二次打散到多机承接；房间维度统计用分布式锁 + 分片合并（类 JDK Striped64 原理）。
- 流控不一刀切：按 subType 指令分级，QoS 分级承诺 SLA，做隔离/优先级/差异化。
- 文中断言：市面上 80% 具备 IM 能力的 APP 采取写扩散简单模式做云端消息同步。

## Important Claims（重要论断）

### Claim 1：写扩散在强互动群聊下必然触顶

1:N 写入把 DB 写入 RT 与存储打到极限（120w/s 写入只换来 3K/s 消息上行），且 IM 写集群还要与营销、交易、物流等通知类消息共享，必须降低扩散比。

### Claim 2：读扩散的可行性建立在消息可分类上

非个性化消息（99.99%）只写一条、全员共享读取；个性化消息（进群欢迎语等单边消息）仍走写扩散——因此落地形态是混合模式而非纯读扩散。

### Claim 3：直播间不是"大群"，需要独立抽象

群聊围绕消息/会话/会话视图/消息漫游设计；直播间围绕大规模实时互动抽象（buffer/批量/订阅关系切片）。群是强关系（确认加群），直播间是弱关系（进出自动建立/取消订阅），两者架构差异化是用户规模与产品需求驱动的必然。

### Claim 4：不确定性流量要工程化地转为确定性流量

手段包括全链路压测/脉冲压测/破坏性压测、流量打标、业务隔离、预案保护、流量感知预警；系统层面追求上下游 1:1，避免写入放大与读取放大的单点瓶颈。

## Implications（影响／启示）

- 为 [[write-fanout|写扩散]] 页补上对称的读扩散侧证据：读扩散的成本是架构复杂度（动态会话队列维护、端侧感知新队列）与冷启动多队列读 QPS，而非写放大。
- "按消息是否个性化分类 → 混合扩散"是可迁移的选型方法：先看数据分布，再定扩散模型。
- 直播间分发链路（buffer 合并批量 + 切片扩散 + 捎带重试）是"弹幕/聊天室"类系统的通用参考架构。

## Limitations（局限）

- 团队一手实践分享，无量化对比数据之外的验收指标细节（如读扩散侧确切读 QPS 数字未给出）。
- "80% APP 用写扩散""99.99% 非个性化消息"为文中经验性断言，未给出统计口径。
- 成文于 2020 双 11 背景，具体数值（120w/s、3K/s、40万~200万在线）反映当时容量，不代表当前。
