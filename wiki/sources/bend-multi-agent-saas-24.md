# B端系统多智能体重构SaaS业务流：产品经理建议收藏（大皮不皮 · B端产品经理 第24篇）

## Overview（概览）

公众号《B端产品经理》专辑第 24 篇（篇号据采集文件名序号；作者 大皮不皮，专辑共 32 篇）。从产品经理落地视角讲如何用多智能体重构 SaaS 业务流：多智能体不是给 SaaS 加聊天机器人，而是把"人找功能"改成"Agent 找决策"，把流程中的判断从人身上剥离出来交给多个 Agent 协作执行。全文给出三层架构（交互层/编排层/执行层）、业务流重构五步法（拆业务事件找决策点→定义 Agent 角色与边界→设计协作协议→嵌入权限审计与人工干预→评测回滚）、四个行业案例（ERP 采买到付款/车贷审批/OA 差旅报销/CRM 线索培育），以及 Agent 化 PRD 新增五模块。

## Key Facts（关键事实）

- 传统 SaaS 隐含假设：流程稳定、角色明确、数据靠人搬运；真实业务里异常、判断、跨系统协作高频发生。
- 堆功能三恶果：用户认知负担越重；跨系统协作依赖人工导出对账；异常场景依赖工单与用户支持、响应慢。
- 核心转变：多智能体把流程中的判断从人身上剥离出来，交给多个 Agent 协作执行（信源论断："多智能体不是把 AI 塞进流程，而是让流程本身具备判断力"）。
- 判断标准：如果一个"AI 功能"只生成文本但不调用业务系统，那不叫多智能体。
- 三层架构：
  - 交互层：用户意图入口（对话/表单/消息卡片/快捷键），PM 设计"意图与槽位"而不只是页面。
  - 编排层：Orchestrator 把业务事件拆成子任务分发给执行 Agent，核心产物是任务卡片（上下文/约束/期望输出/超时策略）。
  - 执行层：Agent 调用工具/API/规则引擎完成查询/计算/审批/写入，工具必须可版本化、可审计。
- 五步法：
  1. 拆业务事件找决策点：按业务事件拆而非功能模块（ERP 采买到付款：请采买单提交→预算校验→供应商比价→采买订单→收货入库→发票校验→付款）。
  2. 定义 Agent 角色与边界：每个 Agent 有身份、目标、工具、不能做的事（预算 Agent 只读预算表、不可改历史数据；财务 Agent 可发起付款计划但需人工确认）。
  3. 设计协作协议：Agent 之间用结构化消息通信不用自然语言自由发挥；任务卡片含任务 ID、来源事件、业务上下文、可用数据范围、期望输出格式、失败回退路径。
  4. 嵌入权限审计与人工干预：执行前校验身份与数据范围；关键动作强留痕；高风险节点强制人工确认；权限模型沿用 RBAC+ABAC 但增加"Agent 权限"维度。
  5. 评测回滚：离线评测集+影子模式上线对比人工处理结果；异常时能回滚到人工流程。
- 案例 1 ERP 采买到付款（某制造企业，采买审批慢、预算超支靠人工事后发现）：采买 Agent 采集需求生成采买单→预算 Agent 实时校验部门预算、余额不足通知采买人补报或升级审批→供应商 Agent 按物料/交付周期/历史评分推荐→风控 Agent 校验供应商黑名单与关联交易→财务 Agent 生成付款计划→人工在采买审批与付款两个节点确认。PRD 要点：预算 Agent 工具为读预算表、写预算锁定；权限为不可修改历史预算；协作协议为"预算余额不足时向采买人返回替代方案，不直接终止流程"。
- 案例 2 车贷审批（进件资料多、人工审核慢、欺诈识别依赖经验）：进件 Agent 抽取 OCR 信息归一化客户/车辆/经销店数据→反欺诈 Agent 校验设备指纹/关系图谱/历史欺诈标签、输出风险标签→风控 Agent 按规则引擎评分输出额度建议与拒绝原因→放款 Agent 生成放款指令人工复核后执行。权限边界：反欺诈 Agent 只输出风险标签不输出拒绝结论；风控 Agent 不能修改规则参数；放款 Agent 不能跳过人工复核。
- 案例 3 OA 差旅报销：行程 Agent 识别出差申请→合规 Agent 校验差旅标准→预算 Agent 锁定部门预算→财务 Agent 生成报销单；超标时自动推经济舱/标准酒店而不是直接驳回。
- 案例 4 CRM 线索培育：线索 Agent 评分、内容 Agent 生成触达、SDR Agent 安排跟进；线索分配不再是静态规则而是根据意向动态调整。
- Agent 化 PRD 五新增：Agent 能力卡片（名称/目标/输入/输出/工具/权限）、协作时序（状态机/时序图）、护栏机制（不可覆盖规则/人工退出路径/灰度策略）、评测集（典型 case/边界 case/预期输出）、指标（任务完成率/人工介入率/业务周期/风险拦截率）。

## Important Claims（重要论断）

### Claim 1：多智能体不是给 SaaS 加聊天机器人

"多智能体（Multi-Agent）的出现，不是给 SaaS 加一个聊天机器人，而是把'人找功能'改成'Agent 找决策'"（信源开篇论断）。堆功能的死循环（客户提需求就加功能→版本越多用户越觉得难用）的根因不是功能不够，而是业务流被固定表单与僵化节点切碎。

### Claim 2：判断标准——调用业务系统才算多智能体

"如果一个'AI 功能'只生成文本，但不调用业务系统，那不叫多智能体"（信源判断标准）。多智能体的本质是让流程本身具备判断力：把流程中的判断从人身上剥离出来，交给多个 Agent 协作执行。

### Claim 3：权限模型必须增加"Agent 权限"维度

"权限模型可沿用 RBAC+ABAC，但必须增加'Agent 权限'维度"（信源论断）：每个 Agent 执行前校验身份与数据范围、关键动作强留痕、高风险节点强制人工确认——传统面向人的权限模型不足以约束 Agent 的执行面。

## Implications（影响／启示）

- 与 [[agent-legacy-system-integration|Agent 对接旧系统]] 互补（解读）：同专辑同作者，那篇讲 Agent 连接旧系统的工程方法（盘点/选型/映射/灰度/复盘），本篇讲业务流本身的多智能体重构（拆事件/定角色/定协议/权限/评测）——一个是"连得上、写得回"，一个是"流程有判断力"，两者是 Agent 落地的两个正交维度。
- 与 [[approval-workflow-engine|审批流引擎（含 AI 改造层）]] 互证（解读）：本文案例的高风险节点强制人工确认（采买审批/付款/放款复核）与审批流引擎 AI 改造层的"受控自动化"思路一致，但组织单元不同——本文以多 Agent 协作流为单位，审批流引擎以单引擎+AI 模块为单位。
- "RBAC+ABAC+Agent 权限维度"与 [[rbac-permission-system|RBAC 权限系统]] 及 [[agent-permission-model|Agent 权限模型]] 呼应（解读）：传统权限管"人"，Agent 时代需把 Agent 作为新的授权主体纳入。
- 评测回滚（离线评测集+影子模式+回滚人工流程）与 [[agent-evaluation|业务 Agent 全生命周期评测]] 的评测纪律一致（解读）：影子模式对比人工处理结果是评测前置的落地形态。

## Limitations（局限）

- 单一作者经验总结文，四个案例均未给上线前后量化对比数据，框架为建议性总结。
- 案例均为匿名口述（"某制造企业""车贷"），无具体企业/系统细节，无法独立验证。
- 停留在产品设计视角：未涉及多 Agent 编排的技术实现（消息队列/事务/失败恢复的具体机制）。
- "影子模式""评测集"的具体构建方法、Agent 权限维度的表达与审计方式均未展开。
