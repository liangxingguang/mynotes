# 工单系统PRD撰写实战：一套可复用的需求文档拆解（大皮不皮 · B端产品经理 第2篇）

## Overview（概览）

公众号《B端产品经理》专辑第 2 篇（据采集文件名序号；作者 大皮不皮，专辑共 32 篇）。以 IT 报修/售后支持为场景，完整拆解一份工单系统 PRD 的写法：需求背景与目标、三类角色权限矩阵、工单生命周期状态机与流转表、五大功能模块（创建/分配/处理/关闭/查询统计）、字段设计、非功能需求与验收标准。概念本体见 [[ticket-system-design|工单系统设计]]。

## Key Facts（关键事实）

- 工单系统核心目标（信源）：任务可追踪、流程可约束、结果可统计。痛点背景：无统一入口时任务散落在 email/微信/口头沟通，处理无记录、无时效管理、无法统计效率。
- 三类角色与权限矩阵（信源）：提交人（数据范围=自己创建的工单；动作=创建/查看/确认关闭/评价）、处理人（=分配给自己的工单；接单/转派/填写记录/申请关闭）、管理员（=全量工单；配置/转派/批量处理/导出）。矩阵写清"数据范围"和"执行动作"是开发容易遗漏的部分。
- 状态机五态（信源）：待受理→处理中→已处理→已关闭，另有已驳回。流转表含 8 条流转规则（接单/驳回/转派/申请关闭/确认关闭/重新打开/修改后重新提交），每条写触发动作、执行人、前置条件、下一状态；管理员保留"强制关闭"处理无效工单。
- 工单编号规则（信源）：类型前缀+日期+顺序号，如 GD20250601-001。创建入口：门户/email/微信服务号/内部系统，各入口字段差异与校验规则不同（email 自动抓主题为标题、正文为描述；服务号允许上传图片）。
- 分配三种方式（信源）：自动分配（按工单类型+组织架构+处理人负载路由）、人工转派、接单模式；需定义路由失败兜底（自动进默认处理组并提醒管理员）。
- 处理与关闭（信源）：处理记录支持文本/附件/图片，申请关闭时至少一条处理记录；SLA 按优先级设响应/处理时限，超时经站内信+email 提醒处理人及其上级；常见问题模板回复。关闭由提交人确认或系统 X 天后自动关闭；关闭后评价维度=响应速度/处理质量/服务态度。
- 查询与统计（信源）：查询条件=编号/状态/类型/优先级/来源/时间范围；统计=工单量/平均处理时长/SLA 达标率/满意度；报表权限仅管理员和分配负责人。
- 字段设计（信源）：18 个关键字段（编号/标题/描述/类型/优先级/状态/来源/关联对象/提交人/处理人/处理组/创建/更新/处理/关闭时间/SLA 时限/附件/评价）；关联对象不直接存名称，只存 ID 和类型，展示层再查询。
- 非功能需求（信源）：列表查询 P95<2 秒、详情页<1 秒；数据权限隔离、处理日志至少保留 12 个月；移动端适配、弱网可提交；流转动作全留痕（执行人/动作/前后状态/时间）；埋点 5 个核心事件（创建成功/接单成功/申请关闭/确认关闭/提交评价）。
- 验收标准（信源）：功能/权限/数据/性能/兼容五类，均需可验证（性能验收示例：1000 条工单数据下列表查询响应符合指标），避免"体验良好"等笼统描述。
- 结论（信源）：工单系统 PRD 的难点不是功能清单，而是状态、权限和规则是否清晰。

## Important Claims（重要论断）

### 工单系统的本质目标是"三可"

工单系统要处理的是"任务可追踪、流程可约束、结果可统计"；PRD 目标须与业务目标对齐，避免只写功能不写价值。

### 状态流转是 PRD 的核心，建议用状态机而非纯文字描述

状态流转是 PRD 的核心，用状态机描述避免开发理解偏差；每个动作都要写触发条件、执行人、下一状态，形成闭环、避免陷入循环。

### 权限矩阵是开发容易遗漏的部分

权限矩阵需用表格写清"数据范围"与"执行动作"，PRD 里写清楚，测试才能按矩阵验权限。

### 字段设计要避免冗余

关联对象不直接存储名称，只存 ID 和类型，展示层再查询。
