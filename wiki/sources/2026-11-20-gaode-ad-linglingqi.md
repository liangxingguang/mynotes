# 高德广告凌凌漆：研发任务的持续执行与可信验收

## Overview（概览）

微信公众号「高德技术」长文，是《信息业务 AI Native Builder》系列的数字员工篇之一。以"一次代码修改 17 项定向测试全通过、构建成功，却仍不能宣布需求完成"为引，点明 AI 进入真实工程后的核心命题：让数字员工持续工作、理解大型工程、用真实证据交付。围绕这一命题介绍高德广告 AI 原生生产系统"广告凌凌漆"：22 项能力入口、四层架构（交互协作/任务控制/研发执行/工程上下文与验收）、可替换 Harness 边界、个人研发环境（Personal Dev）、CodeGraph 影响分析、Knowledge+Mem0 经验治理、Dev Loop 研发契约与验收分层，并以一个真实混合版本配置兼容任务做验收示例。截至 2026-09-18 台账 362 条任务、办结率 96.4%。高德技术一手自述，单信源，置信度中。

## Key Facts（关键事实）

- **核心命题**：让 AI 写代码不够，要让它持续工作、理解复杂工程、用真实证据证明结果。一次代码修改 17 项定向及相邻测试全过、约定模块构建成功，但普通 testCompile 被存量基线阻断、CR/发布/线上验证未发生，故不能宣布需求完成。
- **系列定位**：《信息业务 AI Native Builder》系列数字员工篇；系列含总纲篇、交付篇（星舰 10X、星舰 Cloud Agent）、数字员工篇（本篇）、现场篇（轻舟 Agent）。
- **规模数据**：截至 2026-09-18 一次阶段性快照，广告数字员工任务台账 362 条，349 条已办结，办结率 96.4%；"办结"仅表示任务在台账中已完成或关闭，不等同于答案正确率、研发交付率或业务结果达成率。研发辅助与需求准入、用户问题排查、运维与报警分析三类合计 274 条，占 75.7%。
- **能力接入**：已接入 22 项专业能力入口，归纳六类——需求与研发（需求准入/任务拆解/技术方案/研发任务）、代码与质量（代码图谱/分析/评审/测试策略）、引擎与实验、运维与数据、客资与计费（客资分发/计费/赔付/反作弊）、知识与协同。客资、计费、赔付、反作弊以查询、分析、结论草稿为主；涉及回帖、配置或数据写入、赔付等高风险动作，必须由责任人确认或沿用原系统审批链路，数字员工不会因能调工具而自动获得业务授权。
- **历史样本**：另一批历史问题分析中提炼 8 类共性问题、沉淀 16 项标准答复（口径与任务快照不同，不参与办结率计算）。
- **四层架构**：①交互协作（小七理解请求、补充信息、组织专业能力、反馈结果）；②任务控制（Main Agent 管理被委托研发任务的身份、状态、代码版本、执行环境、交付记录）；③研发执行（Coding Harness 与研发环境完成代码搜索、修改、测试、失败后继续修复）；④工程上下文与验收（CodeGraph、Knowledge、Memory、Evidence、Evaluator）。
- **执行路径分流**：数字员工原生闭环（知识查询/数据获取/标准排查，小七直接完成）、自动化工作流（定时任务/事件触发/多阶段协作）、专业研发闭环（代码修改/跨仓开发/构建测试/严格验收，委托 Main Agent）。Main Agent 不是所有任务的必经之路。
- **可替换 Harness 边界**：前期用 OpenCode 建立多模型研发执行，后 Codex Harness 在 Personal Dev 部分正式研发路径中逐步成为默认执行引擎（非全面迁移，部分预发与存量路径仍用原方式）。Harness 负责代码搜索与阅读、文件修改、命令执行、上下文压缩、多轮修复；平台负责任务身份、仓库与版本、权限、环境、研发契约、验收证据。核心纪律：**自主执行不等于自主授权**——Harness 可自主选实现路径，但不能自行扩大仓库范围、写入权限或完成标准。
- **Personal Dev**：让逻辑研发环境独立于计算实例。对比本机（绑个人设备、本地持久、依赖本机环境、依赖个人操作）、一次性沙箱（依赖临时实例、需额外保存、需恢复现场、需额外控制）、Personal Dev（稳定环境身份、持久卷保存关键状态、受控换代与基础恢复、单 Writer 原则）。环境骨架含稳定环境标识、持久卷、计算存储分离、环境代际管理、任务路由恢复、执行日志。关键不是保存文件，而是避免两个实例同时拥有正式写入权。
- **单 Writer 与代际**：多读、多分析、受控写入；同一正式研发任务主工作区，同一时刻只允许一个受控主执行者持有写入权，其他 Agent 可在隔离分支/worktree/明确文件范围内并行分析评审，非全局串行。环境代际（Generation/Epoch）标识新旧实例，但代际标识本身不是锁；安全接管依赖 lease、fencing 和旧执行器停止，只有正式写入路径验证当前写入权并拒绝失效执行器才形成有效隔离。公开证据尚不足以证明"新实例接管后所有旧实例写入均已被稳定拒绝"。
- **CodeGraph**：将符号定义、引用、调用关系、依赖、配置关联组织成结构化索引，是影响分析的导航、不是代码事实本身（类比大型工程"管线图"）。图谱制品须关联 repo_id、commit_sha、artifact_digest；图谱缺失/过期/与版本不一致时 Agent 应回源码核实。2026-11-02 核验：14 个广告核心仓库的本地/预发/生产三环境完成 14/14 仓库版本、图谱制品及工具链身份一致性检查——仅证明元组一致，不证明每条关系正确，不代表后续自动同步。
- **Knowledge + Mem0**：正式知识（Knowledge）存团队认可的架构、业务规则、SOP；历史记忆（Memory）存排查路径、无效尝试、故障根因、纠正结果。复用 Mem0 的记忆抽取、去重、元数据管理和检索，重点在记忆治理：记录经验的来源、适用范围、对应版本，以及后来是否被采用、拒绝或纠正。小七与 Dev Loop 共享受控广告历史记忆服务。
- **四类信息用途**：①确认当前行为（绑定版本与时间窗口的源码、配置、权威系统记录、日志、运行数据）；②判断目标行为（经责任人确认的业务规则、研发契约、验收标准，不能用错误实现反向定义正确预期）；③缩小排查范围（历史记忆须在当前任务中重新核实）；④形成待验证判断（模型推断只能作假设，不能直接升级为事实或规则）。信息冲突时先区分"系统现在怎样运行"还是"系统应该怎样运行"。
- **Memory 评价三层**：是否可检索、执行时是否被真实采用、采用后是否降低耗时/返工/提升质量；前两层已有阶段性过程数据，第三层需固定任务集与对照验证。"硬采用"仅表示记忆实际进入后续命令/检索/分析/产出，属过程指标，不能证明记忆正确或产生收益。
- **Dev Loop 研发契约**：三要素——目标（Goal）、约束（Constraints）、验收证据（Acceptance Evidence）；先明确目标约束验收标准，再让 Agent 按执行结果选路径。按任务类型调深度：轻量修改（源码/局部搜索/必要测试）、常规研发（调用关系/配置影响/核心测试与构建）、跨仓或高风险变更（跨仓依赖/业务规则/环境验证/回滚依据/人工决策）。每轮执行应带来新可验证事实、关闭缺口或改变策略；连续多轮无新证据且未改变方向时，应停止自动重试、报告阻塞或请求人工判断。
- **四概念分离**：Contract（研发契约，什么条件下算完成）、Trajectory（执行轨迹，实际执行了哪些操作）、Evidence（验收证据，哪些真实结果支持当前结论）、EvalResult（验收结论，依据现有证据最多能宣布到哪一步）。代码差异、测试结果、构建日志、环境验证结果本身可作验收证据，关键是与任务、代码版本、执行环境、验收条件关联。
- **验收三层次**：开发完成（代码差异、必要测试、风险检查达约定标准）≠ 交付完成（代码评审、发布及相关交付步骤完成）≠ 效果确认（线上行为、业务指标或约定结果得到验证）。**研发验收通过 ≠ 代码评审完成 ≠ 发布完成 ≠ 线上效果确认。**
- **真实案例（混合版本配置兼容任务）**：目标让新旧版本共存且旧配置语义不被破坏。Main Agent 关联任务/代码版本/研发状态，Personal Dev 提供工作区，CodeGraph 辅助定位配置处理函数与影响范围后源码复核，Codex Harness 执行修改/测试/构建；研发契约预先把 17 项定向及相邻测试和约定模块构建列为本阶段必要验收项。结果：定向及相邻测试 17/17 PASS、约定模块构建 BUILD SUCCESS、任务级 Eval 研发验收 PASS（可进入代码评审），但普通 testCompile 未形成通过证据、CR 未创建、发布未执行、线上效果验证未执行。现有证据最多支持"研发验收通过、具备进入代码评审条件"，不宣布需求全部完成；testCompile 风险需在后续评审/交付检查中保留补证，不被阶段性 PASS 抵消。
- **下一步**：不追求增加 Agent/工具数量，聚焦统一可比较工程度量（任务、代码版本、执行轮次、证据、验收结论、最终结果关联）、打通业务问题→需求→研发→发布→结果确认的可追踪闭环、把被采用/拒绝/纠正的经验沉淀为候选知识/规则/测试/技能/Memory 并在同类任务中重验。判断标准：系统是否减少无效尝试、返工、人工接管，缩短交付周期，提高有效交付与业务结果确认比例。

## Important Claims（重要论断）

### Claim 1：任务办结 ≠ 研发交付 ≠ 线上效果

办结率只代表台账状态，办结不等于答案正确、交付完成或业务达成；真正要解决的是数字员工怎样持续工作、AI 怎样理解大型工程、凭什么相信它交付的结果。

### Claim 2：自主执行不等于自主授权

Harness 可以自主选择实现路径，但不能自行扩大仓库范围、写入权限或完成标准；涉及高风险动作必须由责任人确认或沿用原审批链路。

### Claim 3：验收分层，证据不足不升级结论

研发验收通过不代表代码已评审，代码已发布不代表业务效果已确认；Evaluator 只能依据契约指定证据限制结论层级，证据不足时停止结论升级。

### Claim 4：区分"当前行为"与"目标行为"

确认当前行为以绑定版本的源码配置日志为据，判断目标行为以责任人确认的规则为据，不能用错误实现反向定义正确预期；模型推断只能作假设不能升级为事实或规则。

## Implications（影响／启示）

- AI 工程化的重心已从"让模型写代码"转向"让 Agent 持续工作并用证据约束结论"：任务身份、执行环境、验收证据三者绑定，才能把一次性成功变成可复现、可追溯的交付。
- "自主执行≠自主授权"与"验收分层"是把 AI 纳入真实研发流程时的两条关键纪律，与 [[harness-engineering|Harness 工程]]、[[acceptance-agent|验收 Agent]] 的思路相互印证。

## Limitations（局限）

- 高德技术一手自述但为单信源；办结率、14/14 一致性等均为阶段性快照，作者明确不外推为正确率/交付率/每条关系正确。
- Personal Dev 的换代接管、多人规模资源竞争等仍"需继续验证"，公开证据不足。
- Memory 第三层效果评价、固定任务集对照验证尚未完成，本文不以总量证明效果。
