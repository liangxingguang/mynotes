# 用一棵树管住 100+ 个红点：SLG 红点系统实现详解

## Overview（概览）

游戏开发系列·红点系统：用三个问题（怎么汇总/何时计算/谁来算）给方案分类，对比五种方案（A 界面自己算 / B 扁平 key+观察者 / C 前缀树+立即冒泡 / D 前缀树+父节点脏集合 / E 运算单元组合+标脏+每帧限量）。本文方案站在 D 基础上：叶子也标脏每帧统一算、拉模式叶子自订阅自计算、脏标记冒泡到根、每帧后序遍历只算脏节点、先取走脏标记再计算、有意全树遍历、变化才通知+UI 先拉后推。附完整 C# 实现（RedPointNode/RedPointLeafNode/RedPointEventLeaf/UIRedPoint）与免费抽卡示例。

## Key Facts（关键事实）

- 红点天然成树：入口数字=页签之和，页签数字=条目之和。中大型游戏红点上百。
- 五方案对比：A 界面自己算（逻辑散落）/ B 扁平 key（无层级）/ C 前缀树+立即冒泡（父链重算多次）/ D 前缀树+父脏集合（流传最广，但叶子没合并、计算在业务侧、时间驱动无挂点）/ E 运算单元+每帧限量（重但共享只算一次）。
- 本文 = D 基础 + 叶子也标脏每帧算 + 拉模式 + 订阅收进叶子生命周期 + 全树 Update 顺带处理时间驱动红点。
- 脏标记冒泡 O(深度)≈常数，幂等，合批效果正来自此。
- 关键细节：脏标记必须**先取走再计算**，否则遍历中新标脏被父节点误清、红点停旧值。
- 全树遍历是有意为之：遍历便宜（微秒级）、计算昂贵，脏标记省的是计算。
- 建树与 Init 分离：防登录数据未齐时红点闪烁。
- 新增红点：写一个叶子类 + 注册表加一行 + UI 挂组件选路径。

## Important Claims（重要论断）

### Claim 1：方案 D 只合并了"汇总"，本文把"计算"也合并了

主流方案 D（前缀树+父脏集合）让父节点每帧算一次（合并了汇总），但叶子仍是推模式——业务算好值推给红点系统。本文让叶子也每帧算一次（合并了计算），业务只需说"变了"。一个红点全部逻辑（订阅什么、怎么算）收进一个叶子类。

### Claim 2：拉模式让业务代码零改动

叶子自己订阅数据事件、收到只标脏；计算写在 `GetCount()`（当前数据的纯函数）里由框架调用。业务模块照常发事件，完全不需要知道红点系统存在。事件风暴（一次 50 条变化）也只是标脏 50 次，标脏近零成本。

### Claim 3：先取走脏标记再计算是正确性关键

若先计算后清脏，遍历中子节点再次标脏会冒泡到父节点，父节点按旧值求和后误清标记，下一帧子节点算出新值但父节点已不脏、不再求和——入口红点停在旧值。先取走再计算：遍历中新标脏留到下一帧，最多晚一帧但不丢。

## Implications（影响／启示）

- 拉模式+脏标记+每帧合批是管理"数量多、层级深、数据来源杂"红点系统的可行范式。
- "先取走脏标记再计算"是延迟计算类系统的正确性关键细节，适用于任何"遍历中可能再次标脏"的场景。
- 全树遍历 vs 脏集合：在百级节点规模下全树遍历更简单且顺带解决时间驱动红点挂点问题；千级才值得改脏集合。

## Limitations（局限）

- 信源为单篇知乎专栏技术文章，无生产规模（红点数上千）的验证数据。
