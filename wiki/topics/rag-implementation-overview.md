# RAG 落地实施总览（天地框架与七大误区）

## Scope（范围）

RAG 落地方法论的导航页：信源（微信 RAG 系列开篇篇）提出的"天地之间"框架（数据细节为地、系统架构为天，索引构建与检索策略居中），以及落地七大误区。用于聚合 RAG 实施环节的实践要点，后续 RAG 实战信源可挂靠本页。

## Current Understanding（当前认知）

RAG 的思想很简单——检索增强生成，难在普适推广。信源以"天地之间"概括落地的两个支点与中间衔接层（信源 2026-11-23）：

- **地（数据细节）**：每个业务数据都是独一无二的，且包含隐私数据。RAG 调试中数据非常重要，落地必须先做数据分析、把数据细节做好，否则无从谈起。
- **天（系统架构）**：工程架构层面，离线、在线怎么做，要保证的是**系统整体最优，而不是局部最优**。优化检索、优化大模型不一定对整体最优——检索策略效果提升可能引入杂质，需测试验证，且检索办法未必完全适配业务。
- **中间（索引构建 + 检索策略）**：索引构建包括离线文档解析、知识入库构建向量 embedding、数据库选型；检索策略包括全文检索、向量检索，检索前用多轮 query 改写，检索后对内容做整合排序排版再送入大模型。中间层是达成"天"（系统架构最优）的路径，不能只考虑局部最优。

落地流程上，围绕业务目标设计流程、实现场景化落地；围绕"天地"展开的七大误区（见下）是最常见的实施陷阱。

## 落地七大误区（信源 2026-11-23）

1. **数据不分析不分库**：数据存在混淆时问答效果差，须先分库、做数据筛选。
2. **过度依赖通用混合检索**：全文检索+向量检索的混合检索并非默认最优——若用户提问多为关键词，全文检索即可命中且更可靠；向量检索适合提问模糊、几乎不含关键词的场景（全文检索会拉低向量检索得分）。应分析到底用单路还是混合。
3. **切块粒度一刀切**：默认 256/512 的切分方式不适合所有文档——法律类文章大段连排，512 更符合，256 过细；内容短小的文档 256 即可。应开放接口让用户按业务选择（用户更懂业务）。
4. **误将召回率等同于检索效果**：召回率之外更要关注精确率、准确率；看 TOP1/TOP3/TOP5/TOP10 结果与 NDCG 等指标确认召回质量。
5. **生成阶段过度依赖大模型**：检索内容带杂质时，"基于以上内容回答"的提示词不足以约束模型，模型可能无视内容与问题的相关性直接回答；须在提示词中约束"严格基于内容、与用户问题相关"地回复。
6. **忽视用户查询意图**：口语化提问（如"手机充电慢怎么解决"）可能只召回到"手机充电原理"等无关内容；需查询改写，把提问改写为标准化问题。
7. **缺前置意图分类与分发**：常见问题与故障类问题混在同一数据源会互相混淆；把两类库分开，前置意图分发——识别用户问题归属哪类库后，在对应库中检索，比全库检索更准。提问后先意图分发确定知识库，再快速改写、检索。

## Open Questions（开放问题）

- 切块粒度 256 vs 512 的分档规则：信源建议按文档类型调整并开放给用户选择，但各文档类型的最优粒度无通用标准，需实测（与 [[rag-chunking]] 的分块策略口径待对齐）。
- 混合检索 vs 单路检索的判定指标：信源给出场景描述（提问是否偏关键词），未给出量化判定规则。
- 评估指标体系：NDCG/精确率/TOP-K 的选取与阈值未量化，待更多实战信源补充。
