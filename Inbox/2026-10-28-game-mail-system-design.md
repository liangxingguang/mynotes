# 游戏开发：邮件系统的分布式逻辑与特殊用法

> 游戏后端核心系统的实战总结：普通邮件的弱时序设计（只关注送达不关注顺序）、公共邮件的读裂变与标记法撤回、跨服可靠性投递的 Seq+Ack 与合服陷阱，以及"一切领奖皆邮件"的 Channel 抽象。

## 核心要点

- **P2P 邮件消失**：风控（盗号资产转移）、经济调控（拍卖行收税）、技术风险三重原因，现代游戏只留系统邮件。
- **附件结构**：附件应直接用 Item 结构而非简化的 MailItem，否则丢失道具细节，无法支持邮寄特殊属性道具。
- **邮件队列**：邮件写独立队列（MongoDB）而非玩家 DB，消费时+定时拉取；弱时序要求允许跨服直接写队列，简化跨服发奖。
- **公共邮件读裂变**：不主动全服写入，玩家在线时由 Game 服拉取插入——避免僵尸号无效写，且延迟执行是撤回的基础。
- **撤回用标记法**：标记无效而非删除（可逆、避免分布式复杂度）；已入玩家邮箱的邮件通过关联 publicId 在拉取时检查撤回。
- **可靠性 = 重发 + 去重**：Game 服定时拉取可领取公共邮件，本地 HashSet 领取记录去重；记录可不删（量小）。
- **分布式事件**：跨服发奖/扣道具封装统一事件机制，可靠性用 Seq+Ack；合服时收发双方保留原始服务器 ID，procVersion 保证新事件排在旧事件后。
- **复杂度克制**：玩家间事件无需时序、单玩家事件多只求成功，通常只需基础可靠性投递，不必实现完整时序保证。
- **邮件的它用**：为邮件设计多 Channel，领奖=领邮件；跨服奖励全走邮件可减巨量复杂度（DNF 模式）。
