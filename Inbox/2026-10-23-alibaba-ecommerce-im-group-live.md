# 阿里电商IM消息平台在群聊、直播场景下的技术实践

> 双 11 强互动场景（盖楼群、百万在线直播间）下电商 IM 的架构实践。群聊侧：写扩散 1:N 把 DB 写入打到极限（120w/s 写入仅支撑 3K/s 上行）→ 利用"群内 99.99% 是非个性化消息"改读扩散，消息只写一条、群会话队列按 syncId 位点推拉同步（客户端存位点去中心化，syncId 差值>1 则拉区间补洞），最终读写扩散混合做到 500ms 端到端。直播侧：直播间是"弱关系特殊的群"（40w~200w 设备），链路为网关→秒级 buffer→编码合并批量→设备分段切片扩散→长连推送；热点用一致性 Hash 二次打散 + Striped64 式分布式统计合并。

## 核心要点

- **读扩散前提**：非个性化消息（全员可见）占 99.99% → 1:N 写压成 1:1；个性化消息（进群欢迎语）仍走写扩散 → 混合模式
- **读扩散同步模型**：群会话队列自增 syncId 保序、客户端存位点、差值判空洞后拉区间数据最终一致；代价是架构复杂、冷启动多队列读 QPS 压力
- **直播分发链路**：小直播间不走 buffer、大直播间 topic 维缓冲 + N 秒/条数异步 flush 削峰；可靠消息（红包/优惠/宝贝卡）持久化 + 重试 3 次 + 下条捎带 + 端侧去重，3 秒内达端
- **订阅关系**：大小直播间分片路由；离线数据分析预判大直播间，主播开播即预分片，脉冲绑定分散到 N 台订阅集群
- **流控不一刀切**：按 subType 指令分级；QoS 分级承诺 SLA，隔离/优先级/差异化
- **热点直播间**：一致性 Hash 热点二次打散到多机承接；房间统计用分布式锁 + 分片合并（Striped64 思路）
- **方法论**：不确定性流量→确定性（全链路压测/脉冲压测/流量打标/预案）；避免写入与读取放大，追求上下游 1:1
