> 淘宝直播互动团队构建了面向 Coding Agent 的 LiveX Wiki：融合 LLM Wiki 编纂、OKF 轻量表达与 Git 版本治理，按"域—场景—知识"三层把跨端跨仓业务经验沉淀为机器可解析的上下文。通过层次索引 + Agentic Search 按需消费、回源核验，由 LLM 与 Git 完成自动更新与工程治理。评测显示端到端生码得分较无知识库提升 39.15%，较 RAG 提升 30.1%，仓库定位准确率从 60% 升至 90%。

## 核心要点

- **问题**：通用 Coding Agent 面对跨仓跨端、含业务黑话与复杂配置的复杂需求，直接喂原始 PRD 产出不可用；RAG 向量库召回"语义相似"材料，但点状知识缺整体视角、业务视角需临时拼装、影响分析需额外调查、新鲜度无约束。
- **四条设计约束**：按需供给而非全量堆给；按业务结构组织而非条目堆积；给可核验路径而非只给结论；有生命周期随变更演进（知识像代码一样版本化）。
- **四维选型**：建模=场景模型+OKF 式轻量表达（Markdown+YAML frontmatter）；生产=LLM Wiki 编纂+人工定界与回源核验；消费=层次索引+Agentic Search；迭代=LLM 增量更新与全量审查+Git 治理。
- **三层建模**：业务域（职责/边界/维护人/场景入口）→ 业务场景（页面或系统全景+核心接口链+查证路径）→ 共享知识（平台接入/规范/共用概念，通过直接依赖复用）。场景按"可独立理解、可明确归责、可单独核验"划分。
- **消费五步**：发现域 → 选择场景 → 按需求选链 → 展开必要依赖 → 回源核验。维护已访问集合，证据齐备即停，未命中报告缺口，不把"查不到"当"没影响"。
- **生命周期三段**：冷启生产（固定版本+两轮搜索跨术语+正反向调查+LLM 核实编纂）；知识自更新（代码 diff→跨仓影响→候选修订）；知识自审查（定期回源查事实与覆盖）+ Git 治理（候选分支、评审、受控发布）。
- **效果**：两批端到端生码测评，综合得分较无知识库基线提升约 54.5%/23.8%，较 RAG 提升约 44.3%/15.9%；需求路由测评中已覆盖场景链路 F1 达 1.38:0.10，定位准确率与召回率显著提升。
- **可迁移方法**：按需求变化决定知识划分；复用已理解结构、重确认当前事实（知识版本与事实版本分开管）；生产/消费/维护/评测指向同一场景对象。局限：场景边界需人参与、依赖图可能遗漏、Git/CI 不保证业务判断正确，人须为准确性兜底。
