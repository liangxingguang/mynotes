# 从 0 设计 10 万 QPS 秒杀系统：10 万请求进来，只有 1000 个能碰到数据库

> 摘要：一篇秒杀系统容量设计实战：以 1 个爆款 SKU、1000 件库存、下单接口 10 万 QPS 为假设，演示从预约量反推峰值（300 万预约 × 首秒 3%~5% 点击 ≈ 10 万），用三层漏斗把 10 万压到 2 万再压到 1000——DB 只按 1000 TPS 设计，而非按入口 QPS 等比放大。核心方案是 Redis Lua 原子预扣 + 32 库存分桶散热 key + Kafka 削峰落账 + DB 唯一索引兜底幂等，附每层组件容量推导与五条避坑清单。

## 核心要点

- 需求先拆清：10 万 QPS 打在哪一层（只有"下单"接口才需要漏斗）、库存多少、能否少卖、是否严格公平；硬约束仅三条：不超卖、不重复、可降级
- 漏斗：前端答题/验证码（50% 通过）→ 网关令牌桶 → Redis 预扣成功最多 1000 次 → Kafka → DB 峰值仅 1000 TPS，被库存总量天然封顶
- 组件容量：网关 6 台、秒杀服务 10 台、Redis 3 主 3 从 + 32 桶、Kafka 6 分区、MySQL 1 主 1 从（无需分库分表）；并发≠QPS（Little's Law），DB 并发仅约 5，连接池按并发配
- Redis Lua 预扣：判断+扣减+买家标记同脚本原子返回；两 key 同 hash tag 防 Cluster 跨槽；脚本内不做重逻辑
- 分桶：userId 固定映射 32 桶解决热 key，代价是少卖（秒杀场景接受、事后补偿）
- 落账闭环：DB 唯一索引 (user_id, sku_id) 是幂等最终防线（Redis 标记会过期丢失）；对账公式 Redis 剩余 + 成功订单 = 初始库存，每 5 分钟跑、差异超阈值告警
- 避坑：网关不查 DB、不用 DB 行锁扛扣减、不用单库存 key、降级不回退 DB（快速失败）、不只前端限流

1. **需求拆解**：六个关键问题表（SKU 数/库存/QPS 层级/时长/可否少卖/公平性），假设 1 爆款、1000 件、下单接口 10 万 QPS、10 分钟（峰值前 10 秒）、可少卖、先到先得+防刷。
2. **容量评估**：漏斗五段（10 万→5 万→2 万→1000 成功→DB 1000 TPS）；QPS 从预约量倒推；带宽/网关/应用/Redis/Kafka/MySQL 逐项推导；并发≈QPS×RT（网关 2000、应用 1000、Redis 10、DB 5）；压测三段走（单机基线→集群线性→全链路峰值）。
3. **架构全景**：CDN+前端 → 网关 → 秒杀服务 → Redis Lua 预扣 → Kafka → 订单服务 → MySQL，旁路配置中心/监控/对账/补偿队列；原则是每层只做自己最便宜的事。
4. **核心设计**：Redis Lua 原子预扣（附脚本，三个细节：同脚本原子、同 hash tag、脚本内轻逻辑）；库存分桶（附 Java 代码，少卖代价与三种补偿方式）；落账对账闭环（Kafka 削峰三理由、唯一索引保底、对账公式与告警）。
