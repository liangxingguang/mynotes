# watch、trace、tt：把方法看透的三件套

> 摘要：三个命令都在"看方法"，分工却完全不同：trace 看耗时卡在哪一层，watch 看数据对不对，tt 把一次调用的现场存下来、事后回放。这篇讲清三者的选择、各自的参数纪律，以及为什么 trace 一定要加次数限制。

## 核心要点

- **一个管时间、一个管数据、一个管现场**：`trace` 看耗时卡在哪一层；`watch` 看入参、返回值、异常对不对；`tt`（time tunnel）先把调用录下来、事后回放。
- **trace 别看最外层**：最外层总耗时你已经知道了，有价值的是**哪一层突然变宽**（如 80% 时间停在 DAO 调用上 → 问题在数据库那一段）。要点：加 `-n` 次数限制；一次只 trace 一个方法，同时挂多个输出会互相穿插。
- **watch 的四个时机参数**：`-b` 执行前看入参、`-s` 正常返回后看返回值、`-e` 抛异常时看异常、`-f` 方法结束后看耗时。调接口前先 `-b` 看入参，就能排除"参数根本没传对"这种最常见的原因。`-x` 是展开深度，嵌套打不出来先调大，刷屏就调小。
- **tt 三步**：`tt -t 类名 方法名` 开始记录（每调一次存一条，带索引和时间戳）→ `tt -l` 列出已记录调用 → `tt -i 索引` 看那一次的入参返回值异常，加 `-p` 可回放。**`-t` 也要加次数上限**，否则记录一直增长占内存。
- **排查顺序：先 trace，再 watch，最后 tt。** 先定位"哪一层"，再定位"什么数据"，最后才是"怎么复现"。顺序反了会在无关的方法上浪费采样次数。
- **三条纪律**：都要加次数上限、排查完一定要停；一次只挂一个观察点（多命令同开比不看还难判断）；先在测试环境验证表达式（写错不报错、只是不输出，会误以为"方法没被调用"）。
- **共同点**：这三个命令都只能告诉你"发生了什么"，不能告诉你"该不该这样"——1.8 秒算不算慢取决于 SLA，返回 null 算不算 bug 取决于业务约定。

## 正文

> 采集说明：正文完整可读，仅配图未加载（1px 占位符）、选择表字段被拆行，信息无损。

`trace`、`watch`、`tt` 是三个最常用的方法级命令，很多人把它们混着用。但它们的定位其实很清楚：**一个管时间，一个管数据，一个管现场。** 选错了命令，你会得到一屏看不太懂的东西，然后开始怀疑工具。

### trace：慢在哪一层

`trace 类名 方法名`，它把这个方法内部的调用链按耗时排出来。看的时候注意一件事：**别看最外层。** 最外层的总耗时是你已经知道的，有价值的是**哪一层突然变宽**。如果 80% 的时间停在一个 DAO 调用上，问题就在数据库那一段，不必再往业务逻辑里翻。

两个使用要点：**加次数限制**（`-n`），不加它就一直挂在线上采样；**一次只 trace 一个方法**，同时挂多个输出会互相穿插。

### watch：数据对不对

`watch` 解决的是另一类问题：**方法被调用了，但结果不对。** 基本写法是给一个观察点表达式，看入参、返回值、异常这三样：

```
watch 类名 方法名 '{params, returnObj, throwExp}' -x 2
```

它还有四个时机参数，决定了什么时候输出：`-b` 方法执行前看入参；`-s` 正常返回后看返回值；`-e` 抛异常时看异常；`-f` 方法结束后看耗时。

调接口前先 `-b` 看入参，就能排除"参数根本没传对"这种最常见的原因。`-x` 是展开深度，**嵌套对象打不出来先调大它**，反过来输出刷屏就该调小。

### tt：把现场存下来

`tt` 是 time tunnel，最容易忽略也最有用。前两个命令是"现在盯着"，`tt` 是"先录下来，回头再看"——在你没法复现、或者要等定时任务跑完之后再分析时，价值很大。

1. `tt -t 类名 方法名` 开始记录，每调一次存一条，带索引和时间戳。
2. `tt -l` 列出已记录的调用。
3. `tt -i 索引` 看那一次的入参、返回值、异常；加 `-p` 可以对这次调用做回放。

**注意 `-t` 也要加次数上限**，否则记录会一直增长、占内存。录到你要的那条就停。

### 一个顺序：先 trace，再 watch

实际排查很少只用一个命令。常见的顺序是：

1. 先 `trace` 找出耗时最大的那一层。
2. 再用 `watch` 看那一层的入参和返回值。
3. 如果问题是偶发的，用 `tt` 录下来，等下一次复现。

**先定位"哪一层"，再定位"什么数据"，最后才是"怎么复现"。** 顺序反了，你会在无关的方法上浪费采样次数。

### 三条纪律

**一、都要加次数上限。** `trace`、`watch`、`tt` 默认会一直生效，排查完一定要停，别让它在你离开之后还挂在生产上。
**二、一次只挂一个观察点。** 多命令同时开，输出互相穿插，比不看还难判断。
**三、先在测试环境验证表达式。** 表达式写错不报错，只是不输出——然后你会误以为"方法没被调用"。这个坑踩一次要查很久。

### 一张选择表

| 你想知道 | 用哪个 | 关键参数 |
|---|---|---|
| 耗时卡在哪一层 | `trace` | `-n` 限制次数 |
| 入参对不对 | `watch` | `-b` + 观察点表达式 |
| 返回值/异常是什么 | `watch` | `-s` / `-e` |
| 想事后回看某次调用 | `tt` | `-t` 录、`-i` 看、`-p` 回放 |

这三个命令的共同点是：**它们都只能告诉你"发生了什么"，不能告诉你"该不该这样"。** 1.8 秒到底算不算慢，取决于这个接口的 SLA；返回 null 到底算不算 bug，取决于业务约定。**工具给事实，判断还得你来。**
