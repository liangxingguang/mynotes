# Arthas 上手：从 attach 到第一个结论，6 个命令够用

> 摘要：官方文档很全，但新手卡在三件事：怎么挂、挂上去敲什么、什么时候退出。这篇按顺序讲清 attach 的两种方式与三类失败原因、6 个命令对应 6 类问题、三个最容易踩的参数细节、退出清理，以及 4 条生产纪律。

## 核心要点

- **挂上去两种方式**：`java -jar arthas-boot.jar` 列出进程后输入序号；进程多或脚本化时加 `--select <pid>` 指定。挂成功提示符变成 `[arthas@进程号]$`。
- **挂不上的三个原因**：执行用户与目标进程不一致（须用启动服务的那个用户）、telnet 3658 与 web 8563 端口被占（可指定端口）、JDK 版本太老（attach 依赖 JVM attach API）。
- **attach 本身会造成极短停顿**，别在流量峰值反复挂、反复退。
- **6 个命令对 6 类问题**：`dashboard` 排除方向；`thread -n 3` / `thread -b` / `thread 线程号` 对付 CPU 高、死锁、看栈；`trace` 看慢在哪一层；`watch` 看入参返回值异常；`jad` / `sc -d` / `sm` 确认线上代码版本；`profiler` 出火焰图。
- **三个参数细节最易踩**：`trace`/`watch` 忘了加 `-n` 会一直挂着；`-x` 展开深度先小后大；条件表达式写错不报错、只是不输出——"明明调用了却没输出"先怀疑表达式，再怀疑方法没被调用。
- **退出要清理**：`stop` 只退出诊断工具、不停业务进程，但退出前必须停掉还挂着的 `trace` / `watch` / `monitor`。
- **4 条生产纪律**：测试环境先跑一遍命令；热点方法别长时间挂 trace；`redefine` / `retransform` 慎用；操作留记录。

## 正文

> 采集说明：正文完整可读，仅配图未加载（正文里残留 1px 占位符），表格字段被拆行，但信息无损。

Arthas 的官方文档写得很全，但第一次用它的人通常卡在三件事：**怎么挂上去、挂上去敲什么、什么时候该退出。**

### 第一步：把 Arthas 挂上去

启动方式两种：直接跑 `java -jar arthas-boot.jar` 让它列进程，输入序号就 attach 上；或加 `--select` 和进程号指定。挂上后提示符变成 `[arthas@进程号]$`。

挂不上去通常是三个原因：**用户不一致**（目标进程是 A 用户启动的，用 B 用户 attach 权限不够，要用启动服务的那个用户执行）；**端口被占**（默认 telnet 3658、web 8563，同机多实例会冲突）；**JDK 版本太老**（attach 机制依赖 JVM attach API）。

还有一个容易被忽略的点：attach 本身会造成极短的停顿，所以别在流量峰值反复 attach、反复退出。

### 6 个命令，对应 6 类问题

1. **dashboard**：不知道从哪查时先敲它。实时刷新面板，看线程数、CPU、堆内存、GC。**作用不是定位问题，是排除方向**——GC 频繁、老年代快满时，排查重点就不在业务代码。
2. **thread**：`thread -n 3` 列最忙的三个线程；`thread -b` 找阻塞其他线程的那个（怀疑死锁先敲它）；`thread 线程号` 看完整栈。判断方法：三个最忙的线程都停在同一个方法上，那就是那里在烧 CPU。
3. **trace**：`trace 类名 方法名` 把调用链按耗时排出来，看**哪一层的耗时突然变大**（如 90% 时间花在某个 DAO 调用上，问题就在数据库那一段）。**一定要加 `-n` 次数限制**，否则一直挂着采样，热点方法上开销不小。
4. **watch**：排查"数据不对"最直接的工具。`watch 类名 方法名 '{params, returnObj, throwExp}' -x 2`，`-x` 控制展开深度（嵌套对象打不出来通常是深度设小了）。还能加条件，只在满足条件时输出——高频方法不加条件只会看到几千条一样的记录。
5. **jad / sc / sm**：这类问题最冤——**代码明明改了，线上行为还是旧的**。`jad 类名` 反编译当前已加载的类；`sc -d 类名` 看由哪个 ClassLoader 加载、来源是哪；`sm 类名 方法名` 看方法签名。三者配合确认"我以为的代码"和"实际在跑的代码"是不是同一份。
6. **profiler**：`profiler start` / `profiler stop`，底层 async-profiler，能出 CPU 和内存火焰图。适合"知道大概哪个方法慢，但想知道更细热点分布"。

### 三个参数细节，最容易踩

**一、忘了加次数限制。** `trace`、`watch` 默认一直生效，排查完记得停，别让它在你离开之后还挂在生产上。
**二、展开深度设错。** `-x` 太小看不到嵌套字段，太大输出刷屏，先小后大一层层加。
**三、条件表达式写错，结果一条都不输出。** 写错不报错，只是不匹配。

### 用完要退出，而且要清理

`stop` 是退出 Arthas 客户端，**只退出诊断工具，不会停掉业务进程**。但退出之前记得把还挂着的 `trace`、`watch`、`monitor` 停掉——诊断命令的会话不清，有些采样会一直跑着。

### 一张速查表

| 遇到什么 | 敲什么 | 关键参数 |
|---|---|---|
| 不知道从哪查 | `dashboard` | 看 GC 和线程数 |
| CPU 高 | `thread -n 3` | 看最忙的线程在跑什么 |
| 怀疑死锁 | `thread -b` | 找阻塞源 |
| 接口变慢 | `trace 类 方法` | `-n` 限制次数 |
| 返回值不对 | `watch 类 方法` | 观察点 + `-x` 深度 |
| 代码版本可疑 | `jad` / `sc -d` | 看实际加载的类 |
| 找性能热点 | `profiler` | start / stop 出火焰图 |

Arthas 的学习成本其实不在命令，在**判断**：这一屏输出说明什么、下一步该敲哪条。命令敲熟是几小时的事，判断能力只能靠一次次排查积累。
