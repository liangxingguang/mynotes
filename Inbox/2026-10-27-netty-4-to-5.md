# Netty源码分析(番外篇6) — Netty 4.x 到 5.x：演进路线与未来展望

> 梳理 Netty 从 3.x 到新 5.0 的版本演进：4.0→4.1 的关键升级、2018 旧 5.0 为何失败、2024 重启的新 5.0 改了什么（JDK17、io_uring、Buffer API 重设计），以及不同场景下的升级建议。

## 核心要点

- 4.1 是当前绝对主流：Epoll 原生传输（吞吐提升 10-30%）、对象池化全面铺开、HTTP/2 原生支持
- 旧 5.0（2018）失败两大原因：用 ForkJoinPool 替代 EventLoop 丢了线程绑定确定性；API 破坏性变更导致迁移成本不可接受
- 新 5.0（2024+）思路是渐进演进：最低 JDK 17（Record/Sealed/Pattern Matching 红利）、清理 deprecated API 但保留 4.1 核心用法
- 最重磅新特性是 io_uring 支持：批量提交+共享环形缓冲，高吞吐场景比 epoll 提升 20-50%
- Buffer API 将拆分读写接口并支持 try-with-resources 自动释放，解决 ByteBuf 接口臃肿问题
- 升级建议：4.1.x 继续用（维护到 2027 后）；新项目且 JDK21+ 可试 5.0；业务应用跟随中间件版本即可
