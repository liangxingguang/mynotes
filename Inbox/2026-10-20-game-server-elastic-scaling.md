# 游戏开发：服务器弹性伸缩

> 游戏服务器弹性伸缩的理论笔记：从登录负载均衡的"信息滞后"问题讲起，给出虚拟负载/动态权重两种解法与防炸服清单；主体部分讨论有状态公会服如何平滑伸缩——引入固定数量的路由服维护路由表，扩容时旧服先存档、压队列、经路由服把数据与积压请求转交新服，用路由切换状态机保证时序；最后指出路由 Key 的本质是"时序的容器"而非数据身份。

## 核心要点

- **负载均衡的信息滞后**：Game 服 5s 定时上报负载，开服瞬间请求会压向同一台。解法一**虚拟负载**：每分配一个请求就加虚拟负载，登录成功/超时后独立移除，选服时真实+虚拟一起算；解法二**动态权重**：`score = rload / weight`。思想相同——分配后立即降低被选概率
- **防炸服清单**：最危险的是创角 DB 操作（大量读写 + 同步驱动阻塞逻辑线程）。措施：Game 服设最大在线数排队/拒登、限制最大登录 QPS（分帧落地）、高开销 IO 迁辅助线程、Login 服限 QPS；核心思想是削峰。真正的问题不是 QPS 而是稳定性（卡顿、断连）
- **路由服**：有状态服务弹性伸缩必须有路由表（类比 MongoDB Mongos）；路由服固定数量不伸缩可大幅简化分布式协调，还可替代 MQ 做自定义 Key 路由、简化数据迁移。业务服两种用法：按 Key Hash 选 Router（简单、推荐先用）vs 绑定特定 Router（时序好但需组网协调）
- **一致性 Hash 的灵活运用**：有状态服不能靠它直接伸缩（会双写）；案例——Center 服不感知 Scene 服，只生成一个 Key 发给所有 Game 服，各自用一致性 Hash 选 Scene 服即收敛到同一台，"简单胜过完美"
- **数据迁移与平滑切换**：扩容不只是新 Key 走新服（那只算扩容不算负载均衡）。流程：旧服感知新服 → 存档待迁数据、期间请求压队列 → 卸内存 → 数据+积压请求**经 Router 转发**新服；Router 用 `sid/nextSid/nextId` 状态机感知路由切换开始与完成，消除目标端队首阻塞，全程消息有序
- **路由 Key 的本质**：框架只保证同一 Key 上请求有序（虚拟 Channel）。Key 不是数据的"身份"而是**时序的容器**，实体 ID 只是恰好常与时序边界重合；选 Key 前先梳理哪些操作必须有序
