# 异步链路幂等实战：本地消息表配套防重，解决重复扣款与消息重放

> 基于商城大促重复扣券真实事故，拆解异步链路重复流量的三大来源，对比四类幂等方案的取舍边界。核心结论：重试是最终一致性方案赖以生存的基础，而重试必然引入重复执行，因此幂等不是可选功能，而是整套最终一致性体系中不可分割的配套约束层。

## 核心要点

- **事故根因**：DB 事务提交后 ACK 丢包，应用判超时但事务已落地（「不确定结果」问题），定时任务重试导致重复扣券
- **异步重复流量三大来源**：本地消息表重试、RocketMQ 主从切换消息重放、第三方支付回调重试；均属系统自治产生，前端防抖/Token 完全无效
- **四类方案取舍**：
  - 唯一索引：仅防新增写入，不防状态变更，高并发有行锁压力
  - 幂等记录表：查询+写入须同事务+唯一索引兜底，需 expire_time 归档防膨胀
  - 业务状态机幂等（主推）：状态校验与业务变更必须包裹在同一事务内，否则并发竞态必然重复执行
  - Token 防重：同步场景专用，异步链路无效
- **三大隐性风险**：幂等键必须全局唯一且重试不变；幂等记录、业务数据、消息状态须同一本地事务提交；Redis 缓存只能前置拦截，必须数据库兜底
- **分层防护闭环**：MQ 链路（msgId+topic）、支付回调（流水号）、本地消息重试（状态机+消息表联动），外层快速拦截、底层持久化兜底
