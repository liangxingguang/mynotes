> **摘要**：RAG 系列开篇。以企业内部制度问答为例：通用大模型给出的数字来自公开语料的常见做法，对不上自家条款。要答案贴合私有知识，工程上有四条路——长上下文、微调、Agent 编排、检索增强生成，实际改的变量不同：长上下文改"一次能读多少"（成本随语料量线性上升），微调改"怎么说"（知识更新须重训、删事实无法定点、过时知识会被复述），Agent 改"做什么、按什么顺序做"（事实仍需从别处取回，RAG 是 Agent 的事实来源）。只有 RAG 改"依据哪些事实说"，内部制度、客服售前、合规法务、研发运维四类场景（知识私有、更新快、答案要能核）非检索不可。

## 核心要点

- **场景切入**：企业内部制度问答（一批 PDF/Word 制度文件，员工问"出差住宿标准是多少"）最易看清 RAG 价值——通用大模型格式完整、数字具体，但数字来自公开语料常见做法，不是这家公司的条款。
- **四条路对比**（改的变量各不相同）：
  - **长上下文**：改"一次能读多少"。窗口涨到几十万 token 后全量塞入可行，但成本随材料量线性上升（语料 100→10000 篇，单次成本涨 100 倍）；检索只与筛出的段数有关，基本不变。
  - **微调**：改"怎么说"。改输出风格、格式与领域表达，但知识供给有三硬约束——改一次知识要重训一次；删一条事实无法定点完成；训练数据里的过时内容会被继续复述。
  - **Agent**：改"做什么、按什么顺序做"。流程变复杂不会让事实变准确，每一步仍要从某处取回材料；**RAG 是 Agent 的事实来源，Agent 是 RAG 的使用者**。
  - **RAG**：改"依据哪些事实说"。
- **非检索不可的四类场景**：内部制度、客服售前、合规法务、研发运维文档。共同点三条：知识私有（公开语料没有）、更新快、答案要能核。
- **判断顺序**：三条同时成立时检索是唯一能同时满足的做法；缺事实先补事实——事实错了，后面两步都在放大错误。
