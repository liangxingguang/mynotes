# 游戏服务器架构应该如何分层？——四层骨架

> 游戏服务器架构可拆解为四层骨架，各回答一个核心问题：**连接层**（客户端怎么连进来：长连接管理、会话绑定、心跳、编解码、鉴权限流、断线重连）；**实体层**（游戏对象怎么存在：有状态实体的生命周期、消息按序投递、状态隔离、AOI、持久化与迁移）；**RPC 约束层**（服务间怎么可靠调用：服务发现、按 entityId/shardId 路由、超时熔断重试、幂等、可观测性）；**协调层**（分布式下对象放在哪里：分片分配、再平衡、故障转移、迁移协调、防脑裂租约）。四层以纯接口隔离，演进路线先单机闭环再上分布式。

## 核心要点

- **连接层只做连接**：严禁写业务逻辑（购买道具/进副本绝不能出现在这里），只负责解包、找归属、转发；避坑是分层的第一条纪律
- **实体层是有状态腹地**：区别于 Web 无状态业务层——实体（玩家/房间/副本/公会）有生命周期且消息必须严格按序到达；目标是让业务只关心"实体收到消息后状态如何演进"
- **RPC 约束层不只是语法糖**：核心是把超时、幂等、熔断、可观测做成契约；跨服调用失败后必须明确降级/报错/重试策略，严禁无限重试
- **协调层是集群大脑**：单机可不存在；基于 etcd/ZK/Redis 或自研 Coordinator，只维护拓扑与分片映射，不碰玩法逻辑；防脑裂靠分布式锁与租约
- **请求流转**：连接层解析 → 查路由 → 本地实体直投 / 远端 RPC 转发 → 结果回推；协调层平时不占消息吞吐，只在节点上下线/分片迁移时更新全网路由
- **落地五建议**：边界清晰、状态有界、重视约束、接口隔离（换网络库/RPC 框架成本低）、先单机闭环再分布式
