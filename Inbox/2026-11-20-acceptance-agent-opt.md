> **摘要**：腾讯云开发者文章（作者吴思）：AI 让代码生成提速后，验收成为需求交付新瓶颈——接口返回 200 只说明调通一次，需求逻辑、边界条件、老数据兼容、异步任务、日志与 DB 状态仍需验证。作者团队在自建 OPT 平台（基于 CodeBuddy 等 CLI 的多 Agent 协同研发平台）的需求交付小队中补上"后端验收 Agent"，核心是 api-acceptance Skill，五阶段流程：变更接口分析（从 git diff 反推验收范围）→ 编译发布与接口验证（确认"能否验"，环境优先隔离环境）→ Gherkin 测试（Given-When-When 拆场景，人工确认后才真实执行）→ TAPD 预测试（补充用例来源）→ 验收结果输出（L1-L4 多层证据链，拒绝"code=0 即通过"）。异常分硬阻塞/软失败：能验证的尽量验证，不能验证的诚实标注。已运行 160+ 次，覆盖 30+ 需求，单次人工投入从约 2 小时降至 20 分钟（-80%+）。

## 核心要点

- **痛点**：AI 代码生成速度 >>> 人工需求验收速度。后端采纳≠代码已生成、≠接口能调通——需求逻辑是否正确、边界条件是否覆盖、老数据是否兼容、异步任务是否生效、日志与 DB 状态是否符合预期，仍需逐层验证，人工验收成为交付新瓶颈。
- **方案定位**：OPT 平台需求交付小队按"需求分析 → 方案规划 → 编码实现 → 代码验收"协同，Leader 调度、人确认预期与最终结论；后端验收 Agent 位于编码之后，不通过则打回修复再验。验收 Agent 的执行内核即 api-acceptance Skill。
- **贯穿设计**：异常分**硬阻塞**（不越过人机确认与环境前提）与**软失败**（发布失败、spec 缺失、日志不可用时继续完成能做的，诚实标注 WARN/SKIP/无法判定）；核心原则——能验证的尽量验证，不能验证的诚实标注，不把受限项伪装成通过。
- **五阶段主流程**：
  1. **变更接口分析**：从 git diff、需求描述、分支信息、接口定义反推验收范围——变更文件/函数、调用链、入口接口，形成测试接口列表，并标注三类兼容性风险（影响不止改动文件本身，字段类型/枚举范围/错误码语义都可能波及调用方）。
  2. **编译发布与接口验证**：先确认"能否验"——服务能否编译发布、环境是否可达、接口能否用最小参数调通、契约是否一致；环境优先级：Agent 专用隔离环境 > 个人开发环境 > 公共测试环境。
  3. **Gherkin 测试**：用 Given-When-Then 把需求拆成可读、可确认、可执行的接口场景（覆盖正常/异常/边界三类）；**硬阻塞点**：场景确认报告必须人工确认后才真实执行——预期错了报告更有迷惑性；参数构造优先真实数据、LLM 推理兜底；需业务测试知识库（鉴权说明、测试账号、数据构造方法）支撑。
  4. **TAPD 预测试**：读取 TAPD 关联用例补充 Gherkin 之外的需求路径与边界场景，分类筛选适合后端独立验证的用例。
  5. **验收结果输出**：避免"接口返回 code=0 就写通过"的表面成功陷阱（字段含义不符、写接口成功但 DB 状态未变、下游失败、异步未消费）；采用 L1-L4 多层证据链（接口返回、业务状态、链路日志、静态 Review 兜底），结论分四档，报告以 HTML 呈现。
- **实践效果**：已运行 160+ 次，覆盖 30+ 需求、80+ 入口接口、800+ Gherkin 场景，发现 20+ 问题并打回修复；典型需求单次人工投入约 2 小时 → 20 分钟（降 80%+）；三个变化：验收提效、问题发现前置到开发阶段、验收能力以 Skill 复用推广到其他医疗业务。
- **五点体会**：确定性先于自动化（先校准"验什么、怎么算对"再自动化）；事实密度影响可靠性（上下文越完整 Agent 越像工程助手，知识库建设至关重要）；用证据链支撑结论；边界标注提升可信度（诚实的 WARN/SKIP 比表面全绿更有价值）；人机协同支撑最终判断（AI 帮助人基于证据决策，不替人担责）。另在探索 H5/小程序端侧 E2E 验收 Agent。
