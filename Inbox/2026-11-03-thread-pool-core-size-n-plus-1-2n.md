# 线程池核心线程数怎么配置？为什么 CPU 密集型常用 N+1，I/O 密集型常用 2N？

> 摘要：线程数的关键不是任务"名字"，而是实际计算与等待比例。CPU 密集型从 N 或 N+1 开始（避免争抢 CPU）；阻塞式 I/O 密集型从 2N 开始（等待与计算交错），更一般估算公式：线程数 ≈ N × U × (1 + W/C)，最终须压测并受下游容量约束。

## 核心要点

1. N = JVM 可用处理器数（`Runtime.getRuntime().availableProcessors()`，容器中需核实 CPU 配额），不是 corePoolSize
2. 线程执行任务只有两类时间：计算时间（占 CPU）与等待时间（不占 CPU 但仍占工作线程）；线程数取决于 W/C 比例而非任务命名
3. CPU 密集型：N 个线程已让 N 个 CPU 有事做；再多只带来上下文切换、栈内存、缓存局部性变差、锁竞争
4. N+1 只是经验值（填补短暂停顿空隙），非规范要求；同进程还有 GC/其他线程池抢 CPU 时甚至应少于 N
5. 2N 的直觉：等待≈计算时，两个线程提供一个 CPU 的持续计算；等待更久则 2N 不足，等待很少则偏大
6. 通用估算：线程数 ≈ N × U × (1 + W/C)，U 为目标 CPU 预算（如 0.8）；公式是简化模型，不是直接配置值
7. 线程数不能无限加：受下游容量约束（如 DB 连接池 20 个，80 线程只会排队等连接）；多类业务应隔离线程池
8. corePoolSize 与 maximumPoolSize 要一起看：先建到 core → 入队 → 队列满才扩到 max；无界队列会让 max 形同虚设
9. 配置四步：判断任务实际 W/C（含 P95/P99）→ 选初始值 → 设置有界资源（队列/超时/拒绝/限流）→ 压测调优

## 正文

**结论先行**：设 N 为 JVM 可用处理器数量——CPU 密集型任务从 N 或 N+1 开始压测；阻塞式 I/O 密集型从 2N 开始尝试，但等待时间较长时合适线程数可能远大于 2N，也可能受下游容量限制而更小。这些都是初始经验值，最终结合等待比例、下游容量和压测结果决定。

**一、为什么任务类型影响线程数**：线程执行任务经历计算时间（占 CPU）与等待时间（等 DB/网络/磁盘/锁，不占 CPU 但占工作线程）。4 个 CPU 下：4 个纯计算线程已让 CPU 很忙，加线程只会争抢；4 个线程大多等 DB 时 CPU 很闲，加线程可让等待与计算交错。关键不是任务名字，而是实际运行的计算/等待比例。（本文讨论传统平台线程 + 阻塞任务；NIO 或虚拟线程调优方式不同。）

**二、CPU 密集型为什么从 N 或 N+1 开始**：典型任务如图片压缩、视频编码、加密哈希、大规模计算、序列化反序列化（仍以运行情况为准，如读远程文件多就未必是纯 CPU）。线程数接近 CPU 数即可让所有 CPU 有事做；增至 20 个线程不会让 4 个 CPU 执行 20 线程，反而带来上下文切换、栈内存、缓存局部性变差、锁竞争。N+1 用于填补短暂等待/缺页/锁竞争的空隙，但"+1"非规范要求、不保证更快；任务几乎纯计算时 N 就够，同进程还有 GC 和其他线程池时甚至应少于 N。稳妥做法是从 N 左右测试 N-1、N、N+1 比较吞吐与延迟。

**三、I/O 密集型为什么常说 2N**：典型任务如同步 HTTP 调用、阻塞 JDBC、读写磁盘、等缓存/MQ。线程池只有 N 个线程而大多在等待时 CPU 闲置，增加线程让等待与计算交错。若任务一半时间计算、一半等待，一个线程平均只占 50% CPU，理想化两个线程提供一个 CPU 的持续计算，故 N × 2 = 2N。隐含前提是等待≈计算；等待更久 2N 不足，等待很少则偏大。

**四、更有解释力的估算公式**：线程数 ≈ N × U × (1 + W/C)，其中 N=可用 CPU 数，U=目标 CPU 预算（如 0.8），W=平均等待时间，C=平均 CPU 计算时间。示例：C=10ms、W=10ms 时 1+W/C=2，U=1 即得 2N。N=8 时：W=0 → 8（近纯 CPU）；W=10ms → 16（=2N）；W=40ms → 40；W=90ms → 80（需特别关注下游容量）。公式局限：并发增大可能让数据库变慢（W 上升）；任务耗时分布差异大；等待同一锁时加线程不增吞吐；缓存竞争/上下文切换/GC 成本随线程数增加；下游有并发限制。算出 80 不代表直接配 80，只是理解"等待越多可能需要越多并发"的起点。

**五、为什么 I/O 线程数不能无限增加**：如数据库连接池最多 20 连接而线程池 80 线程，高负载下最多约 20 个任务同时拿到连接，其余等连接；继续加线程不增 DB 吞吐，反而导致更多内存占用、请求等连接、超时增加、DB 压力扩大、排队变长。也不能简单说"线程数绝不超过连接数"（任务可能只有部分时间持连接），但 DB 连接数、下游并发限制和响应时间必须纳入容量设计。外部依赖多的系统可按任务类型分池，并对 DB、远程接口分别设并发限制，避免慢依赖拖垮其他业务。

**六、corePoolSize 与 maximumPoolSize 一起看**：ThreadPoolExecutor 任务提交顺序为：未达 corePoolSize 创建线程 → 入队 → 队列满才扩到 maximumPoolSize。无界队列下任务一直入队，线程数长期停留在核心数附近，max 形同虚设。配置需同时考虑：核心/最大线程数、队列类型与容量、拒绝策略、下游容量与业务延迟目标。

**七、实际项目配置四步**：
1. 判断任务实际在做什么：统计 CPU 计算时间、DB/HTTP/磁盘等待时间、连接与锁等待、总耗时与尾部耗时（P95/P99），不要只看平均值
2. 选初始值：近纯计算取 N 左右（测 N-1/N/N+1）；明显阻塞 I/O 取 2N 起点或按 W/C 估算；计算与等待混合按实测 W/C 再压测；多类业务混用按业务隔离线程池
3. 设置有界资源：队列容量、排队时间 vs 业务超时、满载后拒绝/降级/调用方执行、DB 与远程服务并发上限、任务超时/取消/限流
4. 压测调整：观察吞吐量、延迟（均值/P95/P99）、CPU 使用率与上下文切换、队列长度与排队时间、拒绝次数、连接池使用率、内存与 GC；选满足目标且留余量的配置，不追最大线程数

**八、面试答法**：核心线程数区分 CPU 与 I/O 密集型，因任务 CPU 占用与等待时间不同。CPU 密集型多在计算，线程过多只争抢 CPU，故从可用 CPU 数附近（N 或 N+1，加一只是经验值）开始；阻塞式 I/O 等待时占线程不占 CPU，可加线程让等待与计算交错，常说的 2N 可理解为等待≈计算时的估算；更一般估算 N×U×(1+W/C)，实际还需考虑连接池、下游容量、线程开销、队列与拒绝策略，最终压测确定。
