# 架构设计 | 积分系统：并发扣减、分批过期、幂等、冲正与对账

> 摘要：从一笔积分消费推演整个积分系统架构——110 积分（50 于 9/30 到期 + 60 于 12/31 到期）消费 80，客户端超时重试、几天后订单退款。难点不在加减，而在回答"第一次成功没有、重试会不会重复扣、80 来自哪些批次、退款怎么退、缓存/MQ/过期任务失败后怎样证明余额仍正确"。八步推演：定不变量 → 总体架构 → 6 类数据模型 → 写入链路 → 异常恢复 → 扩展 → 上线 → 演进。

## 核心要点

- **先定不变量再谈技术**：① 同一业务操作只生效一次 ② 可用积分不能扣成负数 ③ 余额变化有不可覆盖的历史 ④ 退款与修正必须留新记录 ⑤ 余额能由交易、流水、批次共同解释。排行榜可晚几秒，余额、幂等结果、账务历史不能。
- **流量要变成可验证数字**：教学假设 1000 万注册用户、查询峰值 2 万 QPS、变更峰值 3,000 TPS。**还要看单账户最大并发写入**——它直接决定用行锁、乐观锁还是条件更新，也决定热点账户是否单独限流。
- **6 类数据**：账户快照、积分交易（幂等键唯一）、账户流水（只追加）、积分批次（来源/到期日/剩余量）、批次消耗明细、发件箱事件（与核心变更同事务提交）。
- **幂等键 = 业务方 + 业务单号 + 操作类型**，"消费/冻结/确认扣减/取消冻结"是不同操作。网关可拦重复流量，但**最终幂等必须由积分核心持久化并用数据库唯一约束守住**。
- **一次消费的本地事务 7 步**：建交易（已存在返回原结果）→ 锁账户或版本号 → 原子扣减且 ≥0 → **按"较早到期优先"消耗批次** → 写批次消耗明细 + 追加流水 → 更新快照 + 写发件箱 → 提交。**绝不能先读余额、应用里判断后无条件覆盖**。
- **冻结不是固定步骤**：一次调用能完成的兑换直接扣减；只有订单之后还可能确认或取消时才用"冻结 → 确认扣减／取消解冻"状态机。
- **缓存与事件**：Cache-Aside 先提交 DB 再删缓存，删除失败由账务事务里的失效事件重试；需通知多系统或削峰时再送 MQ，**MQ 不是发件箱的必选项**。热点失效用请求合并或短期租约，回填前再校验版本；**扣减始终以数据库为准，不能按 Redis 余额记账**。事务发件箱不保证只处理一次，消费者仍要幂等。
- **异常恢复**：超时重试靠同一幂等键返回首次状态；**退款是新增冲正交易 + 反向流水，绝不删原流水**，按批次消耗明细找回原批次；过期任务按批次处理 + 稳定任务标识 + 调度租约防重复清零。
- **对账三类关系**：余额与流水批次汇总一致、业务与积分系统总量与逐笔状态对应、发件箱与下游读模型有无长期未完成记录。**自动发现问题 ≠ 自动改账**，直接改余额会断审计链且故障继续。
- **扩展顺序**：查询多→缓存 + 异步读模型（读模型不能用于决定能否扣分）；核心数据多→**先归档再决定是否分片**；真到上限才按账户标识稳定路由，流水量大时在分片内按时间分区，**不要只按时间把同一账户打散**（否则幂等键无法靠单库唯一约束全局去重）。热点账户加实例无效，靠限单账户并发、按序执行、缩短事务、拆子账户。
- **演进四步**：① 先把账记对（模块化单体 + 本地事务闭环）② 再移开非核心工作 ③ 按瓶颈扩展（容量到才分片、团队多了才拆服务）④ 提高恢复等级（抵扣高价值权益后才加强清算/容灾/审计）。**思考尽量完整，落地保持克制，演进路线提前留好。**


## 正文

> 采集说明：原文约 8.6 千字符，已一次通读。抓取时**配图全部未加载**（残留 1px SVG 占位符），代码块被压成单行；概念、表格与步骤序号完整可读。

**01 先说清系统承诺，再讨论技术方案**：确认三件事——系统要完成哪些业务动作（发放、消费、冻结与解冻、退款与冲正、过期、查询、对账，不同动作需要的数据不同，只考虑余额加减的话遇到分批过期和退款就要推倒重来）、流量以什么方式到来、哪些结果绝对不能错。对外接口语义要写清：同一笔业务至少带业务方、业务单号、操作类型；返回"积分已经入账"还是"请求已经受理"是两种不同承诺，同步链路和异常处理也不同。

**02 总体架构（核心同步完成，外围异步收敛）**：查询请求 → API 网关 → 积分查询服务 → 优先 Redis，未命中回源权威库并重建缓存；明细与报表走只读副本或专门读模型；扣减冻结等核心判断始终回到账户核心与权威库。一次账户变更涉及的账户快照、交易、流水、批次由**同一个本地事务**提交，通知、报表、排行榜经事件异步更新。接入/规则/账户/过期/对账/查询是**业务边界而非部署边界**，早期用模块化单体先理顺数据所有权和依赖方向；账户核心不宜切得太碎，更不能让其他服务绕过接口直接改账户数据库。

**03 数据模型**：消费 80 的结果是——积分交易 T001（消费 80，处理成功）、账户流水 L001（可用 -80，110→30）、批次消耗 A001（取 B001 的 50）、A002（取 B002 的 30）、账户快照（可用 30）、发件箱事件 E001（`points.consumed`）。交易记整体结果、流水解释总余额变化、批次消耗说明具体来源，有了这层对应关系退款时才能找回原批次和有效期。若涉及多发行方、商户结算或账户间价值转移可采用复式记账；但**积分子账不等于企业财务总账**，单一平台规则简单时"账户快照 + 不可变流水 + 积分批次"已够用——选型标准是余额能否被历史记录完整解释。

**04 一次消费的写入链路（4 步）**：① 用幂等键确认是否处理过；② 一个本地事务完成记账（7 步，见上方要点）；③ **提交数据库后再处理缓存**（先提交后删缓存 + 失效事件重试 + 必要时送 MQ）；④ 跨系统通过事件收敛（订单系统在同一本地事务保存订单状态与发件箱事件，后台任务或 CDC 发送，积分系统按业务单号+操作类型幂等入账）。行锁、乐观锁、条件更新无固定答案，取决于单账户冲突概率与压测结果。

**05 失败后的账务找回**：请求超时——重试只应得到原来的结果，首次仍在处理中可明确返回"处理中"或让调用方有限等待后查询；订单退款——新增冲正，按批次消耗明细找回 A001/A002，若原批次已到期，采用哪条规则属产品规则但必须记录结果；积分过期——按批次处理，同一事务内减少批次剩余量、更新快照、追加过期流水，量大时按到期日期和账户范围拆分任务由多节点执行，调度租约负责分工与故障接管，稳定任务标识防重复清零；对账——三类关系 + 差异生成差错记录与工单（附业务单号、账户、积分数、差异类型），先定位原因再受控修复。

**06 扩展**：查询侧用 Redis 存余额副本/账户状态/热点汇总，历史明细与报表异步构建读模型；缓存键过期时间加少量随机值避免集中失效，无效参数和越权在入口拦截，格式合法但不存在的账户短期缓存空结果防穿透。核心数据侧先归档再决定分片，历史流水分区或转入低成本归档存储（前提是完整性、查询、恢复流程仍可验证），单库容量或写入真到上限才按账户标识稳定路由，跨账户复式分录要让对应分录处于同一事务边界，否则承担独立账本与跨分片协调成本。

**07 上线与演进**：入口按业务方/接口/账户限流；远程调用设超时，只对可重试且幂等的操作做有限重试；连接池、消费线程、批任务并发从下游吞吐反推，不能为追消息积压冲垮账户库；备份与故障转移要通过恢复演练验证，按业务损失明确 RPO/RTO。拆成独立服务后还要处理注册发现、负载均衡、配置管理、灰度发布；指标/日志/链路用统一请求号或交易号串联；除吞吐、延迟、错误率外，还要关注**幂等冲突、账户锁冲突、发件箱积压、消息重试、过期任务进度、对账差异**并设告警。安全上业务接入需认证/授权/防重放，跨网络跨组织按风险加签名校验，高价值兑换加风险校验，人工调账要有专门权限、审批和不可随意修改的审计记录。演进四步见上方要点。

**08 结语**：真正需要设计的从来不只是一次减法。业务规则决定积分怎样消费和退回，数据模型保存可追溯的事实，本地事务守住账户内部一致性，幂等、事件、冲正、对账让系统在超时与故障后重新收敛。方法论：**先画清业务边界、核心流程、数据关系，再给出当前真正要落地的架构；可能出现的下一步另用演进图说明并写清触发条件。幂等、事务边界、数据模型这些后期难改的部分提前想清楚，缓存、MQ、分片、微服务根据真实瓶颈逐步引入——思考尽量完整，落地保持克制，演进路线提前留好。**
