# CPU 打满、接口卡住、线程池耗尽：thread 命令怎么读

> 摘要：线程问题的难点不在命令，在读栈：同样是"卡住"，可能是 RUNNABLE 在等 IO、BLOCKED 在等锁、或者线程池根本没空闲线程。这篇讲 thread 的三条用法、读栈的顺序、线程池耗尽的识别方法，以及三个最容易误判的地方。

## 核心要点

- **先分清三种"卡"**：① CPU 真在算（RUNNABLE 且在跑业务代码，通常是死循环、正则回溯、大对象序列化）→ 改代码；② 在等锁（BLOCKED，等 `synchronized` monitor，特征是**一堆线程停在同一个位置**）→ 拆锁或降并发；③ 在等外部响应（状态也是 RUNNABLE，但停在 socket 读、DB 连接、HTTP 调用上）→ 去看下游。
- **thread 三条用法**：`thread -n 3` 列最忙三个线程（CPU 高时第一条就敲）；`thread -b` 找阻塞源（怀疑死锁或大面积卡顿）；`thread 线程号` 看完整栈。
- **读栈顺序：状态 → 你的代码 → 卡在等什么。** 先看 RUNNABLE/BLOCKED/WAITING/TIMED_WAITING；再往下翻到自己的 `com.xxx` 包（最上面几帧通常是 JDK 的）；最后看卡在哪个方法上（`socketRead0`、`pooledConnection`、`await` 说明是在等，不是在算）。
- **一句话判断：状态是 RUNNABLE 但 CPU 并不高——它多半在等 IO。**
- **线程池耗尽长什么样**：线程名成批出现、编号连成一片（`pool-1-thread-1` 到 `-200` 全停在同一个提交点或下游调用上）。这时看单个线程没用，要看总量与分布（`dashboard` 里的线程总数 + 排队堆积）。**线程池耗尽不是线程的问题，是下游变慢的连锁反应**，改池参数只能缓解。
- **三个最容易误判**：① RUNNABLE ≠ 在算；② CPU 高可能是 GC / `C2 CompilerThread` 等非业务线程；③ **一次采样不能代表持续**——隔几分钟再抓一次，两次都指向同一个方法才值得下结论。

## 正文

> 采集说明：正文完整可读，仅配图未加载（1px 占位符）、对照表字段被拆行，信息无损。

线程问题是线上排查里最容易被带偏的一类。因为它的表现都差不多：接口变慢、请求堆积、CPU 飙高。但**背后的原因可能是三件完全不同的事**，用错方向就会查一整天。`thread` 这个命令本身很简单，难的是看到那几十行栈之后怎么读。

### 先分清三种"卡"

**第一种：CPU 真的在被算。** 线程状态是 RUNNABLE，而且确实在执行你的业务代码。通常是死循环、正则回溯、大对象序列化。
**第二种：在等锁。** 线程状态是 BLOCKED，等的是 `synchronized` 的 monitor。特征是**一堆线程停在同一个位置**。
**第三种：在等外部响应。** 线程状态也是 RUNNABLE，但它停在 socket 读、数据库连接、HTTP 调用上。**看着像在跑，其实什么都没算。**

这三种的解法完全不同：第一种改代码，第二种拆锁或降并发，第三种要去看下游。

### thread 的三条用法

**`thread -n 3`**：列出最忙的三个线程，CPU 高的时候第一条就敲它。
**`thread -b`**：找出阻塞其他线程的那个线程，怀疑死锁或大面积卡顿时用它，比人眼翻栈快得多。
**`thread 线程号`**：看指定线程的完整调用栈。前两条定位到线程之后，用这条看细节。

### 读栈的顺序：状态 → 你的代码 → 卡在等什么

一屏栈有几十行，从上往下读会乱。按这个顺序看：

**第一步，看状态。** RUNNABLE、BLOCKED、WAITING、TIMED_WAITING，四个状态指向四个方向。
**第二步，找你自己的包名。** 栈里最上面几帧通常是 JDK 的，往下翻到你的 `com.xxx` 包，那才是问题发生的地方。
**第三步，看它卡在哪个方法上。** 如果是 `socketRead0`、`pooledConnection`、`await`，那它不是在算，是在等。

一个简单的判断：**状态是 RUNNABLE，但 CPU 并不高——它多半在等 IO。**

### 线程池耗尽，长什么样

线程池打满有个很明显的特征：**线程名成批出现，编号连成一片。** 比如 `pool-1-thread-1` 到 `pool-1-thread-200`，全部停在同一个提交点或同一个下游调用上。这说明池子里的线程都被占住了，新任务在队列里排队。

这种情况用 `thread -n` 看单个线程没用，要看**总量和分布**：线程总数（`dashboard` 里能看到）以及排队任务的堆积情况。

**线程池耗尽不是线程的问题，是下游变慢导致的连锁反应。** 修线程池参数只能缓解，根因还在下游。

### 三个最容易误判的地方

**一、RUNNABLE 不等于在算。** 等 IO 的线程也是 RUNNABLE。看到 RUNNABLE 就认定"CPU 是它烧的"，是最常见的错。
**二、CPU 高可能是 GC 线程，不是业务线程。** `thread -n 3` 里排在前面的线程名如果是 `GC`、`G1`、`C2 CompilerThread` 这类，问题就不在业务代码，去看内存和 GC。
**三、一次采样不能代表持续。** `thread` 是抓当下的快照，偶尔抓到一帧正常不等于没问题。**隔几分钟再抓一次**，两次都指向同一个方法，才值得下结论。

### 一张对照表

| 现象 | 先看什么 | 往哪走 |
|---|---|---|
| CPU 高 | `thread -n 3` | 业务线程 → 查代码；GC 线程 → 查内存 |
| 大面积卡顿 | `thread -b` | 找阻塞源，看锁的粒度 |
| 请求堆积 | 线程总数 + 线程名分布 | 下游变慢或池太小 |
| 偶发超时 | 隔几分钟抓两次栈 | 两次同点才算线索 |

`thread` 的价值不是"看到线程在干什么"，是**帮你排除掉两个错误方向**——排掉"不是在算"和"不是在等锁"，剩下的可能性就不多了。
