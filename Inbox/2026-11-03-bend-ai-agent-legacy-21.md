# B端产品经理实操：AI Agent落地旧系统对接的完整框架

> 旧系统对接是 Agent 落地的首要关卡（无标准接口/文档缺失/权限申请周期长）。本文给五步框架：系统盘点（九字段盘点表：API/认证/实时性/文档/负责人/变更频率/历史故障）、四类对接模式选型（API / 数据库只读+事件表 / RPA 界面自动化 / 中间件网关）、字段映射（数据字典/状态流转/异常码/幂等键）、灰度验证（先只读后写、白名单限流人工确认）、复盘总结。连锁零售案例：10 年旧 CRM，工单录入人力降 40%、录入 T+1→准实时、RPA 写回成功率 95%+。

## 核心要点

- 旧系统对接三大坑：技术方案反复改、灰度范围失控、上线后数据质量不达标；PM 不应把它当纯技术执行，而是主导的落地工程
- 系统盘点九字段：系统名称与业务域、数据库类型与版本、是否提供 API（REST/SOAP/WebService）、认证方式（Token/OAuth/账户密码）、数据实时性（实时/准实时/T+1）、文档完整度、负责人与审批路径、变更频率与发版窗口、历史故障与性能瓶颈
- 四类对接模式：API 对接（有标准接口优先，稳定可维护适合高频读写）；数据库只读+事件表（无 API 但可申请只读，事件表/时间戳捕获增量，只读降写坏风险）；RPA/UI 自动化（无 API 无库权限，模拟人工查看/输入/提交，适合低频规则固定写动作，不适合高频实时）；中间件/消息网关（多系统互调时建统一对接层，Agent 只对接网关）
- 选型五维度打分：实时性、安全、开发投入、稳定性、可维护性；案例：旧工单系统无 API 但库只读可开，采用"数据库只读+事件表+RPA 写回"混合模式
- 落地 SOP 五步：系统盘点→方案选型→字段映射（数据字典/状态流转/异常码/幂等键）→灰度验证（先只读后写、白名单/限流/人工确认开关、少量门店单据起步）→复盘总结（对照上线指标决定是否扩量）
- 案例：连锁零售用户支持部，10 年旧 CRM 无 API 只有客户端+只读库；Agent 自动识别意图/创建工单/分派门店/夜间批量回写
- 对接方案：数据读取用只读账户+事件表捕获增量；写回用 RPA 按固定规则模拟人工+失败重试+人工接管；安全边界 Agent 不直接写核心表，只写中间表由人工确认后同步
- PM 关键动作：提前 2 周申请数据库只读权限；与业务方制定工单状态流转与分派规则形成数据字典；灰度先 1 家门店跑 2 周（只读+待确认写回）稳定后扩 10 家；每日数据核对机制看字段准确率与漏单
- 效果：工单录入人力降 40%、录入及时性 T+1→准实时、RPA 写回成功率 95%+、失败单人工兜底
- 六个常见问题：文档缺失（找供应商补或从表结构/日志反推）、权限申请慢（提前发起先只读降审批压力）、数据质量差（Agent 入口加清洗层+脏数据拦截）、写动作风险（禁直接写核心库，中间表+人工确认）、跨系统一致性（幂等键+重试避免重复写单）、旧系统性能差（限制查询频率错峰执行批量）
- PM 三个核心动作：把业务目标翻译成系统能力要求；用风险预案替代技术理想主义（降级/人工接管/回滚方案）；用灰度数据说服业务方（不一上线全量）

## 正文

### 一、为什么旧系统对接是 Agent 落地的首要关卡？

AI Agent 要产生业务价值，必须连接到真实的业务数据与流程。B 端旧系统往往运行多年，技术栈老、接口能力参差不齐。产品经理如果不提前做系统盘点，很容易出现三种结果：技术方案反复改、灰度范围失控、上线后数据质量不达标。因此，旧系统对接不应被当成纯技术执行，而应作为产品经理主导的一项落地工程。

### 二、先做系统盘点：别急着写方案

产品经理要拉上业务、研发、运维，一起完成旧系统盘点。字段：
- 系统名称与业务域
- 数据库类型与版本
- 是否提供 API：REST/SOAP/WebService
- 认证方式：Token/OAuth/账户密码
- 数据实时性：实时/准实时/T+1
- 文档完整度：接口文档、数据字典、表结构说明
- 负责人与审批路径
- 变更频率与发版窗口
- 历史故障与性能瓶颈

产出物为《旧系统对接盘点表》，避免拍脑袋选方案。

### 三、四类对接模式与选型逻辑

1. API 对接：当旧系统具备标准接口时优先采用。优点是稳定、可维护，适合高频读写。
2. 数据库只读+事件表：当系统无 API，但能申请数据库只读权限时，可以读取业务数据，通过事件表或时间戳捕获增量。只读权限能降低写坏数据风险。
3. RPA/UI 自动化：当无 API、无数据库权限，只能通过界面交互时，用 RPA 模拟人工查看、输入、提交。适合低频、规则固定的写动作，不适合高频实时场景。
4. 中间件/消息网关：当多个系统互相调用时，建设统一对接层。Agent 只对接网关，由网关适配旧系统差异。

选型要综合实时性、安全、开发投入、稳定性、可维护性五个维度打分。例如某旧工单系统无 API 但数据库只读可开，方案采用"数据库只读+事件表+RPA 写回"的混合模式。

### 四、落地 SOP

- 步骤 1：系统盘点。输出系统清单、接口能力、限制条件
- 步骤 2：方案选型。标出每个系统走哪种对接模式，以及开发投入估算
- 步骤 3：字段映射。把 Agent 需要的字段、动作与旧系统能力对齐，明确数据字典、状态流转、异常码、幂等键
- 步骤 4：灰度验证。先跑只读任务，再开放写动作。设置白名单、限流、人工确认开关。灰度范围建议从少量门店/少量单据开始
- 步骤 5：复盘总结。对照上线前定的指标，输出效果数据和遗留问题清单，决定是否扩量

### 五、真实案例：某连锁零售旧 CRM + 智能工单 Agent

背景：某连锁零售企业的用户支持部门，每天要人工录入、分派、回访大量工单。旧 CRM 建设超过 10 年，没有标准 API，只有一套老旧的客户端和可只读访问的数据库。

目标：让 AI Agent 自动识别用户意图、创建工单、分派到对应门店，并在夜间批量回写 CRM。

对接方案：
- 数据读取：通过数据库只读账户读取会员、订单、门店信息，采用事件表捕获新增数据
- 写回动作：对必须在旧 CRM 界面执行的写回，用 RPA 按固定规则模拟人工录入，并设置失败重试与人工接管
- 安全边界：Agent 不直接写核心表，只写入中间表，由人工确认后同步

产品经理的关键动作：
1. 提前 2 周申请数据库只读权限，避免权限申请拖慢排期
2. 与业务方共同制定工单状态流转与分派规则，形成数据字典
3. 设置灰度：先选 1 家门店跑 2 周，只跑只读与待确认写回；稳定后扩到 10 家门店
4. 建立每日数据核对机制，重点查看字段准确率与漏单情况

效果：工单录入人力投入下降约 40%，录入及时性从 T+1 提升到准实时，RPA 写回成功率达到 95% 以上，剩余失败单由人工兜底处理。

### 六、常见问题与应对

1. 文档缺失：找供应商补文档，或通过数据库表结构、日志反推
2. 权限申请慢：提前发起，先做只读权限，降低审批压力
3. 数据质量差：在 Agent 入口加清洗层，设置脏数据拦截规则
4. 写动作风险：禁止 Agent 直接写核心库，使用中间表+人工确认
5. 跨系统一致性：使用幂等键和重试机制，避免重复写单
6. 旧系统性能差：限制 Agent 查询频率，错峰执行批量任务

### 七、产品经理在对接中的三个核心动作

1. 把业务目标翻译成系统能力要求。例如"降低工单录入人力"翻译为"Agent 需支持工单自动创建与分派"
2. 用风险预案替代技术理想主义。上线前准备好降级、人工接管、回滚方案
3. 用灰度数据说服业务方。不要一上线就全量，用少量门店数据证明稳定性和效果
