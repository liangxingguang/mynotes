# 大模型 Agent 混合路由详解：规则路由、模型路由、级联降级一篇讲透

> 摘要：Agent 一律走最强模型会同时烧掉 API 账单与延迟两份钱。文章对比规则路由、模型路由、混合路由三种思路，给出路由模型的数据来源、评分器优于分类器、保守冷启动、离线评估等工程建议，并指出级联降级只适合成本极度敏感、可容忍延迟的场景。

## 核心要点

- **一刀切大模型的代价**：约 80% 请求是闲聊/FAQ/翻译等简单任务，小模型与大模型质量几乎无差、价格差十倍，且延迟从几十毫秒拖到秒级。
- **三种路由思路**：规则路由零成本零延迟但会膨胀、识别不了"看着简单其实复杂"的请求；模型路由灵活但吃训练数据、会误判；工程上真正用的是**混合路由**三层结构。
- **混合路由三层**：高频简单场景规则兜底 → 模糊地带路由模型打分 → 拿不准的一律大模型兜底，精髓是"每层只处理自己有把握的，没把握的往下传"。
- **路由器训练**：数据可来自日志置信度、人工采样或主动探索（5% 请求大小模型对比）；**评分器（0~1 难度分）优于分类器**——加模型只调阈值、不用重训。
- **冷启动铁律**：初期全走大模型、记录置信度攒数据，先只放行置信度极高（>0.95）的请求给小模型，渐进降阈值；宁可多花钱，质量是底线。
- **离线评估**：上线前盯"复杂请求错分给小模型的比例"，低于质量红线才灰度，别拿线上用户当测试集。
- **级联降级的账**：70% 简单场景下比一刀切省一半，但比理想路由多花 25%（复杂请求被小模型白试一次）；且延迟翻倍、置信度阈值难拿捏、存在"看着对藏着错"的漏检风险。适合成本极其敏感、能容忍延迟的场景。
- **工程建议**：先做请求分布分析；从"规则加兜底"起步；阈值是活的、随评估数据持续调；记录每次路由决策形成评估闭环；算总账而非只算模型调用那一栏。
