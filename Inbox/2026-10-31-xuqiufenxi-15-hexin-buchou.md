# 需求分析的核心步骤（一套可重复使用的实战流程）

> 摘要：《需求分析》专辑第 15 篇。把上一篇的拆模块放进完整流程，给一套可直接使用的核心步骤：澄清目标 → 识别用户与场景 → 拆出"用户要完成的事"并归模块 → 界定范围 → 补充关键规则与异常 → 确定优先级 → 写出验收标准 → 对齐确认形成基线。每步都给"输出"。

## 核心要点

- **承接 + 定位**：上一篇讲了如何把模糊需求拆成清晰的功能模块。**拆模块很重要，但如果缺少前后环节，仍然容易变成"拆完了却对不齐"或"拆完了范围又失控"。**
- **第一步：澄清目标与成功标准**——先回答三个问题并写下来：这次要解决什么问题？做成后最希望看到什么变化？怎样算基本成功（尽量用可观察的结果描述）？**目标不清，后面所有拆分和优先级都会失去判断依据。这一步看起来简单，却是最容易被跳过的。** 输出：一句话目标 + 1～3 条成功标准。
- **第二步：识别用户与关键场景**——明确主要用户是谁，列出 2～4 个最核心的使用场景；每个场景用"谁、什么时候、什么情况下、想完成什么"来描述。**场景是连接业务语言和功能模块的桥梁。没有场景，功能很容易变成孤立的点。** 输出：用户列表 + 核心场景列表。
- **第三步：从场景中拆出用户要完成的事，并归成功能模块**（即上一篇的方法）——从每个场景抽出用户实际要做的事情；把相关事情归类形成功能模块；给每个模块用一句话说明它解决什么问题。输出：功能模块列表（每个模块有简短说明）。
- **第四步：界定范围——明确做与不做**——对照目标对每个模块做判断：必须做（没有它核心目标达不成）／应该做（重要但可稍后）／可以不做（本期明确排除）。**把"本次不做"写清楚并与相关方确认，这是防止范围蔓延最有效的动作。** 输出：本期范围清单 + 明确的"不做"清单。
- **第五步：补充关键规则与异常**——对进入本期的模块，把关键业务规则写清楚：正常路径怎么走／关键判断条件是什么／主要异常和边界情况如何处理。**规则不需要一次写到终极细节，但必须写到开发和业务不会产生明显分歧的程度。** 这步是和研发语言对齐的关键点，也是产品经理把业务语言转化研发实现语言最关键的一步。输出：各模块的关键规则说明。
- **第六步：确定优先级**——在本期范围内对准目标再排优先级，常用四个维度一起看：业务价值（对目标贡献大不大）／紧急程度与风险（不做会不会立刻出问题）／依赖关系与实现成本（是不是其他功能的基础、代价高不高）／投入资源的满足度（人力投入超出预算，质量降低、问题多）。排出 P0、P1、P2 并记录排序依据。输出：带优先级的功能列表。
- **第七步：写出可验证的验收标准**——为 P0 和关键 P1 功能补充验收标准，用"在什么前提下、执行什么操作、期望看到什么结果"的方式写，尽量可客观检查。这步也是业务语言转化研发测试语言，转化不好，测试后期问题多。输出：关键功能的验收标准。
- **第八步：对齐确认，形成基线**——把以上内容整理成简短文档或纪要，与业务、开发、测试快速过一遍，确认理解一致后作为当前基线；后续变更基于基线评估影响，而不是推倒重来。**基线形成后整个团队目标就对齐了，团队能够形成一股绳。对自己也是一种很好的保护——碰到项目后期延期、需求失控等问题时大家开始翻旧账，有基线纪要可以明确责任。** 输出：经确认的需求基线。
- **使用时的几点提醒**：小需求可以合并步骤，但"目标 → 场景 → 模块 → 范围 → 规则 → 优先级 → 验收"这个逻辑顺序建议保留；**最容易出问题的地方通常是：目标没钉死就急着拆功能；范围只写"做"不写"不做"；规则和验收标准写得太模糊。** **流程的目的不是增加形式，而是减少返工和误解。每一步都在为后面的执行降低风险。为了流程而流程就是本末倒置，不可取。** 下篇预告：如何界定需求范围，避免无限蔓延——范围守不住，前面的努力很容易白费。

## 正文

> 采集说明：正文可读，全文约 1875 字，八步流程（每步含要点与"输出"）+ 使用提醒 + 收尾。无表格、无代码块，配图已略去。以下为忠实全文。

上一篇我们讲了如何把模糊需求拆成清晰的功能模块。拆模块很重要，但如果缺少前后环节，仍然容易变成"拆完了却对不齐"或"拆完了范围又失控"。下面是一套可以直接使用的核心步骤：

**第一步：澄清目标与成功标准。** 先回答三个问题并写下来：

- 这次要解决什么问题？
- 做成后，最希望看到什么变化？
- 怎样算基本成功？（尽量用可观察的结果描述）

**目标不清，后面所有拆分和优先级都会失去判断依据。这一步看起来简单，却是最容易被跳过的。**

输出：一句话目标 + 1～3 条成功标准。

**第二步：识别用户与关键场景。**

- 明确主要用户是谁，并列出 2～4 个最核心的使用场景。
- 每个场景用"谁、什么时候、什么情况下、想完成什么"来描述。

**场景是连接业务语言和功能模块的桥梁。没有场景，功能很容易变成孤立的点。**

输出：用户列表 + 核心场景列表。

**第三步：从场景中拆出用户要完成的事，并归成功能模块。** 这就是上一篇的方法：

- 从每个场景抽出用户实际要做的事情
- 把相关事情归类，形成功能模块
- 给每个模块用一句话说明它解决什么问题

输出：功能模块列表（每个模块有简短说明）。

**第四步：界定范围——明确做与不做。** 对照目标，对每个模块做判断：

- **必须做**（没有它核心目标达不成）
- **应该做**（重要但可稍后）
- **可以不做**（本期明确排除）

**把"本次不做"写清楚，并与相关方确认。这是防止范围蔓延最有效的动作。**

输出：本期范围清单 + 明确的"不做"清单。

**第五步：补充关键规则与异常。** 对进入本期的模块，把关键业务规则写清楚：

- 正常路径怎么走
- 关键判断条件是什么
- 主要异常和边界情况如何处理

**规则不需要一次写到终极细节，但必须写到开发和业务不会产生明显分歧的程度。这步很关键**——前面有篇"需求分析从业务到研发，中间到底缺了什么"提到语言同频的问题，这里是和研发语言对齐的关键点，这步输出清楚了，研发的问题能够减少很多。**也是产品经理把业务语言转化研发实现语言最关键的一步。**

输出：各模块的关键规则说明。

**第六步：确定优先级。** 在本期范围内，对准目标，再排优先级。常用四个维度一起看：

- 业务价值（对目标贡献大不大）
- 紧急程度与风险（不做会不会立刻出问题）
- 依赖关系与实现成本（是不是其他功能的基础，代价高不高）
- 投入资源的满足度（人力投入超出预算，质量降低，问题多）

**排出 P0、P1、P2，并记录排序依据。**

输出：带优先级的功能列表。

**第七步：写出可验证的验收标准。** 为 P0 和关键 P1 功能补充验收标准。

用"在什么前提下、执行什么操作、期望看到什么结果"的方式写，尽量可客观检查。**这步也是业务语言转化研发测试的语言，转化不好，测试后期问题多。**

输出：关键功能的验收标准。

**第八步：对齐确认，形成基线。**

把以上内容整理成简短文档或纪要，与业务、开发、测试快速过一遍，确认理解一致后，作为当前基线。**后续变更基于基线评估影响，而不是推倒重来。**

基线形成后整个团队目标就对齐了，团队能够形成一股绳。对自己也是一种很好的保护——我碰到的项目到后面延期、需求失控等问题时，大家开始翻旧账，**有基线纪要可以明确责任。**

输出：经确认的需求基线。

**最后，使用时的几点提醒：**

- 小需求可以合并步骤，但"目标 → 场景 → 模块 → 范围 → 规则 → 优先级 → 验收"这个逻辑顺序建议保留。
- **最容易出问题的地方通常是：目标没钉死就急着拆功能；范围只写"做"不写"不做"；规则和验收标准写得太模糊。**

**流程的目的不是增加形式，而是减少返工和误解。每一步都在为后面的执行降低风险。为了流程而流程就是本末倒置，不可取。**
