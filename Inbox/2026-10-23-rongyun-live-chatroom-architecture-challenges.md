# 融云：直播间海量聊天消息的架构设计难点实践

> 融云直播聊天室高可用架构全景：连接层/存储层（Redis 二级缓存）/业务层三层，业务层分聊天室服务（管理类请求：进出/禁言/上行审核，按聊天室 ID 一致性哈希落点）与消息服务（用户信息与消息队列缓存 + 分发，按用户 ID 落点），Zk 服务发现，跨机房容灾。百万在线拆 200 台消息服务各管 5000 人。扩缩容靠 Redis 加载状态 + 渐进式人员转移（扩容按活跃度逐步迁、消息遍历时纠偏落点、拉取时向聊天室服务确认）。用户离线判定：30s 不拉或累计 30 条未拉即踢出。消息优先级三桶（白名单 > 高 > 低）按序拉取。客户端侧：通知拉取 + 首拉取 50 条 + 退出清库；Android 渲染靠 MVVM 子线程预处理、LiveData setValue/postValue 区分、滑动不刷新、DiffUtil 局部更新——中端机 400 条/秒不卡。自定义属性（麦位/角色等必达状态）全量 + 有序 map 变更记录双存储，同样走通知拉取增量回放。

## 核心要点

- **职责分离**：聊天室服务管"人"（进出/封禁/审核），消息服务管"分发"，百万房间 200 台消息服务各管 5000 人
- **一致性哈希落点**：聊天室按房间 ID、用户按用户 ID，行为汇聚单节点提高缓存命中率，内存直读不碰第三方缓存
- **平滑扩缩容**：Redis 备份状态；扩容渐进迁移 + 分发/拉取路径上自动纠偏；销毁前校验归属防误删 Redis 数据
- **离线判定**：30s 未拉取或累计 30 条未拉 → 踢出并同步下线，白名单豁免
- **优先级三桶**：白名单/高/低分别存储，限速时低优先级先丢，客户端按序拉取
- **客户端优化**：首拉传 0 取最近 50 条、差量拉取、排重上抛、退出清库；渲染五招（MVVM/主线程减负/滑动不刷/DiffUtil/局部刷新）支撑 400 条/秒
- **自定义属性**：全量集合 + 时间戳有序 map 变更记录，通知拉取增量回放，满足麦位/角色等必达状态同步
