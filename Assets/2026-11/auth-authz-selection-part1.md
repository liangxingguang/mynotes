## 一、引言

小 A 经历过两次印象深刻的选型翻车。

第一次，是个内部后台，只有十来个用户。技术负责人是个"架构控"，非要上 Keycloak 做 SSO。结果两个开发花了三周才把 Keycloak 部署起来、Realm 配好、业务系统对接上，运维还得额外维护一个 Keycloak 集群。上线后，用户就十几个，Keycloak 占用的服务器资源比业务系统还大。这是典型的**过度设计**。

第二次，是个对外开放的 SaaS 平台。当时图快，用 Sa-Token 一周搞定了登录。半年后要对接企业客户的 AD 域、要给合作伙伴开放 API、要做多租户 SSO——Sa-Token 的私有协议到处碰壁，最后不得不推倒重来，迁移成本远超当初省下的开发时间。这是典型的**选型过浅**。

这两次翻车让小 A 想明白一件事：**选型没有"最好"，只有"最合适"**。而"最合适"的判断，不能靠拍脑袋，要靠一套清晰的维度和方法论。

本文不给"选 A 还是选 B"的标准答案——因为那不存在。它要的是一套**选型决策框架**：从认证与授权的本质区别讲起，建立选型维度模型，逐一拆解候选方案，给出成本模型、迁移路径、源码分析、单元测试、避坑清单。掌握这套方法论，就能在自己的场景里做出不后悔的决策。

## 二、概念定义

### 2.1 认证 vs 授权

| 维度 | 认证（Authentication） | 授权（Authorization） |
| --- | --- | --- |
| 解决问题 | 你是谁（Who are you） | 你能做什么（What can you do） |
| 典型问题 | 登录、身份验证 | 权限校验、资源访问控制 |
| 常见手段 | 账号密码、SSO、OIDC | RBAC、ABAC、ACL |
| 简称 | AuthN | AuthZ |

**打个比方**：认证是门口保安查你身份证（你是谁），授权是进了门之后你能进哪些房间（你能做什么）。

**为什么选型要先分清这俩**：有些方案只做认证不做授权（如纯 OIDC），有些两者都做（如 Keycloak）。如果核心痛点是"细粒度权限管理"，选了只做认证的方案，还得再造一套授权系统。

### 2.2 会话、Token、凭证的关系

| 概念 | 说明 | 例子 |
| --- | --- | --- |
| 凭证（Credential） | 证明身份的原始材料 | 账号密码、证书、生物特征 |
| Token | 认证后颁发的访问凭证 | JSESSIONID、JWT、access_token |
| 会话（Session） | 服务端维护的登录状态 | Servlet Session、Redis Session |

**关系**：用户用凭证（密码）认证 → 认证通过颁发 Token → 服务端建立会话记录登录态。后续请求带 Token，服务端凭 Token 找会话。

**有状态 vs 无状态**：

| 模式 | 会话存哪 | Token 含义 | 主动踢人 |
| --- | --- | --- | --- |
| 有状态 | 服务端（Redis） | 不透明随机串，凭它查会话 | 删会话即踢 |
| 无状态 | 不存 | 自包含 JWT，含全部信息 | 需黑名单 |

选型时这是核心权衡——有状态易踢人但依赖存储，无状态性能好但难吊销。

### 2.3 什么是技术选型

技术选型是在多个候选技术方案中，基于业务需求、团队能力、成本约束等维度，选择最合适方案的系统化决策过程。

选型就像选车——不是越贵越好，也不是越省油越好。要拉货选皮卡，要省油选混动，要面子选豪华。关键是搞清楚"你要拉什么、走什么路、预算多少"。

### 2.4 选型决策框架

| 维度 | 关键问题 |
| --- | --- |
| 团队规模与能力 | 团队能驾驭多复杂的方案？ |
| 系统数量与关系 | 是单系统、多系统还是要对外？ |
| 对外需求 | 要不要对接第三方、开放 API？ |
| 合规要求 | 有没有等保、审计、身份联邦要求？ |
| 运维能力 | 能不能维护额外的中间件/服务？ |

### 2.5 认证授权的分层架构

成熟的认证授权体系是分层的，选型时要在每层分别决策：

| 层 | 职责 | 候选方案 |
| --- | --- | --- |
| 身份源（L1） | 存用户、密码、组织 | DB、LDAP、AD |
| 认证（L2） | 验证身份 | 自研、Sa-Token、Keycloak |
| 令牌（L3） | 签发/校验 token | OAuth2/OIDC、JWT、自研 |
| 授权（L4） | 权限判断 | RBAC/ABAC（见权限模型篇） |
| 审计（L5） | 记录留痕 | 日志系统、SIEM |

**关键认知**：Keycloak 覆盖 L1-L3 + L5，但不深入 L4（业务细粒度权限）。Sa-Token 覆盖 L2-L4，但 L1/L5 要自己补。选型要明确"我要买哪几层"。

## 三、阐述背景：选错方案的代价

### 3.1 过度设计的代价

| 代价 | 表现 |
| --- | --- |
| 开发成本 | 简单需求上了重方案，开发周期翻倍 |
| 运维成本 | 多维护一套服务（如 Keycloak 集群） |
| 学习成本 | 团队要学不熟悉的协议和组件 |
| 复杂度 | 简单场景被复杂方案拖累，排障困难 |

### 3.2 选型过浅的代价

| 代价 | 表现 |
| --- | --- |
| 返工 | 需求演进后原方案扛不住，推倒重来 |
| 扩展性不足 | 私有协议无法对接外部系统 |
| 安全风险 | 简方案缺少必要的安全能力（审计、风控） |
| 技术债 | 临时方案变成永久包袱 |

### 3.3 选型的本质权衡

选型本质上是在两个极端之间找平衡：

```
过度简单（扛不住演进） ←——平衡点——→ 过度复杂（杀鸡用牛刀）
```

**关键认知**：没有"永远正确"的选型，只有"当前阶段最合适"的选型。好的选型不仅看当下需求，还要看演进路径——选的方案能不能随着需求增长平滑升级。

### 3.4 选型的三个时间尺度

| 时间尺度 | 关注点 | 例子 |
| --- | --- | --- |
| 短期（0-3 月） | 快速上线 | 开发成本 |
| 中期（3 月-2 年） | 需求演进 | 扩展性、迁移成本 |
| 长期（2 年+） | 架构稳定 | 标准化、生态、合规 |

**小团队易犯的错**：只看短期，选最快方案，中期返工。**大团队易犯的错**：只看长期，上重型方案，短期开发成本爆炸。好的选型要兼顾三个尺度——选当下够用、中期可演进、长期不堵死的方案。

## 四、类比：选门禁系统

把认证授权选型类比成给大楼选门禁：

| 门禁方案 | 对应技术方案 | 适用场景 |
| --- | --- | --- |
| 机械锁 + 钥匙 | 裸 Servlet Session / 自研最简版 | 单门小屋（单系统、用户少） |
| IC 卡门禁 | Sa-Token / 自研 Redis Session | 普通写字楼（单/少系统、内部用户） |
| 刷卡 + 后台管理 | Spring Security + 数据库权限 | 中型写字楼（需精细权限控制） |
| 人脸闸机 + 访客系统 | Keycloak / Spring Authorization Server | 大型园区（多楼、访客、对外） |
| 联邦身份（一卡通通用） | OIDC/SAML federation | 跨园区联盟 |

选门禁的逻辑和选认证方案完全一致：

- 一个小仓库，挂把机械锁就行，上人脸闸机是浪费
- 一个大型园区，光靠机械锁管不过来，必须上集中式门禁
- 园区之间要互通，就必须用统一的协议（一卡通）
- 门禁系统本身也要维护——越复杂的门禁，运维成本越高

## 五、正反例子

### 5.1 反例：单后台硬上 Keycloak

小 A 经历的第一次翻车：十几个用户的内部后台，硬上 Keycloak：

- 部署：要起 Keycloak 服务 + 数据库
- 配置：Realm、Client、用户、角色，一套搞下来三天
- 对接：业务系统要集成 OIDC Client
- 运维：Keycloak 要监控、备份、升级

**问题**：Keycloak 的价值在"多系统 SSO + 标准协议 + 用户联邦"，单系统、无对外、无 SSO 需求时，它的能力 90% 用不上，纯粹是负担。这就是"用大炮打蚊子"。

### 5.2 反例：对外平台用私有协议

小 A 经历的第二次翻车——Sa-Token 做对外 SaaS。半年后要对接企业客户的 AD 域、开放 API 给合作伙伴，发现：

- Sa-Token 的私有 token 格式，合作伙伴的网关不认
- 对接 AD 域要自己写 LDAP 同步
- 多租户 SSO 要自己造

**问题**：对外场景的硬通货是**标准协议**（OIDC/SAML），私有协议在这些场景处处碰壁。对内可以私有，对外必须标准。

### 5.3 反例：业务代码直接耦合框架

```java
// 反例：业务代码直接依赖 Sa-Token
@GetMapping("/order")
public Order getOrder(Long id) {
    if (!StpUtil.hasPermission("order:view")) {
        // 框架 API 散落业务代码
        throw new ForbiddenException();
    }
    return orderService.get(id);
}
```

问题：迁移到 Spring Security 时，所有 `StpUtil.hasPermission` 调用都要改遍。正确做法是抽象 `AuthService` 接口，**业务依赖接口，框架实现接口，迁移只改实现**。

### 5.4 正例：按规模渐进式选型 + 抽象隔离

正确的做法是**按阶段选型 + 抽象隔离**：每个阶段选当下最合适的方案，并预留向下一阶段演进的路径。业务代码通过 `AuthService` 接口隔离框架，**迁移时只改实现不改业务**。这才是成熟的选型思路。

## 六、选型维度模型

### 6.1 五维度详解

**维度一：团队规模与能力**

| 团队情况 | 适配方案 |
| --- | --- |
| 1-3 人小团队，要快 | Sa-Token / 自研最简版 |
| 中型团队，有运维 | Spring Security + 中间件 |
| 大团队，有专职运维/安全 | Keycloak / 自建 AS |

**关键**：选型不能只看方案能力，要看团队能不能驾驭。Keycloak 再强，没人会维护也是灾难。

**维度二：系统数量与关系**

| 系统情况 | 适配方案 |
| --- | --- |
| 单系统 | 自研 Session / Sa-Token |
| 少量内部系统（2-5 个） | Sa-Token SSO / Spring Security + 自建 AS |
| 大量系统 / 需统一身份 | Keycloak |
| 对外开放 API | 标准 OIDC（Keycloak / Spring Authorization Server） |

**维度三：对外需求**

| 对外情况 | 关键约束 |
| --- | --- |
| 纯内部 | 可用私有协议 |
| 对接第三方登录（微信/GitHub） | 需 OAuth2 Client 能力 |
| 开放 API 给合作伙伴 | 必须标准 OIDC/OAuth2 |
| 对接企业客户 AD/LDAP | 需用户联邦能力（Keycloak） |

**维度四：合规要求**

| 合规要求 | 影响 |
| --- | --- |
| 等保/审计 | 需集中审计日志（IdP 统一记录） |
| 身份联邦 | 需标准协议（SAML/OIDC） |
| 数据主权 | 自建 vs SaaS 的取舍 |
| 多租户合规 | 租户隔离 + 数据不出境 |

**维度五：运维能力**

| 运维能力 | 约束 |
| --- | --- |
| 无专职运维 | 避免独立服务（Keycloak），用嵌入式（Sa-Token） |
| 有中间件运维 | 可上 Redis、可自建 AS |
| 有完整 DevOps | 可上 Keycloak 集群 |

### 6.2 维度交叉的典型组合

| 团队 | 系统 | 对外 | 推荐方案 |
| --- | --- | --- | --- |
| 小 | 单 | 否 | Sa-Token / 自研 |
| 小 | 多 | 否 | Sa-Token SSO |
| 中 | 多 | 否 | Spring Security + 自建 AS |
| 中 | 多 | 是 | Keycloak |
| 大 | 多 | 是 | Keycloak + 多 Realm |

### 6.3 维度评分矩阵

给每个方案在五维度上打分（1-5，5 最优），量化对比：

| 方案 | 团队要求低 | 系统少 | 对外能力 | 合规支持 | 运维简单 | 总分 |
| --- | --- | --- | --- | --- | --- | --- |
| 自研 Redis | 3 | 5 | 1 | 1 | 3 | 13 |
| Sa-Token | 5 | 5 | 2 | 2 | 4 | 18 |
| Spring Security+AS | 2 | 3 | 4 | 4 | 2 | 15 |
| Keycloak | 1 | 2 | 5 | 5 | 1 | 14 |
| JWT | 4 | 4 | 4 | 3 | 5 | 20 |

**注意**：总分不是绝对优劣——JWT 总分最高但无法主动踢人，Keycloak 总分低但企业场景不可替代。评分只是辅助，最终要看场景匹配。

| JWT | 无状态 | 标准 | ✅ | ⚠️ | 无 | 微服务无状态 |

### 7.7 授权层的统一选择

无论认证层选哪个，**授权层（业务权限）通常统一用 RBAC/ABAC**：

| 授权需求 | 方案 |
| --- | --- |
| 角色/权限点 | RBAC |
| 数据级权限 | ABAC + 注解 + 拦截器 |
| 多租户隔离 | tenant_id + 拦截器 |
| 复杂合规 | PBAC 策略引擎 |

**关键认知**：Keycloak/Sa-Token 做认证和粗粒度 scope 授权，业务细粒度权限（按钮、数据）由业务系统用 RBAC/ABAC 实现。认证和授权分层，不要指望一个框架全包。
