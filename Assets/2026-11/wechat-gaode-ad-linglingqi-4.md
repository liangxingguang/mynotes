AI Coding 的普及，正在降低编码门槛，也让我们重新思考研发工作的组织方式。真实业务的交付，需要理解业务问题、形成明确需求，协调多个角色与系统完成实现，并验证结果是否符合预期。我们的 AI Native 探索围绕这些工作展开：让 Agent 承担更完整的任务，让人的经验、判断与实践反馈成为团队能够持续复用和改进的共同能力。

本系列分享高德搜索、推荐、广告技术团队围绕 Agent Teams 开展的工程实践。凌凌漆通过问题排查、主动走查和数据分析形成需求洞察，并持续跟进；星舰 10X 围绕研发目标组织多 Agent 协作，推进跨仓实现与交付核验；轻舟面向产品与前端场景，让更多角色参与产品构建。业务知识、工具接入、评测和云真机等能力，为这些工作提供共同支撑。

我们希望逐步贯通问题发现、需求形成、工程实现和结果验证，让人集中精力判断业务价值与关键取舍，让 Agent 持续推进执行与协同，使个人提效转化为团队可持续的业务交付能力。

本篇导读

一次代码修改，17 项定向及相邻测试全部通过，约定模块构建成功，却仍然不能宣布需求已经完成。原因是普通测试编译仍被存量基线问题阻断，代码评审、发布和线上验证也尚未发生。这正是 AI 进入真实工程现场后必须面对的问题：**让 AI 写出代码并不够，如何让它持续工作、理解复杂工程，并用真实证据证明结果，才是更大的挑战。**

围绕这一问题，我们逐步建设了一套面向高德广告工程的 AI 原生生产系统：广告凌凌漆。在截至 2026 年 9 月 18 日的一次阶段性快照中，广告数字员工任务台账记录 362 条任务，其中 349 条状态为已办结，状态办结率为 96.4%。这里的“办结”仅表示任务在台账中已完成或关闭，不等同于答案正确率、研发交付率或业务结果达成率。其中，研发辅助与需求准入、用户问题排查、运维与报警分析三类任务合计 274 条，占总任务量的 75.7%。

这些数据说明，AI 已经开始进入真实团队工作流。但任务办结不等于研发交付，更不等于线上效果得到验证。我们真正要解决的是三个问题：数字员工怎样持续工作？AI 怎样理解大型工程？我们凭什么相信它交付的结果？

一、从工具接入到任务交付  

广告工程的问题往往横跨多个系统。一次实验没有生效，可能涉及实验参数、配置下发、引擎读取和线上日志；一次看似局部的兼容性修改，也可能影响跨仓调用和旧版本配置语义。

大模型可以调用更多工具，却不会因此自动理解业务。真正困难的是选对信息、组织排查路径、执行必要操作，并判断结果是否可信。

目前，广告数字员工已接入 22 项专业能力入口，可以归纳为六类：

正式知识、历史经验、文档与任务协作

工具（Tool）提供能力接口，技能（Skill）封装可复用的稳定方法，智能体（Agent）围绕专业任务组织上下文、方法和工具。评价标准不是接入数量，而是任务能否得到可信结果。客资、计费、赔付和反作弊等能力当前以查询、分析和结论草稿为主；涉及回帖、配置或数据写入、赔付等高风险动作时，必须由责任人确认或沿用原系统审批链路，数字员工不会因为能够调用工具而自动获得业务授权。

在另一批历史问题分析中，团队曾提炼 8 类共性问题并沉淀 16 项标准答复，作为领域能力建设的样本。该批数据与前述任务快照口径不同，不参与办结率计算。

问题处理不应止于生成 FAQ。排查发现的缺陷可以进入需求准入、研发、测试和上线，最终再将验证过的经验回流到知识、规则、测试或技能中。目前，研发准入、需求拆解、开发、代码差异分析和压测报告分析等关键环节已经形成链路，从一线反馈到线上结果的完整闭环仍在建设。

二、整体架构：数字员工与专业研发各司其职  

表面上，用户通过钉钉与数字员工小七交互；背后则是数字员工运行时、研发任务控制、代码执行环境、工程上下文和可信验收共同组成的系统。

整套系统可以分成四个部分：

•**交互协作：** 小七理解请求、补充信息、组织专业能力并反馈结果。

•**任务控制：** 主智能体（Main Agent）管理被委托研发任务的身份、状态、代码版本、执行环境和交付记录。

•**研发执行：** 智能体执行框架（Coding Harness）与研发环境完成代码搜索、修改、测试和失败后的继续修复。

•**工程上下文与验收：** 代码图谱（CodeGraph）、正式知识（Knowledge）、历史记忆（Memory）、执行证据（Evidence）和评估器（Evaluator）共同支撑任务执行与结果判断。

Main Agent 更像项目经理维护的任务台账：即使执行工具或计算实例发生变化，任务本身仍应有明确的身份和进度。但它不是所有数字员工任务的必经之路。

这样，普通任务不必承担完整研发环境的开销，复杂研发也不会停留在缺少版本和验收记录的普通对话中。

三、从 Codex Harness 到 Personal Dev：让 AI 持续执行  

复杂代码开发不是一次提示词调用，而是反复搜索仓库、阅读源码、修改文件、执行命令、分析失败和继续修复的过程。模型负责判断下一步做什么，智能体执行框架负责将判断持续转化为真实动作。

### 3.1 可替换的 Codex Harness：执行引擎负责怎么做，平台负责能不能做

前期，我们通过 OpenCode 建立多模型研发执行能力；随着实践深入，Codex Harness 在 Personal Dev 的部分正式研发路径中逐步成为默认执行引擎。这不是一次“全面迁移”：部分预发与存量路径仍可能使用原有执行方式。真正的技术选择，是把 Harness 收敛为可替换的执行适配层，而不是把任务体系锁定在某个产品中。

Harness 负责代码搜索与阅读、文件修改、命令执行、上下文压缩和基于真实结果的多轮修复；平台负责任务身份、仓库与版本、权限、环境、研发契约和验收证据。

这条边界的核心是：自主执行不等于自主授权。Harness 可以自主选择实现路径，但不能自行扩大仓库范围、写入权限或完成标准。

平台不必重复建设底层工具循环，但仍然必须控制仓库范围、写入权限、环境绑定和验收条件。

在 Personal Dev 的部分正式研发路径中，Codex Harness 正逐步成为默认、但仍可替换的执行引擎。任务事实、广告知识、工程上下文和验收机制不应被锁定在某个 Harness 中。

### 3.2 Personal Dev：机器可以替换，研发现场不能丢

复杂研发还需要稳定的工作环境。

工程师本机依赖个人在线状态和本地配置；一次性沙箱虽然隔离性较好，但计算实例结束后，工作现场可能随之丢失。因此，我们建设个人研发环境（Personal Dev），让逻辑研发环境尽量独立于具体计算实例。

当前环境骨架包括稳定环境标识、持久卷、计算与存储分离、环境代际管理、任务路由恢复及执行日志。

其中最关键的不是把文件保存下来，而是避免两个实例同时拥有正式写入权。

多读、多分析、受控写入。对同一正式研发任务的主工作区，同一时刻只允许一个受控主执行者持有写入权；其他 Agent 仍可在隔离分支、`worktree` 或明确文件范围内并行分析与评审。因此，单 Writer 不是整个仓库或整个团队全局串行。

环境代际（Generation / Epoch）用于标识新旧执行实例，但代际标识本身不是锁。安全接管仍依赖 `lease`、`fencing` 和旧执行器停止；只有正式写入路径验证当前写入权并拒绝失效执行器，才能形成有效隔离。

目前，持久化、环境绑定、受控换代和基础恢复已形成主体骨架；但现有公开证据还不足以证明“新实例接管后，所有旧实例写入均已被稳定拒绝”。计划外故障、活跃任务中途切换、写入过程中换代，以及多人规模下的资源竞争仍需继续验证。

四、让 AI 理解工程、记住经验  

### 4.1 CodeGraph：从搜索代码到分析变更影响

在大型广告工程中，找到一段代码并不难，难的是判断修改会影响哪些功能、配置和上下游系统。

传统代码搜索擅长查找关键词、定义和引用，但面对跨仓调用、配置驱动和复杂依赖，仅仅找到代码片段还不够。

代码图谱（CodeGraph）将符号定义、引用、调用关系、依赖和配置关联组织成结构化索引，让 Agent 先收敛影响范围，再回到绑定 Revision 的真实源码和配置核实。它是影响分析的导航，不是代码事实本身。

可以把它理解为大型工程的“管线图”：先看图找到相关线路，再到现场确认实际走向。

图谱越完整，版本不匹配造成的误导反而越危险。因此，图谱制品必须同时关联仓库标识（`repo_id`）、代码提交版本（`commit_sha`）和规范化制品摘要（`artifact_digest`）；使用时也要返回相应的版本和来源证据。

在 2026 年 11 月 2 日的一次核验中，14 个广告核心仓库的本地、预发和生产环境完成了 14/14 的仓库版本、图谱制品及工具链身份一致性检查。该结论只适用于这次快照，证明三套环境中的身份元组一致；它不证明图谱中的每一条关系都正确，也不代表后续版本会自动保持同步。

如果图谱缺失、过期或与目标代码版本不一致，Agent 就应回到源码和其他权威信息重新核实，而不能把旧图谱当成当前事实。

在后文的混合版本配置兼容任务中，CodeGraph 用于把搜索范围收敛到目标配置处理函数、相邻调用和潜在兼容影响；哪些路径真正受影响，仍由对应 Revision 的源码、配置和测试结果确认。

目前，我们已经具备核心仓库的图谱能力和制品一致性核验基础。下一步要用真实任务对照数据验证它是否真正降低定位耗时、影响面遗漏和返工，而不能用 14/14 的制品身份一致替代研发收益。

### 4.2 Knowledge + Mem0：区分当前事实、目标规则与历史经验

代码图谱帮助 Agent 理解当前代码，但很多工程经验并不写在代码里。例如，某项配置为什么不能随意修改，某次故障为什么采用特殊处理，以及某条排查路径过去为什么没有效果。

正式知识（Knowledge）保存团队认可的架构、业务规则和标准操作流程；历史记忆（Memory）保存过去任务的排查路径、无效尝试、故障根因及后续纠正结果。

在记忆基础设施上，我们复用 Mem0 的记忆抽取、去重、元数据管理和检索能力，把重点放在记忆治理：记录经验的来源、适用范围、对应版本，以及它后来是否被采用、拒绝或纠正。

小七与 Dev Loop 可以共享受控的广告历史记忆服务，避免不同执行链路各自维护互不相通的长期记忆。

这里不能用一条固定的“可信优先级”同时回答两个不同问题：

1**确认当前行为：** 以绑定目标版本和时间窗口的源码、配置、权威系统记录、日志和运行数据为依据。

2**判断目标行为：** 以经责任人确认的业务规则、研发契约和验收标准为依据，不能用错误实现反向定义正确预期。

3**缩小排查范围：** 历史记忆提供过去任务的路径、失败尝试和纠正结果，但必须在当前任务中重新核实。

4**形成待验证判断：** 模型推断只能作为假设，不能直接升级为事实或规则。

当信息冲突时，应先区分是在讨论“系统现在怎样运行”，还是“系统应该怎样运行”；历史经验和模型推断都不能覆盖本次任务的一手证据与正式规则。

Memory 已经进入真实任务，但资产规模不能直接代表价值。更合理的评价分三层：是否能够检索到，执行时是否被真实采用，以及采用后是否降低耗时、返工或提升结果质量。前两层已有阶段性过程数据，第三层仍需要固定任务集和对照验证。

“硬采用”仅表示记忆实际进入后续命令、检索、分析或最终产出，而不是模型仅读取过它；它属于过程指标，不能证明该记忆正确，也不能直接证明产生了效率或业务收益。

现阶段尚缺能够同时绑定原任务、复用动作和新任务验收结果的可公开样本，因此本文不再以 Memory 总量或来源完整率证明效果。后续应根据新任务的验收结果，决定经验是否升级为正式知识、规则、自动化测试、技能，或保留为带适用条件的历史记忆。

五、Dev Loop 与可信交付：让结果有据可查  

随着 Harness 能力增强，我们不再希望平台规定研发的每一步操作，而是先明确任务目标、约束和验收标准，再让 Agent 根据执行结果选择路径。

研发契约收敛为三个要素：

•**目标（Goal）：** 最终需要解决什么问题。

•**约束（Constraints）：** 哪些业务规则、兼容性和安全边界不能被破坏。

•**验收证据（Acceptance Evidence）：** 需要哪些真实结果证明目标成立。

这套研发协调机制称为 Dev Loop。无论是轻量修改还是正式需求，都应尽可能复用相同的执行底座，但根据任务风险调整上下文深度、治理要求和验证方式。

任务类型

执行与验证要求

轻量修改

源码、局部搜索、必要测试

常规研发

调用关系、配置影响、核心测试与构建

跨仓或高风险变更

跨仓依赖、业务规则、环境验证、回滚依据及必要的人工决策

每一轮执行都应带来新的可验证事实、关闭已知缺口或改变原有策略。如果连续多轮没有新证据，也没有改变处理方向，就应该停止自动重试，报告阻塞原因或请求人工判断。

### 5.1 从执行记录到验收结论

为了避免 Agent 过早宣布完成，我们将四个概念分开管理。

概念

主要回答的问题

Contract（研发契约）

什么条件下才算完成？

Trajectory（执行轨迹）

实际执行了哪些操作？

Evidence（验收证据）

哪些真实结果支持当前结论？

EvalResult（验收结论）

依据现有证据，最多可以宣布到哪一步？

代码差异、测试结果、构建日志和环境验证结果，本身就可以成为验收证据。关键是将它们与任务、代码版本、执行环境和验收条件关联起来。

例如，一组测试全部通过，系统还需要知道测试针对哪个代码版本、覆盖哪些验收条件，以及是否仍有其他验证未完成。

我们将研发结果区分为三个层次：

阶段

需要确认的事实

开发完成

代码差异、必要测试和风险检查达到约定标准

交付完成

代码评审、发布及相关交付步骤已经完成

效果确认

线上行为、业务指标或约定结果得到验证

这三个层次不是所有任务都必须机械执行的固定流程，而是用于明确每种结论需要什么证据。

**研发验收通过不代表代码已经评审；代码已经发布，也不代表业务效果已经确认。**

六、真实研发案例：

17 项测试全部通过，为什么仍不能宣布需求完成  

在一次广告推荐引擎混合版本配置兼容任务中，研发目标不仅是让新旧版本能够共存，还要求旧配置的原有语义不被破坏。实际修改围绕混合版本配置的解析与兼容分支展开，并补充旧配置语义保持、混合版本共存及相邻路径的验证。

本次任务中，Main Agent 关联任务、代码版本与研发状态，Personal Dev 提供研发工作区；CodeGraph 辅助定位配置处理函数、相邻调用和潜在影响范围，再由源码复核；Codex Harness 执行修改、测试与构建。研发契约预先把 17 项定向及相邻测试和约定模块构建列为本阶段必要验收项，Evaluator 只能依据这些证据限制结论层级。

17 项定向及相邻测试全部通过，约定模块构建成功，能够证明本次研发契约中明确列出的行为与构建路径成立；普通测试编译仍未形成通过证据。现有证据不足以确认该阻断由本次修改造成，也不足以在没有基线 Revision 复现的情况下直接归因为“存量问题”。

因此，当前证据最多支持“研发验收通过、具备进入代码评审的条件”。普通测试编译风险需要在后续代码评审或交付检查中继续保留并补证，不能被阶段性 `PASS` 抵消。

这个结论没有宣布需求全部完成，也没有将代码评审、发布或线上效果验证标记为成功。研发验收通过 ≠ 代码评审完成 ≠ 发布完成 ≠ 线上效果确认。

这个案例说明，一项真实研发任务已经能够把任务身份、代码修改、测试构建结果和阶段性验收关联起来，并在证据不足时停止结论升级；但它不能证明所有复杂研发任务都能稳定完成，也不能替代全量回归、跨仓影响复核和线上效果验证。

七、下一步：用真实任务验证系统是否变好  

下一阶段不再以继续增加 Agent 或工具数量为目标，而聚焦三件事：建立统一、可比较的工程度量，把任务、代码版本、执行轮次、证据、验收结论和最终结果关联起来；打通从业务问题、需求、研发、发布到结果确认的可追踪闭环；把被采用、拒绝或纠正的经验沉淀为候选知识、规则、测试、技能或 Memory，并在后续同类任务中重新验证。

判断标准只有一个：系统是否减少无效尝试、返工与人工接管，缩短交付周期，并提高有效交付和业务结果确认的比例。只有建立固定真实任务集与对照基线，模型、Harness、Skill 或 Memory 的升级才有可比较的价值。

让一次成功，成为下一次成功的条件  

广告凌凌漆的核心变化，不是接入了多少工具，也不是模型能生成多少代码，而是把数字员工、研发执行、长期工作环境、工程上下文和可信验收组织成一套协同系统：任务能够被承接和持续推进，结果能够被证据约束，经验能够在下一次任务中重新验证。

AI 原生工程系统真正值得追求的，不是偶尔完成一次复杂任务，而是稳定提高下一次真实任务成功的概率。
