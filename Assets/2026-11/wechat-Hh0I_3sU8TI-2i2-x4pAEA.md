01

一、AI Coding 不只是让 AI 帮我们写代码

随着 Codex 等 AI Coding Agent 的发展，AI 已经不再局限于代码补全，而是能够理解项目、分析需求、修改代码、执行测试，甚至独立完成一个完整的开发任务。

这让我开始思考一个问题：

既然 AI 已经能够参与整个研发流程，我们是否还应该沿用过去以人工操作为中心的研发模式？

例如：

需求文档是否还应该主要使用 Word？

测试用例是否还应该依赖 Excel？

架构设计是否应该只保留在 Visio 图中？

工程操作是否还需要大量依赖 UI？

为什么每次让 AI 开发一个功能，都需要重新解释项目背景和设计约束？

我认为，AI 时代真正值得改变的，不只是编码方式，而是整个软件研发体系。

这套理念可以称为 AI-Native Engineering（AI 原生软件研发）。

02

二、AI-Native Engineering 的六个核心原则

1\. Text First：文本优先

研发文档尽可能采用文本格式，而不是依赖 Word、Excel、PPT 等二进制办公文件。

需求、设计、架构说明优先使用 Markdown；结构化数据使用 YAML、JSON；接口定义使用 OpenAPI、Protobuf；业务规则可以使用 DSL。

文本格式更容易被 AI 理解、修改和生成，也方便 Git 进行版本管理、Diff 和 Review。

核心思想：让研发资产文本化、可读、可追溯。

2\. CLI First：命令行优先

尽可能减少对 UI 的依赖，让工程操作可以通过 CLI 和脚本完成。

例如构建、测试、性能测试、打包、部署，都应该提供统一的命令行入口。

CLI 具有可组合、可重复、可自动化和可追溯等优势，也更容易被 AI Agent 直接调用。

但并不是消灭 UI，而是重新划分职责：

操作尽可能自动化，观察尽可能可视化，决策保留人工控制。

3\. Structured First：结构化优先

能够通过 Schema 表达的内容，不要全部交给自然语言。

例如需求约束、业务规则、接口定义、数据模型、测试场景，都应该尽可能结构化。

自然语言适合表达意图，但结构化数据更容易校验、转换和复用。

核心思想：减少歧义，让 AI 从理解文本逐步转向处理明确的数据结构。

4\. Executable First：可执行优先

研发文档不应该只是描述系统，还应该尽可能驱动实际执行。

例如：

API 定义可以生成接口代码。

Protobuf 可以生成多语言协议代码。

DSL 可以生成业务规则执行代码。

测试规格可以生成测试用例。

部署配置可以驱动自动化部署。

核心思想：让 Specification 不只是文档，而是能够驱动研发流程的工程资产。

5\. Verifiable First：可验证优先

AI 生成的代码和配置不能仅凭人工阅读或模型自我评价判断正确性。

应该通过单元测试、集成测试、静态分析、性能测试、安全检查等方式建立自动化验证体系。

尤其要注意，需求、实现和测试不能完全依赖同一个 AI 自我闭环，需要独立的预期结果和必要的人工审核。

核心思想：AI 可以负责生成，但正确性必须能够被验证。

6\. Git First：版本管理优先

Git 不应该只用于管理源代码，还应该逐渐成为研发资产的核心管理基础设施。

需求、架构设计、ADR、接口定义、DSL、测试规格、自动化脚本等关键资产，都应该纳入版本管理。

这样才能实现变更追溯、分支协作、代码审查和版本回滚。

核心思想：让研发过程中的关键知识和决策都能够被追溯。

03

三、将 First 原则应用到整个研发流程

六个原则不应该只应用于编码阶段，而应该贯穿整个软件生命周期。

研发阶段

AI-Native 实践

需求分析

Markdown + 结构化 Spec

产品设计

领域模型 + 业务规则

架构设计

Markdown + Mermaid + ADR

接口设计

OpenAPI / Protobuf

任务拆解

Spec → Task

编码开发

Agent + CLI

测试验证

Spec → Test

性能测试

Benchmark + 自动化报告

构建部署

CLI + CI/CD

运维管理

Runbook + Scripts

此外，还有几个需要特别关注的方面：

Context Engineering：通过 AGENTS.md、Skills 管理项目上下文，减少重复解释和无效 Token 消耗。

Infrastructure as Code：开发环境、依赖和部署配置代码化，保证环境可复现。

Security & Governance：控制 Agent 权限，关键操作保留人工审批和审计。

Traceability：建立需求、设计、任务、代码、测试和发布之间的追溯关系。

04

四、从 AI Coding 到 AI-Native Engineering

如果从零构建一套 AI 原生研发体系，我会分三个阶段：

第一阶段：基础规范

建立 Markdown 文档规范、统一项目目录、AGENTS.md、CLI 命令入口和脚本化工程操作。

第二阶段：Spec-Driven Development

建立需求规格、架构决策、接口契约、DSL 和 Schema，让需求能够驱动开发任务和测试用例。

第三阶段：Agentic Engineering

让 Agent 参与需求分析、任务拆解、编码、测试和交付，通过自动化验证和人工审批保证结果可靠。

05

五、结语

回到最初的问题：

AI 时代，需求文档是否应该使用 Markdown？研发工具是否应该 CLI 化？是否应该减少对 Word、Excel 和 UI 的依赖？

我认为，这些都只是表象。

真正值得改变的是软件研发的组织方式。

过去，我们习惯于人理解需求、人设计系统、人编写代码、人测试验证。

未来，我们应该逐渐转向：

人定义目标和约束，AI 理解并结构化需求，工具链负责确定性执行，自动化系统负责验证，人负责关键决策。

我认为，AI 时代真正有价值的，不只是让 AI 帮助我们写代码，而是围绕 AI Agent 重新构建一整套软件工程体系。

从 AI Coding 到 AI-Native Engineering，改变的不只是开发工具，而是整个软件研发范式。
