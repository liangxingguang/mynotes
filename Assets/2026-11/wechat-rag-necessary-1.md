企业内部的制度问答，是最容易看清 RAG 价值的场景：一批 PDF 与 Word 制度文件，员工问「出差住宿标准是多少」。

把问题直接交给通用大模型，它会给格式完整、数字具体的答案，但那个数字来自公开语料的常见做法，不是这家公司的条款。

要让答案对上自家制度，工程上有四条路：全量塞进上下文、微调模型、用 Agent 编排流程、检索增强生成。它们常被放在一起比优劣，实际改的变量不同。

长上下文改的是「一次能读多少」。窗口涨到几十万 token 后全量塞入可行，但成本随材料量线性上升：语料从 100 篇到 10000 篇，单次成本涨 100 倍；检索只与筛出的段数有关，基本不变。

微调改的是「怎么说」。它改输出风格、格式与领域表达，但知识供给有三个硬约束：改一次知识要重训一次；删一条事实无法定点完成；训练数据里的过时内容会被继续复述。

Agent 改的是「做什么、按什么顺序做」。流程变复杂不会让事实变准确，每一步仍要从某处取回材料。RAG 是 Agent 的事实来源，Agent 是 RAG 的使用者。

只有 RAG 改的是「依据哪些事实说」。四类场景非检索不可：内部制度、客服售前、合规法务、研发运维文档。共同点是三条：知识私有，公开语料没有；更新快；答案要能核。

三条同时成立时，检索是唯一能同时满足的做法。判断顺序也由此而来：缺事实先补事实，因为事实错了，后面两步都在放大错误。
