# 【JVM 底层修炼记】从 JDK 8 到 JDK 21：ZGC 与低延迟垃圾回收器的演进

在前面的文章中，我们走过了垃圾回收算法的理论基石，见识了 G1 如何通过 Region 与可预测停顿时间模型重塑内存管理，也经历过生产环境频繁 Full GC、OOM 与堆外内存泄露的惊心动魄。

当我们把目光投向今天动辄数十 GB 甚至上百 GB 的大内存微服务、实时风控引擎与高频交易系统时，G1 的停顿时间有时依然难以满足极其严苛的延迟要求。尤其是在高并发、大量对象存活或业务负载波动较大的场景下，GC 停顿可能成为影响接口 P99、P999 延迟的重要因素。

于是，低延迟垃圾回收器（Low-Latency GC）逐渐走上了历史舞台。其中最受关注的代表之一，莫过于 **ZGC（Z Garbage Collector）**。

从 JDK 11 实验性引入，到 JDK 15 正式转为生产可用，再到 JDK 21 引入**分代 ZGC（Generational ZGC）**，ZGC 的发展经历了重要的技术演进。

它究竟是如何实现亚毫秒级的低停顿？染色指针与读屏障又是如何协同工作的？分代 ZGC 又解决了早期版本的哪些问题？

今天，我们就来揭开它的底层原理。

## 一、为什么传统 GC 在“超大堆 + 低延迟”面前力不从心？

无论是 CMS、G1，还是其他传统垃圾回收器，在面对超大堆和极其敏感的延迟要求时，都可能遇到一些性能瓶颈。

这里需要先明确一点：**不同垃圾回收器的停顿机制并不相同，不能简单地认为堆越大，所有 GC 的停顿时间就一定越长。**

例如，Parallel GC 主要通过 Stop-The-World（STW）方式完成垃圾回收，回收工作量较大时，停顿时间通常也会随之增加。

CMS 和 G1 则通过并发处理部分回收工作，尽量缩短业务线程需要暂停的时间，但它们仍然存在必须暂停业务线程的阶段。

主要有两个方面值得关注：

1. **STW 阶段仍然存在**：即使是 G1，也需要在初始标记、最终标记、对象转移等阶段执行一定的停顿操作。实际停顿时间受到根扫描、待回收对象数量、Remembered Set 处理、CPU 资源等多种因素影响。当业务负载复杂、存活对象较多时，实际停顿时间可能超过预期。
2. **并发回收需要额外的协调机制**：垃圾回收线程与业务线程同时运行时，业务线程仍然可能不断创建对象、修改对象引用关系。为了保证并发回收过程中的正确性，GC 必须使用写屏障、读屏障等机制记录和处理这些变化。这些机制会带来额外开销。

需要注意的是，业务线程修改引用关系并不意味着 GC 一定会退化成长时间 STW。真正影响停顿时间的，是垃圾回收器必须在暂停阶段完成多少工作，以及这些工作能否被有效地转移到并发阶段。

ZGC 的核心设计思路就是：**尽可能将标记、对象转移等耗时工作放到业务线程运行期间并发完成，把必须 STW 的工作压缩到非常短的阶段。**

ZGC 的设计目标包括：

- 尽可能将最大停顿时间控制在亚毫秒级。
- 停顿时间不随堆容量、存活集大小简单增长。
- 支持从较小堆到多 TB 级别的大型堆内存。

这并不意味着 ZGC 可以在任何业务场景下保证固定的停顿时间，而是说明它在架构设计上，尽可能避免让整个堆的回收工作量直接转化为业务线程的暂停时间。

## 二、ZGC 的两大核心黑科技：染色指针与读屏障

ZGC 之所以能够实现极低停顿，靠的不是运气，而是两项非常重要的底层机制：

**染色指针（Colored Pointers）与读屏障（Load Barrier）。**

在分代 ZGC 中，还引入了用于处理代际引用关系的写屏障机制。

### 1. 染色指针（Colored Pointers）：把 GC 状态写进指针里！

传统 HotSpot 虚拟机通常会在对象头中保存一些对象元数据，例如对象的锁状态、哈希码和年龄等信息。

而 ZGC 采用了一种不同的设计思路：

**直接利用 64 位对象引用中的部分比特位保存 GC 相关元数据。**

这就是染色指针。

在受支持的 64 位平台上，ZGC 会利用对象引用中的部分位记录与垃圾回收相关的状态信息，例如对象的标记状态、引用是否需要重新映射，以及终结处理相关状态等。

通过这种设计，ZGC 不必每次都访问对象头才能判断引用是否需要进行某些 GC 处理。

染色指针主要带来了两个好处：

- **降低状态判断成本**：GC 可以通过对象引用携带的元数据，判断当前引用是否处于需要处理的状态。
- **为并发对象转移提供基础**：对象被移动后，旧引用可能仍然存在。通过指针状态与后续的屏障处理，ZGC 能够识别并修复这些旧引用。

这里需要注意：

染色指针并不是把对象的全部信息都写进了指针，也不是仅凭指针就能完成所有 GC 操作。它主要负责携带 GC 元数据，真正的引用修复还需要配合读屏障及转发表等机制完成。

另外，具体的指针位布局会随着 ZGC 的实现和版本演进而变化，不应该把某个版本的位布局理解为所有版本永久不变的规则。

### 2. 读屏障（Load Barrier）：按需触发的引用自愈机制

理解了染色指针，我们再来看 ZGC 最重要的机制之一：读屏障。

假设 ZGC 正在后台并发地将对象从旧内存区域转移到新的内存区域，而业务线程此时仍然持有指向旧地址的对象引用。

如果业务线程直接使用这个旧引用，就可能访问到已经不再是当前有效位置的对象。

ZGC 如何解决这个问题？

答案就是**读屏障（Load Barrier）**。

ZGC 会在读取堆中对象引用的相关操作上插入屏障逻辑。当业务线程读取一个对象引用时，屏障会检查引用携带的状态信息，判断是否需要进行额外处理。

如果发现当前引用需要重新映射，例如对象已经完成转移，但引用仍然指向旧地址，读屏障就会：

1. 根据对象转移信息找到对象的新地址。
2. 将旧引用修正为新引用。
3. 在适当情况下，将修正后的引用写回原来的引用位置。
4. 返回可以正常使用的新对象引用。

这种机制被称为**自愈（Self-Healing）**。

它带来的好处是：

即使对象已经被 GC 并发转移，业务线程也不需要等待整个转移过程结束后才能继续访问对象。通过读屏障，ZGC 可以在业务线程访问对象时按需修复旧引用。

这也是 ZGC 能够实现并发对象转移的重要基础。

需要强调的是：

- 读屏障不是每次读取普通变量都会执行完整的 GC 处理，它主要针对堆中对象引用的加载操作。
- 读屏障本身也存在运行时开销。
- ZGC 并不是完全没有 STW，而是将大量耗时工作转移到了并发阶段。

另外，在 JDK 21 的分代 ZGC 中，除了读屏障，还引入了用于记录跨代引用关系的写屏障机制。因为年轻代回收时，必须能够识别老年代对象指向年轻代对象的引用，避免错误地回收仍然存活的对象。

## 三、分水岭：从 JDK 11/15 非分代 ZGC 到 JDK 21 分代 ZGC

早期版本的 ZGC 采用的是非分代（Non-Generational）设计。

这里需要先明确 ZGC 的版本演进：

- **JDK 11**：ZGC 首次以实验性功能引入。
- **JDK 15**：ZGC 正式转为生产可用功能。
- **JDK 17**：仍然使用非分代 ZGC。
- **JDK 21**：引入分代 ZGC，作为可选的实验性模式提供。

早期非分代 ZGC 有一个比较明显的特点：

**它不区分对象的年轻代和老年代。**

无论对象刚创建几毫秒，还是已经存活了几个小时，都处于同一个代际管理体系中。

这并不意味着每次 GC 都会扫描堆内存中的每一个对象，而是指它没有利用年轻代和老年代之间的生命周期差异来缩小回收范围。

对于大量创建短生命周期对象的业务，这种设计存在一定的效率问题：

- **GC 工作量相对较大**：短生命周期对象与长期存活对象处于同一代际管理体系中，回收周期需要处理整个堆的存活对象关系。
- **GC CPU 开销可能较高**：在对象分配速率很高的业务中，非分代模式可能需要投入较多 CPU 资源执行并发回收。
- **分配停顿风险**：如果业务对象分配速度超过 GC 的回收速度，堆内存又缺乏足够的可用空间，业务线程就可能出现等待 GC 回收内存的情况。

### JDK 21：Generational ZGC 正式登场

JDK 21 引入的分代 ZGC，正是为了解决上述问题。

它结合了经典的**弱分代假说（Weak Generational Hypothesis）**：

大多数对象的生命周期都比较短，只有少部分对象会长期存活。

因此，垃圾回收器可以更频繁地回收年轻对象，而不必每次都以相同的方式处理整个堆中的长期存活对象。

分代 ZGC 将堆划分为：

- **年轻代（Young Generation）**：主要存放新创建的对象，回收频率相对较高。
- **老年代（Old Generation）**：存放经过一定存活阶段、仍然被程序引用的对象，回收频率相对较低。

它们并不是两个完全独立的 Java 堆，而是 ZGC 在同一堆内存管理体系中进行的代际划分。

分代 ZGC 的工作方式可以简单理解为：

1. 年轻代中存在大量短生命周期对象，因此可以更频繁地执行年轻代回收。
2. 老年代中的对象通常存活时间更长，不需要跟随每一次年轻代回收都进行同等范围的处理。
3. 通过写屏障等机制记录跨代引用关系，确保年轻代回收时不会遗漏仍然存活的对象。

这样一来，GC 就可以更有针对性地处理短生命周期对象。

**分代 ZGC 带来的主要收益包括：**

- 降低垃圾回收的 CPU 开销。
- 降低维持垃圾回收所需要的堆内存开销。
- 降低业务对象分配速度过快时发生分配停顿的风险。
- 在保留 ZGC 低停顿特性的同时，改善高对象分配速率场景下的整体效率。

需要注意，分代 ZGC 并不意味着所有业务的吞吐量都会提升数倍。实际收益取决于对象分配速率、存活对象比例、堆大小、CPU 资源以及业务负载特征。

### 后续版本的演进

分代 ZGC 在 JDK 21 引入后，又经历了进一步的版本演进：

- **JDK 23**：分代模式成为 ZGC 的默认模式，非分代模式被弃用。
- **JDK 24**：非分代模式被移除，ZGC 统一采用分代模式。

因此，如果我们讨论的是 JDK 21，就需要明确它仍然同时提供分代和非分代两种模式；如果讨论 JDK 24 及之后的版本，则不再需要通过 `ZGenerational` 参数切换模式。

## 四、从 JDK 8 到 JDK 21：升级与选型建议

很多团队至今仍然运行着 JDK 8 的存量系统。面对 JDK 17、JDK 21 以及 ZGC，该如何理性看待？

先看不同版本的垃圾回收器演进：

| 维度 | JDK 8 | JDK 17 | JDK 21 |
| --- | --- | --- | --- |
| 常见默认收集器 | Parallel GC（Server VM） | G1 | G1 |
| G1 | 已支持，可选使用 | 默认收集器 | 默认收集器 |
| ZGC | 不支持 | 已正式可用于生产，非分代模式 | 已正式可用于生产 |
| 分代 ZGC | 不支持 | 不支持 | 引入，可选实验性模式 |
| 主要特点 | 传统收集器生态成熟 | 低延迟 GC 已具备生产可用性 | 开始具备分代 ZGC 能力 |

这里有几个需要特别注意的地方：

**第一，JDK 8 并不是没有 G1。**

G1 在 JDK 7u4 就已经作为实验性功能提供，JDK 8 中也可以通过 `-XX:+UseG1GC` 使用，只不过 JDK 8 的常见默认收集器仍然是 Parallel GC。

**第二，JDK 17 已经可以在生产环境使用 ZGC。**

但此时的 ZGC 仍然是非分代版本，不能直接使用 JDK 21 才引入的分代模式。

**第三，JDK 21 的分代 ZGC 仍然需要显式开启。**

如果要在 JDK 21 中启用分代 ZGC，可以使用：

`-XX:+UseZGC -XX:+ZGenerational`

如果只使用：

`-XX:+UseZGC`

则会使用 JDK 21 中的非分代 ZGC。

而在 JDK 23 及之后的版本中，分代模式已经成为默认模式；JDK 24 及之后也不再支持旧的非分代模式。

### 什么业务适合优先考虑 ZGC？

**1. 对接口延迟极其敏感的业务**

例如：

- 实时风控系统。
- 高频交易系统。
- 实时数据处理服务。
- 对 P99、P999 延迟有严格要求的微服务。

这些业务对 GC 停顿非常敏感，即使一次几十毫秒的停顿，也可能影响请求处理和服务响应。

ZGC 可以将大量回收工作放到并发阶段，从而降低 GC 对业务线程的停顿影响。

**2. 大内存、高对象分配速率的业务**

例如：

- 大型缓存服务。
- 高并发数据处理系统。
- 大规模对象处理服务。
- 需要维护大量长期存活对象的应用。

ZGC 能够支持多 TB 级别的堆内存。Oracle 的 JDK 21 文档介绍了 ZGC 对数百 MB 到 16TB 堆内存的支持范围。

但需要注意，堆容量并不是越大越好，仍然需要根据实际存活集和对象分配速率合理配置。

**3. 不适合盲目切换的业务**

如果服务本身只有几百 MB 的堆内存，GC 停顿对业务没有明显影响，而且 G1 已经能够满足延迟要求，那么没有必要仅仅为了追求新技术而强行切换 ZGC。

因为 ZGC 的低停顿能力并不是没有成本的。

它需要额外的屏障处理，也需要占用 CPU 资源执行并发 GC 工作。对于以极限吞吐量为主要目标的业务，Parallel GC 或 G1 可能仍然是更合适的选择。

### 使用 ZGC 时还需要关注什么？

有一点非常重要：

**ZGC 是并发垃圾回收器，必须为并发回收预留足够的堆内存空间。**

因为业务线程在 GC 执行期间仍然可以持续分配对象。

如果业务对象分配速度很快，而 GC 来不及回收内存，就可能出现分配停顿，业务线程不得不等待 GC 释放可用空间。

因此，在使用 ZGC 时，不能只关注最大堆内存，还应该重点监控：

- 对象分配速率。
- 存活对象集大小（Live Set）。
- GC 并发执行期间的堆内存余量。
- GC CPU 占用。
- 分配停顿情况。
- 接口 P99、P999 延迟。

对于 JDK 21 及之后的版本，还可以通过统一日志查看 GC 运行情况：

`-Xlog:gc*`

最终应该通过真实业务压测，对比 G1 与 ZGC 在吞吐量、GC CPU 开销、停顿时间和尾延迟上的表现，再决定是否切换。

**监控数据与业务诉求，永远是垃圾回收器选型的第一准则。**

## 五、JVM 底层修炼记：阶段性收官

走到今天，我们的《JVM 底层修炼记》系列也正式完成了一个阶段性的收尾。

回望这一系列内容：

从 `.class` 文件加载与 JVM 运行时内存，到对象创建、逃逸分析与可达性分析；从分代回收算法、垃圾收集器演进，到 `jps`、`jstat`、`jstack` 等命令行工具，再到 VisualVM、JProfiler、Arthas 等性能分析工具。

我们还深入分析了生产环境中的 Full GC、OOM、堆外内存泄露，以及从传统垃圾回收器到 ZGC 的低延迟演进。

这些知识并不是彼此孤立的。

它们共同构成了一套完整的 JVM 知识体系：

- **理解原理**：知道 JVM 如何管理内存、创建对象和回收垃圾。
- **掌握工具**：能够通过监控、日志和诊断工具定位问题。
- **分析问题**：面对 Full GC、OOM 和内存泄露时，能够从现象推导原因。
- **优化性能**：结合业务特点、运行环境和监控数据，选择合理的 JVM 参数与垃圾回收器。

学习 JVM 的最终目的，并不是记住多少个参数，也不是背下多少种垃圾回收算法。

而是在面对真实的生产问题时，能够理解 JVM 正在做什么，判断性能瓶颈在哪里，并找到真正有效的解决方案。

愿你在未来的每一次线上护航与性能优化中，都能做到：

**心中有原理，手中有工具，临危不乱，游刃有余。**
