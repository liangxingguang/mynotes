# 需求分析怎么做？三个视角看业务，四步做成价值闭环

> 摘要：一套在真实资产管理项目中跑通的需求分析框架：先用流程/数据/角色三个视角看懂业务，再用定义价值范围、结构化建模、设计最小价值单元、验证管理四步做成价值闭环，并在日志管理领域做迁移验证，证明框架本身可迁移。

## 核心要点

1. **三维认知**：流程视角（事情怎么一步步发生）、数据视角（业务里有哪些实体）、角色视角（谁参与、担什么责）；三视角叠起来对照，交汇处是最值钱的切入点
2. **目标分层**：顶层目标（Why，公司/组织层愿景）vs 业务目标（What，特定范畴为特定角色解决的具体问题）；拆解路径：战略→业务问题→用户角色→业务目标，角色必须先定
3. **结构化建模三块**：流程建模（配人机分工表，能交给系统的绝不留给人）、数据建模（先定实体货架→字段规则→关系）、规则建模（数据验证/流程流转/业务逻辑/异常处理四类各司其职）
4. **最小价值单元公式** = 能独立交付 + 完整价值体验 + 最小功能集合；圈端到端旅程里真正必要的步骤，分批交付小闭环
5. **验证管理**：原型验证（真实用户操作）、三方评审（业务/开发/测试）、需求文档库 + ID 全程追溯 + 变更三步留日志
6. **迁移实验**：换到日志管理领域，产出物从业务表格换成技术模型草案，动作一模一样，框架可迁移
7. **两大价值**：可传授的脚手架（交给同事快速摸业务）、把「我觉得」变成「我假设流程是 A、数据是 B、角色是 C，来验证」的沟通工具

前言

需求分析失控的样子，你大概率见过。要么范围越做越大，什么都想塞进去；要么排优先级全凭感觉；要么功能做出来挺唬人，核心用户的问题一点没解决。

这篇讲一套在真实资产管理项目里跑过的框架。三个视角打底，先把业务看明白；四步走完，把理解变成可交付的产出；最后换个完全不同的领域做迁移实验，看这套框架本身扛不扛用。

### 01 THINKING 思维基础，建立三维认知模型

拿到一个陌生业务，先忍住，别急着问「要做什么功能」。三个视角把业务看一遍，再谈功能。

- **流程视角**，看业务怎么随时间推进，要问的是「事情是怎么一步步发生的」；
- **数据视角**，看业务里有哪些关键实体、它们怎么关联，要问的是「业务世界里存在哪些事物」；
- **角色视角**，看谁在参与、担什么责、有什么权，要问的是「谁在做什么，为什么是他」。

这三个视角别各看各的。流程、数据、角色叠在一起对照，交汇的地方往往就是最值钱的切入点。

三个视角叠起来看业务，交汇处就是切入点

### 02 PRACTICE 实践的展开，四步构建价值交付闭环

#### 第一步，定义价值与范围

先辨析两个容易混的词。顶层目标站在公司和组织的层面，管的是较长周期里的愿景和方向，回答的是 Why，我们为什么要做这件事、为什么要建这个系统。业务目标往下落一层，是在特定业务范畴里、为特定角色要解决的具体问题，回答的是 What，解决什么、为谁解决。

这两层不掰清楚，开头说的三种失控就全来了。拆解有一条固定路径，从战略出发，落到业务问题，再落到用户角色，最后收敛成具体的业务目标。角色必须先定下来。角色不清楚，范围、优先级、满意度就全都没有了评判标准。

拿某企业的资产管理项目走一遍。现状是「线上申请、线下管理」两张皮，账、物、权对不上。问题诊断下来有三条：

- 账、物、权割裂，台账、实物、责任人三边信息分离，数据对不上；
- 流程断裂，线上申请和线下管理脱节，流程不闭环，状态更新靠人工；
- 成本与风险失控，账实不符导致资产流失、重复采购，操作不透明还埋着合规风险。

角色识别跟着展开。按单位类型从总部、二级单位到三级公司，逐层摸清各部门在资产管理里管什么。再对每个角色做一次翻译，把痛点翻成业务目标。

| 角色 | 痛点 | 业务目标 |
|---|---|---|
| 归口部门 | 资产状态无法及时知晓；责任不清，遗失后追责困难；依赖手工台账，账实不符严重；盘点耗时耗力 | 透明可控，实时查看资产状态、位置、价值；权责清晰，线上确认领用责任人；流程闭环，入库、领用、调拨、维修、处置全程线上 |
| 财务部 | 资产账务与实物变动不同步，对账困难；折旧靠手工，易错低效；成本分摊不准 | 资产申请与部门预算联动，预算执行实时可查，减少超支 |

把痛点翻译成业务目标

#### 第二步，结构化分析与建模

价值和范围定了，进入建模。建模分三块，流程、数据、规则。

**流程建模**

先把流程画清楚。员工口头或微信向办公室申请，办公室发起线上申请，领导线上审批，资产出库。图上标注角色职责，谁申请、谁审批，也标出决策点，比如资产可用性检查和审批结果的分支。

流程图之外还要配一张人机分工表，写明白系统做什么、人做什么。

| 步骤 | 人工任务 | 系统自动化任务 |
|---|---|---|
| 申请 | 员工选择物品、填写数量与用途 | 自动填充基础信息，实时校验库存与部门额度 |
| 审批 | 无 | 按公司管理办法自动走对应的审批链 |
| 出库 | 管理员领出后下发给相关人员或部门 | 自动扣减库存，生成出库记录 |
| 数据同步 | 无 | 实时同步库存与资产台账 |

能交给系统的绝不留给人，人的操作越少，流程越不容易断。

流程建模产出

**数据建模**

数据建模拆成三问来看。

- 数据是什么？对现实世界业务实体的属性记录，是信息系统最原始的原材料；
- 数据类型是什么？文本、数值、枚举、日期、关联对象、文件。类型本身就在给数据立规矩，而且是原子级的；
- 数据建模是什么？先定义货架，也就是实体和表，比如资产表、员工表、部门表；再设计货架结构，把字段、规则、外键定下来；最后建立关系，想查某个部门的所有资产，路径是部门表到员工表再到资产表。

**规则建模**

规则分四类，各管一段。

| 规则类型 | 核心职责 |
|---|---|
| 数据验证规则 | 确保进入系统的每个数据格式正确、符合基础标准，录入即触发，硬性约束 |
| 流程流转规则 | 控制业务流程的状态转换路径和顺序，决定流程能否进入下一阶段 |
| 业务逻辑规则 | 基于业务内容做计算、判断和决策，随业务策略调整而更新 |
| 异常处理规则 | 非正常情况发生时系统如何降级或恢复，最好永远用不上，但必须存在 |

四类规则各司其职，缺一类，系统就多一类「没想到」。

四类规则怎么一起起作用？拿同一个场景过一遍。员工张三申请领用一台笔记本电脑。

- 数据验证，申请标题、申请人、资产名称、使用部门这些字段不能空着；
- 流程流转，先查这台电脑的状态是不是「在库」，不是就拦下来，提示「该资产已被占用」；
- 业务逻辑，价值超 1 万，判断要走二级审批，部门经理和财务总监都得过；
- 异常处理，数据库要是不稳定，回滚事务，提示「系统繁忙，请稍后重试」。

#### 第三步，设计最小价值单元

建模做完，还剩一个问题没答，先交付什么。答案就一行公式。

> 最小价值单元 = 能独立交付的 + 为用户提供完整价值体验的 + 最小功能集合

怎么圈？先画端到端的用户旅程，从需求产生到领用资产一共六步。再定义最小完整性。六步里真正必要的只有申请、审批、结果通知这三步，多级审批可以往后放。

于是复杂系统拆成一个个完整的小闭环，分批交付。每一批都让一部分用户完整体验到价值，反馈也拿得回来，下一步往哪走就有依据了。

最小价值单元

#### 第四步，验证与管理

方案写完不算完事，还得验证、还得管。

- **原型验证**，请真实用户来操作关键流程的原型，反馈现场收集；
- **需求评审**，业务、开发、测试三方一起过需求规格，理解对齐了才算过；
- **需求管理**，建需求文档库，所有产出物按框架归位，保证唯一事实来源；需求 ID 从设计跟到测试，全程可追溯；变更走评估、决策、更新三步并留日志；流程确认、范围划定、原型验证这些关键决策点，业务负责人必须深度参与。

### 03 TRANSFER 框架的迁移实验，换个领域破解日志管理

框架好不好用，换个完全不同的领域试试就知道。这次选的是日志管理，一个偏技术的场景。资管项目里那套表格和流程全用不上，框架还能跑吗？

**三个视角照样先上**

- 流程视角，日志怎么产生、怎么收集、怎么处理、怎么被消费，一条线四步；
- 数据视角，关键实体有三个，日志源（哪个系统、什么环境）、日志事件（时间戳、级别、消息）、日志标准（格式规范和字段定义）；
- 角色视角，日志生产者是各业务系统的开发团队，消费者是运维、开发和安全人员，中间还有平台管理者，负责定标准、维护收集管道。

**四步闭环照样能走**

- 第一步，把问题和边界定下来。各系统日志分散、格式不一，出了故障要登好几台服务器翻日志。成功指标定成一句话，关键业务系统的错误日志 100% 收集；
- 第二步，结构化建模。日志源、日志标准、日志事件三个实体的模型草案先出来，再配上收集规则（错误日志立即推送，警告日志批量推送但延迟不超过 5 分钟）和存储规则（存 30 天后归档）；
- 第三步，圈最小价值单元。MVU 1 只做基础收集和查询，先让运维能集中看到关键错误日志，MVU 2 再上统计图表和更强的查询语法；
- 第四步，验证与管理，和资管项目完全一样。

跑完的体会是，产出物从业务表格换成了技术模型草案，动作却一模一样。先三视角看业务，再三步建模，最后圈 MVU。框架本身是能迁移的。

### 04 SUMMARY 总结与探讨，这套框架的价值

**价值一，可传授的学习框架**

有同事要接手一个新业务模块，你可以把这个框架当脚手架交给他。他顺着流程、数据、角色三条线把业务快速摸一遍，比抱着一堆文档自己啃快得多。

**价值二，假设验证的沟通工具**

项目早期大家想法都很模糊。这个框架能把「我觉得」变成「我假设流程是 A、数据是 B、角色是 C，我们来验证一下」。早期讨论的效率和质量，就靠这一步撑起来。

### 最后

回头盘一遍，这套框架真正管用的地方，是把模糊的想法变成可以验证的结构。三个视角帮你看懂业务，四步把理解做成可交付、可验证的产出。文档写得厚不厚，反倒是其次。
