昨天的《[如何用 Coding Agent 构建自己的软件工厂？](https://mp.weixin.qq.com/s?__biz=MzAwNjQwNzU2NQ==&mid=2650411105&idx=1&sn=3f2b466be31efd88a6381a399fc774eb&scene=21#wechat_redirect)》，我们聊了怎样让一项研发任务经过实现、检查和修复，最后交出可供合并的 PR。代码写完以后，CI、审查和人工等待还得有人继续跟进。

今天把视线从代码仓库移到企业业务。把交付物换成一张订单、一张工单或一份付款申请，持续跟进的思路依然有用，但系统要理解的事情变多了。

两个系统里的供应商是不是同一家？邮件说货到了，仓库却没有收货记录，该按什么依据处理？今天等人补录，明天怎样继续？申请提交超时了，到底有没有成功？这些问题会影响业务建模、接口设计，也会决定 Agent 能走到哪一步。

今天就沿这项建设往下看：用 AI Coding 做出原型，用 Ontology 说清业务含义，再把工具、执行和反馈组织进 Harness。**让 Agent 从给出建议走到交回结果，中间缺什么，就沿一项业务逐步补上。**

下面先看整体架构，再用"发票异常处理"逐步展开。这是一个设计示例，接口和流程用于说明各部分怎样配合。

## 太长不看

*   **第一版围绕一项能验收的业务任务。**
    
     从查明发票卡点，到补齐材料、等待审批、创建付款申请，每一步都有明确产物。
    
*   **业务模型同时描述"是什么"和"能做什么"。**
    
     对象编号、数据来源、时效和动作条件，共同决定 Agent 能否正确使用工具。
    
*   **把模型的一轮工作放进可持续跟进的流程。**
    
     模型负责调查和分析，系统保存进度、接收事件、核对动作结果；用真实业务样本逐步扩大自动化范围。

## 整体架构

AI Coding、[Ontology](https://mp.weixin.qq.com/s?__biz=MzAwNjQwNzU2NQ==&mid=2650410012&idx=1&sn=efa78c5a0346d7d297e739c1b4da7dd5&scene=21#wechat_redirect)、[Harness](https://mp.weixin.qq.com/s?__biz=MzAwNjQwNzU2NQ==&mid=2650410709&idx=1&sn=3c870a0602fffffc9e6259fd0daef8c2&scene=21#wechat_redirect)、FDE 经常出现在企业 Agent 的讨论里。先把它们放回各自负责的工作，会更容易看清建设顺序。

工作

在这项建设中负责什么

AI Coding

根据业务规格实现代码、运行检查，帮助团队迭代原型

Ontology（业务本体）

定义业务对象、关系和动作含义，让不同系统的数据能够对应起来

Harness

准备上下文、调用模型和工具、处理反馈，组织 Agent 每一轮工作

Runtime 与任务流程

提供执行环境、持久状态和调度能力，承接暂停、恢复及后续跟进

FDE（Forward Deployed Engineer，前线部署工程师）

深入业务现场，打通需求、系统集成、效果验证和交接

这里有两条线。开发和交付时，FDE 与业务人员一起确认目标，Coding Agent 参与实现和检查；系统运行时，用户请求进入任务流程，Agent 调查问题，业务接口提供数据并执行正式动作。下面这张图画的是运行时的分工。

图 1：企业 Agent 的运行架构（本文设计示例。任务流程按需调用 Agent，也可以直接执行确定的步骤；业务接口承载对象、关系和动作规则。图中是逻辑分工，可以先部署在同一个服务里。）

沿图走一遍：用户要求跟进一张发票，任务流程登记目标和进度；需要查明原因时，Harness 组织模型调用工具，读取采购、仓储和财务记录。Agent 发现缺少收货记录，交回证据和建议，流程据此创建待办、登记等待条件。仓库补录以后，流程重新核对条件，必要时再让 Agent 分析，最后通过业务接口提交申请、确认结果。

这套架构里，我会把**调查路径留给 Agent，把正式动作的校验留在业务服务，把跨轮次的跟进交给持久流程**。原因很具体：查问题可能需要换几个方向，审批和金额规则却已经有明确的负责系统；等待一天以后，也不能只靠一段聊天记住该做什么。

建设可以从一条业务路径起步：先约定完成条件，做出只读原型；用真实数据校准对象和工具，再接入等待、审批与写操作。评估和现场反馈贯穿其中，每增加一种执行能力，就增加相应的验收样本。

## 任务边界

假设财务人员问："这张发票为什么还不能申请付款？请帮忙跟进，满足条件后创建申请。"

这里其实包含两种工作。前半段要找原因，可能需要读发票、采购单、收货记录和往来邮件；后半段要推动业务，可能涉及仓库补录、财务审批和申请提交。调查路径不完全固定，正式动作则有自己的规则。

第一版可以把范围限定为：一个法人主体、一类采购业务、一张发票关联一张采购单，最终停在**付款申请已创建**。实际付款由后续财务流程负责。合并开票、部分付款、红字冲销等情形先作为人工处理分支，后续再逐项接入。

这样就能写下一份具体规格：

```
输入：当前用户身份、发票编号调查：读取关联单据，解释阻塞原因，附上证据编号跟进：材料缺失时创建待办，记录负责人和等待条件执行：材料满足要求且正式审批有效后，创建付款申请完成：财务系统返回有效申请编号，关键字段核对一致转人工：单据无法关联、证据冲突，或提交结果无法确认
```

"有效审批"在这个例子里，指已有审批流程对本次申请内容的授权；如果企业的审批发生在申请创建之后，就调整流程顺序，把"创建待审批申请"作为该阶段的结果。先和业务人员确认真实顺序，后面的状态机才有依据。

FDE 可以从这一步参与：跟着财务看几笔历史异常，追到仓库和采购系统，确认谁补数据、谁作决定、哪些结果能被查询。拿这份规格和实际流程逐项核对，很快就能发现遗漏。

## AI Coding：验证原型

有了这份规格，可以先让 Coding Agent 实现只读调查：输入发票编号，返回关联单据、异常说明和证据。暂时用经过脱敏的样本及模拟接口，把页面到结果展示跑通。

给 [Coding Agent](https://mp.weixin.qq.com/s?__biz=MzAwNjQwNzU2NQ==&mid=2650410984&idx=1&sn=a2278c11e9dcf1d42930359839df7676&scene=21#wechat_redirect) 的材料也随之具体起来：现有服务的接口文档、鉴权方式、几份样本响应、业务规则，以及要运行的检查命令。这样生成的代码才容易接上现有服务，接口和规则也有据可查。

原型的第一组样本，可以从三个情况起步：正常匹配、缺少收货记录、发票金额与采购单不一致。每个样本都写出预期结果。比如"缺少收货记录"这个样本，期望它说明当前证据不足、建议仓库核实，并附上查到的单据；不能把它直接判断成"货还没到"。

这些预期行为构成规格驱动开发（SDD）的起点。金额比较、身份校验、字段转换等确定性逻辑，可以采用测试驱动开发（TDD）：先写一个会失败的测试，再让 Coding Agent 实现到测试通过，随后在测试保护下整理代码。

模型能否找到原因、是否把猜测当事实，则用固定任务和样本数据反复评估。同一份业务规格同时约束代码和 Agent 行为，接口的单元测试通过，还不能说明整项业务已经能正确完成。

OpenAI 的《Harness Engineering》描述过类似的研发分工：工程师明确意图、整理仓库知识、搭建反馈环境，让 Agent 能看到应用、日志和检查结果。[1] 放到这个原型里，就是让 Coding Agent 改完接口以后，能够运行样本、打开页面，看到"证据编号没有显示"这样的实际问题，再继续修。

仓库里可以保留一份短的 `AGENTS.md`，指向业务规格、接口约定和测试入口。业务规则有变化，就修改对应规格和样本；代码实现随后跟进。后续开发从仓库里读取同一份约定，减少反复解释和口径变化。

接入顺序可以按依赖推进：先用样本跑通调查，再替换成测试环境里的真实只读接口，核对返回语义，最后接写操作。**模拟接口跑通，证明的是这条程序路径能工作；真实系统的权限、数据延迟和错误返回，还要在接入时逐项验证。**

原型做到这里，最容易暴露的往往是业务含义：同一个字段，在两个系统里可能根本不是一回事。

## Ontology：业务建模

比如采购系统里的"已完成"，可能指采购流程结束；仓储系统里的"已完成"，可能指货物收齐。把两个字段都映射成 `completed`，模型看到的反而更模糊了。

Ontology 在这里要解决的是：**系统里有哪些业务对象，它们怎样关联，哪些状态和动作对这项任务有意义。**

Palantir 的官方定义把 Ontology 放在已有数据资产之上，同时包含对象、属性、关系，以及动作、函数和动态安全机制。[2] 这是其产品的具体实现。借鉴到自己的系统，可以先围绕发票任务整理一份小范围的业务模型，不必一开始覆盖整个企业。

对象

第一版需要说清的内容

发票

所属法人、供应商、金额与币种、有效状态、关联采购单

采购单

明细、数量、计价口径、变更版本

收货记录

对应采购明细、实收数量、确认状态与时间

审批记录

批准的申请内容、当前状态、适用版本

付款申请

业务编号、关联发票、申请金额、处理状态

这些对象通过稳定编号关联。供应商名称可以用来检索候选，真正执行动作时，还要落到主数据标识及其系统映射上。两个名字相似的供应商，不能靠模型觉得"应该是同一家"就合并。

关系也需要具体。发票关联采购单，采购单明细关联收货明细；核对数量时，要知道计量单位是否一致。金额比较要明确含税还是未税、币种是否相同。第一版如果暂不处理换算，就把无法直接比较的情况返回人工确认。

接着，可以用几个业务问题检查业务模型是否够用：这张发票关联哪些单据？当前缺少什么？谁能补齐？补齐以后允许发起哪个动作？每个问题都能沿对象、关系和规则找到答案，才说明这份模型确实服务于任务。

AI 可以根据接口文档提出对象、字段映射和规则草案，业务负责人再结合样本确认。模型建议"已完成等于可付款"，正好暴露了需要核对的口径；它不能自己批准这条映射。

实现上，这些定义可以先落在数据库视图、带类型的对象结构和领域服务里。需要跨来源交换形式化语义或进行逻辑推理时，再评估 RDF、OWL 等技术。对第一版来说，能沿对象关系找到数据、按明确条件发起动作，已经有了可验证的用途。

这也接续了我们之前 Ontology First 的讨论：RAG 可以查制度和邮件，MCP 可以提供工具接入方式，业务对象模型负责解释编号、关系和动作含义。查到一段"货已送达"的邮件，与查到一条正式收货记录，在这份模型里应当是不同性质的证据。

## 工具：查询与动作

对象关系明确以后，工具就可以围绕"调查这张发票"来设计。

如果直接把采购、仓储、财务的所有接口开放给模型，它得先找供应商，再查采购单，再分页读取收货记录，还要自己拼接字段。这里很多工作其实有确定规则，可以提前放进查询服务。

例如提供 `get_invoice_context(invoice_id)`：在当前用户权限内，读取发票及相关单据，返回本次调查需要的字段、证据编号、各来源的更新时间，以及尚未查明的部分。数据量大时再提供按明细查询的工具，避免一次把所有历史记录都送进上下文。

Anthropic 的工具设计文章专门讨论过这种选择：围绕有价值的工作流设计少量工具，必要时在工具内部组合多次 API 调用，并返回与任务相关的信息；工具数量多，并不天然带来更好的结果。[3]

这个查询工具尤其要分清三种返回：**确实没有记录、当前无权查看、上游查询失败。** 如果超时也返回空数组，模型很容易得出"没有收货"的结论。返回多来源数据时，还要说明哪些查询成功了，哪些尚未完成；它们通常也不构成同一时刻的事务快照。

供应商邮件可以作为线索进入结果，但其中夹带的指令不能改变工具权限或审批规则。执行身份从服务端认证上下文取得，模型传入的用户编号不能直接决定"以谁的权限办事"。

写操作则围绕明确的业务意图设计，例如 `create_payment_request`。下面是这个例子的接口约定，字段名称仅作示意：

```
模型提出：发票编号、申请金额与币种、申请依据执行层补充：已认证身份、稳定操作标识、待核验的版本业务服务校验：权限、单据有效性、金额规则、适用审批成功返回：申请编号、实际金额与币种、当前状态其他返回：条件变化、无权限、业务拒绝、结果待确认
```

模型可以建议申请金额，业务服务仍按自己的规则验证。审批、版本和操作标识也由执行层核对或生成，不能因为模型在参数中写了"已批准"就成立。

Palantir 的 Action types 同样把参数、修改规则、提交条件和副作用纳入动作定义。[4] 其中 Ontology 内的事务语义，不能直接外推为多个外部系统的原子提交；自己的财务接口有什么保证，仍要单独确认。

到这里，业务对象已经变成 Agent 可以使用的查询与动作接口。接下来回到架构图中间，看看 Harness 怎样组织这些调用，以及一轮执行结束后谁来继续跟进。

## Harness：组织执行

一次调查可以从一个简单循环开始：读取任务和必要上下文，调用模型；模型请求工具后，由程序校验并执行，把结果交回模型；直到形成调查结论、需要人工补充，或达到本轮预算。

Harness 就是支撑这段工作的外围程序，负责组织输入、模型调用、工具执行和结果处理。Harrison Chase 在 X 长文里把业务逻辑、Harness 和运行基础设施分开讨论，并将执行中断后的恢复列为生产问题。[5]

Runtime 更偏向运行支撑：执行器在哪里启动，运行状态怎样保存，进程退出后如何重新调度，需要代码执行时怎样提供隔离环境。不同框架对 Harness 和 Runtime 的命名、覆盖范围并不一致。放到本文方案中，Harness 组织当前这一轮；持久存储与调度支撑后续执行，业务任务流程则定义什么时候等待、什么时候继续、什么时候结束。

第一版可以保留一个调查 Agent，配一组查询工具和受控动作。组件之间传任务编号、单据编号和结构化结果，页面展示解释与进度。已有工作流、数据库和执行器能够承接的部分，可以直接复用，不必为了这几个名字各建一个平台。

这套分工也决定了上下文怎样准备。每轮带上任务目标、当前阶段、有效规则和相关证据；完整单据、长邮件和历史工具日志按需读取。分析摘要保留"缺少哪条证据、上次为何停下"，外部状态则重新查询，避免昨天的收货数量成为今天的默认事实。

模型版本、提示词版本、工具版本、本轮耗时和退出原因，可以随运行记录保存。查一次失败时，才能分清是调查策略变了、工具返回变了，还是上游接口不可用。日志里的任务标识还可以把模型调用和业务请求串起来。

停止条件也放进 Harness：最大工具调用次数、本轮时间和费用预算、连续无进展的次数。到了限制，就保存已有证据和未完成项，把任务交回流程。需要等仓库一天，就登记等待条件，结束这轮执行。

这里与研发中的 Harness Engineering 有相通之处：都要让 Agent 获得可用的工具、上下文和反馈。但研发 Harness 面向代码仓库、测试、PR；线上业务 Agent 的 Harness 面向发票、权限、业务动作。两套环境的凭证和可执行操作各自配置。

任务扩大以后，再看是否需要多 Agent。如果合同条款和往来邮件都很长，需要不同工具、独立上下文，而且能够分别调查，就可以拆成子任务；只是同时查三个确定的接口，普通程序并发调用已经够用。

拆开以后，还要约定怎么汇总。每个子任务带着同一张发票的业务编号，返回结论、证据、来源时间和未查明项。由主 Agent 或任务流程汇总；证据冲突就补查或交给人工，子任务失败则明确哪些结论还缺依据。正式写操作仍经统一入口执行。这样做增加了调用、等待和协调成本，可以用同一组任务比较，确认确实改善了调查质量或耗时，再保留这种拆分。

## 等待与恢复

假设调查结果是：当前收货记录不足，供应商邮件称已送达，需要仓库核实。系统创建待办，保存负责人、关联单据和下次检查时间，然后等待。

这时有三种记录，各自回答不同问题：

记录

负责说明什么

业务事实

实际收了多少货、审批是否有效，以负责该业务的系统为准

任务进度

正在等谁、下一次何时检查、哪个动作结果尚未确认

分析记录

当时查过什么、依据是什么、给出过什么建议

它们可以放在已有平台中，通过编号关联，无需因此新建三个服务。聊天里写过"已通知仓库"，仍要有实际待办编号，下一轮才知道去哪里查。

图 2：发票任务的等待与恢复（图中是顺利推进的主路径。收到变化通知后重读业务记录；遇到证据冲突或提交结果不明，进入相应处理分支。）

仓库第二天补录，事件唤醒任务；没有事件接口，也可以定时查询。恢复时先重新读取收货、采购单和申请状态。如果只是数量补齐，程序可以重新核对条件；如果采购金额也变了，再把变化和原调查交给 Agent 分析。**重查事实是恢复的起点，是否重新推理，要看发生了什么变化。**

LangGraph 可以用 checkpointer 保存图状态，生产环境配合持久存储。[6] 如果公司已有工作流系统管理这项业务，就让 Agent 作为其中一个步骤；如果由 LangGraph 管理整个任务，则由它承接等待和恢复。同一项业务进度要有明确的负责方。

接入时有个具体细节：LangGraph 从 `interrupt()` 恢复，会从所在节点开头重新执行。[7] 把"创建待办"和"等待人工"塞进一个节点，恢复时就可能再建一次待办。可以拆开步骤、保存编号，同时让创建操作本身支持重复调用。

外部审批也不能靠恢复消息替代。LangGraph 官方文档明确说明，图外审批应重新查询外部任务状态。人的一句"好了"可以触发检查，正式审批结果仍从业务系统取得。

事件重复或迟到时，按事件编号去重，再核对当前任务阶段和记录版本。任务已经完成，就不因一条旧通知退回等待。再用定时核对补漏，既不要求事件绝不丢失，也不让模型一直空转。

## 幂等与结果确认

材料和审批都满足条件，系统准备创建付款申请。提交时，业务服务再次检查权限、相关版本和有效审批；对自己管理的数据，用条件写入或事务把校验与创建关联起来，防止查询通过后条件又发生变化。跨系统的事实仍受各自接口约束，需要约定版本、有效期或再次确认方式，不能把一次预查询当成所有系统的共同锁定。

假设请求超时了。申请可能没创建，也可能已创建、只是响应没回来。任务先进入"结果待确认"，沿这次操作的标识查询，不能直接改成失败后再发一份新申请。

AWS Builders' Library 的幂等 API 文章讨论过这种情况：调用方用稳定的请求标识表达同一次意图，服务端识别重试，并返回语义等价的结果。[8] 用在这里，同一次申请的重试沿用原标识，关键参数保持一致。

接收方还要真正实现去重：约定标识的作用范围、保留期限，以及相同标识却携带不同参数时如何拒绝。去重记录与业务写入如何保持一致，也属于服务端的实现责任。在请求里多放一个 UUID，本身没有这些效果。

申请内容如果变了，先查清旧请求的结果，再按业务规则变更或撤销；不能换个标识绕过一笔尚未确认的申请。旧接口没有可靠查询和去重能力时，可以先把这类写操作留给人工确认，同时推进业务服务改造。

财务系统返回申请编号后，还要核对关联发票、金额和币种，再将结果写回任务。进程恰好在写回前退出，恢复后仍按原操作标识查询。回退本地 checkpoint，也不会自动撤销远端申请，撤销要调用对应业务流程。

用户最终看到的应该是具体进展："付款申请已创建，编号为……，当前处于……状态。"模型可以补充原因解释，完成状态来自业务回执；申请创建之后的审批、支付或到账，继续按该企业的实际流程跟进。

## 评估与回归

前面的三个原型样本，只覆盖了正常匹配和两类异常。接入等待、审批和写操作以后，评估也要跟着扩展：除了原因找得对不对，还得检查恢复后有没有用旧数据、提交时会不会多建一笔申请。

Anthropic 的 Agent 评估文章区分了运行记录与环境中的最终结果：Agent 说预订好了，不代表数据库里已经有有效预订。[9] Chip Huyen 也把规划失败、工具失败和效率分别讨论，提醒过 Agent 自以为完成、实际没有完成的情况。[10]

单据关联、状态转换、权限和幂等，主要由确定性测试及故障注入验证；原因解释是否准确、证据是否充分，则结合业务人员标注和模型评估。模型评审可以帮助检查表述，数据库中有没有重复申请，直接查系统结果更合适。

每个样本需要固定输入、初始数据和成功条件，运行之间恢复测试数据。模型行为存在波动，同一任务可以重复运行，保留每次的工具轨迹与结果。评估关注的是是否正确完成及是否遵守约束，不必强求每次使用完全相同的查询顺序。

开发时用于改提示词和工具的样本，与最终检查的留出样本分开。已经稳定的能力纳入回归；换模型、改工具描述、更新业务规则以后，都用同一组任务比较。人工抽查再补上自动评分看不出的业务含义。

现场反馈也会改变样本和实现。比如业务人员指出："收货已经补录，只是同步要等一段时间。"这条反馈对应的改动可能是增加来源更新时间、调整查询位置和等待策略，而不只是让模型"再仔细看看"。

另一个例子是同一家供应商在两个系统里有不同编号。解决办法可能是完善供应商编号映射，并补一个关联测试。接口错误被包装成空结果，就改工具返回；审批含义理解错了，就改业务规则及说明。这些改动连同回归样本留在项目中，下一次交付才不用重新口头解释。

## FDE：现场交付

如果已有采购、仓储、审批和财务系统，第一版可以复用它们的事实记录和动作接口。新增部分先保持小：一个业务适配模块、一组 Agent 工具、一个调查 Agent，以及持久化的任务流程。部署可以从一个服务和一个数据库起步，模型调用和已有业务系统通过接口连接。

交付顺序也可以逐步推进。先只读调查，让业务人员比较原因和证据；再用影子运行生成处理建议，由原流程照常办理，核对双方差异。这个阶段关闭真实写操作，避免"影子"任务也创建单据。

调查稳定以后，开放经过人工确认的写操作。系统按前面约定核验正式审批和请求内容，再提交；随后只对规则明确、评估充分的一类任务扩大自动化。每次扩大范围，都要有对应样本和可退回人工的路径。

现场工作还包括明确人工接手方式：页面展示阻塞原因和已取得的证据，允许有权限的人暂停、接管或取消后续任务。已经发出的业务请求仍要核对结果，点击取消不能让在途申请凭空消失。

模型、提示词或工具版本更新后，可以先在小范围任务中启用，和原版本比较。发现异常时，先停止新增自动写操作，把未完成任务交回人工，再处理版本回退；已经提交的申请继续核对结果。恢复程序版本与撤销业务动作，需要分别处理。

这时值得观察的，除了模型回答是否正确，还有一笔异常的处理时长、人工接手次数、重复或无效操作，以及完成一项任务的调用成本。若时间主要耗在等仓库补录，先改善待办分派和恢复时机，往往比继续缩短一次模型响应更有用。

交接给维护团队时，留下的也应当是能够继续使用的材料：业务范围和例外、对象与动作约定、接口及权限配置、任务状态和人工接手方式、评估样本与运行入口。客户特有的编号映射、审批规则和系统地址可以单独配置；已经在多处验证过的通用能力，再提取复用。

第一版先让一张发票从卡住走到申请创建，并能解释每一步依据。后面扩大到更多业务时，究竟该补对象关系、改工具、增加并行调查，还是改善人工协作，就有实际记录可供判断了。
