# 链表已死？C++ 之父：O(1) 不一定比 O(N) 快

> 来源：https://mp.weixin.qq.com/s/M-FKnd1kvdwvRtRNdsDK6g
> 抓取时间：2026-10-21（web-fetch，browser 级）

知乎上一个问题引发热议，实测数据反直觉、和教科书"过时内容"相违背。网上大致分成三派：

- **链表已死派**：在性能敏感的代码里，链表几乎永远是最差选择；
- **输给数组派**：链表没死，但在大多数场景下确实输给了数组；
- **退居幕后派**：链表没死，但它已经从舞台中央退到了幕后。

早在十多年前，国外顶级程序员就为此"打过架"，C++ 之父 Stroustrup 甚至专门写了一篇短文回应：《Are lists evil?》。

## 链表也曾是主角

大学里学过的结论：数组查询快，链表插入快。数组中间插入是 O(n)，链表是 O(1)。大 O 记号一摆，链表赢得干净利落。

但这个结论有一个**隐藏前提**：它假设"访问内存"是免费的，成本只算"基本操作次数"。问题就在于现代计算机恰恰不是这么算账的。

## 内存墙与缓存

过去几十年，CPU 运算速度指数级上涨，而内存（DRAM）延迟改善极慢，形成所谓"内存墙"（Memory Wall）。如今桌面级 CPU 访问 L1 缓存只要几个时钟周期，访问一次主内存可能要多付出上百个周期的等待。

现代 CPU 用两个关键机制弥合鸿沟：

1. **缓存行预取**：CPU 从不按字节取数据，而是按 64 字节左右的缓存行整块加载。你访问了一个 int，它隔壁的 int 也顺带进了缓存；
2. **硬件预取器**：如果发现访问地址线性递增，CPU 会提前把后面的数据也搬进缓存。

这引出著名的**局部性原理（Locality）**：空间上相邻、时间上相近被访问的数据，才是现代 CPU 的"宠儿"。现代 CPU 的性能，极大程度上取决于数据离核心有多近，Cache Miss 正是由于要访问的数据太远。

而链表恰好把这两条全踩中了：

- 节点分散在堆内存各处，每跳一次指针都可能是一次缓存未命中；
- 遍历时"先读到指针，才知道下一个节点在哪"，硬件预取器对这种随机跳转完全无能为力——专业术语叫 pointer chasing（指针追逐）。

数组的"插入要搬移元素"听着很贵，但 memcpy 是连续的、预取友好的，实际快得惊人；链表的"插入只改指针"听着很便宜，但找到插入位置的那一路指针跳跃，可能已经吃了上百次缓存未命中。

> 大 O 说链表赢，CPU 缓存说链表输。而裁判永远是跑出来的真实时间。

## 老外们的"判决书"

**C++ 之父 Bjarne Stroustrup** 在 2012 年 Going Native 大会 Keynote 中用了经典实验（Jon Bentley 出的题）：把随机整数按序插入一个序列，再按随机位置逐一删除，用链表还是数组？

结果反直觉：`std::list` 完败于 `std::vector`，哪怕操作序列表面上全是"链表擅长"的插入删除。

这个实验后来被断章取义成"Stroustrup 说链表是邪恶的"，他不得不在 isocpp.org 发文澄清：

> 我的重点根本不在链表本身。链表有它的用途，但这个例子不属于那些用途。请注意我的结论里既没有出现 list 也没有出现 vector。
>
> - don't store data unnecessarily（不存储不必要的数据）
> - keep data compact（让数据保持紧凑）
> - access memory in a predictable manner（以可预测的方式访问内存）
>
> 我强调缓存效应的重要性。我的经验是，除了真正的专家，几乎所有人在讨论算法时都会忘记这一点。

结尾补刀：我的建议是**默认使用 std::vector**。除非有充分的理由，否则使用连续内存的表示方式，C 和 C++ 就是被设计成默认这样工作的。

**Chandler Carruth**（Google LLVM 技术负责人、C++ 委员会核心成员）在 CppCon 2014《Efficiency with Algorithms, Performance with Data Structures》里态度更激烈：

> Discontiguous data structures are the root of all evil.（非连续的数据结构是万恶之源。）
>
> Please say no to linked lists. There is almost nothing more harmful you can do to the performance of an actual modern microprocessor than to use a linked list data structure.

这场演讲堪称"链表已死论"的源头之一。

## 社区实测，输得有多惨？

- 复现 Stroustrup 实验：list 直到**元素体积 1KB 以上、数量超过一万**时才开始在某些场景反超 vector——此时 vector 搬移成本才真正超过指针追逐成本。
- buddy 内存分配器教学项目：同样分配逻辑，`std::vector` 分配 1 GiB 约两分钟，换 `std::list` **慢到二十五分钟，相差十二倍以上**。
- 高性能 C++ 圈的"编程正确"：如果你在用 `std::list`，八成用错了；99% 的场合该用 `std::deque` 或 `std::vector`。

## 链表真的死了吗？

Stroustrup 本人坚决反对"链表邪恶论"的极端版本："Obviously, that's absurd"。**链表从未死去，它只是换了个活法。**

### 链表无处不在

Linux 内核源码里 `list_head` 侵入式双向链表随处可见：进程调度队列、内存管理、文件系统、定时器……几乎每一个子系统都在用。

内核偏爱链表的原因：

- 节点生命周期由外部对象（进程、页框、inode）决定，**不允许拷贝**，数组式"整体搬移"根本不可行；
- 要求 O(1) 摘除任意节点——一个进程随时可能被 kill，一个页框随时可能被回收；
- 这时链表节点里那 16 字节的前驱后继指针不是负担，而是**嵌入在对象身上的钩子**。

Stroustrup 在 FAQ 里也承认侵入式链表可以非常快，但"a vector is more compact and is therefore smaller and faster in many cases — even when you do inserts and erases"，前提是"你真的需要一个 list"。内核里这个前提成立了。

### 链表依然有用

- 元素体积超 1KB、数量巨大时，vector 搬移成本让链表翻身。游戏引擎、物理引擎的场景图、粒子系统处理的都是大块头对象，链表（或其定制结构）依然是常客——**大对象 + 插入删除密集，链表依然能反杀**。
- 2025 年一篇 arXiv 论文在真实 CPU 缓存层级下对比容器性能，发现"大量摊还 O(1) 插入、极少遍历"模式下，把 `std::list` 换成 `std::vector` 反而让整体运行时间**增加 30% 以上**——链表是真 O(1) 指针操作，vector 搬移在这个模式下成了主导成本。

大 O 分析没有骗人，只是它只在"内存访问成本可以忽略"的模式下才接近真相。

### 链表的新形态

链表的思想活在大量现代数据结构中：

- **跳表（Skip List）**：Redis 有序集合的核心实现，用多层链表换来 O(log n)；
- **B 树 / B+ 树**：数据库索引底层，节点 fanout 拉满，兼具块局部性与 O(log n)；
- **plf::colony、unrolled linked list（分组链表）**：多个元素塞进一个节点，减少指针追逐，是游戏业对链表的"现代化改造"；
- **LRU 缓存**：哈希表 + 双向链表的黄金组合，O(1) 定位 + O(1) 摘除，至今是工业标准答案。

这些结构继承了链表的"逻辑灵活性"，又用工程手段弥补了它的"物理局部性"。Chandler Carruth 在 CppCon 2016 姊妹篇讲的正是这种"混合数据结构"（Hybrid Data Structures）设计哲学。

## 最后

三派观点各自对了一半：

- **链表已死**：对应用层业务代码成立。写 CRUD、遍历多于增删、元素不大的场景，无脑选数组（或 deque）几乎总是对的。
- **链表输给数组**：对性能敏感场景成立。访问模式确定、数据量上得去后，缓存命中率就是生命线，连续内存就是王道。
- **链表退到幕后**：对系统全貌成立。内核、内存分配器、编译器、游戏引擎、数据库深处，链表及其变体依然优雅运转——不再是课堂明星，却是支撑软件世界的"幕后工作者"。

从来不是"链表 vs 数组"谁赢谁输，而是它给所有程序员上了一课：**算法复杂度分析之外，还有一门课叫"计算机体系结构"；大 O 记号之上，还站着缓存行、预取器和内存墙**。不要盲目相信 O(1) 一定比 O(N) 快。
