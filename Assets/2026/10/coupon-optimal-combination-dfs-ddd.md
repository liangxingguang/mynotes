大促复盘时，下单预优惠计算侧暴露过一个隐蔽但影响面不小的问题。早期优惠券直接走贪心逻辑，优先选取面额最高的券叠加。灰度放量之后，客诉陆续涌进来：用户手里明明有多张券，系统算出的实付金额并非全局最优。

尝试暴力枚举之后很快放弃。用户持券量一旦上去，叠加互斥、商品隔离、门槛、优先级、赠品约束，组合空间指数膨胀，随便上万条分支，预优惠计算链路直接超时。

这是电商营销体系里非常典型的行业通病：团队往往卡在两个极端。要么持续使用贪心方案，接受次优结果，长期承担用户投诉；要么把券的叠加、互斥规则硬编码到业务逻辑中，运营调整一条规则就要改代码、走发布流程，营销迭代节奏完全被研发锁死。

我们最终落地的方案，核心本质不是一道算法题，而是一套面向复杂约束的控制面设计：用领域模型收敛多变的业务规则，规则引擎和求解算法做职责隔离，有界 DFS 回溯配合多层剪枝在约束空间内寻优，再叠加降级与一致性兜底守住预计算链路红线。所有设计，都要权衡收益、开发代价与运维成本。

## 一、底层矛盾：贪心与 DP 方案的固有边界

贪心的短板，根源在局部决策。它只评估单张券的优惠收益，看不到组合之后的全局收益。

> 线上真实案例：订单金额 200 元。 
> 
> 券 A：满 200 减 50，店铺券； 
> 
> 券 B、券 C：两张满 100 减 30，同品类可互相叠加，和券 A 互斥。 
> 
> 贪心优先选中面额更大的券 A，优惠 50；而 B+C 组合优惠 60，才是全局最优。 
> 
> 这个缺陷不是参数调优能修复的，是策略本身的边界。

那多维背包 DP 为什么不适合这个场景？

DP 适合维度固定、约束单一的收益求解。优惠券的约束是异构的：互斥分组、商品作用域、准入门槛、叠加上限、优先级、赠品附属约束混杂在一起。每新增一类约束，状态空间成倍扩张，线上根本无法承载内存与计算开销。

场景的核心诉求很清晰：在异构业务约束下求解最小实付组合；同时营销规则高频变更，不能和寻优算法耦合。这就决定了，我们需要一套**规则控制面 + 寻优计算面**分离的架构。DDD 建模，就是这套控制面的载体。

## 二、DDD 领域建模：把口头规则收敛为可计算的领域契约

这里不谈 DDD 基础概念。建模的目标只有一个：把散落在产品文档、运营口头沟通里的优惠规则，固化成统一的领域契约，供给规则引擎消费，避免逻辑碎片化、if-else 无限堆积。

优惠券聚合模型，条件、权益、约束值对象抽象，支撑规则引擎配置

我们抽象两大聚合，配套值对象承载规则语义：

**优惠券模板聚合**，属于配置态静态实体。

*   Condition 值对象：承载准入约束，订单门槛、用户人群、商品范围、时效窗口；
    
*   Benefit 值对象：优惠权益，区分金额型（直减、折扣）、赠品类，赠品不参与金额计算，但会引入独立约束；
    
*   Constraint 值对象，是整个控制面的核心：互斥组标识、跨组叠加开关、单订单可用上限、优惠计算优先级。
    

**用户券实例聚合**，属于运行时实体。用户领券后生成，绑定用户、模板、核销状态、生命周期。

基于聚合边界，落地六张表，每张表都有明确的领域职责，没有冗余：`coupon_template`：存储模板与整套约束契约，规则引擎的配置源；

`coupon_exclude_group`：维护互斥分组关系，是组合约束的基石；

`coupon_activity`：营销活动聚合，管控发券库存、投放渠道、活动周期；

`coupon_user`：券实例存储，预优惠寻优的候选输入源；

`coupon_use_log`：核销流水，用于对账、反作弊、链路审计；

`coupon_combination_snap`：优惠快照。很多人误把它当成缓存组件，它的核心价值是**订单预优惠结果的一致性锚点**。提交订单瞬间固化优惠结果，隔离下单过程中券被其他请求核销、状态变更带来的计算漂移；提速只是附加收益。

限界上下文做三层拆分，从源头防止域污染： 

模板配置域：模板、互斥组、活动配置管理； 

用户券钱包域：领发、状态流转、券实例查询； 

优惠计算引擎域：规则过滤、寻优求解、快照落地、稳定性管控

域之间依靠领域事件 + RPC 同步变更，模板、互斥关系更新后，事件驱动引擎本地缓存刷新，减少重复查询压力。边界划分的红线：营销配置变更，不能侵入计算域的寻优逻辑。

## 三、分层架构：规则控制面与算法计算面解耦

分层的核心取舍：业务约束收敛在规则引擎，算法只负责在合法空间内搜索，双向互不侵入。

1.  模型层：统一领域对象契约，所有输入输出遵循同一套语义；
    
2.  规则引擎层，承担两层职责：前置过滤 + 路径约束校验。 先做候选集裁剪，过期、门槛不满足、商品范围不匹配、已核销的券直接剔除，减少进入递归的基数。 DFS 每尝试纳入一张券、形成临时组合时，引擎实时校验约束：同互斥组排他、叠加权限、张数上限、计算优先级。这套机制带来最大收益：运营调整门槛、互斥关系、叠加策略，只改配置，寻优代码一行不动。这就是控制面的价值，规则变更不需要修改计算逻辑。
    

用户券→规则引擎前置过滤→分组剪枝→DFS 回溯求解→快照缓存 & 降级

3.  算法层：有界 DFS 回溯 + 四层剪枝。目标是合法空间内寻优，拒绝无差别穷举。
    

> 注意：这套回溯与剪枝只是计算面实现，整套方案的稳定性根源，在于前面 DDD 建模收敛出来的约束契约。

> 核心寻优伪代码（工程简化版，保留主干逻辑，剔除框架胶水代码）

```
// 全局上下文，单次求解隔离class SearchContext {    OrderDTO order;    List<Coupon> candidates;    Map<Long, Integer> groupBitMap; // 互斥组Id -> bit下标映射，下标严格小于64    long excludeMask;          // BitMask 互斥标记    BigDecimal bestFinalPay;   // 当前最优实付    List<Coupon> bestCombo;    // 最优券组合    int maxIter = 5000;        // 搜索节点访问上限，压测后确定的业务水位，防止算力击穿    int iterCnt = 0;}// 回溯入口void dfs(SearchContext ctx, int idx, List<Coupon> currentCombo, long mask) {    // 兜底熔断：达到搜索节点上限直接返回    if(ctx.iterCnt++ >= ctx.maxIter) return;    // 递归终止：遍历完所有候选券    if(idx >= ctx.candidates.size()) {        BigDecimal pay = calcPay(ctx.order, currentCombo);        if(pay.compareTo(ctx.bestFinalPay) < 0) {            ctx.bestFinalPay = pay;            ctx.bestCombo = new ArrayList<>(currentCombo);        }        return;    }    Coupon curr = ctx.candidates.get(idx);    // 分支定界估算理论下界：就算剩下所有券全部选上，能不能优于当前最优    BigDecimal lowerBound = estimateLowerBound(ctx.order, currentCombo, ctx.candidates.subList(idx, ctx.candidates.size()));    if(lowerBound.compareTo(ctx.bestFinalPay) >= 0) {        return; // 剪枝：没有优化空间，直接返回    }    // 分支1：不选当前券，直接下一个    dfs(ctx, idx + 1, currentCombo, mask);    // 分支2：尝试选中当前券，规则引擎校验约束    if(ruleEngine.check(ctx.order, currentCombo, curr, mask)) {        int bitIndex = ctx.groupBitMap.get(curr.excludeGroupId);        long newMask = mask | (1L << bitIndex);        currentCombo.add(curr);        dfs(ctx, idx + 1, currentCombo, newMask);        currentCombo.remove(currentCombo.size()-1);    }}
```

注：禁止直接使用业务自增 groupId 作为 bit 偏移；需要预先维护 groupId 到 bit 下标的映射，规避 long 类型 64 位溢出问题。 伪代码只展示主干搜索逻辑，实际工程上，规则引擎`ruleEngine.check`内部会封装：门槛校验、商品范围、叠加上限、赠品约束校验；`estimateLowerBound`就是门槛剪枝 + 收益下界的实现。

### 四层剪枝体系（逐层压缩搜索空间，按收益优先级排序）

四层剪枝链路，逐层压缩搜索空间，控制预优惠计算耗时在 200ms 内

1.  **预处理剪枝，投入产出最高**支配剪枝：同一互斥组内，A 券门槛更低、优惠更高，完全支配 B 券，B 券直接剔除； 连通域拆分：当券绑定的商品集合互不相交、且券不支持跨商品组抵扣时，可以拆成独立子集分开求解，大问题拆成多个互不干扰的小问题。通用全店券场景，该拆分策略失效； 分组降维：以互斥组为单元，每组至多选择一张。组合规模从 2^N，退化至各组可选数量乘积，搜索空间断崖收缩。
    
2.  **排序剪枝**候选券按优惠收益降序排列。优先探索高收益分支，尽早拿到一个较优全局解，为后续分支定界提供基准，提前砍掉大量无效路径。
    
3.  **门槛剪枝**递归路径中持续评估：剩余订单基数，已经无法满足该路径下所有未选券的准入门槛。该分支不可能产出更优解，直接回溯终止。
    
4.  **分支定界剪枝，线上核心优化点**持续维护全局最优实付。对当前分支做理论下界估算：就算把这条路径剩余所有可叠加券全部用上，能拿到的最低实付金额。 如果这个理论下界，大于等于当前最优值，这条分支不存在优化空间，直接剪枝，停止递归。
    

### 互斥校验：BitMask 位图方案

每个互斥组映射一个 bit 位。选中券时置位，后续选券通过位运算判定冲突，O (1) 完成互斥校验，替代循环遍历。 这里有一条落地红线：位图存在容量上限，不适合无限拆分细粒度互斥组。分组膨胀后，需要降级为 HashSet 校验，两套实现按需切换。

## 四、稳定性兜底：预优惠计算链路不可妥协的工程红线

寻优算法本身天然存在算力不确定性，预优惠计算属于下单核心前置链路，不能把业务可用性绑定在算法输出上，必须建立完整的防护体系。

*   硬上限管控：设置递归深度、最大搜索节点阈值，我们线上阈值 5000 组；
    
*   超时熔断：超过预设耗时（200ms）直接终止递归；
    
*   策略降级：触发上限或者超时，放弃最优解，平滑切回经过长期验证的贪心方案，优先保证下单可用；降级回退贪心方案前，业务侧必须兼容优惠金额变动，避免订单金额二次校验拦截，引发下单失败；
    
*   可观测埋点：候选券数量、各层剪枝命中计数、搜索节点遍历量、降级触发次数、单次耗时，全部纳入监控看板。降级量突增，就是预警信号：券规则或者用户持券规模，已经超出预设水位；
    
*   请求幂等：预计算请求携带唯一流水号，避免重复调用带来重复计算、快照重复写入。
    

完整链路复盘： 订单 + 用户请求入参 → 查询用户券实例 → 规则引擎前置过滤 → 预处理剪枝、连通域拆分、分组收敛 → 有界 DFS 回溯，规则引擎实时校验约束、四层剪枝收缩分支 → 产出最优组合，写入快照返回 → 超限、超时自动降级至贪心策略。

## 五、落地评审要点与线上踩坑复盘

这套方案经过多轮架构评审、大促压测、灰度放量，很多风险点在文档设计阶段很难预判，属于只有上线之后才会暴露的隐性代价，整理成评审自检清单。同时，项目复盘、技术交流、口述分享，都可以直接复用这套真实落地素材。

1.  **赠品券与金额券混算，极易出现目标冲突**
    

> 故障案例：一次美妆大促，赠品小样券和满减券混排。原始逻辑只算金额最优，选出的组合满足实付最低，但两张赠品券属于互斥赠品活动，提交订单后履约直接报错。 我们的取舍方案：主优化目标维持实付金额最小，赠品约束后置做硬校验；赠品存在互斥关系时，纳入 Constraint 做二级约束，不并入主搜索目标，避免搜索空间二次爆炸。不追求单轮搜索解决所有目标，多目标拆分是控制复杂度的关键。

2.  **快照生命周期极易被忽略，引发存储膨胀**多数方案只关注快照的一致性作用，缺少清理策略。未支付、取消、超时关闭订单的快照永久留存，大促短时间内就会堆积海量无效数据。 落地策略：快照绑定订单状态，设置 TTL 自动过期；对账周期之外的历史快照异步归档清理，冷热分离。一致性和存储成本，需要做权衡。
    
3.  **灰度放量节奏不能激进**寻优方案 CPU 开销显著高于贪心，不能一刀切全量上线。 落地方式：按用户灰度，双链路并行比对，持续观测最优解与贪心结果的差异率、耗时、降级率。差异稳定、降级水位可控，再逐步放量。灰度不是简单的流量切分，是两套策略风险对冲。
    
4.  **剪枝逻辑的规则变更，需要回归评审**支配剪枝、连通域拆分的判定逻辑，本质是业务规则。运营新增特殊券类型时，很容易击穿原有剪枝假设。 红线：新增券品类、新增约束类型，必须回归架构评审，校验是否会破坏现有剪枝前置假设，不能直接上线。
    

小结：算法正确性只是基础门槛。工程落地真正的难点，从来不在 DFS 递归、剪枝公式本身；而在约束语义管控、数据生命周期、观测体系、灰度对冲这些配套控制面能力上。

## 六、架构取舍与场景边界

任何方案都有适用边界，架构师核心能力，就是识别场景、拒绝过度设计。

> **适合落地场景**  
> 商城大促场景，用户持券量中等，互斥叠加规则复杂，用户对优惠结果敏感，客诉代价高；

> **不适合落地场景**  
> 券量少、规则简单，贪心足够稳定；极致低延迟链路、无分组约束的海量券场景，这套方案维护成本过高，收益无法覆盖代价。

很多研发容易陷入一个误区，盲目追逐算法最优解。架构决策的本质，永远不是选用能力最强的方案，而是在业务诉求、研发成本、线上稳定性之间找到平衡点。
