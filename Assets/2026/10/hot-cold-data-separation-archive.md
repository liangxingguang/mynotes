# 微服务架构落地：大表治理与冷热分离——历史单据到底怎么存？

> 大宗商品销采运储系统・六层架构连载（数据持久层）。来源：公众号「架构落地笔记」。

**一句话定调：冷热分离不是为了省磁盘，而是给数据库做"减负手术"——让热数据跑得更快，让冷数据查得到但不碍事。**

## 一、痛点：历史单据如何拖垮系统

大宗商品系统三年后单表几千万~上亿行，80% 是没人查的历史单据，却死死占着磁盘、污染 Buffer Pool：

1. **缓存污染（最致命）**：历史大表导致 InnoDB 内存频繁换入换出，热数据查询从 10ms 飙到 500ms。
2. **索引树变深**：上亿行让 B+ 树从 3 层变 4 层，每次查询多一次磁盘 IO。
3. **备份与 DDL 灾难**：几百 GB 库全量备份几小时；`ALTER TABLE` 锁表几十分钟，业务瘫痪。
4. **合规红线**：交易单据、财务凭证须保留 10~30 年（《会计档案管理办法》），**不能直接 DELETE，只能分离**。

## 二、冷热数据划分标准（不能拍脑袋）

**按时间（最常用）**：

- 热：近 3 个月（高频查询、修改、流转）
- 温：3 个月~1 年（偶尔对账）
- 冷：1 年以上（仅审计、凭证核查）

**按状态（更精准）**：

- 热：状态 = 流转中/待审核/待出库——没走完流程放多久都是热数据
- 冷：状态 = 已完结/已作废/已红冲，且完结时间 > 3 个月

```
冷数据 = (状态 IN ('FINISHED','CANCELLED')) AND (完结时间 < NOW() - 3个月)
```

## 三、三层分级存储架构

1. **热库：MySQL 分库分表**——只留近 3 个月，单表 ≤500 万行保极速响应。
2. **温库：独立归档 MySQL 实例**——3 个月~1 年数据，普通 HDD 即可，容忍延迟。
3. **冷库**：
   - 纯合规不查 → 导出 CSV/Parquet 存 OSS/COS/MINIO，成本极低
   - 偶尔检索（查三年前订单）→ 同步到 **Elasticsearch / ClickHouse**，提供只读接口

## 四、落地实战：平滑归档方案

绝不能写 DELETE 脚本直接删（主从延迟、锁表、误删）。

**步骤 1：归档任务**——调度服务每天凌晨低峰触发（如 cron `0 0 3 * * ?`），核心逻辑**先复制、后删除**。⚠️ 严禁 `DELETE FROM t_order WHERE create_time < ...` 大长事务——主从延迟瞬间飙升甚至拖垮库。

**步骤 2：应用层冷热路由**：

- 方案 A（推荐）：代码层判断——先查热库，查不到再查冷库
- 方案 B：ShardingSphere 时间路由拦截——查询条件 `create_time` 小于 3 个月强制路由到归档数据源

## 五、踩坑与红线

1. **主从延迟急升**：归档太快产生大量 binlog，从库回放跟不上，读请求读到"正在被删的数据"。规范：分批 Batch + 每批 sleep 几十毫秒限制 TPS。
2. **冷数据查询超时**：冷库（ClickHouse/OSS）延迟必然高于 MySQL。规范：冷查询接口加超时控制（如 3 秒）+ 前端 Loading + Sentinel 限流。
3. **跨库统计失真**：数据进冷库后 `SELECT COUNT(*)` 不准。规范：统计报表走数仓（离线 T+1），**严禁业务库跨热冷实时聚合**。

## 六、小结三句话

1. 冷热划分看状态和时间，已完结的尽早挪走。
2. 归档要分批软删除，严禁长事务大 Delete。
3. 热库查不到去冷库查，统计报表走数仓。
