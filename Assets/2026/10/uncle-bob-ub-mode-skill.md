# 《代码整洁之道》作者 Uncle Bob，给 Agent 写了一份开发 Skill

## Uncle Bob 是谁

Robert C. Martin：程序员、作者、讲师。2001 年 2 月与另外 16 位从业者在犹他州 Snowbird 聚会形成《敏捷软件开发宣言》，他是 17 位署名作者之一。TDD 不是他的发明（1999 年他与 Kent Beck 结对编程学习 TDD，Beck 的节奏细到近乎逐行交替：写一小段失败测试，再写刚够通过的实现）；他的影响来自长期整理、讲解和推广这些实践。

**三本书，三个层次：**

- 《Clean Code》（2008，《代码整洁之道》）：命名、函数、错误处理、测试——代码如何组织
- 《The Clean Coder》（2011，《程序员的职业素养》）：估算、说不、可信承诺——开发者如何承担责任
- 《Clean Architecture》（2017，《架构整洁之道》）：职责、边界、依赖方向——系统如何安排依赖（圈数不是硬性要求，重要的是依赖边界而非照抄四层目录）

## 从书里的纪律到 Agent 的 Skill：ub-mode

`unclebob/ub-mode` 首次提交于 2026 年 10 月 26 日凌晨（北京时间），署名 Robert C. Martin。仓库只有 `README.md` 和 `SKILL.md`，README 说明借鉴了 `@poteto` 的部分规则再作精简，配合确定性质量检查工具——不能把每条规则当作他独创。

重点不在"让模型多写代码"，而是：用小步测试和修改推进、关注结构与行为、保留可核查的工作记录。关于 TDD 的一句话值得单独看：

> **如果难以编写诚实有效的测试，不要写一个糟糕的测试。**

测试能否表达需求，比为证明遵守流程而凑测试更重要。

## 质量检查不能只靠 Agent 自己说

README 指向三个独立工具：

- **Crapper**：计算圈复杂度×覆盖率的 CRAP 分数，目标每函数 CRAP < 10
- **Dryer**：找结构相似的重复代码（Skill 要求处理相似度 0.8，但 Dryer 默认阈值 0.82——文件里的数字不等于已执行配置）
- **Mutator**：变异测试，检查测试能否发现代码被改坏
- 另有 `uml-viewer` 查看结构与度量

工具与 Skill 是分开的仓库，复制 SKILL.md 不会自动配好工具环境。判断：先看 Skill 要求的证据能否由项目实际工具产生；指标不能替代需求验收。

## SKILL.md 完整中文译文

```
---
name: ub-mode
description: >
  编写或修改代码时，遵循这套精简后的原则。每次修改都依次遵循：
  先让它能工作，再把它做好，然后遵循实践要求。
  当用户运行 /ub-mode 或要求遵循这套精简原则时使用。
---

# ub-mode
每次接到修改要求，都遵循：
* 先让它能工作。
* 再把它做好。
* 遵循实践要求。

# 先让它能工作
## 懒惰协议
* 一项决策只放在一个地方。
* 交付能解决问题的最小修改。
## 基础思考
* 编写逻辑之前，先把数据结构设计好。
* 优先做能帮助后续所有阶段的事情。
* 如果并发写入者会影响结果，就不要共享状态。
## TDD
* 修改代码之前，先写一个会失败的测试。
* 亲眼确认它因预期的原因失败。
* 用最小的修改让它通过。
* 如果难以编写诚实有效的测试，不要写一个糟糕的测试。
## 从第一性原理重新设计
* 不要把新需求硬接到旧设计上。
* 想一想：如果这个需求从一开始就存在，你会怎样设计？想清楚，再分块交付。
## 质疑前提
* 当两次修复基于同一前提，却都未通过同一道检查时，用一句话写出这个前提，
  并清点哪些参与者承载着这种失衡。
* 移除这一分配。
* 完成上述步骤之前，不要开始下一次修复。
## 先减后加
* 添加任何东西之前，先消除复杂性。
## 以结果为目标执行
* 瞄准一个可以检查的最终状态。
* 如果事先有计划，并且能够撤销，可以允许中间阶段暂时不可用。
## 构建省力工具
* 如果工作不是一眼就能看明白，就构建完成它的工具。
* 先手工完成一个单元，再让工具产出与这个单元一致的结果。
## 架构
### 为领域建模
* 用一种让非法状态无法出现的结构来表达领域。
* 维护领域术语表。
* 如果代码已经清晰，而且修改范围局部，就保留它。
### 边界纪律
* 在数据进入的地方检查它。
* 进入内部之后，信任它。
* 将业务逻辑保留在纯函数中。
### 类型系统纪律
* 让非法值无法被表达。
* 外部数据只解析一次，就在它进入的地方。
* 不要压制编译器的报错。
### 让操作具备幂等性
* 执行两次，或者执行到一半崩溃后再次执行，最终都应得到相同的状态。
### 先分离，再考虑串行访问共享状态
* 如果它们不需要同一个可变对象，就让各自拥有自己的对象。
* 如果确实需要，就只允许一个写入者，并通过结构强制保证这一点。

# 再把它做好
## 修复根本原因
* 复现问题。
* 修复原因。
* 仅仅掩盖崩溃的防护判断，不算修复。
## 将工作按顺序拆成可验证的单元
* 完成一个小单元，并检查它。
* 然后再开始下一个。
## 测试行为，而非实现
* 测试应当像使用者一样调用代码，并检查使用者能够观察到的结果。
* 如果所有函数都不返回任何东西时，这个测试仍会通过，就丢掉它。
## Crapper
* 使用 crapper 工具。
* 通过拆分函数、补充测试，或同时采用两者，让每个函数的 CRAP 分数低于 10。
* 考虑是否值得减少 case 分支。
## Dryer
* 使用 dryer 工具，消除相似度达到 0.8 或以上的重复代码。
## Mutator
* 使用 mutator 工具。
* 覆盖尚未覆盖的代码。
* 杀死存活的变异体。
* 删除死代码。
## 重构
* 固定代码当前的行为。
* 改变结构。
* 证明行为没有改变。

# 实践
## 保留日志
* 记录每项操作，以及采取该操作的原因。
* 完成后报告这份日志。
## 保护上下文窗口
* 保持主线程简短。
* 将大部分内容交给别处处理，保留摘要。
## 清理 Worktree
* 找出可以安全删除的内容，确认仍在使用的内容不依赖它，再回收磁盘空间。
* 尚未提交的工作留待决定。
## 提交与推送
* 经常提交，保持提交小而有序。
* 每次提交都说明原因、改动内容，以及如何验证。
* 最后推送到主线。
```

## 落地建议

落到修复任务上，先问 Agent：这次要改变什么行为、怎样重现旧问题、哪些检查证明修改有效？再查看它是否真的执行了检查，而不是只生成一份看起来完整的报告。

留意提交、推送和清理要求：通用 Skill 放进自己项目时应服从项目约定和当前授权，不能因为文件里写了推送就自动跳过团队审阅流程。

1999 年那次结对编程留下的是对开发步幅和反馈的重视；到了 ub-mode，执行步骤的参与者加入了 Agent，而开发者仍要判断需求、检查证据、承担交付责任。
