# Kafka 消费积压实战：Lag 从 0 飙到百万——扩容、批量、多线程消费的正确姿势

> 来源：https://mp.weixin.qq.com/s/ZvwtpNmW1jPqtnCl1_2QpA

引言

凌晨 02:17，告警群连续炸了三条：

> **\[P0\] consumer-group `order-settle` Lag 突破 200 万，持续增长中** **\[P0\] 对账任务延迟超过 30 分钟阈值** **\[P1\] 下游结算服务 QPS 跌至 0**

值班同事打开 Grafana 一看，曲线是这样的：

```
Lag200万 ┤                                ╱150万 ┤                           ╱100万 ┤                      ╱ 50万 ┤                 ╱  0 ┼━━━━━━━━━━━━━━━━━╯━━━━━━━━━━━━━━▶ 时间      23:00        01:30(上游补数据)  02:17(告警)
```

根因很快定位：上游订单服务 01:30 做了一次**历史数据补发**，把积压的 180 万条订单事件一口气灌进了 Kafka。而消费组 `order-settle` 的处理能力是 **800 条/秒**——进来的速度是处理速度的 4 倍，Lag 只涨不跌。

更要命的是，消费逻辑里每条消息都要同步调用一次下游结算接口（平均 40ms），还套着"拉取一条、处理一条、提交一条"的朴素写法。**消费端不是被消息打垮的，是被自己的串行处理拖垮的。**

那一晚我们用四步把 Lag 从 200 万清到 0，耗时 47 分钟：

1.  **临时扩分区 + 扩消费者**——分区 12 → 24，消费者实例 4 → 24
2.  **批量拉取**——`max.poll.records` 从默认 500 调到 2000，`fetch.min.bytes` 调大
3.  **业务处理异步化**——poll 线程只拉取，扔给 16 线程的 worker 池处理
4.  **定位卡点**——发现其中 3% 的消息走的是"超时重试"分支，单次耗时 2 秒，单独隔离

复盘之后团队达成共识：**消费积压不是 Kafka 的问题，是"生产速度 > 消费速度"的数学问题。所有解法都只在两个方向上做文章——要么提高消费速度，要么临时增加并行度。** 先放结论总表：

| 手段 | 提升幅度 | 生效速度 | 风险 | 适用阶段 |
|---|---|---|---|---|
| 扩分区 + 扩消费者 | 线性（受分区数上限） | 分钟级 | hash 漂移打乱顺序 | 紧急止血 |
| 只扩消费者（不动分区） | 到分区数为止 | 秒级 | 超过分区数的消费者永远空转 | 紧急止血 |
| 批量拉取 | 2-5 倍 | 重启即生效 | 单批处理超时 → rebalance | 常规优化 |
| 处理异步化 | 5-20 倍 | 需改代码 | offset 管理变复杂，丢消息风险 | 常规优化 |
| 定位并隔离慢消息 | 视占比 | 需埋点 | 无 | 长期治理 |

**一句话破题：消费积压的本质是一道算术题——`消费速度 ≥ 生产峰值速度 × 1.5` 才不会积压。Lag 告警响起时，先别急着加机器，先算清楚"卡点到底在拉取、在处理、还是在某几条慢消息"，再决定动哪个旋钮。**

## 一、先搞清楚：Lag 是什么，怎么算出来的

### 1.1 Lag 的定义比你想的复杂

Lag = **分区最新消息位点（Log End Offset） − 消费组已提交位点（Committed Offset）**，所有分区求和：

```
Topic: order-events（3 个分区）
P0:  LEO = 152000   committed = 150000   → lag = 2000
P1:  LEO = 148000   committed = 146000   → lag = 2000
P2:  LEO = 160000   committed = 100000   → lag = 60000  ← 问题分区
总 Lag = 64000
```

**总 Lag 会掩盖单分区倾斜。** 上面这个例子，总 Lag 6.4 万看起来不吓人，但 P2 一个分区就积压了 6 万——很可能是某类 key 全部 hash 到了这个分区，或者负责 P2 的消费者卡住了。看 Lag 一定要**看到分区粒度**，只看总量等于发烧只量额头的平均温度。

### 1.2 查看 Lag 的三板斧

```bash
# ① 命令行：看消费组每个分区的位点
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
    --group order-settle --describe
# 输出重点看三列：
# TOPIC  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
# order-events  2   100000   160000   60000   consumer-1-xxx

# ② 看 Lag 的增长速率（比绝对值更重要）
# 连续执行两次，算 delta：
# Lag 从 200万 → 180万：在追，速度 20万/小时，还要 9 小时追平
# Lag 从 200万 → 220万：越追越多，当前措施无效，立刻升级手段

# ③ Burrow（LinkedIn 开源）做持续监控，HTTP API 直接查
curl http://burrow:8000/v3/kafka/prod/consumer/order-settle/lag
```

经验法则：**Lag 的绝对值决定"要不要处理"，Lag 的增速决定"用什么手段处理"**。绝对值大但增速为负（在追平），可以喝茶看着；增速为正，每一分钟都在恶化，必须立刻动手。

### 1.3 积压的三大根因分类

动手之前先归类，不同根因的解法完全不同：

| 根因 | 特征 | 占比（我们一年的统计） | 解法 |
|---|---|---|---|
| **流量突增** | 生产速率突然翻倍，消费速率不变 | 45% | 扩容 + 异步化，等洪峰过去 |
| **消费变慢** | 生产速率没变，消费速率掉了 | 40% | 定位卡点（下游慢、GC、慢消息） |
| **消费停滞** | Lag 暴涨且 committed offset 完全不动 | 15% | 消费者挂了/rebalance 死循环，先救活 |

第三类最容易误判。committed offset 一动不动，往往不是没有消息可消费，而是**消费者陷入了"处理超时 → 被踢出组 → rebalance → 重新分配 → 又处理超时"的死循环**。判断方法很简单：看消费组日志里是不是每分钟都在刷 `Revoking previously assigned partitions`。如果是，先解决 rebalance 问题（见 FAQ 8.3），扩容纯属白费。

## 二、第一步（止血）：扩分区 + 扩消费者

### 2.1 铁律：消费者有效并发数 ≤ 分区数

这是 Kafka 消费模型最基础、也最常被违反的一条：

```
分区数 = 12，消费者实例 = 4    → 每个消费者负责 3 个分区，全部干活
分区数 = 12，消费者实例 = 12   → 一对一，并行度拉满
分区数 = 12，消费者实例 = 20   → 8 个消费者永远空转，纯浪费
```

**一个分区同一时刻只能被消费组内的一个消费者实例消费**——这是 Kafka 保证分区内有序的代价。所以"加消费者"这个动作的有效性，完全被分区数封顶。

那晚我们的操作顺序：

```bash
# 1. 先看当前分区数
kafka-topics.sh --bootstrap-server kafka:9092 \
    --topic order-events --describe
# PartitionCount: 12

# 2. 消费者只有 4 个实例 → 先扩到 12（不花钱的提升）
kubectl scale deployment order-settle-consumer --replicas=12

# 3. 还不够 → 扩分区到 24，再把消费者扩到 24
kafka-topics.sh --bootstrap-server kafka:9092 \
    --topic order-events --alter --partitions 24
kubectl scale deployment order-settle-consumer --replicas=24
```

### 2.2 扩分区的两个暗坑

**坑一：分区只能加不能减。** `kafka-topics.sh --alter --partitions` 只支持增加。一次扩到 100，以后想缩回来只能重建 Topic。所以紧急扩容时**宁可用消费端的临时手段补，也别一次把分区数扩到离谱**——我们的经验是日常分区数的 2 倍以内。

**坑二：扩分区会打乱已有 key 的分区映射（hash 漂移）。**

```
扩分区前：hash("order-89757") % 12 = 5   → P5
扩分区后：hash("order-89757") % 24 = 17  → P17
同一个订单的消息，老的在 P5 排队，新的进了 P17
两个分区由不同消费者并行处理 → 顺序被打乱
```

如果你的消费逻辑**依赖同一个 key 的消息按序处理**（订单状态机、账户流水），紧急扩分区必须配合以下任一手段：

| 方案 | 做法 | 适用 |
|---|---|---|
| 等旧消息消费完再扩 | 先靠异步化硬扛，Lag 清零后低峰扩分区 | 顺序敏感且能扛 |
| 消费端加状态机兜底 | 收到"旧状态"事件直接丢弃/重试 | 有状态机的业务 |
| 临时消费者组 | 新组从头消费新分区，老组消费完老分区后下线 | 最稳但最重 |

那晚我们的订单结算消息**不要求严格有序**（每条消息带完整快照），所以直接扩了。这个判断必须在动手前花 30 秒确认——**顺序敏感的业务乱扩分区，积压解决了，数据乱了。**

### 2.3 不想动分区？还有一条临时路子

如果分区不能扩（顺序敏感）、消费者又已等于分区数，还有一个经典的临时方案：**把消息转发到临时大分区 Topic，用临时消费组去消化**。

```
原消费组（12 分区，慢逻辑）
    │ 只做一件事：原样转发，不做业务处理（极快）
    ▼
临时 Topic: order-events-boost（48 分区）
    │
    ▼
临时消费组（48 实例，跑完整业务逻辑）
```

转发逻辑不带业务处理，单实例轻松跑到几万条/秒；真正的业务处理在 48 分区的临时 Topic 上并行跑。消化完 Lag 后，临时链路下线，流量切回原链路。

这个方案的代价是要写转发代码、要处理**重复消费**（切换瞬间两条链路可能同时处理同一消息，幂等必须有），适合积压量巨大（千万级）且耗时敏感的场合。当晚我们 200 万的量级，扩分区 + 异步化就够了，没用到这一招。

### 2.4 结论

止血三板斧的优先级：**先把消费者加到分区数（零风险）→ 确认顺序不敏感后扩分区再扩消费者（分钟级）→ 千万级积压再考虑临时 Topic 转发（小时级）**。分区数就是消费并行度的天花板，这个天花板 2.1 的铁律决定，绕不过去。

## 三、第二步：批量拉取——把网络往返摊薄

### 3.1 消费慢的隐藏元凶：一条一拉

默认配置下，消费者一次 `poll()` 最多拿 500 条。听起来不少，但算一笔账：

```
单条处理 40ms（同步调下游），一次 poll 拿 500 条
→ 每批处理耗时 20 秒
→ max.poll.interval.ms 默认 300 秒，还没超时，侥幸活着
→ 但吞吐上限被钉死：500 条 / 20 秒 = 25 条/秒/实例
```

更糟的是"一条一拉一提交"的写法（我们在老代码里真见过）：

```java
// 反面教材：每条消息一次 poll + 一次同步提交
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        process(record);
        consumer.commitSync();  // 每条一次 RPC 提交，吞吐直接打骨折
    }
}
```

`commitSync` 是阻塞 RPC，每条一次 = 每条额外加一个网络往返。这种写法下单实例吞吐很难超过几百条/秒。

### 3.2 拉取参数的正确组合

```properties
# ── 批量拉取三件套 ──────────────────────────────
max.poll.records=2000            # 单次 poll 最多 2000 条（默认 500）
fetch.min.bytes=1048576          # broker 攒够 1MB 才返回（默认 1 字节）
fetch.max.wait.ms=500            # 攒不够最多等 500ms（配合上一条）

# ── 单分区流量控制 ──────────────────────────────
max.partition.fetch.bytes=4194304   # 单分区单次最多拉 4MB（默认 1MB）

# ── 保底线：处理超时不被踢 ──────────────────────
max.poll.interval.ms=600000      # 两次 poll 最大间隔，按"单批最坏耗时"设
```

三个参数的逻辑关系：

```
fetch.min.bytes + fetch.max.wait.ms  → 决定 broker 端"攒批"
   宁可等 500ms 攒够 1MB，也不要一条一返回
max.poll.records                     → 决定客户端"一次拿多少"
max.poll.interval.ms                 → 决定"这批必须在多久内处理完"
   公式：max.poll.interval.ms ≥ max.poll.records × 单条最坏耗时 × 1.5
```

**最后一条公式是血泪换来的。** 我们把 `max.poll.records` 调到 2000 的当天，消费组开始疯狂 rebalance——单批 2000 条 × 单条最坏 2 秒（慢消息）= 4000 秒，远超 `max.poll.interval.ms` 的 300 秒默认值。消费者处理不完被踢出组，rebalance 后消息重拉，又处理不完，再被踢……**Lag 反而越消越慢。**

正确顺序：**先把慢消息隔离掉（见第五章），再调大批次；批次大小和 poll 间隔必须一起算。**

### 3.3 实测收益

同一消费者实例、同一批积压消息（50 万条，单条平均 12ms）：

| 配置 | 吞吐（条/秒/实例） | 说明 |
|---|---|---|
| 默认（poll 500 条） | 78 | 网络往返占比高 |
| `max.poll.records=2000` | 205 | 2.6 倍 |
| + `fetch.min.bytes=1MB` | 290 | 3.7 倍，broker 攒批后网络次数骤降 |
| + 批量写下游 DB（200 条/批） | 850 | **10.9 倍**，大头在这 |

注意最后一行：**拉取批量化的收益是线性的，处理批量化的收益是数量级的。** 把 `insert` 一条一条改成 `insert ... values (...), (...), ...` 一批 200 条，DB 往返次数从 200 次变 1 次——这才是批量化的主战场。拉取端调参只是把"原料"成批运进来，真正的消化能力取决于业务代码会不会"成批吃"。

### 3.4 结论

批量拉取是**性价比最高**的一步：改几行配置，吞吐翻 2-4 倍。但它有一个硬性前提——**单批消息的处理耗时可预测**。批里只要混进一条 2 秒的慢消息，整批的耗时就会被它拖住。所以批量化和"定位卡点"必须配套做，这就是第五章的主题。

## 四、第三步：业务处理异步化——拉取与处理解耦

### 4.1 串行模型的天花板

Kafka 客户端的标准用法是单线程串行：

```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        process(record);   // ← 40ms 的下游调用，把 poll 线程死死堵住
    }
    consumer.commitSync();
}
```

这个模型里，**poll 线程 = 处理线程**，吞吐上限 = 1000ms ÷ 单条耗时。单条 40ms，单分区上限就是 25 条/秒，神仙参数也救不了。

### 4.2 解耦模型：poll 归 poll，处理归处理

```
poll 线程（1 个）：只负责拉取 + 派发 + 提交位点
    │
    ├──▶ worker-1  ┐
    ├──▶ worker-2  │
    ├──▶ ...       ├─ 16 个线程并行处理
    └──▶ worker-16 ┘
```

```java
// Spring Kafka 风格：listener 里只做派发
private final ThreadPoolExecutor workers = new ThreadPoolExecutor(
        16, 16, 0L, TimeUnit.MILLISECONDS,
        new LinkedBlockingQueue<>(5000),       // ★ 有界队列，防内存暴涨
        new ThreadPoolExecutor.CallerRunsPolicy()  // ★ 满了反压给 poll 线程
);

@KafkaListener(topics = "order-events", groupId = "order-settle")
public void onMessage(List<ConsumerRecord<String, String>> records,
                      Consumer<?, ?> consumer,
                      Acknowledgment ack) {
    CountDownLatch latch = new CountDownLatch(records.size());
    for (ConsumerRecord<String, String> record : records) {
        workers.execute(() -> {
            try {
                process(record);
            } finally {
                latch.countDown();
            }
        });
    }
    try {
        latch.await(55, TimeUnit.SECONDS);     // ★ 等本批全部完成
        ack.acknowledge();                     // ★ 全部成功才提交位点
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        // 超时/中断：不提交位点，这批消息下次重投
    }
}
```

三个关键设计，每一个都是坑换来的：

1.  **有界队列 + CallerRunsPolicy**：worker 池打满时，派发动作退化为 poll 线程自己执行，天然形成反压。用无界队列，积压瞬间会把几十万条消息灌进 JVM 内存，Full GC 直接把你送进内存泄漏排查的场景。
2.  **整批完成才提交位点**：`latch.await` 卡住 poll 线程直到本批全部处理完。**绝不能"poll 出来就提交"**——那是典型的消息丢失点，worker 还没处理完进程挂了，这批消息就永远丢了。
3.  **超时不提交**：等待超时后位点不动，消息重投。代价是重复，所以消费必须幂等。

### 4.3 异步化的代价：顺序与重复

| 代价 | 说明 | 对策 |
|---|---|---|
| 分区内顺序被打破 | 16 个 worker 并行，同分区消息不再有序 | 顺序敏感场景按 key hash 到固定 worker（见 4.4） |
| 重复概率上升 | 整批提交 → 部分完成时宕机，整批重投 | 消费幂等（唯一键/状态机） |
| 位点管理变复杂 | 不能再用自动提交 | 手动 ack + 整批确认 |
| 排查变难 | 处理日志分散在 16 个线程 | 统一 traceId，日志带 offset |

### 4.4 既要并行又要顺序：按 key 分桶的 worker 模型

顺序敏感业务的折中方案——**worker 池内部按 key 再分桶**：

```java
// 同一个 key 永远进同一个 worker → 同 key 有序，不同 key 并行
int workerIndex = Math.abs(record.key().hashCode()) % WORKER_COUNT;
workerPools[workerIndex].execute(() -> process(record));
```

这是"按分区分发"思路的简化版：Kafka 用分区保证 key 有序，你在 JVM 内部用 `hash(key) % N` 复刻同样的结构。**并行度来自桶数，有序性来自同 key 同桶**，鱼和熊掌在这个模型里可以兼得。

### 4.5 实测收益

| 模型 | 吞吐（条/秒/实例） | 相对 |
|---|---|---|
| 串行处理（单条 40ms 下游调用） | 24 | 1x |
| 16 worker + 整批提交 | 360 | **15x** |
| 16 worker + key 分桶（顺序敏感版） | 330 | 13.8x |

### 4.6 结论

异步化是四步里**收益最大、风险也最大**的一步。它把单实例吞吐抬一个数量级，但把"offset 提交时机"这个可靠性命门从框架手里拿到了你手里。**记住一条：位点提交的时机 = 这批消息业务上确认完成的时刻，早一秒是丢，晚一秒是重，没有第三种选择。**

## 五、第四步：定位卡点——快路径被慢消息拖死

### 5.1 一个反直觉的事实：3% 的慢消息能拖垮 97% 的吞吐

那晚排查时发现，真正诡异的不是"整体慢"，而是**消费速率周期性骤降**。给处理耗时加了埋点之后真相大白：

```
97% 的消息：走正常分支，单条 8ms
3% 的消息：命中"结算账户异常"分支 → 调下游超时重试 3 次 → 单条 2000ms
16 个 worker，任何时候只要有 1 个在处理慢消息，该 worker 后面积压的快消息全部排队
等效吞吐 = 16 / (0.97×8ms + 0.03×2000ms) ≈ 235 条/秒
                                       ↑
                          慢消息贡献了 87% 的总耗时
```

**worker 池的平均吞吐由最慢的消息决定，不是由平均消息决定。** 这和分区倾斜的木桶效应是同一个道理，只是木桶从分区换成了消息。

### 5.2 定位卡点的标准化动作

```bash
# ① 先确认卡在消费端还是下游
# 消费者机器上：
top -H                          # CPU 高 → 卡在本地计算/GC
ss -s                           # 大量 ESTABLISHED 到下游 → 卡在下游调用
jstack <pid> | grep -A5 "kafka-coordinator"  # 看 poll 线程在等什么

# ② 看 GC（消费端 JVM 的隐形杀手）
jstat -gcutil <pid> 1000 10     # Full GC 频繁 → 暂停即积压

# ③ 下游服务同步看
# 下游 DB 慢查询、接口 P99 是否和消费者耗时曲线同步
```

埋点代码只需要一个直方图：

```java
long start = System.nanoTime();
try {
    process(record);
} finally {
    long costMs = (System.nanoTime() - start) / 1_000_000;
    histogram.record(costMs);
    if (costMs > 500) {
        // 慢消息单独记日志：topic/partition/offset/key/耗时
        slowLog.warn("slow msg, tp={}-{}, offset={}, key={}, cost={}ms",
                record.topic(), record.partition(), record.offset(),
                record.key(), costMs);
    }
}
```

跑 10 分钟，慢消息的特征（集中在哪个 key、哪种类型、哪个下游）一目了然。

### 5.3 慢消息的三种处置

| 处置 | 做法 | 适用 |
|---|---|---|
| **隔离** | 慢消息识别后转发到独立 Topic，独立消费组慢速处理 | 慢消息是特定类型（如异常账户） |
| **降级** | 积压期间慢消息走简化逻辑（只记库不调下游），事后补偿 | 大促/洪峰期间 |
| **修复** | 下游超时重试 3 次 × 700ms 本身就是 bug，改成快速失败 + 死信 | 根治 |

我们当晚用的组合：**先把"异常账户"类型的消息隔离到 `order-events-slow`（Topic 隔离），消费速率立刻从 235 恢复到 1500 条/秒；第二天再把下游的同步重试改成"写死信表 + 定时补偿"（根治）。**

### 5.4 结论

定位卡点是四步里**唯一不能被"加机器"替代**的一步。扩 10 倍消费者，慢消息还是那 3%，等效吞吐还是被它拖住。**积压治理的最后一公里，永远是对消息本身做画像：快的放行，慢的隔离，病的治病。**

## 六、消化期守则：积压清零前别踩这三个坑

Lag 下降的过程中有三个高发事故，每一个都能让你前功尽弃。

### 6.1 坑一：重复消费洪峰

扩消费者 → rebalance → 位点回退 → 已处理的消息重投。异步化之后"整批提交"也会让部分完成的消息整批重来。**积压消化期的重复率可能是平时的几十倍。**

硬要求：消费端幂等必须在扩容之前就位。三种幂等姿势：唯一索引 / 状态机 / 去重表。

### 6.2 坑二：下游被打爆

消费速率从 800 提到 5000 条/秒，意味着下游 DB 和接口的 QPS 同步翻 6 倍。**Kafka 的积压清完了，下游服务的告警响了。**

```
消化前必须算的账：
下游容量 ≥ 消费峰值速率 × 每条消息的下游调用次数 × 1.5
不够就两条路：
  a. 消费端限流（如 Guava RateLimiter 限制整体速率）
  b. 下游调用批量化（200 条合并一次 RPC/一条 SQL）
```

### 6.3 坑三：消息过期

Kafka 的 retention 按时间或大小删数据，**不管消费组追没追上**：

```bash
# retention.ms = 72 小时，而你的 Lag 需要 80 小时才能追平
# → 最老的那批消息还没被消费就被删了，静默丢失

# 动手前先查：
kafka-configs.sh --bootstrap-server kafka:9092 \
    --entity-type topics --entity-name order-events --describe | grep retention

# 预估消化时长 > retention 的 50%，先临时调大：
kafka-configs.sh --bootstrap-server kafka:9092 \
    --entity-type topics --entity-name order-events \
    --alter --add-config retention.ms=604800000   # 7 天
```

这个坑的阴险之处在于**完全无报错**——消息消失得干干净净，消费端日志一切正常，对账时才发现少了一段。

## 七、长治久安：不让积压再次发生

### 7.1 监控告警的正确配置

| 告警 | 阈值建议 | 级别 | 说明 |
|---|---|---|---|
| Lag 绝对值 | > 10 万（按业务耐受度） | P1 | 触发即排查 |
| Lag 增速 | 连续 10 分钟为正增长 | **P0** | 比绝对值更早暴露问题 |
| 单分区 Lag 倾斜 | 最大分区 Lag > 平均 5 倍 | P1 | 倾斜意味着局部卡死 |
| committed offset 停滞 | 5 分钟无变化且有新消息 | **P0** | 消费者假死/rebalance 死循环 |
| 消费耗时 P99 | > 500ms | P2 | 慢消息的早期信号 |

按团队告警规范：P0 立即电话/on-call，P1 工作时间处理，非 P0 凌晨延迟到早晨——增速和停滞这两条 P0 是那晚之后我们加上的，**它们比 Lag 绝对值早 20-40 分钟暴露问题**。

### 7.2 容量评估公式

```
安全消费容量 = 分区数 × min(单分区拉取吞吐, 单分区处理吞吐) × 安全系数 0.5
单分区处理吞吐 = 1000ms ÷ 单条平均耗时（异步化后按等效并行度折算）
```

举例：24 分区，异步化后单分区等效 500 条/秒，则安全容量 = 24 × 500 × 0.5 = **6000 条/秒**。生产峰值只要超过这个数，积压就是时间问题，不是概率问题。**容量评估每个大促前做一次，和压测报告放在一起。**

### 7.3 架构层的兜底

| 手段 | 说明 |
|---|---|
| 生产端限速/降级开关 | 补数据、数据同步类任务必须带限速，凌晨窗口执行 |
| 洪峰独立通道 | 补数据走独立 Topic，不复用在线链路 |
| 消费弹性伸缩 | K8s HPA 基于 Lag 指标（KEDA）自动扩缩消费者 |
| 常态化异步化 | 核心消费链路默认"poll + worker 池"结构，不留串行代码 |

那晚的事故起点是"上游 01:30 补发历史数据"——**补数据任务没有限速，是所有积压事故里最常见的导火索**，没有之一。

## 八、常见问题

### 8.1 Lag 多少算异常？

看业务耐受度：实时对账类 1 万就该紧张，离线同步类 100 万可能只是慢了点。**真正统一的判据是增速和追平时间**：增速为负且预计 30 分钟内追平 → 观察；增速为正 → 立即处理。

### 8.2 消费者已经等于分区数了，还能怎么扩？

三条路：① 扩分区（注意顺序和 hash 漂移，见 2.2）；② 提升单实例吞吐（批量化 + 异步化，第三、四章）；③ 临时 Topic 转发（2.3）。**优先级是 ② → ① → ③**，因为 ② 改完是永久收益，① 是天花板抬升，③ 是一次性工程。

### 8.3 消费者一直 rebalance，Lag 越消越慢，怎么办？

九成是 `max.poll.interval.ms` 不够用：单批处理时间超过它，消费者被踢，重新分配后重拉同一批，再超时。处理：先调小 `max.poll.records`（比如回到 500），确认 Lag 开始下降，再回头解决慢消息（第五章），最后慢慢调大批次。**rebalance 死循环期间，任何扩容都是无效的。**

### 8.4 异步化之后消息顺序乱了怎么办？

按 key 分桶（4.4）：`hash(key) % worker数`，同 key 进同一个 worker 串行处理。注意这是"单实例内"的方案；如果是顺序强敏感 + 积压严重的组合场景，老老实实串行消费 + 扩分区，别上 worker 池。

### 8.5 能不能直接改 offset 跳过积压消息？

技术上可以（`kafka-consumer-groups.sh --reset-offsets --to-latest`），业务上等于**声明放弃这批消息**。只适用于消息可丢弃的场景（日志、监控指标）。订单、支付类消息这么做，等于手动制造消息丢失事故。真要用，先把跳过的 offset 区间落库存档，事后补偿。

### 8.6 积压期间要不要暂停生产？

一般不要。Kafka 就是设计来当缓冲的，积压说明它在正常工作。**该暂停的不是生产，是"非核心消费者"**——把资源让给核心消费组先追。暂停生产只在一个场景合理：磁盘水位告急，继续写入会让整个集群不可用。

### 8.7 Spring Kafka 的 `concurrency` 参数和手动 worker 池选哪个？

`concurrency = 8` 是起 8 个消费者实例（各占分区），并行度仍受分区数封顶；worker 池是单实例内并行，不受分区数限制但要自己管理位点。**分区数够就先用 `concurrency`（简单可靠），分区数到顶了再上 worker 池（灵活但复杂）。**

### 8.8 积压消化完，临时的扩容要缩回来吗？

消费者实例可以缩，分区**缩不回来**（只能加不能减）。所以扩分区前的口头禅应该是："这个分区数，三年后我还认吗？"

## 九、总结

### 处理决策树

```
Lag 告警响起
├── committed offset 完全不动？
│   └── 是 → 消费者假死/rebalance 死循环
│       ├── 日志刷 "Revoking partitions" → 调小 max.poll.records，查慢消息
│       └── 进程异常 → 先救活，看 GC 和下游
├── Lag 在涨但 offset 在动？
│   ├── 生产速率突增（补数据/大促）
│   │   ├── 消费者数 < 分区数 → 先加满（零成本）
│   │   ├── 顺序不敏感 → 扩分区 + 扩消费者
│   │   ├── 顺序敏感 → 异步化 + 按 key 分桶
│   │   └── 千万级 + 时间紧 → 临时 Topic 转发
│   └── 生产速率没变 → 消费变慢
│       ├── 埋点看耗时分布 → 慢消息隔离/降级
│       ├── 下游 P99 同步恶化 → 先救下游
│       └── Full GC 频繁 → 先救 JVM
└── 全程检查：retention 够不够？下游扛不扛得住？幂等到没到位？
```

### 四步速查表

| 步骤 | 动作 | 关键参数/手段 | 主要风险 |
|---|---|---|---|
| 1. 扩容 | 消费者加到分区数 → 扩分区再加消费者 | 消费者数 ≤ 分区数 | hash 漂移打乱顺序 |
| 2. 批量 | 调大拉取批次 + 业务批量化 | `max.poll.records`、`fetch.min.bytes` | 单批超时 → rebalance |
| 3. 异步化 | poll 与处理解耦 | worker 池 + 有界队列 + 整批提交 | 位点管理失误 → 丢/重 |
| 4. 定位卡点 | 耗时埋点 + 慢消息隔离 | 耗时直方图、慢消息日志 | 无（纯收益） |

### 一句话

> **消费积压是一道算术题：让"消费速度 ≥ 生产峰值 × 1.5"。扩容抬天花板，批量摊薄往返，异步化吃掉延迟，定位卡点拔掉钉子——四步按顺序做，先止血再治病，消化期守住幂等、下游和 retention 三条底线。**

### 关键数字

*   消费者有效并行度上限 = **分区数**（铁律）
*   批量拉取：单实例吞吐 **2-4 倍**；配合业务批量化可到 **10 倍**
*   异步化（16 worker）：单实例吞吐 **15 倍**
*   3% 的慢消息（2s）可拖慢整体吞吐 **87%**
*   `max.poll.interval.ms` ≥ 批次大小 × 单条最坏耗时 × 1.5
*   追平时间 > retention 的 50% → 先调大 retention 再消化

### 给团队的建议

| 现状 | 建议 |
|---|---|
| 还没有 Lag 监控 | 今天就把"增速"和"offset 停滞"两条 P0 告警加上 |
| 消费逻辑是串行处理 | 核心链路本季度内完成异步化改造 |
| 经常补数据/数据同步 | 补数任务强制限速 + 独立 Topic |
| 分区数拍脑袋定的 | 按容量公式重算，一次到位（分区只加不减） |
| 消费没有幂等 | 先补幂等再谈积压治理，顺序不能反 |
