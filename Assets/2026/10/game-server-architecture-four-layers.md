# 游戏服务器架构应该如何分层？

> 来源：https://mp.weixin.qq.com/s/NSVCzrF9UvT67Vtl49nuMg（公众号：架构师修炼指南）
> 抓取时间：2026-10-21（web-fetch，browser 级）

我们在学习或者设计一个游戏服务器架构（让 AI 去写一个服务器 demo），很多同学对游戏服务器架构的分层边界比较模糊。

我个人理解应该是拆解为四层骨架：`连接层`、`实体层`、`RPC 约束层`、`协调层`。

这四层划分分别回答了游戏服务器面临的四个核心问题：

*   **连接层**：客户端怎么连进来？
*   **实体层**：游戏世界里的对象怎么管理？
*   **RPC 约束层**：服务之间怎么可靠调用？
*   **协调层**：分布式节点之间怎么分配分片、迁移状态、处理故障？

* * *

## 一、连接层：客户端接入的边界

连接层是服务器框架的最外层，也是客户端唯一直接接触的边界。它的主要职责不是处理复杂的玩法逻辑，而是**纯粹地管理连接本身**。

### 1. 核心职责

*   **长连接管理**：高效接入 TCP、UDP、WebSocket 等传输协议。
*   **会话绑定**：将底层连接 ID 与玩家 ID、设备 ID、会话状态进行精准绑定。
*   **心跳与超时**：探活客户端连通性，及时回收僵尸连接。
*   **协议编解码**：处理 Protobuf、JSON、自定义二进制包的拆包、粘包、消息头与消息体解析。
*   **鉴权与限流**：登录校验、安全签名、请求频率限制与防重放攻击。
*   **消息分发**：将合法的客户端原始消息路由到正确的实体或服务。
*   **断线重连**：妥善处理玩家掉线后的会话恢复，而非直接销毁。

> **避坑指南**：连接层最忌讳直接编写业务逻辑。诸如"玩家购买道具"、"进入副本"等逻辑绝对不能出现在这里。连接层只负责把消息解开、找到归属，然后交给实体层或 RPC 层。

### 2. 代码抽象示例

```go
type ConnectionLayer interface {
    BindSession(connID string, playerID string) error
    UnbindSession(connID string)
    SendToPlayer(playerID string, msg Message) error
    OnMessage(connID string, raw []byte) error
}
```

## 二、实体层：游戏世界的状态中心

实体层是游戏服务器最核心的腹地。它不应被当作传统 Web 开发中的"无状态业务层"，而应该理解为**有状态游戏对象的生命周期管理层**。

在游戏世界中，万物皆可抽象为实体：

*   玩家、NPC、怪物
*   房间、副本、战场、匹配队列
*   公会、场景、排行榜缓存

这些对象的共同特征是：**它们是有状态的、有生命周期的，且发往它们的消息必须保证严格的顺序性。**

### 1. 核心职责

*   **实体定义**：区分哪些是长期存活的 Entity，哪些只是瞬时数据。
*   **生命周期管理**：控制实体的创建、激活、空闲回收与销毁。
*   **消息投递**：确保发往同一个实体的所有消息按序到达。
*   **状态隔离**：保证不同实体之间的状态互不污染。
*   **AOI 与视野**：管理空间感知、九宫格同步与广播。
*   **持久化与恢复**：实体状态如何安全落盘，服务崩溃后如何快速恢复。
*   **迁移准备**：为实体跨节点热迁移做好状态序列化与管道缓冲。

> **设计目标**：让业务开发者彻底屏蔽连接、RPC、分片等底层细节，只需聚焦于纯粹的领域逻辑——**"这个实体收到某条消息后，状态该如何演进"**。

### 2. 代码抽象示例

```go
type EntityManager interface {
    GetOrCreate(entityID string) Entity
    Route(entityID string, msg Message) error
    Migrate(entityID string, targetNode string) error
    Destroy(entityID string) error
}
```

## 三、RPC 约束层：服务间调用的规则

很多游戏服框架把 RPC 仅仅当作"远程函数调用"的语法糖，但这远远不够。RPC 约束层真正要做的是：**建立服务之间安全、可靠、可观测的契约。**

### 1. 核心职责

*   **服务发现**：动态管理集群节点的上线与下线。
*   **智能路由**：根据 `entityId`、`shardId` 或 `workerId` 准确寻址目标节点。
*   **序列化与协议**：规范高吞吐下的二进制序列化方案。
*   **调用语义**：支持请求响应、单向通知、可靠投递与多播广播。
*   **超时与控制**：防止调用方无限等待造成雪崩。
*   **重试与熔断**：明确界定哪些请求可重试、下游异常时如何保护上游。
*   **幂等设计**：确保重复投递不会造成重复扣费、重复发奖。
*   **可观测性**：统一的日志、Metrics 指标、分布式链路追踪与错误码统计。

> **核心约束**：跨服调用不能盲目。例如跨服匹配失败后严禁无限重试；当节点故障时，调用方必须清晰知道应当执行降级、报错还是重试。

### 2. 代码抽象示例

```go
type RPCLayer interface {
    Call(ctx context.Context, target string, req Message) (Message, error)
    Notify(ctx context.Context, target string, msg Message) error
    Broadcast(targets []string, msg Message) error
}
```

## 四、协调层：分布式分片的控制面

如果游戏服只部署单机，协调层可以完全不存在。但一旦走向多节点、跨服、分片、动态扩缩容，协调层就是整个分布式集群的"大脑"。

协调层解决的核心问题是：**某个分片、某个实体、某个房间，当前到底归哪台机器负责？**

### 1. 核心职责

*   **节点注册与发现**：新节点加入集群时的自动纳管。
*   **健康心跳**：实时探测节点心跳，识别宕机与假死。
*   **分片分配（Shard Allocation）**：决定数据分片落在哪一个 Worker 节点。
*   **分片再平衡（Rebalance）**：节点动态扩缩容时，平滑重新分配分片。
*   **故障转移（Failover）**：节点异常宕机后，迅速由健康节点接管其分片。
*   **迁移协调**：在实体动态迁移期间缓冲消息，防止状态丢失与双写冲突。
*   **分布式锁与租约**：避免出现两个节点同时声明自己拥有同一个 Shard 的"脑裂"现象。

> **实现建议**：协调层通常基于 etcd、Redis、ZooKeeper 或自研轻量 Coordinator 实现。它**不参与任何具体玩法逻辑**，只纯粹维护集群拓扑和分片映射。

### 2. 代码抽象示例

```go
type Coordinator interface {
    RegisterNode(nodeID string) error
    UnregisterNode(nodeID string) error
    AssignShard(shardID string, nodeID string) error
    GetShardOwner(shardID string) (string, error)
    ListNodes() ([]string, error)
}
```

## 五、四层如何协同工作

当一个客户端发起请求时，整个框架的内部运转流程如下：

1.  客户端发送网络消息到达**连接层**。
2.  连接层完成协议解析，识别出对应的玩家 ID 或实体 ID。
3.  通过 **RPC 约束层**（或本地缓存的路由表）查询该实体当前所在的宿主节点。
4.  **若实体在本节点**：直接投递给**实体层**进行状态处理。
5.  **若实体在远端节点**：通过 RPC 转发给目标节点，目标节点解包后交由当地实体层处理。
6.  实体处理完毕后，结果沿原路（或通过 RPC 返回连接层）推送回客户端。

> **提示**：**协调层**平时不直接介入单条消息的实时吞吐，但它在后台持续维护着集群拓扑与路由映射。每当节点上下线或分片发生迁移时，协调层便会动态更新全网的路由规则。

## 六、落地实践建议

1.  **边界清晰**：连接层严禁混入业务代码；协调层保持轻量，只管拓扑不管玩法。
2.  **状态有界**：实体层必须是有状态的，它是领域模型的真正载体。
3.  **重视约束**：RPC 层必须把超时、幂等、熔断和观测能力做到位，分布式世界处处充满抖动。
4.  **接口隔离**：层与层之间通过纯接口契约隔离，未来替换网络库（如从 Netty 换到自研网络库）、RPC 框架或存储组件时成本极低。
5.  **演进路线**：**先做单机闭环，再做分布式**。建议先让连接层、实体层、RPC 层在单节点跑通业务闭环，再引入协调层打通分布式能力。

* * *

## 七、总结

一句话概括这四层骨架的精髓：

*   **连接层**：解决"客户端怎么进来"
*   **实体层**：解决"游戏对象怎么存在"
*   **RPC 约束层**：解决"服务之间怎么通信"
*   **协调层**：解决"分布式状态下对象放在哪里"

游戏服务器天然具备**有状态、长连接、对消息时序敏感、高频跨服迁移**等复杂特性。将这些职责通过清晰的四层架构剥离，不仅能让边界变得异常坚固，也能让后续的业务迭代和架构演进更加可控。
