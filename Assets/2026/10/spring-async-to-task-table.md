# Spring Boot 一个任务跑 20 分钟，我把 @Async 删了：改成了"任务表 + Worker"

> 抓取正文（web-fetch, browser 级）。原始出处：https://mp.weixin.qq.com/s/DxS0YQAlpbFpP3sJVFUhKw
>
> 注：原文中代码块为图片，抓取时仅保留方法签名片段，正文逻辑完整。

前段时间做一个文件处理功能。

用户上传一个几十 GB 的数据文件以后，系统需要完成解析、校验、转换，再生成最终结果。小文件可能几十秒，大文件经常要十几分钟，极端情况下甚至会跑二十多分钟。

第一版实现很简单。Controller 收到请求以后创建一个任务编号，然后把真正的处理逻辑交给 `@Async` 执行，接口立即返回。

```java
@PostMapping("/files/process")
```

真正的耗时逻辑放在异步方法里：

```java
@Async("fileTaskExecutor")
```

为了不让这些长任务把默认线程池占满，我们还专门配置了一个 Executor。

刚上线的时候，这套方案看起来没什么问题。用户提交任务以后，接口立即返回，后台线程慢慢处理，前端只需要根据 taskId 查询状态即可。

真正的问题出现在第一次滚动发布。

那天正好有几个大任务正在执行，其中一个已经运行了 12 分钟，进度大约到了 70%。随后 Kubernetes 开始更新实例，旧 Pod 被停止，新版本重新启动。

发布结束以后，页面上的任务状态却一直停留在 `PROCESSING`。等了半个小时，任务仍然没有任何变化。

查日志以后才发现，任务并不是"还在执行"，而是已经彻底消失了。

因为它真正存在的地方，不是数据库，也不是消息队列，而只是旧 JVM 里的一个线程。Pod 一旦结束，线程随之消失，那个已经跑了 12 分钟的任务自然也没有任何恢复机会。

这时候我才意识到：`@Async` 能解决的是"不要让当前 HTTP 请求一直等待"，但它并不能自动把一个二十分钟的业务流程变成一个可靠任务。

* * *

正常运行的时候，`@Async` 的调用链非常简单：HTTP 请求 → 线程池 → 异步方法。所以平时很容易产生一种错觉：只要任务已经进入线程池，它最终就一定会执行完成。

但真实生产环境里，长任务执行期间随时可能遇到服务发布、Pod 驱逐、进程 OOM、机器故障，甚至只是一次普通重启。只要 JVM 消失，线程里的执行状态就没有了。

更麻烦的是，业务数据库可能仍然认为这个任务处于 `PROCESSING`。于是用户看到的是"正在处理"，系统实际上却已经没有任何线程在处理它。

这类任务最危险的地方，不是执行慢，而是**执行状态只存在内存里**。

* * *

业务量增加以后，第二个问题也很快出现了。

我们的线程池配置是 4 个核心线程、8 个最大线程，队列容量 100。这个配置看起来并不小，但如果一个任务平均要执行 15 分钟，前 8 个任务占满线程以后，第 9 个任务就只能进入队列。

假设前面已经排了 40 个任务，第 41 个任务虽然页面显示"提交成功"，但它到底什么时候真正开始执行，系统其实并不知道。

因为这些排队信息只存在 `ThreadPoolExecutor` 的内部队列里。业务系统看不到每个任务当前排在什么位置，也很难准确回答"现在有多少任务等待执行""某个用户的任务为什么一直没开始"。

更别说后面如果还要增加取消、重试、优先级、失败恢复、限流，这些能力都很难优雅地建立在线程池队列之上。

到这里，问题已经不再是"线程池参数应该怎么调"，而是我们把一个真正的业务任务，当成了普通的 `Runnable`。

* * *

后来我把 `@Async` 从核心任务流程里移掉，先建立了一张真正的任务表。

```sql
CREATE TABLE process_task (...)
```

任务状态先保持简单，只定义四种：`WAITING` `PROCESSING` `SUCCESS` `FAILED`。

用户提交文件以后，Controller 不再直接启动一个二十分钟的后台线程，而只是负责把任务可靠地保存下来（`@Transactional`）。接口立即返回 taskId。

这个改动最大的价值并不是"用了数据库"，而是任务终于不再依赖某个 JVM 的生命周期。

HTTP 请求结束以后，任务还在。服务重启以后，任务还在。应用发布以后，任务还在。即使所有 Worker 暂时都挂掉，任务依然会以 `WAITING` 状态保存在数据库中，等服务恢复以后继续处理。

从这一刻开始，任务才真正变成了一个业务对象，而不是线程池里的一个临时执行单元。

* * *

接下来才轮到 Worker。

最简单的实现可以通过定时任务周期性扫描等待中的任务，然后交给专门的线程池执行：

```java
@Scheduled(fixedDelay = 1000)
```

这里仍然可以使用线程池。也就是说，我并不是认为 `@Async` 或 `TaskExecutor` 不适合后台任务，而是把它们的职责重新放回正确的位置。

线程池负责的是：**当前这个实例同时执行几个任务。**
数据库负责的是：**系统里到底有哪些任务、它们现在是什么状态。**

一旦把这两个职责拆开，线程挂掉和任务丢失就不再是同一个问题。

* * *

不过如果服务有多个实例，新的问题马上又来了。

假设现在有三个 Worker（worker-1/2/3），它们每秒都扫描 `status = WAITING`。如果数据库里有一个待处理任务，三个 Worker 很可能同时查到它，然后同时开始执行。

所以真正领取任务时，不能只是先查询，再由 Java 判断自己要不要执行。我们后来直接通过条件 UPDATE 抢占任务：

```sql
UPDATE process_task SET status='PROCESSING', worker=?
WHERE id=? AND status='WAITING'
```

Java 代码只看受影响行数。假设三个实例同时争抢同一个任务，最终只有一个 Worker 能把状态从 `WAITING` 改成 `PROCESSING`：Worker A affected=1，B 和 C 都是 0。真正执行任务的只有 Worker A。

不需要 JVM 本地锁，也不需要几个 Worker 之间互相通信，数据库状态本身就完成了最基本的任务协调。

* * *

Worker 成功领取任务以后，再执行真正的业务逻辑。真正处理文件时，我们顺手把进度也存下来——以前任务进度可能只存在内存里，现在直接保存在任务表。前端查询 `GET /tasks/{taskId}` 可以返回状态和进度，用户看到的不再只是一个无限旋转的 loading，而是一个真正有状态、有进度的后台任务。

* * *

真正让我觉得任务表值得做，是后来"失败重试"这个需求出现以后。

有些任务失败并不是业务数据有问题，而只是遇到了临时故障。比如对象存储短暂超时、第三方模型返回 503、外部服务暂时不可用，这些场景重新执行一次很可能就成功。于是任务表里的 `retry_count` 开始真正发挥作用：可重试错误把状态改回 `WAITING`，稍后 Worker 再次处理；但文件格式错误、字段缺失、不支持的编码这类错误重新执行十次也不会成功，直接标记为 `FAILED`。

系统终于能够区分：**"值得再试一次"** 和 **"继续重试没有意义"**。

如果整个任务只是一个 `@Async void process()`，当这些需求一个个出现时，代码会越来越难维护。

* * *

不过做到这里，还没有真正解决服务中途崩溃的问题。

假设 Worker 在 10:00 成功把任务状态改成 `PROCESSING`，执行到 10:08 时 Pod 突然被杀掉。数据库里的状态仍然是 `PROCESSING`，而下一轮 Worker 扫描只寻找 `WAITING`，这个任务就会永久卡住。

后来我们给任务增加了 `heartbeat_time`。Worker 在执行长任务期间，每隔 30 秒更新一次心跳。如果当前已经 10:20，而最后一次心跳还停留在 10:08，就说明这个任务很可能已经失去执行者。Recovery Job 定期扫描这类心跳超时任务，确认超时后把任务重新放回 `WAITING`，下一台 Worker 就可以重新领取它。

这样一次服务重启造成的结果，不再是"任务永久消失"，而只是"任务稍后重新执行"。这两种可靠性差别非常大。

* * *

但是一旦系统开始支持故障恢复，就必须接受另一个现实：**同一个任务可能执行两次。**

比如 Worker A 实际上没有死亡，只是因为数据库网络短暂异常，心跳更新失败。Recovery Job 误以为它已经挂掉，于是重新把任务放回 `WAITING`。这时候 Worker B 又领取了任务，A 和 B 就可能短暂地同时执行。

因此，一个真正可靠的任务系统不能建立在"每个任务一定只会执行一次"的假设上。更合理的设计是：**任务至少执行一次，但最终业务结果必须幂等。**

比如生成文件时，可以固定按照 `taskNo` 保存（`/result/T202610200001/output.zip`），不管任务执行一次还是两次，最终结果都写到同一个位置。数据库结果表也可以用 `task_id` 建唯一约束，避免重复执行产生两份业务数据。

很多任务系统最后出问题，并不是因为 Worker 不够复杂，而是业务代码默认认为"这个方法绝对只会调用一次"。在分布式环境里，这个假设通常并不可靠。

* * *

后来我们还增加了任务取消。

以前用 `@Async` 时，用户如果说"刚才选错文件了，能不能把任务停掉"，处理起来并不轻松。直接调用 `Future.cancel()` 看起来很简单，但任务可能正在读取大文件、调用第三方服务或者执行模型推理，并不是所有步骤都能在收到 interrupt 后立即停止。

任务表模式下，我们没有选择强行杀线程，而是增加了一个 `CANCEL_REQUESTED` 状态。用户点击取消时更新状态；Worker 在几个安全节点（如下载完成、转换开始前）主动检查，一旦发现取消请求，就完成必要的清理，再把任务标记为 `CANCELLED`。

这种方式属于协作式取消。对于需要长时间执行、同时还要保证资源正确释放的任务来说，通常比简单粗暴地"杀线程"更加稳妥。

* * *

任务越来越多以后，优先级需求也自然出现了。例如普通批处理任务 `priority = 10`，用户正在页面等待结果的任务 `priority = 50`，管理员提交的紧急任务 `priority = 100`。Worker 查询时直接 `ORDER BY priority DESC, created_at`。

到这里就会发现，真正的业务队列需要表达的信息其实非常多。它不仅仅需要知道"这里有一个 Runnable"，还需要知道是谁提交的、什么时候提交的、优先级是多少、失败几次、当前进度、哪个 Worker 在处理、最后一次心跳时间，以及任务是否允许取消。这些信息本来就不是 `BlockingQueue<Runnable>` 擅长表达的东西。

所以后来我越来越确定：线程池可以是执行工具，但不应该天然承担业务任务队列的职责。

* * *

当然，这套设计也有自己的边界。

如果只是发送一封邮件、异步刷新缓存、记录一条日志，或者执行一个几秒钟的小动作，我仍然会直接使用 `@Async`。这种场景下，`@Async` 足够简单，也足够好用。

我真正开始考虑"任务表 + Worker"的，通常是那些会出现以下特征的任务：执行时间可能达到几分钟甚至几十分钟；用户需要查看进度；失败以后需要重试；服务发布不能直接丢失任务；多个实例需要共同消费；或者用户明确需要取消。当这些需求开始同时出现两三个时，再继续往 `@Async` 上堆逻辑，往往已经不是最合适的方向。

* * *

整套方案用到的技术其实并不复杂，核心仍然只是数据库、线程池、定时扫描和条件 UPDATE。但它解决的问题，和一个单独的 `@Async` 已经完全不同。

`@Async` 解决的是：**这段代码不要让当前请求线程等待。**

而任务系统解决的是：**无论服务重启、Worker 故障还是任务积压，我都能知道这件业务现在到底处于什么状态，并且有办法继续处理。**

* * *

后来我们把这套方式又用到了很多完全不同的功能上：AI 图片生成、视频转码、文档 OCR、批量数据校验、代码扫描、大型压缩包解压、历史数据重新计算，以及一些需要调用外部模型十几分钟才能结束的分析任务。

这些业务看起来完全不同，但底层都有同一个共同点：**它们已经不再是一次 HTTP 请求里的"小异步动作"，而是一个有完整生命周期的业务对象。**

一旦把"任务"当成业务对象看待，很多设计会自然变得清晰。它应该有任务 ID、状态、进度、开始时间、结束时间、执行者、失败原因和重试次数，而不是只剩一句 `executor.execute(runnable)` 然后希望它最终一定能够执行完成。

所以现在再看到 `@Async` 这种代码，我不会直接认为它写错了。但我一定会继续问几个问题：

服务五分钟后发布，这个任务怎么办？执行到 80% 时进程挂了怎么办？用户怎么知道任务是否还活着？失败以后谁负责重试？同一个任务会不会被两个实例重复执行？用户想取消时怎么处理？

如果这些问题都没有答案，那么真正缺的通常并不是一个更大的线程池。而是：**这个任务早就不应该只存在于一个线程里了。** 它应该有状态，能够恢复，能够重试，能够观察，也应该在服务重启以后继续存在。
