> 开篇观点：许多 MMO 不好玩，策划担主要责任，程序（服务器）担次要责任——大量程序员设计架构时只从技术出发，对产品思考不足。例如为堆单服承载而按场景绑定线程，严重限制玩家交互范围和策划玩法设计。

## 传统单服队伍架构

1. 队伍系统直接在玩家所在的 Game 服，即**队伍数据和玩家数据在同一个线程**
2. 玩家只有在同一个频道（分线）才能组队，即**玩家必须在同一个线程才能组队**

### 优缺点

1. 玩家在同一线程，**可以精确检测进入副本条件、扣除道具等**
2. 玩家必须在同一频道才能组队，**在移动端游戏中导致糟糕体验**（移动端用户时间零散，通常允许同队玩家各自做各自的事）

### NPC 入队

分布式队伍通常支持 NPC 入队，因为玩家数据和队伍数据离得远，成员结构与玩家解耦；传统单服架构下开发者可能将队伍成员和玩家直接绑定，导致不支持 NPC 入队。

```csharp
class TeamMember {
    long guid; // 成员唯一id
    int npcId; // npcId - 非0表示为Npc
    string name; // 成员名
    int level; // 等级
}
```

## 传统分布式队伍架构

1. 队伍系统部署在跨 Game 的匹配服或队伍服
2. 在 Game 服或玩家身上维护队伍数据缓存，队伍数据变化时主动同步到 Game 服或玩家

### 缓存在玩家身上

```csharp
class GamePlayer {
    Player player; // 持久化数据
    ServerInfo serverInfo; // 服务器元数据
    TeamInfo teamInfo; // 队伍
    GuildInfo guildInfo; // 公会
    FriendInfo friendInfo; // 好友
}
// 广播队伍内玩家和离开队伍的玩家
private void OnTeamChanged(Team team, List<long> leftPlayers) {}
```

优缺点：

1. 以玩家为单位广播，**按需广播**，只同步在线玩家
2. 队伍人数少，按人头广播开销更低
3. 工会人数多，按人头广播可能产生大量同步包（服务器间 RPC）
4. 不支持机器人（NPC）成员——NPC 无法更新缓存队伍数据

### 缓存在 Game 服

```csharp
// 游戏服的队伍管理器，维护队伍镜像 -- 玩家内存数据也在这里
class GameTeamMgr {
    public Dictionary<long, TeamInfo> teamMap; // 队伍信息镜像
    public void OnTeamChanged(TeamData team) {} // 由队伍服调用RPC同步
}
```

优缺点：

1. 数据变化时**总是需要同步**，以正确维护副本集
2. 队伍人数少，缓存在 Game 服开销更大（服务器数量 > 队伍玩家数）
3. 工会人数多，按服务器同步开销更低（服务器数量 < 在线玩家数）
4. 工会数据量大，缓存在 Game 服节省内存
5. 测试玩家是否同队/同工会时，引用相等是安全的

缓存在 Game 服还是 Player 上需按项目权衡；除内存和广播量外，**解决方案的一致性**也要考虑。作者更推荐缓存在 Game 服：队伍本就独立于玩家，保持独立可避免引入奇怪限制，更有利于策划玩法设计。

### 优缺点

1. 不要求队伍内所有人在同一频道（线程），更适合移动端
2. 玩家可能在不同线程甚至进程，精确检测进副本条件和扣道具变困难
3. **创建队伍需要走网络**（异步），引入不确定性，部分业务编码困难

### 补救方案

程序应针对架构缺陷向策划提补救方案，而非简单说"不支持"：

1. 副本次数/道具不稀有：允许极限边界扣除失败，或通过其它方式**限制产出/奖励次数**
2. 次数/道具非常稀有（如每周 1~3 次副本）：设计**等候（集结）场景**，所有玩家到达同一场景后才能开始（如 DNF 安徒恩集结频道）
3. 离散进入：不再一次性传入所有玩家，玩家自行进入副本时再扣道具

## 互为镜像式队伍架构

### 项目需求

作者第三个项目（放置类 MMO）出现两个需求，迫使改进队伍架构。

**个人小队**：玩家可设置个人小队，非组队模式进副本时自动创建队伍。传统分布式架构创建队伍要走网络，会增加核心状态机复杂度和进副本时间。可行方案：**先构建一份假的队伍数据**（本地缓存类型），先进副本，再同步到远程服务器——假设总是成功（绝大多数确实成功），提升体验。

```csharp
TeamInfo CreateSquadTeam(Player player) {
    TeamInfo teamInfo = CreateTeam(player.squadInfo); // 本地缓存数据类型
    TeamCreateRequest request = CreateRequet(teamInfo);
    rpcClient.Call("TeamService/CreateTeam", request); // 远程RPC创建队伍
    SyncTeamInfo(player, teamInfo); // 通知客户端
    return teamInfo;
}
```

**NPC 入队**：剧情副本特定阶段 NPC 直接加入队伍并显示在队伍栏。NPC 显式入队体验优于仅变为友方单位。理论上可用预测回滚实现，但当时队伍数据缓存在玩家身上不支持——因此发现缓存在 Game 服扩展性更好。

### 互为镜像式架构

1. **游戏服和跨服都包含队伍服务**：游戏服支撑单服队伍，跨服支持跨服队伍
2. 队伍数据分真实队伍数据和镜像队伍数据，数据结构相同
3. 跨服队伍数据变化（创建、解散、队员变更）广播所有 Game 服；Game 服队伍变化也同步给跨服
4. Game 服和跨服最终都包含所有队伍数据
5. 玩家同时出现在 Game 服队伍和跨服队伍时，**以 Game（单服）队伍为准**，自动离开跨服队伍

```csharp
class Team {
    long guid; // 唯一id
    long leaderId; // 队长id
    List<Member> members; // 成员
    bool isMirror; // 是否是镜像
}
```

Q：冲突时为什么以单服队伍为准？
A：不是因玩家数据在 Game 服，而是职责决定的——**Game 服队伍系统主要用于支持特殊玩法**，因此具有更高优先级（权重）。

### 优缺点

**越是复杂的玩法，越要尽可能避免分布式或多线程逻辑，否则必将坠入复杂度的深渊。**

应想办法支持类似传统单服队伍的编程体验，镜像式架构可实现：限定特定频道或副本只能创建单服队伍，避免分布式问题，安全支持特殊玩法（如集结场景更适合用单服队伍）。

镜像式架构稍复杂，但队伍数据不涉及玩家持久化数据，对分布式边界情况容忍度较高，增加的复杂度有限。

---

## 结语

游戏开发者需要懂游戏，不能单纯从技术层面分析如何实现需求；要在用户体验、安全性、性能等方面做权衡，实现综合最好的方案。
