# 开源 Pi-durable，把持久化做进协议，看看架构是如何支持的

我们常常碰到一种情况：让 agent 跑一个大活儿，跑到第四十分钟，终端突然退出了，进程没了。重启，上下文还在（Pi 自己就支持 /resume），但执行现场没了：做了一半的工具调用不知道执行到哪一步。

上篇 Pi 1.0 的介绍提到了 Pi-durable，这次详细介绍一下 pi-durable 这个构建"随处运行、可崩溃恢复、多端协同、无限长"的 Agent 应用的框架。半个月里它从 1.0 走到 1.3。

这篇拆开讲它的持久化机制、五层架构、一次任务的完整流程，最后说清楚它和 Pi coding agent 的区别，以及能拿来二次开发什么。

## 一条公理管住整个框架

pi-durable 的规格文档第 0 条写了一句核心公理：一个 Session 原子地提交不可变条目（entries）、完整任务记录（tasks）和文档（documents），只有已提交的状态才是可观察的。

翻译过来：对话转录、每一次模型调用、每一次工具执行、系统提示词、你自己的业务状态，全部先写存储、后可见。UI 看到的一切都是已经落盘的状态，没有旁路的内存通道。进程在任何一个瞬间死掉，重新打开同一个存储，工作就从上一个检查点继续。

存储里有四张表加一组文档。四张表：conversations（对话）、entries（不可变的转录条目）、tasks（任务）、submissions（提交）。文档是类型化的 JSON 状态，每个对话自动带五个：pi.agent 存 agent 配置（模型、工具、扩展名单），pi.live 存运行态（当前 run、流式部分回答、重试退避），pi.inbox 存排队中的输入，pi.usage 记 token 和花费台账，pi.provider 存一个 UUIDv7 会话身份，跨重开、重试、压缩存活，用来保住 provider 侧的 prompt cache。

## 五层架构，四个存储后端

整套框架分五层，从下往上读，一层管一件事。

**① 最底下 Storage** 管把数据真正写到硬盘。它的接口刻意做得极简：写入一批数据，按编号查记录，没了。写到哪儿可以换，官方提供四个后端：

| 后端 | 一句话解释 |
|---|---|
| Memory | 只放内存，进程一退就清零，写代码调试用 |
| SQLite（Node） | 一个数据库文件，进程崩了数据一定还在，断电最多丢最后一次写入 |
| JSONL | 一个纯文本流水账，一行一条记录，只追加不改写，天然抗进程崩溃 |
| Cloudflare Durable Object | 云上的 SQLite，一次事务就是一次提交 |

想换成自己的存储也行。官方带了一整套一致性测试，`registerStorageConformance()` 跑一遍，合格不合格马上知道。1.3 版还加了表前缀，多个存储可以共用同一个数据库文件或同一个 Durable Object。

**② 往上是 Session**，纪律层。不管上面多热闹，所有写入排成一条队，一批一批提交，每批要么全部落盘、要么当没发生过。像银行转账，扣款和入账同生共死，不会出现扣了钱、对方没收到的一半状态。前面说的"原子提交"就在这一层兑现。

**③ 再往上是 Documents**，就是上一节那五个 pi.\* 文档的家。应用也能用 defineDoc() 加自己的文档，和别的写入同批落盘。每个文档存一份底稿加一串增量改动，界面每次只收改动的那一小段，不用整份重发。

**④ 长跑的能力在 Tasks 层**。每个任务是一个小状态机：做到哪一步（checkpoint 里记着）、下一步是什么，全写在存储里。调度器像个工头，约 1950 行代码，不关心任务具体干什么，只按规矩派活：每个阶段开工前查三件事，任务是不是已经结束、系统是不是在关闭、进度是不是真的落了盘。其中一条规矩管热重载：你改了代码，正在跑的阶段用旧代码跑完，下一个阶段自动换上新代码，不用重启进程。配置也一样，pi.agent 文档里只存扩展的名字、不存代码，装回同名扩展，卡住的任务立刻复活。

任务和对话之间有父子关系，组成一棵所有权树，两条规则：一是中止往下传，前台子代理随 Esc 一起死靠的就是它，后台任务是例外，普通的中止打不进；二是父节点想收工，得先把孩子节点手里的事等完。1.2 版做过一轮性能改造，官方基准里 500 个任务连环结算从 12 秒降到 50 毫秒。

**⑤ 最上面 Harness** 是出厂自带的部分：模型对话（generation）、执行工具（tool）、压缩上下文（compaction）三个任务内置，不用你写。你加的东西都走扩展：提示词段落、事件钩子、包装工具、自定义任务，装进 registry 就生效。

## 一次问答的完整旅程

拿"修这个测试"这个输入走一遍。全程只发生在已提交状态里：

提交输入后，一个 pi.user 条目和 run 记录同批落盘，对话进入忙碌。generation 任务先在 prepare 阶段渲染系统提示：系统提示是增量的，每次请求前和已展示版本做 diff，只把变化写成补丁条目，provider 的 prompt cache 因此保持温热。如果上下文超过阻塞阈值，它会先创建一个压缩任务并等它完成；超过后台阈值则顺手创建一个后台压缩，不阻塞。

request 阶段流式请求模型，部分回答每 100ms 提交进 pi.live。classify 阶段把响应分类：纯文本就结算 done；带工具调用就追加条目，同一次提交里为每个调用创建一个 pi.tool 任务，然后进入 waiting。

工具任务各自走三明治：提交意图（参数校验、beforeTool 钩子之后），执行（真正的读文件、跑 bash，输出节流提交），提交结果条目。多个调用默认并行，声明 sequential 则串行。工具轮收尾后有个 postTools 边界：你趁忙插的话（steer）在这里放进上下文，然后创建下一个 generation 任务，把 run 的归属交接过去。

所以一次 run 实际上是一条 generation 任务链，每轮一个新任务，靠 pi.live.run 文档交接"谁负责结算这些输入"。工具是 generation 拥有的子任务，压缩可能插进等待链。进程在任何一步死掉，重开后调度器从存储里扫出活任务接着跑。

挑几行崩溃恢复速查表感受一下语义：

| 崩溃时刻 | 重开后的行为 |
|---|---|
| 流式回答到一半 | 已提交部分转 aborted 条目（usage 已计），请求重发 |
| 工具副作用进行中 | replay safe 的重跑；其余合成 interrupted 错误结果，run 继续 |
| 审批已通过 | memo 首写胜出，重放拿到同一决策，不二次审批 |
| 退避重试中 | 到点继续；退避期间改的模型配置生效 |
| 扩展代码没了 | 任务阻塞不终止，装回扩展立即复活 |

## 和 Pi coding agent 是什么关系

两个项目共享 pi-ai 模型层和同一套哲学（极简与可塑），定位完全不同：

| | Pi coding agent | pi-durable |
|---|---|---|
| 形态 | 终端里的单人编码代理 | Agent 应用框架（library） |
| 生命周期 | 一次终端会话 | 天级周级长程运行，随时崩溃随时重连 |
| 交互 | 单人键盘 | Slack、Web UI、API，多端多人在场 |
| 上下文 | 会话内 | 无限长（compaction 滚动压缩） |
| 工具执行 | 内存 agent loop，不持久化 | 每次调用一个持久任务 |

工具系统是"同源契约、各自实现"：两边都以 pi-ai 的 Tool 类型（name、description、parameters 四个字段）为地基，接口刻意对齐（连 replay、executionMode 这些字段都同名同义），但代码独立移植，pi-durable 不依赖编码代理的任何包。内置工具目前是 read、write、edit、bash（含 powershell）加 image 的移植子集。

官方自己给了个对照：仓库里 packages/coding-agent/src/experimental/durable 是用 pi-durable 重建的迷你编码代理。杀掉进程再 --continue，被中断的工具调用得到 interrupted 结果，没跑完的 turn 自动跑完。

1.2 版之后这套地基明显在往"工具平台"方向长：工具可以嵌套调用工具（各自仍是持久任务，重启可重新挂接），可以声明结构化输出，可以标记 deferred 不进系统提示词、由 tool_search 按 BM25 检索按需加载，还有一个 code mode：模型写一段脚本编排工具，脚本本身是持久任务，重启后从日志确定性重放继续跑。

## 拿来二次开发，六个方向

它是 library，不带 UI，你的代码负责界面和触发源。

**IM 常驻机器人**。博客的典型画面就是 Slack：频道映射为一条对话，thread 映射为一次 fork（共享父历史、无需复制），你随时可以 steer 插话，Agent 崩了重启接着聊。团队预告过未来几周会发布自建工具，方向就是 Slack bot 和 GitHub triage bot。

**长程业务编排**。defineTask 定义自己的任务类型，支付是官方示例：Checkout 任务等四个 Payment 子任务，failFast 策略下第一个失败就给其余的发中止标记，abort handler 自底向上清理（退款），进程重启后续跑，等于把 Temporal 那套 durable execution 的思路搬进了 agent 框架。

**前后台子代理**。所有权树加 background 边界，前台子代理随对话中止而死，后台常驻代理不受影响，答案回报后退出。官方示例里两种模式的完整实现都有。

**人机协同审批**。beforeTool 钩子拦截危险操作，memo 保证重启后不重复弹审批。适合内部运维类 agent：高风险命令必须过人，其余全自动。

**云端部署**。可移植核不依赖 Node API，Cloudflare Durable Object 的 SQLite 事务就是一次提交，横向扩展的单位是"一个存储等于一个 Harness"，一个 DO 就是一个分片（1.3 起多个存储可共享一个 DO 数据库）。

**观测与审计**。viewState 和 watchEvents 从已提交状态免费派生出编码代理风格的事件流，可以增量推给远程客户端；taskGraph 是全 Session 活任务树的实时仪表盘；usage 台账按模型和工具记账，失败尝试也计。断线重连从当前快照开始，不重放历史。

## 上手

Node 22.19 以上：

```
npm install @earendil-works/pi-durable @earendil-works/pi-ai @earendil-works/chord
```

仓库 test/examples 下有 32 个可运行示例，值得按顺序看：13-recovery（崩溃恢复）、22 和 23-subagent（前后台子代理）、24-child-tasks（支付编排）、25-compaction（三种压缩）、26-coding-agent（用内置工具搭迷你持久化编码代理）。
