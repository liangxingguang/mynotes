# 本地消息表终极实战｜商城分布式事务落地：最终一致性避坑，Seata 之外最稳方案

聊分布式事务，第一反应就是 Seata。商城交易链路重构时踩过典型误区：下单场景直接引入 Seata AT，大促压测热点商品全局锁争用爆发，事务超时率飙升、下单失败、告警刷屏。

复盘认清的现实：**不是所有最终一致性场景都要上重型分布式事务框架**。下单后发短信、预创建物流、更新热度统计这类链路允许短暂不一致，本地消息表是性价比最高的方案。但工程暗坑极多：消息丢失、重复执行、重试风暴、数据库击穿，任一上线即资损。

## 一、三个核心线上故障案例

### 案例 1：业务与消息写入非原子化，静默丢消息

**现象**：大促部分订单创建成功，但用户收不到短信、无物流预生成记录——订单在，消息凭空消失。

**根因**：业务事务与消息插入拆成两段独立事务。订单提交后，插消息瞬间数据库节点卡顿，消息插入失败。业务数据永久留存，下游动作彻底丢失且无告警。

**修复**：订单记录与消息记录封装在**同一个本地事务**提交，同生共死。

⚠️ **取舍**：单库事务保原子性的代价是拉长事务窗口，热点场景加剧行锁等待。**硬性规范：事务内禁止调用任何远程接口，只做数据库写操作。**

### 案例 2：重试无退避无上限，重试风暴打垮 DB

**现象**：物流接口短暂超时，消费失败。定时任务持续拉取失败消息反复重试，上万条消息循环执行，DB CPU 拉满，正常下单超时，交易链路雪崩。

**根因**：无指数退避、无最大重试次数，下游抖动时失败消息集中爆发。

**修复**：

1. **指数退避**：1min → 3min → 10min → 30min，逐步拉长间隔
2. **最大重试 8 次**，超阈值转死信表
3. **定时任务限流**：单次拉取固定条数，分片限流

**补充**：消息表必须有 `retry_count` 字段，每次重试 +1——仅靠状态字段无法控制重试次数。

**消息状态流转：**

| 流转阶段 | 状态 | 说明 |
|---|---|---|
| 业务事务提交 | INIT（待发送） | 消息随业务数据一同入库 |
| 消费成功 | INIT → SUCCESS | 更新状态 |
| 消费失败 | INIT → FAIL | retry_count += 1，等下轮重试 |
| 达最大重试 | FAIL → DEAD | 死信，实时触发告警 |

### 案例 3：消费成功但状态更新超时，无幂等导致重复业务

**现象**：网络抖动，物流接口已成功建单，但本地更新消息状态 SQL 超时。定时任务再次拉取重试，重复调物流接口，生成多条物流单、用户收多条短信。

**根因**：误以为本地消息表天然防重。消息表只保证**至少投递一次**，无法杜绝重试的重复执行。

**方案**：以业务唯一流水号作幂等 Key，消费逻辑第一步先校验幂等记录。

⚠️ **取舍**：幂等表有存储开销；轻量场景可用唯一索引，但必须捕获冲突异常并**区分「重复请求」和「唯一约束业务冲突」，不能一概判重**，否则掩盖真实业务错误。

## 二、两个速览小案例

**A：消息表无限留存，索引失效查询变慢**——几年历史数据全保留，大促全表扫描拖慢 DB。✅ 冷热分离：已完成消息归档至归档表，主表仅留待处理+近期消息，定期归档脚本。

**B：定时任务单机单点，消费停滞**——单实例宕机后无人拉消息。✅ 分布式锁 + 多实例部署：同一时间只一个实例执行拉取，既防重复调度又解单点。

## 三、方案选型边界（架构评审核心）

**✅ 适合本地消息表**：

- 仅要求最终一致，不要求强一致
- 业务数据和消息表同库，可用本地事务
- 下游允许短暂延迟（短信通知、统计、物流预创建）

**❌ 禁止硬套**：

- 跨库强一致（如下单同时扣余额）
- 千万级超高吞吐——DB 消息表成瓶颈，优先 RocketMQ 事务消息

## 四、生产评审红线清单（任意一条不达标禁止上线）

1. 业务写入与消息写入必须同一本地事务；事务内禁止远程调用
2. 重试强制指数退避 + 最大次数 + 死信表 + 死信实时告警；必须带 retry_count
3. 消费接口必须自带幂等，不能依赖消息表去重
4. 定时任务必须分布式锁 + 多实例，规避单点与重复调度
5. 消息表合理索引，历史成功消息定期冷热归档
6. 死信新增触发告警，禁止人工定期查表巡检

## 五、架构取舍总结

本地消息表的本质：用**单库事务原子性 + 重试机制可靠性**，替代跨库分布式事务的复杂度。优势轻量、可控、易排查；代价是事务窗口拉长、依赖单库、需自建幂等和死信兜底。

选方案前先问：这个场景**到底需不需要毫秒级强一致**？允许短暂不一致，本地消息表就是性价比最高的解。
