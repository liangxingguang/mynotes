# AI 写代码越来越快，研发交付系统该怎么演进？

> 来源：微信公众号「架构师（JiaGouX）」

现在，一项需求最早完成的部分，常常是代码。

Agent 能读仓库、改接口、补测试，也能很快交出一个看起来完整的候选版本。可再往下追问：需求理解对不对，旧接口有没有被破坏，测试验证的是不是这份代码，部署后的实例是否真的生效，答案就没那么快了。

代码写完后，队列并没有消失。它只是换了位置。

过去最费时间的是实现。现在，实现越来越快，需求澄清、变更审查、环境验证和上线确认开始排队。前面跑得越快，后面的等待越容易暴露。

这也是今天想聊的问题：**当 AI Coding 提高了一个环节的产能，研发交付系统该怎样演进，才能让一次变更顺利穿过整套系统？**

## 瓶颈搬家了

软件交付从来不是“写完代码”这一件事。

一项改动从想法走到生产环境，要经过需求、设计、实现、验证、发布和运行观察。每个环节都会产生新事实，也可能推翻前面的判断。代码只是其中最容易被看见的一段。

DORA 在 2025 年的研究中，把 AI 称为组织能力的放大器。边界清楚、测试可靠、平台能力完整的团队，更容易把生成速度变成交付速度；原本需求含糊、系统脆弱、发布依赖人工确认的团队，得到的往往只是更多待审代码。

METR 对成熟开源项目做过一项受控实验。在特定样本和 2025 年初的工具条件下，熟悉仓库的开发者使用 AI 后，完成任务的时间反而增加了 19%。这项结果不能外推成“AI 会拖慢开发”，但它说明了一件事：局部动作变快，不等于整个任务更早完成。

从架构上看，这很像给一条管道换了更大的泵。水流得更快，原本不明显的窄口、弯头和阀门，很快就会成为新的限制。

AI 把编码这一段拓宽以后，研发系统的窄口也随之向两边移动：上游要更准确地表达意图，下游要更快地形成可信证据。

于是，候选代码越来越多，交付队列反而可能更长。生成端按机器速度工作，验证、决策和发布仍按原来的方式排队，新增产能很快就变成了待审变更。

**研发系统最后能交付多少，取决于最慢的那一段，不取决于最快的那一段。**

## 堵点藏在交接里

假设业务提出一个常见需求：给订单列表增加批量导出。

开发 Agent 很快就能补上导出接口、异步任务表和前端按钮。测试 Agent 也能生成一批用例。单看每份产物，似乎都完成了。

代码交出去以后，问题才陆续出现：哪些订单允许导出，谁有权限，文件保留多久；旧客户端依赖同步错误码，新的异步接口是否兼容；测试环境只有几百条数据，大文件和超时怎么验证；发布完成以后，运行中的服务有没有加载新配置。

这些问题不属于某一个 Agent。它们分布在需求、代码、环境和运行系统之间。

如果每个环节只把一份文档或一句“已完成”交给下一个环节，信息就会在交接中逐渐变薄。后面的 Agent 不得不重新读仓库、猜背景、补检查。人也会回到熟悉的工作：翻聊天记录、找会议纪要、确认到底验证过哪个版本。

**多串几个 Agent，解决不了这种断点。**关键不在角色数量，而在一次变更的目标、状态和证据能不能一起往前走。

端到端的重点不在于让一个 Agent 包办九个阶段。变更跨过每个边界时，上一步留下的事实足够清楚，下一步不用重新猜，这条链才算连上了。

## 把交付变成状态机

传统研发流程通常按角色展开：产品写需求，架构师出方案，开发写代码，测试做验证，运维负责发布。这个分工方便组织团队，却不适合直接拿来设计 Agent 系统。

Agent 不需要一张更复杂的岗位表。它需要知道当前处理的是哪一次变更，这次变更处于什么状态，进入下一个状态还缺什么。

昨天拆解 Scion 时，我们把源码层的一次变更分成了“已持久化、已合并、已验证、可部署”。这个区分放到完整交付链路里，还需要向前、向后各补一步：

> 当前意图 → 候选变更 → 已持久化 → 已合并 → 已验证 → 可部署 → 已生效

多造几个状态名没有意义。**这里要避免的，是一句“做完了”同时代表七件不同的事。**

代码已经保存，不代表进入了共享主干；主干已经合并，不代表测试覆盖了当前快照；构建已经部署，也不代表运行实例加载了新版本。每次状态变化，都要回答三件事：变化的是哪个不可变版本，依据是什么，失败后停在哪里。

要让这条链跑起来，三类信息不能分家：状态说明它走到了哪里，证据说明这一步为什么成立，风险门槛决定谁能把它继续往前推。

每次推进都留下旧状态、新状态、对象版本、证据引用和发起者。以后排查问题，不必重放整段对话，只要沿着状态记录就能找到：哪一步放行了哪个版本，当时依据的是什么。

此时，研发系统的核心对象不再是某个 Agent 的对话，而是一次持续推进的变更。Agent 可以更换，任务可以中断，执行环境也可以销毁。状态和证据还在，下一轮就能接着做。

## 规格跟着事实走

Agent 开工前仍然需要规格。目标、约束和验收条件不写清楚，模型只能猜。

规格也不会在开工时一次写死。需求表达的是当前意图，代码和依赖保存着已有约束，运行环境还会不断给出新事实。三者冲突时，系统要更新理解，不能为了执行原计划忽略现实。

Addy Osmani 在讨论 Agent 规格时，强调目标、边界、测试和项目结构。Karpathy 所说的 Context Engineering 也不只是写提示词，而是把任务说明、示例、检索结果、工具、状态和历史装进有限的上下文。

落到研发系统里，规格更像一份会随事实更新、但每次修改都留痕的意图版本。目标和验收条件相对稳定，方案与任务拆分随着证据更新。Agent 发现旧接口仍被外部客户调用，兼容性就要补回约束；发现已有异步任务框架可以复用，改动范围也随之收缩。

规格的价值不在于写得长，而在于每次变化都有来由。后来的人能看见，哪项决定来自业务目标，哪项调整来自代码事实，哪项限制来自运行环境。

把整份需求、全部仓库知识和所有历史记录一次塞进上下文，通常不够稳。当前做到哪一步，就取哪一小片材料：设计批量导出接口时，需要权限、数据范围和兼容约束；走到发布时，需要构建版本、配置变化和回滚条件。上下文跟着状态选择，关键约束不容易漏，也不会被无关材料淹没。

## Harness 留住现场

长任务很少一次完成。Agent 要读仓库、调用工具、修改文件、等待测试，也会遇到权限不足、依赖失败、上下文压缩和任务转交。

只保留最终回复，真正的执行现场就丢了。

Harness 保存的是这些容易消失的状态：任务走到哪一步，调用过什么工具，产生了哪些变更，正在等待什么结果，哪里可以安全重试，哪里必须先回读外部系统。

这部分看起来不像“智能”，却决定了系统能否恢复。测试超时以后，状态可能是失败，也可能是仍在运行；发布请求没有返回，远端可能已经创建了新版本。把这些情况都压成“失败，再试一次”，很容易制造重复资源或二次发布。

执行状态和业务事实也要分开。**Harness 保存执行现场，业务系统保存权威事实。**Harness 可以记住“发布请求已经发出，正在等待回读”，却不能因为一次请求超时，就自行把业务状态写成“发布失败”。

模型适合处理含糊问题，状态机适合守住确定边界。两者分开，Agent 才能在不确定的研发任务里持续工作，又不会把外部状态越改越乱。

## 证据绑定版本

代码生成得越多，验证越不能靠生成者自证。

“单元测试通过”需要说明测试对应哪个提交；“部署成功”需要说明目标环境运行的是哪个构建；“配置已更新”还要确认实例已经加载。证据如果没有绑定版本、环境和时间，过一会儿就很难再用。

Addy Osmani 在 Agentic Code Quality 中提到，随着 Agent 生成更多代码，质量检查会更多地进入 Harness、环境和确定性约束。AgentSWE 公开的失败轨迹也很典型：实现只贴合可见样例，运行时看似完整、内部却是空壳，以及在证据不足时直接宣称完成。

越早把验证交给模型之外的确定性工具，后面的结论越可靠。接口契约交给测试，构建产物记录摘要和来源，外部动作通过资源 ID 回读，发布以后再检查真实流量和指标。只有结果本身需要语义判断时，再让模型参与评估，并保留它引用的材料和判断口径。

一条证据链可能长这样：

> 意图 v3 → 代码 c7 → 构建 b12 → 测试 r19 → 发布 d4 → 运行回读 o8

编号只是示意，引用关系才有用。测试 r19 只证明构建 b12；如果代码已经变成 c8，旧测试就不能继续给新版本背书。发布 d4 也只有在运行回读指向同一构建时，才能说明线上真正生效。

**完成不是某个 Agent 给出的结论，而是一组能够回查的事实。**

## 知识也会过期

Agent 进入完整研发流程以后，会越来越依赖项目知识：架构约束、接口惯例、故障记录、审核意见、历史决策。这些内容能减少重复探索，也可能把旧结论带进新任务。

腾讯 OK 的公开实践里有一个很实在的处理：知识带有效期；Agent 发现知识与当前代码不一致时可以反馈；主干出现新提交后，再增量刷新仓库描述。这个细节比简单统计沉淀了多少文档更接近工程问题。

在这套系统里，**知识库更接近缓存；代码、配置和运行系统才是事实来源。**缓存没有版本、来源和更新时间，数量越多，冲突越难发现。可靠的知识进入上下文时，至少能追溯到它从哪里来、针对哪个版本、什么时候需要复核。发现冲突以后，系统也不该让 Agent 在两份说法里自行挑一份，而要回到事实源重新确认。

这样的知识回路会把一次失败写回规格、测试或 Harness，下一次相似变更直接继承新的约束。组织能力是在这里积累的，不在某个 Agent 越来越长的聊天记录里。

## 人守住分叉口

Martin Fowler 强调，人仍要对软件的行为和实现负责。Kief Morris 则把人的位置描述为从“in the loop”移到“on the loop”：人不再逐步告诉 Agent 每一行怎么改，而是设计工作回路，给出规格、检查和升级条件。

人仍在研发过程里，只是注意力从重复执行移到了更难委托的分叉口：为什么要做这项变更，多个约束冲突时保留哪一个，哪些风险可以自动继续，哪些动作必须有人确认。

低风险、单仓库、容易回滚的改动，可以在明确边界内自动推进。涉及数据迁移、资金、权限、公开 API 或跨团队承诺时，系统停在具体状态，把决定交给有权限的人。

这种分流不必只看任务名称。改动范围、可回滚性、数据影响和外部承诺，都能成为门槛的一部分。同样是“改一个接口”，内部实验接口和已经被客户依赖的公开接口，显然不该走同一条自动化路径。

**人守住的是业务取舍和系统边界，不必再充当每个环节之间的传话人。**

## 先跑通一条链

端到端研发很容易被画成一张大图：多个 Agent、统一知识库、自动评审、自动发布，一次全部到位。图很完整，真正难的状态转换却可能一个都没跑通。

如果从小处落地，我更愿意先挑一类边界清楚的需求，例如单仓库里的内部接口或低风险配置变更。先把这一类变更的状态、证据和升级条件跑顺，让 Agent 能读代码、做修改、跑验证，也能在失败后停在可恢复状态。

这时，我会更关心“交付得怎样”，而不是“生成了多少”：需求到可验证变更用了多久，发生了几次返工，人工等待占多少时间，未知状态出现多少次，一次失败要多久才能恢复。

这些数字不会直接回答系统该怎么设计，却能指出队列搬到了哪里。

AI Coding 让候选代码更早出现。接下来真正影响交付速度的，是研发系统能不能沿着同一次变更，保存意图、执行状态、验证证据和运行结果；底层事实发生变化时，也能知道哪些旧判断已经失效。

判断一条链路是否成熟，也许只需要做一个很朴素的检查：任务中断、人员交接或部署超时以后，下一位工程师或 Agent 能否从系统事实继续工作，还是仍要翻聊天记录、到处问人，再猜一次远端现在是什么状态。

如果还要猜，堵点就不在写代码。
