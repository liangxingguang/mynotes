**💡 系列导读**

很多人落地本地消息表，以为把消息状态机写对就万事大吉了。大促放量 40 分钟，重复扣券事故直接告诉你：**重试不是附加功能，是这套一致性方案赖以生存的基础；一旦开启重试，就必须接受重复执行的可能性。**

本文基于商城真实重复扣券事故，从底层机制拆解异步重复流量的来源与特征，逐一对比四类幂等方案的取舍边界，最后给出分层防护闭环架构。核心结论只有一句话：**幂等不是独立可选功能，是整套最终一致性体系中不可分割的一环。**

**01\. 现象复盘：大促突发重复扣券事故**

去年商城大促压测放量阶段，整套基于本地消息表的最终一致性链路，单元测试、集成测试、单链路压测全部通过，指标表现平稳。上线放量至峰值 40 分钟，优惠券对账告警触发：部分用户单笔订单，连续扣减两张优惠券。

第一时间排查本地消息表状态流转逻辑，消息状态仅分为待处理、处理成功、处理失败三态，代码评审阶段确认状态机无分支漏洞。拉取数据库 binlog 后发现一个诡异事实：消息表最终标记为成功，但业务侧优惠券扣减逻辑执行了两次。

根因回溯：业务扣券逻辑执行成功，事务提交瞬间，数据库出现毫秒级网络抖动，本地消息表状态更新语句落地出现确认异常。很多人会默认，同一个事务内要么全部成功、要么全部回滚，忽略了这种边界场景：TCP 是面向连接的协议，DB 完成事务提交后返回 ACK 报文，若网络抖动导致这个 ACK 丢包，应用端判定为超时。**数据库事务已经落地，但应用侧无法确认结果，这就是分布式系统经典的「不确定结果」问题。**定时任务扫描到这条仍然处于待处理状态的消息，再次触发消费逻辑，重复执行扣券。

**🔑 最反直觉的结论：**本地消息表的重试自愈能力，本身就是重复执行的源头。重试不是附加功能，是这套一致性方案赖以生存的基础；一旦开启重试，就必须接受重复执行的可能性。

很多团队落地本地消息表，重心全部放在消息状态流转、事务编排，默认只要状态机写对，就能保证最终一致。异步链路里，MQ 主从切换、支付平台回调重试、本地消息定时轮询，产生的重复流量，属于系统自治产生的内部重复，不是用户手动重复点击。**前端防抖、一次性 Token 这类面向人的防护手段，完全无法拦截。这也是异步幂等和同步接口幂等最核心的边界。**

**02\. 底层机制拆解：异步场景下重复流量的来源与特征**

同步接口的重复请求，触发主体是终端用户，流量特征离散，可在接入层拦截。而异步链路重复流量，是分布式系统网络不可靠带来的固有产物，无法彻底根除，只能做副作用隔离：

**1\. 本地消息表重试：**业务事务执行完成，事务 commit 回执丢失，应用捕获超时异常，消息停留在待处理状态。定时任务扫描轮询，自动重试整条业务逻辑。

**2\. RocketMQ 消息重放：**Broker 主节点宕机，集群切换，消费者未成功提交 offset。新主节点投递已消费但位点未确认的消息，也就是消息重放。

**3\. 第三方支付回调：**支付平台的重试策略是兜底机制，只要我方返回非 200 成功、连接超时，平台会持续推送回调，无论订单业务是否完成扣款发货。

**⚠️ 第一大坑：**很多团队试图从源头消灭重复流量。关闭重试，确实不会重复执行，但直接引入消息丢失、数据不一致。重试是故障自愈，幂等是配套约束。二者共生，不可单独取舍。

**幂等本质目标不是拦截请求，**而是基于业务领域状态，判断本次动作是否已经持久化落地；若已完成，直接跳过业务变更，仅返回成功。

**03\. 工程踩坑细节：四类幂等方案的取舍与代价**

**方案一：数据库唯一索引**

很多工程师优先选择唯一索引，以业务唯一标识建立唯一约束，重复写入直接抛出唯一冲突异常。

优点：数据库原生保障，实现成本极低，业务代码改动少。

**工程隐性代价**

高并发重试场景，多条并发请求争抢同一唯一索引记录，触发大量行锁等待，大促峰值会放大数据库压力；分库分表架构下，幂等记录必须和业务数据落在同一个分片，跨分片场景无法直接复用；

极易被忽略的短板：唯一索引仅能拦截新增类写入，**无法防护状态变更操作**。订单、优惠券状态更新语句，重复执行不会触发唯一冲突，依然会重复执行业务动作。

**✅ 取舍结论：**新增流水、单据创建这类场景可有限使用；扣减库存、优惠券、状态流转场景，**绝对不能单独依赖唯一索引**。

**方案二：幂等记录表（业务流水幂等）**

独立幂等表，存储全局幂等键、业务类型、业务单据号，执行业务前先查询幂等记录。

标准流程：开启事务 → 查询幂等记录 → 不存在则执行业务逻辑，写入幂等记录 → 提交事务。

**❌ 致命竞态漏洞**

查询与写入非原子。不加锁的前提下，两条重试请求同时查询，都判定记录不存在，双双执行业务逻辑，直接造成重复扣款。

**解决方案：**查询、业务执行、幂等记录写入放到同一个事务，依靠唯一索引保护幂等表，杜绝并发竞态。

**长期运维债务**

幂等表持续写入，大促期间数据高速膨胀。如果缺少归档清理策略，半年表数据上亿，幂等键检索性能持续衰减，查询 RT 上涨，拖慢整条异步链路。

**✅ 落地规范：**幂等记录增加 expire\_time 过期字段，业务闭环超过保留窗口的数据，离线迁移归档至历史库；线上业务库仅保留最近 N 天幂等数据。

幂等表建表核心 SQL

```sql
CREATE TABLE biz_idempotent_record (
  id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '主键',
  idempotent_key VARCHAR(128) NOT NULL COMMENT '全局幂等键:msgId/支付流水号',
  biz_type TINYINT NOT NULL COMMENT '业务类型：优惠券/订单/库存',
  biz_no VARCHAR(64) NOT NULL COMMENT '业务单据号',
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  expire_time DATETIME NOT NULL COMMENT '过期归档时间',
  UNIQUE KEY uk_idempotent_key (idempotent_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**注解：**uk 唯一索引用来解决并发竞态；expire\_time 是绝大多数方案遗漏的设计，用于离线归档清理，防止表无限膨胀。

**方案三：业务状态机幂等（商城主推方案）**

订单、优惠券、库存这类具备完整生命周期的领域对象，可以依托业务自身领域状态实现幂等。执行业务动作前，校验领域对象当前状态，只有处于允许变更的状态，才执行业务变更。

优惠券扣减场景规则：优惠券状态为**【未使用】**才允许扣减；状态已经是**【已扣减】**，直接返回成功，跳过扣减逻辑。

**❌ 当年线上故障版本代码（竞态缺陷）**

```java
// 故障版本：状态校验脱离事务隔离，并发重试必然竞态
public void consumeCouponMsg(String msgId, Long couponId){
  // 查询在事务之外！并发重试会读到过期快照状态
  Coupon coupon = couponMapper.selectById(couponId);
  if(!CouponStatus.UNUSED.equals(coupon.getStatus())){
    log.info("消息重复，优惠券已扣减 msgId:{}", msgId);
    return;
  }
  // 错误：事务内的业务操作与状态校验分离
  couponMapper.deductCoupon(couponId, CouponStatus.USED);
  localMsgMapper.updateStatus(msgId, MsgStatus.SUCCESS);
}
```

**❌ 复盘解读**

这段代码是当年缺陷逻辑的简化演示，核心问题不是注解写法，而是**状态校验脱离事务隔离**。单元测试、普通流量下看不出问题，只有大促并发重试流量才会触发。两个重试线程几乎同一时刻查询数据库，都读到优惠券状态为未使用，先后进入事务。数据库行锁串行执行两次扣减语句，最终优惠券被扣减两次。

**核心红线：**领域状态校验和业务变更，必须包裹在同一个数据库事务内。状态校验脱离事务，并发场景必然出现竞态漏洞。

**✅ 修复后的核心业务代码**

```java
// 修复版：状态校验、业务扣减、消息状态更新封装在同一事务
@Transactional(rollbackFor = Exception.class)
public void consumeCouponMsg(String msgId, Long couponId){
  // 1. 业务状态校验（全部纳入事务）
  Coupon coupon = couponMapper.selectById(couponId);
  if(!CouponStatus.UNUSED.equals(coupon.getStatus())){
    log.info("消息重复，优惠券已完成扣减 msgId:{} couponId:{}", msgId, couponId);
    return;
  }
  // 2. 执行业务扣减 + 更新业务状态（事务内原子操作）
  int rows = couponMapper.deductCoupon(couponId, CouponStatus.USED);
  if(rows <= 0){
    throw new BizException("优惠券扣减失败，状态变更无行数");
  }
  // 3. 更新本地消息表状态，标记已完成
  localMsgMapper.updateStatus(msgId, MsgStatus.SUCCESS);
}
```

**✅ 配套文字注解：**状态校验、业务扣减、消息状态更新，全部封装在同一个本地事务。如果事务提交阶段网络抖动，应用收到 commit 超时，数据库事务实际提交成功。定时任务重试再次进入方法，查询优惠券状态已经是 USED，直接返回，不会二次扣减。

**优势：**无需额外新建幂等表，没有额外存储开销，业务语义贴合领域模型，故障排查直观。

**边界约束：**仅适用于带有明确生命周期、状态流转的领域实体；纯通知、推送这类无状态操作无法使用；状态校验与状态变更不能拆分，拆分就会引入并发竞态漏洞。

**💡 取舍代价：**状态机幂等不是万能方案。如果是纯消息通知场景，比如推送短信、站内信，业务实体不存在状态流转，强行套用状态机，只会污染领域模型，这类场景更适合独立幂等记录表。状态机幂等本身也要求业务模型维护完整的状态生命周期，对应的领域建模复杂度会同步抬升。

**方案四：Token 防重（同步场景专用，异步链路直接无效）**

一次性 Token 方案面向前端接口，用户请求前获取 Token，后端一次性消耗 Token 实现防重。

但 MQ 重放、第三方支付回调这类后端异步流量，根本不会携带前端一次性 Token。很多团队直接把同步接口防重方案复用在异步链路，上线后幂等防护完全失效。**Token 方案在异步链路没有任何防护能力，不可混用。**

**04\. 隐性控制面风险：容易被忽略的幂等体系缺陷**

**风险一：幂等键设计缺陷**

幂等键不能随意选取，必须是**全局唯一、业务含义稳定、多次重试不会变化**的标识。

错误选型：自增 ID、服务本地随机串；重试场景每次生成新值，丧失防重能力。

正确选型：业务单据号、支付平台回调流水号、MQ 消息 msgId + topic 组合。

额外注意：第三方外部传入 ID，必须做合法性校验，防止恶意构造 ID 绕过幂等逻辑。

**风险二：幂等逻辑的超时与补偿边界**

幂等校验通过，不等于业务一定落地。业务执行中途崩溃，幂等记录写入成功，但业务变更未执行。后续重试，幂等判断直接放行，不会再次执行业务，形成永久数据缺口。

这是分布式架构经典矛盾：幂等记录前置写入，会出现幂等标记已存在，业务未落地；后置写入幂等记录，并发场景无法阻挡重复执行。

**✅ 解决方案：**幂等记录、业务数据、消息状态，在**同一个本地事务内提交**。本地消息表方案刚好满足这个条件，这也是本地消息表搭配业务状态机幂等成为商城首选组合的根本原因。

**风险三：缓存幂等的击穿风险**

部分团队使用 Redis 存储幂等标记，查询 Redis 判断是否已经执行。

**⚠️ 隐患：**Redis 集群宕机、key 过期、网络闪断，缓存查询异常时，业务直接放行，重复执行。Redis 缓存仅适合前置快速拦截，**绝对不能作为唯一幂等数据源**，底层必须依靠数据库持久化兜底。缓存只是性能优化手段，不能替代持久存储。

**05\. 多层架构闭环：异步链路分层幂等设计**

不要试图一套幂等方案覆盖全部流量入口。商城生产架构采用分层防护策略，不同流量入口，匹配对应的防重机制，形成多层防护闭环：

**1\. MQ 消费链路：**msgId + topic 组合作为幂等键，结合业务状态机校验；Redis 前置快速校验，数据库兜底；

**2\. 第三方支付回调：**使用支付平台交易流水号作为幂等键，订单业务状态二次校验；

**3\. 本地消息表重试链路：**依托业务领域状态机，联动消息表状态校验，为本场景核心防护层。

**🏗️ 分层设计的核心思想：**外层快速拦截，底层持久化兜底。外层缓存失效，数据库层守住最后防线，不会直接击穿业务。分层不是重复造轮子，是故障域隔离，避免单点组件失效导致整套防重体系崩溃。

**06\. 落地评审清单（架构评审直接复用）**

**1.** 幂等键是否全局唯一，外部传入 ID 是否做合法性校验；

**2.** 幂等校验和业务变更，是否封装在同一个数据库事务；

**3.** 是否评估并发竞态场景，是否存在查询和写入非原子的漏洞；

**4.** 幂等记录表是否设计归档、过期清理策略，评估长期存储成本；

**5.** 区分流量入口：MQ / 回调 / 本地消息重试，各自幂等方案是否匹配；

**6.** 缓存幂等仅作为前置优化，是否存在把缓存当作唯一数据源的情况；

**7.** 故障预案：幂等逻辑异常、脏数据产生后，数据修复脚本是否提前准备；

**8.** 压测验证：并发重试场景做专项压测，验证高并发下幂等防护有效性。

**07\. 架构体系升维总结**

很多架构师看待幂等，仅仅把它当成开发层面的工具函数，加唯一索引、写几行判断逻辑就算落地。放到分布式异步体系视角，幂等本质是**分布式重试自愈机制的配套约束层**。

本地消息表依靠重试解决消息丢失、数据不一致问题，而重试天然引入重复执行风险。幂等不是独立可选功能，是整套最终一致性体系中不可分割的一环。

不存在万能的幂等方案。唯一索引、独立幂等表、业务状态机，各自有适用边界、性能开销、长期运维债务。

**🎯 架构取舍的核心：**不是追求最强的防重能力，而是结合业务领域模型、流量峰值特征、存储成本，划定清晰的边界，构建分层可控的防护闭环。脱离业务场景盲目叠加幂等逻辑，只会增加系统复杂度，埋下数据卡死、故障难以修复的隐性技术债务。**分布式架构设计，本质就是在各类内在矛盾之间寻找可控平衡点。**
