> 最冤的一类线上问题：代码明明改了，行为还是旧的。这篇讲三件事——用 jad / sc / sm 确认线上跑的是哪版代码，为什么"改了没生效"通常有四个原因，以及 redefine 能改什么、不能改什么、为什么它只适合临时止血。

有一类线上问题特别冤：

**代码明明改了，线上行为还是旧的。**

这时候最容易犯的错，是直接怀疑"发布没成功"，然后重新发一遍。但如果实际原因是**类加载器加载了两份**，重发也没用。

正确顺序是先确认，再动手。

## 三个"看"的命令

### jad：反编译当前已加载的类

`jad 类名`，它把 JVM 里**实际加载的那份字节码**反编译出来。

这句话的重点是"实际加载"。你本地 IDE 里看到的是源码，线上跑的是编译产物，两者可能不是同一版。

判断方法很直接：看你改的那行在不在。不在，就说明线上没跑你的代码。

### sc -d：这个类是谁加载的

`sc -d 类名`，能看到类的详细信息，其中两个字段最有用：

*   **ClassLoader 的标识**：同一个类被不同 ClassLoader 加载，会有两份互不相干的 Class 对象。
    
*   **代码来源**：这个类是从哪个 jar 或目录加载的。
    

**如果同一个类名出现了两个不同的 ClassLoader，你的问题就找到了。**

### sm：这个方法长什么样

`sm 类名 方法名`，看方法的签名信息。

它适合确认"方法到底存不存在、参数是不是这个"。有时候你以为调用的是 A 方法，实际走的是重载的 B 方法。

## "改了没生效"的四个常见原因

**一、发布根本没到这台机器。** 集群里只发了一部分，或者灰度没覆盖到出问题的那台。

**二、多 ClassLoader 加载了旧类。** 热部署、插件化、自定义 ClassLoader 都可能造成这个结果。`sc -d` 一看就知道。

**三、热部署没真正生效。** 有些环境的热部署只重载了部分类，被引用的旧类还在。

**四、改的分支没合进去。** 发布的是 release 分支，你改在 feature 分支上。这个最常见，也最容易被忽略。

前三个用命令能确认，第四个只能去看发布记录。

## redefine：能改什么，不能改什么

`redefine` 是热替换已加载的类，它底层用的是 JVM 的 Instrumentation 机制。

**它能做的很有限：**

*   只能改**方法体内部的逻辑**。
    
*   不能新增或删除字段。
    
*   不能新增或删除方法。
    
*   不能修改方法签名。
    

**而且有个前提：正在执行的方法没退出，新的逻辑不会生效。** 所以替换完如果立刻还是老行为，不代表失败，等那批请求跑完再看。

还有一个细节：Arthas 底层做了"内存编译"的处理（把源码在内存里编译成字节码再替换），成功率高一些，但这不改变上面的边界。

## 三个风险，必须知道

**一、和框架的增强机制冲突。** Spring 的代理、各类字节码增强框架，都可能和你替换后的类对不上，表现是"方法进去了但注入的对象不对"。

**二、类结构不一致会引发更难查的问题。** 字段、方法对不上的情况下强行替换，可能让后续调用出现意料之外的行为。

**三、它只是临时止血。****下一次正常发布，你的热替换就被覆盖了，问题会原样回来。** 如果没记录，几周后同样的故障会再来一遍。

## 正确的姿势

1.  用 `jad` 确认线上代码版本，先排除"根本没生效"。
    
2.  用 `sc -d` 检查是不是多 ClassLoader。
    
3.  在**测试环境**验证你的 redefine 命令。
    
4.  生产上只做临时止血，同时记一条明确的 TODO。
    
5.  走正常发布覆盖掉，别让热更新变成"隐形的一版代码"。

热更新最大的诱惑是"不用发布就能修"。

但也正因为不用发布，它**不会留下任何版本记录**——三个月后没人知道线上那版代码曾经被改过。

真要长期可靠，还是得走发布。
