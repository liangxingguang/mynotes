# Pi 实用技巧系列（四）：联网与并行的实战方案

# Pi 实用技巧系列（四）：联网与并行的实战方案

> 抓取正文（web-fetch, browser 级）。原始出处：https://mp.weixin.qq.com/s/5ZRpRUFVM3DtudXweQHCRA

### 〇、前言：Pi 不内置联网，但 MCP 已经原生

Pi 核心给模型四个工具：read、write、edit、bash。没有 WebSearch，没有 WebFetch。模型不能直接联网查最新资讯。

（先说一句变化：MCP 的情况已经和早期不一样了。PI 在 0.99 版本把 MCP 客户端原生内置，1.0 正式版又补齐了 OAuth 登录与凭证安全。所以「Pi 能不能连 MCP 服务器」如今的标准答案是「内置支持，不用再装社区桥接包（pi-mcp-adapter 这类历史方案仅作兼容）」。MCP 的协议细节、服务器配置、OAuth 流程，系列里已有专文细讲，本篇不展开安装与配置步骤，只保留它「把 Pi 接到外部工具/系统」这部分说明。）

这不是漏掉的功能，而是 Pi 的设计立场。Mario Zechner 的观点是：联网能力应该是扩展的事情，不是核心内置的事情——你需要联网，就加一个联网扩展。核心保持极小，扩展自由组合。

这一设计带来两个结果：

1. **Pi 默认是离线的**。你不装扩展，它查不了网。
2. **联网/外部能力全靠扩展生态**。MCP 现已内置；其余能力（联网搜索、浏览器自动化、并行子代理）仍由社区扩展与自建 Skill 支撑。

这一篇就是来梳理：Pi 要联网、要接 MCP 外部工具、要并行、要控制浏览器，社区与内置里有哪些桥接方案，分别适合什么场景，怎么选。

* * *

### 一、先看看 Pi 连接外界的四种路线

| 路线 | 代表扩展/包 | 解决的问题 | 适合场景 |
|---|---|---|---|
| MCP（内置客户端） | PI 原生 | 连接外部工具与系统（数据库、API、SaaS…） | 接具体外部系统/可执行工具 |
| pi-web-access | 社区包 | 联网搜索和内容提取 | 需要查最新信息、抓网页 |
| 自建 Skill + CDP | Armin 的做法 | 控制真实浏览器，做浏览器自动化 | 需要与网页交互、验证表单、截图 |
| pi-side-agents | 社区包 | 生成子代理并行处理任务 | 多任务并行调查/写作/查错 |

此外还有 pi-draw（画流程图）、pi-web（浏览器界面）、pi-acp（ACP 适配器接入 IDE）等，但它们不在「连接外界」的核心问题里，这一篇不展开。

这四种路线不是互斥的。可以同时装多个，按任务选。

* * *

### 二、MCP：把 Pi 接到外部工具与系统（已内置，不展开配置）

#### 现状：MCP 已经原生，不用再装桥接包

PI 从 0.99 起把 MCP 客户端原生内置，1.0 正式版补齐了 OAuth 登录与凭证安全。也就是说，Pi 现在直接就能连 MCP 服务器，标准答案是「内置支持」，不需要再装社区桥接包（pi-mcp-adapter 这类历史方案仅作兼容）。

#### 它把 Pi 连到什么（重点保留）

MCP 的价值在于「客户端—服务器」模型：Pi 作为客户端，通过 MCP 协议对接一台台外部服务器，把模型原本没有的能力接进来。常见能连的外部资源包括：

- **数据源**：数据库、数据仓库、本地文件、对象存储；
- **在线服务**：搜索、日历、邮件、工单、各种 SaaS API；
- **工具与执行环境**：命令行、浏览器、代码运行器、CI；
- **业务系统**：内部 API、知识库、CRM 等。

本质上，MCP 是 Pi 连接「外部世界工具」的一条标准化总线：你接上哪台服务器，Pi 就多出哪类能力。这和「联网查信息」（pi-web-access）不同——MCP 接的是可执行的工具/系统，而不只是抓取网页文本。

#### 什么时候该用 MCP

- **需要把 Pi 接到某个具体的外部系统/工具**（数据库、内部 API、SaaS）。
- **想要标准化的接入方式**，避免为每个工具各写一个 Skill。
- **已经有现成的 MCP 服务器**可用。

#### 什么时候不用

- 只是想查最新资讯、读网页 —— 用 pi-web-access 更轻。
- 只是想控制浏览器做交互 —— 用自建 CDP Skill（见下一条）。
- 只是想并行跑任务 —— 用 pi-side-agents。

* * *

### 三、pi-web-access：联网搜索和内容提取

#### 它是什么

pi-web-access 是社区包，给 Pi 加联网能力。通常包括：

- **联网搜索**：查最新信息，获取搜索结果。
- **内容提取**：抓取网页内容，喂给模型阅读。

#### 什么时候该用

- **需要查最新资讯**。代码库的最新版本、技术文档更新、社区动态等，靠离线知识不够。
- **需要抓取网页内容**。指定的文档页面、博客文章、技术资料，想让 Pi 读一下。
- **信息收集任务**。调查某个技术、某个产品、某个项目，联网搜集信息。

#### 使用例子

用户：查一下目前最新的 Node.js LTS 版本是什么
Pi: [调用 web-access 搜索，返回结果]

用户：读取这篇技术文档 https://example.com/guide
Pi: [调用 web-access 抓取页面内容，读给模型]

#### 局限与注意

- **联网质量依赖底层服务**。web-access 的搜索能力取决于它使用的搜索服务。有些实现可能用免费的搜索 API，有些可能需要配置密钥。
- **抓取受网站限制**。有的网站禁止爬虫，有的页面是动态渲染的，简单抓取拿不到完整内容。这种情况可能需要浏览器级别的抓取（见下一条）。
- **联网是有风险的**。联网扩展会向外发送请求，返回外部内容。检查扩展的行为范围，确保它只做你想要的事情。

### 四、自建 Skill + CDP：浏览器自动化的另一条路线

#### Armin 的做法

Armin Ronacher（mitsuhiko）在他的博客和 agent-stuff 仓库里提到，他用 Skill + CDP（Chrome DevTools Protocol）来做浏览器自动化。

他的逻辑是：

- 桥接外部能力，MCP 是一条标准化路，但直接控制浏览器也是一条独立的路。只要能控制浏览器，模型就能和网页交互。
- CDP 是直接的浏览器控制协议。不需要额外的服务器层，直接跟浏览器对象打交道。
- 自建 Skill 把 CDP 包装成模型能调用的工具。模型需要操作浏览器的时候，调用 Skill 里的工具，Skill 底层用 CDP 和浏览器通信。

这是在说明：控制浏览器、和外部网页交互的能力，不一定非要依赖社区包或 MCP。根据需求自己写一个 Skill，用 CDP、Playwright、Puppeteer 等底层工具控制浏览器，也是一种正经路线。

#### 什么时候该用自建 Skill + CDP

- **需要真实浏览器交互**。比如填写表单、点击按钮、验证动态渲染的页面、截图。
- **现有网络扩展不能满足**。比如要模拟特定用户操作流程，不只是查信息。
- **想完全控制自动化行为**。自建意味着你定义工具的语义、限制、安全边界。

#### 什么时候不用

- **简单的信息获取**。查个版本号、读篇文档，用 pi-web-access 更省事。
- **不想写代码**。自建意味着写 Skill/扩展。有现成的包能用，就用现成的。

#### 这条路线的成本

- **开发成本**。需要写 Skill 或扩展，封装 CDP/Playwright 的调用。
- **维护成本**。浏览器自动化依赖浏览器版本、协议稳定性，长期可能需要调整。
- **安全边界由你定义**。自建意味着你负责确保自动化行为在可控范围内。

### 五、pi-side-agents：多任务并行

#### 它是什么

pi-side-agents 是社区包，让 Pi 能生成子代理并行处理任务。Pi 本身不内置子代理能力（系列四提过），社区提供了这个包来补充。

#### 什么时候该用

- **同时跑多个独立任务**。比如调查三个不同技术方案、并行写多篇文档、并行查几个代码库的差异。
- **任务之间没有依赖**。可以并行，不需要按顺序。

#### 和联网的关系

pi-side-agents 本身不是联网扩展。它是多任务并行能力。但组合起来有用：比如一个子代理负责联网查信息，另一个负责代码审查，彼此独立。

#### 局限

- **Pi 还是单进程**。子代理是通过扩展模拟的，并不是真正的进程隔离。资源分配和隔离程度有限。
- **管理多个 agent 的上下文**。多个 agent 并行，上下文管理更复杂。需要注意结果整合。

### 六、怎么选：四条路线的决策

| 你的需求 | 推荐路线 | 说明 |
|---|---|---|
| 接具体外部系统/工具（DB、API、SaaS） | MCP（内置） | 标准化接入 |
| 查最新信息、读网页 | pi-web-access | 直接联网 |
| 需要控制浏览器、交互网页 | 自建 Skill + CDP | 更细粒度的控制 |
| 需要并行跑多个任务 | pi-side-agents | 多 agent 并行 |
| 简单信息获取 + 并行任务 | pi-web-access + pi-side-agents | 组合使用 |
| 没有浏览器控制需求 | pi-web-access / MCP 单独够用 | 最轻量 |
| 想完全自控浏览器行为 | 自建 Skill + CDP | 自建最灵活 |

#### 组合使用的例子

一个实际场景：调查某个技术的最新状态，同时写一份对比文档。

```
# 子代理 1：联网调查
调用 pi-web-access，查最新版本、社区反馈、竞品动态

# 子代理 2：写文档
基于子代理 1 的调查结果，组织对比文档

# 如果需要浏览器验证
其中一个子代理用自建 CDP Skill 验证官网演示
```

这种组合下，联网靠 pi-web-access，浏览器控制靠自建 CDP，多任务靠 pi-side-agents，外部系统接入靠 MCP，各司其职。

### 七、装社区扩展的安全注意

Pi 的扩展运行在宿主系统的完整权限下。装社区扩展之前，看源码是必要习惯。具体检查：

- **扩展做了什么**。联网扩展向外发送请求、读取返回内容。确认它只请求你允许的目标。
- **有没有不必要的权限**。比如一个查信息的扩展不应该有写文件权限。
- **Maintainer 是谁**。知名度高的开发者（Armin、社区知名成员）的扩展相对更可信，但依然要看代码。
- **包的来源**。npm 包、git 仓库，确认来源可靠。避免使用来历不明的包。

这一点在系列一和系列七都提过：Pi 的生态扩展很自由，但自由意味着你得自己负责安全评估。

* * *

### 八、客观评价与风险

#### 联网扩展的局限

- **联网质量不稳定**。搜索 APIs、有网页抓取限制，会影响结果质量。
- **信息真实性**。联网返回的信息可能过时、片面。模型可能会把联网信息当作可信任的来源，不加批判。用户需要自行判断。
- **依赖外部服务**。联网扩展依赖底层搜索引擎或抓取服务。服务改变、停掉，扩展可能失效。

#### 自建路线的局限

- **开发和维护成本**。
- **浏览器依赖**。CDP/Playwright 的版本兼容性问题可能需要处理。

#### MCP 路线的局限

- **能力取决于服务器**。Pi 能接什么，由你接入的 MCP 服务器决定；没有现成服务器时，仍要自己写或找。
- **配置与安全面**。连外部系统意味着把凭证/权限交给那台服务器，OAuth 与最小授权仍是你要自己把关的事。

#### 多代理的局限

- **真隔离度有限**。Pi 的子代理扩展不是真正的进程隔离。
- **协调复杂**。多个 agent 的结果整合需要额外处理。

#### 其他注意

- **别装过多联网扩展**。会增加上下文复杂度和潜在安全面。
- **扩展按需加载**。和其它 Skill 一样，联网扩展可以在需要时加载，不用时不占提示词缓存。

* * *

### 十、选型总结表

| 需求 | 最小方案 | 完整方案 |
|---|---|---|
| 接外部工具/系统 | MCP（内置） | MCP + 结果整合 |
| 查信息、读网页 | pi-web-access | pi-web-access + 自建 CDP（如果需要交互） |
| 浏览器自动化 | 自建 Skill + CDP | 自建 Skill + CDP + 子代理管理 |
| 多任务并行 | pi-side-agents | pi-side-agents + 联网扩展 + 结果整合脚本 |
