## 三、核心技术原理

### 3.1 分片处理（Sharding）

**分片**是将大任务拆分成多个小任务的核心思想。对于百万级推送，分片方式有：

分片方式

实现

适用场景

**按 ID 范围分片**

`WHERE id BETWEEN ? AND ?`

自增主键，数据分布均匀

**按分页分片**

`LIMIT offset, size`

通用，但深分页慢

**按游标分片**

`WHERE id > lastId LIMIT size`

推荐，性能恒定

**按哈希分片**

`WHERE MOD(id, N) = ?`

需要并行处理，互不干扰

**本文采用：游标分片（按 ID 升序逐批拉取）**，避免深分页，性能稳定。

### 3.2 线程池隔离

**为什么不能用默认的线程池？**

*   `ForkJoinPool.commonPool()`：线程数少，适合 CPU 密集型，不适合 IO 密集型
    
*   `Executors.newFixedThreadPool()`：使用无界队列，任务堆积会 OOM
    
*   `Executors.newCachedThreadPool()`：线程数无上限，可能创建数万个线程
    

**正确做法**：自定义线程池，核心参数根据 IO 密集场景设置：

```
ThreadPoolExecutor executor = new ThreadPoolExecutor(
```

**线程数估算**：

```
IO 密集型任务：线程数 = CPU核心数 × (1 + 等待时间/计算时间)
```

**实际取值**：根据短信服务商的 QPS 限制，一般 10-50 个线程。

### 3.3 异步任务与进度追踪

**异步执行**：将推送任务提交到后台线程池，立即返回任务 ID，不阻塞用户。

**进度追踪**：使用 Redis 存储任务进度（已处理数/总数/成功数/失败数），支持实时查询。

### 3.4 失败重试与死信处理

*   单条发送失败：记录到失败列表，稍后重试
    
*   重试超过 3 次：写入死信表，人工处理
    
*   整批任务失败：记录任务状态，支持断点续跑

## 六、进阶优化

### 6.1 分批提交，避免大事务

如果推送前需要更新用户状态，建议分批提交：

```
// 每批处理完后，单独提交
```

### 6.2 限流保护短信服务商

短信服务商通常有 QPS 限制，可以使用 Guava RateLimiter 限流：
