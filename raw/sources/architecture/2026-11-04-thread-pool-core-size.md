# 线程池核心线程数怎么配置？为什么 CPU 密集型常用 N+1，I/O 密集型常用 2N？

先说结论：两种任务的区别，在于线程执行任务期间，有多少时间真正占用 CPU。

设 N 为 JVM 可用的处理器数量：

*   CPU 密集型任务：可以从 `N` 或 `N + 1` 个线程开始压测。

*   阻塞式 I/O 密集型任务：可以从 `2N` 开始尝试，但等待时间较长时，合适的线程数可能远大于 `2N`，也可能受下游容量限制而更小。

*   这些都是初始经验值，不是通用最优解。最终需要结合任务的等待比例、下游容量和压测结果决定。

这里说的 N 是可用 CPU 处理器数量，不是 ThreadPoolExecutor 的 corePoolSize。可以通过下面的方法获取：

```
int cpuCount = Runtime.getRuntime().availableProcessors();
```

它返回的是 JVM 可用的处理器数量。部署在容器中时，还需要结合 JDK 版本和实际容器 CPU 配额核实结果，不能只看宿主机有多少核。Oracle：Runtime.availableProcessors

* * *

## 一、为什么任务类型会影响线程数？

一个线程执行任务时，通常会经历两类时间：

1.  计算时间：线程正在使用 CPU 执行代码。

2.  等待时间：线程等待数据库、网络、磁盘或锁等，暂时没有使用 CPU，但仍占用一个工作线程。

假设只有 4 个可用 CPU：

*   如果 4 个线程都在做纯计算，CPU 可能已经很忙。继续增加线程，只会让更多线程争抢有限的 CPU。

*   如果 4 个线程大部分时间都在等数据库，CPU 可能很闲。这时增加线程，可以让一些线程等待时，另一些线程继续计算。

所以，线程数的关键不是“任务名字叫 CPU 密集型还是 I/O 密集型”，而是任务实际运行时的计算与等待比例。

> 本文主要讨论传统的平台线程 + 阻塞式任务。如果使用非阻塞 I/O 或虚拟线程，线程数的含义和调优方式会有所不同。

* * *

## 二、CPU 密集型：为什么通常从 N 或 N+1 开始？

### 2.1 什么是 CPU 密集型？

任务的大部分时间都用于计算，等待外部资源的时间较少。例如：

*   图片压缩、视频编码；

*   加密、哈希计算；

*   大规模数据计算；

*   复杂规则计算；

*   数据解析、序列化和反序列化。

这些只是常见例子，实际仍要以运行情况为准。例如，处理图片时如果大量时间花在读取远程文件上，整个任务就未必是纯 CPU 密集型。

### 2.2 为什么线程数接近 CPU 数量？

假设有 4 个可用 CPU，且有足够多、持续可运行的计算任务：

```
CPU 1 → 线程 1 计算
```

此时 4 个线程已经可以让 4 个 CPU 都有事做。

如果增加到 20 个线程，并不会让 4 个 CPU 同时执行 20 个线程。多出来的线程需要等待调度，可能带来：

*   更多上下文切换；

*   线程栈占用更多内存；

*   CPU 缓存局部性变差；

*   更激烈的锁和共享资源竞争。

因此，对接近纯计算的任务，线程数通常应从 CPU 数量附近开始测试。

### 2.3 为什么有人推荐 N+1？

N + 1 的思路是：即使任务总体是 CPU 密集型，线程也可能偶尔因为短暂等待、缺页、锁竞争或调度等原因暂停。多一个线程，在部分情况下可以填补短暂的空隙。

但要注意：

> “+1”不是 Java 规范要求，也不能保证一定比 N 更快。

如果任务几乎完全计算，N 可能就够；如果同一进程还有 GC、Web 请求、其他线程池和系统任务需要 CPU，这个线程池甚至可能需要少于 N，以免占满整个进程的 CPU 预算。

比较稳妥的做法是从 N 左右开始，测试 N - 1、N、N + 1 等配置，比较吞吐量和延迟。

## 三、I/O 密集型：为什么常说 2N？

### 3.1 什么是阻塞式 I/O 密集型？

任务执行过程中，有较多时间在等待外部资源，例如：

*   同步调用远程 HTTP 接口；

*   使用阻塞式 JDBC 查询数据库；

*   读写磁盘文件；

*   等待缓存、消息中间件等服务响应。

当线程发起阻塞调用后：

```
工作线程发起数据库查询
```

如果线程池只有 N 个线程，而这些线程大部分时间都在等待，CPU 可能没有充分利用。增加线程，可以让等待和计算交错进行。

### 3.2 2N 背后的直觉

假设任务的运行时间中：

*   一半时间在计算；

*   一半时间在等待。

那么一个线程平均只有约 50% 的时间需要 CPU。理想化地看，两个这样的线程可以共同提供约一个 CPU 的持续计算需求。

所以：

```
N 个 CPU × 每个 CPU 约需要 2 个线程
```

这就是 2N 常见的直觉来源。

但它隐含了一个重要前提：等待时间大致等于计算时间。如果等待更久，2N 可能不足；如果等待很少，2N 可能偏大。

## 四、比 2N 更有解释力的估算公式

可以用下面的公式估算阻塞式任务的线程数起点：

```
线程数 ≈ N × U × (1 + W / C)
```

其中：

*   `N`

    ：JVM 可用的 CPU 数量。

*   `U`

    ：希望这个工作负载使用的目标 CPU 比例，例如 `0.8`。

*   `W`

    ：单个任务中平均等待的时间。

*   `C`

    ：单个任务中平均使用 CPU 计算的时间。

### 4.1 公式怎么理解？

假设一个任务：

```
CPU 计算时间 C = 10 ms
```

这个线程平均只有：

```
10 / 20 = 50%
```

的时间在使用 CPU。因此，理想情况下约需要两个这样的线程，才能提供相当于一个 CPU 的持续计算需求。

此时：

```
1 + W / C = 1 + 10 / 10 = 2
```

如果目标是让全部 N 个 CPU 都用于这个工作负载，即 U = 1：

```
线程数 ≈ N × 2
```

这时就得到 2N。

如果只希望这个线程池占用约 80% 的 CPU 预算，以第二行为例：

```
8 × 0.8 × (1 + 10 / 10)
```

这里的 U 更准确地说，是分配给这个工作负载的 CPU 预算。实际进程中还有 GC、其他业务线程、操作系统等开销，不能认为公式算出的线程数一定能让整机 CPU 正好达到某个比例。

### 4.3 公式有什么局限？

这个公式是简化模型，假设任务有足够的并发需求，计算和等待比例相对稳定，且增加并发不会显著恶化等待时间。实际中可能出现：

*   并发增大后，数据库变慢，`W` 反而上升；

*   不同任务的耗时分布差异很大；

*   任务等待的是同一个锁，增加线程不能增加有效吞吐；

*   CPU 缓存竞争、上下文切换和 GC 成本随线程数增加；

*   下游服务对并发有限制。

因此，公式算出 80 个线程，不代表就应该直接配置 80。它只是帮助理解“等待越多，可能需要越多并发”的起点。

## 五、为什么 I/O 线程数不能无限增加？

假设线程池中的任务都需要使用数据库，而数据库连接池最多只有 20 个连接：

```
线程池：80 个工作线程
```

高负载下，最多大约只有 20 个任务能同时拿到连接，其他任务可能在等连接。继续增加工作线程，并不一定增加数据库吞吐量，反而可能导致：

*   更多线程占用内存；

*   更多请求等待连接；

*   请求超时增加；

*   数据库压力扩大；

*   任务排队时间变长。

也不能简单地说“线程数绝不能超过连接数”：任务可能只有部分时间持有连接，其余时间执行其他操作。但数据库连接数、下游并发限制和响应时间，必须纳入容量设计。

对于外部依赖较多的系统，还可以把不同类型的任务放到不同线程池，并对数据库、远程接口等分别设置并发限制，避免一个慢依赖拖垮其他业务。

## 六、corePoolSize 和 maximumPoolSize 要一起看

对于 ThreadPoolExecutor，任务提交后的主要顺序是：

```
线程数未达到 corePoolSize → 创建工作线程
```

例如：

```
new ThreadPoolExecutor(
```

这里并不是负载一上来就直接增长到 32 个线程。通常是：

1.  先按需创建到 8 个工作线程；

2.  接着任务进入队列；

3.  队列满了之后，才尝试继续增加到最多 32 个线程。

如果使用无界队列，任务通常会一直入队，线程数就可能长期停留在核心数附近，maximumPoolSize 也就很难发挥作用。Oracle：ThreadPoolExecutor 队列与线程数关系

所以，配置时至少要同时考虑：

*   核心线程数；

*   最大线程数；

*   队列类型与容量；

*   拒绝策略；

*   下游容量和业务延迟目标。

## 七、实际项目中怎么配置？

### 第一步：判断任务实际在做什么

统计或采样任务的：

*   CPU 计算时间；

*   数据库、HTTP、磁盘等等待时间；

*   获取连接和锁的等待时间；

*   任务总耗时和尾部耗时，比如 P95、P99。

不要只看平均值。部分任务如果偶尔等待很久，会显著影响线程占用和排队。

### 第二步：选择初始值

假设 JVM 有 N 个可用 CPU：

任务类型

可用于压测的初始值

重点

接近纯计算

`N`

    左右，例如测试 `N-1`、`N`、`N+1`

留意 CPU 竞争和上下文切换

存在明显阻塞的 I/O 任务

`2N`

    可作为一个起点，也可结合 `W/C` 估算

留意连接池和下游并发上限

同时包含大量计算和等待

根据实测 `W/C` 估算，再压测

必要时拆分不同阶段

多类业务混用

按业务隔离线程池

防止慢任务占满全部工作线程

### 第三步：设置有界资源

线程数之外，还要明确：

*   队列能容纳多少任务；

*   排队时间是否会超过业务超时；

*   满载后拒绝、降级还是由调用方执行；

*   数据库和远程服务能承受多少并发；

*   是否要给任务设置超时、取消和限流。

### 第四步：压测并调整

逐步调整线程数，观察：

*   吞吐量：每秒完成多少任务；

*   延迟：平均值、P95、P99；

*   CPU 使用率与上下文切换；

*   队列长度、排队时间、拒绝次数；

*   数据库连接池使用率、远程服务延迟；

*   内存占用、GC 情况。

一个常见现象是：

```
线程数增加
```

通常应选择满足吞吐量和延迟目标、同时保留一定余量的配置，而不是追求最大的线程数。

## 八、面试时可以这样回答

> 核心线程数要区分 CPU 密集型和 I/O 密集型，主要是因为任务的 CPU 占用时间和等待时间不同。CPU 密集型任务大部分时间都在计算，线程过多只会争抢 CPU，因此通常从可用 CPU 数量附近开始，例如 N 或 N+1；其中加一只是经验值。
>
> 阻塞式 I/O 任务在等待数据库或网络时会占用线程但不占用 CPU，可以增加线程，让一部分线程等待时，另一部分继续执行。常说的 2N，可以理解为任务等待时间和计算时间大致相等时的一个估算。更一般的估算是 `N × U × (1 + W/C)`，但实际还要考虑连接池、下游容量、线程开销、队列和拒绝策略，最终通过压测确定。
