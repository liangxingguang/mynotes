# 腾讯面试官：微信朋友圈 10 亿人发内容，怎么保证你能看到好友的最新动态？按时间倒序查就行？

> 来源：微信公众号文章。以微信朋友圈时间线设计为切入，对比读扩散与写扩散两种 Feed 流方案，解析好友上限 5000 作为写扩散成本天花板的架构意义，并给出削峰、合并、只推活人三个优化手段。

## 题目

晚上八点到十点，全国有几亿人在这段时间里刷朋友圈。你发一条动态，点提交那一刻，理论上你的 300 个好友下次刷新时都该看到它。而同一秒，平台上还有几十万条新内容正在产生，各自落进自己的关系链里。

10 亿用户、人均几百个好友、内容要秒级可见——这条时间线该怎么设计？

## 解题思路

### 先思考一下这道题

这道题是微信典型的业务场景题，题目本身很普通，但它有着一个几乎所有人第一反应都会踩的坑。

朋友圈、微博的关注流、抖音的关注页，属于同一类东西：**每个用户打开的主页里，装的都是别人生产的内容**。业内管它叫 Feed 流。

它和普通业务最不一样的地方在于，一条数据要同时服务两个方向：一条内容要「到达」很多人，一个人要一次「看到」很多人的内容。发布者和接收者之间有一张关系网，而这张网的规模是不均匀的——有人只有几十个好友，有人接近上限。

> 贯穿全文的假设数字
>
> 为了让后续的推导有个准头，我们先约定一组假设数字，后面所有账都按它算：10 亿用户，人均 300 个好友，每天产生 1 亿条新动态（也就是十分之一的用户当天发了一条）。这几个数字都是量级假设，不影响结论的方向。

接下来让我们一起分析一下：直接按时间倒序查朋友圈数据，可行吗？「写扩散」是什么方法？ 微信好友上限和这道题有什么关系？为什么偏偏卡在 5000？

### 一、按时间倒序查就行？

题目刚说完，最常听到的答案大概率就是这句：按时间倒序查不就行了？

听上去很有道理，时间线嘛，按时间排的，加个索引倒序查，取前 20 条，完事。

做法也很清晰：你刷新朋友圈的时候，系统拿着你的好友列表，批量查询他们最近发布的数据，同时按时间排个序，返回给你。

```sql
SELECT * FROM moment   WHERE user_id IN (好友A, 好友B, ... /* 共 300 个 */)   ORDER BY create_time DESC   LIMIT 0, 20;
```

这条 SQL 写得出来，结果也准确，分页也能分。但是这个方法忽略了一个问题：**数据量**。

按照我们开头的假设，你 300 个好友，假设这些好友的平均微信注册周期是3年，按人均每10天发一条算，也就 3 万多条数据。3 万多，并不多，排个序也很轻松。

可是当用户的体量达到10亿呢？如此庞大的用户体量，如此庞大的数据量，单表存储是不可能的，分库分表难以避免。而你那300个好友，在最糟糕的情况下，可能会分布在300个不同的分片里。你朋友圈刷新一次，要扇出300路查询。这里的根子不在分库分表——数据是**按发布者存的**，你要的 300 个人的动态天然散在 300 个来源里，读者只能自己一个个去拼；分库分表只是把这笔成本显形，不是它的起因。

> 扇出（fan-out）
>
> 扇出（fan-out）是指一次操作要分发到多少个目标。放这儿说，就是你刷新一次，得挨个去查 300 个好友所在的分片；写扩散同理，一次发布要扇出到 300 个收件箱。

这只是你的一次刷新，把视角放到全站再看：

- 10 亿用户，假设人均每天刷 10 次朋友圈 → 100 亿次刷新/天
- 每次刷新挨个问 300 个好友 → 3 万亿次后端读取/天
- 均摊下来约 **3500 万 QPS**，而且是读 QPS

如此庞大的QPS恐怕再好的服务器资源也吃不消，而且这个超高并发量并不是偶尔，是一直如是！

且不说如此庞大的并发量，服务器能不能吃得消；即便是吃得消，单次刷新需要300次查询加上内存归并排序、分页处理，不仅内存消耗十分巨大，响应时间也没法保证。

看到这，你可能已经意识到那句「按时间倒序查就行」问题的所在：**时间倒序确实是对的排序方式，但你手里根本没有那张排好序的表。** 你要先把 300 个人发的东西凑到一起，才谈得上排序——而凑的动作，就是全部成本所在。

其实这种解决问题的思路，叫做**读扩散**，也叫拉模式。针对所需的数据，需要用的时候现场拼。

既然读扩散不行，那能不能反过来看：别在读的时候拼，而是在写的时候就把时间线拼好呢？

### 二、换条路：发布时替好友把内容放进收件箱

这个方法就是**写扩散**，也叫推模式。

思路很直白：给每个人都准备一个「收件箱」。你发动态的时候，除了写自己的发件箱，还把这条动态的 ID 复制若干份，分别投进每个好友的收件箱里。好友刷新时不用再拼，直接打开自己的收件箱就行——这时候「按时间倒序查」才真正成立，因为收件箱本身就是一条按时间排好的线。

收件箱用 Redis 的 ZSet 承载是常见做法——score 存发布时间戳，集合本身按时间排好，倒序取出来就是时间线（`ZREVRANGE`，Redis 6.2+ 用 `ZRANGE ... REV`）。score 底层是 double，只能精确表示 ±2^53 以内的整数，所以我们用「毫秒时间戳 ×1000 + 毫秒内序号」把精度铺到微秒——当前时间戳约 1.76e15，远在安全区内：

```java
// 发布一条动态：投递到每个好友的收件箱
long postTime = System.currentTimeMillis();
long score = postTime * 1000 + seq;  // seq = 毫秒内自增序号，避免同毫秒并列后乱序
ZSetOperations<String, String> zset = redis.opsForZSet();
// 注意：生产上走 pipeline 批量提交，不要逐条 add（见第四节「削峰」——把投递放进异步消费者批量提交）
for (Long friendId : friendIds) {
    zset.add("inbox:" + friendId, postId, score);
}
```

这一换，读侧的成本结构彻底变了：原来一次刷新要 300 次查询 + 归并，现在变成 1 次查询。分页也简单了——收件箱本身就是有序的，翻页只需要记住一个位置，而不是 300 个。

那代价呢？代价在写入侧。**发布一条动态，要写 300 次。** 看起来也不多，一次 Redis 写而已。但只要把总量算出来，画风就变了：

- 1 亿条动态/天 × 300 好友 = **300 亿次收件箱写入/天**
- 均摊约 35 万 QPS

拿这个数和刚才的 3500 万 QPS 比一比：**同一个业务，读扩散要扛 3500 万的读，写扩散只要扛 35 万级的写。差了整整一百倍。**

这就是写扩散为什么在 Feed 流里这么流行——它把「排序」这件事从「每次读都要现做」挪到了「写一次就结清」。

但这里有个前提被我们悄悄用掉了：**一次发布的扇出是有上限的**——也就是这条内容最多要复制多少份。300 是个均值，可如果某个人有 5000 万粉丝（单向关注，没有上限），一条动态就要写 5000 万次。这个前提一旦塌掉，整个方案跟着塌。所以下一个问题必须问清楚：关系网能长多大？

### 三、好友上限 5000，其实是写扩散的成本天花板

微信里能看朋友圈的好友上限是 5000。张小龙在公开场合提过，已经有近百万用户的好友数接近这个上限。新浪微博对普通账号的关注数也有上限，2000 个。

大多数人把它当产品规则看。但从架构视角看，**它同时是一道护栏：它决定了写扩散最坏情况下要复制多少份。**

算一笔极端账：如果没有上限，一个账号可以有 5000 万粉丝。他随手发一条动态，写扩散就是 5000 万次投递。哪怕每次只要 1 毫秒，串起来也是 14 个小时——等你的内容铺完，热点早就过去了。更糟的是，这种账号一天发十条，就等于给系统安排了十次小规模雪崩。

**写扩散的成本不取决于你有多少用户，而取决于单个节点最多要复制多少份。** 这个数字被锁在 5000，单次扩散的成本就有了天花板，最坏情况可以被算清楚。

反过来说，当一个系统的「单次扩散成本 × 最大复制份数」能被算清楚，它才敢用写扩散。刷屏的大 V 场景之所以难，恰恰是因为它要推的人没有上限——这是产品形态决定的，不是技术选型能绕开的。

那么总量那一关呢？300 亿次写入也不是小数目，何况朋友圈的发布明显集中在晚上那几个小时。

### 四、总量过不去，就少写一点：削峰、合并、只推活人

三个手段，一个比一个有效。

**第一，削峰。** 用户点「发表」时，接口只同步做一件事——写自己的发件箱，然后立刻返回成功。真正的扩散任务丢进消息队列，由消费者慢慢投递。用户感知不到延迟，峰值却被摊平了。这是最基础的一层，几乎不损失任何东西。

**第二，合并。** 同一个收件箱在短时间窗口内可能被连着投递好几次（比如你连发三条动态，或者你的多个好友同时在发），把这几笔写入合并成一次批量操作，能省掉大量重复的往返开销。

**第三，只推活人。** 这一刀最省——一个已经三个月没打开 App 的用户，你给他推那 300 条内容纯属浪费。对长期沉默的账号暂停扩散，等他下次上线时，用一个离线时间点去拉取这期间好友的动态补齐——相当于临时退化成一次读扩散。

三个手段叠起来看，写侧的账就从「峰值硬扛 300 亿次写入」变成了「削峰后的平稳写入 + 批量合并 + 大幅削减无效投递」。写扩散真正贵的那一点——单次发布要复制几百份——并没有被绕开，只是被摊平了。

### 写在最后

回头看开头那句「按时间倒序查就行」——它之所以听着对，是因为我们下意识把「查」当成了一个纯技术动作：表在那儿，索引加好，查就完了。

**可这条时间线在数据库里根本不存在，它得有人先造出来。** 造它的时机只有两个：读的时候造，或者写的时候造。这道题的全部难度，就落在两个时机的选择上——而答案是把造的动作挪到写侧：发布时就替好友把内容放进收件箱，读的时候一次查询直接取。

写扩散能成立，靠的是被我们提前算清楚的那件事：**单次扩散要复制多少份，必须有上限。** 微信的好友上限 5000 就是这道护栏，它把最坏情况的成本锁进了可计算的范围内。有了这个天花板，「1 亿条动态 × 300 好友 = 300 亿次写入」才有资格靠削峰、合并、只推活人摊平；没有这个天花板，写扩散连摆上桌的资格都没有。
