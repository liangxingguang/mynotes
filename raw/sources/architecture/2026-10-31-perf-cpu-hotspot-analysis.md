## 如何使用 perf 排查：定位系统的性能问题

> 每天 15 分钟 · 复利成长 ｜《性能分析》第 2 篇 / 共 n 篇  
> 上一篇：第 1 篇 · 读懂系统负载

上一篇分清了系统忙在运行，还是忙在等待。如果已经确认某个业务线程持续占着 CPU，接下来就要回答：它到底在执行哪段代码？

源码有几万行，不适合凭感觉挑函数加计时。用 perf 采一段问题出现时的运行数据，看看开销集中在哪里，再决定读哪部分源码。

## perf 采集

perf 是 Linux 的性能分析工具。这里用它做 CPU 采样：程序运行时，周期性地留下执行位置，并在条件允许时记录调用栈。它不会逐行停住程序，也不要求你先列出所有可疑函数。

比如某个函数很占 CPU，采样点就更容易落在它里面。把一段时间里的记录汇总，就能得到值得优先检查的热点。采样只覆盖部分时刻，所以它给的是分布线索，不能还原每一次函数调用。

实际排查时，最常用的两个动作是：

*   • `perf record`：在目标程序运行时采集，写出 `perf.data`。
*   • `perf report`：打开这份文件，查看热点、调用关系和符号。

**记录覆盖的是选定范围内的程序执行，不是一次只能测一个函数。**同一份数据可以反复排序、筛选和展开调用栈。换一种查看方式，通常不需要再运行一遍业务。

你可能还见过 `perf stat`。它统计一段执行的事件总量，例如 CPU 时间、指令数。它适合回答“总共花了多少”，但不是找函数热点前必须先跑的一步。本篇先把 `record → report`这条路走通。

## 使用 perf 前要准备什么

perf 不是 BusyBox 自带的命令，裁剪后的板端系统也未必附带它。开始采集前，先确认下面这些条件。

| 要准备什么 | 为什么需要 |
| --- | --- |
| 可运行的 perf 工具 | 架构和依赖要适配目标根文件系统；通常由 SDK、构建系统提供，或从内核源码的 `tools/perf`构建 |
| 内核事件支持和采集权限 | 内核需启用 `CONFIG_PERF_EVENTS`，支持所选事件；当前账户也必须有权采集 |
| 与运行版本一致的程序和符号文件 | 把采样地址还原成函数名；需要定位源码行时，再用调试信息 |
| 可用的调用栈回溯方式 | 不仅知道热点函数叫什么，还要知道它从哪条路径被调用 |

工具是否存在，可以先用 `perf --version`检查；事件名称看 `perf list`，是否真能采到还要试采。只有“能列出事件”，并不能证明权限和底层支持都没问题。

如果报权限错误，检查 `/proc/sys/kernel/perf_event_paranoid`和设备的权限策略。在受控调试环境选择有权限的账户，不要一上来就修改整台设备的安全配置。

**符号和调用栈是两件事。**有函数名，不代表能还原它的调用者；编译时加了 `-g`，也不等于自动保留了帧指针。

本篇用帧指针方式回溯，也就是沿着保存下来的栈帧关系往上找。准备自己的调试版本时，可以保留优化，同时加上 `-g -fno-omit-frame-pointer`；叶函数等细节还取决于架构和编译器，相关库也要有可用的回溯条件。后面的 demo 给出了本次实际使用的完整编译命令。

如果现有程序省略了帧指针，可以考虑 `--call-graph dwarf`，但它需要 perf 的构建支持和程序、库的回溯信息，数据量也通常更大。先选一种在设备上能完整回溯的方式，不必一开始就研究所有模式。

## 如何采集

工具准备好之后，还要选对时机：业务得真的处在你想分析的状态。程序启动后一直空闲，即使录了很多秒，也回答不了“处理一帧为什么慢”。

下面两种方式按实际情况选一种。

### 程序可以从头运行

假设 `./app`是能复现问题的业务程序：

```sh
perf record -e cpu-clock:u -F 199 \  --call-graph fp -o perf.data -- ./app
```

这条命令启动 `app`，采集随它退出而结束。后面的业务命令换成什么，就采那次执行；不需要把业务里的每个函数名写进去。

### 程序已经在后台运行

假设你已经确认要分析的进程 PID 是 1234，在问题出现时采 10 秒：

```sh
perf record -e cpu-clock:u -F 199 \  --call-graph fp -p 1234 \  -o perf.data -- sleep 10
```

这里 `-p 1234`指定被观察的进程，`sleep 10`限定采集时长。采集结束后，业务进程继续运行。以 Linux 5.10 的 perf 为例，`-p`会覆盖该进程当时已有的线程，默认还继承到它们随后派生的新线程和子进程；这不等于自动纳入附加前已经存在的子进程。若只想看一个已知线程，再考虑 `-t TID`，它默认不继承。

先理解这几项就够用：

| 参数 | 本篇为什么这样选 |
| --- | --- |
| `-e cpu-clock:u` | 按软件 CPU 时钟采样，先观察用户态代码，不依赖硬件周期计数器 |
| `-F 199` | 设定目标采样频率为 199 Hz；实际样本数还受运行状态、权限范围和内核限制等影响，199 不是通用最优值 |
| `--call-graph fp` | 同时保存调用栈，使用前面准备的帧指针回溯 |
| `-o perf.data` | 把采集结果留给后续查看 |

这里特意只采用户态，是为了先分析业务代码。如果你怀疑 CPU 消耗发生在系统调用或内核中，就要调整采集范围；一份 `:u`报告本来就不包含内核执行位置。

也不要把软件事件里的 `cpu-clock`当成 CPU 主频。它按纳秒计数；硬件事件 `cycles`则统计处理器周期，两种事件的占比含义不同。无论选哪种，普通 CPU 热点采样都不能完整解释线程睡眠等待的时间。

## 日常查看，用交互界面先抓住大头

采完后，先打开数据：

```sh
perf report -i perf.data
```

在支持终端交互界面的 perf 构建中，从交互终端直接运行通常会进入一个可浏览的热点界面。你可以选择条目、展开调用关系、缩小查看范围，具体按键看界面帮助；不用每看一个函数就重新敲一条采集命令。

我会先看占比明显的几条路径。如果一个函数占了九成，先沿它查；不要因为列表里还有几千个函数，就从第一行一直读到最后一行。

有些板端 perf 没编入交互界面，或者你在脚本里保存分析结果，这时用文本模式也完全可以：

```sh
perf report --stdio -i perf.data
```

复杂项目里，逐条展开调用栈容易看漏不同路径之间的关系。可以先用报告确认热点，再用火焰图把这些路径放到一张图里看。

下面把报告导成文本，方便你对照原始输出学会读数。后面的文本导出选项按需查即可，不必每次都执行一遍。

## 用 demo 演示一遍

这次实测用的是一个小程序：`main()`调用 `process_frame()`，后者依次执行 `pixel_work()`和 `log_work()`。两个函数都只做整数循环，分别模拟计算量不同的两段工作，完整代码放在文末。

`pixel_work()`循环 20 亿次，`log_work()`循环 2 亿次。先用这种能看清全部代码的例子，确认采样结果和实际工作量能对上，再把方法迁移到业务程序。

用前面“从头运行”的命令，把 `./app`换成 `./demo`，本次采集得到 742 个样本，报告显示丢样本为 0。

### 先问：哪个函数自己在消耗 CPU

`Overhead`是本次所选事件的贡献占比，`Symbol`是函数名，`[.]`表示用户态符号。下面是关闭调用链累计后的原始热点表摘录；右侧 IPC 栏没有数值，这次不需要看它：

```console
# Samples: 742  of event 'cpu-clock:u'# Overhead  Symbol              IPC  [IPC Coverage]
  9.16%  [.] log_work    -        -
 90.84%  [.] pixel_work  -        -
```

读到这里，下一步已经很明确：先查 `pixel_work()`。约九成采样贡献落在它里面，而 `log_work()`只有约一成。表里谁排在第一行并不重要，要看的是占比和你关心的业务。

这和源码里两段循环的工作量差异相符。但别把它读成“`pixel_work`调用了更多次”：本例两个函数各调用一次。采样占比不能替代调用次数，10 倍循环量也不保证每次都采出精确的 10∶1。

### 再问：谁把这段工作安排进来的

对同一份数据展开调用树，`pixel_work`条目的原始片段是：

```console
  90.84%  [.] pixel_work  -        -
          |
          ---_start
                __libc_start_main
                      main
                        process_frame
                            pixel_work
```

这个视图按调用者到被调用者的方向显示。跳过程序启动层，从 `main`往下读，就能找到 `process_frame → pixel_work`这条路径。

示例只有一个调用入口，容易看清。换成真实业务，热点可能是很多模块都在调用的 `memcpy`。这时只知道“复制很热”还不够，要沿调用栈区分：是图像处理在复制，还是日志拼接、网络发送在复制？如果上层反复拷贝同一份数据，先减少重复工作，往往比直接钻进 `memcpy`的实现更值得尝试。

这才是记录调用栈的用处：把一个热点函数，连回到可以做工程判断的业务路径。

### 别把入口的累计占比当成它自己的开销

默认报告还可能显示 `Self`和 `Children`：`Self`看采样位置落在函数自身的贡献；`Children`包含自身及调用链后代的累计贡献。报告通常按每个样本代表的事件计数加权，不是简单数样本条数。

在本例的累计报告中，`process_frame`的累计贡献是 100%，自身却是 0%。它主要负责调用两个计算函数，大部分计算发生在下面；这里的自身 0% 表示本次没有采到落在它自身的样本，不代表调用和返回完全不耗时。不要看见入口函数累计占比高，就直接优化入口那几行；也不要把父子函数的累计百分比相加。

如果报告里大量出现 `[unknown]`或调用链中途断掉，先解决符号、二进制版本和回溯问题。此时换成火焰图，也不能自动补出原来没采到的调用关系。

## 调用路径多了，可以画成火焰图

对这个 demo，热点表和一条调用链已经足够。真实程序里，同一个库函数可能被多个模块调用，逐条展开时，很难同时看清各条业务路径占了多少。

火焰图会把采到的调用栈合并，画成一层层相连的方块：上下连接表示调用层级，方块宽度表示这条路径在采样数据中的权重。这样，哪条路径占得多、下面又分出了哪些工作，就能放在一张图里观察。

**前面保存的 `perf.data`已经包含调用栈，可以继续用来生成火焰图。**不必为了换一种视图再跑一遍业务；如果原数据缺少调用栈或符号，画图也补不出这些信息。

本篇先走通“采集 → 看热点 → 追调用者”。下一篇接着用这份数据，讲怎样生成火焰图、在浏览器里打开，再通过缩放和搜索查看具体路径。

热点只告诉你值得先查哪里。改了代码之后，仍要用相同输入和负载验证吞吐、请求延迟或每帧耗时是否改善；某个函数占比下降，也可能只是其他路径变得更忙。

## 附：想亲手复现，再看这些命令

只想掌握排查方法，读到这里已经够了。下面保留完整 demo 和文本导出命令，方便复现前面的原始输出。

保存为 `demo.c`：

```c
#include <stdint.h>
#include <stdio.h>

__attribute__((noinline))
uint32_t pixel_work(uint32_t x) {
    for (uint32_t i = 0; i < 2000000000u; ++i)
        x = x * 33u + i;
    return x;
}

__attribute__((noinline))
uint32_t log_work(uint32_t x) {
    for (uint32_t i = 0; i < 200000000u; ++i)
        x = x * 17u + i;
    return x;
}

__attribute__((noinline))
uint32_t process_frame(uint32_t x) {
    x = pixel_work(x);
    return log_work(x);
}

int main(void) {
    printf("checksum=%u\n", (unsigned)process_frame(1));
    return 0;
}
```

以下是本次 ARM64 GCC 使用的编译命令。`noinline`防止函数被内联，编译选项保留帧指针并禁止尾调用优化，让教学示例的调用关系容易辨认。`-static`仅用于这次实验打包，普通业务程序不必照搬。程序最后打印结果，避免整段计算成为无用代码；无符号整数回绕是预期行为。

```sh
gcc -O2 -g -fno-omit-frame-pointer \
    -mno-omit-leaf-frame-pointer \
    -fno-optimize-sibling-calls \
    -static -o demo demo.c
perf record -e cpu-clock:u -F 199 \
    --call-graph fp -o perf.data -- ./demo
```

程序输出 `checksum=962548993`，perf 记录提示如下。这些是本次实测值，复跑的样本数和比例会有波动。

```console
[ perf record: Woken up 1 times to write data ]
[ perf record: Captured and wrote 0.069 MB perf.data (742 samples) ]
```

前面的热点表，用下面这条命令从同一份数据导出：

```sh
perf report --stdio --no-children \
    --sort symbol -F overhead,symbol \
    -g none -i perf.data
```

`--no-children`关闭调用链累计，`--sort symbol`按函数归组，`-F`指定显示字段，`-g none`隐藏树形展开。注意这里 `report -F`选字段，与 `record -F`设采样频率是两个子命令的不同选项。

调用树则这样导出：

```sh
perf report --stdio --no-children \
    --sort symbol -F overhead,symbol \
    -g graph,0.5,caller -i perf.data
```

其中 `caller`指定从调用者向下展示，`graph`使用全局比例，`0.5`是 0.5% 的显示阈值。这些参数改变查看方式，不会重新采样。

## 一句话总结

用 perf 采一次问题现场，再从热点函数追到业务调用路径；有了可信的调用栈，后续就能继续用火焰图查看整体分布。
