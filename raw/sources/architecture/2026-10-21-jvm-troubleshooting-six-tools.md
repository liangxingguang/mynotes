# JVM 排查别乱试：6 个工具各管什么

# JVM 排查别乱试：6 个工具各管什么

> 来源：https://mp.weixin.qq.com/s/9eAlETU99LUBabyJ892kGQ
> 抓取时间：2026-10-21（web-fetch，browser 级）

线上接口突然变慢，先别急着导出堆转储，也别一上来就重启服务。很多 JVM 问题，第一轮排查只需要几个随 JDK 提供或可单独安装的工具。

真正容易搞混的是：`jps` 找进程，`jstat` 看 GC，`jstack` 看线程，`jinfo` 看配置，`jcmd` 做综合诊断，VisualVM 负责把这些信息放到图形界面里观察。前五个工具以 `j` 开头，VisualVM 是另一套图形化工具，分工并不重复。

## 先按问题选工具

| 想确认什么 | 先用哪个 | 主要看什么 |
| --- | --- | --- |
| 机器上跑了哪些 Java 进程 | `jps` | PID、主类、启动参数 |
| JVM 当前有哪些诊断能力 | `jcmd` | 线程、堆、类、运行参数 |
| GC 是否频繁、老年代是否顶住 | `jstat` | 各区使用率、GC 次数和耗时 |
| 线程卡在哪里 | `jstack` | 线程栈、锁等待、死锁线索 |
| 进程到底带了哪些 JVM 参数 | `jinfo` | JVM flags、System Properties |
| 想看趋势和关联关系 | VisualVM | CPU、GC、堆、线程和快照 |

排查顺序通常是：先找到 PID，再判断是内存、线程还是启动参数，最后才决定要不要做高成本操作。别把"能执行"误当成"现在就该执行"。

## 1. jps：先把目标进程找出来

很多命令都需要 PID。`jps` 就是 JVM 进程清单，适合排查的第一步：

```bash
jps -lv
```

`-l` 显示主类的完整包名或 JAR 路径，`-v` 带出 JVM 启动参数。输出大致：

```
21891 com.example.OrderApplication -Xms2g -Xmx2g
```

拿到 PID 后，后面的 `jcmd 21891 ...`、`jstat ... 21891`、`jstack ... 21891` 才有目标。

`jps` 不是万能的进程发现工具。在容器里，宿主机 PID 和容器内 PID 可能不是同一个；不同用户启动的 Java 进程，也可能因为权限看不到。看不到目标进程时，先确认当前用户、容器 PID 命名空间和 JDK 版本，别急着判断"服务没启动"。

## 2. jcmd：大多数时候先从它开始

`jcmd` 可以向正在运行的 JVM 发送诊断命令。先看它支持什么：

```bash
jcmd 21891 help
```

几个常用命令：

```bash
# 查看 JVM 启动命令和参数
jcmd 21891 VM.command_line

# 查看当前生效的 JVM flags
jcmd 21891 VM.flags

# 打印线程信息
jcmd 21891 Thread.print

# 查看堆的基本信息
jcmd 21891 GC.heap_info
```

它的好处是入口比较统一，而且不同 JDK 版本支持的诊断命令可能不同，先执行 `help` 再决定下一步，比死记参数可靠。

不过 `jcmd` 也有轻重之分。`Thread.print` 通常适合快速取线程现场；堆转储、类直方图等操作可能带来明显的暂停或磁盘压力，线上执行前要看命令说明和当前负载。

## 3. jstat：别凭感觉判断 GC

接口变慢时，GC 经常被怀疑，但"感觉像 GC"不算证据。`jstat` 可以连续观察 JVM 的统计数据：

```bash
jstat -gcutil 21891 1000 10
```

这条命令每秒采样一次，共输出 10 次。重点看几件事：

- `YGC`、`YGCT`：年轻代 GC 次数和累计耗时；
- `FGC`、`FGCT`：Full GC 次数和累计耗时；
- `O`：老年代使用率；
- `GCT`：各类 GC 的累计耗时。

如果 `FGC` 在问题时间段持续增长，`FGCT` 也明显增加，同时接口延迟出现尖峰，GC 才有可能是主要嫌疑。只看某一次 `O` 达到 80%，还不能直接下结论，关键是观察趋势和发生时间是否对得上。

`jstat` 的输出是采样窗口里的统计，不会替你解释业务对象为什么变多。确认 GC 只是第一步，后面还要结合 GC 日志、对象分配和请求流量继续查。

## 4. jstack：线程到底堵在哪里

CPU 飙高、接口超时、线程池满了，常见原因可能是死循环、锁竞争、连接池等待，或者下游调用迟迟不返回。这类问题要看线程栈：

```bash
jstack -l 21891 > jstack-21891.log
```

`-l` 会尽量带出锁信息。拿到线程栈后，先搜这些线索：

- 大量线程卡在同一个业务方法；
- 多个线程处于 `BLOCKED`，等待同一把锁；
- 大量线程停在连接池、HTTP 客户端或数据库驱动；
- 不同线程互相持有对方需要的锁，形成死锁环。

一次线程栈只能说明一个瞬间。现场允许时，可以间隔几秒采三次，比较相同线程是否一直停在同一位置。JDK 版本支持时，也可以用 `jcmd 21891 Thread.print`，把它作为统一诊断入口。

## 5. jinfo：把启动配置摊开看

有些问题不在代码，而在"线上到底用什么参数启动的"。部署脚本、容器环境变量和启动命令经常不是同一份，`jinfo` 可以直接查看目标进程的配置：

```bash
jinfo -flags 21891
jinfo -sysprops 21891
```

前一条主要看 JVM flags，后一条看 Java System Properties。排查堆大小、GC 选择、类路径和自定义系统属性时，它比翻一堆部署文件更直接。

`jinfo` 适合确认现场，不适合拿来随便改线上参数。能否动态修改取决于具体 flag 和 JDK 版本，修改前还要评估暂停、回滚和重启后的失效问题。现在很多诊断场景也可以优先看 `jcmd` 提供的对应命令。

## 6. VisualVM（jvisualvm）：适合看趋势，不适合替代判断

喜欢图形界面的话，可以用 VisualVM。官方页面把它定位为整合 JDK 命令行工具和轻量级分析能力的可视化工具，它能看到 CPU、GC、堆、Metaspace、类加载数量和线程状态，也能查看线程转储和堆转储。

现在通常需要单独下载 VisualVM，别在新版本 JDK 的 `bin` 目录里一直找 `jvisualvm`。连接目标进程还要注意 JDK 版本、用户权限和远程连接方式。生产环境使用前，先确认采样、转储操作不会影响业务。

VisualVM 的价值在于把变化趋势放在一起看：CPU 上升时 GC 是否同步变频繁，堆使用率是否持续爬升，线程数量和等待状态有没有一起变化。它能帮你缩小范围，但最终结论仍要回到日志、线程栈和业务请求上。

## 一套不容易走偏的排查顺序

遇到线上 JVM 异常，可以按这个顺序走：

1. 用 `jps -lv` 找到正确 PID，并确认自己看到的是目标容器里的进程；
2. 用 `jcmd <pid> VM.command_line` 和 `VM.flags` 确认启动参数；
3. 怀疑 GC，就用 `jstat -gcutil <pid> 1000 10` 看一段连续数据；
4. 怀疑线程，就用 `jcmd <pid> Thread.print` 或 `jstack -l <pid>` 取现场；
5. 需要看趋势时再打开 VisualVM；
6. 只有明确需要时，才做堆转储、类直方图等更重的操作。

这 6 个工具没有谁能单独给出"根因报告"。它们提供的是不同角度的现场证据：进程、配置、GC、线程和趋势。把几份证据放到同一条时间线上，定位问题才会快。

## 最后记住这张小抄

`jps` 找谁，`jcmd` 先问 JVM，`jstat` 看 GC，`jstack` 看线程，`jinfo` 查配置，VisualVM 看全局趋势。

排障不是工具越多越专业，而是每次只拿能回答当前问题的那一个。命令少敲一点，结论反而更容易靠谱。
