以下以现代 Elasticsearch 为主，涉及默认值或底层实现时说明版本差异。每题先给可以直接回答的版本，再补充常见追问。

## 一、基础概念与倒排索引

![图片](data:image/gif;base64,iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVQImWNgYGBgAAAABQABh6FO1AAAAABJRU5ErkJggg==)

### 1\. Elasticsearch 是什么？适合什么场景？

**答：** Elasticsearch（ES）是基于 Lucene 的分布式搜索与分析引擎，适合全文搜索、日志检索、商品搜索、数据聚合等场景。

**追问：ES 能替代 MySQL 吗？**  
通常不能直接替代。MySQL 更适合事务和关系数据管理；ES 擅长全文检索和分布式分析。常见做法是 MySQL 作为业务主数据源，ES 作为搜索索引。

* * *

### 2\. ES 为什么搜索快？

**答：** 核心是倒排索引：先根据词条找到匹配的文档集合，再结合过滤、排序和分片并行完成查询。词典索引、Posting List 压缩、缓存等也能减少查找和 I/O 成本。

**追问：所有查询都快吗？**  
不是。高基数聚合、深分页、前置通配符、复杂脚本、过多分片或大范围扫描都可能很慢；性能取决于数据规模、查询方式和资源配置。

* * *

### 3\. 什么是倒排索引？和正排索引有什么区别？

**答：**

*   **正排视角：**
    
     文档 ID → 文档内容或字段值。
    
*   **倒排视角：**
    
     词条 → 包含该词条的文档列表。
    

例如：

```
doc1：华为手机doc2：苹果手机华为 → [doc1]苹果 → [doc2]手机 → [doc1, doc2]
```

**追问：MySQL 一定要逐行扫描吗？**  
不一定。MySQL 的 B+ 树索引也能快速定位精确值、范围和符合条件的前缀；MySQL 也支持全文索引。`LIKE '%关键词%'` 通常不能利用普通 B+ 树做前缀定位。

**追问：倒排索引查找是 O(1) 吗？**  
不能笼统这么说。词典查找、遍历匹配文档、合并结果和取回字段都有成本，具体复杂度取决于实现和查询。

* * *

### 4\. Term Dictionary、FST 和 Posting List 是什么？

**答：**

*   **Term Dictionary：**
    
     保存字段中出现过的词条及其关联信息。
    
*   **词典索引：**
    
     帮助快速定位词条；Lucene 不同版本和编码格式的实现可能不同，FST 是常见实现思路之一。
    
*   **Posting List：**
    
     记录包含某个词条的文档，以及按配置保存的词频、位置等信息。
    

**追问：Posting List 一定包含位置和 offset 吗？**  
不一定。是否记录词频、位置和偏移量取决于字段的 `index_options` 等配置。短语查询通常需要位置；高亮可使用 offset 或其他方式获取位置信息。

**追问：Posting List 一定使用 Roaring Bitmap 吗？**  
不是。Lucene 会使用多种编码和数据结构；典型思路包括对有序文档 ID 做差值编码和压缩。不要把某一种压缩方式当成所有场景的固定实现。  

**追问：查到 docId 后就不需要取文档了吗？**  
不一定。倒排索引用于定位匹配文档；如果需要返回 `_source` 或其他字段，通常还要读取相应数据。

* * *

### 5. `doc_values` 是什么？

**答：**`doc_values` 是面向“文档 → 字段值”的列式数据结构，主要用于排序、聚合和脚本访问。倒排索引则主要用于“字段值或词条 → 文档”的查找。

**追问：所有字段都有** `doc_values` **吗？**  
不是。例如普通 `text` 字段默认不支持 `doc_values`；需要对文本做精确聚合或排序时，常使用其 `keyword` 子字段。

* * *

### 6\. ES 查询一定使用倒排索引吗？

**答：** 不一定。文本和关键词检索常用倒排索引；数值、日期等字段的范围查询通常使用适合多维范围检索的索引结构；排序和聚合常使用 `doc_values`。具体取决于字段类型和映射配置。  

## 二、分词与 Mapping

### 7\. ES 的分词流程是什么？

**答：**

```
原始文本 → Character Filter → Tokenizer → Token Filter → 词条
```

*   Character Filter：预处理字符，例如去除 HTML。
    
*   Tokenizer：把文本切分为词元。
    
*   Token Filter：处理词元，例如小写化、去停用词。
    

**追问：怎么检查分词结果？**  
使用 `_analyze` API，分别检查索引时和查询时的分析结果。

* * *

### 8. `text` 和 `keyword` 有什么区别？

**答：**

*   `text`
    
    ：通常经过分词，适合全文搜索。
    
*   `keyword`
    
    ：通常作为完整值索引，适合精确匹配、排序和聚合。
    

**追问：一个字段既要全文搜索又要精确匹配怎么办？**  
使用多字段，例如 `title` 定义为 `text`，同时提供 `title.keyword` 用于精确匹配和聚合。

**追问：**`keyword` **一定完全不处理吗？**  
它不做全文分词，但可以配置 `normalizer`，例如统一转小写。

* * *

### 9. `match` 和 `term` 有什么区别？

**答：**

*   `match`
    
    ：通常先按字段的搜索分析器处理查询文本，再检索词条，适合全文搜索。
    
*   `term`
    
    ：按给定词条做精确查找，通常用于 `keyword`、ID、状态等精确条件。
    

**追问：为什么对** `text` **用** `term` **经常查不到？**  
因为索引时原文可能已经被切成多个词条，而 `term` 不会按全文搜索的方式对输入分词。具体还受字段类型和映射影响。

* * *

### 10\. 中文分词怎么做？

**答：** 中文通常需要选择合适的中文分析器，例如安装与 ES 版本兼容的 IK 插件；也要结合业务词典和实际查询测试。

**追问：**`ik_max_word` **和** `ik_smart` **有什么区别？**  
通常前者切分更细、召回更多，后者切分更粗。实际结果受词典和具体文本影响，不能只看名称，要用 `_analyze` 验证。

**追问：索引和查询时的分词器必须一样吗？**  
不必须，但必须保证查询产生的词条能够匹配索引词条。比如索引时使用较细粒度、查询时使用较粗粒度是常见方案，需结合召回率和准确率验证。

* * *

### 11\. 前缀搜索和模糊搜索怎么实现？

**答：**

*   **前缀搜索：**
    
     可考虑 `edge_ngram`、`search_as_you_type` 或 completion suggester。
    
*   **子串搜索：**
    
     可评估 `ngram` 或适合通配符场景的字段与查询。
    
*   **拼写容错：**
    
     可评估 fuzzy query。
    

**追问：**`edge_ngram` **的查询端一定不分词吗？**  
不一定。通常查询端使用与索引端不同、不会再次生成大量前缀词元的分析器；具体要根据语言和需求配置。

**追问：分词天然支持任意模糊匹配吗？**  
不支持。普通分词只能匹配已生成的词条；任意子串、前缀和拼写纠错是不同需求，需要对应设计。`ngram` 也会增加索引体积和写入成本。

* * *

### 12\. Mapping 是什么？字段类型能直接修改吗？

**答：** Mapping 定义字段类型、分析器和索引方式。已存在字段的类型通常不能原地修改；需要创建新索引并重建数据。

**追问：如何平滑修改字段类型？**  
创建新索引及正确 Mapping → 全量 Reindex → 补齐期间的增量变更 → 校验 → 原子切换别名。增量同步和切换一致性要按业务设计。

**追问：动态 Mapping 有什么风险？**  
可能推断出错误类型，或因字段不断增加造成 Mapping 爆炸。生产环境通常对关键字段显式定义 Mapping，并控制动态字段。

* * *

### 13. `object` 和 `nested` 有什么区别？

**答：** 普通对象数组会被扁平化，查询时可能把不同数组元素的字段错误组合；`nested` 把数组元素作为独立的内部文档，使条件限定在同一个元素内。

**追问：**`nested` **的代价是什么？**  
会增加内部文档数量和查询成本，应只用于确实需要保留数组元素关联关系的场景。

## 三、写入与数据可靠性

### 14\. ES 的写入流程是什么？

**答：**

```
客户端 → 协调节点 → 目标主分片                     ├─ 在主分片执行并记录 Translog                     └─ 转发给需要同步的副本                  → 满足确认条件后返回
```

随后 refresh 使数据可搜索；flush 生成 Lucene commit，降低恢复时需要重放的 Translog 范围。

**追问：Translog 是先于 Lucene 内部写入吗？**  
不能简单说成“先写 Translog，再写 Index Buffer”。官方描述是：操作先由内部 Lucene 索引处理，再写入 Translog，之后才确认给客户端。Translog 用于恢复尚未包含在 Lucene commit 中的已确认操作。  

**追问：写成功是否代表所有配置的副本都已写入？**  
不一定。要区分**已分配且参与复制的副本**与未分配副本；默认成功不代表所有期望副本都存在。`wait_for_active_shards` 可在写入前要求指定数量的分片副本处于活动状态，但它不是写入完成后的绝对成功保证，应检查响应中的 `_shards` 信息。

* * *

### 15\. Refresh、Flush、Merge 有什么区别？

机制

作用

是否决定搜索可见性

**Refresh**

打开新的搜索视图，使近期变更可被搜索

是

**Flush**

执行 Lucene commit，并开始新的 Translog generation

主要解决持久化和恢复成本

**Merge**

合并 Segment，并逐步清理已删除文档占用的空间

不负责保证写入立即可见

**追问：Flush 就是把 Segment 从缓存刷到磁盘并清空整个 Translog 吗？**  
不准确。Flush 的核心是 Lucene commit 和开启新的 Translog generation；旧日志何时删除还取决于恢复和保留需要。

**追问：Flush 默认是 30 分钟或 512 MB 吗？**  
不能作为通用结论，默认值会随版本变化。当前官方文档中的 `index.translog.flush_threshold_size` 默认值为 **10 GB**；应以目标版本文档为准。  

* * *

### 16\. 为什么说 ES 是近实时搜索？

**答：** 写入成功后，数据通常要等 refresh 才能被搜索到，因此搜索可见性有延迟。

**追问：是不是一定 1 秒后能查到？**  
不是。普通 Elastic Stack 默认 refresh 间隔通常为 1 秒，但存在搜索空闲优化，且负载和配置也会影响实际时间；Elastic Cloud Serverless 的默认值不同。

**追问：如何实现写完就能搜索？**  
写入时使用 `refresh=wait_for`，等待一次 refresh 后再返回。`refresh=true` 会主动触发 refresh，频繁使用会影响性能。

**追问：写完后按 ID 查询也要等 refresh 吗？**  
通常不需要。Get API 默认支持实时读取；Search API 的可见性依赖 refresh。

* * *

### 17\. Translog 的 `request` 和 `async` 有什么区别？

**答：**

*   `request`
    
    ：默认模式，在确认请求前，对主分片及相关已分配副本的 Translog 执行持久化。
    
*   `async`
    
    ：按 `sync_interval` 周期持久化，默认间隔通常为 5 秒；故障时可能丢失上次同步以来已确认的操作。
    

**追问：**`request` **能保证任何情况下绝不丢数据吗？**  
不能。它降低故障时已确认写入丢失的风险，但无法替代副本、故障域隔离和快照备份；多副本同时损坏、误删除等仍可能造成数据丢失。

* * *

### 18\. Segment 为什么设计为不可变？

**答：** 不可变 Segment 有利于并发读取、缓存和简化索引文件管理。新增数据产生新 Segment；更新和删除通过标记旧文档失效，并在后续 merge 中回收空间。

**追问：更新文档是原地修改吗？**  
通常不是。更新本质上会生成新版本并使旧版本失效；即使只修改一个字段，也需要考虑重新索引文档的成本。

**追问：删除一定体现为** `.del` **文件吗？**  
面试中说“标记文档删除，后续 merge 清理”即可；文件格式是 Lucene 实现细节，不宜固定为某一种后缀。

* * *

### 19\. 如何提高批量写入性能？

**答：**

1.  使用 Bulk，并通过压测确定批次大小和并发数。
    
2.  允许更长可见延迟时，适当增大 refresh 间隔。
    
3.  简化不必要的字段、分词和索引配置。
    
4.  监控 CPU、磁盘、队列、merge 和 `429`，对拒绝请求做退避重试。
    

**追问：Bulk 返回 HTTP 200 是否代表全部成功？**  
不是。Bulk 可能部分成功，必须检查每个 item 的结果，并对可重试失败单独处理。

**追问：可以临时关闭副本吗？**  
初始全量导入时可以评估，但会降低可用性和数据保护能力；导入后需恢复副本，并等待恢复完成。建议以压测为依据。  

## 四、查询、排序与分页

### 20\. ES 的查询流程是什么？

**答：** 默认通常是 **Query Then Fetch**：

1.  协调节点将查询发给相关分片的一份可用副本。
    
2.  各分片执行查询，返回候选文档标识及排序信息。
    
3.  协调节点合并，选出全局结果。
    
4.  Fetch 阶段从对应分片获取需要返回的文档或字段。
    

**追问：一定会查所有分片吗？**  
不一定。指定 routing、索引范围或利用分片预过滤时，可减少参与查询的分片。

* * *

### 21\. Query Context 和 Filter Context 有什么区别？

**答：**

*   **Query Context：**
    
     判断是否匹配，并计算相关性分数。
    
*   **Filter Context：**
    
     只判断是否匹配，不参与评分；符合条件的过滤结果可能被缓存。
    

**追问：**`filter` **一定比** `must` **快吗？**  
不能保证。它省去评分，并可能受益于缓存，但实际性能还取决于查询、数据和缓存命中情况。  

* * *

### 22. `must`、`filter`、`should`、`must_not` 如何理解？

**答：**

*   `must`
    
    ：必须匹配，通常参与评分。
    
*   `filter`
    
    ：必须匹配，不参与评分。
    
*   `should`
    
    ：满足后通常可以提高评分；是否必须匹配受 `minimum_should_match` 和其他子句影响。
    
*   `must_not`
    
    ：必须不匹配，处于过滤上下文。
    

**追问：**`should` **默认至少匹配几个？**  
如果同一个 `bool` 中有 `should` 且没有 `must` 或 `filter`，默认至少匹配一个；否则默认可为零。需要明确控制时设置 `minimum_should_match`。

* * *

### 23\. ES 如何计算相关性？

**答：** 常见文本字段默认使用 BM25。它综合考虑词频、词条在整个文档集合中的稀有程度、文档长度等因素；分数越高通常表示越相关。

**追问：为什么相同内容在不同分片得分可能不同？**  
默认评分使用分片本地统计信息；数据量小或分布不均时差异更明显。`dfs_query_then_fetch` 可先收集全局统计信息，但会增加一次分布式交互和开销。  

* * *

### 24\. 深分页为什么慢？如何解决？

**答：**`from + size` 越深，每个分片通常都要收集更多候选结果，协调节点也要合并，导致 CPU 和内存开销上升。默认结果窗口通常限制为 10,000。

**追问：深分页用什么？**  
使用 `search_after` 搭配稳定排序；需要跨页保持一致视图时，加上 **PIT**（Point in Time）。它适合顺序翻页，不适合直接跳到任意页。

**追问：Scroll 适合用户实时翻页吗？**  
通常不适合。Scroll 主要用于批量处理等场景；当前官方文档推荐深分页和需要一致视图的导出优先考虑 `search_after + PIT`。  

* * *

### 25\. 聚合为什么可能很慢或结果不精确？

**答：** 聚合成本受匹配文档数、字段基数、分片数量和桶数量影响；`terms` 聚合在分布式场景下返回的部分桶计数可能有误差。

**追问：怎么优化？**  
先缩小过滤范围，使用适合聚合的字段，控制桶数；若需要遍历大量不同桶，可评估 composite aggregation，而不是无限增大 `terms.size`。

## 五、集群、分片与扩容

### 26\. ES 集群中有哪些节点角色？

**答：**

*   **Master-eligible 节点：**
    
     参与选主；被选中的 Master 管理集群状态、索引元数据和分片分配。
    
*   **Data 节点：**
    
     存储分片，执行索引、搜索和聚合。
    
*   **Ingest 节点：**
    
     执行 ingest pipeline。
    
*   **协调节点：**
    
     接收请求、路由并汇总结果；每个节点都可以承担协调职责。
    

**追问：Master 节点一定不存数据、不处理请求吗？**  
不一定，取决于节点角色。生产中的专用 Master 通常不配置 data 角色，也应避免将其作为业务请求入口；但它仍具备协调能力。

* * *

### 27\. 主分片和副本分片有什么作用？

**答：**

*   **主分片：**
    
     承担该分片组的写入协调，也可处理搜索。
    
*   **副本分片：**
    
     保存数据副本，提升可用性，并可分担读请求。
    

**追问：主分片故障后怎么办？**  
集群会从符合条件的副本中提升新的主分片，并在资源和分配条件允许时恢复副本。

**追问：副本能替代备份吗？**  
不能。误删除或逻辑错误也可能同步到副本；需要通过 Snapshot 等机制备份，并验证恢复能力。

* * *

### 28\. 文档如何路由到分片？

**答：** 默认使用文档 `_id` 作为 routing 值，通过哈希确定目标主分片；也可以指定自定义 routing。

**追问：公式一定是** `hash(routing) % 主分片数` **吗？**  
这是便于理解的简化。实际公式与索引创建版本、routing shards 和分区路由配置有关；例如旧版本创建的索引使用不同的路由公式。  

**追问：自定义 routing 有什么好处和风险？**  
可让同一业务实体的数据集中，查询时减少涉及的分片；但可能导致热点和数据倾斜。读、更新、删除时也要正确提供相同 routing。

* * *

### 29\. 主分片数量能修改吗？

**答：** 已创建索引的主分片数不能通过普通动态设置原地修改。但可以通过 **Split、Shrink 或 Reindex 创建新索引**，从而得到不同的主分片数。

**追问：Split 有什么条件？**  
需要满足源索引只读、集群健康和分片倍数等要求，具体可拆分数量受 routing shards 等设置约束。  

**追问：副本数呢？**  
副本数可以动态调整；但副本能否分配成功，还要看节点数量、磁盘和分配规则。

* * *

### 30\. 分片数量如何设计？

**答：** 从预计数据量、增长速度、读写吞吐、恢复时间和节点资源出发，通过压测确定。官方常见经验是单分片约 **10～50 GB**、文档数低于 **2 亿**，但不是硬性规则。

**追问：主分片数必须小于等于数据节点数吗？**  
不必须。一个节点可以承载多个主分片；主分片过少可能限制写入并行度和扩容空间，过多则带来管理和查询开销。

**追问：每 GB 堆内存最多 20 个分片还适用吗？**  
这是旧经验，官方已废弃，不应作为现代版本的固定准则。应结合版本、Mapping、负载和实际资源监控。  

* * *

### 31\. ES 如何扩容？加节点一定能提升性能吗？

**答：** 新节点加入后，集群会根据分配规则和资源情况迁移或重新均衡分片。迁移期间会占用网络、磁盘和 CPU，需要监控恢复进度与业务延迟。

**追问：加了节点却没有分片，为什么？**  
可能是分片数量不足、数据层或分配规则不匹配、磁盘水位限制、节点角色不匹配等。用 `_cluster/allocation/explain` 查看具体原因。

**追问：单个主分片能自动拆开分给多个节点吗？**  
不能。加节点不会自动把现有主分片拆成多个；可根据场景考虑 Split、Reindex 或后续 rollover 时使用新的分片设计。

* * *

### 32\. 什么是脑裂？如何避免？

**答：** 脑裂是指网络分区后，多个分区各自认为自己有权管理同一个集群，导致状态冲突。现代 ES 通过基于多数派的集群协调机制，避免同一集群出现这种不一致。

**追问：三个 Master-eligible 节点如何容错？**  
当投票配置为这三个节点时，多数派是两个。网络分成 2:1 后，包含两个投票节点的一侧可以维持或选出 Master，另一侧不能独立选主。

**追问：奇数节点本身就能防脑裂吗？**  
不能。关键是正确的多数派选举和集群协调协议；奇数通常能更高效地利用投票节点。ES 7 及之后由集群自动管理投票配置，不再使用旧版 `minimum_master_nodes` 配置方式。  

**追问：生产环境为什么常用三个专用 Master？**  
三个 master-eligible 节点通常可容忍其中一个故障，并降低数据任务对集群管理的干扰；具体仍要考虑可用区部署和业务规模。

* * *

## 六、数据同步、可靠性与排障

### 34\. MySQL 和 ES 如何保持数据一致？

**答：** 常见方案是以 MySQL 为数据源，通过 Binlog、CDC 或消息队列把变更异步同步到 ES，并配合失败重试、监控和定期对账。

**追问：异步同步能保证强一致吗？**  
通常只能做到最终一致，存在同步延迟。需要明确业务能否接受延迟；强一致要求高的关键判断应基于权威数据源设计。

**追问：如何处理重复消息和乱序？**  
使用稳定的文档 ID 保证重复写入可控，并结合业务版本或事件顺序防止旧变更覆盖新数据；删除事件也要纳入同步和补偿。

* * *

### 35\. ES 支持事务吗？

**答：** ES 支持单文档级别的原子操作和并发控制，但不提供类似关系数据库的通用跨文档、多表 ACID 事务。

**追问：并发更新怎么防止覆盖？**  
可使用 `_seq_no` 和 `_primary_term` 做乐观并发控制；冲突时由业务决定重试或返回失败。

**追问：近实时和事务是一回事吗？**  
不是。近实时描述的是**搜索可见性延迟**；事务描述的是一组操作的原子性和隔离等性质。

* * *

### 36\. ES 查询慢，怎么排查？

**答：** 先确认是所有查询慢还是特定查询慢，再依次检查：

1.  查询范围、分片数量和是否存在深分页、通配符、脚本或高基数聚合。
    
2.  慢日志、查询 Profile，以及协调节点和数据节点负载。
    
3.  CPU、JVM、GC、磁盘 I/O、页缓存、线程池队列和拒绝数。
    
4.  分片大小、热点、数据倾斜和近期 merge、恢复任务。
    

**追问：Profile 的耗时等于用户看到的总耗时吗？**  
不一定。Profile 主要帮助分析查询内部执行，通常不能覆盖网络、排队和全部协调开销。

* * *

### 37\. 写入突然变慢或出现 429，怎么办？

**答：**`429` 通常表示节点暂时无法承受当前请求速率。先让客户端做指数退避和重试，再检查 Bulk 大小、并发、线程池、磁盘、CPU、merge、refresh 和分片热点。

**追问：直接扩大线程池队列可以吗？**  
不应作为首选。队列变大可能只是延后拒绝，并增加内存压力；应先找出瓶颈并控制写入速率。

* * *

### 38\. 分片未分配或集群变红怎么处理？

**答：** 先查看集群健康和未分配分片，再用 allocation explain 查原因；常见原因包括节点故障、磁盘水位、分配规则和副本不足。

**追问：能直接强制分配空主分片吗？**  
要非常谨慎。强制分配可能丢失原有数据；应先确认是否能恢复原节点、有效副本或快照，再决定恢复方案。
