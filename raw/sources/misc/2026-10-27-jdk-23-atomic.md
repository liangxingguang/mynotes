# AtomicInteger / AtomicLong / AtomicBoolean —— 无锁并发的基石

## AtomicInteger / AtomicLong / AtomicBoolean —— 无锁并发的基石

## 1\. 类的基本介绍

在并发编程中，最朴素的需求就是对计数器做递增、对标志位做赋值。很多人第一反应是 `synchronized` 或 `Lock`，但这两个东西对"改一个整数"来说太重了——线程挂起、上下文切换、锁竞争放大，光想想就心疼。

JUC 包里的 Atomic 系列类，包括 `AtomicInteger`、`AtomicLong`、`AtomicBoolean`，专门就是为了解决"对一个变量做原子更新"这个场景。它们全部在 `java.util.concurrent.atomic` 包下，底层依赖 **CAS（Compare-And-Swap，比较并交换）** 和 `Unsafe` 类，走的是**无锁（lock-free）路线**，比加锁通常快一个数量级。

### 继承体系

它们仨之间没有继承关系，各自独立：

```
AtomicInteger  extends Number  implements SerializableAtomicLong     extends Number  implements SerializableAtomicBoolean  implements Serializable
```

`AtomicInteger` 和 `AtomicLong` 继承了 `Number`，所以可以当做数值用。`AtomicBoolean` 只实现了 `Serializable`，不过内部维护的是一个 `volatile int`（valueOffset 是 1 代表 true，0 代表 false）。

## 2\. 源码截图

### 2.1 AtomicInteger 核心源码

```
// java.util.concurrent.atomic.AtomicIntegerpublic class AtomicInteger extends Number implements Serializable {    private static final Unsafe U = Unsafe.getUnsafe();    private static final long VALUE;  // value 字段的内存偏移量    static {        try {            // 通过 Unsafe 获取 value 字段在对象内存布局中的偏移量            VALUE = U.objectFieldOffset(AtomicInteger.class.getDeclaredField("value"));        } catch (ReflectiveOperationException e) {            throw new Error(e);        }    }    // volatile 保证可见性，但不保证原子性    private volatile int value;    public AtomicInteger(int initialValue) {        value = initialValue;    }    public AtomicInteger() {    }    // 核心方法：CAS 自旋递增    public final int incrementAndGet() {        // 在循环中不断尝试 CAS，直到成功        for (;;) {            int current = get();          // 读取当前值            int next = current + 1;      // 计算新值            // CAS 操作：如果当前 value == current，则更新为 next            if (U.compareAndSetInt(this, VALUE, current, next))                return next;            // 成功则返回新值            // CAS 失败说明其他线程改了，继续重试        }    }    // 等价写法，语义更明确    public final int getAndIncrement() {        for (;;) {            int current = get();            int next = current + 1;            if (U.compareAndSetInt(this, VALUE, current, next))                return current;  // 返回旧值        }    }    // 自定义delta的自旋    public final int addAndGet(int delta) {        for (;;) {            int current = get();            int next = current + delta;            if (U.compareAndSetInt(this, VALUE, current, next))                return next;        }    }    // compareAndSet：外部调用的CAS，你期望值是expected就改成newValue    public final boolean compareAndSet(int expectedValue, int newValue) {        return U.compareAndSetInt(this, VALUE, expectedValue, newValue);    }    // 懒更新——不保证其他线程立即看到新值    // 但性能更好，适合"最终一致"的场景    public final void lazySet(int newValue) {        U.putIntRelease(this, VALUE, newValue);    }    // --- 从Number继承的转换方法 ---    public int intValue()       { return get(); }    public long longValue()     { return (long)get(); }    public float floatValue()   { return (float)get(); }    public double doubleValue() { return (double)get(); }}
```

### 2.2 AtomicBoolean 源码

```
public class AtomicBoolean implements Serializable {    private static final Unsafe U = Unsafe.getUnsafe();    private static final long VALUE;    static {        try {            VALUE = U.objectFieldOffset(AtomicBoolean.class.getDeclaredField("value"));        } catch (ReflectiveOperationException e) {            throw new Error(e);        }    }    // 内部用 int 存储，1=true，0=false    // 因为 Unsafe.compareAndSetInt 对 int 做 CAS，没有针对 boolean 的    private volatile int value;    public AtomicBoolean(boolean initialValue) {        value = initialValue ? 1 : 0;    }    public AtomicBoolean() {}    public final boolean get() {        return value != 0;    }    // 核心：原子地设置新值，返回旧值    public final boolean getAndSet(boolean newValue) {        int nv = newValue ? 1 : 0;        // 自旋CAS：不管当前是什么值，都替换成新值        for (;;) {            int current = value;            if (U.compareAndSetInt(this, VALUE, current, nv))                return current != 0;        }    }    // 最常用的方法：只有当前值等于expect时才改成update    // 常用于实现"一次性标记"（只执行一次的逻辑）    public final boolean compareAndSet(boolean expectedValue, boolean newValue) {        int e = expectedValue ? 1 : 0;        int n = newValue ? 1 : 0;        return U.compareAndSetInt(this, VALUE, e, n);    }}
```

### 2.3 Unsafe 层面的 CAS 实现（native 代码）

`compareAndSetInt` 最终路由到 JVM 的 `Unsafe_CompareAndSetInt`，在 HotSpot 中会用 CPU 的 **`cmpxchg` 指令**（x86 架构）。如果多核 CPU，指令前会加 **`lock` 前缀**，锁住缓存行（cache line），实现原子性。

```
// 伪代码级别的理解boolean CAS(int* addr, int expected, int newValue) {    if (*addr == expected) {        *addr = newValue;        return true;    }    return false;}
```

这个过程是**硬件级别保证原子**的，不涉及线程挂起、锁等待。

## 3\. 核心原理

### 3.1 CAS（Compare-And-Swap）

CAS 是乐观锁思想的体现。它假设冲突很少发生，直接尝试更新，失败了就重试——这就是 **自旋（spin）**。

```
线程A：读取 value = 5线程B：读取 value = 5线程A：CAS(5 → 6) → 成功，value = 6线程B：CAS(5 → 6) → 失败（value现在是6了）→ 重新读取6 → CAS(6 → 7) → 成功
```

整个过程**没有锁的申请和释放**，没有线程切换，所以轻量级。但高并发下自旋次数多就会浪费 CPU，这叫 **CAS 空转（CAS spin waste）**。

### 3.2 volatile + CAS

Atomic 系列用 `volatile` 保证了可见性——一个线程改了 value，其他线程立即可见。但 volatile 不能保证 `value++` 的原子性（这是个读-改-写三步操作），所以需要 CAS 来把这三步合并成一步原子的操作。

**所以：AtomicInteger = volatile 保证可见性 + CAS 保证原子性，缺一不可。**

### 3.3 AtomicLong 与 AtomicInteger 的不同

AtomicLong 的源码几乎跟 AtomicInteger 一模一样，只是把 `compareAndSetInt` 换成了 `compareAndSetLong`。但在 32 位 JVM 上，long 是 64 位的，分高 32 位和低 32 位存储，CAS 在 32 位架构下实际上需要两条 CPU 指令来保证。不过 HotSpot 在 32 位上也用 `cmpxchg8b` 指令保证了 64 位 CAS 的原子性。

**64 位 JVM 上两者性能差异可以忽略。**

### 3.4 AtomicBoolean 为什么用 int 而不是 boolean？

这是很多人第一次看到源码时的一个小困惑。原因很简单：`Unsafe` 只有 `compareAndSetInt`、`compareAndSetLong`、`compareAndSetObject` 这些方法——**没有针对 boolean 的 CAS 操作**。所以内部用 int 存储，1=true、0=false，复用 int 的 CAS 是最直接的做法。

## 4\. 使用示例

### 4.1 计数器：多线程统计请求数

```
import java.util.concurrent.*;import java.util.concurrent.atomic.*;public class AtomicCounterDemo {    private static final AtomicInteger requestCount = new AtomicInteger(0);    public static void main(String[] args) throws Exception {        int threadCount = 10;        int requestsPerThread = 10000;        ExecutorService pool = Executors.newFixedThreadPool(threadCount);        CountDownLatch latch = new CountDownLatch(threadCount);        for (int i = 0; i < threadCount; i++) {            pool.submit(() -> {                for (int j = 0; j < requestsPerThread; j++) {                    // 模拟处理请求                    processRequest();                    requestCount.incrementAndGet();                }                latch.countDown();            });        }        latch.await();        pool.shutdown();        System.out.println("期望值: " + (threadCount * requestsPerThread));        System.out.println("实际值: " + requestCount.get());        System.out.println("结果正确: " + (requestCount.get() == threadCount * requestsPerThread));        // 输出：期望值: 100000, 实际值: 100000, 结果正确: true    }    static void processRequest() {        // 模拟耗时        Thread.yield();    }}
```

如果用 `int count` + `count++`，结果大概率小于 100000。用 AtomicInteger 保证每一次++都是原子的。

### 4.2 一次性初始化标记（AtomicBoolean 的经典用法）

```
import java.util.concurrent.atomic.*;public class LazyInitDemo {    // 用 AtomicBoolean 做"只执行一次"的开关    private final AtomicBoolean initialized = new AtomicBoolean(false);    public void init() {        if (initialized.compareAndSet(false, true)) {            // 只有第一个调用 compareAndSet 成功的线程会进来            System.out.println(Thread.currentThread().getName() + " 执行初始化...");            doExpensiveInit();            System.out.println(Thread.currentThread().getName() + " 初始化完成");        } else {            System.out.println(Thread.currentThread().getName() + " 跳过——已经初始化过了");        }    }    private void doExpensiveInit() {        try { Thread.sleep(1000); } catch (InterruptedException e) {}    }    public static void main(String[] args) {        LazyInitDemo demo = new LazyInitDemo();        for (int i = 0; i < 5; i++) {            new Thread(demo::init, "线程-" + i).start();        }    }}
```

输出示例：

```
线程-0 执行初始化...线程-2 跳过——已经初始化过了线程-1 跳过——已经初始化过了线程-3 跳过——已经初始化过了线程-4 跳过——已经初始化过了线程-0 初始化完成
```

这个模式在框架里很常见——比如连接池的首次初始化、缓存的懒加载、配置的一次性加载。

### 4.3 AtomicLong 做唯一 ID 生成器

```
import java.util.concurrent.atomic.*;public class IdGenerator {    private static final AtomicLong sequence = new AtomicLong(System.currentTimeMillis());    // 生成全局唯一的递增ID（单机范围内）    public static long nextId() {        return sequence.incrementAndGet();    }    public static void main(String[] args) throws Exception {        // 多线程环境下，不会产生重复ID        for (int i = 0; i < 10; i++) {            new Thread(() -> System.out.println(nextId())).start();        }    }}
```

> 注意：这只是最简单的递增ID。生产级别的发号器（比如雪花算法Snowflake ID）要考虑机器ID、时间回拨、时钟同步等问题，但核心也是AtomicLong。

### 4.4 用 compareAndSet 实现非阻塞链表节点入队

```
import java.util.concurrent.atomic.*;class Node {    final int value;    final AtomicReference<Node> next = new AtomicReference<>(null);    Node(int value) { this.value = value; }}public class LockFreeQueue {    // 这里展示 AtomicReference（AtomicInteger 的引用版）的CAS用法    // 原理和 AtomicInteger 完全一样，只是操作的是引用而非 int    private final Node dummy = new Node(-1);    private final AtomicReference<Node> tail = new AtomicReference<>(dummy);    public void enqueue(int value) {        Node node = new Node(value);        for (;;) {            Node currentTail = tail.get();            // 尝试CAS设置当前尾节点的next            if (currentTail.next.compareAndSet(null, node)) {                // 成功后移动tail指针（这里简化了，实际需要处理并发移动）                tail.compareAndSet(currentTail, node);                return;            }            // CAS失败说明其他线程已经改了next，推动tail            tail.compareAndSet(currentTail, currentTail.next.get());        }    }}
```

## 5\. 注意事项

### 5.1 ABA 问题

CAS 的核心是"比较当前值和期望值是否相等"，但这有个坑：

```
线程A：读取 value = A线程B：value 从 A → B → A（改了一圈又回来了）线程A：CAS(A → C) → 成功！但 value 已经不是原来的 value 了...
```

解决方法：用 `AtomicStampedReference`（后面会写到的类），带版本号/时间戳来区分"同值不同代"。

绝大多数场景（计数器、递增ID）不会有 ABA 问题，只有链表、栈这种涉及到引用对象复用的场景才要小心。

### 5.2 伪共享（False Sharing）

AtomicLong 在高并发计数器场景（比如 `LongAdder` 诞生前）会遇到伪共享问题：多个 AtomicLong 恰好在同一个缓存行（cache line，通常 64 字节）上，修改一个会导致其他 CPU 的缓存行失效。

JDK 8 引入了 `@Contended` 注解解决这个问题，不过 `AtomicLong` 本身没加，`LongAdder` 内部的 Cell 数组加了。

### 5.3 性能考量

*   **低/中并发**：AtomicInteger/Long 性能极好，远超 `synchronized`
    
*   **极高并发（万级+线程争抢同一个变量）**：CAS 自旋次数暴涨，CPU 空转严重 ➡ 改用 `LongAdder`（分段累加，最终汇总）
    
*   **AtomicBoolean 的 compareAndSet 比 getAndSet 更高效吗？** 不，两者底层都是 CAS，只是语义不同
    

### 5.4 不要用 AtomicInteger 代替 volatile 做所有线程通信

AtomicInteger 的 CAS 自旋适合**写多读少的竞争更新**场景。但如果你只需要"一个线程写、多个线程读"，普通 `volatile` 就够了：

```
// volatile 就够了——只有一个写线程volatile boolean stopped = false;// 没必要用 AtomicBooleanAtomicBoolean stopped = new AtomicBoolean(false);
```

### 5.5 常见误区

```
// ❌ 错误：先get再操作，不是原子的！int value = atomicInt.get();if (value > 0) {    atomicInt.decrementAndGet();  // 此时value可能已经变了}// ✅ 正确：用CAS自旋for (;;) {    int current = atomicInt.get();    if (current <= 0) break;    if (atomicInt.compareAndSet(current, current - 1)) break;}// 或者直接用 JDK 8 的 updateAndGetatomicInt.updateAndGet(n -> n > 0 ? n - 1 : n);
```

**选型建议：**

*   **简单计数、累加** → `AtomicInteger` / `AtomicLong`
    
*   **标记位、一次性开关** → `AtomicBoolean`
    
*   **高并发写（万级以上）** → `LongAdder`（计数器）、`LongAccumulator`（累加器）
    
*   **引用更新** → `AtomicReference` / `AtomicStampedReference`
    
*   **读多写极少** → `volatile` 就够了，别上Atomic

## 总结

AtomicInteger 三兄弟是我个人觉得 Java 并发包里设计最"通透"的类。三个类的源码加一起不到 500 行，CAS 自旋的 for 循环就是全部秘密。它们展示了无锁编程的核心理念：**不要阻塞，失败了就再试一次**。

我特别喜欢它们的 API 设计——`incrementAndGet`、`compareAndSet`、`getAndUpdate`（JDK 8 加入），方法名即文档，看一眼就知道干什么。

理解 AtomicInteger 是理解 JUC 所有高级并发工具（ReentrantLock、ConcurrentHashMap、ThreadPoolExecutor 等）的前置知识。下一期会写 `LongAdder`，看看它在 AtomicLong 的基础上是怎么解决高并发 CAS 自旋痛点的。我们下期见。
