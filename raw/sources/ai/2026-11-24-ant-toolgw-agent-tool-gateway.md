# 蚂蚁 AI 工具网关 ToolGW：全站统一的 Agent 工具流量入口 | 能力全景与技术架构详解

> 来源：金融级分布式架构（公众号）｜作者：董振兴（单延），蚂蚁集团研发工程师，超算中间件团队，ToolGW 负责人｜2026年11月24日

## 01 Agent 要干活，先得够得着工具

背景：Agent 干活靠调用工具（查订单、发消息、跑流水线、检索知识库），而蚂蚁的工具"住"在线上——几万个存量 RPC/HTTP 服务、内部自建 MCP Server、社区公网 MCP，散布在十几个租户、几十个机房。

两类调用方、两张网：
- **办公网·终端 Agent**：本地跑的 Claude Code、Codex 等，要访问线上 MCP Server 与远程 API，本地够不着线上服务，也不能放任直连绕过管控。
- **生产网·线上 Agent**：业务 Agent 应用要调用远程 MCP Server，需统一、安全、可审计的通道。

直连不是答案，面临四困：
- **安全之困**：员工/Agent 身份核验、工具粒度权限、调用审计与内容审核无人兜底。
- **拓扑之繁**：多业务主体、多站点、多租户网络彼此隔离，叠加办公网/生产网、内部员工/数字员工/C 端用户、内部工具/社区工具，复杂度不该甩给调用方。
- **供给之难**：存量服务讲 RPC（Dubbo、gRPC）与 HTTP API，Agent 听 MCP 或 CLI，横着协议鸿沟，无翻译则需逐个重开发 MCP/CLI，几万能力重复建设。
- **入口之乱**：MCP 与 CLI 流量此前由不同独立网关承接，甚至客户端直连服务端域名，缺乏统一入口。

**一句话定位**：全站统一的安全工具流量入口。支持全站各类型、各技术栈的 MCP、CLI 流量代理，以及所有 RPC、HTTP（含流式）服务（AI Tool），让各类调用方、各站点、各环境都能以 MCP 或 CLI 形式简单、高效、安全地访问工具。

**当前规模**：MCP 接入量 10000+ ｜ 存量 RPC API 上翻 MCP Server 4000+ ｜ CLI Tool 60000+ ｜ 整体峰值 QPM 25w+

## 02 不做"又一个网关"，做"唯一入口"

四条设计理念：
1. **AI Tool 是可治理的能力对象**：CLI、MCP、API、Skill 只是能力的消费形态，能力沉淀一次、各形态按需消费，ToolGW 是所有形态背后的统一流量与安全底座。
2. **协议、网络、站点三轴正交**：任一能力 × 任一协议 × 任一网络/站点/环境，都应在一张部署矩阵中可定位、可验收、可观测。
3. **安全默认开启，而非默认豁免**：身份、授权、审核、风险、审计内置在链路里，业务接入即享受。
4. **能力合并，入口统一**：MCP 代理与 CLI 流量代理收敛于同一网关、一套底座，避免多套系统并行维护。

## 03 三层体系，全站矩阵

**整体架构三层**：
- **产品平台 ATC**（Ant Tool Center，蚂蚁 AI 工具中心）：面向用户的统一入口，开放 Server/Tool 的注册、编排、上架、授权与可观测、评测、治理。
- **网关管控面**：各类型/场景/技术栈 MCP Server 配置与 AI Tool 配置的统一管控，面向 ATC 开放管控 API。
- **数据面 ToolGw**：协议接入、路由寻址、鉴权、限流、协议转换、Session 粘连、Mock、流量录制等，全链路可观测可治理。

**数据面流水线**：协议适配层（识别并解包 MCP SSE / MCP Streamable / CLI REST）→ ToolEngine（协议无关的调用引擎，MCP 与 CLI 共享同一实例）→ 协议转换层（按注册声明把请求翻译成对 RPC 或 HTTP 后端，或原生 MCP Server 的真实调用）。

**技术栈**：纯 Go 自研数据面，基于 SOFA 体系的 RPC 泛化调用、SOFA Registry 注册中心服务发现、配置中心推送、分布式缓存、SOFAMQ 消息、向量数据库（承载流量录制与 Mock 数据），加上统一权限平台、异步安全审核、加密服务。

**部署**：每个租户独立部署单元的全站矩阵。各业务站点独立部署网关节点，另有面向社区公网流量与 C 端/商户流量的独立部署单元——本质是同一个 ToolGW 应用，按流量类型物理拆分部署、彼此隔离，统一迭代、统一运维。数据面在每个业务租户内部就近闭环，跨租户访问再经网关统一出口转发。办公网与生产网流量统一经 ToolGW 完成 Agent 到资源（A-R）、人到资源（H-R）的身份核验。

## 04 核心能力与技术机制

### 4.1 双协议接入：一张菜单，一个点餐窗口

三个词：**API 是后厨**（真正做菜的地方）；**MCP 是带完整菜单的餐厅**（菜单写给 Agent 看，每道菜是什么、要什么参数、返回什么都写明）；**CLI 是直接点餐的通道**（不翻菜单，报菜名就下单）。

- **MCP**：含完整菜单的点餐——Agent 先翻菜单（tools/list），看清工具是什么、怎么用，再下单（tools/call）。
- **CLI**：直接点餐——工具已知、用法已明，报菜名就下单，一条命令直接调用。

统一两入口的原因：同一工具若菜单一套、窗口一套，要维护两份接入、两份权限、两份观测治理。ToolGW 让两个入口共用一个门面、一套底座，菜只做一遍。

**工具协议转换引擎**：MCP 侧支持标准双传输（SSE 长连接与 Streamable HTTP），CLI 侧是统一的 /api/v1/** REST 入口。MCP 入口接各类 Agent 框架与自研标准 MCP Server，统一入驻、由网关代理转发（路由寻址、鉴权、Session 粘连归网关，服务仍由原团队维护）；存量 RPC/HTTP 上翻出的 AI Tool，由网关现场"翻译"，以 MCP 协议与客户端标准交互。

关键机制：MCP 和 CLI 流量代理共享同一个 ToolEngine——协议层只做适配，Tool 元数据与调用内核完全复用。Engine 按注册声明路由后端：上翻的 AI Tool 走协议推断（声明 HTTP 就翻译成 HTTP 请求，声明 RPC 就按 RPC 泛化调用），结果由网关封装为标准 MCP 协议响应或原生响应吐出；自研 MCP 接入方背后的原生 MCP Server（内部 Agent 框架/FaaS/Serverless/开源框架/社区）由网关直接代理转发、不做翻译。调用方全程不用关心后端是 RPC、HTTP API 还是原生 MCP Server。

**三种寻址方式**：
- **MCP serverCode 寻址**：内部对 MCP 服务约定统一服务标识 ServerCode，客户端直连 Tool 网关域名，Header 或 URL 带 ServerCode 即可。
- **CLI URL 寻址**：按注册时声明的 URL（如 /api/v1/users/{userId}）直接匹配，路径参数自动提取，对 Coding Agent 友好。
- **注册中心服务发现**：生产网 Agent 应用推荐姿势——toolgw 将代理的 MCP Server 以服务形式发布（pub）到注册中心，调用方经 MOSN 服务发现直接寻址，像调普通 RPC 一样调 MCP，无需感知网关域名。

打通五类流量场景：场景 1–4 由"一次 Tool 注册"打通；场景 5 是网关对自研、社区 MCP Server 的纯代理接入——治理归网关，实现归原团队。

### 4.2 全站路由代理：一张网管住所有工具流量

蚂蚁各租户之间网络本身隔离——各站点机房域互不相通，办公网与生产网也是两张独立网。跨租户访问只能经各租户网关之间打通的转发链路（安全管控打通的网络通道），这正是"每租户独立部署网关单元、出口互连"架构存在的根本理由。

**内部全站：注册入驻、发现与路由**：每租户独立部署网关单元，Tool 元数据经配置中心推送、就近加载；多机房基于 SOFA Registry 做多机房服务发现，同机房优先、带权重轮询；跨站点调用只需多带一个目标租户标识 Header，网关自动转发到目标租户网关，链路对调用方完全透明。

**外部社区工具托管代理**：高德这类社区 MCP Server，企业内不该人人直连。ToolGW 用独立公网部署单元统一代理——与各租户网关是同一 ToolGW 应用，仅为社区公网流量物理拆分部署；集采 API Key 平台托管、统一限流管控计费；个人 Key 上传后进安全托管体系，调用时以托管凭证标识携带，Key 不暴露给调用方。

**C 端流量隔离**：C 端用户与第三方商户工具流量由独立入口承接，配独立身份体系，与内部员工/Agent 流量物理隔离。

**分布式 Session 粘连**：针对 MCP 有状态会话维持——SSE 长连接要求"同一会话的推送必须由建立连接的那台网关机器完成"。连接建立时把 SessionID 与机器映射写入分布式缓存，后续请求不管落到哪台机器，都按 Session 定位到持有连接的网关机器精准转回，多机部署下会话不串机。

### 4.3 Agent 时代的身份与安全：谁在调用，能调用哪个工具

安全是 ToolGW 第一卖点：身份核验、权限管控、参数防篡改、内容审核全部内置。

**双身份体系**：两类调用责任主体不同——员工办公网调用是员工个人行为，出问题要找得到人；生产网调用是 Agent 应用行为，权限责任落到应用与负责人。办公网来的是员工，出示员工身份令牌；生产网来的是 Agent 应用，出示 Agent 身份标识（内含 Agent 编码），两套身份各走各的核验链路。

早期简单身份体系有短板：纯 Agent 编码与裸露员工令牌存在权限放大、绕行等风险。为此向**统一 AgentToken** 演进——Agent 身份与员工身份合而为一，统一经 ToolGW 完成身份认证与换签；纯 Agent 身份访问进一步收口，所有内部访问落到员工身份或数字员工身份上鉴权，落实为 A-R（Agent 到资源）+ H-R（人到资源）核验。

**Tool 粒度权限管控**：能力一旦开放给 AI，权限若只做到 Server 粒度，等于拿到入口授权就能调用其下所有工具——AI 场景最经典的越权事故。网关与统一权限平台协同做两层鉴权：第一层验入口权限（MCP Server/CLI），第二层验具体工具调用权限。最实用设计是**血缘自动管理**：MCP Server/CLI 与 Tool 对应关系由平台自动记录，申请权限时面向整体一键申请，关联全部 Tool 权限同时生效。

**跨站点身份互通与转换**：集团内多个独立业务主体，员工身份体系各自独立。A 主体 Agent 直接揣员工身份访问 B 主体工具，B 主体服务不认识外来身份。跨租户访问必须由网关完成身份互通与转换：发起方 ToolGW 发起跨租户调用时，先经互通中心换取互通 Token，再携 Token 代理转发到目标站点网关，经目标站点权限平台换成其可识别的身份后，由目标站点网关调用业务服务端，服务端照常按"自己人"鉴权——调用方全程无感，各主体身份体系不用互相打通重建。全链路透传身份到下游，网关侧完成应用令牌到员工身份令牌的换签。

**全链路可信参数**：AI 场景特有难题——模型可能"好心"替你填错敏感参数（如把订单 ID 编错）。解法：敏感参数在注册时标记为"固定可信值"，调用时调用方主动往加签身份链路串中注入，由网关解包后根据可信参数标识替换注入，模型看不见、更无法篡改。

**数据安全**：内容安全采用异步审核模式——ToolGW 在日志中记录每次工具调用的出入参数，由安全审核平台采集后异步审核，全程可审计可追溯；加密服务管传输加密，响应脱敏插件确保敏感数据不出现在响应里。

### 4.4 工具供给侧：存量服务的零代码上翻

蚂蚁几万个存量服务，不能让每个团队重新学 MCP、全部重开发 MCP Server。ToolGW 答案：**零代码上翻**。

**RPC 上翻：存量服务零代码变 MCP**：RPC 与 HTTP 两类后端本质同一件事，只是后端 API 协议不同，现均已上线——在产品页选好服务与方法、写清工具描述与参数描述，或在 Claude Code 等 Agent 里跑转换 Skill 几分钟自动完成，存量 RPC/HTTP 服务变成标准 MCP Server，不改一行后端代码。

机制三点：
- **虚拟 Server 集群**：上翻转换出的 MCP Server 是网关内虚拟服务实例——配置经动态配置中心推送，网关订阅即生效，发布不用重启；当前 4000+ MCP Server、20000+ MCP Tool 规模全靠这套配置热更新机制撑着。
- **协议转换**：tools/list 按元数据动态生成标准 MCP 协议工具描述，tools/call 把 JSON-RPC 参数按声明翻译成 RPC 泛化调用或 HTTP 请求；HTTP 侧每个参数能指定去处（path/query/header/body），路径占位符与 Header 变量替换都支持，同时支持参数默认值、模型可见性、可信参数、系统参数等配置。
- **响应模板**：后端返回的原始响应数据 JSON 可经自定义模板渲染成模型友好的结构化文本。

**多协议跨服务的 AI Tool**：一个后端 API 注册为一个 AI Tool，注册时声明后端协议（RPC 或 HTTP，其它可扩展），调用方不用管；多个 AI Tool 按业务场景组成工具分组——"订单工具组"里可同时有 HTTP 的查用户和 RPC 的建订单；同一 Tool 还能同时上架给多个 MCP Server 和多个 CLI，一处配置、处处使用。

顺带解决 MCP "上下文膨胀"问题：业内实测，给 Agent 挂 3 个 MCP Server，光工具定义就能吃掉 200K 上下文的七成，工具越多选择准确率越低。场景化分组天然是"工具懒加载"——一个 Server 只装当前场景需要的工具，少而准，Agent 工具选择更可靠。

**CLI 研发流水线**：平台侧设计基于 AI Tool 的 CLI 研发流程——可基于已注册 AI Tool 自动初始化 CLI 代码工程、建仓、初始化元数据，完成基于所选 AI Tool 的 CLI 代码开发、构建与上架。同时支持安全访问：CLI 基于统一 CLI SDK 构建并默认集成可信身份，安装下来无需手动配置凭证即可安全、可审计地访问后端 API。工程链路全自动：平台一键完成 CLI 工程创建与初始化，把 Tool 远程调用契约打包成开发 Prompt，交给本地 Coding Agent 辅助生成远程调用功能代码，流水线完成安全检查、血缘关联授权与制品构建。

### 4.5 流量治理与可观测：既防打挂，也防漂移

**限流防护**：Agent 调工具不知道心疼后端——一次任务动辄连环发起成百上千次调用，后端可能瞬间被打挂；社区 MCP 通常按量计费，被刷一轮就是真金白银。限流必须长在网关上，而不是让每个后端服务自己配闸机。分四个层次，集群维度采用异步限流：单机本地计数、定期扣减全局额度，既保准确又不给调用加时延。

**MCP/CLI Mock**：四个研发日常堵点——后端接口还在开发，Agent 侧干等；后端不稳定，测试时好时坏（flaky）；超时、报错、流式中断等边界场景想复现却复现不了；工具或后端升级后说不清行为是否还一致。

ToolGW 解法：把 Mock、录制、回放全部内置到网关链路——MCP 的 tools/call（Streamable）与 CLI 的 /api/v1 调用在 Engine 层收敛于同一调用入口，MockInterceptor 在此一次拦截，双协议全覆盖；拦截点位于鉴权、路由之后、后端调用之前，精确到 Tool 粒度——Mock 请求照常过鉴权、照常记 Trace（Mock 流量全程可审计），InputSchema 与响应模板等元数据全部复用，无需额外部署 Mock Server。

能力设计：
- **三类匹配条件**：参数（JSONPath 定位字段 + 13 种操作符）、请求 Header、来源 Agent（如仅对 codex 生效）、来源人员，同一规则内可组合、按优先级逐条匹配。
- **五种响应模式**：fixture 固定响应、随机响应、error 模拟业务错误、timeout 模拟延迟与超时、record_replay 录制回放。
- **产品化配置**：MCP 详情页与 AI Tool 详情页各自新增 Mock Tab，按 Tool 配规则、指定生效环境，保存即热更新生效。

**MCP/CLI 流量录制与回放**：与 Mock 并列的独立能力——Mock 是"假造响应、不打后端"，录制回放是"调真实后端、把请求响应原样落盘、再按需重放"。两者与重放客户端一起构成"录/改/放"完整闭环——RecordInterceptor 负责录制、Replayer 负责主动重放，三者共用同一套主体标识（MCP 为 serverCode + toolName，AI Tool 为 groupName + toolName）与同一份录制数据，独立部署、互不依赖。

覆盖五类高频场景：线上偶发故障复现；回归测试数据集（真实调用沉淀为回归基线，CI 持续回放断言）；低频接口离线分析；Mock 数据自动生成（录制流量一键生成 fixture 规则反哺 Mock）；协议兼容性验证（Tool 升级前后各回放一轮验证响应一致性）。

**流量录制**：先选 Tool 再配策略——总开关 → Tool 列表逐个开启 → 为每个 Tool 配保留时长、录像条数上限与录制环境，四种录制策略可叠加：按采样率（0~1 控制流量与成本）、按 Header 条件、按参数条件、按来源 Agent（如仅录 codex 发起的调用），多策略同时存在时全部满足才录制。录制模式固定为"录放"——无命中回放规则时调真实后端并录制，有命中直接短路返回。最近录制记录表支持"生成规则"反哺 Mock，也可导出录像文件用于跨环境回放。

核心技术架构两条主线：流量 **Mock** 走 ToolGW 内置的 Mock 拦截器——请求在 Engine 层按规则匹配，命中即返回 Mock 响应、不打后端；流量**录制**基于 ToolGW 的消息异步投递——Engine 完成真实后端调用后，把请求与响应异步投出（不阻塞调用链），管控面消费并持久化到向量数据库中，用于后续复用回放或作为 Mock 数据源。

回放两种玩法互不替代。回放任务以任务列表方式管理：新建任务支持多 Tool 复选同发、数据源选向量数据库或导入文件、对比模式选 strict 全等或 json-path 按字段（自动忽略 trace_id、耗时、时间戳等天然不可复现的噪声字段），并发数与速率可调。发起入口三种——Console 界面任务、独立回放 CLI（供 CI 与脚本批量调用）、定时任务（如每日对 P0 Tool 全量重放）。

回放完成后进入独立**回放报告页**：KPI 仪表盘汇总一致/不一致/错误三态结果与总时长，按 Tool 分组展示对比明细，基线与实际响应并排呈现、行级差异高亮——升级改了什么，报告页一看便知。

再叠加 Mock 的混沌评测能力——error/timeout 模式按参数精准注入超时与错误，验证 Agent 的重试、容错与用户提示逻辑——这套"录/改/放"体系构成 Agent 研发的完整测试基座：问题在上线前就能暴露，不用等线上用户帮你发现。

**可观测**：五类标准日志（client-digest / server-digest / event / stat / error）、Tracer 全链路追踪、统一错误码体系、系统/Tool/协议三级监控告警——出了问题，从网关到后端一条 Trace 查到底，配套问题排查 SOP，不靠猜。

## 05 结语：一个入口，全站可达

ToolGW 把 Agent 工具访问做成全站基础设施：
- **能力一次沉淀**：存量 RPC/HTTP 服务零代码上翻、各技术栈自研 MCP Server 统一入驻。
- **入口顺手即用**：MCP 与 CLI 双协议门面、多种寻址，调用方怎么顺手怎么来。
- **全站一张网**：租户独立部署、出口互连，跨租户访问对调用方完全透明。
- **安全默认开启**：双身份、Tool 粒度权限、可信参数、限流防护、全链路可观测——接入即享受。

工具生态还会继续演化，MCP、CLI、API、Skill 都只是能力的消费形态；真正不该重复建设的，是背后统一的流量与安全底座。
