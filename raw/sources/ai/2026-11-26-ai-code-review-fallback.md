> 故善战者，求之于势，不责于人，故能择人而任势。 —— 《孙子兵法·兵势》

前两天那篇聊代码审查退场的文章发出去以后，引来不少同行讨论。大家的分歧很有意思，几乎把当下软件工程界最真实的一批焦虑全摊在了桌面上。

有人觉得步子还得慢慢迈，先一点点提高 AI 审查的置信度，等团队心里踏实了，再逐步放开 PR 的合并数量。也有人走得更远，觉得 PR 本身就是给人类设计的旧流程，未来有且只有一个标准：把镜像流量直接引到生产环境里跑端到端验证，连手写测试都成了多余。当然，还有更冷静也更彻底的看法，觉得编程这件事纪律性和逻辑性太强，正中大模型的胃口，未来消失的恐怕不止是代码审查，连传统意义上的程序员岗位都会被重写。

这些声音背后有个绕不开的前提：新公司和旧公司完全活在两个世界里。白手起家的新团队可以直接把旧流程掀翻重来，连 CI 都可以从底向上推倒重做；背着十几年历史包袱的大公司，只能在保证业务不停摆的前提下缓缓转身，这个过程可能要花一两年，也可能需要三五年。

热闹归热闹，讨论里最值得认真琢磨的，还是几位一线资深工程师抛出来的两个实打实的反问。第一个问题是，那些逻辑全对、测试全绿，却藏在热路径里的隐蔽坑，不审代码怎么防？第二个问题更戳心：代码从来没细看过，真到线上出大事、还得由人来背锅的时候，手里没底气怎么办？

这两个问题问到了骨头上。如果答不清楚，所谓「放弃代码审查」听上去就真成了一句不负责任的暴论。今天索性接着往下深挖一层：code review 终究只是一种手段，要是回到第一性原理，把软件工程的旧习惯先搁一边，未来最合理的兜底方案到底该长什么样？

## 一、逻辑全对，照样会出事

先看第一个反问。做过高并发系统的工程师，多半都见过一类特别让人头疼的线上隐患。

设想一个 API 网关里的请求鉴权或日志脱敏中间件，逻辑很简单：每次请求进来，顺手编译一条正则表达式去匹配路径，或者把一段静态路由策略重新反序列化一遍再查表。单看这几行代码，逻辑严丝合缝，可读性极佳，单元测试跑得飞快且全部通过。搁在普通的后台管理接口里，这么写挑不出半点毛病。

可坏就坏在，这段代码挂在每秒处理几十万次请求的网关入口热路径上。每一次请求进来都白白消耗不少 CPU 和内存，平时在测试环境或者低流量灰度里风平浪静，一旦遇上业务高峰，CPU 瞬间打满，长尾延迟一路窜上去。

这就是很多工程师对 AI 生成代码最忌惮的地方。大模型写出来的代码，最常见的隐患早就不只是语法报错或者空指针了，恰恰是这种「一眼看上去完全正确，甚至写得很优雅，但坑藏在真实流量规模里」的实现。写代码的人也好，干活的智能体也罢，心里如果没装着这份流量背景，顺手就会写出这种低负载下毫无破绽、高负载下直接拖垮服务的实现。

有人马上会问：那把这条经验写进 `AGENTS.md`，或者补一组性能基准测试，不就结了吗？

事情偏偏没这么简单。先说 `AGENTS.md`，稍微深度用过编码智能体的人都知道，这类写在提示词里的软约束，本质上全看模型当下的心情，时灵时不灵。文档一旦攒到几百行，模型在复杂上下文里照样会选择性失忆，该忽略还是忽略。更要命的是「事后诸葛亮」的困境：性能测试当然管用，可你之所以想到要给某个函数加基准测试，往往是因为系统在某次高峰期真的吃过亏，才事后补上。面对一个全新的仓库、全新的业务模块，在真正出事故之前，谁能提前预知系统里需要埋下哪几百道护栏？

这正是不少经验丰富的工程师坚持「审还是得审」的理由。靠老手扫一眼，运气好确实能提前拦下这种坑。

可把这件事反过来想一想，恰恰暴露了人工审查最脆弱的地方。那类热路径里的性能暗雷，真的是靠规范的 code review 流程稳稳挡下来的吗？现实往往很骨感：并不是每个评审者脑子里都时刻记着全站每条接口到底有多大流量。一个看似无害的正则编译或者重复解析，混在几十个文件的 diff 里顺手就滑过去了；偶有资深同事凭直觉拦下一处，靠的多半也是个人经验和凑巧碰上，而不是流程本身有多可靠。

**把系统的生死寄托在某位老专家恰好状态在线、又恰好熟悉这条链路的流量规模，这不叫工程保障，这叫撞大运。**

一个连资深工程师都只能靠碰运气才能抓出来的缺陷，指望强行保留全员 code review 来兜底，多半只是图个心理安慰，实际拦不住多少事。代码里的缺陷，无论是人写的还是智能体写的，从来都躲不掉。真正把我们卡死的，其实是一种潜意识里的执念：总觉得只要在合入主干之前把关够严，就能把所有未知的隐患提前消灭在萌芽里。

可现实世界里的复杂系统，从来不吃「事前全知」这一套。

## 二、不看代码，心里没底

技术盲区之外，另一个反问其实更让人纠结：责权分离。

智能体可以一晚上提交几十个 PR，可以把十几个微服务重构一遍，但到了真出大事故的时候，系统瘫痪、客户投诉、业务停摆，最后站出来向老板解释、向用户道歉、给整个事故背锅的，依然是活生生的人。智能体不会丢饭碗，也不会半夜三点盯着报警群血压飙升。

活是机器干的，锅却得人来背，这种错位自然让人心里发毛。以前代码是自己一行行敲出来的，或者至少是自己逐行审过、在心里过了一遍执行路径的。线上真出了故障，哪怕现场一团糟，工程师心里好歹有张地图，大概知道哪几个模块爱出幺蛾子，查日志往哪翻，回滚会不会把数据库里的数据搞乱。

换到智能体大规模产出的代码库里，情况就变了味。面对一大片自己压根没细看过的代码，一旦撞上大型线上事故，比如前段时间业界闹得沸沸扬扬的某云办公套件大停摆，人站在控制台前会突然发现自己无从下手。不知道根因藏在哪一层，不敢轻易切回旧版本，拖来拖去，恢复时间被越拉越长。

更尴尬的局面发生在修复阶段。就算你把现场日志喂给智能体，让它十分钟内吐出一个修复补丁，人看着屏幕上的 diff，心里还是虚的。因为你对周围几万行代码压根不熟，根本没有底气签字确认这个补丁真的修掉了根因，而不是在慌乱中又惹出一个更大的次生灾害。

这种「心里没底」的感受，我非常理解，也绝不觉得是矫情。机器干活的速度早就甩开人脑理解的带宽几条街，可最后的责任依然压在人肩上，人的底气到底该往哪儿找？

过去四十年，我们习惯把「底气」和「读过每一行源码」画上等号。可稍微跳出来看一眼其他工程领域，就会发现这种绑定其实很脆弱。民航机长要对一整架飞机几百条人命负责，他上飞机前会去逐行审阅飞控计算机的源代码吗？芯片架构师要为几千万美元的流片背锅，他会用肉眼去核对版图上几十亿个晶体管的连线吗？

他们当然不会。他们之所以敢握住操纵杆、敢签字流片，是因为整套工程体系给他们提供了比「肉眼通读」硬得多的底气：明确的边界隔离、冗余备份、靠谱的仪表盘，以及出事时能把后果锁死在局部的安全机制。

软件工程之所以一直靠「我读过代码」来给自己壮胆，说白了是因为在很长一段时间里，我们造出来的系统既缺乏清晰的物理隔离，又缺乏靠谱的线上护栏，只好靠人脑充当最后一块防弹衣。**当代码规模和变更速率翻了十倍，靠人眼通读换来的安全感早就靠不住了，继续硬逼着人去读更多 diff，找不回底气，只会制造更深的麻木。**

## 三、有些代码本就没法审

再往深里想一层，还有个更绕不开的现实：就算我们咬着牙把 code review 死守下来，未来软件系统里很大一块核心逻辑，压根就不是能「审」的东西。

看看今天的软件系统都在往哪儿长吧。以前我们写的程序，几乎百分之百是确定性的规则代码，输入什么、走哪条 `if-else` 分支、输出什么，白纸黑字写在文件里，人只要耐着性子，总能顺着调用栈一行行看懂。

但这个比例正在肉眼可见地剧烈倾斜。推荐排序、风控拦截、内容审核、客服路由、意图识别，越来越多原本靠规则堆出来的关键路径，正在被深度神经网络和大语言模型接管。今天一个典型业务系统里，纯规则代码和神经网络组件的占比大概还在九比一；往后看几年，这个比例很可能会滑向六比四。而剩下那六成确定性代码里，绝大部分又是由编码智能体生成的。

面对那四成深度神经网络，你怎么 code review？去逐行审阅几百亿个浮点权重参数吗？去给反向传播算出来的注意力矩阵提修改意见吗？显然是天方夜谭。

可这些黑箱一片、压根没法逐行讲清楚道理的神经网络，今天照样稳稳跑在支付风控、广告竞价、自动驾驶和医疗影像的生产环境里。它们靠什么活下来的？靠的是事前用影子流量做对比评测，靠构造刁钻样本、按人群分片测试去主动找茬，靠运行时的护栏与置信度阈值把离谱输出拦下来，更靠上线后全天候的数据监控、异常告警和秒级熔断回滚。

退回到第一性原理，事情一下子就清楚了。

**我们要的终极目标，始终是把任何未知缺陷的爆炸半径压到可控范围，同时把发现和修复的闭环缩到最短。**

无论出问题的是人类手写逻辑、智能体代码，还是黑箱神经网络，它们在线上惹出来的祸，模样其实都差不多：延迟飙升、错误率抬头、账单失控、数据写脏。既然系统里越来越大的一块核心组件天生没法审，整个软件工程的质量底座就得彻底转向：放弃「事前全靠人眼审透」的幻想，老老实实默认缺陷必然逃逸，靠架构隔离和线上闭环来兜底。

顺着这条线往下推，就会明白为什么未来要动手术的不止是 code review，连传统 CI 都要从底向上重做。传统 CI 的底子是静态世界里的「一次性准入考试」：代码合入前跑一遍固定的单测和构建，过了就万事大吉，后面的事交给运维。可在高频迭代加上概率组件的新世界里，真正的验证不可能在合并那一刻结束。它得是一套贯穿事前约束、事中隔离、事后持续巡检的完整防线。

## 四、学习传统工厂

光讲道理不管用，落到每天要交付产品的工程团队手里，想把爆炸半径真正压下来，具体该怎么干？结合我这段时间的实战和琢磨，至少得做好四件事。


第一件，是动笔之前先把笼子扎紧，别指望靠提示词里的软规矩管住智能体。

前面提到，把注意事项写进 `AGENTS.md` 很容易被模型忽略。既然软话管不住手脚，那就干脆从工具链和语言层面把路堵死。把智能体能使用的语言特性收缩到一个严格的子集，把那些容易暗藏副作用的动态特性禁掉；把项目允许引入的第三方库锁定在审查过的供应链白名单里，不让智能体图省事随手拉进来一堆来历不明的依赖。在此之上，再配上一套严密的本地测试套件和静态检查，把架构边界、类型约束和热路径禁忌，尽量做成机器几毫秒就能报错的硬规则。

这里藏着一个很实在的工程取舍：人的精力有限，与其天天跟在智能体屁股后面擦地板，不如把精力集中在打造这座「笼子」本身。笼子的栅栏越密、越确定，智能体在里面撒欢翻车的概率就越低。

事前拦不住的，就得在线上安一双全天候盯着数据和账单的眼睛。

前面聊到热路径里反复编译正则、重复解析配置的坑，为什么静态审查防不住？因为很多性能退化和资源浪费，是在几十个应用不断叠加新特性、真实流量形态悄悄变化之后才冒出来的。与其指望谁在合并前慧眼识珠，不如直接把优化这件事变成一条持续运转的后台流水线。

我自己现在就在这么干：每天定时把 AWS 的 CUR2 账单明细和运行指标喂给专门的巡检智能体，给它定下清晰的目标，去盯紧每一笔异常花销和性能波动，挖空心思找优化空间。跑了一段时间，效果比预想的还要惊喜。它顺着账单和指标，帮我揪出了好几个不同应用里藏得极深的毛病：有的服务触发了不必要的 CloudFront 缓存失效，有的在 KVS 上产生了离谱的读放大，还有 DynamoDB 的无效写入和 S3 的冗余读写。

仔细想想，这些跨模块、跨服务的性能与成本问题，哪怕找十个资深工程师坐在一起审 PR，十有八九也看不出来。因为单独看每一个 PR，逻辑都合情合理，只有把它们放进真实流量和实打实的云账单里，异常才会像黑夜里的探照灯一样亮出来。只要这双眼睛每天盯着指标，一旦发现延迟飘了或者账单翘尾了，顺藤摸瓜就能把热路径里的隐患挖出来，顺手再补上一条确定性的回归基准测试。

再往流程里看，软件团队其实该老老实实向现代工厂借几招。

软件行业干了几十年，总喜欢把自己当成一门充满灵感的艺术，遇到质量管理却还停留在手工作坊的思路上。其实汽车厂、芯片厂早就把「高吞吐下的质量控制」玩明白了，人家可从来不靠质检员把流水线上的每一颗螺丝钉拿在手里盘一遍。

工厂里有三条朴素又管用的老规矩，搬进智能体时代的研发体系正合适。其一是统计抽检：既然全量审查已经走不通，资深工程师就退一步当质检员，按 N-sigma 的标准在关键链路里定期抽检。抽检的目的很明确，就是持续校准整条流水线的健康度，及时察觉智能体最近有没有出现系统性的偷懒或漂移。

其二是「拉绳停线」。丰田生产方式里最著名的安灯系统，只要发现产线出了严重品质异常，工人有权立刻拉绳停机。放到多智能体协作里，一旦线上出了事故，别让其他智能体继续热火朝天地往主干合代码，先按影响范围停掉相关智能体手头的活，稳住现场、锁住状态。

其三是「阳光下的蟑螂法则」。家里厨房只要看见一只蟑螂，墙角缝里肯定藏着一窝。线上抓到一个热路径 CPU 空转或者权限绕过的 bug，绝不能让智能体打个单点补丁就草草收兵。停机整顿的真正价值，在于借这只蟑螂把整个代码库里同类的写法全扫一遍，然后把教训沉淀成一条永不失效的编译器规则、Linter 检查或者性能回归测试。这样一来，每一次线上交的学费，都会把系统的底盘垫高一截，免得过阵子在同一块石头上再摔一次。

最后，把神经网络那套在线上保命的法子，原封不动地铺到所有代码变更上。

在真正切入生产流量之前，让新版本先接一份镜像流量跑在影子模式里，把输出差异、延迟分布和内存占用跟线上老版本逐笔比对。正式发布时，严格按小比例灰度放量，配齐运行时的限流、降级与熔断开关；一旦关键指标越线，系统自动在几十秒内无损切回上一版。把这套机制做成默认底座之后，PR 合并就不再是一场赌上全站生死的走钢丝，它变成了一次随时可以撤回的可控实验。

## 五、告别手工作坊的执念

绕了一大圈，再回头看那个最戳心的问题：如果不再逐行审阅智能体写的代码，人作为最终背锅者，底气到底从哪来？

事故发生时人之所以慌，根源在于系统像一团剪不断理还乱的毛线球：牵一发而动全身，回滚怕丢数据，止血怕误伤正常业务，修完又没有手段验证。

当你把防线真正建在架构隔离、硬规则约束、影子流量对比、持续巡检和秒级回滚上时，人的角色和底气都会跟着换一副模样。你不需要知道某个微服务里那三万行胶水代码具体写了什么魔法。你只要确信底座已经把它的权限边界和资源配额死死锁住，就算彻底发疯也炸不出这个隔间。线上只要指标越线，监控和熔断几分钟内就能把它切回上一版。哪怕需要智能体紧急出补丁，后面还有镜像流量和确定性验证集替你把关，用不着靠肉眼硬猜。

**新时代工程师的底气，不再来自「我把所有代码都看过了」的幻觉，它来自你亲手设计并验证过的风险控制机制。**

当然，这绝不意味着明天早上所有团队就该一刀切地把 GitHub 上的 Approve 按钮砸掉。老系统债台高筑、测试覆盖稀烂、发一次版要靠人工祈祷的团队，在把自动回滚、监控闭环和隔离边界补齐之前，贸然撤掉人工审查无异于闭着眼睛飙车。新体系的演进注定是分层的：从零起步的新项目和 AI 原生团队，可以直接把交付流水线彻底重造；包袱沉重的老公司，则得花上几年工夫，一边把线上护栏和确定性验证补齐，一边把人从繁琐的日常 diff 里一点点解放出来。

软件工程走到今天，正在经历一场迟到了几十年的工业革命。过去我们习惯把自己当成手艺精湛的铁匠，每一寸铁皮都要亲手敲打、亲眼端详才敢出炉。面对智能体带来的百倍产能，以及越来越没法逐行解释的神经网络组件，铁匠铺的质检法子已经走到了尽头。

放下对每一行源代码的占有欲，转而去划边界、校仪表、控住爆炸半径，工程师并没有退场，只是终于从手工作坊跨进了真正的系统工程。就像《庄子》里那位解牛多年的庖丁，早年盯着满眼牛骨筋肉生怕下错刀，练到火候之后，便不再靠肉眼死磕每一寸皮肉，而是顺着系统的结构缝隙游刃有余：

> 以神遇而不以目视，官知止而神欲行。（《庄子·养生主》）
