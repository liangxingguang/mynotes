# 复杂度归谁：Pi 与 DSH 把 Agent 带向了两种未来

今天的 Coding Agent 有一种熟悉的膨胀路径：先加入文件工具，再加入终端、计划模式、任务列表、Subagent、MCP、记忆、权限审批和后台任务。每一项功能单独看都合理，叠在一起却会产生新的问题——上下文越来越重，执行路径越来越长，用户也越来越难回答一个基本问题：

**Agent 此刻为什么这样做？**

Pi 与 DeepSeek Harness（DSH）都试图解决这个问题，却给出了方向相反的答案。

Pi 选择压低系统默认承担的责任，把复杂度留给开发者按需添加；DSH 则把复杂系统拆成可组合、可卸载的模块，希望运行时也能参与能力配置。两者真正争论的并非功能多少，而是一个更根本的问题：

**复杂度应该在什么时候进入系统，又该由谁决定它是否存在？**

### Pi：让复杂度先证明自己有必要存在

Pi 默认只向模型提供 `read`、`write`、`edit` 和 `bash` 四个工具。它明确不把 MCP、Subagent、Plan Mode、权限弹窗、内置待办和后台 Bash 纳入默认产品，而是允许用户通过 TypeScript Extensions、Skills、Prompt Templates 与第三方包自行添加。[Pi 的项目说明](https://github.com/praxstack/pi-mono/blob/main/packages/coding-agent/README.md)对此表达得相当直接：核心保持克制，工作流由使用者塑造。

这种设计看似只是功能精简，背后其实有一套完整的复杂度观。

任何内置能力都会产生至少三种成本：

1. **上下文成本**：模型必须理解更多工具定义、状态和规则；
2. **决策成本**：Agent 多出新的行动路径，也多出新的误用方式；
3. **维护成本**：开发者需要处理兼容性、权限边界与异常状态。

因此，Pi 对新功能采取的是"举证责任倒置"：一项能力不能因为"可能有用"就进入核心，它必须先证明自己值得让所有用户长期承担成本。

这也解释了 Pi 为什么强调文件、终端和可观察性。计划可以写进文件，多 Agent 可以通过外部进程组织，权限隔离可以交给容器。它优先使用用户已经理解的操作系统原语，而不是继续制造 Agent 专属抽象。

这条路线的优势十分现实：执行过程容易追踪，故障边界相对清晰，开发者能够直接看到系统究竟做了什么。尤其在个人工具和中小型项目中，少一层状态机，往往就少一类难以复现的错误。

Pi 的核心信念可以概括为：

**缺失的功能可以稍后补上，失控的复杂度却很难再拿掉。**

### DSH：让复杂度成为可撤销的结构

DSH 接受了另一项前提：复杂能力不会因为核心拒绝容纳就自动消失。只要用户需要模型切换、权限控制、持久会话、并行 Agent 或动态工具，这些机制迟早会出现在外围脚本、胶水代码和第三方服务里。

问题随之发生变化：与其消灭复杂度，不如让复杂度获得清晰边界。

DSH 基于 Cordis 构建，模型适配器、工具注册表、会话日志乃至 Agent Loop 都通过插件组合。其[架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)强调，各项注册是可卸载的副作用，系统能力可以随插件装载和卸载而变化。Agent 接口也刻意不依赖某一种具体循环实现，使调度逻辑本身可以被替换。[相关说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent/README.md)显示，Subagent 等能力同样被放在核心接口之外，由独立 Provider 负责。

这里的关键机制是**可逆组合**。

传统大而全工具的问题在于，一旦某项能力写进主流程，其他模块便逐渐依赖它，最后很难拆除。DSH 尝试让模型、工具、沙箱、会话与调度通过明确接口连接，使一项能力既能加入，也能退出。

从这个角度看，DSH 的目标并非制造一个永远庞大的 Agent，而是让 Agent 的形态可以随着任务改变。代码审查、市场研究和自动化运维需要的权限、工具与循环方式并不相同。若底层组件能够按任务组合，同一个 Harness 就可以承载多种 Agent，而不必为每种场景重新造一套系统。

### 分歧的核心：设计时控制与运行时控制

Pi 与 DSH 最深的差异，落在控制权进入系统的时点。

Pi 更信任设计时的显式选择。开发者编写扩展、安装包、启动进程并决定隔离方式；Agent 在这套边界内完成任务。即使 Agent 可以帮助生成扩展代码，能力是否进入运行环境，通常仍然经过用户可见的安装或加载过程。

DSH 则试图让一部分配置权进入运行时。官方的 `tool-cordis` 扩展允许 Agent 检查当前 Cordis 运行环境，在沙箱中定义工具或服务，并临时挂载到当前进程。[官方文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/extensions/tool-cordis/README.md)也明确写出了现阶段的边界：这些定义只存在于进程内，DSH 重启后会消失，也不会自动写入项目配置。

这一能力很容易被描述为"自我进化"，但更准确的名称应当是**运行时自我改装**。

进化意味着经验能够跨任务保留，失败会影响下一轮选择，有用能力经过验证后能够稳定沉淀。当前的临时插件主要完成了其中第一步：发现缺口后生成并挂载新能力。它尚未自动解决版本管理、长期持久化、回归测试、权限审计和能力淘汰。

换句话说，DSH 打开了一扇门，但门后的治理制度仍在建设。

### 极简与模块化并不互相替代

Pi 最强的反对意见是：很多所谓模块化系统，只是把一个复杂核心拆成许多复杂包。插件数量增加后，依赖顺序、版本冲突、隐式事件和生命周期管理依然可能形成新的"分布式核心"。此时，架构图虽然漂亮，理解系统的成本却没有真正下降。

DSH 对 Pi 的反驳同样有力：外围复杂度也是真实复杂度。把 Subagent、审批与调度交给脚本，不会让它们消失，只会让它们缺少统一接口、状态记录和生命周期管理。当系统走向多人协作、长期运行和多种 Agent 共存时，极简核心可能把维护成本转移给每一个集成者。

因此，两条路线各有适用范围。

Pi 更适合能力边界稳定、开发者深度参与、可观察性优先的场景。DSH 更适合能力组合频繁变化、多个运行环境并存、需要统一治理的系统。前者优化的是"单个 Agent 如何保持清醒"，后者优化的是"许多不同 Agent 如何共享一套基础设施"。

### 自我扩展真正缺少的是宪法

我的判断是，DSH 的长期想象空间确实更大，但风险也更容易被"自进化"这个词遮蔽。

当 Agent 可以生成新工具时，能力增长速度会快于人工开发；与此同时，攻击面、状态空间和故障组合也会同步增长。一个能够修改自身运行环境的 Agent，至少需要回答四个问题：

* 新能力可以访问哪些资源？
* 由谁验证它确实解决了原问题？
* 出错后能否立即回滚？
* 哪些临时能力有资格成为长期能力？

如果这些问题没有制度化答案，自我扩展只会把插件系统变成自动生成的技术债。Agent 每解决一次局部问题，都可能给未来运行增加一个难以察觉的依赖。

所以，DSH 下一阶段最重要的指标不应是"Agent 又能造出多少工具"，而应是新能力能否经过沙箱试验、权限收缩、测试验证、效果评估和人工确认，再进入持久配置。

真正成熟的自进化系统，需要的首先是一部宪法。

### 结语

Pi 与 DSH 展示了两种都值得尊重的工程理性。

Pi 认为，默认能力越少，行为越容易理解，开发者也越能保有最终控制权。DSH 认为，真实需求终会带来复杂度，关键在于把它拆成可替换、可撤销、可治理的结构。

前者要求每一项复杂度先证明自己的价值；后者要求每一项复杂度都能被隔离和撤回。

我的判断更接近这样一条组合原则：**用 Pi 的标准决定什么值得进入系统，用 DSH 的结构管理已经进入系统的东西。**

未来真正强大的 Agent Harness，可能既不会拥有一个不断膨胀的固定核心，也不会把所有集成责任留给人类。它应当允许 Agent 形成新能力，同时保留清晰的边界、记录、验证与撤销权。

能力可以生长，控制权不能随之蒸发。
