Agent 的执行循环可以很短，但运行时的职责不能都塞进一个循环。

模型提出下一步，工具产生实际结果，调度器推进任务，核验器检查产物。它们共同处理一项工作，却不应拥有相同的状态修改权。**Harness 的设计，首先要明确这些模块之间的边界：谁保存事实，谁提交状态，谁决定继续或结束。**

本文从整体架构展开，分析模块划分、状态模型与执行时序，再通过中断恢复和产物核验的实测，检验这些边界是否成立。

## 01问题定义与设计目标

### 1.1 模型回合与业务任务的边界

模型 API 返回的是一轮推理结果，可能是一段文字，也可能是一组工具调用。业务任务的结束条件则由用户要求决定，例如完成对账、列出异常、生成说明，并提供可打开的文件。一个任务往往包含多轮推理，工具产生的结果又可能保存在模型会话之外。

这里存在两种相互独立的失败。模型可以顺利结束回复，但文件中的公式没有缓存值，业务结果不合格；工具也可以完成文件写入，但后续请求中断，执行记录没有正常收尾。它们需要不同的修复动作。

如果把这两种情况都压成“失败”，恢复时只能从头重跑，或者让模型根据聊天历史猜测进度。如果统一写成“完成”，则可能交付不合格成果。增加提示词并不能恢复数据库没有保存的事实。

本文所说的 Harness，是组织模型与工具执行、管理任务进度并处理结束条件的运行时。模型仍负责推理和选择动作，工具仍负责实际操作；Harness 负责记录这些动作属于哪项工作、依据哪个版本，以及结果是否允许进入后续流程。

图1将产品交互与执行内核分开。桌面窗口接收请求、展示进度；模型适配器处理推理协议；文件和业务连接器完成实际操作。知识库、记忆和 Skills 为执行提供资料与方法，但不承担本次任务的状态提交。

### 1.2 本文要检验的设计判断

这套架构围绕三个判断展开。第一，运行时只有保留任务、执行尝试和操作的不同身份，才有条件识别旧回包与重复动作。第二，执行状态与成果检查分开后，恢复可以处理局部缺口，不必丢弃全部进度。第三，核验需要绑定原始要求和具体产物，否则增加检查轮数也可能扩大错误。

这些判断分别对应可观察的行为：过期派发不能提交当前状态；恢复不能改写已经确认的文件；返修不能把一份文档的要求转移给另一份文档。后文用提交规则解释前两项机制，用工程测试分析成果保留和核验的实际表现。

本文不重复前几篇的上下文压缩、记忆整理与模型路由。它们是运行时的重要输入，但这里关注的是：**输入确定之后，系统如何推进、暂停、核对和交付一项工作。**

## 02从执行循环到任务运行时

### 2.1 执行循环与交付条件

OpenAI 在《Unrolling the Codex agent loop》中，将用户输入、模型推理、工具执行与结果回送组织成循环；一个用户回合可以包含多次模型与工具交互，实际成果也可能是环境中的代码文件，而非最终回复。

这一设计提供了本文执行路径的参照。不过，回合结束仍需映射到具体产品的交付条件。办公任务中的“表格可用”“全部异常已列出”“用户可以下载”，需要应用定义检查规则，不能仅从模型停止调用工具推导出来。

### 2.2 跨会话进度与产物记录

Anthropic 的长任务实践用初始化环境、进度文件和增量工作组织跨会话接续，并指出压缩上下文本身不足以避免半成品和过早宣布完成。 后续应用开发 Harness 又将规划、生成与评估分开，让评估者实际检查运行中的应用，同时讨论评估标准与校准问题。

对本文项目，这两项工作分别提供了连续执行和独立检查的参考。迁移到文件任务时，还需把进度关联到具体文件、版本和操作记录。仅有一份文字进度报告，不足以判断远端提交是否发生，也不足以判断当前文件是否仍是当时检查过的版本。

### 2.3 检查点与外部操作

LangGraph 将线程内图状态的检查点与跨线程 Store 区分开；内存型检查点不会在进程重启后保留。 Pregel 执行源码维护检查点、任务准备和待处理写入等机制。 这些能力提供了恢复执行的基础，但外部操作回执、文件质量和业务批准仍需应用建模。

本项目围绕交付条件、产物归属和操作确认补充运行时机制，让执行循环取得推进任务所需的状态。

表1：执行能力与本项目的设计补充

| 执行能力 | 本项目的设计补充 |
| --- | --- |
| 模型与工具循环 | 声明交付物，分别检查文件与交付状态 |
| 跨会话接续与评估 | 将进度、要求和返修反馈绑定到具体产物 |
| 状态持久化与恢复 | 记录外部操作，按回执决定是否继续执行 |

这些机制沿用原有模型与工具循环，通过任务控制、操作记录和产物检查协作。下文按状态归属和调用顺序展开，说明每个模块接收什么、保存什么，以及哪些变化允许提交。

## 03系统架构与运行契约

### 3.1 执行路径和状态所有权

图2中间是执行路径：请求进入引擎，模型提出动作，执行器调用工具，结果返回循环，经过检查后交付。任务控制模块保存有效要求与进度，操作记录保存实际动作，产物记录保存文件及其检查结果。

![图2：执行路径、控制模块与证据存储](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)图2：执行路径、控制模块与证据存储

模型可以提出下一步，调度器可以派发工作，但状态变化需要经过相应模块的提交接口。工具执行器返回“文件写入成功”，只能提交这次写入的事实；它不能据此宣布整项对账完成。核验器指出缺少汇总表，也只能提交检查缺口，不能自行新增用户要求。

这种分工限制了状态修改的范围。每个模块接收有身份的输入，返回可解释的结果；上层依据结果决定是否继续。任务失败时，可以沿着提交链寻找缺失环节，而不用把模型回复、工具输出和界面提示混在一起解释。

当前实现中的部分职责仍共处一个引擎进程，甚至位于同一个较大的循环模块。图2表示逻辑边界，不表示已经拆成独立服务。桌面产品先隔离依赖和状态写入口，通常比立即引入多服务协调更容易验证。

### 3.2 一项工作为什么需要多种身份

会话、任务、执行尝试、外部操作和产物的生命周期不同。会话可能持续多天；一个工作目标可以拆出子任务；某个子任务超时后再次派发，目标没有变化，执行尝试却已经变化。仅有一个会话 ID，无法判断迟到的结果应该由谁接收。

![图3：会话、任务、派发、操作与产物的关联](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)图3：会话、任务、派发、操作与产物的关联

以下是便于分析的概念契约，不是项目私有接口的字段清单。一次派发至少要关联工作目标、有效要求版本、执行尝试、输入引用和产物要求。执行结果则要带回所属尝试、实际操作收据、成果引用以及停止原因。

假设执行尝试 A 超时，调度器已经派发 B。A 的回包稍后到达，如果只按任务编号更新状态，就可能覆盖 B 的进度。因此，结果提交需要同时检查活动状态和派发身份。检查失败时，记录拒绝原因，留下拒绝记录供排查，但不将该回包作为当前尝试的完成结果。

要求版本处理的是另一种竞争。用户在执行中更正了对账范围，旧计划不能凭“最后写入”覆盖新要求。运行时保留真实输入及来源，提交计划时检查相关要求或计划是否已变化；遇到冲突，让执行重新读取当前依据。

操作身份不能直接等同于尝试身份。同一次工作可能包含多次写入，恢复时也可能建立新的派发。已经发出的操作仍需沿用原记录查询状态；新产生的操作则需要新的位置，避免读取旧收据后误以为自己已经执行。

产物身份还要包含文件版本。相同路径可能被后续工具覆盖，路径相同不代表内容相同。内容哈希、检查时间和所属运行把一次检查限定到具体文件；文件变化后，旧检查结果不能直接作为新内容的验收结论。

### 3.3 本地状态提交与外部执行

一次正常调用从保存用户要求开始。运行时记录当前有效版本，执行循环准备本轮输入，模型返回工具请求，执行器完成操作并保存结果，循环再决定下一步。界面订阅这一过程中的事件，但不负责反向推断任务状态。

![图4：一次工具调用与状态提交的执行时序](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)图4：一次工具调用与状态提交的执行时序

已有任务状态模块在同一 SQLite 事务里保存当前状态、变更事件和版本快照。这样，一个已提交版本具有对应的状态与事件。若把三次写入分开，进程可能只保存了“已更新”的事件，却没有保存更新后的状态，恢复时便缺少一致的读取依据。

这项保证只覆盖本地事务。文件写入、远端请求与数据库提交之间仍有间隔。工具可能已经完成写入，而记录尚未来得及保存；远端也可能已经处理请求，而本地没有收到回执。

**数据库事务覆盖不了外部工具。** 因此，执行边界还要记录动作何时开始、是否发出、取得了什么回执。恢复时结合文件读回或远端查询，确认外部结果。单纯回滚本地状态，不能撤销已经发生的外部动作。

工具结果的完整记录与模型输入也应分开。模型可以读取摘要或截取片段，完整结果则保存为可回读引用。核验需要细节时沿引用查证；归档失败或只读到部分数据时，检查结果必须保留这一范围。

### 3.4 调度依赖与局部执行循环

任务图描述工作之间的先后关系，执行循环处理一项工作内部的动态步骤。两者可以同时存在。读取发票和读取付款可以并行，余额计算要等待两份输入，异常说明则依赖计算结果。

![图5：任务依赖图与工作进程内部的执行循环](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)图5：任务依赖图与工作进程内部的执行循环

调度器管理输入引用、依赖、派发与返回结果，不规定每次模型应该调用哪个工具。工作进程拿到一项范围明确的任务，在局部循环里处理表格格式、读取失败和计算步骤。规则明确的计算仍可直接用函数完成，无需另外派发一个 Agent。

拆分要有具体收益。独立输入适合并行，长时间等待批准适合单独保留依赖；频繁交换大量中间资料的两个步骤，拆到不同上下文可能增加信息损失与汇总成本。角色数量本身不是设计目标。

现有编排将执行完成与用户接受分开记录。工作进程完成并满足声明产物条件后，可以更新执行状态和下游就绪条件；需要人工批准的动作，应显式配置审批依赖，不能将普通上游完成解释为授权。

## 04一致性约束与中断恢复

### 4.1 用状态组合保留不同事实

一个“成功／失败”字段无法同时表达执行、外部操作和成果质量。本文将三类状态分别讨论：执行状态记录工作停在哪里，操作状态记录动作是否发生，产物核验记录成果满足了哪些条件。

![图6：执行状态、操作事实与产物核验分别记录](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)图6：执行状态、操作事实与产物核验分别记录

各模块分别维护状态，恢复入口做决定时再读取相关记录，无须穷举所有状态组合。例如，执行中断且文件已核对，可以补处理交付；请求超时且写入结果不明，则要查询或等待确认。

表2：状态组合与恢复动作

| 已知事实 | 对应处理 |
| --- | --- |
| 执行中断，声明文件已经可用 | 保留文件，检查剩余步骤 |
| 执行结束，产物未通过检查 | 限定范围返修或返回缺口 |
| 外部请求已发出，结果不明 | 查询回执，暂不重复写入 |
| 部分成果完成，仍在等用户 | 展示已有成果，保留等待状态 |

流式连接的结束另属传输层。`[DONE]` 或 token 用量只能说明流与计量情况，不能替代任务终态。后台消费者需要读取实际阶段、停止原因和错误事件，避免连接正常结束后直接把工作写成 completed。

已有事件契约将终态解析从 HTTP 路由中抽出，供后台和其他入口消费。前一次失败、后续合法接续完成，应按后续结果解释当前运行；后续又发生错误，也不能继续沿用此前的成功信号。统一解析规则可以减少入口之间的状态分歧。

### 4.2 恢复决策的顺序

恢复入口首先读取持久记录，区分界面断连和引擎中断。如果原执行仍在推进，只需重新订阅；工作已经结束，则读回结果；确认需要继续时，才进入新的执行尝试。

![图7：恢复决策中的读回、确认与继续执行](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)图7：恢复决策中的读回、确认与继续执行

接续时恢复原工作目录、有效要求、已完成事实和操作记录。方法内容或输入版本已经变化时，应重新建立相应依据，不能把旧试跑结论直接带入。恢复消息属于系统提供的运行资料，也不能冒充用户的新要求。

对于结果不明的外部写入，查询能力决定恢复方式。支持按业务单号查询时，先查最终状态；支持幂等键时，按接口约定复用；没有这些能力时，保留未知状态，取得确认后再处理。更换模型不会增加业务授权，也不会消除不确定的外部结果。

停止同样不是回滚。用户点击停止后，运行时可以阻止继续派发，但已经在外部执行的请求仍可能返回。晚到结果需要检查所属尝试和当前状态，已发生的操作事实则应保留。直接清空记录，会让下一次执行失去去重和确认的依据。

### 4.3 为什么恢复测试要检查旧文件

仅检查最后生成的文件，无法区分“接着完成”和“从头重做”。对于纯计算，两者可能只差耗时；对于发送、提交与付款，重复执行会产生不同业务结果。因此，恢复测试既检查新增结果，也检查此前已经完成的对象。

本文实验使用原草稿的字节内容和修改时间判断是否重写，同时核对运行身份、工作目录与后续文件。内容哈希相同但修改时间变化，仍可能表示模型重新写了一遍，不能算作保留原稿。

这种检查也有范围：文件未变化只能证明该文件被保留，不能证明远端没有重复提交。外部操作需要自己的回执和查询证据。将两类证据分别归档，才能定位恢复机制究竟覆盖了什么。

## 05产物核验与独立交付

### 5.1 核验输入不能只来自执行模型

执行模型给出的任务概括可能遗漏要求。核验如果再以这份概括为准，执行与检查会共享同一个错误。本文采用原始有效要求、指定产物的可读取事实和检查问题共同组成核验输入。

![图8：原始要求、文件事实与限定范围返修](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)图8：原始要求、文件事实与限定范围返修

确定性读取负责文件结构与明确数据，例如表头、行数、公式、缓存值及 Word 表格；模型核验负责较难用固定规则描述的对应关系和文字含义。两类检查分工后，模型不用凭文件名推测内容，程序也不必把语义判断全部硬编码成规则。

已有 Office 事实读取复用解析库，以只读方式提取有限内容，不启动 Office、不重算、不改写文件。文件过大、依赖缺失或读取异常时返回未知。检查只覆盖被读取的范围，未知结果不能自动归为通过。

一条返修反馈应关联具体要求、具体产物及检查证据。例如说明文档缺少汇总表，修复目标就是说明文档；不能把反馈概括成“增加汇总信息”，再让执行模型自行挑选文件。修改后既要检查缺口，也要检查原先已经满足的条件。

限定返修对象，可以收窄判断错误影响的范围。核验器本身仍会漏判、误判或没有结论，因此需要正确文件和错误文件组成的对照样本，不能只用成功生成的任务评价它。

### 5.2 核验预算属于执行架构

核验输出需要完整形成才能消费。若输出额度耗尽，只留下推理片段而没有结论，上层应记录核验未完成；不能将空结果解释为默认通过，也不应把它包装成业务失败的具体原因。

执行预算因此要覆盖探索、工具执行、核验与收尾。只为模型主循环设置总轮数，而没有给检查和最终结算留下空间，可能出现文件已生成、核验尚未结束就耗尽请求额度的情况。

增加核验额度会增加资源消耗，也不能自动修正判据错误。预算不足和跨文件误修是两个问题：前者影响有没有结论，后者影响结论是否正确、修改对象是否准确。后文分别分析，不把它们合并成一次“核验能力提升”。

### 5.3 文件入口独立于最终回复

模型的最后一段回复可以解释结果，但文件发现不必完全依赖这段文字。运行时已有声明产物记录，可以检查允许目录内的文件并构造可打开入口。末尾调用失败时，用户仍有机会取得已经生成的成果。

![图9：入口适配、共享运行时与成果读回](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)图9：入口适配、共享运行时与成果读回

收集范围只限本次声明产物，不能扫描整个工作区。目录里可能有旧文件、上传资料和临时结果；把它们混进交付列表，会造成来源误认。模型或工作进程自报的成果入口，也需要经过实际文件检查。

交付入口记录可用文件，原任务则继续保留自己的失败或待确认状态。文件存在、非空、哈希可读，说明文件可取得；内容是否正确需要另行核验。开头的回放实验之所以能区分二者，是因为文件内容此前已有独立检查，而补链接只做只读处理。

桌面、后台和渠道入口应共用这些语义。接入层处理认证、请求格式和展示，运行时负责终态解释与成果记录。更换界面或增加入口时，就不必再复制一套“什么算完成”的判断逻辑。

## 06实验设计与评价方法

本节整理既有工程测试，不是本次写作新跑的基准。业务输入为合成资料，文件、数据库与隔离引擎实际运行；部分故障通过 HTTP 替身或受控阻塞注入。不同实验的源码版本和运行条件不同，结果按组分析。

### 6.1 四组实验与检查对象

E1 检查停止、重启和显式继续后的运行身份及文件保留。E2 检查多份关联产物的核验、返修和交付。E3 固定文件级核验输入，观察输出预算调整后的结论。E4 使用配对基础任务检查新旧版本的完成结果、调用与耗时。

表3：实验分组与观察项

| 实验 | 主要观察项 |
| --- | --- |
| E1 生命周期恢复 | 同一运行与目录、原稿字节及修改时间、后续文件 |
| E2 多产物任务 | 文件内容、返修对象、任务终态、文件入口 |
| E3 核验输出控制 | 是否截断、是否有结论、正反例判断 |
| E4 基础任务对照 | 产物与终态通过数、调用数、端到端耗时 |

这些实验没有汇总成一个分数。生命周期通过可能伴随业务内容错误；文件内容通过，也可能缺少交付入口。分别报告，才能判断改进应落在恢复、核验还是交付模块。

### 6.2 多产物任务的验收条件

E2 输入为 24 张发票、38 笔付款和 14 项异常，要求输出对账工作簿、异常 CSV 与 Word 说明。每份产物都有明确要求，模型生成的“已完成”不参与最终评分。

工作簿首表须保留 24 行发票明细、指定字段与余额公式，并具有正确缓存值。CSV 须精确列出 14 项异常。Word 需包含异常编号与汇总表，三项金额分别是未付款 4,998、超付 150、未匹配 200；资料净额为 4,848。

这组输入用来制造跨产物约束：同一业务事实会出现在多个文件里，但文件结构并不相同。实验既检查数据是否一致，也检查某一文件的要求有没有被错误施加到另一文件。

正式执行前，测试准备正确文件，以及公式缓存、CSV 或 Word 结构存在错误的反例，检查独立验证器能否区分。最终结果直接读取文件，并同时检查持久化终态和文件入口。

### 6.3 对照条件与归因

E4 的配对任务使用相同输入与模型条件，但模型执行轨迹仍可能不同。耗时包含执行与核验；请求截断、重试和模型响应波动都会影响结果。比较时先看每个任务的轨迹，再解释汇总数值。

E3 同时改变输出额度和截止时间，因此只用于检验调整后的配置是否能形成正确结论，不能单独归因于某一个参数。E2 的后续修正又使用了不同候选提交，不能与前面的基础任务成绩拼成一个统一版本的表现。

## 07实验结果与机制分析

### 7.1 E1：接续执行保留了什么

实测记录生命周期测试通过真实 HTTP 入口启动、取消和恢复，实际重启隔离引擎。第一阶段用受控模型响应建立草稿，后续接续使用真实模型：恢复到同一运行与工作目录，先读原稿，再生成后续文件。原稿字节与修改时间均未变化，最终文件内容也经独立读回。

这个结果支持的是固定测试路径中的“保留已完成工作并继续”。它比只检查最后有没有文件更严格，因为重新生成相同内容也会被修改时间检查发现。恢复由显式操作触发，不意味着重启后自动执行工具。

早期失败也解释了身份设计的必要性。恢复后的操作序号曾从零开始，导致第二份文件与已完成操作的收据冲突；另一次接续则重写了原本正确的草稿。前一问题需要从已有操作位置继续，后一问题需要执行阶段先读回成果并限制修改范围。

因此，“能加载检查点”不足以说明恢复完成。身份、操作位置与文件使用方式必须共同验证。对于任意远端业务写入，还需要该系统的回执与幂等能力；文件测试不能代替外部事务测试。

### 7.2 E2：核验反馈把要求转移到了错误文件

多产物任务的一次候选运行，在第 15 次模型请求的核验环节，把 Word 汇总表要求套到 Excel 上。执行模型随后插入 Summary 首表，破坏了工作簿“首表为发票明细”的原要求。错误发生在调用上限之前，不能只归结为最后额度耗尽。

旧版的另一次运行则出现相反问题：Excel 没有公式缓存，Word 缺少汇总表，内部任务仍标成 completed；独立检查判为失败。这里既有核验漏判，也有执行状态与内容质量不一致。

两种失败共同指向核验输入和反馈契约。原始要求要按产物归属组织，文件事实应独立读取；返修反馈要说明修改哪份文件、补什么缺口、哪些已满足条件需要保留。增加一个核验角色而不限制输入与反馈，不能排除误修。

修正过程中加入只读 Office 事实后，缺少公式缓存的情况能够作为明确证据送入核验并被拒绝，但跨文件要求转移仍出现。这说明文件事实读取改善了可观察性，却没有独自解决语义归属。两项机制需要分别检验，不能把一处有效当作整条返修链通过。

### 7.3 E2：产物合格却没有交付入口

另一模型的候选运行生成了三份内容合格的文件，但没有形成最终链接，任务停在 ready，最后受到请求上限影响。依靠最终回复提取链接的路径因此没有给用户提供完整交付。

实测记录对这些文件做只读回放后，新回执处理返回三个入口，上游模型调用为零，原文件与原任务数据库的哈希均未变化。原失败任务没有被修改成成功，执行模型也没有重新运行。

**这组结果验证了补交付入口可以与重新生成文件分离。** 对已有成果，运行时能够独立读回和展示；需要继续的部分仍由任务状态表达。这里的收益是避免为取得链接而重做已有文件，不是宣称整个复杂任务已经自动恢复成功。

另一个真实引擎进程测试，在写出 CSV 后由本地 HTTP 服务注入错误，再重启引擎。任务继续保留失败状态，文件入口和内容仍可读回，依赖任务没有启动。该测试检查失败交付路径，不属于供应商自然故障或完整产品真机验收。

### 7.4 E3：核验器没有结论与判断错误不同

文件级控制实验给核验器分别提供正确文件和错误文件。初始输出上限为 1,600 tokens，两次都以长度截断结束，结论为空；不能因为没有返回错误项就算作通过。

实测记录随后保留相同模型、消息与温度，将输出上限提高到 4,096 tokens，截止时间由 60 秒改为 120 秒，不运行执行模型。错误文件得到拒绝，指出 Word 缺表与 Excel 缓存为空；正确文件得到通过。两次均有完整结论，无截断。

这是一组两例的配置对照。它支持为核验保留足够输出和等待空间，也支持将“核验未完成”独立记录；它不提供大样本准确率，更没有验证修复意见能否被执行模型正确落实。

对架构而言，核验服务需要返回完成状态、判断结果和检查范围，而不能只提供一个 pass 布尔值。上层据此区分继续检查、限定返修与停止等待，避免把服务自身失败误用为业务结论。

### 7.5 E4：调用减少不等于任务更快

基础对照包括 Office、招聘和客服任务，分两轮执行。每个版本合计 12 项，旧版与候选均为 12/12 通过。这个结果提供了所选样本上的非退化观察，没有显示整体完成率提高。

表4：两轮基础任务的配对结果

| 轮次与指标 | 旧版 → 候选 |
| --- | --- |
| 第一轮，4 项通过数 | 4/4 → 4/4 |
| 第一轮，总模型调用 | 31 → 25 |
| 第一轮，总耗时 | 203.625 秒 → 220.163 秒 |
| 第二轮，8 项通过数 | 8/8 → 8/8 |
| 第二轮，总模型调用 | 52 → 53 |
| 第二轮，总耗时 | 368.196 秒 → 319.682 秒 |

第一轮调用减少而总耗时增加，第二轮调用略增而总耗时减少。两个指标并不单调对应，不能选择其中一轮就得出固定提速或节费结论。第一轮旧版还出现输出截断后恢复，这也影响耗时的可比性。

基础任务均通过，复杂多文件任务却暴露了误修和交付缺口，说明评测需要覆盖状态组合和跨产物约束。只增加同类简单题数量，难以发现“文件合格但未交付”这一类故障。

这批实验没有逐项关闭机制的消融对照。现有证据适合定位缺口、检查具体修正和建立回归样本，不能量化每个模块对整体成功率的独立贡献。

## 08Harness 与基础设施的架构边界

### 8.1 基础设施承载执行，Harness 定义工作规则

从部署架构看，Harness 依赖 Infra，但二者承担的职责不同。Infra 提供模型访问、身份与凭据、运行环境、数据连接、持久存储、日志和监控等基础能力；Harness 决定怎样使用这些能力推进任务，包括派发、等待、重试、恢复、核验和交付。

两层之间需要清楚的接口。存储保证记录能够保存和读回，Harness 定义记录代表什么；执行环境提供运行工具的能力，Harness 决定何时允许执行；日志记录发生过的事件，Harness 利用这些事件区分中断、未知结果与完成。

把数据库、队列和沙箱部署好，并不会自动得到业务恢复能力。数据库能读回一条操作记录，却不能替应用判断是否应该重发；沙箱能重新启动，也不代表先前的文件仍然存在。Harness 必须根据存储和执行环境的实际保证，定义恢复入口和检查条件。

Anthropic 在 Managed Agents 的工程设计中，将 Harness、会话记录与沙箱拆开，允许分别失败或替换。这种分离有直接的工程意义：执行实例可以重建，任务记录不必随之消失，工具也不必与推理循环部署在同一环境。具体业务如何验收，仍由应用定义。

选择托管服务或自行建设时，应逐项核对这些接口保证：记录保留多久，执行环境销毁后文件是否还在，重建实例如何找回任务，超时请求能否查询结果。接口保证不同，Harness 的恢复策略也要不同。最终交付给客户的是 Harness 与 Infra 共同运行的系统，但两层应能分别演进，不必把一次执行实例与任务的整个生命周期绑在一起。

### 8.2 长期积累来自业务规则与失败经验

采用现成模型的团队可以更换模型，但更换模型不会替客户确定一项工作的完成标准。哪些合同版本有效、什么操作需要审批、哪份报告可以交付、重复提交怎样处理，必须结合业务流程定义，并落实到执行与检查中。

**Harness 的长期价值，在于把业务经验变成下一次执行仍然有效的机制。** 对账中发现 Word 要求被套到 Excel，就要收紧产物与要求的关联，并保留跨文件误修反例；发现文件正确却没有入口，就要把交付读取从末尾回复中分离。改动必须进入运行路径，不能只记在复盘文档里。

因此，持续迭代不应只看提示词改了多少、接了多少工具。更有用的问题是：上次失败后，系统新增了什么检查？相同问题再次出现时能否识别？新规则会不会误伤原本正确的任务？这些问题把产品迭代与回归测试联系起来，也让项目经验能够复用。

这并不意味着 Harness 越复杂越好。模型能力变化后，为旧模型设计的补救逻辑可能失去必要性。Anthropic 的 Managed Agents 实践也记录了这种情况：某些上下文重置措施随着模型升级变成了多余负担。长期迭代既包括补机制，也包括通过对照删除无效机制。

对企业应用团队，本文更看重这条积累路径：业务要求进入运行契约，实际失败进入回归样本，验证有效的修正进入下一版。领域数据、工具质量和基础设施继续影响效果，Harness 则把这些投入组织成可检查的工作过程。

### 8.3 用异常路径检查模块边界

模块边界是否有效，可以沿异常路径检查：要求中途变化后，旧结果是否仍被接受；外部操作超时后，是否盲目重发；执行进程退出后，成果能否找回；核验误判后，是否改坏其他文件。这些问题分别指向版本提交、操作确认、持久化和返修范围，不能全交给执行循环里的一个异常处理分支。

本文测试中，基础任务的新旧版本都能通过，复杂任务仍出现跨文件误修和结果入口缺失。前者要求核验反馈绑定具体产物，后者要求结果读取能够独立于执行循环完成。测试结果由此指向不同的架构改动，而不是统一增加重试次数。

一张模块图还不足以说明这些边界成立。需要继续检查接口是否限制了状态写入、恢复是否沿用了已有操作记录、返修是否只修改指定产物。架构图中的分工，最终要在执行记录和回归测试里找到对应行为。

## 09设计取舍与适用范围

### 9.1 持久化粒度与恢复成本

保存完整轨迹有利于追溯，也会增加存储与读取成本。本文方案区分模型输入和事实记录：摘要服务下一轮推理，原始资料和工具结果通过引用保留，恢复与核验按需读取。对超大结果，完整性状态与读取范围同样重要。

检查点过粗，中断后要重新处理较多步骤；过细则增加写入和协调。任务要求更新、工具动作开始与结束、派发变化、产物检查等位置具有不同作用，不能只按固定时间间隔保存一份聊天快照。

持久化也不要求跨系统统一事务。本地状态、事件与快照可以共同提交；外部动作通过记录、查询和确认处理。在没有远端支持时保留未知状态，比作出无法兑现的自动恢复承诺更符合实际接口能力。

### 9.2 独立核验的收益与代价

独立核验可以发现执行模型遗漏的问题，但它会增加调用、等待和误判风险。E3 说明核验自身需要足够预算，E2 则说明有了结论也可能改错对象。两者共同要求核验具有可追溯输入和受限输出。

核验范围可以随任务风险变化。确定性表格字段可以先由程序读取，文字与业务解释交给模型分析；涉及外部写入或高影响决策时，还可能需要人工确认。没有必要把普通问答也强制送入完整文件验收流程。

返修次数应受预算和实际进展限制。重复返回同一缺口、文件却没有变化时，继续循环未必增加成功机会。停止时保留可用成果和未解决问题，使后续执行能够从具体缺口继续。

### 9.3 统一内核与入口差异

共享运行时不要求所有入口拥有相同权限或交互方式。桌面可以询问用户，后台可能只能保存等待事项；渠道可以展示链接，技能试跑可以展示运行记录。需要统一的是身份、状态解释、结果读取与停止语义。

迁移时可以先抽出共享终态解析和目录解析，再逐个替换入口的重复判断。当前部分后台代码仍依赖路由层，不宜把逻辑架构图理解为已经完成全部服务化。相同事件流经过不同入口后，应获得一致的运行结论，再检查各入口的有意差异。

## 10评测标准：怎样判断一次架构改动有效

同一批对账文件，内容检查通过，任务却可能停在收尾阶段。如果只统计“文件生成率”，这次执行就会被记成成功；如果只检查任务终态，又看不出已有成果是否还能使用。评测标准必须同时说明检查对象和判定依据。

NIST AI RMF 强调记录测量方法、适用条件与不确定性；Anthropic 的 Agent 评测指南区分任务、试验、评分器和环境最终状态；LangSmith 将固定数据集上的版本对照与上线后的监测分开。这些资料提供方法，不替具体业务规定及格线。以下是结合本文架构提出的验收规则，不是通用认证，也不代表前述实验已经覆盖全部规则。

### 10.1 固定输入、环境和成功条件

一个评测样本应包含原始要求、输入资料版本、初始环境、允许的操作、预期产物和判定程序。需要测试中断时，再声明故障发生的位置及恢复后允许执行的动作。不能等 Agent 给出结果后，才根据结果调整标准。

例如本文的多文件对账任务，成功条件包括工作簿首表与公式、异常 CSV、Word 汇总和文件入口。每项检查都绑定对应产物。路径、格式或精度要求应提前告诉执行系统，不能让评分器用隐藏要求判错。

比较 Harness 版本时，固定输入、模型配置、工具版本和调用预算，并记录实际环境。每次试验从独立的初始状态开始，避免上一次留下的文件让下一次“直接完成”。不同业务类别分别统计，不能用大量简单问答掩盖多文件任务的失败。

### 10.2 分项判定，不用总分掩盖关键错误

对文件处理与业务操作类任务，建议采用下表的判定结构。实际断言应随任务要求配置；没有外部写入的任务，不应虚构一项外部回执检查。

表5：Harness 评测对象与判定证据

| 检查对象 | 判定证据 |
| --- | --- |
| 状态与权限 | 派发身份、要求版本和授权记录匹配；过期结果不得覆盖当前状态 |
| 外部操作 | 通过回执或查询确认结果；未知结果不能直接计为成功 |
| 中断恢复 | 已确认成果保留；未获授权的重复写入未发生；从声明的恢复位置继续 |
| 产物正确性 | 读取实际文件或业务数据，核对必需字段、计算与跨文件一致性 |
| 任务结束 | 终态、停止原因、待处理事项与结果入口一致 |
| 效率 | 在相同质量要求下，统计端到端耗时、调用次数及实际成本 |

**任务成功率的分子，是全部必需条件通过的试验次数。** 分母是预先纳入该组评测的全部试验次数。超时、失败和无法判定都要列出，不能从分母里悄悄删掉。确属测试环境损坏的无效试验，应按事先约定的规则单列，说明原因并重跑。

恢复成功率则只统计进入指定故障场景的试验，成功条件须同时包括正确接续和原成果保留。耗时应从请求进入到结果可用计算，包含等待、重试与核验；报告中保留失败运行的耗时，避免只展示成功任务中较快的一部分。

模型执行有波动，同一个样本需要重复运行并保留每次结果。多次尝试中至少成功一次，与每次都成功，是两个问题。小样本先列通过数、总次数和失败分布；要声称稳定提升，还需足够样本及不确定性分析，不能把一次成功写成稳定能力。

### 10.3 评分器也需要验收

金额、行数、文件哈希和状态版本优先用程序检查；说明是否覆盖要求、解释是否符合资料，可用有明确评分规则的模型辅助判断，再由人工抽查校准。评分器应读取环境中的真实结果，不能只接受执行 Agent 对自己的评价。

核验器至少需要一组已确认合格的产物和一组带有已知缺陷的产物。分别记录漏检率和误拒率：漏检率是错误产物被放行的数量除以错误产物总数；误拒率是合格产物被判失败的数量除以合格产物总数。缺少某类样本时，对应指标不可计算，不能填零。

评分器超时、输出截断或缺少依据，应单列为无法判定，不混入合格结论。调整评分提示、输出预算或核验模型后，也要重跑这组校准样本。本文 E3 的正反例检查验证了特定配置能够给出正确结论，但还不足以估计核验器在各种业务上的误判率。

### 10.4 哪些问题应阻止发布

**关键约束不参与平均分补偿。** 本文建议把越权写入、旧派发覆盖新状态、错误重复提交，以及静默破坏已确认成果列为发布阻断项：测试中出现一次，就保留失败并阻断该候选版本。这里的零容忍是发布规则，不是对生产零风险的承诺。

任务成功率、恢复成功率、误判率和耗时的门槛则应按业务风险与既有基线提前确定。没有基线时，先建立首版测量结果，不凭空写一个“95%合格”。新版本既要满足业务下限，也要检查已通过样本是否退化；速度变快，不能抵消必需结果缺失。

每次架构改动应保留样本集版本、评分规则、运行配置和逐次结果。故障修正后，重跑对应失败样本，也重跑原本通过的任务。上线后的超时、人工接管和错误成果，再经过确认转为新的离线样本。这样才能区分：改动提高了任务能力，还是只适配了眼前几道测试题。

## 11结论：用测试与评测检验架构

这套设计把任务要求、执行尝试、外部动作和产物检查分别保留，通过受控提交与读回组织执行。它使系统能够表达“文件已完成但交付未结束”“运行结束但内容不合格”等状态，并据此选择不同恢复动作。

已有实验验证了固定路径中的原稿保留、失败成果读回，以及核验输出配置调整后的正反例判断。复杂任务中的跨文件误修和内容漏判，则说明原始要求、产物事实与返修范围仍需共同检查。

架构图说明模块怎样协作，工程测试检查状态约束是否成立，任务评测检查这种协作能否得到合格结果。持续改进 Harness，需要把失败留成可重放样本，把关键约束写成断言，再用相同标准比较修改前后。模块分得更细、核验轮数更多，都应接受这组检查，而不能直接算作能力提升。
