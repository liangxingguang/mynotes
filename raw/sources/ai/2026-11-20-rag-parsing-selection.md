# 05 · RAG 解析方案怎么选

把文档变成结构化文本有三条路线：用规则读文件内部结构、用模型做版面分析、调用商用解析服务。三者机制不同，适合的语料也不同。

规则解析不看图像，读的是文件内部的排版对象：字体的字号粗细、文本块坐标、段落与列表标记。一页纯文本 PDF 毫秒级，不需要 GPU，结果可复现，出问题能追到具体规则。但扫描件没有文本对象，它拿不到任何内容；双栏排版里坐标排序会把左右两栏按行合并；文本框、嵌套表格、图片化文字的文档，内部对象与实际阅读顺序不一致。

版面模型把每页渲染成图像，先检测标题、正文、表格各占的区域，再逐区域识别。它处理的是人眼看到的版面，不受内部对象混乱影响，扫描件必须走这条路。代价三块：算力上单页从毫秒升到百毫秒到秒级，纯 CPU 部署吞吐会明显下降；准确性上 OCR 有识别错，生僻字、印章遮挡、细线表格都影响，跨页与合并单元格是常见失败点；工程上模型版本与环境要维护，升级可能改输出格式，已有分块与索引要跟着重建。

商用 API 把文件交给服务商，接入成本最低。要接受三个约束：数据出域，制度合同财报通常有保密要求；限流与成本，按页按次计费，全量导入要排队或分批；能力边界固定，支持什么格式、还原到什么程度都由服务商定义。

实际系统里最常见的不是单选，而是分层。规则解析跑全量，产出异常（文本过少、顺序混乱、表格失败）的挑出来再走模型，模型只处理少数难例；或按文档来源分流，识别出某系统导出的 PDF 是扫描件就固定走 OCR；或按用途分流，预览要粗略文本，检索要完整结构。

怎么选，按顺序判断：先看有没有扫描件，有就必须能处理图像；再看能否出域，不能就排除商用 API；再看来源数量，来源多、模板各异时先建分流逻辑；最后算总成本，自建的维护、升级、人工复核常常超过服务费。

还有一个容易忽略的绑定：换解析器意味着同样文档产出不同文本，文本变了分块就变，向量全部失效，必须全量重建索引。所以选型要在建库之前定，或至少记录每份文档用的解析器与版本，换方案时能精确知道哪些需要重建。
