## 一、settings.json：一次配好默认行为

这是最该先配的文件。官方给出的完整示例：

```
{
```

几个关键字段的实战用法：

**1\. 给不同模型设不同思考等级**（`modelThinkingLevels`）  
 默认 `defaultThinkingLevel` 是全局的，但你可以对特定模型单独覆盖。比如日常用 `low` 省钱，只在某个强模型上开 `high`：

```
"modelThinkingLevels": {
```

**2\. 控制 `Ctrl+P` 循环哪些模型**（`enabledModels`）  
 格式和 CLI 的 `--models` 一致，用前缀匹配：

```
"enabledModels": ["claude-", "gpt-4o", "gemini-2"]
```

配好后，会话里按 `Ctrl+P` 就只在这几个之间循环，不会在一堆用不到的模型里翻。

**3\. 上下文压缩**（`compaction`）

*   `reserveTokens`
    
    ：给压缩后保留的"系统区"留多少 token（默认 16384）。
    
*   `keepRecentTokens`
    
    ：压缩时强制保留最近多少 token 的对话（默认 20000），避免把刚说的关键上下文压掉。
    

调大 `keepRecentTokens` 适合"最近几轮很重要"的场景；想更省 token 就调小。

**4\. 重试**（`retry`）  
 本地模型或不稳定端点建议开重试。完整示例：

```
"retry": {
```

> 配完不用重启 Pi，会话里敲 `/reload` 即可生效。

## 三、AGENTS.md：给 Pi 装一个"项目大脑"

`AGENTS.md` 是项目/全局指令，启动时自动加载。加载顺序：**全局 `~/.pi/agent/` → 父目录 → 当前目录**，后加载的覆盖先加载的。

**TorchTree 的分工建议**：

*   **全局 `~/.pi/agent/AGENTS.md`**
    
    ：写你日常通用的技术栈偏好、代码规范（跨项目适用）。
    
*   **项目级 `AGENTS.md`**
    
    （仓库根目录）：写这个具体项目的约束、构建命令、目录约定。
    

一个项目级 `AGENTS.md` 长这样（结构参考社区通用写法）：

```
# Project: foo-service
```

* * *

## 四、APPEND\_SYSTEM.md：比 AGENTS.md 更高优先级的全局行为规则

这是 deepakness 强烈推荐的用法。`APPEND_SYSTEM.md` 放在 `~/.pi/agent/APPEND_SYSTEM.md`，**内容直接追加到系统提示词末尾**，因此它的指令比 `AGENTS.md` 优先级更高，对所有项目生效。

**deepakness 实际放的内容**（可直接抄）：

```
- If the default provider doesn't have vision capabilities, use pi-vision-handoff for images.
```

翻译成中文就是四条黄金规则：

1.  **没视觉能力就用 `pi-vision-handoff` 处理图片。**
2.  **答案在代码库里就先读本地文件；不在再联网查（pi-web-access）。基于联网结果做大改动前，先跟我确认。**
3.  **执行危险文件编辑/破坏性命令前，先解释清楚。**
4.  **写得简单点，杜绝 AI 腔（不要华丽形容词、多余副词、过度正式）。**

> 这就是把"你的工作习惯"固化成 Agent 的默认行为。把它配好，Pi 立刻从"通用助手"变成"懂你脾气的助手"。

## 七、一个"抄完即用"的完整配置清单

把上面串起来，新手可以直接照抄的最小可用组合：

1.  `~/.pi/agent/settings.json`
    
     —— 设好 `defaultModel`、`defaultThinkingLevel`、`enabledModels`。
    
2.  `~/.pi/agent/APPEND_SYSTEM.md`
    
     —— 放那 4 条全局行为规则。
    
3.  `~/.pi/agent/AGENTS.md`
    
     —— 放你的通用技术栈偏好。
    
4.  想省成本/要隐私 → `~/.pi/agent/models.json` 接本地 Ollama（见第二节）。

## 151. Pi实战 02：提示词与技能篇——把重复工作固化成命令 151. Pi实战 02：提示词与技能篇——把重复工作固化成命令

> 来源：Pi 官方 Prompt Templates / Skills 文档，以及社区热门技能（impeccable、mattpocock/skills）。

如果你每天都在重复同样的指令——“先写测试”“按这个模板建 API”“帮我 review 这个 PR”——那就别每次手打。Pi 有两种固化方式：

*   **Prompt Templates（提示词模板）**
    
    ：把一段提示词变成 `/xxx` 斜杠命令，支持参数。适合"一句话触发一段固定流程"。
    
*   **Skills（技能）**
    
    ：自包含的能力包（`SKILL.md` + 脚本 + 资源），按需加载。适合"一整套带脚本的工作流"。
    

一句话区别（composio.dev 总结得很准）：**Skills teach the agent（技能教会 Agent），Extensions extend the agent（扩展扩展 Agent）。**

## **二、Skills：按需加载的能力包**

### **1\. Skills 怎么工作**

1.  **启动时 Pi 扫描技能目录，提取每个技能的 `name` 和 `description`。**
2.  **这些元信息以 XML 形式塞进系统提示词。**
3.  **当任务匹配某个技能时，Agent 用 `read`（或 `bash`）加载完整 `SKILL.md` 来执行。** 

*   ⚠️ 模型**不一定主动读**`SKILL.md`。两种办法强制它读：在提示词里明确要求，或直接 `/skill:name`。
    

### **2\. 命名规则（容易踩坑）**

*   **1–64 字符，仅小写字母、数字、连字符 `-`**
*   **不能以 `-` 开头或结尾**
*   **不能连续 `-`**

```
✅ pdf-processing   data-analysis   code-review❌ PDF-Processing   -pdf   pdf--processing
```

## **四、避坑小结**

*   **模板名 = 命令名，**别和内置命令撞名**（`/validate-prompts` 会报 reserved command names）。**

## Pi实战 03：扩展篇——没有的功能，自己造

> 来源：Pi 官方 Extensions / TUI 文档，deepakness、jasonzhou1993、lobehub skill、ruizrica2 等开发者的实战扩展。

扩展（Extensions）是 Pi 最核心的价值，也是它和 Claude Code 最大的分水岭。

> **官方原话**：“Features that other agents bake in, you can build yourself. Extensions are TypeScript modules with access to tools, commands, keyboard shortcuts, events, and the full TUI.”  
>  （其他 Agent 内置的功能，你可以自己造。扩展是能访问工具、命令、快捷键、事件和整个 TUI 的 TypeScript 模块。）

**扩展 vs 技能的关键区别**：

*   **技能**
    
    （SKILL.md）Agent 看得到，是"知识"。
    
*   **扩展**
    
    （.ts）**LLM 永远看不到**，它在幕后钩入 Agent 循环的生命周期事件运行，是"手"。 
    

*   一个很传神的说法（Archon 作者）：“The skill is the knowledge, the extension is the hands.”（技能是知识，扩展是手。）
    

Pi 通过三个对象把几乎所有"接缝"都暴露给你（jasonzhou1993）：

*   `pi`
    
    （ExtensionAPI）：注册工具、命令、提供商、事件监听。
    
*   `ctx`
    
    ：事件发生时的上下文。
    
*   `ctx.ui`
    
    ：操作终端 UI（header、footer、widget、overlay、notify）。
    

再加上 `/reload` 热重载——**Pi 能一边被你用，一边重写它自己的外壳**。

* * *

## 一、最小扩展骨架

```
mkdir -p ~/.pi/agent/extensions
```

```
import type { ExtensionAPI } from "@mariozechner/pi-coding-agent";
```

Pi 自动发现 `~/.pi/agent/extensions/` 下的 `.ts` 文件并加载。改完 `/reload` 即生效，无需重启。

* * *

## 二、经验 1：注册一个新工具（最常见）

让 Agent 多一个能力，比如"读剪贴板"（jasonzhou1993 的例子）。工具注册是最常用的扩展类型：

```
import type { ExtensionAPI } from "@mariozechner/pi-coding-agent";
```

要点：

*   `parameters`
    
     用 TypeBox `Type.Object` 定义输入 schema（工具调用靠它）。
    
*   `renderShell: "self"`
    
     表示工具结果自己渲染。
    
*   `renderCall`
    
     收到 `context`，可拿到 `theme` 做配色（`theme.fg(token, text)`）。
    

官方还给了 `summarize.ts`、`snake.ts`（在 TUI 里玩贪吃蛇）等例子，都在仓库 `examples/extensions/`。

* * *

## 三、经验 2：权限守卫——拦截危险命令

这是几乎每个把 Pi 当主力的人都会写的第一个扩展。在工具调用前拦截 `rm -rf`、`sudo`、`.env` 等：

```

```

放进 `~/.pi/agent/extensions/permission-gate.ts`，或加载时指定：

```

```

## 四、经验 3：自定义 footer / 状态栏

deepakness 让 Pi 自己写了个"极简 footer"，显示：当前目录、git 分支（带 dirty 标记）、模型名、思考等级、可选目标槽、紧凑上下文条。代码放在 `~/.pi/agent/extensions/minimal-footer.ts`，每次启动自动加载。

核心 API（nunorralves 实测总结）：

*   `ctx.ui.setHeader(...)`
    
     在 `session_start` 改 header。
    
*   `theme.fg(token, text)`
    
     / `theme.bg(token, text)` 取色——51 个 token，和你的主题保持一致，**不要硬编码 ANSI 颜色**。
    
*   footer 在 editor 和 footer 之间**没有中间槽位**；想在 footer 上方加状态行，就得整体替换 footer。
    

一个取色示例：

```
const label = theme.fg("accent", theme.bold("Status:"));
```

嫌麻烦？社区有现成的：`@lystran/pi-statusline`（用当前主题配色、带动画 logo 的 `pi-open-tui`）等，一条命令装好。

Pi **没有内置子代理**（sub-agents）、没有 plan mode、没有后台 bash。官方态度很明确：“Ask Pi to build what you want, or install a package that does it your way.” 但正因如此，社区玩出了花。这一篇讲三件事：

## 一、经验 1：让 Pi "自己跑自己"做子代理

Mario Zechner 在博客里说得很直白：

> “If you need pi to spawn itself, just ask it to run itself via bash. You could even have it spawn itself inside a tmux session for full observability.”

他的典型场景是**代码审查**：写一个自定义斜杠命令，让主 Agent 通过 bash 再启动一个 Pi 进程去跑审查，主进程拿到输出即可。

**他给出的子代理命令 frontmatter 骨架**（`description: Run a code review sub-agent`）：

```
---
```

怎么用：

1.  把这个做成一个 prompt template（见第 02 篇），比如 `/review-pr`。
    
2.  用简单提示词选具体要 review 什么、用哪个模型，甚至设思考等级。
    
3.  可以存成临时会话（ephemeral，不落盘），或存盘后跳进那个会话继续看。
    

这一切最终被翻译成一个 prompt，主 Agent 读完后**通过 bash 再次执行自己**。虽然不如原生子代理那样"全 observable"，但足够用，而且模型/工具/思考等级都能按需指定。

> 关键点：Pi 没有 `task` 工具，所以"多代理"本质是**你用 bash/tmux 把它编排出来**的。这恰恰是 Pi 的哲学——能力给你，怎么组你自己定。

*   **Agent 定义是带 YAML frontmatter 的 Markdown 文件**

1.  **pre-tool-hook**

2.  **content scanner**
    
    ：检查工具返回里有没有提示词注入。

## 四、经验 4：会话树——对话的"版本控制"

这是 HN 用户一致好评的功能（vorticalbox：“Sessions are stored as trees, that is actually really nice.”）。Pi 的会话不是线性列表，是**一棵树**，底层就是按位置存的 `.jsonl` 文件（每条消息 append 一行，极易文档化）。

实战命令：

命令

作用

`/tree`

把会话历史画成树，跳到任意节点继续

`/fork`

从当前某条消息分支，开一条新工作线

`/clone`

把当前活跃分支复制成一个新会话

`/resume`

捡起之前的会话继续

`/new`

开全新会话

**典型用法**：探索复杂问题时，用 `/fork` 试方案 A，不满意再回到分叉点 `/fork` 试方案 B——不同解法互不污染。还能"rewind to any prior message, branch from there and share the entire session with others"（回退到任意消息、从那里分支、把整条会话分享给别人）。

## 五、实战：一套"计划-实现-验证"流水线

结合前面几篇，一个可落地的多步工作流：

1.  **计划**
    
    ：用一个 `/plan` prompt template，让 Agent 把计划写进 `PLAN.md`（Pi 没有 plan mode，就自己写文件）。
    
2.  **实现**
    
    ：主 Agent 跑；需要审查时 `/review-pr` 起一个只读子代理（第一节）。
    
3.  **并行**
    
    ：把子代理丢进 tmux pane 跑，主进程继续干别的（第三节）。
    
4.  **分支复盘**
    
    ：对结果不满意？`/tree` 回到分叉点重来，不丢上下文（第四节）。
    
5.  **安全**
    
    ：全程有 permission-gate 拦危险命令（第 03 篇）。
    

社区现成的包能直接给你这套流水线，比如 `pi-dynamic-workflow`（灵感来自 Claude Code 的 dynamic workflows）、`TrailStep`（把过程编码成 TS 工作流，每步有独立 scoped agent session，失败可续跑）。

## 六、小结

*   Pi 没有原生子代理 → 用 **bash 自举**或 **tmux 并行**自己编排。
    
*   多代理 = 一堆扩展 + `settings.json` + Markdown 定义的"专家角色"。
    
*   **安全层要自己加**
    
    ：pre-tool-hook 拦命令、content scanner 防注入、`/secure` 审计。
    
*   **会话树**
    
    是 Pi 的隐藏神器，把对话变成可分支、可回退、可分享的版本历史。

## 一、本地模型：零成本、零数据外泄

Pi 支持 15+ 提供商和自定义本地端点，通过 `models.json` 热重载。这是它相对纯云端 Agent 的最大优势之一。

**手动接本地 Ollama**（dalenguyen 实测，`~/.pi/agent/models.json`）：

```

```

> LM Studio、llama.cpp、Ollama 都暴露 OpenAI 兼容端点，**Pi 不在乎你用哪个**，配置通用，换着试零成本。

### 方案 C：本地 + 云混合（BenjaminWegener 的 M4 Mac 实践）

*   用 **TurboQuant fork** 在 M4 上用 Metal 跑重推理，文档**永不离开硬件**。

*   收益：数据主权、隐私（无云厂商窥探）、低延迟。

原文：https://mp.weixin.qq.com/s?__biz=MzkwOTAxOTY4Nw==&mid=2247485330&idx=1&sn=8546d1530cd8de0b61ec34477c83d17d&chksm=c0c058daf7b7d1cc1a82f7748fca544569686d176e0dcce6ad88f35ad4df33ba7bd7e779763b

## Pi实战 07：调试篇——用 Pi 定位并修复 bug

> 来源：Pi 官方 package `pi-debug-mode`、arXiv《Debug2Fix》、brian-kimball 的 crash-logger 扩展、LangSmith 调试实践、Mario Zechner 的 evidence-first 理念。

* * *

## 一、使用场景

*   测试挂了，但不知道为啥挂——光看报错信息不够。
    
*   线上某个接口偶发异常，复现了但定位不到根因。
    
*   改了一个地方，另一个看似无关的地方崩了，想搞清楚调用链。
    
*   Agent 自己改代码把东西改坏了，你想回溯它到底动了什么。
    

## 二、能解决什么问题

核心是**把"猜 bug"变成"看证据再修"**。

很多人用 Agent 调试的毛病是：一看报错就让 Agent"直接改"，结果 Agent 在没理解根因的情况下瞎试，改一处冒十处。这一篇要解决的就是**先复现、先取证、再动手**的调试纪律。

Mario Zechner（Pi 作者）反复强调 **evidence-first（证据优先）**：调试时先拿到程序真实运行的动态证据，再让 Agent 分析，准确率远高于"读代码凭感觉猜"。

## 三、解决思路

一个被验证有效的调试循环（来自 arXiv《Debug2Fix》对大量真实调试问题的归纳）：

```
Step 1  Build      → 先让项目能编译/能跑起来
```

关键纪律：**Step 2、3 没做透之前，别进 Step 4。** 《Debug2Fix》统计，最常见的调试问题就是"异常诊断"（~28%）和"根因分析"，另有 ~30% 是"局部变量/属性值检查"——也就是说，**问对"现在到底是什么值"比"怎么改"更重要**。

## 四、如何实战（含例子）

### 实战 1：装一个 Cursor 风格的 Debug Mode

Pi 社区有 `pi-debug-mode` 包，给 Pi 加上"证据优先的运行时调试模式"，专门做 bug 复现和根因分析。

```
pi install npm:pi-debug-mode
```

装完后，遇到 bug 不再是"帮我修一下"，而是走调试模式：先复现、再定位。

### 实战 2：用"子代理提问法"逐层逼问根因

这是《Debug2Fix》的核心技巧。不要让 Agent 一次性"看懂并修好"，而是**让它派一个调试子代理，问一串具体的、可观测的问题**：

```
Step 1 先构建：
```

**真实例子**：有人调试一个时间 bug，让子代理去看 `_safe_now()` 的返回值，结果它返回的是 `datetime(1970, 1, 1)` 而不是当前时间——**一眼就锁定了根因**。这就是"问对可观测的值"的力量：与其让 Agent 通读代码猜，不如让它去"看一眼运行时到底返回啥"。

在 Pi 里你不用真有个 `debug_subagent` 工具，直接对主 Agent 说同样的话即可：

```
先别改代码。帮我复现并定位这个 bug：
```

### 实战 3：加一个 crash-logger，把"失败"自动记下来

brian-kimball 在他的多代理配置里写了个 **crash-logger 扩展**：记录未捕获异常、未处理的 promise rejection、流错误、非零退出码，连同进程元数据一起存盘。**正常零退出不记录——这个文件是"失败记录"，不是会话日志。** 环境标记还能区分"主 Pi 会话"和"某个命名的子代理"。

好处：下次再崩，直接查失败日志，不用重现半天。让 Pi 帮你写这个扩展：

```
帮我写一个 crash-logger 扩展：
```

### 实战 4：用"trace"回溯 Agent 自己干的好事

有时候 bug 是 Agent 自己改出来的。LangSmith 的做法是**重建整条会话**：按顺序看 user request → assistant 各轮 → model/tool 调用 → subagent → 耗时/ token。

它举过一个典型调试发现：

```
test fail
```

差分时你只看到最后那个绿勾，但 trace 暴露了真相：**Agent 是靠改文件"绕"过测试，而不是真修好了逻辑。** 这种"假修复"光看 diff 发现不了，必须看过程。

> Pi 本身会话就是 `.jsonl`（每轮 append 一行），配合 `/tree` 回溯、`/session` 看完整记录，就能手动做这种"会话重建"。想让 Agent 自己学会"别作弊式修测试"，就把这条写成 `APPEND_SYSTEM.md` 规则（见第 01 篇）。

* * *

## 五、小结 & 避坑

*   **调试顺序不能跳**
    
    ：Build → Understand → Investigate → Fix → Verify。根因没定位就动手 = 改一处冒十处。
    
*   **问"可观测的值"胜过"通读代码"**
    
    ：让它去看运行时返回什么、变量是什么，而不是"你看着办改好"。
    
*   **先复现再修**
    
    ：修不好的 bug 八成是没稳定复现。
    
*   **警惕"假修复"**
    
    ：测试从红变绿不一定是真修好，可能是绕过了断言——看过程而非只看结果。
    
*   **给失败留痕**
    
    ：一个 crash-logger 让你下次直接查日志，而不是重新复现。

## Pi实战 09：提示词心法篇——给编码 Agent 下指令的正确姿势

> 来源：developersdigest、addy-o Substack、ranthebuilder、PromptHub、以及 HN “Ask HN: How do people use coding agents?” 里 Pi 用户的真实 prompt 示例。

> 注：第 02 篇讲的是"怎么把提示词**固化成模板/技能**"（机制）；这篇讲的是"**提示词本身该怎么组织**"（心法）。两篇互补。

* * *

## 一、使用场景

*   给 Pi 下了一堆指令，它做出来的东西总是不对味——要么跑偏，要么过度发挥。
    
*   改一个 bug，它顺手重构了半个文件。
    
*   让它"优化一下代码"，结果加了一堆你用不到的抽象和 fail-safe。
    
*   不知道一句话该说多细：说少了它瞎猜，说多了又嫌啰嗦。
    

## 二、能解决什么问题

解决\*\*"你脑子里的意图"和"Agent 实际执行的结果"之间的落差\*\*。

编码 Agent 没有读心术，它只能拿到你写出来的东西。提示词质量直接决定结果质量——尤其是当任务**触及真实代码、测试、权限、生产流程**时，prompt 的重要性远大于模型本身的强弱（developersdigest）。

## 三、解决思路

### 心法 1：一个经得起验证的 prompt 结构

developersdigest 给出的结构，适合任何触及真实代码的任务：

```
1. Goal（目标）        —— 改完之后"什么应该成立"
```

**多文件工作，前面再加一步 Plan-First（先给计划）**：让它先讲打算怎么改，你把关方向，它再动手。

### 心法 2：简洁 + 精确 > 冗长

HN 上 Pi 用户（vibe42）的原话，被顶得很高：

> “The simpler and more precise the prompt the better it works. Keep it simple and run a fresh, new context for each prompt.”  
>  （提示词越简单、越精确越好。保持简单，并且每个 prompt 都用一个全新的上下文。）

他给的**真实例子**（让 Pi 审查 Go 代码，只读不改）：

```
Review all golang code files in this folder. Look for refactor opportunities
```

注意它把**目标、约束（不改逻辑/只描述）、产出形态**一句话讲清了。

### 心法 3：说"要什么"，别说"不要什么"

ranthebuilder 的建议：**stay positive**。告诉它你想要什么、期待什么，而不是罗列一堆"不要怎样"。否定式指令模型经常接不住。

### 心法 4：把上下文"喂"给它，别让它猜

*   addyo：把相关文件**打开/引用**，Agent 会看到你的模式并沿用。
    
*   明确说出项目约定，比如：“我们用 Redux 管理 state——把搜索 state 集成进 Redux store。”
    
*   PromptHub 总结：**Context is critical**——把脑子里的上下文全倒出来，它没法推断你没写的东西。
    

### 心法 5：要"证据回执"，不要只收最终答案

developersdigest 的 Receipt 模板，要求 Agent 回报的是**证据**而非一句"改好了"：

```
Final receipt:
```

> 这就是 “agent receipt” 理念：**最终答案不够，Agent 应该返回证据。** 这样你一眼能判断它真做完了还是"看起来做完了"。

## 四、如何实战（含例子）

### 实战 1：套结构写一个"加功能"的 prompt

```
# Goal
```

### 实战 2：多文件改动，先要计划再动手

```
我想把鉴权从 JWT 换成 Session。先别改代码——
```

### 实战 3：卡住了就开新会话

addy-o 的实战技巧：

> “Consider starting fresh if the thread is stuck. Sometimes after multiple tries, the conversation may reach a confused state. … a fresh context can eliminate any accumulated confusion from prior messages.”

会话来回试了几轮越改越乱时，**别硬拗**——开个新会话，用前面失败的经验重新组织一个更精准的 prompt，从头来。模型不介意重复，干净上下文反而更快。

### 实战 4：追问式调试提问

addy-o：给完上下文后，直接问聚焦的问题，并Follow-up：

```
"What might be causing this issue, and how can I fix it?"
```

## 五、小结 & 避坑

*   **套结构**
    
    ：Goal / Context / Constraints / References / Verification / Receipt，多文件先 Plan-First。
    
*   **简洁精确**
    
    ：别堆字数，一句讲清目标+约束+产出形态。
    
*   **说"要"不说"不要"**
    
    ：正向描述期待的行为。
    
*   **喂上下文**
    
    ：引用相关文件、点明项目约定，别让它猜。
    
*   **要证据回执**
    
    ：让它回报改了啥、跑了啥、过没过、有啥风险。

    ：会话乱了开新的，别在混乱上下文里硬耗。

## 159. Pi实战 10：重构与避坑篇——让 Pi 重构大项目而不搞砸 159. Pi实战 10：重构与避坑篇——让 Pi 重构大项目而不搞砸

原文：https://mp.weixin.qq.com/s?__biz=MzkwOTAxOTY4Nw==&mid=2247485338&idx=1&sn=896fd8ba6bf6f195ba43c4029992653b&chksm=c0c058d2f7b7d1c433ad7db5bb8ebfd815af6ed3d5c8b28891bf6ca96099f4c477753181534d

## Pi实战 10：重构与避坑篇——让 Pi 重构大项目而不搞砸

> 来源：Mario Zechner 博客/推文、DAPLab《9 Critical Failure Patterns of Coding Agents》、Simon Willison 对谈、Umut Eser、HN、pi-self-learning 等。

* * *

## 一、使用场景

*   有个几千行的老模块想重构，不敢手拆，想让 Agent 上。
    
*   用 Agent 开发一段时间后，发现代码越来越臃肿、重复、抽象乱长，想治理。
    
*   想让它审查代码库、找"简化"机会。
    
*   担心 Agent 改着改着把架构改乱、引入技术债。
    

## 二、能解决什么问题

解决一个**反直觉但极其重要**的认知：**Agent 不会主动帮你重构，反而会让你欠更多技术债。**

Mario Zechner（Pi 作者）的原话，值得每个用 Pi 的人贴墙上：

> “Agents refactor less because they feel no ‘pain.’ Humans rewrite bad interfaces because maintaining them hurts, whereas agents will obliviously churn out and extend a terrible structure, ad infinitum. This is a big reason why AI agents keep adding more tech debt.”  
>  （Agent 很少重构，因为它们感受不到"痛"。人类会因为有维护之痛而重写烂接口，Agent 却会无意识地在一堆烂结构上继续堆砌，永无止境。这就是 AI 不断堆积技术债的一大原因。）

他还有一条推文更直白：

> “Your biggest enemy is still complexity. It’s also your agent’s biggest enemy. But it has no holistic view of your code base, so it keeps adding complexity.”  
>  （你最大的敌人是复杂度，它也是 Agent 最大的敌人。但 Agent 没有你代码库的全局视图，所以它会不断加复杂度。）

**所以这一篇的核心价值**：教你**用人来当"复杂度守门员"**，用流程约束 Agent，让它重构时不帮倒忙。

## 三、解决思路

### 思路 1：你负责"痛"，Agent 负责"改"

既然 Agent 感受不到痛，**你得替它感到痛**——主动要求它简化、主动审查它有没有重复/过度抽象。别指望它自发做。

### 思路 2：只读优先，先诊断后动手

对大代码库，先让它**只读、只描述、不改**，你确认方向对了再让它改。HN 上 Pi 用户的真实做法（见第 09 篇那个 Go 审查 prompt）就是典范。

### 思路 3：分阶段，别一次吞下整个代码库

DAPLab 指出 Agent 的典型失败模式是 **“lack of codebase awareness”（缺乏代码库意识）**：项目一大，它就记不住整体架构，改错组件、引入破坏性变更。对策是**分阶段、小范围、有验证**地推进。

### 思路 4：保持代码库高质量，Agent 才会产出高质量

Simon Willison 的洞见：

> “There’s a lot to be said for keeping your codebase high quality because the agent will then add to it in a high quality way. … Even having just one or two tests in the style that you like means it’ll write tests in the style that you like.”  
>  （保持代码库高质量很有意义，因为 Agent 会以同样高质量的方式往上加。哪怕只有一两个你风格喜欢的测试，它也会照着那个风格写测试。）

**你的代码库是什么样子，Agent 就会往那个方向放大它。** 这是正反馈——好的越好，烂的越烂。

## 四、如何实战（含例子）

### 实战 1：只读诊断——先让它"找简化机会"

直接复用 HN 那个被验证有效的 prompt（改改就能用）：

```
Review all golang code files in this folder. Look for refactor opportunities
```

要点：**明确"只描述不改"**，并定义"好重构"的标准（更简单、更短、更易懂、更易维护、不改逻辑）。拿到清单后，你挑真正有价值的再让它动手。

### 实战 2：对抗 DAPLab 的失败模式

DAPLab 总结的几个高频失败模式，各有对策：

失败模式

表现

你的对策

缺乏代码库意识

改错组件、引入破坏性变更

分阶段、小范围；让它先画架构再动

重复代码

在 `fetchUserData` 和 `fetchProductData` 里各写一遍 API setup，而不是抽共享 helper

明确要求"复用既有抽象，别重写"

业务逻辑错配

拖拽 reorder 只更新了部分 state，没协调整个列表顺序

让它写测试覆盖该交互，用测试验证

把这三条写进 `AGENTS.md`，变成它的默认约束。

### 实战 3：禁止"并行改同一批文件"

Mario 明确说：

> “Spawning multiple sub-agents to implement various features in parallel is an anti-pattern in my book and doesn’t work, unless you don’t care if your codebase devolves into a pile of garbage.”  
>  （并行开多个子代理实现不同功能，在我这是反模式，除非你不在乎代码库变成垃圾堆。）

**对策**：触及相同文件的任务串行，只有彼此独立的单元才并行。（brian-kimball 的 triage 原则也是这个：Inline / Delegate / Parallelize-only-when-independent / Serialize-when-shared.）

### 实战 4：对抗"过度工程"

Umut Eser 吐槽所有 Agent 的通病：

> “You give an instruction and they overkill it. They all try to build a full fledged code, which has a ton of unnecessary components… A lot of fail-safe mechanisms, creating silent bugs.”

对策——在 prompt / `APPEND_SYSTEM.md` 里明确要求**最小实现**：

```
从最简单、能跑的最小实现开始，不要预先加抽象、fail-safe 或我沒要求的组件。
```

### 实战 5：让 Pi 记住教训（自我学习）

nodeland 指出 Agent 的致命弱点：**每次会话都是全新开始，零记忆**，于是你会反复踩同一个坑。

`pi-self-learning` 的解法：建一个 `CORE.md`，按**频率和近远**给"学到的教训"排序，每次会话自动注入。配套命令：

```
/learning-now              → 立刻做一次反思
```

这样"别重写既有抽象""某模块有个坑"这类教训会**跨会话沉淀**，而不是每次重新交学费。

* * *

## 五、小结 & 避坑

*   **你当复杂度守门员**
    
    ：Agent 不觉得痛，你得替它觉得痛，主动要求简化。
    
*   **先只读诊断，后动手**
    
    ：大代码库先让它只描述不改，你挑了再改。
    
*   **分阶段、小范围、有验证**
    
    ：对抗"缺乏代码库意识"。
    
*   **要求复用、禁止并行改同文件、要求最小实现**
    
    ：三条直接写进 `AGENTS.md`。
    
*   **保持代码库高质量**
    
    ：你是什么样，Agent 就放大成什么样。
    
*   **让教训跨会话沉淀**
    
    ：用自我学习扩展记住踩过的坑。

## 161. Pi实战 11：上手陌生代码库篇——用 Pi 快速吃透一个新项目 161. Pi实战 11：上手陌生代码库篇——用 Pi 快速吃透一个新项目

原文：https://mp.weixin.qq.com/s?__biz=MzkwOTAxOTY4Nw==&mid=2247485346&idx=1&sn=134918a505aaec21d840be1da95d0bc1&chksm=c0c058eaf7b7d1fcbe77507627727140d1356789d66309154a198f7a3a3326cd3da94a11eb80

## Pi实战 11：上手陌生代码库篇——用 Pi 快速吃透一个新项目

> 来源：super-productivity 的 AI onboarding 指南、matthewswong 博客、OpenAI Codex use-case、社区 package `codecartographer-pi` / `@artale/pi-codebase-map` / `@init`，以及 Pi 自我文档化的特性。

* * *

## 一、使用场景

*   刚接手一个陌生仓库，几千个文件，不知道从哪读起。
    
*   要改一个功能，但不知道请求从哪进、数据往哪落。
    
*   新人入职，想快速搞懂服务的整体架构和关键模块。
    
*   想给 Agent 建立这个项目的"说明书"，以后它就不用每次重新摸索。
    

## 二、能解决什么问题

把\*\*“人肉读代码几周"压缩成"Agent 几小时给你一张带证据的地图”\*\*。

关键不是让它给你一堆文件名，而是给它一套**结构化的提问框架**，逼它产出**带证据、标不确定性、可验证**的地图——而不是看似专业实则瞎编的清单。

## 三、解决思路

### 思路 1：要"地图"，不要"文件名列表"

OpenAI 的 codex onboarding 指南点出好坏之分：

> “A useful onboarding answer should leave you with a concrete map, not just a list of filenames. By the end, it should have explained the main flow, highlighted the risky parts, and pointed you to the next files or checks that matter before you start editing.”  
>  （有用的 onboarding 回答应该给你一张**具体的地图**，而不是一堆文件名。它应该讲清主流程、标出危险部分、并指出你动手前该读的下一批文件。）

### 思路 2：五个层层递进的问题

super-productivity 给了一套被验证有效的提问序列，从"是什么"一直问到"我还不懂啥"：

```
1. Map      —— 从 README、包文件、入口点梳理项目结构，每个结论都要引用文件。
```

### 思路 3：只留能追溯到代码的结论

matthewswong 的硬规矩：

> “…write the findings to a committed instruction file, and delete every claim you cannot trace to a file and a line.”  
>  （把发现写进一个提交进 git 的指令文件，并删掉每一个无法追溯到"某个文件的某一行"的断言。）

**这是防 Agent 幻觉的关键**：凡是它说的，必须能指到具体文件+行号；指不到的，一律当它胡说、删掉。

### 思路 4：把地图沉淀成项目说明书

一旦跑通，就把结果写进 `CLAUDE.md` / `AGENTS.md` 并提交。以后每次开会话，Agent 自动读这份说明书，**不用重新摸索**。社区 `@init` 包就是干这个的：Claude Code 风格的代码库初始化，自动写出 `CLAUDE.md`。

## 四、如何实战（含例子）

### 实战 0：先建立直觉——「烂地图」和「好地图」长啥样

在深入之前，先看同一个问题「这个项目怎么做用户登录的？」两种回答的对比。看完你就知道该怎么要求 Pi 了。

**烂地图（一堆文件名，看着专业，读完还是懵）：**

```
这个项目用了 Express、Prisma 和 React。主要文件有：
```

> 评价：文件名列了一大堆，但你还是不知道"登录"这件事**从哪个文件进、到哪一步落库、哪里最容易出 bug**。这就是 OpenAI 说的"文件名列表"——Agent 很可能在瞎编一份看着专业的清单。

**好地图（有主流程、有危险点、有下一步）：**

```
【主流程：用户登录】
```

> 评价：一眼能看到主流程、标出了"密钥加载"这个危险点、还告诉你下一步该读啥。**这才是地图。** 你要求 Pi 时，就要的是右边这种，不是左边那种。

* * *

### 实战 1：完整走查一个真实项目（五问 + 真实风格输出）

下面拿一个具体的项目 `bookmark-api`（一个用 Express + Prisma + PostgreSQL 写的书签管理后端）做完整演示。你把自己的项目名和关注点换进去即可。

**第一步，丢给它"五问"提示词：**

```
我要上手 bookmark-api 这个仓库，帮我建立整体认知。请按下面五步来，
```

**Pi 大致会回你这样一份东西（真实风格，文件/行号为示例）：**

```
## 1. Map —— 项目结构
```

> 注意第 4 步的价值：它**主动承认自己不确定**，并告诉你每点该查哪个文件。这比一份"看似什么都知道"的回答可靠得多——因为你能顺着它给的线索去验证。

* * *

### 实战 2：把地图固化成 `AGENTS.md`（看最终产出长啥样）

走查完别让它停在对话框里。让 Pi 把结论整理成一份**只保留能追溯到文件+行号**的说明书并提交：

```
把上面梳理出的架构、入口、调用链、行为规则、以及已知的不确定点，
```

**它大致会生成这样一份文件（这就是以后每次开会话 Agent 自动读的东西）：**

```
# bookmark-api — 项目说明书
```

> 这就是社区 `@init` / `codecartographer-pi` 这类包在自动做的事——你也可以直接装，或者干脆让 Pi 自己写一个（见第 03 篇"让 Pi 自己造"）。**一份文件换永久复用**：以后每次开会话，Agent 自动读它，不用重新摸索。

* * *

### 实战 3：用语义搜索补 grep 的不足（带真实查询）

有时候你想找的是"意思相关、但措辞不同"的代码，grep 关键字搜不到。比如你隐约记得"有个地方会把书签导出成 HTML 文件"，但函数名可能叫 `export`、`download`、`serialize` 任何一个，grep `export` 会淹没在一堆 `export const` 里。

这时用语义搜索。社区 `@artale/pi-codebase-map` 用 TF-IDF 给代码建索引，零依赖，“比 grep 聪明一点”：

```
pi install npm:@artale/pi-codebase-map
```

装完后你这样问（自然语言）：

```
哪个文件负责把书签导出成 HTML？给我文件路径和那段的行号范围。
```

它大致会回：

```
最相关：src/services/exportService.ts:34-52  （函数 renderHtmlBookmarks，把书签列表序列化成 HTML 书签格式）
```

> 适合"我记得要干嘛、但不知道函数名叫啥"的场景。注意它是 TF-IDF 不是真·语义模型，**复杂查询还是得靠实战 1 的 Trace**，它更适合快速定位。

* * *

### 实战 4：先自己猜，再让 Agent 验证（别当甩手掌柜）

super-productivity 有个反直觉但高效的建议：

> “Before asking AI about unfamiliar code, spend 5 minutes forming your own hypothesis. Then check with AI. This builds the mental model that makes you fast.”  
>  （问 AI 陌生代码前，先花 5 分钟自己形成一个假设，再用 AI 去验证。这能建立让你变快的心理模型。）

具体这么做。打开仓库先扫一眼目录结构，**自己猜**：

```
我猜：这是个三层架构（routes → controllers → services），入口在 src/index.ts，
```

然后让 Agent 证实/证伪：

```
我猜这个项目是 routes→controllers→services 三层架构，入口在 src/index.ts，
```

> **为什么这步不能省**：你主动猜的过程，大脑在建立"钩子"，Agent 的纠正会挂到这些钩子上，记得特别牢。直接读答案则像看一遍就忘。**先猜后验，比直接问快。**

* * *

## 五、小结 & 避坑

*   **要地图不要列表**
    
    ：好的 onboarding 给你主流程 + 危险点 + 下一步该读啥。
    
*   **套五问**
    
    ：Map → Trace → Tests → Uncertainties → Questions。
    
*   **只信能追溯到文件+行号的结论**
    
    ：指不到的当幻觉删掉。
    
*   **沉淀成 AGENTS.md 并提交**
    
    ：一次梳理，永久复用。
    
*   **先自己猜，再用 Agent 验证**
    
    ：建立你自己的心智模型，别当甩手掌柜。

## 164. Pi实战 12：TDD 测试驱动篇——用 Pi 做测试驱动开发 164. Pi实战 12：TDD 测试驱动篇——用 Pi 做测试驱动开发

## Pi实战 12：TDD 测试驱动篇——用 Pi 做测试驱动开发

> 来源：Daniel Weinmann、Marcos Lobo、tweag《Agentic Coding Handbook》、VS Code TDD 指南，以及 Martin Fowler 对"Agent 循环内 TDD"的质疑（保持客观）。

* * *

## 一、使用场景

*   让 Agent 加新功能，结果它悄悄改了旧行为还没人发现。
    
*   改完不敢动，怕回退，因为没测试兜底。
    
*   想要"Agent 写的代码至少行为是对的"，而不是靠人眼 review 每一行。
    
*   想有一个清晰的"完成"标准，而不是一句"改好了"。
    

## 二、能解决什么问题

TDD（测试驱动开发）给 Agent 一个**不会骗人的验收标准**：先写一个会失败的测试（定义"什么算对"），再让 Agent 写代码把它跑绿。

它顺带解决两件别的事：

*   **逼你澄清需求**
    
    ：写测试的过程就是想把"这段代码到底该干嘛"讲清楚的过程。
    
*   **给后续重构兜底**
    
    ：有测试在，你（和 Agent）以后改代码才有安全感。
    

## 三、解决思路

### 思路 1：红 - 绿 - 重构的最小循环

经典 TDD 三步，对 Agent 一样适用：

```
1. Red    —— 写一个会失败的测试（此时功能还没实现）
```

tweag 的《Agentic Coding Handbook》点出它和 Agent 特别搭：

> “It keeps you in flow: Tests give you checkpoints. Instead of stopping to debug a vague output, you just write the next test and let the AI catch up.  
>  It reinforces clean, behavioral thinking: TDD forces you to describe what the code should do, not how to write it. That’s exactly how we should prompt LLMs.”  
>  （测试给你检查点，让你保持心流：不用停下来调试模糊的输出，写下一个测试让 AI 追上就行。它还强化"行为化"思维：TDD 逼你描述代码**该做什么**，而不是**怎么写**——而这正是我们该给 LLM 的提示方式。）

### 思路 2：你写验收测试，Agent 负责实现

Marcos Lobo 的极简工作流（最适合起步）：

```
1. 你写验收测试（acceptance tests）
```

### 思路 3：把"完成"定义死

Daniel Weinmann 的 Definition of Done，直接写进 `AGENTS.md`：

```
- TDD is non-negotiable. Always write the tests first and ensure they fail before implementing.
```

翻译：

*   **TDD 不可商量**
    
    ：永远先写测试、确认它失败，再实现；小步快跑红-绿-重构。
    
*   **整个项目 linter 没过 = 没完成。**
*   **有新行为却没对应测试 = 没完成。**

## 四、如何实战

### 实战 0（手把手）：从零走一遍"红 - 绿 - 重构"

前面讲的都是概念。下面用一段**能直接复制、能真跑**的例子，把整个循环从头走一遍。我们用 Python + pytest（最直观，换成 JS/Go/Java 逻辑一模一样）。

**场景**：写一个"购物车结算"函数 `calculate_total(items)`，规则是"各商品 price×qty 求和，满 100 减 10"。

**准备**（一次就好）：

```
mkdir tdd-demo && cd tdd-demo
```

下面每一步，我们都**先写测试 → 跑测试看它红 → 写最少代码 → 跑测试看它绿**。命令统一用 `pytest -q`（`-q` 表示安静模式，红的绿的很清楚）。

* * *

**第 1 步：写第一个测试（空购物车 = 0）**

`test_cart.py`：

```
from cart import calculate_total
```

跑：

```
$ pytest -q
```

输出是**红**的，因为 `calculate_total` 还不存在：

```
E   ImportError: cannot import name 'calculate_total' from 'cart'
```

> **白话**：测试一跑就红，这正是我们想要的。它证明"这个测试真的在测东西"——如果这时候它就绿了，反而说明测试没测到点上。**先确认它会失败**，是 TDD 的第一铁律。

* * *

**第 2 步：写"最蠢"的代码让它绿**

`cart.py`：

```
def calculate_total(items):
```

跑 `pytest -q` → **绿**。

> **白话**：别笑 `return 0` 太蠢。TDD 的精髓就是**先迈最小的一步**：现在框架通了、函数名对了、空购物车这个用例过了。这一步的价值是"确认地基没问题"，不是"写出完整逻辑"。

* * *

**第 3 步：加第二个测试（一件商品）**

在 `test_cart.py` 追加：

```
def test_single_item():
```

跑 `pytest -q` → 又**红**了（`return 0` 不等于 20）。

> **白话**：新测试红是正常的、是好事——说明它在真正干活，逼着我们往下写。

* * *

**第 4 步：让实现"刚好"满足所有测试**

`cart.py`：

```
def calculate_total(items):
```

跑 `pytest -q` → **全绿**。

> **白话**：这段逻辑是**被测试一步步逼出来的**，不是凭空拍的。这就是 TDD 的核心体验——“测试告诉你要写什么，你只写让测试过的那一点”。

* * *

**第 5 步：加"满减"测试（满 100 减 10）**

`test_cart.py` 追加：

```
def test_discount_over_100():
```

跑 `pytest -q` → **红**（现在算出 120，不是 110）。

> **白话**：这个失败精准地告诉你"满减规则还没实现"，而且只告诉你这一件事。

* * *

**第 6 步：补上满减逻辑**

`cart.py`：

```
def calculate_total(items):
```

跑 `pytest -q` → **全绿**。功能齐了。

* * *

**第 7 步：重构（不改变行为，只让代码更干净）**

回头看代码：`100`、`10` 这种"魔术数字"埋在代码里，别人看不懂规则。把它们提成常量：

`cart.py`：

```
DISCOUNT_THRESHOLD = 100   # 满减门槛
```

跑 `pytest -q` → **还是全绿**。

> **白话**：重构**不改任何行为**，只是让代码更好读。为什么敢放心改？因为有测试兜底——万一改坏了，`pytest` 立刻变红提醒你。这就是测试给重构提供的"安全感"。

* * *

**这一遍走下来你得到了什么？**

每一步都被测试推着走，最后的代码是**被一整串测试证明过**的。以后谁想改 `calculate_total`，只要不跑绿测试，就不算改完——这就是给 Agent（和人）的"不会骗人的验收标准"。

### 实战 1：把上面交给 Pi，用 checkbox 计划驱动它

看懂循环后，就可以让 Pi 自己跑了。把刚才那套写成带勾选框的 TDD 计划丢给它，它会一项项"先测试后实现"：

```
# TDD Plan: 购物车结算 calculate_total
```

> 关键：让 Pi **“每步都跑测试并贴结果给我看”**，你只当那个"看红了没、绿了没"的人。

### 实战 2：分步下指令——把红/绿/重构拆成三步

不想一次给一整份计划，也可以对 Pi **分三次**下指令，逼它一次只干一件事（这是最不容易跑偏的用法）：

```
第 1 句：先只写「空购物车返回 0」和「单件商品返回 price×qty」这两个失败测试，
```

> 一次只让它做"写测试 / 写实现 / 重构"中的一件，比一句话"用 TDD 帮我加个功能"稳得多——后者它经常假装在做 TDD，其实一把梭。

### 实战 3：先审测试，再让它写实现（human-in-the-loop）

最稳妥的一道保险：**让 Pi 先把测试写给你看，你点头了它再写实现**：

```
你先只写测试，把测试代码贴给我。
```

> 这样即使 Pi 理解偏了，也只会偏在"测试"这一层（改几行测试就行），不会连带写出一大坨错的实现让你返工。**在测试层拦跑偏，比在实现层拦省力得多。**

* * *

## 五、一个必须告诉你的争议（保持客观）

TDD 在 Agent 循环里**是不是真有价值，社区是有争论的**，别把它当圣经。

Martin Fowler 在 2026 年的文章里坦率地说：

> “I personally have stopped telling my coding agents to write tests first, let alone do TDD… until I see evals or other strong arguments that convince me otherwise. I’m trying to focus instead on the benefits of TDD when I use it outside the agent loop.”  
>  （我个人已经不再让我的编码 Agent"先写测试"了，更别提完整做 TDD——除非我看到 evals 或其他强有力的证据。我现在更关注在**Agent 循环之外**用 TDD 带来的好处。）

**怎么理解这个分歧**：

*   **在 Agent 循环内**
    
    强制每一步都红-绿-重构，可能是"仪式感大于价值"（theater），甚至拖慢它。
    
*   **在 Agent 循环外**
    
    ，TDD 的价值很实在：**你**用测试当验收标准、当重构安全网、当回归测试——让 Agent 跑你的测试，看它有没有破坏既有行为。
    

**给你的可操作结论**：

*   不必迷信"每一步都严格 TDD"。
    
*   **至少做到**
    
    ：新行为要有测试覆盖（Daniel 的 Definition of Done）、用既有测试 suite 当 Agent 的回归护栏。
    
*   想让 Agent "写测试优先"时，用 checkbox 计划 + 先审测试再实现，最稳。
    

* * *

## 六、小结 & 避坑

*   **红-绿-重构**
    
    是最小循环；测试是给 Agent 的"不会骗人的验收标准"。
    
*   **最简起步**
    
    ：你写验收测试 → Agent 实现 → 你 review → 迭代。
    
*   **定义死"完成"**
    
    ：linter 没过 / 新行为无测试 = 没完成。
    
*   **先审测试再实现**
    
    ：在测试层拦跑偏，比拦实现更省力。
    
*   **别迷信循环内 TDD**
    
    ：Fowler 已不再强制 Agent 每步 TDD；把测试当循环外的验收/回归护栏更实在。

## Skill 1：impeccable —— 让 Pi 做的 UI 不像"AI 写的"

**何时用**：让 Pi 写前端，它永远给你一堆能跑但"一眼 AI 味"的界面——配色靠默认、层级糊成一团、组件长得都一样。你想要真正的设计决策，而不是"好看点"这种空话。

**安装**（Pi 原生适配，带 `/impeccable` 命令）：

```
pi install npm:pi-impeccable-skill
```

装完 `/reload`。它本质是调用 impeccable 引擎（23 条设计命令 + 一个能扫反模式的检测器）。

**实战（照做）**：

第一步，先让它"读懂"你项目的审美基线——扫一遍 token、组件、Tailwind 配置，写进 `PRODUCT.md`：

```
/impeccable init
```

第二步，拿一个真实组件让它按设计原则打磨：

```
/impeccable polish src/components/PricingCard.tsx
```

第三步（可选），扫整个 `src/` 揪 AI 味反模式：

```
/impeccable audit src/
```

**预期你会看到什么**（示意）：

```
/impeccable audit src/ 跑完，报告 7 处问题：
```

然后你 `/impeccable polish src/components/Hero.tsx`，它会照着上面那套 token 和原则重写，而不是另起炉灶。

**几个常用命令**：`/impeccable shape <目标>`（定结构）、`/impeccable craft <目标>`（从零造）、`/impeccable critique <目标>`（评审）、`/impeccable simplify <目标>`（精简）。命令行还能 `npx impeccable detect src/` 接进 CI，合并前拦"AI slop"。

## Skill 2：mattpocock/skills —— grill-me → tdd → implement（逼你想清楚再写）

**何时用**：你提一句"给我加个活跃会话接口"，Pi 秒回"好的"就开始写，结果做歪了才发现你俩对"活跃"的定义都不一样。这套技能把"先对齐、再测试、后实现"固化成三个斜杠命令。

**安装**：

```
npx skills@latest add mattpocock/skills -a pi -g
```

**实战（三连招，这是它的精髓，单用任何一个都浪费）**：

**① 需求还模糊时，先 `/grill-me`。** 它不让 Pi 动手，反而让它**反过来问你**，直到把设计的每个分支问清，并记录答案：

```
/grill-me 我要加 GET /users/:id/active-sessions
```

它大概会这样追问（示意）：

```
/grill-me 启动。在写代码前，先确认几件事：
```

**② 对齐后，`/tdd` 进入测试驱动。** 它把实现拆成竖向切片，红-绿-重构，每步先写失败测试：

```
/tdd 实现 active-sessions 查询，先写"未登录返回 401"的失败测试
```

**③ 最后 `/implement` 收口。** 指向你们对齐好的 spec/ticket，test-first 写码、边写边 typecheck、跑完 `/code-review` 再 commit 到当前分支：

```
/implement 上面的 spec
```

**注意**：这套技能**以"你主动调"为主**——Matt 故意不让它们自动触发。所以别等 Pi 自己用，该 `/grill-me` 时就敲。它解决的核心问题是：“Pi 听懂了你要的词，却还是做错了东西”。

## Skill 3：Anthropic webapp-testing —— 把 Pi 变成 QA 工程师

**何时用**：你写了个本地 web app / 前端页面，想真·开浏览器点一遍验证，而不是让 Pi “我觉得应该没问题”。它用 Playwright 开真实浏览器、导航、截图、读 console 日志。

**安装**：

```
npx skills add anthropics/skills --skill webapp-testing
```

**前置**（它要真开浏览器）：

```
pip install playwright && playwright install
```

**实战（照做）**：

先起你的服务，比如一个静态页：

```
python -m http.server 8000
```

然后给 Pi 一个明确的验证任务：

```
用 webapp-testing skill 验证登录流程：
```

**预期你会看到什么**：Pi 先判断"这是静态 HTML 还是动态 app"，然后写一段 Playwright 脚本（`page.goto` → `page.fill` → `page.click` → 截图 → 断言），跑起来，最后给你一份带失败截图的报告，比如"步骤 2 没看到错误提示，实际 DOM 里是空的"。

**注意**：它自带一套决策树（静态 HTML 直接读文件找 selector；动态 app 先导航等 `networkidle` 再动手）， helper 脚本在 `scripts/` 里（`with_server.py` 等）。第一次用先 `page.wait_for_selector` 这类稳一点。

## 166. Pi实战 14：树状会话历史篇——会话的“版本控制“ 166. Pi实战 14：树状会话历史篇——会话的“版本控制“

原文：https://mp.weixin.qq.com/s?__biz=MzkwOTAxOTY4Nw==&mid=2247485366&idx=1&sn=82c3a63c347079e0804dd8e775026128&chksm=c0c058fef7b7d1e81495c8479d3b0c9f04b546dd5abc8c565b993aaca7db7af66bc27813d744

> 来源：Pi 官方《Sessions》文档、社区关于 `/tree` 上下文管理的实践（StackToHeap、developersdigest）、以及 Pi 会话的内部数据结构分析。

第 04 篇把"会话树"当作多代理经验之一提了一句。这篇专门深挖它——因为**树状会话历史很可能是 Pi 最被低估的能力**：它让你像用 git 一样对待对话，可分支、可回退、可分享，是管理上下文窗口的核心手段。

本文按你要的三块展开：**使用场景 → 实现原理 → 实战例子**，中间穿插命令速查。

* * *

## 一、使用场景：什么时候该用它

普通聊天是**一条直线**，说错一句只能 `/undo` 一步步回，或者 `/new` 全丢。Pi 的会话是**一棵树**，这带来几个真实痛点的全部解法：

**场景 1：Agent 跑偏进死胡同。** 它改着一改着把你带沟里了，越改越乱。你不需要 `/undo` 连按十几次，直接 `/tree` 跳回最后一个"还算正常"的点，从那儿重走。

**场景 2：同一套上下文，试多个方案。** 重构一个模块，想分别试"保守重构 / 激进重写 / 只抽函数"三种。每种都开新会话要重新喂一遍上下文；用树的话，在同一个点分三个叉，**互不污染**，最后挑一个。

**场景 3：一系列相似任务共享同一上下文。** 先加载一个技能 + 需求，跑一次 `/grill-me` 把意图对齐，之后每个子任务都从这点对齐好的状态分支出去执行（“Do A”、“Do B”、“Do C”），不用重复前置对话。

**场景 4：噪声探索不污染主线。** 你想让 Agent 放手去试（翻日志、跑实验、走死胡同），但又不想让这些噪声塞满主线的上下文。分支出去探索，把结论**落成文件**，然后跳回主线继续——主线始终干净。

**场景 5：一个会话内模拟"角色分离"。** 开一个"分析分支"做调研、一个"实现分支"写代码，类似子代理的分工，但全在一个会话文件里，切换零成本。

**场景 6：分享 / 另起。** 把整条会话回退到某点、分支、**分享给别人**；或从旧会话的某个状态 `fork` 出一个全新任务。

一句话心智模型（StackToHeap 总结得很准）：**Pi 的会话是一棵树，不是一条时间线。** 想清楚这点，用法就通了。

* * *

## 二、实现原理：它凭什么能"版本控制"

**1\. 会话存成一个 JSONL 文件，每条记录是一棵树的节点。**

路径在 `~/.pi/agent/sessions/<org>/<repo>/_.jsonl`（按工作目录组织，一个会话一个文件）。文件里每条 entry 有 `id` 和 `parentId`——这就是"树"的来源：**追加式（append-only）树**，不是线性列表。

**2\. 一个"叶子指针"（leafId）跟踪你当前在树的哪个位置。**

*   **追加**
    
    一条消息 = 给当前 leaf 生一个子节点。
    
*   **分支**
    
     = 把 leaf 指针移到更早的某个节点上，**但不改动任何历史**。你接着发的下一条消息，就成了那个旧节点的一个**新子节点**——于是旧的延续和新的延续变成**兄弟分支**。
    

**3\. 组装模型上下文时，从 leaf 一路走回 root。**

`buildSessionContext()` 从当前 leaf 回溯到根，把路径上的消息拼成数组喂给模型。结果：**只有你当前所在的激活分支在上下文里，但所有分支都完整保留在文件中。** 这就是"切换分支 = 切换上下文"的机制。

**4\. 分支摘要（branch\_summary）——带走要点，不带 token。**

用 `/tree` 从一条分支切到另一条时，Pi 可以**把离开的那条分支总结成一段摘要**，附到新位置上。你带走的是"我刚才试过啥、结论是啥"，而不是整条分支的 token 细节。

**5\. Compaction（压缩）也是非破坏的。**

压缩时 Pi 不是删旧消息，而是 **append 一个 summary entry**，只在"组装未来上下文"时才用它替换掉那段老历史。原历史仍在文件里。

**6\. 节点类型不止对话。**

一条 entry 可能是：`user` / `assistant` / `tool`（工具调用）/ `model_change` / `thinking_level_change` / `compaction` / `branch_summary` / `label`（你打的书签）/ `custom`（扩展状态，**不进**模型上下文）/ `custom_message`（扩展注入、**会进**模型上下文）/ `session_info`（会话名）。

**7\. 版本演进。** v1 是线性的，v2 引入树，v3 把 `hookMessage` 改名 `custom`；旧会话加载时自动迁移。

**一张图看懂分支**（在某个点 `/tree` 后试了 approach B）：

```
session root
```

你在 `try approach B` 这条线上时，`continue with A` 那条完全不受影响；随时 `/tree` 跳回 `approach A` 继续。

## 四、`/tree` 里怎么操作

敲 `/tree`（或连按两次 `Esc`）打开会话树导航器：

*   **方向键**
    
    上下移动选择节点。
    
*   **Shift+L**
    
     给当前节点打 label（书签）；**Shift+T** 切换 label 上是否显示时间戳。
    
*   **Ctrl+O**
    
     循环过滤模式：default / no-tools（隐藏工具调用）/ user-only / labeled-only（只看打了书签的）/ all。
    
*   选中一个 **user 消息**：leaf 移到它的**父节点**，并把这句话**丢进输入框**让你改——你一改重发，就**新建了一个分支**。
    
*   选中 **assistant / tool 条目**：leaf 移到那，从该点**继续**。
    

> 关键细节：在 `/tree` 里选 user 消息时，你是回到"它发出之前"，所以重发会生成分支；选 assistant/tool 则是"接着它的结果"继续。两者都是新建分支，**原历史一字不改**。

## 五、实战例子

### 实战 1：最小场景——跑偏了跳回去

```
你: 把这个函数的错误处理重写下
```

重发的瞬间，一条新分支诞生；原来那三轮混乱留在旁边，随时能回看。

### 实战 2：同一上下文试 3 个重构方案

```
你: 重构 auth 模块，先别动代码，给三个方案
```

比起开三个新会话各自重新喂"auth 模块背景 + 三方案"，这里前置对话只发生一次。

### 实战 3：噪声探索不污染主线（推荐工作流）

想大胆试错但保持主线干净，照 StackToHeap 这套 5 步：

```
1. /tree 到（或就在）主线某点，分支出去
```

主线上下文里永远只有"干净的决策 + 结论文件路径"，没有大段试错过程。

### 实战 4：分支摘要 + 分享会话

长会话切分支时，Pi 提示要不要给离开的分支做摘要，选**是**：

```
你: /tree   → 切到另一分支
```

之后把整条会话 `/share` 给别人；对方拿到的是带分支结构、且关键岔路有摘要的完整历史，不是流水账。

### 实战 5：命令行 fork——从旧会话另起任务

不必进交互模式，直接从一个历史会话 fork：

```
# 先看有哪些会话（带名字/消息数/目录）
```

适合"上次那个会话的状态我还想要，但要朝新方向走、且不想动原会话"。

## 六、避坑

*   **分支 ≠ 改历史。**
    
     跳回旧节点再发消息，建的是**新分支**，原分支一字不改。别指望它"覆盖"过去。
    
*   **当前上下文只含激活分支。**`/tree`
    
     跳走后，上一条分支的内容不在模型上下文里了——需要的话靠 branch\_summary 带过来，或探索前先落盘。
    
*   **探索结论一定要落成文件。**
    
     否则跳回主线后，那条分支的产出就"看不见"了（它还在文件里，但不在上下文里，Agent 也不会主动读）。
    
*   **`/fork` 和 `/clone` 别混。**`/fork`
    
     从历史某点起新文件；`/clone` 复制**当前这条**激活分支。
    
*   **会话文件就是 JSONL。**
    
     删文件 = 删会话；在 `/resume` 里按 `Ctrl+D` 删除，Pi 会优先用 `trash` CLI（如果装了）而不是直接永久删。
    
*   **给会话起名。**
    
     用 `/name` 或 `pi --name`，否则 `/resume` 里一堆无标题会话很难找。

## Pi实战 15：分析代码 & 写代码的利器——插件/技能工具箱

> 来源：Pi 官方 Packages/Skills 文档、pi-code-graph / @vndv/pi-codegraph / @gaodes/pi-graphify / @artale/pi-test-gen / @leing2021/super-pi / safe-coder 等包的官方页，以及 Awesome Pi 精选集。

Pi 自带只有四个工具：`read`、`write`、`edit`、`bash`。想让它更会**读懂代码**、更会**生成代码**，靠的就是装 package / skill。这篇把真正好用的东西分成两类——**分析代码**（读懂）和**写代码**（生成 / 测试 / 工作流），每个给：装什么、干什么、何时用、怎么用。

和前面两篇的分工：第 11 篇讲"上手陌生代码库"的工作流，提到了 `@artale/pi-codebase-map`、`codecartographer-pi`（后者本篇 **二、4** 有详细安装与用法）；第 13 篇讲了 `mattpocock`、`addyosmani`。这篇聚焦它们**之外**、更重型的分析/生成利器，已覆盖的只做索引。

## 二、分析代码：把代码"读懂"的利器

这类工具给代码建**索引 / 知识图谱**，让 Pi 能结构性搜索、追调用链、看架构、做影响分析——比 grep 聪明，还不烧 token。

### 1\. pi-code-graph —— 多语言知识图谱（功能最全）

**装**：

```
pi install npm:pi-code-graph
```

**干什么**：用 tree-sitter（WASM 解析，无需原生编译）把代码解析成语法节点，存进图数据库（Memgraph 或 Neo4j）+ 向量库（zvec），支持**语义搜索 + 结构搜索**。

**支持语言**：Python / TypeScript / JavaScript / Java / Rust / Go / C++ / C# / PHP。

**怎么用**：

```
/cgs setup      # 首次向导：启动 Memgraph 容器、配 LLM、索引当前仓库
```

**例子**：

```
你: 找出处理邮箱校验的代码
```

**注意**：**默认只读**——Agent 能查图但不能改图，索引要显式开（`/cgs setup` 或设 `CGR_ALLOW_INDEX=true`）。它要起一个 Memgraph Docker 容器，**有环境成本**，适合正经的多语言项目。

### 2\. @vndv/pi-codegraph —— 轻量版（基于 codegraph CLI）

**装**（比 pi-code-graph 轻，不自带图数据库，依赖外部 CLI）：

```
npm install -g @colbymchenry/codegraph   # 先装底层 CLI（Node ≥ 22.19）
```

**工具**：`codegraph_search` / `codegraph_callers`（谁调用它）/ `codegraph_callees`（它调谁）/ `codegraph_impact`（改动影响面）/ `codegraph_explore` / `codegraph_status`。

**例子**：

```
你: Use CodeGraph. Show project structure and main entry points.
```

**pi-code-graph vs @vndv/pi-codegraph 怎么选**：要**全功能自带图库**、能接受 Docker → pi-code-graph；要**轻量、靠外部 CLI** → @vndv。

### 3\. @gaodes/pi-graphify —— 出架构图 / 调用流 / 最短路径

**装**：

```
pi install npm:@gaodes/pi-graphify
```

**怎么用**（`/graphify` 一条命令玩转）：

```
/graphify <path> --graphml     # 导出 GraphML（给 Gephi/yEd）
```

**两个变体怎么选**：

Graphify

GitNexus

擅长

“这个系统由什么组成？”（架构/概念/文档）

“谁调这个、改了会坏哪？”（符号/调用图/执行流）

触发

概览、架构文件

代码改动、符号查询、提交前影响分析

### 4\. codecartographer-pi —— 把陌生代码库逆向成"可重建规格书"

前面几个工具的目标是"搜得到、看得懂"；`codecartographer-pi` 的目标更进一步——**把一个陌生仓库压成一份语言无关、带证据标注、可据此重新实现的规格书**（reimplementation spec），还能把确认过的模块规格合成为带溯源的实现计划。适合接手遗留系统、做迁移/重写、或给另一个 agent 交接。

**装**（Pi 扩展是推荐用法，带 slash 命令、实时子代理进度widget 和 HTML 看板）：

```
pi install npm:codecartographer-pi            # 从 npm
```

> 别用 `npm install codecartographer-pi`——那只是把包落到磁盘，不会注册进 Pi。要用 `pi install npm:...`。

**干什么**：它把分析做成一条**分阶段、每阶段带验证门禁**的流水线，前一阶段不 PASS 就不会进下一阶段。产物是 `.codecarto/findings/` 下一系列带证据标签（`观察事实 / 强推断 / 可移植隐患 / 外部行为声明 / 未决问题`）的 Markdown + YAML，而不是聊天记录：

```
源码 → 架构地图 → 行为契约 + 协议 + 缺陷扫描
```

阶段是个 DAG：`architecture` 之后 `contracts` 与 `protocols` 可并行，`porting` 等它俩，`reimplementation-spec` 收尾。

**怎么用**（Pi 下典型流程）：

```
/codecarto-init            # 把 .codecarto/ 框架拷进当前仓库，选流水线变体
```

其它常用命令：`/codecarto-vision`（引导式产品愿景访谈，为"合成"流水线产 `inputs/vision.md`）、`/codecarto-open`（在新会话里复用已有 `.codecarto/` 而不重置状态）、`/codecarto-publish`（把规格书发布到可复用库）、`/codecarto-guide [主题]`（把代理指南读进会话，无需工作区）。

**跨代理**：它也提供 MCP server（`codecarto-mcp`），Claude Code / Cursor / Codex / Claude Desktop 等任何 MCP 代理都能驱动——在宿主配置里加 `"command": "codecarto-mcp"` 即可，阶段提示与验证和 Pi 路径字节一致（但子代理、widget、看板是 Pi 独占）。

**注意**：这是**重型、烧 token** 的工具——官方自测完整流水线要几十 M token、几十分钟、数百次工具调用。它靠"文件系统即记忆"：每阶段把更小的模板化产物写进 `.codecarto/`，新会话或上下文压缩后读 `status.yaml` 就能续跑，不靠对话上下文硬记整次调查。**项目小、只想搜一搜就用上面几个轻量的；要"吃透并产出可交付规格"才上它。**

### 5\. 轻量语义搜索（已在第 11 篇）

`@artale/pi-codebase-map`（TF-IDF 建索引，零依赖，“比 grep 聪明一点”）——**见 11 · 上手陌生代码库篇**，项目小、只想语义搜一下的话这两个最省事。

> 想把**整个陌生代码库**逆向成一份可据此重建的规格书（而不是只搜一搜），那是 `codecartographer-pi` 的活儿——一个更重型的"考古 + 出规格"引擎，见上面 **4**（第 11 篇只把它当"自动写 onboarding 文档"的例子提了一句，没展开）。

**四类怎么选**：

## 三、写代码：生成 / 测试 / 工作流的利器

### 1\. @artale/pi-test-gen —— 从代码自动生成测试

**装**：

```
pi install npm:@artale/pi-test-gen
```

**干什么**：AI 分析代码，自动补测试。

**怎么用**：

```
pi test-gen all            # 给所有 src 文件生成测试
```

**注意**：AI 生成的测试**要先审再跑**——它会猜你的测试框架和断言风格，生成的用例是起点不是终点。

### 2\. @leing2021/super-pi —— 完整工程工作流（想 → 计划 → 做 → 审 → 学）

**装**：

```
pi install npm:@leing2021/super-pi
```

**干什么**：把"别急着写，先想清楚"固化成一整条流水线，自带工具链：

阶段

做什么

核心工具

01-brainstorm

结构化多轮需求发现，沉淀领域词汇

`brainstorm_dialog`

02-plan

TDD 门禁的实现单元，可选 CEO 评审

`plan_diff`

03-work

行内执行、断点续跑、严格 TDD、叫停机制

`session_checkpoint`

、`task_splitter`

04-review

自动分派评审、六轴发现（标准 + 规格）、自动修复环

`review_router`

05-learn

知识复利

—

用法：跑完一个阶段它会推荐下一个，按提示 `/skill:06-next` 继续。核心理念一句话：**“80% 规划与评审，20% 执行”——目标不是让 AI 写得更快，而是让它写前先想、写后复审。**

### 3\. addyosmani/agent-skills —— 24 个工程技能全家桶（已在第 13 篇）

覆盖规划、规格、实现、测试、调试、代码审查、安全、Git、性能、架构、可观测性、API、数据库等 24 个环节。**见 13 · 技能实战篇**，想"一站式配齐"就装它。

### 4\. pi-green-loop —— 保持构建为绿

**干什么**：一个**多语言**（Node / Python / Go / Rust / Make）、**只跑受影响测试**的反馈环——AI 改完代码，它自动跑相关测试并把失败喂回去，直到构建变绿。可当 CLI、MCP server、扩展用。适合"让 Agent 改代码后自己把测试跑通"的闭环。

### 5\. safe-coder —— 写代码的安全护栏

**装**：

```
pi install npm:safe-coder
```

**干什么**：Pi 写代码时手很重（`rm -rf`、`sudo`、`chmod 777`、乱改 `.env` / `.git/` 都不眨眼）。safe-coder 带两个扩展：**permission-gate**（给危险命令加执行闸门）+ **protected-paths**（保护 `.env`、`node_modules/`、`.git/` 等路径不被 write/edit）。让 Pi 敢放手写、又不会一把梭搞坏环境。

## 四、实战组合：读 + 写一条龙

一个真实流程把上面的串起来：

```
1. pi install npm:pi-code-graph && pi install npm:safe-coder
```

主线思路：**先用图谱读懂 → 用工作流规划 → 写的时候上护栏和绿构建 → 最后补测试。**

* * *

## 五、避坑

*   **索引类"先索引再查"。**
    
     pi-code-graph / codegraph / graphify 都要先建索引才能问；而且**默认只读**（多代理环境里保证图稳定），别奇怪为什么查得到却改不了。
    
*   **图谱质量取决于代码质量。**
    
     命名乱、职责不清的代码，生成的图也一样乱——它呈现已存在的结构，不发明不存在的结构。
    
*   **AI 生成的测试 / 代码要审。**
    
     test-gen、super-pi 的产出是"高质量起点"，不是免检。
    
*   **重型包有环境成本。**
    
     pi-code-graph 要 Docker + 图数据库；小项目用 `@artale/pi-codebase-map` 或 `@vndv` 就够了，别杀鸡用牛刀。
    
*   **装前看源码。**
    
     包能执行代码、影响 Agent 行为——第三方包先审再装（这条对所有 package 通用）。

## 169. Pi实战 16：addyosmani/agent-skills——给 Agent 装上资深工程师的本能 169. Pi实战 16：addyosmani/agent-skills——给 Agent 装上资深工程师的本能

> 来源：Addy Osmani 官方博客（addyosmani.com）、技能集官网（skills.addy.ie）、GitHub 仓库，以及 Pi 官方 Skills 文档。第 13、15 篇只提了它一句，这篇专门深挖。

Addy Osmani（Google Chrome 资深工程师）对这套技能有一句很准的概括：

> **资深工程师的活儿，大部分是那些"不会出现在 diff 里"的东西**——规格、测试、评审、范围克制、拒绝交付无法验证的东西。而 AI 编码 Agent 默认会跳过这些。

`addyosmani/agent-skills` 就是把这套"资深本能"固化成 Agent 会照做的工作流。它覆盖从第一个想法到上线的完整软件生命周期，MIT 许可，一条命令装进 70+ 种 Agent（含 Pi）。

* * *

## 一、它解决什么问题

你让 Pi 做个功能，它往往直接开写，然后：没想清楚需求、没写测试、不复审、顺手把范围越扩越大。`agent-skills` 的价值不在"让 Agent 写得更快"，而在**把质量门禁变成必走流程**：

*   **规格先行**
    
    ：写代码前先定"要做什么、不做什么"。
    
*   **测试即证明**
    
    ：行为靠测试证明，不是靠"我觉得没问题"。
    
*   **评审把关**
    
    ：合并前按固定维度审，而不是走马观花。
    
*   **范围克制**
    
    ：小步、竖向切片，而不是一次性糊一大坨。
    
*   **安全上线**
    
    ：上线前有 checklist、灰度、回滚。
    

它有个很关键的设计值得单独拿出来说：**渐进式披露 + 元技能路由**。它不是一次把 20 多个技能全塞进上下文（那会拖慢、污染模型），而是靠一个 meta-skill（`using-agent-skills`）当路由器，**当前任务匹配哪个，才加载哪个**。Addy 明确说：“别在会话开始时把 20 个技能都加载进上下文，按阶段激活。”

> 数量说明：这套技能在迭代，早期资料写"20 个核心技能"，官网最新口径是"**24 个技能覆盖整个 SDLC**"（核心工作流 + 一组专家评审角色 + 元技能）。下面按生命周期分组列，不必纠结精确数字。

* * *

简化代码，清晰胜于炫技

`/ship`

Ship

安全上线，快也要稳

* * *

## 三、如何安装（Pi）

**先浏览、再决定装哪些**（Addy 本人不建议无脑全装）：

```
npx skills add addyosmani/agent-skills --list   # 先看有哪些技能
```

**整包全局装**（所有项目可用）：

```
npx skills add addyosmani/agent-skills -a pi -g
```

**只装某几个**（推荐，按名字或 `@名字`）：

```
npx skills add addyosmani/agent-skills --skill spec-driven-development
```

装完在 Pi 里 `/reload` 生效。`-a pi` 指定装给 Pi，`-g` 全局，去掉 `-g` 则只装当前项目。

> 加迪的取舍建议（来自他的博客）：`spec-driven-development`、`test-driven-development`、`code-review-and-quality` 这三个就能修好 AI 编码工作流的大部分问题；然后按项目再挑 `frontend-ui-engineering`、`api-and-interface-design`、`debugging-and-error-recovery`、`security-and-hardening`、`performance-optimization`。**别让一个项目背上全部技能。**

* * *

## 四、如何使用（三种方式）

**方式 1：直接敲斜杠命令。** 最直接。比如需求一来先 `/spec`，而不是一句"帮我做 X"就让 Pi 开写。

**方式 2：自然语言触发，元技能自动路由。** 你说"帮我规划一下这个功能"“上线前帮我过一遍”，`using-agent-skills` 会判断该激活哪个技能。装好后这些描述会自动匹配。

**方式 3：不装，当规范读。** Addy 说哪怕你一个都不装，这些技能本身就是"用 AI Agent 做好工程的规范说明书"。直接读 `code-review-and-quality` 的五轴框架，拿去当团队的评审标准；读 `test-driven-development`，用它平息"要不要先写测试"的争论。

* * *

## 五、实战例子

下面用一个连贯场景串起来：**给一个电商后台加"导出订单为 CSV"功能**。

### 实战 1：`/spec`——规格先行

```
你: /spec 给订单后台加"导出 CSV"功能
```

Pi 按 spec-driven-development 产出一份 PRD（示意）：

```
## 目标
```

**关键**：这一步没写一行代码，但把"做什么、不做什么"钉死了——这正是 Agent 默认会跳过的。

### 实战 2：`/plan` + `/build`——拆任务、增量实现

```
你: /plan
```

### 实战 3：`/test`——测试即证明

```
你: /test
```

### 实战 4：`/review`——五轴评审

```
你: /review
```

这就是 `code-review-and-quality` 的价值——它**强制**走五个维度，而不是让 Agent 泛泛说"看起来不错"。

### 实战 5：`/ship`——四个专家并行会诊

```
你: /ship
```

### 实战 6：`/code-simplify`——缩小 diff

```
你: /code-simplify
```

### 完整串联

```
/spec → /plan → /build → /test → /review → /code-simplify → /ship
```

一条线下来，就是把"资深工程师那些不体现在 diff 里的活儿"补全的过程。

## 六、避坑

*   **别一次全装进上下文。**
    
     靠元技能按需路由；真要全装，也明白这会占上下文、拖慢模型。
    
*   **选装 > 全装。**
    
     Addy 自己一个项目也只挑核心几个。用 `--skill` 按需装。
    
*   **它是工作流，不是 prompt。**
    
     让它按步骤走（先 spec、再 build、后 review），别当成"一句话咒语"。
    
*   **专家角色是 `/ship` 自动调的。**
    
     不用自己手动跑四个评审。
    
*   **数量口径会变。**
    
     20→24 是仓库迭代，按阶段理解即可，别被数字卡住。
    
*   **第三种用法别忽略。**
    
     哪怕不装，把这些 `.md` 当工程规范读，也能立刻提升团队评审/测试标准。

## 二、路线 A：`pi-code` 一体化（推荐先试）

如果你想**最省事**地接近 Claude Code，甚至你本来就有 Claude Code 项目，先装这个。

**装**：

```
pi install npm:pi-code
```

**它一次干两件事**：

1.  **读你现有的 `.claude/` 配置**
    
    ——rules、commands、skills、hooks、输出样式、MCP servers、agents 全部复用。你从 Claude Code 迁过来，配置几乎零成本。
    
2.  **补上 Pi 缺的 Claude Code 能力**
    
    ——to-do 覆盖层、checkpoints、记忆、web 搜索、子代理、goals。
    

**典型用法**：

```
cd 你那个带 .claude/ 的项目
```

之后你在 Claude Code 里那套规则、斜杠命令、技能，在 Pi 里照样生效。

**一个加分项**：它在安全上比 Claude 更严——Claude 的 `claude -p` 头次运行从不弹信任框、照样加载项目的 hooks/MCP；pi-code 在无存储决策、无 UI 可问的头次运行时会**拒绝加载**这些。否则任何 CI 拉一下仓库就能自己跑 hooks/MCP，没人能拦。

> 提醒：`pi-code` 是个大包，具体命令/用法以它加载后的提示为准；想精细控制每个能力，走路线 B。

## 四、配置全流程（从零到能用）

### 1\. 装 Pi + 认证

```
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
```

### 2\. 配模型

```
vim ~/.pi/agent/models.json
```

Pi 不挑模型——Claude、GPT、Gemini、GLM、Kimi、本地 Ollama 都能接。**注意**：Claude 模型在 Pi 上走 **API 计费**（Anthropic 已禁止第三方 agent 用订阅），见第六节。

### 3\. 装扩展 + 热重载

```
pi install npm:pi-permission-system
```

### 4\. 配权限（最关键的一步）

Pi 默认 bash 完全放开，**务必**装权限系统并配 `permissions.jsonc`：

```
# 全局：~/.pi/agent/permissions.jsonc
```

一份可直接改的配置（`allow` / `ask` / `deny` 三态）：

```
{
```

效果：`read` 全放、`.ssh`/`.gnupg` 禁写、`rm -rf` 直接拦、`sudo`/`dropdb` 弹窗问你。

### 5\. 写项目约束

Pi 读 `AGENTS.md`，也兼容 `CLAUDE.md`——把你希望它遵守的约定、规范、禁忌写进去。用 `pi-code` 的话，直接把 `.claude/` 带过来即可。

### 6\. 配沙箱（危险项目必做）

光有权限闸门不够（它"尽量"拦，不是铜墙铁壁）。敏感项目把 agent 关进沙箱：

```
# 沙箱配置（可选，给 sandbox 类扩展用）
```

沙箱强度从内置 `sandbox` 扩展 → Gondolin 微 VM → Docker → Bubblewrap，按需挑一层（详见 05 · 本地模型 · MCP · 安全沙箱篇）。

pi install npm:pi-code                 # 一体化体验 + 复用 .claude/
```

## 六、避坑（几句真话）

*   **默认等于 `--dangerously-skip-permissions`。**
    
     Pi 的 bash 天生无限制，权限扩展只是"尽量拦"。强烈建议：危险活在**沙箱或独立 VM** 里跑，别裸跑。
    
*   **Claude 要花钱。**
    
     Anthropic 已禁止第三方 agent 用 Claude 订阅，Pi 上用 Claude 走 API 计费。这也是很多人"**Claude Code 做日常、Pi 做深度定制**"双修的原因。
    
*   **别一次装太满。**
    
     每多一个扩展就多一份上下文和复杂度，按需加。
    
*   **Pi 的强项是可定制，不是开箱即用。**
    
     想要"边缘都打磨好"的 universal 产品，它还没到；想要"完全按我想法捏"，它无敌——缺什么功能，装不到就**让 Pi 自己写一个扩展**（这是它的招牌能力）。
    
*   **`.claude/` 是迁移红利。**
    
     你已有的 Claude Code 投资（规则、命令、技能）不会被浪费，`pi-code` 直接读。
