# 架构拆解：DeepSeek 刚发布的 Super-agent

> 来源：<https://mp.weixin.qq.com/s/cxfdWtDRfVunY5FU75oQGA>（微信公众号「架构师 JiaGouX」文章抓取正文）

就在昨晚，DeepSeek 产品部发布了《Super-agent 设计探索：迈向更自主的 Agent 系统》，并公开了研究原型。

这次的设计，可能得从一个挺熟悉的麻烦讲起：Agent 能同时改几个需求了，人却可能比以前更忙。

一个窗口在跑测试，一个在等评审，另一个需要补充条件。群里有人追加了要求，GitHub 又来了 CI 失败的通知。情况和变化越来越多，代码有人写，消息还需要人来转达，进度依然需要我们来询问。

DeepSeek 这次尝试把跨渠道的交互与协调留在 Router 层，把具体任务交给多个 Worker 并行执行，再用事件和持久记录，让中间停下来的工作能够继续。

读完设计文章，再沿着公开原型的代码看下来，作者认为这套架构值得拆的地方就在这里：**上下文需要连贯，执行需要分开；任务中途停了，两者的联系还得保留。**

公开的 `dsh-superagent-prototype` 是研究原型，仓库明确说明，它与内部版本、设计文章并不完全一致，文章中的部分方向尚未实现。

## 一、群里提的问题，到了 PR 里还得有人认得

假设群里有人反馈："新版本导出的文件打不开。"

Agent 复现问题、修改代码、提交 PR。评审者在 GitHub 上要求补一个兼容性测试，随后 CI 又报错。过了一会儿，最初提问的人回到群里，补充说只有旧版客户端受影响。

我们知道这一直是同一件事，系统却未必知道。群聊消息、评审评论、CI 结果来自不同入口。如果每个入口只有自己的聊天会话，人还是得找回原来的窗口，再解释一遍：这条消息说的就是刚才那个问题。

把消息全塞进同一个会话，来龙去脉容易接上，但修复、评审、其他需求会挤在同一个执行循环里，互相打断。每来一条消息就新开会话，并行是方便了，刚补充的旧版客户端限制，又可能到不了正在改代码的那个会话。

Super-agent 用两层分工来处理这个矛盾：

- **Router 层**：维护跨渠道的上下文，判断新消息要不要处理、交给谁，并统一组织对外沟通。
- **Worker 层**：在独立会话里执行具体任务，读取代码、运行工具，向 Router 汇报进展与结果。

兼容性测试该怎么写，留给 Worker 处理。修复比较复杂时，它还可以再用子 Agent 或 Agent Team。这里的两层说的是职责，各层内部仍然可以有自己的分工。几个 Worker 的上下文隔开了，共享文件、分支和写入顺序仍要另外协调。

这套分工底下，用的还是 DeepSeek Harness（DSH）。公开原型作为它的插件运行，Router 和 Worker 都是 DSH 会话，只是各自的提示词、工具和职责不同。会话的创建、恢复和输入投递，继续调用 DSH 的接口。

DSH 已经能保存会话、恢复子 Agent。这次对照的版本里，实验性 Agent Teams 还支持持久成员和共享任务板，消息也能唤醒未加载的成员。拿这项修复来说，**DSH 负责让执行接得上，Super-agent 则记录这次执行属于哪项工作、与哪些讨论有关。** 评审者在 PR 里说"还要补一个测试"，系统据此找到原来的修复任务，再交给执行会话。对方不必先找到 Agent 的聊天窗口。

若每条 CI 通知、每句评审意见都要让 Router 重新理解、再转交，这个负责协调的会话仍会越来越忙。

## 二、消息多了，Router 会不会先忙不过来？

设计文章把单条环境事件称为 Trigger，把同一个话题或同一个 PR 下的连续事件称为 Thread。

群聊和代码平台里的消息，大部分并不需要 Agent 动手。来源、群组、用户或机器人是否在允许范围内，可以先用程序检查，需要理解语义的候选事件再交给模型判断。

首次发现一项新工作时，Router 判断并分派。Worker 随后订阅相关 Thread，同一条事件流里的后续消息就由程序直接送过去，无须每次请模型重新决定归属。

回到导出缺陷，修复任务可以同时关注群聊话题和自己的 PR。评审意见沿 PR 的订阅送达，旧版客户端的补充沿群聊话题送达，两边都能回到这项修复。同一个讨论也可能与几项工作有关，订阅并不限于一对一。原型在唤醒执行器前，还会检查是人的跟进还是机器人消息、任务是否已经结束。

Router 仍可读取事件与任务记录，了解全局情况，只是不用亲自转发每次往返。模型判断出的关系，变成了程序可以持续使用的投递依据。

但群里同时冒出十个新问题，就无法全靠已有订阅分流了。对这些仍需判断归属的消息，设计采用了批处理：**Router 上一轮推理期间积压的事件，会合并到下一轮一起处理。**

消息稀疏时，来一条处理一条；集中到达时，一次推理可以做出多个分派决定。这样做是否划算，要看合并以后增加了多少耗时。Router 主要读上下文、输出简短决定，输入预处理（Prefill）有并行计算的空间，所以多读几条事件，耗时未必同比例增加。

团队单独测了这部分：Router 调用真实模型，Worker 使用模拟模型。需要决定的事件从每分钟约 1 条增加到约 40 条时，平均批次从 1.0 条变成 2.8 条，单次模型请求耗时从 2.5 秒增加到 3.9 秒。至少在这组 Router 压测里，合并处理确实分摊了一部分推理开销。

不过，单次请求更划算，每条消息却未必更快。它仍可能排队等上一轮结束；上下文窗口能装多少、模型一轮能准确处理多少条，也限制着批次大小。

再往上扩，就涉及 Router 的水平切分了。多个 Router 可以提高并发，但怎样拆会影响它们各自知道什么。假设按渠道拆，群聊里的兼容性要求和 PR 评审就可能落到不同 Router，两边又得关联任务、同步条件。把同一任务的输入留在一起，能减少这类往返；跨任务的共享信息仍需要协调。

保留一个 Router，前后发生的事比较容易放在一起理解；拆成多个 Router，就得多付一份同步上下文的成本。过滤、订阅和批处理让单 Router 在这组负载下够用，更大规模怎样分片、怎样维持共享记忆，原文还没有定论。

## 三、执行可以停，Ticket 还在

这里就用到了公开原型中的 Ticket。群聊话题和 PR 是两个 Thread，Ticket 把它们与同一项修复关联起来，保存输入和派工记录。

这项修复可能做几轮：Assignment 记录这轮由谁执行，Executor Session 承载模型和工具调用，Mandate 留下接单的依据和范围。几轮执行都挂在同一个 Ticket 下。

代码写好、PR 已提交，执行器报告 `ready`，就可以先释放执行名额，等评审意见到了再继续。Ticket 和订阅仍然保留，原型会跟踪关联 PR，按关闭、合并及后续跟进的规则判断任务何时结束。Worker 这轮忙完了，修复这件事还没完。

`Store` 用 SQLite 保存事件、任务关系、接单决定、待执行动作和消息发送状态。恢复时，DSH 的会话日志让执行器接上之前的交互，这些任务记录则告诉系统：它在等哪个 PR，还有什么动作没做。

但写进数据库，还没等于事情已经做了。系统可能刚决定接单，就在启动 Worker 前退出。原型的 `Engine` 因此先把任务、授权依据、派工和待执行动作放进同一笔事务，提交后再启动执行器、投递输入或发送消息。

这样重启以后，数据库里仍能查到等待启动的动作。如果发送消息失败，`Effects` 队列会记录失败并退避重试，`Outbox` 保存发送状态。

这里仍有一个容易出错的地方：平台已经收到消息，而本地尚未来得及记下成功，重试就可能重复发送。对于运行中断的任务，原型也会给新的 Assignment 加上恢复提示，让执行器先检查目录、Git 历史和 GitHub，再决定是否重做外部操作。数据库能保存进度，已经发生在外部的事还得核实。

人隔天回来问进度时，模型也不必一次读完全部历史。设计文章提出 Inline & Spill：先提供近期相关的信息、摘要和对象 ID，长内容留在窗口外，按需读取。链式召回让模型顺着消息、Thread、Worker 等对象的引用，逐步找回关联内容。

比如旧版客户端的限制留在群聊里，后续修改就需要沿着这些引用找回那条补充。记录留在数据库中，还得在需要的时候读到它，否则模型仍可能按旧条件继续改。

## 四、持续跟进，也包括知道什么时候等人

等几小时评审，把执行名额先让给其他工作，很合算。但评审意见到了，还得重新排队；新任务不断进来，旧任务照样可能等很久。

原型的 `WorkerSlots` 为此做了一个小安排：人的跟进可以使用普通并发上限之外的一个额外名额，唤醒已有工作的优先级也高于启动新工作。后台批量开工时，人的补充不用一直排在新任务后面；额外名额用满后，仍然需要等待。

等待也会发生在一次执行内部。兼容性测试跑了很久，群里这时又补充一个条件，前台若一直等测试返回，就迟迟无法处理新消息。

这里涉及设计文章里的异步 ReAct Loop：启动后台工作后先返回，结果以后作为事件进入会话，前台继续接收消息。团队称相关机制已在 DeepSeek Harness 实现，但尚未默认开启。群里的新要求可以及时进来，已经发出的命令却不会因此自动撤销，后续仍要处理两者的冲突。

能及时收到消息以后，还需要分清它是补充条件，还是一项新的请求。群里顺口提了另一个问题，是否也该立刻开始改？

这一步，原型先检查来源和身份，再按策略交给模型判断。系统从讨论里自行推断出来的任务，默认处于 `observe` 模式：记录本来会接下什么，先不启动执行。启用 `auto` 后，仍按预先写好的规则评估；人的明确请求另有处理路径。

Ticket 里的 Mandate 保存接单范围和依据。修复任务关注着整个群聊话题，可以读到新消息，但订阅本身不会扩大它的工作范围。

设计文章里"静默复现并修复"的例子，也有团队预先配置的策略：后台尝试，有可用结果再交付，否则保持安静。这个取舍挺贴近日常协作。每发现一个可能的问题就向整个群问一次，省下的操作时间，很可能又变成了更多消息。

同一项修复，在群里可能只需说清结果和待确认的问题，在 PR 里则需要交代改动、背景与验证过程。这些沟通由 Router 统一组织，Worker 的工具输出可以留在内部。

## 五、"一直在线"还需要执行环境配合

任务有了持久记录，仍然可能因为电脑休眠而停住。

设计文章进一步把三部分拆开：推进模型与工具循环的计算、持久保存的状态，以及代码仓库和工具链所在的执行环境。按这个设想，云端 Agent 通过端侧常驻进程访问用户机器，代码和工具链可以留在本地。

DeepSeek 在这里引用了 Anthropic 4 月公开的 Managed Agents 架构。Lance Martin 等作者把 Harness、持久会话日志和执行沙箱分开：运行 Harness 的进程可以替换，会话记录仍在，执行环境通过工具接口接入。DeepSeek 进一步考虑了日常开发机：上面可能有未提交的修改、内网依赖，而且会离线。

回到导出缺陷，能复现它的依赖、配置和修改可能都在那台开发机上。只搬一份代码到云端，未必能重建现场。计算与环境分开后，Agent 可以在云端继续运行，需要本地工具时再访问原来的环境。

但本地机器离线时，依赖那台机器的命令依然不能执行。云端可以继续保存任务、接收消息，等设备上线后再推进相应步骤。**系统在线、任务记得住、执行环境可用，需要分别成立。**

云端计算与跨设备执行是设计文章讨论的方向；公开原型目前展示的是 SQLite 保存本地任务状态等实现。

即使环境一直可用，修复也可能停在原地。Worker 持续输出消息，却迟迟没能复现缺陷，这种情况光看"正在运行"发现不了。设计因此安排了主系统之外的 Watchdog Session，定时观察 Worker 的报错、恢复异常，以及是否长期没有实质进展。主循环卡住时，它仍有机会发现问题并介入。

Simon Willison 今年 8 月的一则短文，把有效使用 Coding Agent 的关键概括为两部分：能够清楚地指导修改，也能够有把握地验证修改正确。Watchdog 可以帮助发现停滞；至于这项修复是否完成，还是要看兼容性测试有没有覆盖旧版客户端、PR 有没有解决最初的问题。另一个模型说"有进展"，还不足以回答这些问题。

## 六、实验先说明了调度收益

DeepSeek 给出的初步实验，每轮约 300 条消息，其中约 20 条是工作请求，每种方案运行 5 次。**编码工作用只消耗时间的工具代替，测的是调度与协作。**

Super-agent 的任务完成时间 p50 为 12.4 分钟、p95 为 15.7 分钟；中性提示下，单 Session 加 Subagent 工具的方案，p95 为 29.5 分钟。

不过，中性提示的 5 次运行里，模型一次都没调用 Subagent。改成优先委派的提示后，5 次里有 4 次进行了委派，完成时间随之缩短。

这几轮运行里，把分派交给 Router，并行工作更稳定地发生了。基线配了工具，模型却未必会用；要进一步比较架构，还得让它也稳定地用上并发委派。这里比较的是特定会话配置，不能据此判断 Super-agent 与完整 DSH 的优劣。

直通机制的收益则主要体现在开销。去掉直通后，任务完成时间基本一致，Router 决定次数增加约 30%，单次实验总读缓存 token 从 2323 万增加到 3177 万。

换算一下，无直通版本多读约 37% 的缓存 token；以它为基准，启用直通后则少读约 27%。这还不能直接换成费用降幅，其他输入、输出也要一起算。Super-agent 的总读缓存 token 仍高于单 Session，直通省下的是一部分重复协调。

任务完成时间为什么没明显变化？结合前面的 Router 压测，团队给出的解释是，这组负载还没把 Router 推到吞吐瓶颈。少做一些重复判断，先省在了推理开销上。要判断单 Router 何时需要拆分，也就得看过滤和订阅之后，还剩多少工作必须由它判断，不能只数入口一共来了多少消息。

回到开头那项修复，作者接下来更想看到的是：它跨过几轮评审、CI 和群内补充以后，能否交出验证过的改动，而人少做了几次转述、追问和重新解释。
