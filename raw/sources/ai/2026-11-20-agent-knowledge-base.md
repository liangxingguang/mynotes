# 一文搞懂 Agent 知识库：从 RAG 到 GraphRAG，从 LLM Wiki 到 Ontology

企业做 AI，最先遇到的问题通常是：**模型不知道公司的内部信息。**

于是大家接入知识库，用 RAG 从文档里找答案。后来发现，很多问题不只需要找到相关段落，还要看清业务对象之间的关系，于是 GraphRAG 开始受到关注。再往后，Agent 不只回答问题，还要调用工具、执行任务，企业就得继续追问：它理解的业务世界是什么？

这条路上出现了几种常被放在一起讨论的技术：RAG、GraphRAG、LLM Wiki 和 Ontology。它们都在帮助 AI 获取上下文，但解决的问题并不相同。

可以先用一句话把它们分开：

> **RAG 找相关知识，GraphRAG 找关系，LLM Wiki 整理可持续更新的知识，Ontology 定义业务对象、规则和关系语义。**

它们不是一代替代一代的产品清单，而是从“找到信息”逐步走向“理解业务上下文”的几种能力。

## 01 先从知识库的老问题说起

企业知识散落在 PDF、网页、会议纪要、产品手册、工单和各种内部系统里。模型即使很强，也不会天然知道这些内容。

最简单的办法是把资料交给模型，但资料一多，就会遇到上下文窗口、更新、权限和检索准确性等问题。更常见的做法是：在提问时先从知识库里找出相关内容，再把内容交给模型回答。

这就是 RAG 的基本思路。

## 02 RAG：让 AI 找到相关资料

RAG 通常会把文档切成较小的文本片段，计算向量表示并存入索引。用户提问时，系统检索相似片段，再把它们作为上下文交给模型。

它主要回答：

> **哪些资料和这个问题有关？**

例如，员工问“差旅报销需要哪些材料”，RAG 可以从制度文档中找出相关条款，再由模型组织答案。

RAG 的优势是能利用已有文档，不必把所有资料都塞进模型，也便于更新知识库。但它依赖资料本身：如果制度过期、文档缺失，或者问题需要跨多份资料进行复杂关联，检索到几段相似文本未必足够。

RAG 找到的是“可能相关的内容”，不是经过业务系统确认的当前状态。问“订单现在到哪一步了”，答案往往需要查实时业务数据，而不只是搜索旧文档。

## 03 GraphRAG：让 AI 沿着关系查找

有些问题需要的不是一段相关文字，而是一条关系链：

*   哪些订单受到某供应商延迟的影响？

*   某产品使用了哪些关键物料？

*   一项政策变化会影响哪些地区和客户？


传统 RAG 可以找出提到“供应商”“物料”或“订单”的段落，但要把分散内容连起来，往往还要模型自己推断。GraphRAG 则把实体和它们之间的关系纳入检索过程，帮助系统沿关系网络查找信息。

它主要回答：

> **这些对象之间有什么关系，问题会沿着哪些关系传播？**

例如，企业可以把“供应商—物料—产品—订单—客户”的关系组织起来。查询某供应商出现风险时，系统就能进一步定位它可能影响的物料、产品和订单。

GraphRAG 仍然主要在回答和检索层工作。它可以把关系讲清楚，却不一定能统一企业里的业务定义，也不一定知道企业当前的实时状态。

## 04 LLM Wiki：让知识能够持续整理和更新

RAG 与 GraphRAG 主要关心“提问时怎么找”。但知识库还有另一个难题：**知识怎么维护？**

很多组织的知识不是一份份互不相关的文档，而是需要不断整理的内容。新资料会补充旧结论，多个来源可能互相矛盾，项目中的决策和经验也会随着时间变化。

LLM Wiki 是一种把知识库做成“可维护的知识空间”的思路。它让系统从资料中提取主题、实体、关系和摘要，再持续整理、更新这些内容。用户查询时，可以使用整理后的知识，也可以回到原始资料核对依据。

它试图回答：

> **知识之间如何组织，哪些内容需要更新，结论依据是什么？**

不过，“LLM Wiki”不是一个边界完全统一的标准术语。不同实现可能只是用模型自动生成页面，也可能包含来源链接、版本更新、冲突处理和人工审核等机制。判断它是否有用，不能只看页面是否像维基百科，还要看知识是否能回到可信来源、是否能正确更新，以及错误如何被发现和修正。

## 05 Ontology：把企业业务世界定义清楚

当 AI 要回答复杂的业务问题，光有文档和关系还不够。系统还需要知道：

*   企业里有哪些业务对象？

*   这些对象有什么状态和属性？

*   对象之间是什么业务关系？

*   不同系统中的同名对象如何对应？

*   业务规则和指标采用什么定义？


这就进入了 Ontology，也就是企业本体或业务本体的范畴。

在企业系统里，Ontology 可以把客户、订单、产品、供应商、工厂等对象，以及它们之间的关系，用统一的业务语义表达出来。不同系统里名称各异、编码不同的记录，可以映射到共同的业务对象上。

Ontology 的关键不只是“对象和关系”，还在于这些对象和关系具有什么业务含义。以 Palantir 的 Ontology 为例，其概念包括 Objects、Properties 和 Links。对理解知识库而言，重点是它如何统一业务对象、关系和语义。

可以粗略地理解为：

> **Ontology 不只告诉 AI 企业里有什么，还定义这些东西在业务上意味着什么，以及它们之间如何关联。**

一个供应商、一张订单，在不同企业里的业务含义和处理规则可能不同。Ontology 要表达的正是这些与具体企业相关的定义。

## 06 把几种能力放在一起看

能力

主要回答

常见对象

RAG

哪些资料与问题相关？

文档、文本片段、检索结果

GraphRAG

对象之间有什么关系？

实体、关系、知识网络

LLM Wiki

知识如何整理、更新和追溯？

主题、摘要、来源、版本

Ontology

企业业务对象是什么，彼此如何关联？

对象、属性、关系、业务定义

它们可以组合使用。

企业可以用 RAG 搜索制度和流程文档，用 GraphRAG 分析跨对象的关系，用 LLM Wiki 持续整理知识，再用 Ontology 统一业务对象、关系和术语定义。

关键是不要把它们当成同一种“知识库”来选型。它们处理的信息形态和应用目标不同。

## 07 一个供应链例子

假设汽车制造企业发现一批订单可能延期。

RAG 可以先搜索延期处理规范、供应商通知和相关会议记录。GraphRAG 可以沿着“供应商—电池组件—车型—生产计划—订单”的关系，查出哪些产品和订单可能受影响。

如果企业有 LLM Wiki，它可以把已经确认的供应商情况、历史处置经验和相关资料整理起来，并保留来源，供后续查询和更新。

Ontology 则可以把供应商、物料、工厂、产线和订单映射成有业务含义的对象，并统一它们之间的关系和关键术语。Agent 据此结合库存、产能等当前数据，比较不同方案的成本、交付和风险，并说明建议依据。

在这个过程中，几种能力各自承担不同工作：

*   RAG 帮忙查文档。

*   GraphRAG 帮忙连关系。

*   LLM Wiki 帮忙整理可更新的知识。

*   Ontology 帮忙表达业务对象、关系和定义。

*   Agent 根据上下文组织分析并提出建议。


## 08 企业什么时候需要往这条路走？

并非每个知识库都需要 GraphRAG、LLM Wiki 或 Ontology。

如果需求是搜索几百份制度文档，RAG 可能已经足够。如果主要问题是从多份资料中追踪人物、事件或供应链关系，GraphRAG 值得评估。如果知识需要持续归纳、追溯和更新，可以考虑 LLM Wiki 一类的做法。

Ontology 通常更适合业务对象复杂、系统分散，而且 AI 需要跨系统理解业务语义的场景。特别是当“客户”“订单”“风险”等概念在不同部门或系统中含义不一致时，清晰的业务模型会变得重要。

评估时可以先从具体流程入手，而不是先决定“要不要上 Ontology”：

1.  业务对象和关系是否难以用现有系统表达？

2.  数据孤岛是否让关键决策依赖人工拼接？

3.  Agent 是否需要结合实时业务状态回答问题？

4.  不同系统中的同名对象是否代表同一业务实体？

5.  如何追踪定义、数据和结论的来源？


如果这些问题还没有明确答案，先把一个流程和它的对象、状态、规则梳理清楚，往往比先搭建一套很大的知识图谱更有价值。

## 结语：让 Agent 找到知识，并在业务语境中理解它

RAG 的核心是找到相关资料，GraphRAG 把关系纳入检索，LLM Wiki 关注知识如何持续整理，Ontology 则尝试把企业业务世界中的概念和关系表达成可供系统和 Agent 使用的模型。

这条演进线不是单向替代关系。企业仍然需要文档检索，也仍然需要关系分析和知识维护。随着 Agent 开始处理更复杂的业务问题，统一的对象定义、关系和术语会变得格外关键。

所以，企业做 Agent 知识库，真正需要回答的问题不只是：

> **AI 能不能找到答案？**

还包括：

> **它依据什么理解业务？不同系统里的对象如何对应？结论能否追溯到来源？**

从 RAG 到 GraphRAG，从 LLM Wiki 到 Ontology，变化的是知识库要承担的责任：从帮助 AI 找到信息，逐步走向让 AI 理解业务上下文。

真正值得关注的，不是再给知识库叠加多少新名词，而是让 Agent 找对知识、理解业务定义，并说清结论依据。
