# Pi 支持沙箱吗：从什么是沙箱，到 Pi 的两层隔离

**Pi 支持沙箱吗？支持——但没有一个叫 `--sandbox` 的开关。**

我翻过它的命令行参数：`--tools` 里可以开启某个代码执行扩展，但**没有任何沙箱开关**。原因不难理解：**隔离不是"启动时加个参数"的事**，它要么换**进程边界**（把 Pi 整个放进容器），要么换**工具后端**（让工具执行跑到别处去）。**这两件事改变的是"Pi 在哪跑"，而不是"Pi 怎么跑"。**

所以这篇分三步：**什么是沙箱 → 它靠什么原理起作用 → Pi 具体怎么用**。

（文中事实来自 Pi 官方文档与仓库源码，抓取时间 2026-10。）

## 三句话版本

1.  **沙箱不是"检查代码有没有坏心思"，而是"不让它有能力干坏事"**——核心动作是**收窄可达面**，不是审查行为；
    
2.  **实现路径有四条**：能力收窄的运行时、操作系统级限制、命名空间隔离（容器）、硬件虚拟化（虚拟机）——**越往下越强，也越贵**；
    
3.  **Pi 提供两层**：**脚本级**（写代码调工具时，脚本被关进"只有工具、没有操作系统"的环境）与**进程级**（五种做法，从容器到微虚拟机到"只给命令加限制"）；**而"哪些调用会真的进沙箱"，取决于你用的是哪一层**。
    

## 一、什么是沙箱

\*\*沙箱（sandbox）\*\*这个词来自游乐场的沙坑：**给你一块边界明确的沙地，你在里面怎么刨怎么堆都行，但出不去。**

搬到软件里，一句话：**给不可信的代码或输入划一块地方——在里面它想干什么都行，但碰不到不该碰的东西。**

有两点必须说清，否则很容易用错：

**第一，沙箱的本质是"能力限制"，不是"行为审查"。** 它不判断你做的事对错，**它只是让你没有那个能力**。装了沙箱的系统里，恶意代码依然可以"试图"删你的文件——**只是它找不到、或者删不动**。这和"扫描代码、发现危险动作再拦住"是两条路：**前者靠环境，后者靠识别；识别会漏，环境不会漏。**

**第二，它保证的是"影响范围"，不是"绝对安全"。** 沙箱里跑的东西**依然会影响你主动暴露给它的资源**——你把文件夹挂进去，它就能改里面。**"在沙箱里就安全了"是句危险的话**，正确的说法是：**"沙箱把风险压缩到了我暴露的那一小块。"**

> **一句话小结**：**沙箱 = 有边界的自由**——它不审查你想干什么，它只决定**你能碰到什么**。

## 二、沙箱靠什么起作用：四条实现路径

不管产品怎么包装，实现基本落在这四条路上（从弱到强）：**① 能力收窄的运行时**——换一个"什么都没给"的环境，只暴露允许的能力（精简脚本引擎、受限解释器）；**② 操作系统级限制**——用系统自带机制限制能读写的路径与能访问的网络（macOS 的 `sandbox-exec`、Linux 的 `bubblewrap`）；**③ 命名空间与资源隔离**——让进程"以为自己是全世界"（容器）；**④ 硬件虚拟化**——边界由 CPU 提供（虚拟机、微虚拟机）。

**强弱关系很清楚**：① 最轻、几乎不影响体验，但能力最窄；④ 最重、要付启动与内存成本，但边界最硬。**而它们的共同动作只有一个：减少可达面**——可达的文件、可连的网络、可用的凭据、能启动的进程。**理解了"可达面"这一个词，就理解了所有沙箱。**

> **一句话小结**：**沙箱的实现千差万别，落点只有一个词：可达面**——少一个入口，就少一类风险。

## 三、沙箱到底换来了什么

四样东西：**限制可达面**（看不见、碰不到、连不上——这是"让 AI 自己动手"的前提）；**限制影响范围**（里面的改动默认不是你的真实环境，写坏了丢掉重建）；**让试错变便宜**（AI 干活最贵的不是算力，是"错了要回滚"）；**让结果可复现可审计**（环境是声明出来的，同一套配置跑出同一类结果——这是做评测和回归的基础）。

**四样里最被低估的是第三条**：**沙箱把"错了"的代价压到接近零，并行、重试、多方案对比才成为常规操作。**

> **一句话小结**：**沙箱换来的是"敢用"**——敢让它动、敢让它试、搞坏了可以扔。

## 四、Pi 的默认姿势：默认不沙箱，按需开

先说清现状：**Pi 默认不在沙箱里跑**——工具直接以启动它的那个账号的权限工作。**官方立场很硬，值得原样记住**：**"把模型生成的命令和代码当作不可信。"……"看会话、用项目信任、审阅改动，都不构成安全边界。"** 安全来自**限制它可访问和影响的文件、凭据、进程与网络**；而\*\*"整个跑在容器、虚拟机或沙箱里，通常是实践中最强的选项"\*\*。

**它没有沙箱开关，但把该有的挂点都留出来了**：工具可以替换、可以包装、可以拦截输入；进程可以整体放进容器；扩展可以自己实现隔离。

> **一句话小结**：**Pi 不替你决定隔离到什么程度**——默认设在"就在你机器上跑"，同时把每一层都留好了挂点。

**为什么必须是"一次性"的？** 因为隔离改变的不是"某一次调用怎么跑"，而是\*\*"进程在哪跑、工具后端是什么"**——这类决定只能在**部署期或加载期\*\*做。而"每次都要再声明"这条路，Pi 是有明确态度的：**用户命令的拦截器一旦出错，它直接阻断该命令**（fail-closed），而不是"当作没拦到、继续执行"。**同一个思路——安全不能建立在"记得"上。**

**三个容易被当成"沙箱"的东西，其实都不是**：**项目信任**（管的是"启动时加载哪些项目资源"，**明确不限制工具访问**）、**默认工具列表**（那是"有哪些能力"，不是"这些能力被关在哪"）、**看 diff / 看会话 / 逐步批准**（官方原话：**不构成安全边界**）。

**一个实用判断法：看边界由谁提供。** 由**运行环境**提供（容器/虚拟机）→ Pi 里无需声明；由**扩展**提供（命令沙箱、工具隔离）→ **加载即声明**；由**语言运行时**提供（脚本沙箱）→ **用它就自动带上**。

> **一句话小结**：**沙箱要么在部署时声明、要么在加载扩展时声明，但绝不该靠"每次记得说明"。**

**三个必须记住的认知坑**：

*   **坑一：以为脚本沙箱保护了工具。** 不是——**脚本不能自己读文件、连网络，但它在脚本里调一次命令工具，那条命令照样以宿主权限执行**；
    
*   **坑二：以为"命令沙箱"等于全工具沙箱。** 它的名字很诚实，**只覆盖命令**——装了它之后，模型仍然可以用写文件工具覆盖你项目里的任何文件；
    
*   **坑三：以为"只隔离工具"能保护整台机器。** 那两个扩展方案里，**宿主上的 Pi 进程、以及不用隔离后端的扩展工具，都还在外面**。
    

**所以三层是可以叠加的（而且叠加才有意义）**：**脚本层**限制"能碰到哪些工具"，**命令层**限制"工具执行时能碰到什么"，**整体层**才限制"所有东西"。**想让模型触发的所有动作都在边界里，只有整体隔离一条路**——因为**唯一能把扩展工具、MCP 工具、子进程一起关进去的，是把整个 Pi 关进去。**

> **一句话小结**：**"进了沙箱"这四个字必须补全主语**——是脚本进了、某个工具进了、还是整个进程进了？**主语不同，保护的东西完全不同。**

## 七、第一层：脚本级沙箱（"只有一个工具的宇宙"）

Pi 内置了一个代码执行扩展：**模型不逐个发工具调用，而是写一小段 JavaScript 去调工具。** 这段脚本跑在一个被剥干净的环境里：**没有文件系统、没有网络、没有进程、没有环境变量**——它唯一能碰的东西，是**被注册进来的那些工具**。

它属于四条路径里的第一条：**能力收窄**。脚本当然可以"试图"读你的私钥，但**它的世界里没有"读文件"这个动作**。它还顺手把边界写进了契约：**输出有出口清单**（只能用指定的展示函数、控制台或返回值）；**有限额**（可声明输出上限与超时，超长输出保留首尾、完整内容落临时文件）；**失败保留部分输出并指路**（早期只陈述错误，现在会告诉你怎么改）。

**代价也清楚**：**它能做的事的上限就是那些工具**——**适合编排和过滤，不适合跑通用程序。**

> **一句话小结**：**最小攻击面的做法是"不给"，不是"拦着"**——这一层之所以小，是因为它的世界里压根没有系统调用。

> **一句话小结**：**五种做法其实是三种立场**——整个进程包起来、只把工具挪走、只给命令加限制；**立场不同，保护面和成本都不同。**

## 九、隔离的真正边界：你暴露什么，它就能碰什么

官方文档里最实在的一段，是**它自己列出的漏洞**：**读写挂载**（挂进去就能改）；**挂载代理目录**（等于把凭据、设置、扩展、会话一起交出去）；**环境变量**（传进容器的变量，容器里的进程就能读到）；**网络**（有网络，代码或工具输出就可能离开这个环境）；以及\*\*"只隔离工具"的局限\*\*（宿主上的进程与不使用隔离后端的扩展完全不受约束）。对应的建议就一句：**只暴露任务真正需要的东西，能只读就别可写，能拷进拷出就别直接挂。**

还有一条边界值得记住：**评测这套能力的人自己承认**——因为模型访问本身需要网络，**所以"跑在容器里"无法证明 agent 写的任意代码从不使用网络**。**能说清自己的边界，比多一层防护更难得。**

> **一句话小结**：**隔离不是"装上就安全"，而是"你暴露多少，它就能碰多少"。**
