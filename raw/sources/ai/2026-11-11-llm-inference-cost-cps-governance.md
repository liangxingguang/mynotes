## LLM 推理成本治理：从 Token 单价到每个合格交付的真实成本

> 面向多租户 LLM Gateway、Agent Runtime 与 AI 平台工程团队

> 阅读对象：负责模型路由、Agent Runtime、LLM FinOps 或多租户 AI 平台的工程与技术管理人员
> 
> 适用范围：本文讨论按量调用与自托管推理的成本治理方法，不构成任何供应商报价、性能或合规承诺。除明确标注的官方文档外，文中的价格、实验结果和阈值均为合成示例，读者应以自身合同、区域和服务版本为准。

把代码审查助手切到小模型后，单次请求的账单可能更低；但在复杂 diff 上，它可能漏掉关键问题，继而触发补拉上下文、工具重试与大模型复核。调用报表显示成本下降，业务却可能为每一份真正合格的审查结果支付更多费用。

因此，成本治理不应优化“每次调用多少钱”，而应在既定的质量、时延、安全与交付合同下，优化 **每个合格交付的成本**（Cost per Successful Task，CPS）。这要求把供应商用量、工具、运行时、重试、人工与验收结果放进同一套可审计的账本和实验框架。

假设两条策略处理同一批 1,000 个任务：大模型直达花费 90 美元、成功 900 个；小模型优先花费 76 美元、成功 700 个。平均提交任务成本从 0.090 美元降至 0.076 美元，但 CPS 从 0.100 美元升至约 0.109 美元，成功率还下降 20 个百分点。本文以代码审查为例说明如何从供应商计量走到生产发布决策。除外部价目表说明外，示例数据均为合成数据。

## 读者先看：四个结论

1.  1. **先守质量，再谈降本。** 只有在成功定义、验收版本、风险边界与时延目标相同的前提下，CPS 才具有比较意义。
    
2.  2. **成本必须归到任务。** Token、工具、重试、升级、生产校验和退款调整都应进入同一可审计账本；只看单次模型调用必然失真。
    
3.  3. **预算不是一个数字，而是一套状态机。** 预留、发送、结算、用量缺失、超额与退款要有明确的幂等和恢复语义，才不会在并发下失效。
    
4.  4. **发布以统计门禁为准。** 候选策略应先证明关键质量指标非劣，再证明 CPS、P95 延迟和安全边界达到预设目标。

一项策略只有同时满足交付质量、合规边界、预算与时延目标，才有资格比较成本。成本低但质量不达标的路径不是“更优”，而是不可用。

对于按量 API，价目表至少以 `provider`、计费账户或合同、模型及版本、区域、服务档位和生效时间为键。价格还可能取决于用量分档、Batch、长上下文与合同折扣。每个计费操作保存实际使用的 `price_version`；供应商账单到达后用独立差额事件回补，而不是重写历史事件，从而保证历史可重算。

自托管模型的边际成本、分摊成本与整池支出应分开报告：前者服务路由决策，后者服务租户报表，整池支出服务容量决策。可先固定计算池与 KV Cache 池的预算比例，再分别按 GPU 工作时间和缓存字节秒分配，避免两套权重分别分摊完整 GPU 账单。闲置支出必须单列，或按已公开的预留容量规则分摊。

建议同时公布直接交付 CPS 与全成本 CPS，并在每张报表上写清成本范围、分摊规则和成功定义。两种口径必须使用同一任务队列与同一验收版本，不能以不同分母制造“降本”。

## 2｜调用计量：把 Token、缓存、工具统一为可审计费用

原始供应商 usage 应原样保存，再归一化为互斥计费桶。若输入总量已包含缓存读取，则普通输入应扣除缓存部分；若供应商分别返回普通输入、缓存创建与缓存读取，则直接映射。推理 Token 若已包含在输出计费量中，只能计一次。缺失、未知、零值与估算值必须由不同状态表达，不能将缺失默认成零。

以每百万 Token 计价，一次模型调用的费用可写为：

```
model_cost = (input_uncached × p_input            + input_cache_write × p_write            + input_cache_read × p_read            + output_billable × p_output) / 1_000_000           + fixed_request_fee
```

例如，普通输入 3,000、缓存读取 7,000、输出 800；报价分别为 3、0.3、15 美元/百万 Token，则模型费用是 0.0231 美元。若再执行两次各 0.004 美元的搜索，直接费用为 0.0311 美元。工具返回内容传回模型后产生的 Token 已在模型输入中计费；`tool_result_tokens` 可用于解释上下文膨胀，但不是另一笔模型成本。

### 缓存必须按净收益而不是命中率决策

以下盈亏平衡只比较同一段稳定共享前缀；动态后缀、最小缓存长度、失败写入和额外工具输入仍按普通输入另计。设该前缀普通输入一次成本为 `P`，首次缓存写入为 `wP`，后续读取为 `rP`。实际命中 `n` 次时：

```
cache_cost  = P × (w + n × r)normal_cost = P × (1 + n)严格省钱条件：n > (w - 1) / (1 - r)，其中 r < 1
```

例如某短 TTL 价型 `w=1.25, r=0.1`，一次实际命中即可回本；若 `w=2`，至少需两次命中。线上统计应按模型、区域、档位、TTL、前缀版本和真实复用间隔拆分，分别报告冷启动成本、写入失败、TTL 失效与净节省。不能用“缓存命中率”替代节省金额。

输出成本可通过结构化结果、逐步输出上限和推理档位控制；工具成本通常更适合从源头压缩：分页、字段投影、去重、停止条件和工具结果摘要。可离线交付的任务再评估 Batch，但必须将折扣、等待时限和失败重投一起纳入成本。

### 调整、退款与负向金额

供应商折扣回溯、退款、纠错和未用量回补不应覆盖原始流水。应追加带 `adjustment_type`、`reference_event_id`、金额符号与原因码的调整事件。报表同时给出 `gross_cost`、`credits` 与 `net_cost`；预算规则须明确是否允许信用释放额度，以及释放发生在供应商确认时还是财务结算时。这样既能对账，也能避免退款被误当成一笔新的负成本调用。

供应商对账按账户、账单周期、SKU、币种与税费范围对齐，持续跟踪已归属、未归属、暂估、调整与差额。若只能获取聚合账单，必须保留分摊依据、未分配余额和置信状态，不能把估算伪装成实际用量。

策略比较以任务首次分配的 `policy_id` 分组；小模型失败后升级产生的全部成本仍留在原策略组。一个成功任务不得同时记给两个模型后再汇总。

下面是 PostgreSQL 事务边界的参考伪代码。预算行维护 `spent`、`held` 与 `limit_amount`；所有事务固定先锁租户预算行，再锁任务预算行，以降低死锁风险。

```
reserve(operation_id, upper_bound, period_id):  BEGIN  lock tenant_budget(period_id), then task_budget(task_id)  if reservation(operation_id) exists:      return existing reservation after verifying request fingerprint  require spent + held + upper_bound <= limit_amount on both rows  insert reservation(operation_id, period_id, upper_bound, state=RESERVED)  add upper_bound to held on both rows  COMMITsettle(operation_id, source_event_id, actual):  BEGIN  lock original budget rows in the same order, then reservation  if source_event_id already posted: return existing result  require reservation is eligible for settlement  append immutable ledger entry; mark reservation SETTLED  subtract reserved amount from held; add actual to spent  insert outbox event  COMMIT
```

数据库提交后才发送供应商请求。发送前以条件更新将 `RESERVED` 改为 `DISPATCHING`，仅状态转换获胜者可发送。预留后崩溃与发送成功但响应丢失是不同故障：前者确认未发送后释放；后者转为 `PENDING_USAGE` 并继续占用额度，等待供应商查询、账单回补或保守暂估。若上游支持幂等键，恢复时复用同一键；若不支持，在未确认状态下允许重发时必须新建操作并重新预留。

“硬上限”必须精确定义。若上游能强制执行输出 Token、工具次数和单请求费用上限，则可实现**事前执行硬上限**。若真实费用可超过预留或工具费用无法预先封顶，只能实现**事后财务上限**：照实记账、阻止后续预留并记录超额风险，而不能承诺零超支。账期由首次预留固定，跨月返回仍结算原预算行；供应商账期另存用于财务对账。

Redis 可承担 RPM、TPM 与并发控制，但货币预留必须由具备事务和故障恢复语义的持久存储负责。固定窗口的键携带窗口起始时间，首次设置过期；每次刷新 TTL 会悄然改变窗口语义。

## 5｜路由、缓存与降级：在质量约束内选择最低成本路径

代码审查可用 diff 行数、涉及模块、跨文件、事务修改、并发路径、敏感目录与历史失败率分层。先排除不满足能力、数据边界、上下文窗口和预算的模型，再在剩余候选中比较预期总成本。

若小模型失败后允许升级，升级概率为 `q`：

```
E[cost] = route_cost + small_cost + q × E[escalation_cost | escalation]CPS ≈ E[cost] / P(task_success)
```

估计必须来自全链路样本。升级概率由生产校验与业务规则决定；未被校验器发现的错误仍计为潜在失败，需要以独立标注或人工抽样测量。复杂任务低于质量门槛时，应先验证大模型直达能否减少重复上下文和尾延迟，而非继续堆叠廉价模型调用。

## 6｜多租户安全与可观测性：成本账本也是敏感数据系统

成本系统至少应落实以下边界：

1.  1. `tenant_id` 从服务端鉴权上下文取得，不能相信客户端传入值。
    
2.  2\. 缓存、检索结果、工具输出与知识版本默认租户隔离；跨租户复用需要显式授权范围和审计记录。
    
3.  3\. Prompt、工具结果、Trace 与账本明细按最小必要原则保存，支持脱敏、访问控制、保留期限与删除策略。
    
4.  4\. 区域、数据驻留和供应商传输边界在路由前校验，不能在成本更低时绕过。
    
5.  5\. 运营报表默认使用聚合和最小权限访问；人工复核样本使用脱敏材料并留审计轨迹。
    

这些措施不是独立的合规附录。权限指纹、知识版本、区域和缓存范围本身就是正确归因、正确命中与正确成本比较的必要维度。

## 7｜CPS：固定分子、分母、时间窗口和估算状态

```
CPS = 队列内所有可归属净成本 / 队列内通过同版验收的任务数成功率 = 通过同版验收的任务数 / 队列内提交的合格任务数平均任务成本 = 队列内所有可归属净成本 / 队列内提交的合格任务数
```

“合格任务”是满足实验准入条件的有效提交。准入后被预算拒绝、超时、取消或到观察截止仍未完成的任务保留在成功率分母中；失败、重复尝试和提前取消已经发生的费用保留在 CPS 分子中。若成功数为零，CPS 记为 `NULL`，同时显示成本、样本数与失败原因。

按任务创建时间划 cohort，等待统一结果观察期和账单回补期，并标识 `provisional` 或 `final`。回补与退款进入原 cohort，但另记录其入账时间。成熟 cohort 才能作正式发布结论；未结算用量和暂估比例超过阈值时，只能出预览报表。

先将账本聚合为每任务一行，再与任务结果关联。以下查询以美元展示；生产系统应保存原币种与 FX 版本，并显式选择净额、暂估与调整事件口径。

```
WITH cohort AS (   SELECT tenant_id, task_id, policy_id, complexity, succeeded   FROM task_outcome   WHERE submitted_at >= :start_atAND submitted_at < :end_at    AND eligible = TRUE    AND rubric_version = :rubric_version), cost_by_task AS (   SELECT l.tenant_id, l.task_id, SUM(l.amount_usd) AS net_amount_usd   FROM cost_ledger l   JOIN cohort c USING (tenant_id, task_id)   WHERE l.cost_scope = 'direct_delivery'    AND l.posted_at <= :as_of    AND l.estimate_state IN ('ACTUAL', 'APPROVED_ESTIMATE')   GROUP BY l.tenant_id, l.task_id)SELECT c.policy_id, c.complexity,        COUNT(*) AS submitted,        COUNT(*) FILTER (WHERE c.succeeded) AS successes,        SUM(COALESCE(k.net_amount_usd, 0)) AS net_cost_usd,        COUNT(*) FILTER (WHERE c.succeeded)::numeric / COUNT(*) AS success_rate,        SUM(COALESCE(k.net_amount_usd, 0))            / NULLIF(COUNT(*) FILTER (WHERE c.succeeded), 0) AS cps_usd,        PERCENTILE_CONT(0.95) WITHIN GROUP            (ORDER BY COALESCE(k.net_amount_usd, 0)) AS p95_task_cost_usdFROM cohort cLEFT JOIN cost_by_task k USING (tenant_id, task_id)GROUP BY c.policy_id, c.complexity;
```

P95 表示每个提交任务的成本分布，而非仅成功任务。发布报表还应显示计费操作覆盖率、待结算金额、暂估比例、退款比例、预算拒绝率、失败原因及端到端 P95 延迟。跨租户汇总使用总成本除总成功数；不得平均各租户的 CPS。

### 统计门禁

不要用单个点估计宣布“更便宜”。对质量采用预注册的非劣门槛：例如候选策略相对基线的关键问题召回差值，其单侧置信下界不得低于 `-δ`；复杂层也要单独通过。对 CPS、成本和延迟报告分层配对 Bootstrap 区间。只有以下条件同时满足，才可发布：

1.  1\. 总体与关键复杂层质量满足非劣门槛；
    
2.  2\. 安全、授权、数据驻留和预算拒绝率满足交付合同；
    
3.  3\. P95 延迟不劣于预设容忍范围；
    
4.  4\. CPS 差值区间支持预期降幅，且暂估与未结算比例未超过阈值。
    

重采样单位应匹配相关性：若同一仓库、租户或共享缓存会话内样本相关，应以仓库、租户或会话为 cluster 重采样，并保持策略配对。线上使用任务稳定分流并固定策略版本，待 cohort 成熟后再比较；成本改善只能在相同任务组成、验收标准和风险边界下解释。

## 9｜上线顺序与验收清单

1.  1\. 建立任务结果、操作计量与不可变账本；用一段真实账期完成从调用 usage 到供应商账单的对账，量化未归属和暂估比例。
    
2.  2\. 落地身份、缓存和数据驻留边界；验证跨 Worker 恢复、Trace 缺失、权限变更和缓存失效不会造成跨租户归因或数据泄露。
    
3.  3\. 以影子预算记录“本应拒绝”的路径，校准预留上界；随后演练并发预留、重复结算、发送后响应丢失、流式取消、退款调整与跨账期回补。
    
4.  4\. 跑冻结 cohort 的同任务对照，先验证质量非劣，再按复杂度确定小模型可覆盖的流量。
    
5.  5\. 将路由、升级、缓存逐项灰度上线；每项变更在同一报表中留下质量、CPS、P95 延迟、预算拒绝率与安全事件的前后对比。
    

真正成熟的成本治理不是压低 Token 单价，而是让每一次成本、每一份交付和每一次风险取舍都可追溯、可复算、可验证。只有这样，模型路由与缓存优化才会带来真实且可持续的业务收益。
