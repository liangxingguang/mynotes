本篇导读

**星舰10X是一个面向研发工作的协作平台。** 研发人员可以通过对话提出要求，也可以通过异步任务或工作流，把项目分析、方案编写和结果检查等步骤串联起来。平台调用智能体（Agent）执行这些工作。

**Cloud Agent 是星舰内部负责云端执行的后台服务。** 它为 Agent 安排远程运行环境，启动并管理执行，收集结果，再交回星舰展示。星舰是用户使用的平台，Cloud Agent 是其中的执行服务，二者不是同一个概念。

例如，用户在星舰中提出：“读取这个项目，整理模块关系，生成一份报告。”Agent 收到要求之前，谁去取仓库？报告写在哪台机器上？用户关掉页面，工作是否还在继续？报告生成后，又如何回到页面供用户下载？

这些步骤由 Cloud Agent 管理；真正阅读项目、使用工具和撰写报告的，是运行在远程环境中的 Agent。

架构与职责边界  

这项工作的主要路径是：

**星舰接收要求 → Cloud Agent 安排执行 → 沙箱中的 Agent 阅读项目并写报告 → Cloud Agent 收集报告 → 星舰展示结果。**

沙箱（Sandbox）是分配给 Agent 的独立远程工作环境，包含所需工具和工作目录。

这条路径中有四个容易混淆的角色。

角色

在报告任务中负责什么

不负责什么

星舰

接收用户要求，组织工作流或会话，展示过程和结果

不直接承载 Agent 的构建、测试和文件操作

Cloud Agent

记录任务，安排环境，启动和管理执行，收集结果

不替代 Agent 理解项目，也不决定业务是否验收通过

沙箱

提供 Agent 使用的工具、仓库目录和计算资源

不理解用户希望报告包含哪些结论

Agent

阅读项目、调用工具、形成结论并写出文件

Agent 在沙箱中读取仓库和生成文件，Cloud Agent 则在沙箱之外安排和管理这项工作。

除运行中的部分外，系统还要长期保存两类内容：一类是**管理记录**，保存任务归属、当前阶段和负责处理它的管理节点；另一类是**文件与历史记录**，保存报告、执行记录和归档包。报告必须先离开临时工作目录进入长期存储，才能在沙箱回收后继续被下载。保存了任务记录，不等于报告文件或全部执行过程也已经保存。

### 为什么不直接让 Agent 跑在星舰服务里

Agent 可以执行读取文件、安装依赖、运行构建和测试等操作。在线业务服务主要处理请求，这两种负载对运行环境的要求不同。

把它们放在同一个业务容器中，任务使用的工具和文件就容易与在线服务混在一起。任务需要安装新工具，应用镜像未必具备；运行测试消耗资源，可能挤占服务；业务发布重启，也可能直接中断任务。

独立沙箱将实际工作移出业务服务。星舰负责接收要求和展示结果，Cloud Agent 负责管理，Agent 的文件操作和工具运行在沙箱里完成。

![image](<data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate\(-249.000000, -126.000000\)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E>)

这不是说本地运行或业务容器运行没有价值，而是运行方式要与任务范围匹配。

运行位置

适合怎样的工作

环境由谁照看

个人电脑

使用者负责本地工具、文件与持续在线

业务应用容器

工具固定、范围明确且负载受控的执行

沙箱底座提供运行空间，Cloud Agent 补上任务记录、会话、恢复和文件交付。星舰因此复用已有沙箱能力，而没有重新建设计算资源平台。

### 六个阶段

**第一步：把要求登记为一项任务。** 星舰提交的不只是“写报告”这句话，还包括本次的执行条件：使用哪个仓库及版本、放入哪些材料、使用哪种 Agent、需要哪些工具，以及允许运行多长时间。Cloud Agent 检查条件后建立任务记录，并返回可查询的任务信息。后续查看进度、取消工作或获取结果，针对的都是这项任务。

先保存记录再安排执行，是为了避免管理服务重启后，平台只剩一个还在运行的进程，却不知道它属于哪项工作。

**第二步：为任务找到运行环境。** Cloud Agent 向沙箱资源管理部分申请环境：条件合适时复用预先准备或允许复用的沙箱，否则创建新沙箱；容量不足时等待资源。“有一只空闲沙箱”不等于“这次可以直接使用”。环境复用的设计要求是核对使用身份、授权范围、用途和共享方式，不能因为环境仍然存在，就默认下一项工作可以继承前一项工作的访问权限。

**第三步：把仓库、材料和工具准备好。** 平台将指定仓库取到工作目录，放入附件，准备 Agent 需要的工具与能力。对于报告任务，Agent 需要能读取项目文件；如果还要运行测试，环境就要具备相应测试工具。环境准备与 Agent 工作分开记录，星舰因此能区分“仓库还没准备好”和“已经在分析项目”。Agent 能启动，不代表它有仓库、权限和工具。

**第四步：启动 Agent，持续接收工作过程。** Cloud Agent 启动选定的 Agent 并交出任务要求。执行过程中接收文本输出、工具活动和状态变化，再提供给星舰展示，用户因此不必等整项任务结束才得到消息。时间限制和取消请求也是任务管理的一部分，不能只关注 Agent 是否还在输出。

**第五步：把报告从沙箱收回来。** 报告写在沙箱工作目录里，Cloud Agent 识别本次生成和修改的文件，将需要交付的部分收集到长期存储并形成文件清单。不是所有工作文件都应交付——仓库原始文件、工具缓存和临时材料也在同一环境中。收集失败或文件超过允许范围时，需要说明哪些文件可用，哪些缺失或未收集。

**第六步：把结论和文件交给星舰。** 平台返回最终回答、执行结果和文件清单，用户可以阅读结论、下载已归档的报告。若任务属于工作流，可用归档文件可以交给后续节点，后续任务拿到的是明确材料，而不必从前一段回答里重新推测结果。

### 状态转换与交付结果｜设计要求

从阅读者的角度，正常流程可以概括为：

**环境准备 → 执行中 → 成果收集 → 结果收口**

阶段说明工作进行到了哪里，执行结果说明工作因何结束，交付结果说明用户实际拿到了什么。下表是流程说明，不对应某个接口的具体状态枚举。

阶段或结果

表示什么

需要同时说明什么

环境准备

正在申请和配置沙箱，准备仓库与材料

准备是否完成；失败、超时或取消时停在哪里

执行中

Agent 正在处理要求

是否正常结束，或因失败、超时、取消而停止

成果收集

正在识别和归档交付文件

已收回、缺失和未收集的文件；取消或超时是否已生效

正常结束

本次执行按正常路径结束

不等于文件全部交付，也不等于业务验收通过

失败

工作遇到错误，无法按原路径继续

错误所在阶段，以及仍可使用的结果和文件

超时

达到约定的时间限制，进入停止或收尾处理

哪部分工作未完成，已有成果保留到了哪里

已取消

取消请求已经实际生效

停止了哪些后续工作，哪些文件或操作已经形成

**执行结果与交付完整性分开表达。** “部分交付”不必新增为任务状态，而可以在交付结果中说明。例如，Agent 执行失败，但已经形成的报告初稿成功归档，结果应同时表达“执行失败”和“初稿可下载”；Agent 正常结束，但有附件没有收回来，也不能只给用户一个笼统的成功提示。

这里的“完成”还要分清层次：引擎执行正常结束、成果归档处理结束、交付文件完整和业务验收通过，不是同一个结论。

### 三个关键机制

**同一创建请求如何去重｜设计要求。** 网络重试会让同一个创建请求重复到达。一次创建及其重试需要使用同一个稳定的请求标识，新的工作使用新的标识；只因为两段要求文字相同，不能判断它们是同一次创建。

去重的作用范围是“这一次任务创建”：重复请求应对应同一项任务，并发到达也不能各自启动一份工作。例如，“生成报告”的创建响应丢失后，再提交的是原创建请求的重试，应返回原任务；用户随后要求“重写第二章”，则是一项新的工作。这个例子说明去重边界，不代表报告里的每次工具操作都不会重复。

**取消和超时如何阻止后续执行｜设计要求。** 收到取消请求与取消实际生效需要区分。停止后，自动拉起、续跑和重试都应先检查原任务是否还允许继续，不能一边向用户表示已取消，一边再次启动工作。超时也需要说明时间限制覆盖的范围，以及停止时工作停在哪一阶段。

成果收集期间也可能收到取消请求。需要说明当前收集能否停止、是否仍需完成必要收尾，以及已经归档的文件是否保留，不能把“受理取消”直接等同于“全部操作立即停止”。取消或超时都不意味着已经完成的外部操作自动撤销，也不意味着已有成果必须删除。

**执行结束但成果收集失败时如何标记｜设计要求。** Agent 正常退出不等于交付完整。收集失败、文件缺失或超限时，交付结果应列出缺失项及影响；已成功归档的部分仍可交付，不需要为了表达这一点另造一个任务状态。用户应能区分“Agent 没完成工作”和“工作已完成，但文件没有全部收回来”。

会话管理  

一次性任务的目标是把报告交出来。但实际使用常常不会在这里结束，用户可能接着说：

“第二章再展开一些。”“保留原来的图，增加一张流程图。”“按新的规范修改这份报告。”

这些要求都依赖已经生成的报告。持续会话（Session）就是为这类工作准备的。

### 会话、轮次与执行环境的关系

层级

是什么

生命周期

会话

一段持续的工作关系，关联环境与历史

跨越多轮，与单次处理分开管理

轮次

会话中的一条用户消息及其处理

单次，按顺序推进

执行环境

沙箱工作目录、工具与进程

可被保留或回收，与会话记录分离

会话记录的不只是聊天内容。在可用的原工作目录中继续修改报告，既需要前面讨论的上下文，也需要那份实际报告。只保存对话，不能替代保存文件。

### 排队与并发边界

同一会话的主要轮次按顺序推进，避免两条用户要求同时修改同一份文件。Agent 内部的并行子任务是另一回事，不等于两条用户消息可以不加顺序地操作同一文件。

### 环境保留与回收

空闲会话不必一直维持完整运行负载：可以让不必要的驻留进程退出，同时保留可用的历史和工作文件。但进程退出、环境保留和沙箱回收是三个不同动作：

•**进程退出**：文件可能仍在工作目录；重新启动后能否继续，还取决于历史和环境是否可用。

•**环境保留**：沙箱和文件仍在，只是没有活跃执行。

•**沙箱回收**：原工作目录不再可用，需要依靠已保存的历史、归档文件或快照重新准备环境。

这些状态必须分清。保留了会话记录，不等于完整保留了执行环境；保留了报告文件，也不等于已经恢复了此前所有讨论。

### 与一次性任务的区别

使用方式

给出的要求

后续怎样继续

一次性任务

“读取项目，生成报告”

交付后结束；新工作显式带入已有报告

持续会话

“先生成报告，再按反馈修改”

多轮要求围绕同一段工作持续推进

一次性任务完成后再创建新会话时，报告需要作为输入材料带入，不能假设新会话自动继承旧任务的工作目录。

中断恢复  

独立运行使用户连接、管理服务和实际执行不必一起结束，但它们仍然可能分别出问题。以下讨论不同中断情况下的设计要求，不将恢复路径的描述当作演练已经通过的证明。

### 四种中断情况｜设计要求

**用户关掉页面。** 这首先是展示连接断开，不应直接理解为任务被取消。后台执行与页面连接需要分开管理；用户回来后，应能查询原任务中已经保存的记录和结果，而不是因为页面重连就重复启动工作。

**管理服务重启。** 沙箱和 Agent 进程可能仍然存在。新的管理节点应先查询任务记录，再核对执行现场，判断是继续管理原进程，还是重新准备执行。不能在不知道原进程状态时立即再启动一份工作。

管理权接管需要回答三个问题：原管理者何时失去继续处理的资格，多个节点争取接管时由谁确认唯一归属，旧节点恢复连接后哪些操作不能再生效。这不仅是重新连接沙箱，还包括状态更新、成果归档和沙箱释放等处置边界。

例如，原节点中断后，另一个节点确认原归属已失效并接手任务；原节点随后恢复连接，也不应继续以旧归属更新结果或释放新节点仍在使用的沙箱。设计上，这些操作都需要依据当前管理归属作出判断，而不能只在接管开始时检查一次。这里说明的是管理责任与隔离要求，不展开具体实现。

**Agent 进程退出。** 沙箱中的报告初稿和工具环境可能还在。应根据已保留的材料、失败原因和剩余时间，判断是否能在原环境继续。权限不足、额度不足等前提问题，需要先修正条件，而不是反复重启。重新启动进程，也不等于自动恢复原上下文。

**沙箱已经终止。** 原工作目录不再可用，只能依靠已保存的历史、归档文件或快照重新准备环境。快照是某个时刻保存的可恢复材料，并不等于保存了整个环境。已归档报告可以作为继续工作的输入，但未保存的修改可能丢失。

### 区分“连不上”和“已经终止”｜设计要求

网络暂时不可达时，旧 Agent 可能仍在工作。直接新建一份环境，可能同时产生两份执行。因此，暂时不可达时需要核对管理记录与执行现场；确认原执行已无法继续后，再判断是否重建。连接失败本身不能证明原进程已经停止。

### 恢复的三种粒度｜设计要求

恢复不是一个“重新启动”动作，也不能统一称为恢复成功。

粒度

适用情况

结果说明要写清什么

接管仍在运行的进程

沙箱和 Agent 仍存活，仅管理侧失联或重启

原执行是否继续，哪些过程记录已经保存

恢复文件后继续会话

进程已退出，沙箱或归档文件仍可用

恢复了哪些文件和上下文，哪些修改无法恢复

重新执行任务

原执行环境无法继续，且没有足够材料直接恢复

重新做了哪些工作，与此前结果如何区分

无论哪种，都要说明报告和修改保留到了哪里，不能只给一个笼统的成功提示。本文仅介绍架构设计，不包含真实中断案例或故障演练结果，不据此给出无损恢复或可靠性结论。

内容

用途

存放与保留

运行环境

给 Agent 当下使用：仓库、工具、临时文件、进程

占用计算资源，不能无限期保留

过程记录

实时展示和事后查看

实时输出先进入内存缓冲，再保存为可回看的消息和事件；短暂展示不等于已经持久化

交付文件

工作成果，脱离沙箱后仍可获取

成功归档后进入长期存储，下载入口指向归档文件

这也解释了为什么任务需要单独的收集阶段：Agent 停止运行、报告写在工作目录、报告已经可下载，是不同的完成点。

**过程记录恢复｜设计要求。** 管理服务重启后，应以已经保存的读取进度和过程记录确定从哪里继续，识别重复片段，并说明未保存部分的边界。尚未持久化的输出不能因为执行仍在继续，就被视为已经完整恢复。因此，第四部分所说的“执行继续了”和“过程记录完整恢复了”是两项不同判断。

### 收集规则｜设计要求

•**收集范围**：识别本次生成和修改的文件，并结合任务声明的交付物确定清单。约定用于交付的目录优先，其余目录不自动视为成果。

•**排除项**：凭据、工具缓存、依赖安装目录和临时文件不进入交付清单；执行记录也不应暴露凭据。

•**缺失与超限**：文件缺失、超出允许大小或数量时，交付结果说明哪些文件可用、哪些缺失或未收集，不能只显示成功。

•**可恢复边界**：已归档文件可以作为新环境中的恢复材料；只存在于已回收工作目录、没有其他保存副本的修改无法据此恢复；快照只提供其保存时点的材料。

排查“报告没出来”时，可以分别检查：仓库是否就绪、Agent 是否中断、文件收集是否失败。不同位置需要不同处理，不能统一归结为模型回答不好。

### 更换 Agent 时，哪些部分需要变化

Agent 引擎指实际执行任务的智能体软件。不同引擎都能生成报告，但接收输入、返回执行过程和继续会话的方式不完全相同。

Cloud Agent 用适配层把不同引擎接到相同的任务入口上：对星舰来说，仍然是提交任务、查询进度和获取文件；对具体引擎来说，平台按其实际支持的方式启动、传入要求、读取结果。

适配层需要区分五类交互：

交互

统一表达什么

引擎差异如何处理

启动

一次带要求与工具的启动调用

参数形式不同，在适配层转换

过程输出

增量文本与工具事件

引擎只给部分信息时，不补造缺失记录

正常结束

引擎执行正常结束及其结果摘要

不等同于成果归档完成或业务验收通过

异常结束

失败信息与原因

无法归类的原因保留原始信息，不吞掉

会话恢复

是否支持继续同一上下文

不支持或材料不足时明确说明，不能静默当成恢复成功

边界在于：适配层解决“不同 Agent 怎么接入”，不是“让所有 Agent 表现完全一样”。能使用同一个入口，不代表能力完全一致。引擎结束以后，仍要分别看执行结果、文件交付和业务验收，不能用一个“成功”代替三项判断。

结语  

回到开头的报告任务：星舰接收要求，Cloud Agent 将工作安排到沙箱，Agent 在其中读取项目并写报告，Cloud Agent 将文件归档，星舰再展示结论和下载入口。后续修改进入会话，分阶段协作进入工作流。Cloud Agent 的位置就在这几次交接之间：它让业务入口不必直接照看远程进程，也让 Agent 不必承担整个平台的资源和结果管理。
